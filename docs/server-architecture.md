# 서버 내부 구조 — 반복되는 결정만 못 박는다

> 대상: `omf-mes-server` 구현. 시스템 아키텍처(스택·배포·인증 3층·도메인 경계)는
> 설계팀 `02-SW설계사양서.md` 가 확정했고 **이 문서는 그것을 바꾸지 않는다.**
> 여기서 정하는 것은 **그 위에서 서버 코드가 같은 일을 100번 반복할 때의 형태**다.
>
> 기준: 계약 `77a067b`(482 오퍼레이션) · 물리 모델 182표 · 실측 2026-09-02

## 왜 지금인가

Phase 0(오류 봉투·계약 검증·권한·인증)까지는 **사용처가 생긴 뒤에** 만들었다.
도메인 482건은 다르다 — 재고를 건드리는 오퍼레이션이 ~100건, `status_code` 를 가진 표가
**61개**, `version_no` 를 가진 표가 **95개**다. 한 번 정하지 않으면 **도메인마다 다른
구현이 선다.**

⛔ 그렇다고 미리 레이어를 쌓지 않는다(CLAUDE.md). **여기 적은 여섯 가지만** 정하고,
나머지는 계속 사용처를 보고 만든다.

## 1. 레이어 — 세 겹, 그 이상 두지 않는다

```
controller   계약 경계.  @Contract 바인딩 · 요청/응답 형태만 안다.  업무 규칙 없음.
service      업무.       트랜잭션 경계를 «여기서» 연다.  코어를 부른다.
core         반복.       재고 posting · 상태기계 · business_date · 채번 · lot 계보.
```

- **repository 층을 두지 않는다.** Prisma 가 이미 그 자리다. 한 겹 더 두면 482건 × 얇은 위임이 된다.
- **도메인 엔티티 클래스를 두지 않는다.** 계약이 형태를 정하고 DB 가 상태를 갖는다 —
  가운데 모델을 두면 세 곳을 맞춰야 한다.
- `core` 는 **여러 도메인이 같이 쓰는 것만** 들어간다. 한 도메인만 쓰면 그 도메인 service 에 둔다.

### 모듈 배치 — 스키마가 아니라 **계약 경로**를 따른다

계약의 최상위 경로가 곧 모듈이다(`/mdm` 115 · `/logistics` 82 · `/app` 69 · `/quality` 62 ·
`/production` 40 · `/maintenance` 35 · `/planning` 28 · `/inventory` 24 · `/integration` 13 ·
`/trace` 13 · `/audit` 1).

```
src/
  common/      errors · contract · permissions            (이미 있음)
  auth/                                                    (이미 있음)
  core/        inventory-posting · document-state · business-date · numbering · lot-genealogy
  mdm/ logistics/ quality/ production/ ...                 도메인 11
```

⛔ **도메인이 다른 도메인의 service 를 부르지 않는다.** 공유가 필요하면 그것은 `core` 다.
지금 아는 공유는 하나 — 재고 posting 을 물류·생산·품질·재고 넷이 쓴다.

## 2. 코어 — 반복 100회 이상인 여섯

### C-1. 재고 posting — **원장에 쓰고, 잔량은 그 결과로 움직인다**

```
posting(입력) →  ① inventory_transaction(헤더) + inventory_transaction_line(라인) append
                 ② 그 라인이 가리키는 (창고·위치·LOT·품질상태) 잔량 행을 갱신
                 ③ 라인에 from_qty_after_transaction / to_qty_after_transaction 기록
```

- **재고를 바꾸는 길은 이 함수 하나뿐이다.** 도메인 service 가 `inventory_balance` 를
  직접 UPDATE 하지 않는다 — 결정 08 의 「잔량 직접 덮어쓰기 금지」가 그 뜻이다.
- `available_qty` 는 **DB 가 계산한다**(`on_hand − reserved − picked − blocked` DEFAULT).
  서버도 화면도 다시 빼지 않는다(계약 `availableQty`).
- `reserved_qty`·`picked_qty` 는 **posting 이 움직인다.** 「서버 전기가 올리고 소진되면
  내린다 — 화면은 계산하지 않는다」(계약 `reservedQty`).
- ⛔ **차단 판정은 `blocked_qty` 를 보지 않는다.** Lot Status 단일 지점을 본다(결정 10).

### C-2. 전표 상태기계 — **전이표 한 벌, 문서마다 값만 다르다**

`status_code` 를 가진 표가 **61개**다. 각자 `if` 를 쓰면 61가지 규칙이 흩어진다.

```
transition(문서유형, 현재상태, 사건) → 다음상태 | 거부(이유)
```

- 전이표는 **데이터**로 둔다. 코드에 상태 문자열을 박지 않는다 —
  ⛔ **`'PREISSUED'` 교훈**: 값이 CHECK 한 곳에만 있고 아무 데서도 안 쓰였다.
- 값 목록은 `#213`(리소스별 상태값) 소관이라 **아직 안 왔다.** 그때까지 전이표는
  `prisma/seed.ts` 의 코드 그룹에서 읽고, 없으면 **막는다**(F-6 「판정할 수 없음을
  통과로 처리하지 않는다」).
- 취소는 상태 전이 + **취소 흔적 3컬럼**(`cancelled_at`·`cancelled_by`·
  `cancellation_reason_code`)이다. 지금 **2/14 표에만** 있다(`§I-38` — 우리 결손).

### C-3. `business_date` — **함수 하나, 41자리가 쓴다**

```
timestamptz → plant.timezone_code 로컬 시각 → shift 판정 → 그 shift 시작 로컬 날짜
```

- ⛔ **타임존 캐스팅 금지**(CLAUDE.md). `shift.crosses_midnight` 때문에 단순 캐스팅이 틀린다.
- `@db.Date` **49자리**가 이 값을 받는다(2026-09-02 실측).
  ⚠ `CLAUDE.md` 는 41 이라 적고 있다 — 표를 더하며 늘었다. 별건으로 고친다. 원장 라인(`inventory_transaction_line.business_date`)도 그중 하나다.
- 서버·컨테이너·DB TZ = UTC 고정. 공장 로컬은 `plant.timezone_code` 로만 푼다.

### C-4. lot 계보·상태 3축 — **섞지 않는다**

| 축 | 자리 | 이력 |
| --- | --- | --- |
| ① 수명주기 | `trace.lot.lifecycle_status_code`(대기/활성/폐번) | `trace.lot_lifecycle_history` |
| ② 품질 판정 | `trace.lot.status_code` + 재고 행의 `quality_status_code` | `trace.lot_status_event` |
| ③ 작업 홀드 | `trace.lot_hold` | 같은 표 |

- 전이는 셋이다 — `L1` 대기→활성(첫 실적) · `L2` 대기→폐번(마감, 실적 없는 슬롯) ·
  `L3` **활성→폐번**(작업지시 취소).
  ⚠ `SW설계사양서 §4.4` 는 「대기→활성·대기→폐번**뿐**(활성→폐번 **없음**)」이라 적었는데
  이는 `PLOT`(2026-07-29)을 인용한 것이고, **`DR-007`(2026-08-12)이 그것을 넘어섰다** —
  「`:cancel` 이 선발행 슬롯을 **전건** 즉시 폐번한다. **R82 의 「실적 없는 슬롯만」과는
  대상 집합이 다르다**」(`W-02-06` §5-5). **§4.4 가 낡았다 — 회신 대상**(§5).
- ⛔ `L3` 를 여는 것은 **작업지시 취소 오퍼레이션 한 곳뿐이다.** 사람이 화면에서 직접
  폐번하는 경로는 없다.
- 계보는 `trace.lot_relation`(자재LOT↔생산LOT **N:M** · 관계 ③).
- 축을 섞어 읽는 코드가 들어오면 그 자리에서 막는다 — PR #70 이 겸용 시절의
  죽은 CHECK 분기를 걷어낸 것과 같은 이유다.

### C-5. 트랜잭션 경계 — **한 오퍼레이션 = 한 트랜잭션**

- 계약의 오퍼레이션 하나가 트랜잭션 하나다. 서비스가 열고 컨트롤러는 모른다.
- 한 트랜잭션 안에 드는 것: 전표 쓰기 + posting + 상태 전이 + `audit_event` + 멱등 기록.
  예 — 재고 재등록은 **보류 해제 + LOT 상태 전이 + 이동 문서**가 한 트랜잭션이다.
- `Idempotency-Key`(쓰기 250건)는 **트랜잭션 안에서** 기록한다. 밖에 두면 커밋과 어긋난다.
  자리는 `app.idempotency_record` 로 이미 있다.
- `If-Match`(155건)는 **읽은 `version_no` 로 UPDATE 조건을 건다.** 0행이면 409.

### C-6. 채번 — **설계가 이름까지 붙여 뒀다(CORE-1)**

- 3계층 중 **가운데(작업지시)는 항상 MES 가 만든다.** 상위지시(ERP)는 nullable FK.
- 생산LOT 은 `UNIQUE(plant_id, lot_no)` · 설정형 채번규칙 · **W/O 발행 시 일괄 발번**.
- 오프라인 대비 **선배포**가 전제다(P3 선발행) — 단말이 끊겨도 번호를 쥐고 있어야 한다.

## 4. 구현 순서

```
코어      C-3 business_date → C-1 재고 posting → C-2 전표 상태기계
          (각 전용 PR · diff ≤ 200줄 — CLAUDE.md 코어 규칙)
남은 기반  Idempotency-Key → If-Match/ETag → 권한 게이트 → 페이징

          → quality → planning → maintenance → integration
```

`mdm` 을 먼저 두는 이유는 다른 전 도메인의 FK 원천이고 CRUD 라 기반을 실전 검증하기에

**완료 정의**: `contract-coverage.spec.ts` 의 단언을 `registry.size` 로 뒤집는 것.
