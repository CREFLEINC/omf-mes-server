## 답이 필요한 것

### 1. 공통코드 쓰기 6개를 만들지 않았다

| | |
|---|---|
| 대상 | `POST`·`PUT`·`:deactivate` × (`/mdm/code-groups`, `/mdm/code-values`) |
| 계약 | 여섯 개 모두 정의되어 있다 |
| 구현 | **만들지 않았다.** 조회 4개만 있다 |

**왜.** 그룹 코드가 서버 소스에 문자열로 박혀 있다.

```
warehouse.validator.ts   warehouseTypeCode: 'WAREHOUSE_TYPE'
location.validator.ts    locationTypeCode:  'LOCATION_TYPE'
item.validator.ts        fifoPolicyCode:    'FIFO_POLICY'
```

화면에서 `WAREHOUSE_TYPE` 을 바꾸면 **그 순간부터 창고를 하나도 등록할 수 없다.** 서버를
다시 배포하기 전까지 그렇다. 코드값을 바꾸면 그 값을 쓰던 기존 행이 목록에 없는 값이 된다.

지금 41개 그룹·174개 값이 **전부 마이그레이션과 시드로** 들어와 있다. 화면으로 만든 것은
하나도 없다.

계약도 같은 방향을 적어두었다 — 코드값은 「ERP 수신본이라 읽기 전용이어야 하는데 판정할
컬럼이 없다(#65)」, 코드그룹은 「잠정적으로 MES 등록을 허용한다」.

**필요한 답.** 「조회만으로 확정」인가, 「그래도 만들어야 한다」인가. 후자라면 소스에서
그룹 코드 문자열을 걷어내는 선행 작업이 필요하다.

---

### 2. `:activate` 를 `mdm` 에도 넣어달라

| | |
|---|---|
| 대상 | 창고 · 로케이션 · 부서 |
| 계약 | `:deactivate` 만 있다. `PUT` 도 `isActive` 를 받지 않는다 |
| 구현 | **`:activate` 를 서버가 먼저 만들었다** |

**왜.** 중지를 되돌릴 경로가 없다. 잘못 누르면 API 로 복구가 안 된다.

**2026-08-10 갱신분에서 계약도 같은 판단에 도달했다.**

```
/logistics/putaway-rules/{id}:deactivate
/logistics/putaway-rules/{id}:activate     ← 새로 들어갔다
```

적치 규칙에는 짝이 들어갔는데 `mdm` 에는 아직 없다.

**필요한 답.** 창고·로케이션·부서(그리고 쓰기를 만든다면 코드그룹·코드값)에도 같은 짝을
넣어달라. 서버 구현은 이미 있다 — 계약에 반영만 하면 화면이 알 수 있다.

---

### 3. `conflictCause` 3값을 판정할 근거가 없다

| | |
|---|---|
| 계약 | 저장 충돌 시 `user` · `erpSync` · `workerLease` 중 하나를 내려야 한다 |
| 구현 | **항상 `user`** |

**왜.** 스키마에 판정 재료가 없다. 「이 행을 무엇이 바꿨나」를 남기는 칸도, 「워커가 잡고
있다」를 표시하는 칸도 없다. 없는 근거로 지어낼 수 없다.

계약이 스스로 이 문제를 적어두었다.

> 구분 없이 내려주면 화면이 **「다른 사용자가 먼저 수정했습니다」라는 사실과 다른 안내**를
> 하게 된다

**필요한 답.** 셋을 구분할 재료(예: `updated_by_system` 컬럼, 리스 테이블)를 물리 모델에
추가할지, 아니면 계약에서 `user` 하나로 줄일지.

---

### 4. 「공통코드」라는데 그 코드 목록이 없다 — 두 곳

| 필드 | 계약이 적은 것 | 실제 |
|---|---|---|
| `ItemExternalCode.externalSystemCode` | 「공통코드」 | 해당 코드그룹이 `mdm.code_group` 에 **없다** |
| `WorkerQualification.qualificationTypeCode` | 「공통코드 — **값 목록 미정** §8-5」 | 없다 |

`%EXTERNAL%`·`%SYSTEM%` 으로 찾아도 0건이다.

**구현.** 지금은 글자 길이만 본다. 아무 값이나 들어간다.

**필요한 답.** 그룹 코드와 값 목록. 정해지면 창고의 `WAREHOUSE_TYPE` 과 같은 방식으로
`code_value` 대조를 붙인다 — 서버 작업은 각 2줄이다.

---

### 5. `certifiedBy` 가 무엇을 가리키는지 모른다

| | |
|---|---|
| 위치 | `WorkerQualification.certifiedBy` |
| 스키마 | FK 없는 `bigint` |
| 계약 | 「FK 없음 — 무엇을 가리키는지 근거 없음 §8-2」(#64) |

사용자 번호인지, 인증 기관인지, 검사자 번호인지 알 수 없다.

**구현.** 형태만 본다. 참조 검사는 하지 않는다.

**필요한 답.** 어느 테이블을 가리키는지. 정해지면 FK 와 참조 검사를 붙인다.

## 알려만 두는 것

계약에 없어 서버가 정했다. 문제가 있으면 알려달라 — 없으면 이대로 간다.

### 6. 목록 정렬 기준

계약에 정렬이 없다. 불안정하면 **페이지를 넘길 때 같은 행이 두 번 나오거나 빠진다.**
마스터마다 유일키로 못 박았다.

| 마스터 | 정렬 |
|---|---|
| 창고 | `(plant_id, warehouse_code)` |
| 로케이션 | `(warehouse_id, location_code)` |
| 사업부 · 공장 | `(legal_entity_id, 코드)` |
| 생산라인 · 설비 | `(plant_id, 코드)` |
| 부서 · 품목 · 작업자 · 코드그룹 · 단위 · 거래처 · 법인 · 공정 | 전역 유일키 한 칸 |
| 코드값 | `(display_order, code)` |

`display_order` 에는 유일 제약이 없어 **`code` 로 동점을 깬다** — 안 그러면 순서가 같은
값들이 페이지를 넘길 때 흔들린다.

부속 컬렉션(품목 3종·작업자 자격)은 페이지가 없어 흔들릴 여지가 없지만, 화면이 매번 같은
차례로 보도록 각 테이블의 유일키를 따라 정렬한다.

### 7. 목록 `size` 상한 200

계약에 상한이 없다. 없으면 `size=1000000` 한 번으로 전 테이블을 긁어간다.

### 8. 상세 조회의 404

계약에는 200 만 있다. 없는 id 에 200 을 줄 수 없어 서버가 정의했다.

### 9. 편집 권한 매트릭스 (계약 §8-8 미결)

서버가 지어내지 않고 **시드·역할 데이터가 이미 전제하는 체계**를 그대로 썼다.

```
조회        MASTER_READ
쓰기·중지    MASTER_{LOGISTICS|SYSTEM|ORGANIZATION|PRODUCTION|EQUIPMENT|QUALITY}_{WRITE|DEACTIVATE}
```

`mdm` 에서 **실제로 쓰는 것은 넷**이다.

| 권한 | 붙은 곳 |
|---|---|
| `MASTER_READ` | 조회 전부 |
| `MASTER_LOGISTICS_{WRITE,DEACTIVATE}` | 창고 · 로케이션 |
| `MASTER_ORGANIZATION_{WRITE,DEACTIVATE}` | 부서 · 작업자 자격 |
| `MASTER_PRODUCTION_WRITE` | 품목 · 품목 부속 |

`SYSTEM` 은 코드그룹·코드값 몫이나 **쓰기를 만들지 않아 쓰이지 않는다**(위 1번).
`EQUIPMENT`·`QUALITY` 는 `mdm` 밖이다.

**한 가지 더.** 계약의 `RolePermission.permissionCode` 예시가 `MASTER_EDIT` 로 적혀 있다.
시드가 쓰는 이름 체계와 다르다. `mdm` 에서는 문제가 없지만, `/app` 라운드에서 권한 코드가
API 로 오가기 시작하면 **이름이 서로 맞아야 한다** — 그때 한 번 맞춰야 할 항목이다.

### 10. 중지 응답에 `ETag` 를 붙였다

계약은 `PUT` 에만 `ETag` 를 선언했다. 재개(`:activate`)의 `If-Match` 에 필요하고, 멱등
재전송도 같은 헤더를 되돌려주어야 한다.

### 11. 자식 컬렉션에 동시 수정 보호가 없다 — 계약대로 갔다

| | |
|---|---|
| 대상 | 품목 부속 3종, 작업자 자격 |
| 스키마 | `version_no` 컬럼이 없다 |
| 계약 | 자식 `PUT` 에 `If-Match` 를 두지 않았다 |

**두 사람이 같은 품목의 부속을 동시에 고치면 나중 사람이 앞사람 것을 조용히 덮어쓴다.**
경고가 없다.

계약대로 구현했다(2026-08-10 결정). 부속 정보라 충돌이 드물다는 판단으로 보이는데, 의도한
것이 맞는지만 확인해달라.

### 12. 계약 문구 정정 — 코드그룹은 「셀 수 있다」가 아니다

계약이 이렇게 적었다.

> `groupCode` 는 `code_value` 가 FK 로 참조하므로 **참조 건수를 셀 수 있다**

**셀 수는 있으나 다른 것을 센다.**

| | 셀 수 있는 값 | 편집 잠금이 물어야 할 값 |
|---|---|---|
| 코드그룹 | 그룹에 값이 몇 개인가 | 그룹 **코드 글자**를 쓰는 곳이 어딘가 |

FK 가 `code_group_id`(숫자)로 걸려 있어, 코드 글자를 쓰는 곳은 서버 소스 문자열이고 셀 수
없다. **`editability` 를 코드값과 같이 `NOT_COUNTABLE` 로 내린다.**

### 13. `RECEIVED_FROM_ERP` 판정(#65)은 세 곳에서 답이 달랐다

같은 미결이 공통코드·품목·작업자에 붙어 있었는데 답이 갈렸다. 갈리는 지점이 「수신본인가」가
아니라 **「막을 수단이 있는가」**였다.

| | `#65` 에 대한 답 |
|---|---|
| 공통코드 | 막을 수단이 없다 → 쓰기 6개를 뺐다 (위 1번) |
| 품목 | `ItemUpdate` 가 원본 4열을 받지 않는다 → 구조로 막힌다 |
| 작업자 | 쓰기 경로 자체가 없다 → 문제가 되지 않는다 |

**품목·작업자는 `#65` 가 해결되지 않아도 막힌다.** 계약이 이미 그렇게 설계되어 있다.
`#65` 해소가 필요한 곳은 공통코드뿐이다.

# 추가 — 2026-09-03 라운드 (계약 사본 `77a067b`)

새 계약으로 조직(부서·PR #114)·작업자(PR #115)를 만들며 나온 것.
위 1~13번과 번호를 잇지 않는다 — 대상 계약 사본이 다르다.

## A. `PUT /mdm/departments/{departmentId}` — 계약 스스로 「폐쇄 대기」라 적었다

계약의 설명이 이렇다.

> ⛔ 조직(부서)은 기간계 수신본이라 읽기 전용이 확정이다(W-06-06 §5-4). 이 경로는 편집
> 본문에 원본 필드 넷을 그대로 담고 있어 **그 확정과 어긋난다** — 잠정 노출이며 화면은
> 부르지 않는다. **폐쇄 여부는 결정 대기다.**

**구현.** 계약에 있으므로 만들었다. 다만 확정을 서버가 지킨다 —
`source_system_code = 'ERP'` 인 행은 이 경로로도, `:deactivate` 로도 바뀌지 않는다(409
`STATE_LOCKED`).

**필요한 답.** 폐쇄인가 유지인가. 폐쇄면 경로 넷(`PUT`·`:activate`·`:deactivate`·`POST`)
중 어디까지인지. 서버 작업은 라우트 제거뿐이다.

## B. `Department.sourceSystemCode` — 계약만 있고 물리 컬럼이 없었다

계약이 `x-source-column: source_system_code` 로 선언했는데 `mdm.department` 에 그 컬럼이
없었다(실측 2026-09-03). **표시용이 아니라 편집 잠금의 근거**다 — `Editability.reason` 의
`RECEIVED_FROM_ERP` 를 서버가 내릴 재료가 이것뿐이라, 없으면 ERP 수신본을 화면이 고칠 수
있게 된다.

**구현.** 컬럼을 세웠다(`20260903000000`). 기본값 `'MES'`, `CHECK (IN ('ERP','MES'))`.
기존 행과 등록 경로는 자체 등록분이므로 `MES` 다. **ERP 연계가 서면 그쪽이 `'ERP'` 를
넣어야 한다** — 넣지 않으면 수신본이 편집 가능한 채로 남는다.

## C. `GET /mdm/workers/{workerId}` 에 `ETag` 를 붙였다

계약은 `ETag` 를 `GET .../qualifications` 에만 선언했다. 그런데
`PUT .../{workerId}:update-name-translation` 은 `If-Match` 를 **필수**로 요구한다 —
화면이 그 값을 얻을 자리가 계약 안에 없다.

**구현.** 작업자 상세 응답에 `ETag` 를 붙였다(작업자의 `version_no`). 헤더가 하나 더 오는
것은 계약 위반이 아니고, 없으면 그 쓰기를 부를 수 없다. 이전 라운드 10번과 같은 성질이다.

## D. 자격 목록의 `ETag` 축은 «작업자»의 `version_no` 다

`worker_qualification` 에 `version_no` 가 없다(계약이 그 사실을 적었다). 통째로 교체되는
자식 컬렉션이므로 부모 한 축으로 잠갔다 — 자격을 바꾸는 사이 다국어 명칭이 바뀌는 교차
갱신도 같이 걸린다.

**이전 라운드 11번이 여기서 풀렸다.** 그때는 자식 `PUT` 에 `If-Match` 가 아예 없었다.

## E. 부서 계층의 순환은 서버가 막는다

계약이 적어 두었다 — 「`ck_department_parent` 는 자기 자신만 막고 순환은 막지 않으므로
서버가 검사한다」. 그대로 구현했다(상위로 타고 올라가며 자기 자신을 만나면 400 `INVALID`).

## F. 편집 잠금 판정 — 세 자원이 서로 다르다

| 자원 | 판정 | 근거 |
|---|---|---|
| 코드 그룹·코드 값 | `NOT_COUNTABLE` (항상 잠금) | 코드 «글자»를 계약이 151곳에서 리터럴로 부른다 |
| 작업자 | `RECEIVED_FROM_ERP` (항상 잠금) | 계약이 「항상 고정한다」로 못박았다 |
| 부서 | `EDITABLE` / `REFERENCED` / `RECEIVED_FROM_ERP` | FK 일곱 자리로 셀 수 있다. `departmentCode=` 리터럴은 계약에 **0곳** |

부서만 세는 이유가 마지막 칸이다 — 코드 글자를 부르는 자리가 없어 FK 건수가 곧
「이 코드를 고치면 곤란해지는 곳」의 수다.

## G. 「설비 그룹」의 저장처가 `mdm.production_line` 이다 — 알려만 둔다

계약 `EquipmentGroup` 의 다섯 칸이 `x-source-column` 으로 전부 생산라인 표를 가리킨다.

| 계약 | 저장 컬럼 |
|---|---|
| `equipmentGroupId` | `production_line_id` |
| `groupCode` | `line_code` (「`uq_production_line(plant_id, line_code)`」까지 적혀 있다) |
| `groupName` | `line_name` |
| `groupTypeCode` | `line_type_code` |
| `parentGroupId` | `parent_line_id` |

다섯이 일관되고 유일 제약까지 짚었으므로 옮겨 적은 실수로 보지 않았다. **그대로
구현했다** — 「설비 그룹」과 「생산라인·작업구역」은 같은 나무의 같은 노드이고, `W-05-12`
가 사실상 그 마스터의 관리 화면이다. 계약이 `/mdm/production-lines` 에 「관리 화면이
인벤토리 108건에 없다 … 귀속 화면이 미정」이라 적은 것과 맞물린다.

**따라오는 결과 둘.**

1. `mdm.equipment_group`·`mdm.equipment_group_member` 는 계약 어느 스키마도 가리키지
   않는 표가 됐다. 지금 지우지 않는다(하위 호환) — 두 릴리스 뒤 제거 후보다.
2. `mdm.equipment_group_inspection_item.equipment_group_id` 는 `equipment_group` 을
   가리키는데, API 의 `equipmentGroupId` 는 `production_line_id` 다. **그룹 점검항목
   부여를 구현하려면 이 FK 를 옮겨야 한다** — 다음 PR 에서 다룬다.

`groupTypeCode` 는 계약이 「값 목록이 확정되지 않았다」로 적었으나 시드에
`LINE_TYPE`(LINE·WORK_AREA)이 있어 그 그룹으로 대조한다. 다르면 알려달라.

## H. `equipment_inspection_item.data_type_code` 를 계약이 안 받는다

물리 컬럼이 `NOT NULL` 이라 판정 방식에서 도출한다 — `MEASUREMENT`=`NUMERIC`,
`VISUAL`=`BOOLEAN`. 계약이 이 칸을 쓰지 않으므로 두 릴리스 뒤 제거 후보이기도 하다.

## I. 「가장 가까운 것이 이긴다」(B-17)를 상위 그룹까지 올라가는 것으로 읽었다

계약이 설비 점검항목 해석을 이렇게 적었다.

> 설비에 부여가 있으면 그것, 없으면 소속 그룹의 것, 둘 다 없으면 점검 대상이 아니다.
> 설계 규칙: **가장 가까운 것이 이긴다** — 공유계약 B-17

**구현.** 설비 → 소속 그룹 → 그 상위 그룹 → … 순으로 «처음 만나는» 부여를 쓴다.
`resolvedFromGroupId` 에는 실제로 이긴 그 그룹을 담는다.

**왜.** 그룹은 나무다(`parent_line_id`). 「소속 그룹 하나」로만 읽으면 상위 그룹에 붙인
부여가 어디에도 닿지 않아 계층이 뜻을 잃는다. `resolvedFromLevelCode` 의 값이
`EQUIPMENT`·`EQUIPMENT_GROUP`·`NONE` 셋뿐이고 층 번호를 따로 두지 않은 것도, 어느 층에서
왔든 「그룹에서 왔다」로 묶는다는 뜻으로 읽었다.

**알려만 둔다.** 소속 그룹만 보는 것이 맞으면 한 줄(반복문)을 빼면 된다.

## J. 부여가 「사용 중지된 점검항목」을 새로 받지 않는다

FK 는 존재만 보고 사용 중지는 안 본다. 중지한 항목을 새로 부여하면 중지의 뜻이 없어지므로
서버가 막는다(400). 이미 부여된 것은 건드리지 않는다 — 코드값 대조(#116)와 같은 형태다.

## K. `Terminal.locationId` 가 「비어 있을 수 있다」인데 타입이 nullable 이 아니다

```
"locationId": { "type": "integer", "format": "int64", "description": "설치 위치. 비어 있을 수 있다" }
```

`type` 이 `"integer"` 뿐이라 `null` 을 실으면 응답이 계약을 어긴다(계약 검증으로 확인).

**구현.** 비면 칸 자체를 뺀다. `required` 에 없으므로 계약을 만족한다.
`["integer","null"]` 로 바꾸는 것이 뜻에 맞아 보인다 — 같은 스키마의 `equipmentId` 는
그렇게 되어 있다.

## L. 단말 등록 토큰과 세션 쿠키가 «같은 비밀키»로 서명된다

계약이 토큰 모양을 공개하지 않으므로 서버가 정했다. 그런데 `sub` 를 단말 번호로 두면
그 토큰을 세션 쿠키로 들이밀었을 때 **같은 번호의 사용자 세션으로 풀린다** — 서명은
유효하기 때문이다.

**구현.** 모든 토큰에 종류(`typ`)를 담고 검증하는 쪽이 확인한다.
`session`·`terminal` 두 값이다. 세션 해석기는 `typ !== 'session'` 이면 거절한다.

## M. `mdm.equipment_group_inspection_item.display_order` 를 계약이 안 쓴다

부여별 순서를 계약이 받지 않고, 응답의 `sequenceNo` 는 점검항목 마스터의 것이다.
`is_required_override` 도 같다 — 계약 입력에 `requiredFlag` 가 없다. 둘 다 두 릴리스 뒤
제거 후보다.

## N. 설비 «유형» 코드 그룹이 계열마다 다르다

계약이 「공통코드 — 계열마다 그룹이 다르다. 계측기 계열은 `INSTRUMENT_TYPE`」로 적었다.
지금은 설비 계열의 `EQUIPMENT_TYPE` 으로만 대조한다 — 계측기 등록 경로가 서면 그때 가른다.

# 남은 mdm 9건 — 답이 필요해 멈춘 것 (2026-09-03)

mdm 115건 중 **106건을 구현**했다. 남은 아홉은 «우리가 정할 수 없는 것»에 걸려 있다.
물리 모델을 고치는 것은 우리 일이지만, 아래는 **업무 어휘와 업무 관계**라 지어내면
그것이 사실상의 설계가 된다.

## O. 금형(툴) 7건 — 결손 넷

`Mold` 열아홉 칸 중 아홉이 물리에 없고, 그중 넷은 컬럼을 더하는 것만으로 안 풀린다.

### O-1. `labelIssueCount` 의 출처가 없다

계약이 상세 응답에 요구한다 — 「이 툴로 발행된 라벨 회차 수. **1 이상이면 코드가 현장에
물리적으로 나가 있어 참조 건수가 0이어도 잠근다**」. `Editability.reason` 의
`LABEL_ISSUED` 가 이것을 위한 값이다.

그런데 **툴 라벨 발행 이력을 담는 표가 없다.** `app.document_issue_log` 가 있으나 이것이
그 자리인지 알 수 없다.

**필요한 답.** 툴 라벨 발행을 어디에 남기는가. 표가 정해지면 세는 것은 두 줄이다.

### O-2. 보전오더가 툴을 가리키지 못한다

목록 필터 `withOpenMaintenanceOrder`(「열린 보전오더가 있는 툴만/없는 툴만」)를 걸 수 없다.
`maintenance.maintenance_order.equipment_id` 는 **NOT NULL 이고 `mold_id` 가 없다.**

**필요한 답.** 툴 보전오더를 어떻게 담는가 — ① `maintenance_order` 에 `mold_id` 를 더하고
`equipment_id` 를 nullable 로 푼다 ② 툴 전용 표를 둔다 ③ 툴을 설비로도 등록한다.
①은 보전오더의 «대상» 개념을 바꾸는 일이라 우리 선에서 정하지 않았다.

### O-3. 도구 유형 어휘가 없다

`toolTypeCode` 는 `Mold` 의 **필수** 칸이다. 계약이 「금형 · 지그 · 그 밖의 도구」라 개념을
적었으나 **코드 값이 없다** — `TOOL_TYPE` 코드 그룹 자체가 시드에 없다.

공유계약 `G-31`·`G-32` 가 「코드 값은 누가 정하는가」를 설계·고객 쪽에 두었으므로,
`MOLD`·`JIG`·`OTHER` 를 우리가 넣지 않았다.

**필요한 답.** 그룹 코드와 값 목록. 정해지면 `EQUIPMENT_TYPE` 과 같은 방식으로 붙는다.

### O-4. `MOLD_STATUS` 값이 계약과 다르다

| | |
|---|---|
| 계약 | 「자산 수명주기 — **운용 또는 폐기 두 값**. 고장·보전 중·비가동은 거래가 만드는 조건」 |
| 시드 | `NEW` · `NORMAL` · `REPAIR` · `DISPOSED` — **넷** |

`REPAIR`·`NEW` 는 계약이 「거래가 만드는 조건」이라 뺀 축이다. 설비(`EQUIPMENT_STATUS` =
`IN_SERVICE`·`DISPOSED`)와도 어긋난다.

**필요한 답.** 시드를 둘로 줄이는가, 계약이 넷을 받는가. 상태기계(`:dispose`)를 등록하려면
먼저 정해져야 한다 — 값 목록 없이 전이를 지어내지 않는다(`F-6`).

### 정할 수 있는 것은 정해 두었다

`pmTriggerTypeCode`(SHOT·DATE·BOTH)와 `pmCycleUnitCode`(DAY·MONTH)는 **계약이 코드를 직접
적었다.** `availableShotCount`·`nextPmDate`·`pmDue`·`pmDueAxisCode`·`shotUsageRatio` 는
서버 계산이라 결손이 아니다. 위 넷만 풀리면 나머지는 한 PR 이다.

## P. `:import` 2건 — 받을 열이 미정이다

`POST /mdm/spare-parts:import`·`POST /mdm/molds:import` 둘 다 엑셀을 받는다.
계약이 `x-internal-note` 에 적었다 — 「**받을 열은 현행 엑셀 실물을 수집해야 정해진다.
지금은 코드·명칭만 확실하다**」.

지금 만들면 코드·명칭만 읽는 파서를 세우고, 열이 정해지면 다시 짠다. 엑셀 파서
의존성(운영이 인터넷 없는 온프렘이라 번들해야 한다 — `C11`)도 함께 들어온다.

**필요한 답.** 현행 엑셀의 열 목록. 정해지면 둘을 한 PR 로 낸다.

## Q. `W-CO-02` 의 「통째로 교체」 셋에만 `If-Match` 가 없다 — 알려만 둔다

계약이 같은 형태의 저장을 두 가지로 선언했다.

| 오퍼레이션 | `Idempotency-Key` | `If-Match` |
|---|---|---|
| `PUT /mdm/partners/{partnerId}/roles` | ✔ | **✔** |
| `PUT /mdm/items/{itemId}/uom-conversions` | ✔ | **✔** |
| `PUT /app/roles/{roleId}/permissions` | ✔ | ✘ |
| `PUT /app/users/{appUserId}/roles` | ✔ | ✘ |
| `PUT /app/users/{appUserId}/data-scopes` | ✔ | ✘ |

거래처 역할 쪽 계약은 그 이유까지 적어 두었다 — 「통째로 교체하는 저장이라 보호가 없으면
**남이 방금 붙인 역할이 조용히 사라진다**」. 그 문장이 아래 셋에 그대로 들어맞는다.

**지금 일어나는 일.** 관리자 둘이 같은 역할의 권한 격자를 함께 열고 각자 저장하면, 뒤에
저장한 쪽이 앞의 부여를 지운다. 오류도 경고도 없다. 배정·접근범위도 같다.

**서버가 지금 하는 것.** 계약대로 `If-Match` 를 요구하지 않는다 — 계약에 없는 헤더를
서버가 필수로 만들면 화면이 보내지 않아 전건이 막힌다. 다만 관리 권한이 0명이 되는
치환은 `LAST_ADMIN` 으로 막으므로, 되돌릴 수 없는 사고는 나지 않는다.

**필요한 답.** 셋에 `If-Match` 를 선언할 것인가. 선언하면 잠금 축은 «역할»·«사용자»의
`version_no` 다(자식 표에 자기 버전이 없다 — §11 과 같은 형태). 선언하지 않기로 하면
그 판단의 근거를 계약에 적어 두는 편이 낫다 — 지금은 같은 형태가 두 가지로 보인다.

## R. 「공장만」인 접근범위가 세션에 안 실린다 — 부여해도 아무 효과가 없다

두 스키마가 어긋난다.

| | `businessUnitId` |
|---|---|
| `UserDataScope`(저장) | **비어 있을 수 있다** — 「비어 있으면 (전체)」 |
| `SessionScope`(로그인 응답) | **required** |

`ck_user_data_scope_target` 도 「사업부·공장 중 하나 이상」이므로 **공장만 지정한 범위**가
정상 입력이다 — 「사업부는 전체, 이 공장만」이라는 뜻이 된다.

**지금 일어나는 일.** 그렇게 저장한 범위는 `GET /app/sessions/current` 의 `scopes` 에서
빠진다(`SessionScope.businessUnitId` 가 required 라 실을 수가 없다). 관리자는 범위를
부여했는데 화면은 그 범위를 못 받는다 — 오류도 경고도 없이 **아무 효과가 없다.**

**서버가 지금 하는 것.** 저장은 계약대로 받는다(공장만도 정상). 세션은 손대지 않았다 —
`SessionScope` 의 모양을 서버가 바꿀 수는 없다.

**필요한 답.** 둘 중 하나다.
1. `SessionScope.businessUnitId` 를 선택으로 바꾼다 — 「사업부 전체, 이 공장만」이 그대로 실린다.
2. 「공장만」을 금지한다 — 그러면 `ck_user_data_scope_target` 과 `UserDataScope` 설명(「비어
   있으면 (전체)」)을 함께 고쳐야 하고, 서버는 400 `PAIR` 로 막는다.

⚠ 서버가 `plant.business_unit_id` 로 사업부를 «채워» 실는 세 번째 길은 두지 않았다 —
그 컬럼이 nullable 이라 못 채우는 공장이 있고, 그러면 같은 부여가 공장마다 다르게 산다.

## S. Routing — 알려둘 둘

### S-1. 확정 상태의 코드 문자열이 `ACTIVE` 다 — 계약 스스로 되돌리라 적었다

계약 `Routing.statusCode` 의 `x-internal-note` 가 이렇게 적혀 있다.

> example 이 `'ACTIVE'` 였다 — 결정 07 이 확정한 뜻은 작성중·확정·폐기 셋이고 그중 어느
> 것도 아니다. 공유계약 `G-32` 가 설비 자산 상태에서 같은 결함을 잡아 「사용 여부
> (`is_active`)와 수명주기에 같은 낱말을 쓰지 않는다」로 고쳤다(`ACTIVE` →
> `IN_SERVICE`·`DISPOSED`). 여기도 코드 문자열이 정해질 때까지 자리표시로 되돌린다.

**금형(§O-4)과 다르다 — 여기는 셀 수 있다.** 시드 `REVISION_STATUS` 가 `DRAFT`·`ACTIVE`·
`OBSOLETE` 셋을 담고 있고, 결정 07 이 확정한 상태도 셋(작성중·확정·폐기)이라 짝이 하나뿐이다.
그래서 **구현했다** — 이름만 나쁘고 값 집합은 정해져 있다.

⚠ 이름을 바꾸기로 하면 고칠 자리가 **둘**이다. 코드 상수(`ROUTING_STATUS`) 한 줄과,
`uq_routing_default` 가 술어에 `'ACTIVE'` 를 박아 두었던 자리 — 후자는 이 PR 의 선행
마이그레이션이 이미 술어에서 상태를 빼서 사라졌다.

**필요한 답.** 확정 상태의 코드 문자열. `CONFIRMED` 가 액션 이름(`:confirm`)과 짝이 맞다.

### S-2. `usableOnly` 의 「지금」이 어느 날짜인지 정해져 있지 않다

`GET /planning/routings?usableOnly=true` 는 「지금 새 작업지시에 걸 수 있는 개정만 낸다.
**판정은 서버가 한다**」인데 **날짜 파라미터가 없다.**

Routing 은 공장에 매이지 않아 `plant.timezone_code` 로 풀 자리도 없다. 그래서 서버는
UTC 날짜로 읽는다 — 컨테이너 TZ 가 UTC 고정이기 때문이다.

**지금 일어나는 일.** 하노이 로컬 `00:00~07:00` 에는 UTC 날짜가 하루 이르다. 그 시간대에
「오늘부터 유효」인 Rev 가 아직 목록에 안 걸린다. 야간조가 새 Rev 로 작업지시를 내려다
「없다」를 보는 창이 매일 일곱 시간 생긴다.

**필요한 답.** 둘 중 하나다.
1. `businessDate` 파라미터를 받는다 — 클라이언트가 공장 업무일을 안다(공유계약 `C-8` 과 같은 방향).
2. 서버가 공장 로컬로 읽는다 — 그러려면 어느 공장인지가 질의에 있어야 한다.

⚠ 서버가 임의로 「UTC+7」을 박는 길은 두지 않았다. 공장이 늘면 그것이 곧 틀린 값이 된다.

### S-3. 신규 Rev 가 선후행을 물려받는지 계약이 말하지 않는다 — 물려받게 했다

`POST /planning/routings/{routingId}:new-revision` 의 설명은 이렇게 적혀 있다.

> 헤더 속성(`routingCode`·`effectiveFrom`·`effectiveTo`)과 **공정 라인 전부**를 함께
> 복제한다(§8-7).

**선후행(`routing_operation_dependency`)은 안 적혀 있다.** 라인만 옮기면 새 Rev 는 공정
순서 관계를 잃은 채 열리고, 관리자가 「복사했는데 선후행이 비었다」를 손으로 다시 그려야 한다.
그것은 복사의 뜻이 아니라고 보아 **선후행도 함께 복제했다** — 원본 라인 id 를 새 라인 id 로
바꿔 옮긴다.

**필요한 답.** 이 판단이 맞는가. 아니라면 「신규 Rev 는 선후행을 비운 채 연다」를 계약에
적어 두는 편이 낫다 — 지금은 읽는 사람마다 다르게 구현한다.

### S-4. 신규 Rev 번호를 「원본 +1」이 아니라 「품목 최댓값 +1」로 잡았다

계약은 「지정한 Rev 를 복사해 `routingVersion+1` 의 작성중 Rev 를 새로 만든다」로 적었다.

⚠ 그대로 하면 **최신이 아닌 확정 Rev 에서 부를 때 `uq_routing` 이 깨진다.** Rev 1·2 가
있는데 Rev 1 에서 발행하면 2가 이미 있다. 계약이 「최신(확정) Rev 위에서 호출」을 전제하지만,
서버가 그 전제를 강제하지 않으므로(계약도 「상태가 확정이어야 한다」만 요구한다) 최댓값 다음을
쓴다 — 그 자리만이 언제나 비어 있다.

**필요한 답.** 「최신 확정 Rev 에서만 발행할 수 있다」를 서버가 막아야 하는가. 막으면 계약
문구대로 `+1` 이 되고, 안 막으면 지금처럼 최댓값 다음이 맞다.

## T. BOM — 알려둘 둘

### T-1. `Bom.statusCode` 의 값 목록도 「미정」인데 `usableOnly` 는 그것을 봐야 한다

계약 `Bom.statusCode` 는 「공통코드 — 값 목록 미정」이고, `x-internal-note` 가
`Routing.statusCode` 와 **토씨까지 같다**(둘 다 `omf-mes#259`, 둘 다 `ACTIVE` 를 되돌리라
적었다).

`GET /planning/boms?usableOnly=true` 는 「지금 새 작업지시에 걸 수 있는 개정만」이라 확정
상태를 알아야 한다. 시드 그룹 이름이 `REVISION_STATUS`(개정 상태)로 **자원 이름이 아닌**
데다 Routing 과 계약 문구가 같아, 둘이 같은 축을 쓰는 것으로 읽고 같은 상수를 썼다.

⚠ **BOM 상태는 서버가 «쓰지» 않는다** — ERP 정본이라 읽기만 한다. 그래서 이 판단이
틀려도 손상은 `usableOnly` 필터 하나에 갇힌다.

**필요한 답.** BOM 과 Routing 이 같은 코드 그룹을 쓰는가. 다르면 BOM 쪽 그룹 이름과 값.

### T-2. `conflictCause` 를 `updated_by` 의 빈칸으로 갈랐다

계약이 `PUT /planning/boms/{bomId}/components/{bomComponentId}` 의 409 에 이렇게 적었다.

> `conflictCause=user` 는 다른 사용자, `erpSync` 는 ERP 재동기화 배치가 같은 BOM 을
> 갱신했을 가능성이 높다(`bom_component` 도 원본 열을 통해 재동기화 대상이다).

**서버가 그 둘을 가릴 근거가 `updated_by` 하나뿐이다.** 연계는 세션 없이 쓰므로 그 칸을
채울 수 없고, 화면은 세션이 있으니 채운다. 그래서 「마지막 갱신자가 비어 있으면 `erpSync`」로
읽었다. 이 PR 이 확장 열 수정에 `updated_by` 를 쓰도록 함께 고쳤다 — 안 채우면 판정이
언제나 `erpSync` 가 된다(실제로 그렇게 나와서 드러났다).

⚠ 완벽하지 않다. 연계가 «언제» 돌았는지는 여기서 모르므로, 사람이 고친 뒤 연계가 덮은
경우와 연계가 덮은 뒤 사람이 고친 경우를 순서로 가리지 못한다.

**필요한 답.** ERP 연계가 `bom_component` 를 갱신할 때 남길 표식이 따로 있는가
(예: `updated_by` 에 연계 전용 계정, 또는 `source_system_code` 류 칸). 있으면 그것으로 가른다.

## U. 불량코드-공정 매핑의 쓰기 둘에 `403` 선언이 없다 — 알려만 둔다

| 오퍼레이션 | 403 선언 |
|---|---|
| `GET /quality/defect-codes/{defectCodeId}/processes` | 없음(조회라 자연스럽다) |
| **`POST` …/processes** | **없음** |
| **`DELETE` …/processes/{processId}** | **없음** |
| 같은 화면의 다른 쓰기(`POST /quality/defect-codes` 등 8건) | 있음 |

권한 게이트는 **계약이 403 을 선언한 자리에서만** 돈다(`permission.guard.ts` — 선언하지
않은 곳에서 403 을 내면 계약과 어긋난다). 그래서 이 둘은 **로그인만 하면 누구나 부를 수
있다.** 같은 화면(`W-06-03`)의 다른 쓰기 여덟은 `W-06-03` 을 요구하는데 이 둘만 열려 있다.

**영향.** 매핑은 「POP 불량 입력 화면이 자기 공정의 불량코드만 본다」의 근거다(계약 §4-D).
바꾸면 현장 작업자에게 보이는 불량코드 목록이 바뀐다 — 조회용 데이터가 아니다.

**서버가 지금 하는 것.** 계약대로 게이트를 안 건다. 서버가 계약에 없는 403 을 내면
그 자리를 쓰는 화면이 통째로 막힌다.

**필요한 답.** 두 오퍼레이션에 403 을 선언할 것인가. 선언하면 권한은 `W-06-03` 이다
(같은 화면의 나머지와 같다).

## V. 검사기준 — 알려둘 둘

### V-1. 버전 상태의 값 목록이 「W-06-01 준용 여부 미정」이다 — 준용했다

계약 `InspectionPlanVersion.statusCode` 는 「공통코드 — 값 목록 미정. **W-06-01 의
작성중/확정/폐기 준용 여부 §8-2**」이고, 액션은 Routing 과 똑같이

**`REVISION_STATUS`(`DRAFT`·`ACTIVE`·`OBSOLETE`)를 준용했다.** BOM(§T-1)과 같은 판단이다.

⚠ 이쪽은 BOM 과 달리 **서버가 상태를 «쓴다»**(`:confirm` 등이 전이시킨다). 값이 다르게
정해지면 이미 저장된 행이 어긋나므로, BOM 보다 답이 급하다.

**필요한 답.** 준용하는가. 준용하지 않으면 그룹 이름과 값 셋.

### V-2. 「이미 승인된 기준을 다시 승인」을 계약이 말하지 않는다 — 막았다

`POST /quality/inspection-plans/{id}:approve` 는 「`approvedBy`·`approvedAt` 을 서버가
동시에 기록한다. **승인 해제(취소)는 제공하지 않는다**」로 적혀 있다.

**두 번 부르면 어떻게 되는지는 안 적혀 있다.** 그대로 두면 승인자와 시각이 덮인다 —
해제가 없는데 「누가 언제 승인했는가」만 바뀌므로, 사실상 감사 기록을 지우는 쓰기다.
그래서 400 `STATE_LOCKED` 로 막았다.

**필요한 답.** 이 판단이 맞는가. 「마지막 승인자로 갱신한다」가 업무 규칙이면 되돌린다.

## W. 적치 규칙 `:activate` 의 중복 판정이 지금은 걸릴 수 없다 — 알려만 둔다

계약이 두 자리에 서로 다른 유일 조건을 적었다.

| 오퍼레이션 | 계약 문구 |
|---|---|
| `POST /logistics/putaway-rules` | 「같은 **품목·창고·위치** 조합이 이미 있으면 400」 |
| `POST …/{id}:activate` | 「같은 (품목, 창고, 위치, **우선순위**)로 이미 **활성**인 규칙이 있으면 400」 |

물리 인덱스는 앞쪽과 같다 — `uq_putaway_rule(item_id, warehouse_id, COALESCE(location_id,0))`
이고 **부분 인덱스가 아니다**(`WHERE is_active` 가 없다).

**그래서 `:activate` 의 판정은 도달할 수 없다.** 같은 (품목, 창고, 위치)의 행이 애초에
둘일 수 없으므로 우선순위까지 볼 것도 없다. 서버는 계약이 요구한 검사를 그대로 두었다 —
인덱스가 부분으로 바뀌면 그때 살아난다.

**필요한 답.** 둘 중 하나다.
1. 인덱스를 `WHERE is_active` 로 좁힌다 — 중지된 규칙 옆에 새 활성 규칙을 세울 수 있게 되고
   `:activate` 의 판정이 살아난다. 대신 등록 쪽 문구(「이미 있으면」)를 「활성인 것이 있으면」
   으로 함께 고쳐야 한다.
2. `:activate` 의 문구를 지운다 — 등록이 이미 막으므로 중복이다.

⚠ 지금 서버는 **중지된 규칙도 세어** 등록을 막는다(계약 문구 그대로). 같은 조합을 다시
쓰려면 되살리는 것이 유일한 길이고, 오류 문구가 그것을 알린다.

## X. 연계 — 알려둘 셋

### X-1. 「확정된 수신 대상 다섯」의 코드 문자열이 없다

계약 `InterfaceDefinition.targetCode` 는 이렇게 적혀 있다.

> 확정된 수신 대상은 **품목 · 자재명세 · 조직 · 작업자 · 구매발주** 다섯이며 그 밖의 값도
> 받는다 — 막지 않고 표식만 한다. 확정 목록 안인지는 `withinConfirmedScope` 가 말한다.

**낱말로만 적혀 있고 코드 문자열이 없다.** `example` 이 `ITEM` 하나를 보였을 뿐이다.
서버는 그 결에 맞춰 다섯을 적었다 — `ITEM` · `BOM` · `ORGANIZATION` · `WORKER` ·
`PURCHASE_ORDER`.

⚠ **틀려도 손상은 좁다.** 이 목록은 «막는» 목록이 아니라 `withinConfirmedScope` 를 계산하는
데만 쓴다. 값이 틀리면 화면에 「확정 목록 밖입니다」 표식이 잘못 붙거나 안 붙을 뿐,
저장은 그대로 된다.

**필요한 답.** 다섯의 코드 문자열.

### X-2. 「연결 시험」이 시험할 수 있는 것은 우리 DB 안뿐이다

계약 `:test-connection` 은 「**중계 테이블에 닿는지만** 본다. 실제 동기화는 돌리지 않는다」
이고, 실패 원인을 `UNREACHABLE` · `TABLE_NOT_FOUND` · `PERMISSION_DENIED` 셋으로 가르라 한다.

서버는 `relayTableName` 이 가리키는 표가 **우리 데이터베이스 안에** 있는지와 읽을 권한이
있는지를 본다. 그래서 `TABLE_NOT_FOUND` 와 `PERMISSION_DENIED` 는 나오는데
**`UNREACHABLE` 은 나올 자리가 없다** — 중계 테이블이 «다른» 데이터베이스에 있고 그쪽으로
가는 접속 정보가 있어야 「닿지 않는다」가 뜻을 갖는다.

물리 모델의 `transport_code`·`endpoint_uri` 가 그 자리로 보이는데, **계약에 그 두 축이
없다**(등록·수정 요청에 없다). 그래서 서버는 그 칸을 채우지 못하고 비워 둔다.

**필요한 답.** 중계 테이블이 우리 DB 안인가 밖인가. 밖이면 접속 정보를 어디에 두는가
(`endpoint_uri` 를 계약에 올릴 것인가).

### X-3. 「아직 보내지 못한」을 완료 시각으로 셌다 — 상태 값 목록이 없어서다

`pendingMessageCount` 는 「아직 보내지 못한 연계 메시지 수」인데,
`IntegrationMessage.statusCode` 의 값 목록이 「아직 서지 않았다」(계약 · `omf-mes#213`).

그래서 상태 문자열 대신 **`completed_at IS NULL`** 로 셌다 — 완료 시각이 비어 있으면
아직 끝나지 않은 것이고, 그 판정에는 어휘가 필요 없다.

⚠ 「실패해서 더 시도하지 않는 것」도 이 셈에 든다. 상태 어휘가 정해지면 「대기·처리중」만
세는 쪽이 맞을 수 있다.

**필요한 답.** 연계 메시지 상태의 값 목록(최소 대기/처리중/완료/실패).

### X-4. 연계 메시지 상태의 값 목록이 없다 — 넷을 적고 재처리를 세웠다

계약 `IntegrationMessage.statusCode` 는 「공통코드 — **값 목록이 아직 서지 않았다.**
최소 구분: 대기/처리중/완료/실패」이고 추적처가 `omf-mes#213` 이다.

그런데 `:retry` 는 「`statusCode`=**실패** 이고 `lockedBy` 가 비어 있어야 한다」라,
그 낱말이 어떤 문자열인지 모르면 **화면의 본체가 서지 않는다**(`W-06-10` 의 존재 이유가
재처리다).

근거 셋을 모아 `PENDING`·`PROCESSING`·`COMPLETED`·`FAILED` 를 적었다.

1. 계약 자신이 `statusCode` 의 `example` 로 **`FAILED`** 를 보였다.
2. 설계의 웹프론트 착수안내가 재처리 화면 목업에 **`statusCode: FAILED`** 를 썼다.
3. 이 표에 쓰는 **워커가 아직 없다** — 어긋날 기존 데이터가 없다.

⛔ **금형(`MOLD_STATUS`, §O-4)과 갈리는 지점이 여기다.** 그쪽은 시드 4값이 계약 2값과
«어긋나» 어느 쪽도 고를 수 없었다. 여기는 시드도 CHECK 도 없고 계약의 예시와 설계 목업이
같은 값을 가리킨다 — **모름이지 모순이 아니다.**

값이 다르게 정해지면 상수 한 줄(`MESSAGE_STATUS`)을 바꾼다.

**필요한 답.** 넷의 코드 문자열. 특히 「실패」 — 그 하나가 재처리의 판정 축이다.

### X-5. 송신 항목 — 저장된 줄이 없을 때의 기본값이 정해져 있지 않다

계약 `GET /integration/outbound-item-settings` 는 「송신 항목 **다섯**의 켜짐·꺼짐과 잠금
여부」를 낸다. 그런데 **아무것도 저장한 적이 없는 처음 상태**에서 무엇이 켜져 있어야 하는지는
적혀 있지 않다.

서버는 **「켜짐」을 기본으로 두었다.** 근거는 계약 자신의 문장이다 — 「끄는 순간 외부로
나가는 전표가 끊기고 **되돌려도 그 사이는 복구되지 않는다**」. 즉 «끄는 것»이 의도적인
조작이고 «보내는 것»이 평소다.

⚠ 반대 판단도 가능하다 — 아무것도 설정하지 않았는데 나가는 것보다 안 나가는 편이 안전하다는
읽기다. 다만 생산 실적은 `locked` 라 끌 수 없으므로 **적어도 하나는 반드시 켜져 있어야
한다** — 그것과 어긋나지 않는 쪽이 「켜짐」이다.

**필요한 답.** 처음 상태의 기본값. 「꺼짐」이면 시드로 다섯 줄을 넣는 편이 낫다.

### X-6. 「사용자」인가 「작업자」인가 — §X-1 의 보강

`omf-mes#197` 정합주가 확정 수신 대상을 「품목·자재명세(BOM)·조직·**작업자**·구매발주
다섯」으로 적으면서, 같은 문단에 「**'작업자'→'사용자' 개명**은 그대로 유효하다」를 함께
적었다. 서버는 계약 본문의 낱말을 따라 `WORKER` 로 두었으나 `USER` 일 수 있다.

**필요한 답.** §X-1 의 다섯 코드와 함께 이 하나를 짚어 주면 된다.
