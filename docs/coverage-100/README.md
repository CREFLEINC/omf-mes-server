## 1. 작업 방식

1. **계획**: 시작 시 1회, 남은 전부에 대해 3관점(API 설계·UI/UX 설계·통합) 계획서 → 충돌은 브레인스토밍 → 통합 계획서 1개.
2. **슬라이스마다**: 개별 계획안 1개 → **3관점 재수립(기본값)** → 통합자가 §0-재수립 R-n 표로 통합 →
   통합 계획서 해당 절 수정 → 구현.
   ⭐ **2026-09-07 변경** — 재수립은 조건부가 아니라 **기본값**이다. 옛 「차이가 크다」 3조건(없던
   마이그 · 다른 슬라이스 순서 · 새 문의)은 I-1~I-12·I-24 **13슬라이스에서 13번 다 걸려** 한 번도
   거르지 못했다. 관문 논증을 없애고, 계획자는 §0 에 조건 판정 대신 **「리뷰가 반드시 볼 자리 5개」**
   (자기가 ⭐ 로 표시한 갈림길 + 뒤집히면 PR 분할이 바뀌는 자리)를 적는다. 통합자의 리뷰 브리프는
   그 다섯을 그대로 판정 항목으로 삼는다 — 브리프를 손으로 다시 세우지 않는다.
   ⛔ 건너뛰는 것은 **선행 슬라이스의 복제가 명백할 때**뿐이고, 그때도 사유를 계획안 §0 에 적는다.
3. **순서**: `development-strategy.md` 순서 우선. 같은 도메인의 조회 GET 은 함께 묶어 커버리지를 올린다.
4. **PR**: 「전표 하나 + posting 연결 + e2e」 단위. 마이그레이션은 별도 선행 커밋. merge commit(`--merge`). 동기화·병합 확인·자식 PR의 base 변경·브랜치 삭제 절차는 **[`lanes.md` §2](lanes.md#2-병합-절차-병렬이라-달라지는-부분)** 를 따른다. ⛔ rebase·force-push·`gh pr merge --delete-branch` 금지.
5. **리뷰·병합**: 크레플 `pr-review` 규칙. Blocker 0 · Major 0 · CI green · 충돌 없음이면 **내가 바로 병합**.
   마이그레이션이 든 PR 은 병합 전에 한 줄 보고만 하고 넘어간다(멈추지 않는다).
6. **보고 주기**: PR 병합마다 한 줄(번호·오퍼레이션 수·커버리지 n/487), 슬라이스 끝에 짧은 절,
   루틴 끝에 전체 보고 + 검토 요청서 목록 + 건너뛴 오퍼레이션 목록.

## 2. 설계 미정 갈림길 판정 절차 (「보수적」 대신 이 절차)

**0단계 — 선례.** 계약 본문 · `docs/기존-구현-도메인-규칙.md` · 이미 구현된 다른 전표. 있으면 인용(판단 아님).

**1단계 — 가장자리 / 본길.**
- 가장자리(특정 조건의 입력에서만 갈림) → 2단계.
- 본길(모든 호출의 결과가 달라짐) → 계약 문자를 먼저 따른다. 계약도 침묵하면 **1-1단계**로 간다.

**⭐ 1-1단계 — 물어볼 것인가, 정하고 통보할 것인가 (2026-09-08 사용자 지시로 신설).**

> **기본값은 「정하고 통보」다.** 정말 중요한 핵심 로직은 이미 설계가 정해 두었으므로, 남은 것은
> 우리가 결정한다. **아래 두 축에 «둘 다» 걸릴 때만 묻는다.**

| | **바꾸는 비용 높다** | **바꾸는 비용 낮다** |
|---|---|---|
| **MES 본질** | ⭐ **묻는다**(그리고 답이 올 때까지 그 자리만 미룬다) | **정하고 통보** |
| 본질 아님 | **정하고 통보** | **정하고 통보** |

- **「MES 본질」** — 현장의 업무 규칙 · 추적성(계보) · 재고 원장 · 회계 기간이 달라지는 것.
- **「바꾸는 비용이 높다」** — 셋 중 하나에 걸리는 것:
  ⓐ **지금 안 적으면 소급이 불가능한 데이터**(그 시점 정보가 사라진다)
  ⓑ **이미 쌓인 행을 정정할 수 없다**(예: 원장은 `block_ledger_header_mutation` 이 UPDATE·DELETE 를 막는다)
  ⓒ 고치려면 **계약이 광범위하게 바뀐다**
- ⛔ **「본길이라 임의로 못 고른다」는 폐기**한다. 본길이어도 위 표에서 갈린다.
- **정하고 통보**로 가면 **회신을 기다리지 않는다** — 구현하고, 통보문을 쓰고, 다음으로 간다.
- **묻는 것으로 가면** 그 자리만 미루고 **나머지는 진행**한다. 슬라이스를 통째로 멈추지 않는다.

⭐ **선례(2026-09-08 판정)** — 같은 자리에서 갈린 둘:
- **문의 052**(LOT 계보) → **물었다.** 본질(추적성) + 투입 시점에 안 적으면 **소급 영구 불가**(ⓐ). ⇒ **회신: 「현행 유지 · LOT 단위 정밀 추적은 1차에 불필요」**(2026-09-08). W/O 단위 계보로 간다.
- **문의 051**(자재 반출이 원장 밖) → **정했다.** 본질(재고 원장)이지만 반출 기록이 온전해 **나중에 소급 전기가 가능**하다. ⇒ 전기 ✕ 유지 + 배포 노트.

**2단계 — 나중에 뒤집는 비용이 싼 쪽. 같으면 개발 난이도가 낮은 쪽.** 위에서부터 먼저 걸리는 기준으로 결정.
1. 재고·원장·상태를 쓰지 않는 쪽
2. 거부하는 쪽(명시적 에러 코드) — 거부→허용은 호환 완화, 허용→거부는 깨는 변경
3. 스키마를 안 늘리는 쪽, 늘려야 하면 nullable
4. 값을 조용히 도출하지 않는 쪽
5. 개발 난이도가 낮은 쪽 — 위 넷으로 안 갈리거나 서로 충돌할 때. 난이도는 코드 양이 아니라
   **새로 만드는 개념의 수**(테이블·상태값·코드 그룹·상태 전이)로 잰다.

**3단계 — 흔적.** 에러 코드/고정값에 이름, 요청서에 「몇 단계 몇 번 기준으로 골랐음」.
- **묻는 것**(1-1 에서 「묻는다」로 간 것) → 단언 테스트에 `// 설계 미정 — 문의 NNN`
- **정한 것**(기본값) → 단언 테스트에 **`// 결정 — 통보 NNN`**. ⛔ 「설계 미정」으로 적지 마라 — **기다리는 것처럼 읽힌다.**

## 6. 속도 (2026-09-06 · #213 뒤 사용자 지시 「품질 영향 최소로 시간 단축」)

- **게이트를 두 번 돌리지 않는다** — 구현자가 PR 본문에 게이트 실측(명령·숫자)을 적는다. 리뷰어는 diff 를 읽고 **단위 전체 + 바뀐 e2e 파일만** 돌린다. 회귀 e2e(다른 파일)는 통합자가 병합 직전에 한 번 돌린다.
- **비테스트 diff 예산은 구현 브리프에 350** — 리뷰 수정분(+20~30)이 들어갈 자리를 남겨 400 맞추기 왕복을 없앤다. 한도 400 자체는 그대로다.
- **리뷰 Major 가 계획서 쪽 구멍이면** 코드를 고치기 전에 §0-재수립 한 줄로 판정을 먼저 적는다 — 「일어날 수 없다」 류 추론은 리뷰어가 실측으로 뒤집을 수 있으므로 계획 단계에서 단위 테스트 이름으로 못 박는다.
- 다음 PR 을 리뷰 중인 PR 위에 스택으로 먼저 스폰한다(I-4 ③→④→⑤ 선례). 바꾸지 않는 것: 리뷰어 ≠ 구현자 · 병합 전 e2e 파일 단위 실행.

### 6-1. 2026-09-07 추가 (I-24 뒤 측정 · 사용자 승인)

측정: 최근 830분 구간에서 **계획 30%(8건 · 평균 31분) · 구현 63%(29건 · 평균 18.1분) · 마감 docs 7%(7건 · 평균 8.3분)**.
재수립 R 행 **134개 중 102개(76%)가 계획을 실제로 바꿨다** ⇒ 3관점 자체는 유지하고 **중복과 대기만** 걷어낸다.

1. ⭐ **리뷰어에게 재측정을 시키지 않는다 — 「계획자가 보지 않은 자리」가 리뷰어의 몫이다.**
   근거: I-24 에서 계획을 뒤집은 8건 중 **7건이 「계획자가 그 자리를 아예 안 봤다」**였고(반환 순서 보장 ·
   채번 `plantId` 축 · `ProductionConflictResponse.code` enum · 마감 트리거 · `reason` 컬럼 주석 ·
   `message_key` 150자 · 전이 단언 27) **오측정은 1건**뿐이었다. 반면 같은 사실을 두세 관점이 따로
   측정한 겹침이 findings 의 약 절반이었다.
   ⇒ 계획자는 계획안 말미에 **「실측 부록」**(사실 + `파일:줄`, 표 하나)을 붙인다. 리뷰 브리프에 그대로 넣고
   **「이 표의 값은 재측정하지 않는다. 단 네 판정이 그 값을 뒤집는다면 반드시 재측정한다」**를 명시한다.
2. **재수립 조건 판정을 없앤다** — §1-2 참조(기본값 + 「반드시 볼 자리 5」).
3. **조회 PR ① 을 리뷰 라운드와 나란히 스폰한다.** 근거: I-24·I-12·I-11 에서 계획을 뒤집은 R 들이
   **전부 마이그·코어·심장(②③④) 범위**였고 조회 PR 에 닿은 것은 주석 문구 하나뿐이었다.
   ⇒ 리뷰 3개를 띄운 직후 ① 구현자를 같이 띄운다. 재수립이 ① 을 건드리면 그 PR 리뷰에서 고친다.
   ⛔ **마이그·코어·심장 PR 에는 적용하지 않는다** — 그쪽은 R-n 확정 뒤에만 스폰한다.
