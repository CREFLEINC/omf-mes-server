## 1. 작업 방식

1. **계획**: 시작 시 1회, 남은 전부에 대해 3관점(API 설계·UI/UX 설계·통합) 계획서 → 충돌은 브레인스토밍 → 통합 계획서 1개.
2. **슬라이스마다**: 개별 계획안 1개 → **3관점 재수립(기본값)** → 통합자가 §0-재수립 R-n 표로 통합 →
   통합 계획서 해당 절 수정 → 구현.
   ⭐ **2026-09-07 변경** — 재수립은 조건부가 아니라 **기본값**이다. 옛 「차이가 크다」 3조건(없던
   마이그 · 다른 슬라이스 순서 · 새 문의)은 I-1~I-12·I-24 **13슬라이스에서 13번 다 걸려** 한 번도
   거르지 못했다. 관문 논증을 없애고, 계획자는 §0 에 조건 판정 대신 **「리뷰가 반드시 볼 자리 5개」**
   (자기가 ⭐ 로 표시한 갈림길 + 뒤집히면 PR 분할이 바뀌는 자리)를 적는다. 통합자의 리뷰 브리프는
   그 다섯을 그대로 판정 항목으로 삼는다 — 브리프를 손으로 다시 세우지 않는다.
   ⛔ 건너뛰는 것은 **선행 슬라이스의 복제가 명백할 때**뿐이고, 그때도 사유를 계획안 §0 에 적는다.
3. **순서**: `development-strategy.md` 순서 우선. 같은 도메인의 조회 GET 은 함께 묶어 커버리지를 올린다.
4. **PR**: 「전표 하나 + posting 연결 + e2e」 단위. 마이그레이션은 별도 선행 커밋. merge commit(`--merge`). 동기화·병합 확인·자식 PR의 base 변경·브랜치 삭제 절차는 **[`lanes.md` §2](lanes.md#2-병합-절차-병렬이라-달라지는-부분)** 를 따른다. ⛔ rebase·force-push·`gh pr merge --delete-branch` 금지.
5. **리뷰·병합**: 크레플 `pr-review` 규칙. Blocker 0 · Major 0 · CI green · 충돌 없음이면 **내가 바로 병합**.
   마이그레이션이 든 PR 은 병합 전에 한 줄 보고만 하고 넘어간다(멈추지 않는다).
6. **보고 주기**: PR 병합마다 한 줄(번호·오퍼레이션 수·커버리지 n/487), 슬라이스 끝에 짧은 절,
   루틴 끝에 전체 보고 + 검토 요청서 목록 + 건너뛴 오퍼레이션 목록.

## 2. 설계 미정 갈림길 판정 절차 (「보수적」 대신 이 절차)

**0단계 — 선례.** 계약 본문 · `docs/기존-구현-도메인-규칙.md` · 이미 구현된 다른 전표. 있으면 인용(판단 아님).

**1단계 — 가장자리 / 본길.**
- 가장자리(특정 조건의 입력에서만 갈림) → 2단계.
- 본길(모든 호출의 결과가 달라짐) → 계약 문자를 먼저 따른다. 계약도 침묵하면 **1-1단계**로 간다.

**⭐ 1-1단계 — 물어볼 것인가, 정하고 통보할 것인가 (2026-09-08 사용자 지시로 신설).**

> **기본값은 「정하고 통보」다.** 정말 중요한 핵심 로직은 이미 설계가 정해 두었으므로, 남은 것은
> 우리가 결정한다. **아래 두 축에 «둘 다» 걸릴 때만 묻는다.**

| | **바꾸는 비용 높다** | **바꾸는 비용 낮다** |
|---|---|---|
| **MES 본질** | ⭐ **묻는다**(그리고 답이 올 때까지 그 자리만 미룬다) | **정하고 통보** |
| 본질 아님 | **정하고 통보** | **정하고 통보** |

- **「MES 본질」** — 현장의 업무 규칙 · 추적성(계보) · 재고 원장 · 회계 기간이 달라지는 것.
- **「바꾸는 비용이 높다」** — 셋 중 하나에 걸리는 것:
  ⓐ **지금 안 적으면 소급이 불가능한 데이터**(그 시점 정보가 사라진다)
  ⓑ **이미 쌓인 행을 정정할 수 없다**(예: 원장은 `block_ledger_header_mutation` 이 UPDATE·DELETE 를 막는다)
  ⓒ 고치려면 **계약이 광범위하게 바뀐다**
- ⛔ **「본길이라 임의로 못 고른다」는 폐기**한다. 본길이어도 위 표에서 갈린다.
- **정하고 통보**로 가면 **회신을 기다리지 않는다** — 구현하고, 통보문을 쓰고, 다음으로 간다.
- **묻는 것으로 가면** 그 자리만 미루고 **나머지는 진행**한다. 슬라이스를 통째로 멈추지 않는다.

⭐ **선례(2026-09-08 판정)** — 같은 자리에서 갈린 둘:
- **문의 052**(LOT 계보) → **물었다.** 본질(추적성) + 투입 시점에 안 적으면 **소급 영구 불가**(ⓐ). ⇒ **회신: 「현행 유지 · LOT 단위 정밀 추적은 1차에 불필요」**(2026-09-08). W/O 단위 계보로 간다.
- **문의 051**(자재 반출이 원장 밖) → **정했다.** 본질(재고 원장)이지만 반출 기록이 온전해 **나중에 소급 전기가 가능**하다. ⇒ 전기 ✕ 유지 + 배포 노트.

**2단계 — 나중에 뒤집는 비용이 싼 쪽. 같으면 개발 난이도가 낮은 쪽.** 위에서부터 먼저 걸리는 기준으로 결정.
1. 재고·원장·상태를 쓰지 않는 쪽
2. 거부하는 쪽(명시적 에러 코드) — 거부→허용은 호환 완화, 허용→거부는 깨는 변경
3. 스키마를 안 늘리는 쪽, 늘려야 하면 nullable
4. 값을 조용히 도출하지 않는 쪽
5. 개발 난이도가 낮은 쪽 — 위 넷으로 안 갈리거나 서로 충돌할 때. 난이도는 코드 양이 아니라
   **새로 만드는 개념의 수**(테이블·상태값·코드 그룹·상태 전이)로 잰다.

**3단계 — 흔적.** 에러 코드/고정값에 이름, 요청서에 「몇 단계 몇 번 기준으로 골랐음」.
- **묻는 것**(1-1 에서 「묻는다」로 간 것) → 단언 테스트에 `// 설계 미정 — 문의 NNN`
- **정한 것**(기본값) → 단언 테스트에 **`// 결정 — 통보 NNN`**. ⛔ 「설계 미정」으로 적지 마라 — **기다리는 것처럼 읽힌다.**

> 틀리는 게 아니라 **행이 통째로 사라진다** — 「값이 다르다」로는 안 잡힌다.

> | **응답에 안 실리는 인자**(`runIdempotent` 의 `FAMILY_CONFLICT_CODE`) | 성공 응답이 안 바뀌고 409 갈래를 안 태우면 끝 | **불변식 spec**(`family-conflict-code.spec.ts` 가 계약을 훑어 호출부 수까지 센다) |
> | **저장 칸이 응답에 없다**(`created_by`) | 계약 응답에 그 칸이 없어 화면도 e2e 도 안 본다 | e2e 에서 **저장값을 직접 조회해 단언**(선례 `quality-nonconformance-write.e2e-spec.ts:138`) |
> | ⭐ **잠금 «범위»**(`FOR UPDATE OF x`) | **넓혀도** HTTP 응답이 한 글자도 안 바뀐다 — 깨지는 것은 형제 행을 «동시에» 쓸 때뿐이라 e2e 는 타이밍에 기대게 된다(I-22 ⑦b 실측: `OF a` → `OF a, s` 가 e2e **31/31 GREEN**) | 서비스 spec 이 SQL 을 **끝을 앵커해** 본다 — `/FOR UPDATE OF a$/`. ⛔ 앵커 없는 `/FOR UPDATE OF a/` 는 «제거»만 잡고 «확대»를 놓친다(⑥ 이 그 모양이다) |
> | ⭐ **헤더 값의 «공백»** | HTTP 파서가 헤더 값의 **OWS 를 잘라** `'   '` 가 핸들러에 «닿지 않는다» — `trim()` 을 지워도 e2e 는 전건 초록이다(I-22 ⑦b 리뷰 실측 3회) | 검증 함수를 **단위로 직접 부른다**(`assertWorkerNoPresent('   ')`). e2e 에는 `''` 축만 남긴다 |
>
> ⛔ **「반증 불가」는 결론이 아니라 «어느 층으로 내려갈지»의 신호다.** **여섯 번 다** 그 층이 실재했다.

**⛔ 그리고 하나 더 — 고쳤으면 «망가뜨려서 다시» 확인해라.**
2026-09-09 에 **리뷰어가 제안한 처방이 두 번 헛수고**였다: ⓐ 제안한 픽스처의 값이 우연히 덮어쓸 값과
같아 여전히 초록이었다(①b) ⓑ 경계로 고른 `0.15+0.15` 가 함정을 안 건드렸다(②b). **구현자가 고친 뒤
그 변이를 다시 돌려** 둘 다 잡았다. ⇒ **「지적을 반영했다」로 끝내지 마라. 반영 뒤 변이가 RED 인지 보고한다.**

**⛔ 403 을 «미선언»한 오퍼레이션에 수동 권한 행을 넣었다면 `operation-permissions.spec.ts` 단언과 반드시 짝지어라.**
`permission.guard.ts` 가 「403 을 «선언한» 자리에서만」 보므로 그 행은 **런타임에서 무효**이고 e2e 로는
영영 반증되지 않는다. 2026-09-09 에 통보 **181·189** 두 번 같은 자리에서 났다. 그 spec 에 이미 같은
모양의 단언 둘이 서 있다 — 옆에 한 줄 더하면 된다.

⚠ **이 절은 I-21 에서 나왔지만 모든 슬라이스에 걸린다** — 특히 ⑷·⑸ 와 권한 항은 원장·수량·인가를
다루는 모든 슬라이스에 걸린다.

### 6-4. ⭐ 2026-09-09 추가 — **FK 를 더했으면 «남의» `*_REFERRERS` 도 같이 고쳐라** (main 이 빨강인 채로 여러 PR 이 얹혔다)

`*_REFERRERS`(`src/mdm/*/*.service.ts` · `src/app/access/role.service.ts`)는 시험 픽스처가 아니라
`countReferences()` 가 그대로 `count(*)` 항으로 펴는 **운영 상수**다(`src/common/master/reference-count.ts:27-33`).
빠진 표는 `referenceCount` 에 안 세어지고, 그 값이 `editability.codeEditable` · `reason` 으로 **클라이언트에 나간다**.

**실사고.** 어느 레인이 `maintenance.collection_channel*` · `app.notification_subscription_recipient.role_id`
FK 를 더한 마이그를 병합했는데 **자기 레인이 안 쥔 상수 셋을 아무도 갱신하지 않았다**. 그 표만 가리키는
공정·설비·역할이 `codeEditable: true` · `EDITABLE` 로 응답했다(#491 이 둘, #494 가 나머지 하나를 닫았다).

> **마이그레이션이 새 FK 를 만들면, 그 FK 가 «가리키는» 마스터의 `*_REFERRERS` 에 한 줄을 더한다.**
> 그 파일을 내가 만들지 않았어도 **같은 PR 에서** 고친다 — 상수 한 줄이라 충돌이 나도 자명하다.
> 찾는 법: `grep -rn "_REFERRERS" src/` → 새 FK 의 `confrelid` 표를 쥔 상수.

⚠ ⭐ 「참조 목록이 DB 의 FK 와 정확히 같다」 e2e 가 이걸 **잡긴 한다**. 다만 그 스펙들은 대개 내 PR 이 안 건드린 파일이라
**병합 직전 전수 회귀를 돌릴 때에야** 드러난다(§6-1) — 그때는 이미 여러 PR 이 얹힌 뒤다.

#### ⭐⭐ 일반화 — **공용 레지스트리를 늘리면 그것을 지키는 «불변식 표»도 같이 늘려라**

같은 사고가 **하루에 세 번** 났다. `*_REFERRERS` 는 그중 하나일 뿐이다.

> **레지스트리에 줄을 더할 때는 「이 줄을 지키는 표가 어디 있는가」를 먼저 찾아라.**

> «전건 열거» API)를 부르는 spec 을 grep 한다. **그런 spec 이 있다는 것 자체가 「여기 표가 있다」는 뜻이다.**

⛔ **반대 방향도 같다 — 표가 «남이 만든» 파일이어도 그 줄은 네가 채운다.** 위 표의 마지막 줄이 그 모양이다:
`X-Worker-No` 판정을 하나 더 쓰거나 `mdm.worker` 를 새로 읽는 순간, `worker-no.spec.ts` 가 빨개진다.
**그 spec 에 한 줄을 더하는 것이 네 PR 의 일이다** — 갈래(형식만 / 실재까지 / `worker_id`)를 고르는 판정은
그 자리를 만든 사람만 할 수 있다.

⭐ **이 부류는 「내 파일이 아니다」가 이유가 안 된다** — 레지스트리를 늘린 쪽이 표도 채운다.
안 채우면 **내 PR 이 아니라 병합 직전 전수 회귀에서** 터지고, 그때는 이미 남의 PR 이 여럿 얹혀 있다.
