| `qtyAfter` number | ✅ | **칸 없다** | ⛔ **결손 4** |
| — | | `line_no integer NOT NULL CHECK (line_no > 0)` | 계약에 원천 0(서버가 붙인다 — 정렬 축) |
| — | | `moved_qty app.qty_t NOT NULL **CHECK (moved_qty > 0)**` | ⛔ 계약에 원천 0 · **0 을 못 담는다**(변화 없는 라인·전량 이동 잔량 0) |
| — | | `uom_id bigint NOT NULL FK` | ⛔ **계약에 원천 0** — 계약 라인에 `uomId` 자체가 없다 |

**⛔⛔ 결정적 충돌 — `ck_handling_unit_reconfiguration_distinct`**

계약의 **대표 경로가 취급 단위 «하나»짜리 사건**이다:

- `PUT /inventory/handling-units/{handlingUnitId}/contents` 는 **한 HU 의 구성을 치환**하고, 그 치환이 이벤트를 만든다(계약 description).
- 그 사건의 `handlingUnitId` 는 **하나**다 ⇒ `source = target` ⇒ **CHECK 위반으로 INSERT 가 실패한다.**
- 화면도 같은 말을 한다 — `M-04-03` §3 의 유형 셋 중 「**재구성 — 내용을 바꾼다**」가 그것이고, §5-4 는 「분할 **잔량은 원 포장 번호를 그대로 씁니다**」라 적어 **잔량 쪽이 새 HU 가 아님**을 못 박았다.

그리고 헤더 두 칸(1 source → 1 target)은 **`MERGE`(N source → 1 result)를 구조적으로 못 담는다** — `M-04-03` §5-5 가 「`HandlingUnitRepackEventLine` 의 `roleCode=SOURCE` **행들**이 그 출처를 남긴다」로 **라인 축**임을 명시했다.

**판정 — README §2 절차**

- **0단계(선례).** `plan.md` §0 **#7** 이 같은 모양을 이미 갈랐다: 계약 스키마가 실재하고 물리에 담을 데가 없으면 **「물리가 계약을 따른다」**(`Printer.status`). README §5 도 같다 — 「물리 모델과 계약이 다르면 **물리를 고친다**」. `plan.md` §0 #9 의 「기존 표 우선」은 **「기존 표로 안 되면」**이라는 단서를 스스로 달았고, 위 대조가 그 단서를 만족시킨다.
- **재사용을 억지로 세우면** 라인에 **칸 4 추가** + 헤더 NOT NULL **3 완화** + `performed_by` 유지 + **CHECK 1 삭제** + `moved_qty` CHECK 완화 = **변경 9건**이고, 그러고도 `reconfiguration_no`(채번 필요)·`reason_code`·`source/target_handling_unit_id`·`uom_id`·`moved_qty` **5칸이 영영 빈 채로** 남는다. §2 2단계 **기준 3**(스키마를 안 늘리는 쪽)으로 재도 신설(2표 · 13칸)이 더 작지 않지만, **기준 5**(새로 만드는 «개념»의 수)로는 재사용 쪽이 「뜻이 다른 칸 5개를 영구히 죽이는」 개념을 하나 더 만든다.

⇒ **표 2 신설.** `plan-uiux.md:592` 의 판정(「본길 · 헤더+라인 두 표를 만든다」)과 **일치**하고, `plan-integration.md:348`(「표가 이미 있다」)·`plan.md` §0 #9 를 **뒤집는다**. 통합자는 §12-1 표대로 셋을 고친다.

## 3. ⭐ `POST /inventory/handling-units/{handlingUnitId}:pack` — 포장 확정(심장)

계약 description 원문: 「포장 단위와 내용물 N행을 **한 트랜잭션**으로 확정한다(공유계약 B-8). **내용물이 비면 400 이다. 이미 확정된 포장은 409 다.** ⛔ 라벨·인식표 출력은 이 오퍼레이션 밖이다 … 오프라인 대상이다(공유계약 C-9). 근거: `P-02-08` §5-6」

### 3-1. 한 트랜잭션 순서

```
tx 밖  ① X-Worker-No 존재 검사 → 없으면 400 REQUIRED (§8-5)
       ② 본문 형식 검증 — contents 0건이면 400 LINE_REQUIRED · qty<=0 400 INVALID
                          · (itemId, lotId) 중복 400 UNIQUE_VIOLATION
                          · businessDate/occurredAt 형식만(저장 안 함 · §5 규칙 7)
       ③ 채번 없음 — 이 액션은 번호를 만들지 않는다
tx 안  ④ handling_unit 을 잠근다(SELECT … FOR UPDATE 대신 UPDATE … WHERE version_no 로)
          없으면 404
       ⑤ status_code === 'PACKED' 면 **409** ConflictResponse{conflictCause:'user'}
       ⑥ If-Match 가 «있으면» version_no 대조 — 어긋나면 409(conflictCause:'user')
       ⑦ FK 존재 검사 — item·lot·uom·location (없으면 400 INVALID · field 지정)
       ⑧ handling_unit_content DELETE(그 HU 전건) → INSERT N행 (전량 치환)
       ⑨ handling_unit UPDATE — status_code='PACKED'
                              · location_id = 본문에 있으면 그 값(없으면 유지)
                              · updated_by = 세션 userId · version_no = version_no + 1
       ⑩ ⛔ 재포장 이벤트를 만들지 않는다(§3-4)
       ⑪ ⛔ 원장을 부르지 않는다(§3-5)
tx 밖  ⑫ 200 HandlingUnitDetailResponse{handlingUnit, contents[]} · ETag 안 붙인다(계약 미선언)
```

- 전체를 `runIdempotent(this.idempotency, request, HttpStatus.OK, …)` 로 감싼다(`plan.md` §5 규칙 2 · `putaway-task.controller.ts:52-60` 형).
- ⛔ `runVersioned` 를 못 쓴다 — If-Match 가 **선택**이다(§1-1).

### 3-2. ⭐ `status_code` 값의 원천 — **상수 «둘»** (plan-api 초안을 뒤집는다)

**사실 넷**

1. `handling_unit.status_code` 는 `app.code_t` **NOT NULL**(baseline `migration.sql:1244`).
2. 계약이 코드 그룹을 **영영 세우지 않겠다**고 닫았다 — `x-no-code-key` 원문: 「코드 그룹을 세우지 않는다 — 이 리소스는 «전표»가 아니라 «물건»(팔레트·박스 같은 담는 그릇)이다 … 담긴 것의 진행은 `:pack` · `/contents` · `/repack-events` 가 이미 담고, 라벨 발행 여부는 boolean 축이면 충분하다 … ⚠ `P-02-08` §8-4 가 「포장 해체 화면이 없다」고 적어 뒤쪽 값이 업무에 없다 — 해체 업무가 서면 그때 세운다(A-21 · 사용자 결정 2026-09-02)」. 화면 셋이 같은 문장을 복사해 두었다(`P-02-08` §4-A · `M-04-03` §4-A · `P-04-01` L107).
3. 그런데 **계약이 「이미 확정된 포장은 409 다」를 요구한다** — 「확정됨」을 가릴 축이 데이터에 있어야 한다.
4. 그리고 **두 화면이 `statusCode` 로 목록을 거른다** — `P-04-01` L172 「`GET /inventory/handling-units?warehouseId=…&statusCode={포장 가능}`」 · `P-04-04` L175 「대기 목록 조회 | 항상 — **상태 = 라벨 발행 대기**」 + L108 「값 목록이 정해질 때까지 **자리표시 상수**를 쓴다(G-2)」.

**판정 — README §2**

- **1단계**: `:pack` 의 409 는 **본길**(모든 재호출의 결과가 달라진다)이나, 계약이 **규칙을 문장으로 줬고 값만 안 줬다** ⇒ 「계약 문자 그대로 + 문의」로 갈 수 있다(건너뛰지 않는다).
- **2단계 기준 3**(스키마를 안 늘리는 쪽): 칸은 이미 있다 — **마이그 0**.
  ⛔ `plan.md` §0 #10 의 「NOT NULL 해제(nullable)」는 **여기서 안 선다** — 계약 `HandlingUnit.required` 에 `statusCode` 가 들어 있어 널이면 응답에 실을 값이 없다(I-3 재수립 **R-9** 와 정확히 같은 모양).
- **2단계 기준 4**(값을 조용히 도출하지 않는 쪽): 상수에 **이름을 붙이고** 한 파일에 모은다.
- **개수**: 사실 3 이 **최소 2** 를 강제한다. `plan-api.md:194` 의 「고정 상수 **하나**」는 `:pack` description 의 409 문장을 안 본 초안이다 ⇒ **뒤집는다**.
  ⛔ **셋으로 늘리지 않는다** — 사실 4 의 「라벨 발행 대기」는 `M-04-03` §8 미결 2 가 **스스로 철회**했다(「⛔ 그 퇴로가 닫혔다(2026-09-03) … 중간 상태를 담는 자리는 이 칸이 아니라 **재구성 이벤트**(`/repack-events`)다」). 「포장 가능」 = `'OPEN'`, 「발행 대기」 = 「이벤트가 있는데 라벨 기록이 없다」로 화면이 푼다.

| 2 | `contents` 0건 | 400 | `LINE_REQUIRED` |
| 3 | `qty <= 0` · `businessDate`/`occurredAt` 형식 위반 | 400 | `INVALID` |
| 4 | `contents` 안 `(itemId, lotId)` 중복 | 400 | `UNIQUE_VIOLATION` |
| 5 | HU 없음 | **404** | — |
| 6 | 이미 `PACKED` | **409** | `ConflictResponse{conflictCause:'user'}` |
| 7 | If-Match 있고 어긋남 | **409** | `ConflictResponse{conflictCause:'user'}` |
| 8 | FK 미존재(item·lot·uom·location) | 400 | `INVALID` (field 지정) |

순서가 판정이다 — **1~4 는 tx 밖**(본문만 본다) · **5~8 은 tx 안**. ⚠ 6 과 7 의 순서: **「이미 확정」이 먼저**다. 확정된 포장에 낡은 토큰으로 다시 쏘면 「다시 읽어 오면 풀린다」(409 stale)가 **거짓말**이 되기 때문이다 — 재로드해도 안 풀린다. 단위 테스트로 못 박는다.

### 3-4. ⭐ 재구성 이력 행을 만드나 — **만들지 않는다**

- 계약이 이벤트를 **`PUT …/contents` 에만** 걸었다(그 description 과 `HandlingUnitRepackEvent` description 둘 다 「이 **치환**은 …」). `:pack` description 에는 이벤트 이야기가 **한 글자도 없다**.
- `HandlingUnitRepackEvent` description 이 반대 방향까지 못 박았다 — 「**신규 생성분(신규 발번)은 이 이벤트가 아니라 `POST /inventory/handling-units` 가 별도로 만든다**」.
- `:pack` 은 「빈 포장을 내용물과 함께 «닫는» 첫 채움」이라 「재구성」이 아니다(`:pack` `x-internal-note`).
- §2 2단계 **기준 1**(재고·원장·상태를 «덜» 쓰는 쪽) · **기준 3**.

⇒ `:pack` 은 `handling_unit_repack_event` 를 **0행** 만든다. 뒤집혀도 싼 쪽이다(나중에 추가는 호환 · 지우기는 이력 손실).

### 3-5. ⭐ 원장을 부르나 — **부르지 않는다**(`plan-integration.md:180` 의 ⚠ 미정을 닫는다)

| 실측 | 값 |
|---|---|
| `inventory_balance` 차원에 `handling_unit_id` | **없다**(§2-5 · 11칸 전수) |
| 계약 `HandlingUnitPack` 에 창고·품질상태·재고상태 축 | **없다**(`locationId` 하나뿐 · 원장 라인 한쪽 끝을 못 만든다 — `PostingEndpoint` 는 `warehouseId`·`locationId`·`qualityStatusCode`·`inventoryStatusCode` 넷을 요구한다 · `posting.types.ts:2-7`) |
| 화면 | 「`handling_unit` 은 … **재고 잔액을 갖지 않는다**」(`M-01-10` §5-2:161) · `P-02-08` §5-6 이 그린 트랜잭션은 「① `handling_unit` ② `handling_unit_content`」 **둘뿐** · `P-04-01`·`P-04-04`·`P-01-02` 셋 다 원장 문장 **0건**(화면 실측) |

⇒ **§2 2단계 기준 1**(재고를 안 쓰는 쪽) 그대로. `plan-integration.md:129`(「원장 없음이 유력」)·`:348`(「원장을 만들지 않는다」)과 일치하고 **`:180` 의 「⚠ 미정」만 닫힌다.**

⚠ 그러면 `inventory_transaction_line.handling_unit_id` 는 **누가 채우나**: 오늘 채우는 곳은 **적치 하나**다 — `putaway-complete.service.ts:188`(`handlingUnitId: id(task.handling_unit_id)`) → `putaway-posting.ts:66` → `inventory-posting.service.ts:198`. I-16 은 그 칸을 **안 채운다**(원장을 안 지나므로). I-13 A4 와의 관계는 §12.

### 3-6. 멱등 · If-Match · `X-Worker-No`

- 멱등: `Idempotency-Key` 필수. 같은 키 재전송은 **첫 응답을 그대로 되돌린다**(200 · `runIdempotent(…, HttpStatus.OK, …)`). ⇒ 재전송이 409 를 만나지 않는다.
- If-Match: **선택**. 없으면 잠금 검사를 건너뛴다(오프라인 큐 · C-9). 있으면 `version_no` 대조.
- `X-Worker-No`: 400 `REQUIRED` + `mdm.worker.worker_no` 존재 확인 후 **버린다**(§8-5).

## 4. `POST /inventory/handling-units` — 취급 단위 등록(201)

### 4-1. 본문 칸 매핑

§1-3 표 그대로. `contents[]` 가 있으면 같은 트랜잭션에서 `handling_unit_content` N행을 만든다.

```
tx 밖  ① X-Worker-No 검사(400 REQUIRED) · 본문 형식 검증
       ② handlingUnitTypeCode 를 mdm.code_value(HANDLING_UNIT_TYPE) 로 대조 — 없으면 400 INVALID
       ③ ⭐ 채번 — numbering.next('HANDLING_UNIT', null, <서버 UTC 날짜>) · $transaction «밖»
tx 안  ④ parentHandlingUnitId 가 있으면 존재 확인 + 순환 검사(§4-4)
       ⑤ warehouse·location·item·lot·uom 존재 확인 — 없으면 400 INVALID
       ⑥ handling_unit INSERT — status_code = HU_STATUS_OPEN · created_by = 세션 userId
       ⑦ contents 가 있으면 handling_unit_content INSERT N행
tx 밖  ⑧ 201 + ETag(version_no=1) + HandlingUnitDetailResponse
```

### 4-2. 400 갈래

| 조건 | 코드 |
|---|---|
| `handlingUnitTypeCode` 없음/공백 | `REQUIRED` |
| 그 값이 `HANDLING_UNIT_TYPE` 에 없음 | `INVALID` |
| `parentHandlingUnitId` 미존재 | `INVALID` |
| **순환**(A→B→A · 자기 하위를 상위로) | `INVALID` |
| `warehouseId`/`locationId` 미존재 | `INVALID` |
| `contents[i]` 의 `itemId`/`lotId`/`uomId` 미존재 | `INVALID` |
| `contents` 안 `(itemId, lotId)` 중복 | `UNIQUE_VIOLATION` |
| `qty <= 0` | `INVALID`(계약 `exclusiveMinimum: 0`) |
| `X-Worker-No` 없음 | `REQUIRED` |

⚠ **404 를 선언하지 않았다** — 없는 부모/창고/위치는 위 표대로 **400** 이다(I-3·I-5 선례와 같은 가름).

### 4-3. ⭐ 채번 — `DEFAULT_PREFIX` 에 **한 줄**

`handling_unit_no` 는 `business_no_t NOT NULL UNIQUE` 인데 계약 본문에 원천이 0 이고 화면이 「MES 채번 · **자동**」이라 적었다(`P-02-08` §4-A). `app.numbering_rule` 에 `HANDLING_UNIT` 행이 **없다**(DB 실측 3행).

```ts
// src/core/numbering/numbering.service.ts DEFAULT_PREFIX
/** 규칙 미등재 — `HU-{YYYYMMDD}-{SEQ4}`(계약 example `HU-2026-000058` 은 형식만 · I-16 §4-3). */
HANDLING_UNIT: 'HU',
```

⭐ **기간 축이 문제다.** `next()` 의 `periodDate` 는 「호출자가 이미 가진 날짜」인데 **`HandlingUnitCreate` 에 `businessDate` 가 없다**(전수 실측). ⇒ **서버 시각의 UTC 날짜**를 쓴다 — I-10 `MATERIAL_RETURN`(「기간 축은 서버 시각 UTC 날짜」)과 같은 자리. ⚠ 하노이(UTC+7) **00:00~07:00 발행이 전날 번호를 받는다**(I-6 `WO-`·`MIR-` 와 같은 결함). 문의 144 · 「알려둘 것」.

⛔ 채번은 **`$transaction` 을 열기 전에** 부르고 문자열만 넘긴다(`plan.md` §3 채번 칸 · `numbering.service.ts:62-70`). 결번은 허용한다.

### 4-4. `parent_handling_unit_id` — 순환 방지는 **서버 몫**

물리 CHECK 원문(baseline `migration.sql:1250-1251`):

```sql
    CONSTRAINT ck_handling_unit_parent
        CHECK (parent_handling_unit_id IS NULL OR parent_handling_unit_id <> handling_unit_id)
```

화면이 부족분을 적었다 — 「자기참조는 막히나 **A→B→A 순환은 막지 않는다** — 서버 책임(A-9 ⓐ)」(`P-02-08` §4-A) · 「순환 중첩(A→B→A) | 서버가 막는다」(§6).

⇒ 등록 시 부모 사슬을 **위로 타고 올라가며** 자기 자신을 만나면 400 `INVALID`. 사슬 깊이 상한은 **안 둔다**(`P-04-01` §8 미결 4 「포장 계층 깊이 — 2단인가 그 이상인가」가 **미정** · §2 2단계 기준 2 로 「거부」를 고르면 열려 있어야 할 3단을 막는다 ⇒ 여기서는 **기준 1**(상태를 안 쓰는 쪽)로 상한 0). 무한 루프 방지로 **반복 200회 상한**을 두고 넘으면 500 이 아니라 400 `INVALID`.

### 4-5. `warehouse_id`·`location_id` nullable · `status_code` 초기값

- 둘 다 **nullable** 이고 계약도 `["integer","null"]` 이다. 화면이 뜻을 적었다 — 「창고·위치 | **완료 후 이동 시 채워짐**」(`P-02-08` §4-A). ⇒ **비운 채 만들 수 있다.** 서버가 기본값을 도출하지 않는다(§2 2단계 기준 4).
  ⚠ 예외적으로 `P-04-01` L106 은 「자동 — **배분 응답의 `warehouseId`** 를 그대로 보낸다 · ⛔ 비우지 않는다」라 적었는데 그것은 **클라이언트 규칙**이다 — 서버는 안 채운다.
- `status_code` 초기값 = `HU_STATUS_OPEN`(§3-2).

## 5. `PUT /inventory/handling-units/{handlingUnitId}/contents` — 구성 치환(200)

### 5-1. 전량 교체 의미

계약 `HandlingUnitContentUpsert` description: 「구성 **전체 치환** 항목. **요청에서 빠진 기존 행은 삭제한다.** 근거: 공유계약 A-5」. ⇒ `DELETE WHERE handling_unit_id = :id` → `INSERT` N행. `items` 는 required 이나 **`minItems` 가 없다** — 빈 배열이면 **전건 삭제**가 된다.

⚠ 빈 배열 허용 여부: 계약이 막지 않았고 `:pack` 만 `minItems: 1` 을 걸었다 ⇒ **허용한다**(§2 1단계 — 계약 문자 그대로). 다만 `M-04-03` §6 이 「분할 잔량 0 | ⚠ **허용** — 전량을 새 포장으로 옮기는 것도 재구성이다」라 적어 업무도 그것을 요구한다. 「알려둘 것」에 남긴다(빈 포장이 `PACKED` 인 채로 남는다).

### 5-2. `uq_handling_unit_content` 와 중복 400

물리 `UNIQUE (handling_unit_id, item_id, lot_id)`. 요청 배열 안에 같은 `(itemId, lotId)` 가 둘이면 **DB 에 닿기 전에** 400 `UNIQUE_VIOLATION`. 화면이 같은 규칙을 적었다 — 「같은 LOT 이 만남(합병) | ⚠ **합친다** + 「80 에 60 을 더해 140 이 됩니다」」(`M-04-03` §6). ⛔ **서버가 합치지 않는다** — 합치는 것은 클라이언트가 보내기 전에 한다(계약이 `qty` 를 「담긴 양」으로 정의했고 배열은 치환이다 · §2 2단계 기준 4 「조용히 도출하지 않는다」). 문의 143 ⓑ.

### 5-3. ⭐ 재구성 이력을 남기나 — **언제나 남긴다**(리뷰 자리 ③)

계약 description 원문: 「⭐ 결정 13 되살림(2026-08-30) — **이 치환은 서버가 `HandlingUnitRepackEvent`(헤더) + Line(수량 변경 전/후)을 함께 기록한다.** 신규 발번·새 라벨 대상은 이 이벤트가 아니라 `POST /inventory/handling-units`(P-04-04)가 별도로 만든다.」 조건절이 **없다**.

**이벤트 한 건의 모양**(치환 1회 = 헤더 1행)

| 칸 | 값 |
|---|---|
| `repack_type_code` | ⭐ **계약이 본문에 안 준다**(§10-1 #3) → **`'RECONFIGURE'` 고정** |
| `performed_by` | 계정 세션 `userId`(`plan.md` §5 규칙 9 「주체는 계정 세션」) |
| `occurred_at` | **서버 시각**(계약 본문에 `occurredAt` 이 없다 — `:pack` 과 다르다) |

**라인 생성 규칙** — 치환 «전» `handling_unit_content` 를 읽어 `(item_id, lot_id) → qty` 맵을 만들고, 치환 «후» 맵과 합집합을 돈다.

| 경우 | `role_code` | `qty_before` | `qty_after` |
|---|:-:|---|---|
| 전에 있었고 후에도 있다 | `RESULT` | 전 qty | 후 qty |
| 전에 없고 후에 생겼다(최초 채움 포함) | `RESULT` | **0** | 후 qty |
| 전에 있었고 후에 빠졌다 | `SOURCE` | 전 qty | **0** |

- ⛔ **변화 없는 줄도 남긴다**(`qty_before === qty_after`) — 계약이 「변화가 있을 때만」을 안 적었고, 「그 시점의 구성 전체」가 이력으로 더 쓸모 있다. §2 2단계 **기준 4**(조용히 도출·생략하지 않는다).
- `line_no` 는 1부터 — 정렬은 `(role_code DESC, item_id, lot_id)` 로 안정화한다(`SOURCE` 가 위).
- ⛔ **`MERGE`/`SPLIT` 을 서버가 추론하지 않는다** — 계약이 유형을 본문에 안 받는다. 문의 143 ⓐ.
- ⛔ 다른 HU 를 건드리지 않으므로 라인의 `handling_unit_id` 는 **전부 경로의 그 HU** 다. `M-04-03` 이 그리는 「합병」(여러 원 포장)은 클라이언트가 **PUT 을 여러 번** 쏘는 모양이 되고, 그러면 이벤트도 여러 건이 된다 — 계약이 여러 HU 를 한 요청에 담는 자리를 안 줬다. 문의 143 ⓐ.

### 5-4. If-Match 는 **부모 버전**

계약 description 이 못 박았다(§1-1 인용). ⇒ `handling_unit.version_no` 와 대조. 선택이라 없으면 건너뛴다.

### 5-5. 재고를 옮기나 · `version_no` 를 올리나

- **재고**: 안 옮긴다 — §3-5 와 같은 근거(`inventory_balance` 에 `handling_unit_id` 차원 0 · 계약 본문에 원장 축 0 · `M-04-03` §5-3 「**LOT 은 그대로이고 어느 포장에 들었는지만 바뀐다**」 · §5-6 「Lot Status 판정 | ⛔ **쓰지 않는다** — 포장 구성만 바꾼다」). §2 2단계 기준 1.
- **`version_no`**: **올린다**(+1) — If-Match 의 잠금 단위가 부모이므로 자식을 바꿨는데 부모 토큰이 안 늙으면 두 치환이 서로를 덮는다. ⛔ `updated_at`/`updated_by` 도 함께.
- **`status_code`**: **안 옮긴다** — 치환은 확정도 해제도 아니다(§3-2 · 「해체 업무가 서면 그때」).
- 응답: `HandlingUnitContentListResponse{items[]}` — **ETag 안 붙인다**(계약 미선언).

### 5-6. 400·409 갈래

| 조건 | 봉투 | 코드 |
|---|---|---|
| `X-Worker-No` 없음 | 400 | `REQUIRED` |
| `items` 없음(키 자체) | 400 | `REQUIRED` |
| `(itemId, lotId)` 중복 | 400 | `UNIQUE_VIOLATION` |
