## ⭐ 0-재수립. 3관점 재검토 결정 (2026-09-06) — **아래 본문과 다르면 이 절이 정본이다**

### R-1. 코어 «자리» — `src/core/approval/` + `src/app/approval/` 둘로 가른다 (통합 G-1 · 셋 동의)
`server-architecture.md` §1 「도메인이 다른 도메인의 service 를 부르지 않는다. 공유가 필요하면 그것은 `core` 다」. 9 상신자가 7 도메인이라 `src/app/` 에 두면 정면으로 걸린다.
- `src/core/approval/` — `ApprovalModule`(`CoreModule` 형제 — `document-state`·`inventory-posting` 과 같은 층) · `ApprovalService`: `selectRoute` · `expandSteps` · `currentStep` · `approve` · `reject`. I-2 가 `request`·`assertNoOpenRequest`·`assertApproved` 를 여기에 더한다.
- `src/app/approval/` — 컨트롤러 12건 · 결재선 CRUD 서비스 · 결재함 조회·매퍼(app 전용).

### R-2. 시그니처 정정 — `approvalTypeCode` 축 · `expandSteps`·`currentStep` 은 I-1 코어 (통합 G-2 · 조건 1 · API §5 · UI/UX §5-b)
- `goods_issue` 한 표가 `GOODS_ISSUE_DISPOSAL`(I-4)·`GOODS_ISSUE_CANCEL`(I-5) 두 유형을 탄다. 유형을 안 보면 「취소 요청이 승인된 출고」를 `:post` 가 품의 승인으로 읽는다 — 원장 오전기. ⇒ I-2 의 `assertNoOpenRequest`·`assertApproved` 는 `(targetTypeCode, targetId, approvalTypeCode)` 셋으로 조회한다. **정본은 언제나 다형 축**(R-3).
- `expandSteps(tx, approvalRouteId, approvalRequestId)` — 결재선 → `approval_step` 전개(`step_no` 1..N · `approver_id ← approver_user_id`). I-1 에 둔다: `approve` 의 순차 판정과 I-2 `request()` 의 생성이 한 규칙이어야 조용히 어긋나지 않는다. e2e 픽스처도 이것으로 만든다(R-8).
- `currentStep(steps)` — 「`step_no` 오름차순 첫 미결 단계」. 결재함의 `currentStepNo`·`isMyTurn`·`isCurrent` 와 코어의 `NOT_YOUR_TURN` 판정이 **같은 함수**다. 그래서 코어 PR 이 맨 앞이다(R-9).
- `selectRoute(…, businessUnitId)` — **I-2 의 P/O 만 전표 값을 주고 나머지 8자리는 `null`(공통본)** 을 준다. `reasonCode → business_unit` 매핑은 계약에도 물리에도 없다(문의 022). I-4 가 매핑표를 지어내지 않는다.
- 트랜잭션: `runIdempotent` 는 자기 `tx` 를 work 에 넘기지 않는다(`master-write.ts:31`). **app 서비스가 `prisma.$transaction` 을 열고 코어에 `tx` 를 넘긴다.** 코어가 `tx` 를 받는 이유는 I-2 상신이 «자기 트랜잭션 안»에서 부르기 때문.

### R-3. 정본 연결 — FK 는 업무 승인만, 취소·특수 승인은 다형 축 (통합 G-3 → `plan.md` §5 #12)
문서의 `approval_request_id` FK 는 **업무 승인 하나만** 담는다(`PURCHASE_ORDER`·`GOODS_ISSUE_DISPOSAL`·`INVENTORY_ADJUSTMENT`). `*_CANCEL`·`IQC_SKIP`·`PRODUCTION_RESULT_CORRECT` 는 FK 를 쓰지 않는다 — 정본은 `approval_request.(target_type_code, target_id, approval_type_code)`. 안 박으면 I-5 가 `goods_issue.approval_request_id` 를 취소 요청으로 덮어 I-4 흔적이 사라진다(되돌리려면 데이터 복구).

### R-4. `PUT …/steps` — **선례를 따른다: `runVersioned`** (§5-3 셋째 항목 폐기 · API §6 #1)
`PUT /mdm/items/{itemId}/bu-item-maps` 등 자식 치환 6자리가 계약에 ETag 선언이 없는데도 `runVersioned` 로 부모 버전을 올리고 ETag 를 내린다(`item-detail.service.ts:184 withBumpedItem`). §2 0단계 — 판단 아님. ETag 를 안 내리면 화면이 연속 저장마다 부모 GET 을 다시 해야 한다. 계약이 헤더를 선언 안 한 것은 **「알려둘 것」**(R-11). e2e 이름: `단계 — PUT …/steps 는 부모 version_no 를 올리고 새 ETag 를 준다`.

#### ⛔ `inProgressCount` — 셀 연결 칸이 없다 (핵심 결손)

- 계약: 「이 결재선으로 진행 중인 요청 수. 결재선을 고쳐도 이 요청들은 옛 결재선으로 끝난다 — 화면이 그것을 보인다(공유계약 J-9)」 · **`required`**
- 실측: `app.approval_request` 에 `approval_route_id` 도 `business_unit_id` 도 **없다**(`grep approval_route_id prisma/schema.prisma` → `approval_route`·`approval_route_step` 만).
- ⇒ 「이 결재선으로」를 정확히 셀 수 없다.

**§2 절차 판정**
- **0단계 선례**: 없다. 다른 파생 카운트(`Notice.acknowledgedCount`)는 실재하는 연결 표를 센다.
- **1단계**: `approvalTypeCode` 축으로만 세면 **활성 결재선이 그 유형에 하나뿐일 때는 정확**하고, 사업부 지정본과 공통본이 함께 활성일 때만 둘이 같은 수를 보인다 → **가장자리**.
- **2단계**: 기준 1 해당 없음(원장 안 씀) · 기준 2 해당 없음(허용/거부 갈래가 아님) · **기준 3 「스키마를 안 늘리는 쪽」이 먼저 걸린다** → **칸을 더하지 않고 `approval_type_code` 로 센다**.
- **3단계 흔적**: ① 서비스에 주석 `// 설계 미정 — 문의 018` ② 단언 테스트 이름에 「⚠ 유형 축 근사」 명기 ③ 요청서에 「2단계 기준 3 으로 골랐음」.
- **되돌릴 때**: `ALTER TABLE app.approval_request ADD COLUMN approval_route_id bigint REFERENCES app.approval_route(...)` 한 줄(추가·nullable) + 집계 `WHERE` 교체. 되돌림 비용이 싸다는 것이 이 선택의 근거다.
- ⭐ 이 판정 덕에 **마이그레이션이 A6 하나로 유지되고 「차이가 크다」 조건 1 을 피한다**.

### 2-6. 마이그레이션 SQL 초안 — **A6 하나. forward-only · 추가만.**

```sql
-- I-1 선행 커밋 · A6 (plan.md §4)
-- 계약: 「같은 (approvalTypeCode, businessUnitId) 로 활성 결재선이 이미 있으면 400 이다 —
--        활성 결재선은 한 벌이어야 고를 것이 하나로 정해지므로 계약이 막는다」(POST /app/approval-routes)
-- ⚠ business_unit_id 가 nullable 이라 COALESCE 로 접는다. 같은 형태의 선례가
--    uq_user_data_scope 다(data_model_v4 — COALESCE(legal_entity_id, 0) …).
CREATE UNIQUE INDEX uq_approval_route_active
    ON app.approval_route (approval_type_code, COALESCE(business_unit_id, 0))
    WHERE is_active;
```

- **삭제·NOT NULL 조임 0건** → 두 릴리스 규칙(컬럼·테이블 삭제) 미해당 → 멈춤 조건 아님.
- **`schema.prisma` 는 안 고친다** — Prisma 는 부분 유일 인덱스를 표현하지 못한다. 선례: `uq_worker_lease_active`·`uq_warehouse_layout_active` 도 `schema.prisma` 에 없다(실측). ⇒ `prisma generate` 불필요, `@default` 변경 없음.
- 이름은 `uq_*` 관행. **FK 가 아니므로** 「FK 제약 이름은 Prisma 기본형」 규칙 대상이 아니다.
- ⚠ **적용 전 중복 확인**이 필요하다 — 활성 중복이 이미 있으면 `CREATE UNIQUE INDEX` 가 실패해 마이그레이션이 멈춘다. `seed.ts` 에 `approval_route` 행이 **0건**(실측)이라 로컬·CI 는 안전하고, 하노이 개발 서버는 적용 직전 다음으로 센다:
  ```sql
  SELECT approval_type_code, COALESCE(business_unit_id,0) bu, count(*)
    FROM app.approval_route WHERE is_active GROUP BY 1,2 HAVING count(*) > 1;
  ```
  마이그레이션이 든 PR 이라 **병합 전 한 줄 보고**(README §1-5).

## 3. 코어 인터페이스 — `src/core/approval/` (컨트롤러·CRUD·매퍼는 `src/app/approval/`)

⛔ 재수립 R-1 — 처음 안(`src/app/approval/` 한 곳)은 `server-architecture.md` §1 「도메인이 다른 도메인의 service 를 부르지 않는다. 공유가 필요하면 그것은 `core` 다」에 걸린다. 코어는 `src/core/approval/`, 계약 경로 `/app/…` 의 컨트롤러는 `src/app/approval/`.

### 3-1. 시그니처 (재수립 R-2 반영)

```ts
/** src/core/approval/approval.service.ts — 결재선 선택·단계 전개·순차 결재 판정. 뒤의 9 상신 오퍼레이션이 이것만 부른다. */
@Injectable()
export class ApprovalService {
  /**
   * ① 사업부 지정본이 전 사업부 공통본을 이긴다 ② 그러고도 둘 이상이면 400 ROUTE_AMBIGUOUS.
   * 0건이면 400 ROUTE_NOT_FOUND. 단계 0개인 결재선도 ROUTE_NOT_FOUND 로 본다.
   * businessUnitId: I-2 의 P/O 만 전표 값. 나머지 8 상신자는 null(공통본) — 설계 미정, 문의 022.
   */
  selectRoute(tx: Tx, approvalTypeCode: ApprovalTypeCode, businessUnitId: bigint | null):
    Promise<{ approvalRouteId: bigint; steps: RouteStep[] }>;

  /** 결재선 → approval_step 전개(step_no 1..N · approver_id ← approver_user_id). I-2 request() 와 e2e 픽스처가 부른다. */
  expandSteps(tx: Tx, approvalRouteId: bigint, approvalRequestId: bigint): Promise<void>;

  /** step_no 오름차순 첫 미결 단계. 결재함 currentStepNo·isMyTurn·isCurrent 와 NOT_YOUR_TURN 판정이 이 하나를 쓴다. */
  currentStep(steps: ReadonlyArray<StepRow>): StepRow | null;

  /** 승인. 결재선에 없는 사용자면 403, 차례가 아니면 400 NOT_YOUR_TURN. 마지막 단계면 요청 상태를 APPROVED 로 옮긴다. */
  approve(tx: Tx, approvalRequestId: bigint, version: number, actor: Actor, comment?: string):
    Promise<{ detail: ApprovalRequestDetail; versionNo: number }>;

  /** 반려. comment 필수. 한 번에 요청 상태를 REJECTED 로 옮긴다. */
  reject(tx: Tx, approvalRequestId: bigint, version: number, actor: Actor, comment: string):
    Promise<{ detail: ApprovalRequestDetail; versionNo: number }>;

  // I-2 코어 PR 에서 더한다 — 셋 다 approvalTypeCode 축을 받는다(goods_issue 가 두 유형을 탄다, R-2):
  //   request(tx, { approvalTypeCode, targetTypeCode, targetId, businessUnitId, actor, reason }): Promise<ApprovalRequestRef>
  //   assertNoOpenRequest(tx, targetTypeCode, targetId, approvalTypeCode): Promise<void>
  //   assertApproved(tx, targetTypeCode, targetId, approvalTypeCode): Promise<void>
}
```
`tx` 는 app 서비스가 `prisma.$transaction` 으로 열어 넘긴다(`runIdempotent` 는 tx 를 주지 않는다).

### 3-2. 결재선 선택 규칙 (계약이 정본을 가졌다 — §2 0단계, 판단 아님)

계약 `ApprovalRoute.description` 원문:
> 「선택 규칙을 계약이 정본으로 갖는다 — ① 사업부 지정본이 전 사업부 공통본(businessUnitId=null)을 이긴다 ② 그러고도 둘 이상이면 상신이 400(code=ROUTE_AMBIGUOUS)이다. 서버가 임의로 하나를 고르지 않는다. 근거: W-06-15 §5-3 · 공유계약 B-12」

구현: `WHERE approval_type_code = ? AND is_active AND (business_unit_id = ? OR business_unit_id IS NULL)` → 지정본 있으면 그것, 없으면 공통본. 각 층에서 2건 이상이면 `ROUTE_AMBIGUOUS`.
⭐ A6 인덱스가 걸리면 각 층은 최대 1건이라 `ROUTE_AMBIGUOUS` 는 **인덱스 이전 데이터에서만** 난다. 그래도 남긴다 — 계약이 이름을 적었고, 인덱스는 나중에 지울 수도 있다.

### 3-3. 순차 결재 · 승인자 유형

| 규칙 | 계약 문장 | 구현 |
|---|---|---|
| 순차 강제 | 「앞 단계가 전부 승인이 아니면 400(code=NOT_YOUR_TURN)이다」 | `approval_step` 을 `step_no` 오름차순으로 읽어 첫 미결 단계를 찾고, 그 단계의 `approver_id` 가 주체가 아니면 `NOT_YOUR_TURN` |
| `isCurrent` | 「앞 단계가 전부 승인이고 이 단계가 아직 결재되지 않았을 때만 참이다」 | 같은 계산의 부산물 |
| 승인자 유형 | 「USER 외의 값은 400(code=APPROVER_TYPE_NOT_SUPPORTED)이다」 | `PUT …/steps` 검증에서 던진다. **1차는 USER 만**(요구서 §1-1 ①) |
| 반려 즉시 종결 | 「번복은 새 요청이다」 · `statusCode` 3값뿐 | 한 단계라도 `REJECTED` 면 요청은 `REJECTED` — 뒤 단계를 만들지 않는다 |

### 3-4. ⭐ J-8 — 승인이 대상 문서를 «실행»하지 않는다. 그럼 후속을 어떻게 알리나?

계약: 「⭐ 승인은 자물쇠를 풀 뿐 실행하지 않는다. 이 오퍼레이션은 approval_request 의 상태만 바꾸고 전기·출고·조정 반영은 대상 화면이 별도로 한다」

**두 갈래 중 「상태 조회」를 택한다 — 콜백을 만들지 않는다.**

| 갈래 | 판정 |
|---|---|
| 콜백/훅(승인 시 대상 도메인 서비스를 부른다) | ⛔ **채택 안 함**. ① 계약이 「실행하지 않는다」로 못박았다 ② 도메인 간 service 호출 금지(`server-architecture.md` §1 · `plan-integration.md` §8 위험 8 과 같은 형태) ③ 사용처가 9곳이라 훅 등록표가 사실상 두 번째 라우팅표가 된다 |
| **상태 조회**(대상 도메인의 `:post` 가 승인 상태를 «읽고» 자물쇠를 판정) | ✅ **채택**. 계약이 이미 길을 적었다 — 「업무 화면이 「이 문서의 승인 상태」를 찾을 때 `GET /app/approval-requests?targetTypeCode=&targetId=` 에 싣는다」. 서버 안에서는 같은 질의를 `ApprovalService` 가 함수로 낸다 |

⇒ I-2 이후 호출자가 쓸 넷째 함수를 **여기서 이름만 정해 둔다**(구현은 첫 사용처 슬라이스):
```ts
/** 「승인 전이면 400」의 자물쇠. APPROVAL_REQUIRED / APPROVAL_IN_PROGRESS 를 가른다. */
assertApproved(tx, targetTypeCode, targetId): Promise<void>;
```
⛔ **I-1 에서 만들지 않는다** — 사용처가 0이다(CLAUDE.md 「사용처 하나뿐인 추상화·선제적 레이어 금지」).

### 3-5. ⛔ `request()`(상신)는 I-1 에 두지 않는다 — I-2 코어 PR 로 미룬다

근거 셋 —
1. **계약에 상신 오퍼레이션이 없다.** 요구서 §7: 「**요청 생성**(`:request-approval`) | 각 도메인 계약 소관 — 대상이 무엇이냐에 따라 검증이 다르다」 · 「⛔ **`/app/approval-requests` 에 `POST` 를 신설하지 않는다**」. ⇒ I-1 12건 중 요청을 만드는 것이 **0건**이다.

### 4-2. `transitions.ts` 등록 줄

```ts

   * 결재 요청 진행. 값은 시드 `APPROVAL_REQUEST_STATUS`(PENDING·APPROVED·REJECTED · isSystemOwned).

      from: ['PENDING'],
```

### 5-2. 멱등 — 쓰기 7건 전건

| 자리 | 감싸는 법 | 성공 상태 |
|---|---|---|
| `POST /app/approval-routes` | `runIdempotent(..., HttpStatus.CREATED, …)` + `setEtag` | 201 |
| `PUT …/{id}` · `:activate` · `:deactivate` · `:approve` · `:reject` | `runVersioned(...)` (멱등 + `If-Match` + 새 ETag) | 200 |
| `PUT …/{id}/steps` | **`runIdempotent` + `ifMatchVersion(request)` 직접** — §5-3 | 200 |

조회 5건에는 붙이지 않는다.

### 5-3. `If-Match` 6건 · ETag 8건 — ⛔ 함정 하나

- `If-Match` **필수 6**(선택 0). 가드 `requirement()` 판정을 그대로 믿고 조이지도 풀지도 않는다.
- `PUT …/{id}/steps` 의 토큰은 **부모 `approval_route.version_no`** 다(계약 원문 인용은 §1-3). `plan.md` §5 #3 「`PUT .../lines` 는 부모 버전」과 같은 형태.
- ~~`runVersioned` 를 `PUT …/steps` 에 쓰면 안 된다~~ → **재수립 R-4 로 뒤집혔다.** 자식 치환 선례(`item-detail.service.ts:184 withBumpedItem`)가 계약 미선언에도 `runVersioned` 로 부모 `approval_route.version_no` 를 올리고 ETag 를 내린다. 그대로 따른다(두 관리자의 동시 치환 중 늦은 쪽이 409). 계약 미선언은 「알려둘 것」.
- ETag 8건은 `setEtag(response, versionNo)` — 본문 필드로 내리지 않는다(A-4).

### 5-4. `@Contract` · 봉투

- 12건 전건 `@Contract('METHOD /path')`.
- 409 봉투는 **기본 `ConflictResponse`** — 도메인 전용 넷(`Production`·`Quality`·`Shipment`·`StockReinstatement`)은 이 슬라이스에 **해당 없다**(실측: 이 12건의 409 는 전부 `#/components/schemas/ConflictResponse`).
- 404 는 `NotFoundException`(봉투 `ErrorResponse`). 422 없음.
