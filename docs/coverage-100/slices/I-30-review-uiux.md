# I-30 독립 계획 리뷰 · UIUX

계획 §0의 5축과 지정 화면 3개를 전부 읽고 W-05-05·P-02-02·고정 계약·기존 구현을 대조했다. 다른 관점 리뷰는 읽지 않았다. 적용: `design:design-critique`의 사용성·일관성·구체적 수정 제안, `crefle-agent-skills:coding-rules`의 TypeScript·커밋 규칙. 실측 부록의 사실을 뒤집지 않아 재측정·DB 접근·게이트 실행은 없다. **계획 수정 필요이며 코드 리뷰 승인이 아니다.**

## 놓친 경계와 근거

### U1 · 원인 유보는 맞지만 ‘품질 마스터를 쓰면 해소’가 아니다

- 근거: `contracts/equipment-05설비툴.json:3315,3507,3525`는 **mdm.cause_code 행 식별자·공통코드 금지**다. `contracts/mdm-기준정보.json:6735,18645`의 선택 API는 품질용이다. `W-05-04-설비고장상세처리.md:79,123,177,195`는 품질 사용 금지·빈 목록 비활성·완료 차단을 정한다.
- 왜: 필수 원인이 없는 O9의 모든 성공 요청에 걸리는 본길이다. 화면의 공통코드 구상도 고정 계약의 대체 근거가 되지 않는다. 다만 서로 다른 도메인의 마스터를 가리키므로 이것만으로 두 API 계약이 양립 불가능하다고 확정하지 않는다.
- 수정안: O9 유보·핸들러 미등록을 통합 결정으로 남긴다. O7은 `causeCode` 생략/명시 null과 메모 저장을 계속 허용하고 비null만 명시 거부한다. **원인 선택 불가와 메모 저장 불가를 같은 제한으로 표시하지 않는다.**

### U2 · Major — UTC 날짜로 ‘오늘의 최신 점검’을 보장할 수 없다

- 근거: `I-30.md:237,243`은 기간 필수+UTC 하루를 고정한다. `P-02-02-작업전점검이력확인통제.md:61,165,175,177`은 오늘 도래한 유형의 주기 내 최신 기록을 본다. `CLAUDE.md:35`는 공장 로컬을 `plant.timezone_code`로 풀도록 한다. 기존 UTC 선례는 **공장 축이 없는 조회**라는 이유다(`src/logistics/goods-issue/goods-issue-query.service.ts:108`).
- 왜: 하노이 `2026-09-07T00:30:00+07:00`는 UTC 9월 6일이다. From=To=9월 7일이면 당일 정상 점검이 빠진다. 날짜를 하루 넓혀 size=1로 받는 것도 현재 주기 밖의 더 최신 기록을 고를 수 있어 일반 해법이 아니다. 이는 조회가 생산 통제의 근거가 되는 본길의 의미다.
- 수정안: 기간 필수·미발행 예외는 계약 `:28,57,119`대로 유지하되 **UTC=공장 하루라는 승인을 철회**한다. 날짜 의미를 문의하고 조회 PR의 R에 결정한다. 공장 하루로 정하면 설비→공장 timezone을 써야 하며 고정 +07·서버 TZ로 도출하지 않는다. 미정 동안 P-02-02 연계 완료를 주장하지 않는다.
- 추가 누락: 최신 판정 호출은 equipment/type/주기/page=1/size=1로 좁히되 **overallResultCode를 보내지 않아야** 한다. PASS 필터 후 최신을 고르면 오래된 PASS가 최신 FAIL을 가린다(`contracts/equipment-05설비툴.json:97,119`; P-02-02 `:175,177`). 일반 목록의 판정 필터 기능은 유지한다.

### U3 · Major — 다른 귀속의 같은 키를 성공 재생하지 않는다

- 근거: `I-30.md:334,468`은 사번 변경에도 기존 응답을 재생한다. `contracts/equipment-05설비툴.json:3012`는 그 쓰기의 귀속을 사번으로 지정하며 `W-05-04-설비고장상세처리.md:81`은 처리자를 로그인 사용자로 정한다. 코어는 `appUserId`를 기록하지만 재생 비교는 지문뿐이다(`src/common/idempotency/idempotency.service.ts:73,111`).
- 왜: 작업자 B가 같은 키·본문으로 보낸 입력에 A의 사번을 담은 201이 돌아오고 큐가 성공 처리될 수 있다. 관리웹 actor 변경도 앞 사람의 성공으로 응답한다. worker 필수 검사가 콜백 안에만 있으면 같은 키 재생에서 사번 누락조차 검사하지 않는다(`I-30.md:318,347`).
- 수정안: 공용 코어 변경 없이 지문 재료에 인증 actor와 O3/O6의 **귀속 사번 원문**을 포함한다. 사번 필수·길이는 재생 전 검사하고 존재 확인은 최초 업무 tx에서 한다. 같은 키의 다른 actor/사번은 기존 409 user로 거부·기존 귀속 불변. If-Match는 지문에 넣지 않아 정상 재시도는 첫 결과를 재생한다. I-28 초안의 actor 분리도 같은 선례다(`.backend-dev/lane-b/I-28-draft.md:263,271`).
- 절차: 다른 actor/사번인 특정 입력은 README §2 가장자리→① 새 업무 쓰기 없음→② 명시 거부다. O3/O6의 409 미선언 문의는 별도로 유지한다. 지문 보강은 기존 실측값 변경이 아니라 I-30 호출부의 수정이다.

### U4 · Major — 계정 없는 작업자의 201은 로그인 생략 검증이 아니다

- 근거: `I-30.md:133,135,461,487`의 worker 계정 부재는 맞지만 `src/auth/authentication.guard.ts:16,42`는 계정 세션 없으면 401이다. `src/auth/terminal-token.ts:11`도 단말 토큰이 인증을 대체하지 않는다고 명시한다. 화면은 로그인 없이 사번 입력이다(`M-05-01-설비점검입력.md:30,85`; 계약 `:3012,3013`).
- 왜: 권한 있는 다른 계정의 쿠키를 붙인 테스트는 worker→계정 연결이 없어도 귀속 가능한지만 입증한다. 세션이 없는 모바일 전송은 서비스까지 못 오므로 `reported_by=null` 성공 경로는 현 가드 아래 도달하지 않는다.
- 수정안: E-I12/E-B11에 **별도 인증 계정 세션+계정 없는 worker**를 명시한다. 세션 없음/단말 Bearer만 있음은 현재 401을 별도 기록한다. 기존 문의 054에 I-30 두 모바일 쓰기의 영향을 인계하고 로그인 생략은 미해소 본길로 남긴다. 이 리뷰를 이유로 공용 인증 우회나 사번 계정 생성은 추가하지 않는다.

### U5 · Major — 메모 저장 뒤 처리 시작에는 새 상세 GET이 필요하다

- 근거: `contracts/equipment-05설비툴.json:506,2992`는 상세 ETag를 다음 If-Match에 담게 하고 쓰기 응답 `:561,749`에는 ETag가 없다. `I-30.md:300`은 집계가 필요할 때만 재조회를 설명하며 `:377,378`은 매 쓰기 버전을 올린다. 화면에는 연속 처리 입력/전이가 있다(`W-05-04-설비고장상세처리.md:178,179,198`).
- 왜: GET(v1)→메모 PUT→start(옛 v1)는 사용자 한 명이어도 409다. 쓰기 응답의 목록형 집계를 상세 화면 전체에 덮으면 열린 비가동 경고까지 사라진다.
- 수정안: 새로운 후속 쓰기 전에는 상세 GET으로 ETag와 집계를 갱신하는 호출 흐름을 명시한다. `GET→PUT(메모)→GET→start→GET`을 기본 체인으로 적고 쓰기 응답에서 버전을 추정하지 않는다. 실패/409에서 입력 메모를 보존하고 재조회로 새 시도와 같은 키 재시도를 구분하도록 클라이언트에 인계한다.

### U6 · 검증 보강 — 오프라인 허용과 필수항목 검증 책임을 분명히 한다

- 근거: `M-05-01-설비점검입력.md:128,164,181`은 자동 판정 덮기 금지·필수항목 전건을 요구하면서 `:218,257`은 옛 부여/기준 입력을 허용한다. 요청에는 resultCode·measuredValue만 있고 기준/필수집합/버전은 없다(`contracts/equipment-05설비툴.json:3123,3236`). `I-30.md:348,350`은 최신 마스터 재판정·필수집합 검사를 하지 않는다.
- 판정: 받은 라인 판정을 보존하는 방향은 유지한다. 그러나 **빈 lines 거부가 필수라인 완결성 검증은 아니다.** 계획대로면 일부 필수항목을 뺀 비어 있지 않은 PASS 요청도 서버는 구분하지 못한다. I-11도 판정을 재검증하지 않는다(`src/production/precheck-decision/precheck-decision.service.ts:100`).
- 수정안: 현재 마스터 검사로 오프라인 정상 입력을 막지 말고, 단말이 캐시한 effective 항목의 필수검사·측정 자동판정을 책임진다고 명시한다. 서버는 전송 판정 보존/종합 합성/빈 라인/FAIL 헤더 비고까지만 보장한다. 온라인 조작과 정상 옛 기준을 서버가 구별할 근거가 없다는 한계를 문의에 남긴다. 유형코드 활성 검사는 별도 현행 거부 경계(`I-30.md:349`)이며 ‘마스터 변경 전부 허용’이라고 넓히지 않는다.
- FAIL 비고는 **헤더**가 필수이고 라인 비고는 권장이다(`M-05-01-설비점검입력.md:87,97`). 라인 비고만 채운 FAIL은 헤더 REQUIRED, PASS의 비고 누락은 성공으로 고정한다. 조회의 현재 itemName/judgeMethodCode는 당시 기준 스냅샷이라고 표시하지 않는다(`I-30.md:95`).

### U7 · 표시 보강 — null·0을 ‘없음’으로 읽으면 연결과 경고를 잃는다

- 근거: `I-30.md:283,298,300`은 다중 지시/null, 소수 분/null, 목록 count=0을 선택한다. 계약 `:3347`은 발행하면 연결됨, `:3417,3425,3430`은 상세 전용 집계를 정한다. `W-05-04-설비고장상세처리.md:83,136,197`은 연결·지시 없는 완료 구분·열린 비가동 경고를 소비한다.
- 판정·수정안: 다중 연결에서 임의 최근 1건을 고르지 않는 것과 소수 분 반올림을 지어내지 않는 방향은 유지한다. 다만 현재 응답만으로 **지시 0건과 복수건 null을 구분할 수 없다**는 부분 제한을 인계하고 null을 미발행/지시 없음 통계의 근거로 쓰지 않는다. minutes=null은 0분으로 표시하지 않고 미산출로 다룬다. 목록 count=0은 실제 비가동 없음이 아니며 상세 GET 전 경고 해제 근거가 아니다.
- 유지할 조회 흐름: 완료 목록은 `openOnly=false+기간`, 미발행 고장은 `withoutMaintenanceOrder=true`와 고장 상태 필터를 독립 전달한다(`I-30.md:260`; 계약 `:362`). 다중 지시여도 미발행 목록에서는 제외한다. 취소 지시 흔적·다형 id 충돌·직접 FK/트리거 중복 제거 기대값도 유지한다.

### U8 · 인계 보강 — notify=true가 알림 전송 성공은 아니다

- 근거: `M-05-02-설비고장현장보고.md:233,244,307`은 연결 뒤 호출·본문 먼저/사진 나중을 기대한다. `I-30.md:410,414,416`의 확정 범위는 알림 의사 저장·첨부 제외다.
- 수정안: 보고 201은 본문 접수 성공으로만 표시한다. 현재 범위에서 ‘연결되면 알림/사진이 전송된다’는 약속은 성립하지 않으므로 기능 미지원과 일시적 오프라인 대기를 구분해 클라이언트에 인계한다. 체크 기본 true·명시 false 보존·급하면 직접 연락 안내를 유지한다. 이 제한을 숨겨 커버리지 8건을 화면 전체 완료로 보고하지 않는다.
