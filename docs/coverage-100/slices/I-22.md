### 3-4. 400 · 404 · 409 갈래 — **순서가 판정이다**

| 순 | 검사 | 왜 이 자리인가 |
|:-:|---|---|
| 1 | 계약 가드(형식·required·enum·`minItems`) | 서비스가 다시 세면 **되돌려도 안 깨지는 절**(I-21 R-15) |
| 2 | 헤더 필수(`X-Worker-No`) | ⛔ 가드가 헤더를 **안 본다**(`contract-validation.guard.ts:39`) |
| 3 | 계약이 «안» 건 수량 절(`pickedQty > 0`·`allocatedQty > 0`) | ⚠ **「01 과 정반대라서」가 아니다**(R-6) — **이중 그물이 저장소 관행**이고(`picking-pick.service.ts:200`) **04 는 그물이 하나뿐이라 더 그래야 한다** |
| 4 | 존재·소유(404) | 남의 작업지시의 라인을 열지 않는다 |
| 5 | 참조 무결·널 정책(400 `INVALID`/`RANGE`) | 대상이 있어야 본문을 판정한다. **잔여 유효기간도 여기다**(R-4) |
| 6 | **업무 거부(409)** | ⭐ **재로드로 풀리는 것만** 온다 — 보류 해제·다른 출하 취소·수량 정정 |
| 7 | 코어 하한(400 `NEGATIVE_BALANCE`) | **둘째 그물** — 도달하면 6 이 새는 것이다 |

⭐⭐ **409 `message` 문구 규약(R-18 · uiux γ).** `code` 는 넷 다 `INVALID_STATE` 라 화면이 분기할 축이 없다. ⇒ **`message` 가 넷을 가르고 숫자·사유를 싣는다**:

## 5. 파생 축 셋 — **계약이 판정식을 가진 쪽 / 안 가진 쪽**

### 5-1. `shipmentProgressCode` — 6값 (⭐ **R-7·R-11 로 다시 썼다**)

한 작업지시의 라인 4수량 합으로 판정한다. **R = Σrequested · A = Σallocated · P = Σ(reserved − released) · S = Σshipped.**

| 값 | 계약 문장 그대로 |
|---|---|
| `NOT_ALLOCATED` | `A = 0` |
| `PARTIALLY_ALLOCATED` | `0 < A < R` |
| `PICKING` | `A = R` **그리고** `P < A` |
| `PICKED` | `P = A` **그리고** `S = 0` |
| `PARTIALLY_SHIPPED` | `0 < S < A` |
| `SHIPPED` | `S = A` |

⭐ 계약이 「**판정 순서는 뒤가 이긴다**」라 적었다.

#### ⛔⛔ 그대로 구현하면 `NOT_ALLOCATED` 가 **도달 불가**다 (R-7 ⓐ · R-11)

`A = 0`(그리고 `P = 0`·`S = 0`)이면:

| 값 | 식 | 참? |
|---|---|:-:|
| `NOT_ALLOCATED` | `A = 0` | ✓ |
| **`PICKED`** | `P = A ∧ S = 0` → `0=0 ∧ 0=0` | **✓ 공허참** |
| **`SHIPPED`** | `S = A` → `0 = 0` | **✓ 공허참** |

「뒤가 이긴다」이므로 답이 **`SHIPPED`** 다. ⇒ `shipmentProgressCode=NOT_ALLOCATED` 질의가 **영영 빈 목록**이고, ⛔ **초판의 「역순 if 사슬(`SHIPPED` → … → `NOT_ALLOCATED`)」이 자기 픽스처 `SR-F`·e2e L-14~L-19 와 모순**이었다.

⇒ **판정(README §2 2단계 기준 4 「값을 조용히 도출하지 않는 쪽」 + 기준 2)**:

```
if (A == 0)                      return NOT_ALLOCATED;    // ⭐ 「뒤가 이긴다」에서 벗어나는 «유일한» 예외
if (S == A && A > 0)             return SHIPPED;
if (S > 0 && S < A)              return PARTIALLY_SHIPPED;
if (P == A && S == 0)            return PICKED;
if (A == R && P < A)             return PICKING;
                                 return PARTIALLY_ALLOCATED;   // 0 < A < R
```

**+ 통보**(`W-04-02` 「상태」 드롭다운에 `NOT_ALLOCATED` 가 있는데 늘 0건이면 화면이 못 쓴다).

#### ⚠ `PICKING` 함정 — **초판이 과장했다**(R-7 ⓑ)

⛔ 「부분 배정은 **아무리 피킹해도** `PARTIALLY_ALLOCATED` 에 머문다」는 틀렸다 — **`PICKED` 는 `A = R` 을 요구하지 않는다.** 갇히는 구간은 **`A < R` 이면서 `0 < P < A`(피킹 «진행 중») 하나**뿐이다.
⭐ **출하 확정은 안 막힌다** — 진입 필터를 계약이 `pickingCompleteOnly`(수량 축)로 못박았다(「`W-04-04` 출하 처리의 진입 필터다 — 출하는 이 화면이 만들므로 `/logistics/shipments` 로는 진입할 수 없다」).
⛔ **진짜 사고는 배지다** — `W-04-04` §5-4 가 「**막힌 이유를 목록에서 보인다** — 「피킹중 ⛔」」의 원천을 **`shipmentProgressCode = PICKING`** 으로 못박았다. `W-04-01` §5-1 이 「**부분 배정이 정상이다**」라 한 **상시 구조**에서 그 배지가 안 뜨고, 운영자는 `M-04-01`(피킹을 끝내야 한다)이 아니라 **`W-04-01`(배정을 더 넣는다)로 잘못 간다.** ⇒ **통보 후보 α 신설**(초판의 「알려둘 것」으로는 부족하다).

#### ⭐⭐ TS 와 SQL **두 벌**로 구현된다 — 한 파일에 나란히 둔다 (R-14 계열 · 통합 M-4)

| 자리 | 어디서 도는가 |
|---|---|
| `ShipmentRequest.shipmentProgressCode`(응답) | **TS** 판정 함수 |
| `?shipmentProgressCode=` · `?pickingCompleteOnly` · `?shippableRemainderOnly` | ⛔ **SQL** — 페이지네이션 «전»이라 TS 함수를 못 부른다 |
| `summary.pendingInspectionCount`·`incompletePickingCount` | ⛔ **SQL** |

선례가 주석으로 남아 있다 — `disposition-rollup.ts:20-23` 「⭐ `export` 다 — 질의 필터는 페이지네이션 «전»이라 이 함수를 못 부르고 **같은 판정을 SQL 로 다시 적는다.** 문자열이 갈리면 「목록이 거른 것」과 「행이 보이는 값」이 어긋난다(I-20 R-2 형)」.
⇒ **`shipment-progress.ts` 한 파일에 TS 판정과 SQL 술어를 나란히 둔다.** 그리고 **e2e 가 두 벌을 «대조»한다** — 「6값 각각에 대해 **필터로 부른 목록**과 **응답 필드**가 같은 집합」(L-14~L-20). ⛔ 초판처럼 L-14~L-19(필드)와 L-21(필터 한 값)로 나누면 **5값이 반증 공백**이다(README §6-3 ⑵).

⚠ `P` 는 예약 롤업이고 값이 `numeric(20,6)` 이다 — **`Decimal` 로 비교**한다(`0.1 + 0.2` · e2e L-12).

### 5-2. `shippingInspectionStatusCode`(**헤더 required 칸**) · `oqcPassed` — **한 함수로 통일**(R-5·R-10)

⚠ **용어 정정** — `shippingInspectionStatusCode` 는 `ShipmentRequest` 의 **헤더 required 칸**이지 라인 축이 아니다. `ShipmentRequestLine` 에는 `shippingInspectionRequired`(boolean)뿐이다. **라인별 판정은 계약 필드가 아니라 롤업의 «내부 중간값»**이다.

**0단계 선례** — `inspection_request.target_type_code` enum 은 `LOT`·`WORK_ORDER`·**`SHIPMENT_REQUEST`** 셋이고 계약 설명이 「LOT(**OQC 제품 LOT**) … 출하 지시(`SHIPMENT_REQUEST` · OQC)」로 두 축을 다 적었다. ⭐ **그리고 `inspection_request.lot_id` 는 `target_type_code` 와 «병존»한다**(`W-04-03` §4-A 「대상 LOT | `lot_id` | nullable — **다형과 병존**」 · `schema.prisma:3374`) — 헤더 대상 의뢰도 **어느 LOT 인지 적을 수 있다**(R-5).

**라인 하나의 검사 상태 — `lineInspectionStatus(line)`:**

```
required = shipment_request_line.shipping_inspection_required
if (!required)                                     return NOT_REQUIRED;

lots = 이 라인이 집은 LOT 집합(= picks[].lotId)
결과 모집단 =
  quality.inspection_result r JOIN quality.inspection_request q ON q.id = r.inspection_request_id
  WHERE q.inspection_type_code = 'OQC'
    AND r.status_code = 'CONFIRMED'                       ⭐ DRAFT 를 세지 않는다
    AND r.inspection_round = (그 request 의 CONFIRMED 최대 회차)
    AND (
         ( q.target_type_code = 'LOT'
           AND coalesce(q.lot_id, q.target_id) IN lots )
      OR ( q.target_type_code = 'SHIPMENT_REQUEST'
           AND q.target_id = 이 작업지시
           ⭐ AND (q.lot_id IS NULL OR q.lot_id IN lots) )   ← R-5: lot_id 병존을 버리지 않는다
       )

모집단 0건                    → PENDING
REJECTED 하나라도             → REJECTED
HELD 하나라도(REJECTED 없음)  → HELD
그 밖(전건 ACCEPTED)          → PASSED
```

**헤더 롤업** = 라인들의 값에 `REJECTED > HELD > PENDING > PASSED > NOT_REQUIRED` 적용.

#### ⛔⛔ `oqcPassed` 를 «같은 함수»로 낸다 (R-10 · uiux Blocker 2)

초판은 `oqcPassed` 를 **LOT 축만**으로 냈다. 그러면 **OQC 를 헤더 대상으로 낸 작업지시**에서:

| 화면 | 값 | 결과 |
|---|---|---|
| `W-04-02` §4-A 「검사」 | 라인 축 → `PASSED` | 「✅ 합격」 |
| `W-04-04` §5-4 관문 ② | 라인 축 → 합격 | 출하 확정 통과 ⭕ |
| `P-04-02` §5-1 대상 목록 | `oqcPassed` → LOT 축 0건 → **false** | ⛔ **영영 발행 불가** |

`P-04-02` §5-6 이 「**발행 취소 ⛔ 두지 않는다**」라 되돌릴 수도 없다. ⇒ **「합격인데 납품라벨을 영원히 못 뽑는」 영구 상태**다.

⇒ **`oqcPassed = (required === false) ? true : lineInspectionStatus(그 배분의 라인) === 'PASSED'`.** ⭐ 배분이 매달린 `shipment_line → shipment_request_line` 을 타고 **같은 함수**를 재사용한다.
⭐ **PR 배치가 바뀐다** — `oqcPassed` 를 **⑦a 에서 ④ 로 당겨** 검사 롤업과 한 PR 에 둔다(§10). e2e 도 **A-6~A-9 와 L-23~L-30 이 같은 픽스처를 공유**해야 어긋남이 드러난다.
⚠ 「검사 대상이 아닌 배분은 `true`」는 계약이 명시한 것이다 — 「검사를 안 거쳤다」가 「발행하면 안 된다」가 아니다(「알려둘 것」 ⓕ).

### 5-3. `packedQty` — **0 또는 배정 전량 둘뿐**

물리는 `handling_unit_id` **한 개 nullable FK** 다. ⇒ `packedQty = handling_unit_id IS NULL ? 0 : allocated_qty` · `unpackedOnly` = `handling_unit_id IS NULL`.
⛔ **`handling_unit_content.qty` 로 세지 않는다** — `uq (hu, item, lot)` 라 같은 (품목·LOT)의 배분 둘이 한 포장에 들어가면 수량이 합쳐져 못 가른다.
⭐ `P-04-01` §3-3 의 「포장 N = 서로 다른 비어있지 않은 `handlingUnitId` 수」와 **일관**한다(uiux 확인).
