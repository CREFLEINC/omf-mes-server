```sql
    '상위 고객사 출하지시서. nullable — 단독 생성(무지시)이 상시 구조다(W-04-01 §5-2). GET /logistics/sales-orders?unassignedOnly 가 이 칸으로 편성 여부를 판정한다.';

CREATE INDEX ix_shipment_request_sales_order
    ON logistics.shipment_request (sales_order_id);
```

- ⛔ **FK 제약 이름을 짓지 않는다** — Prisma 기본형이어야 `migrate diff` 가 드리프트를 안 낸다(사용자 메모리 · `prisma-fk-constraint-name-must-be-default`). 위 DDL 은 이름 없는 `REFERENCES` 라 PG 가 `shipment_request_sales_order_id_fkey` 를 만든다.
- 인덱스 이름은 저장소 관행 `ix_<table>_<col>` 을 복제했다(`ix_shipment_request_line`·`ix_shipment_lot`·`ix_reservation_source`).
- `schema.prisma` 에 `sales_order_id BigInt?` + 관계 + `@@index` 를 함께 넣고 **`npx prisma generate`**.

### 3-4. 400 · 404 · 409 갈래 — **순서가 판정이다**

| 순 | 검사 | 왜 이 자리인가 |
|:-:|---|---|
| 1 | 계약 가드(형식·required·enum) | 서비스가 다시 세면 **되돌려도 안 깨지는 절**이 된다(I-21 R-15) |
| 2 | 헤더 필수(`X-Worker-No`) | ⛔ 계약 가드가 헤더를 **안 본다**(`contract-validation.guard.ts:39` — body·query·params 만 본다) |
| 3 | 계약이 «안» 건 수량 절(`pickedQty > 0`·`allocatedQty > 0`) | ⭐ 04 는 `exclusiveMinimum` 이 없어 **여기가 유일한 그물**이다 |
| 4 | 존재·소유(404) | 남의 작업지시의 라인을 열지 않는다 |
| 5 | 참조 무결(400 `INVALID`) | 400 이 404 보다 뒤 — 대상이 있어야 본문을 판정한다 |
| 6 | **업무 거부(409)** | ⭐ 재로드로 풀리는 것만 여기 온다 |
| 7 | 코어 하한(400 `NEGATIVE_BALANCE`) | **둘째 그물** — 도달하면 6 이 새는 것이다 |

⚠ **`ShipmentConflictResponse` 에 `conflictCause` 가 함께 실린다** — 공용 `ConflictException` 이 언제나 넣는다(`conflict.exception.ts:55`). 계약은 `VERSION_CONFLICT` 때만 요구하지만 `additionalProperties` 를 안 닫아 유효하고, I-6·I-21 이 같은 모양이다. `'user'` 로 낸다. 「알려둘 것」 ⓘ.

### 4-2. `GET /logistics/shipment-requests` — 질의 13

## 5. 파생 축 셋 — **계약이 판정식을 가진 쪽 / 안 가진 쪽**

### 5-1. `shipmentProgressCode` — 6값 · 계약이 식과 순서를 «적었다»

> ⛔ 통합 계획서(`plan-integration.md:399`)가 「도출 규칙은 **값 이름이 그대로 말한다**」라 적었다. **믿지 않고 덤프해 실측했다** — 계약이 6값의 식과 우선순위를 문장으로 갖고 있다(부록 #3).

한 작업지시의 라인 4수량 합으로 판정한다. **R = Σrequested · A = Σallocated · P = Σpicked(예약 롤업) · S = Σshipped.**

| 값 | 계약 문장 그대로 |
|---|---|
| `NOT_ALLOCATED` | 배정 합 0 (`A = 0`) |
| `PARTIALLY_ALLOCATED` | `0 < A < R` |
| `PICKING` | `A = R` **그리고** `P < A` |
| `PICKED` | `P = A` **그리고** `S = 0` |
| `PARTIALLY_SHIPPED` | `0 < S < A` |
| `SHIPPED` | `S = A` |

⭐ **판정 순서는 「뒤가 이긴다」** — 위에서부터 재고, **마지막으로 참이 된 값**을 낸다. ⇒ 구현은 **역순 if 사슬**(`SHIPPED` → … → `NOT_ALLOCATED`)이고 마지막이 `NOT_ALLOCATED` 다.

⚠⚠ **함정 — `PICKING` 은 「배정 합 = 요청 합」을 요구한다.** 부분 배정(`A < R`)은 `W-04-01` §5-1 이 「**부분 배정이 정상이다**」라 못박은 상시 구조인데, 그런 작업지시는 아무리 피킹해도 `PARTIALLY_ALLOCATED` 에 머문다(「뒤가 이긴다」로 `PICKED`·`PARTIALLY_SHIPPED`·`SHIPPED` 가 나중에 이긴다). ⇒ **계약 문자대로 구현하고 통보한다**(§9-1 #2 · 통보 후보 없음 — 계약이 명시적으로 그렇게 적었고 뒤 값들이 덮으므로 화면이 막히지 않는다. 「알려둘 것」 ⓖ).

⚠ **`P` 는 예약 롤업이다**(§0 #2) — 값이 `numeric(20,6)` 이므로 **`Decimal` 로 비교한다**. ⛔ JS `number` 로 접으면 `0.1 + 0.2 !== 0.3` 이 `PICKING` 과 `PICKED` 를 갈라 버린다(e2e #L-12).

### 5-2. `shippingInspectionStatusCode`(5값) · `oqcPassed` — 계약이 **조인 축을 안 적었다**

계약이 준 것: 값 정의 5 + 롤업 순서 `REJECTED > HELD > PENDING > PASSED > NOT_REQUIRED`.
계약이 안 준 것: **「그 라인의 검사 결과」를 어디서 찾나.**

**0단계 선례** — `inspection_request.target_type_code` enum 은 `LOT`·`WORK_ORDER`·**`SHIPMENT_REQUEST`** 셋이고 설명이 「검사 대상 — LOT(**OQC 제품 LOT**) · 작업지시(PQC) · **출하 지시(`SHIPMENT_REQUEST` · OQC)**」이며 「`W-04-03` §4 가 「다형 — **출하작업지시 · LOT**」로 적어 두었다」(부록 #20). ⇒ **두 축 다 실재한다. 라인 축은 없다.**

**판정** — 라인 하나의 검사 상태:

```
required = shipment_request_line.shipping_inspection_required
if !required                                   → NOT_REQUIRED
결과 모집단 = quality.inspection_result r
              JOIN quality.inspection_request q ON …
              WHERE q.inspection_type_code = 'OQC'
                AND r.status_code = 'CONFIRMED'            ⭐ DRAFT 를 세지 않는다
                AND ( (q.target_type_code = 'LOT'
                       AND coalesce(q.lot_id, q.target_id) IN (이 라인이 집은 LOT))
                   OR (q.target_type_code = 'SHIPMENT_REQUEST'
                       AND q.target_id = 이 작업지시) )
              AND r.inspection_round = (그 request 의 CONFIRMED 최대 회차)
모집단 0건                                     → PENDING
REJECTED 하나라도                              → REJECTED
HELD 하나라도(REJECTED 없음)                   → HELD
그 밖(전건 ACCEPTED)                           → PASSED
```

헤더 롤업 = 라인들의 값에 `REJECTED > HELD > PENDING > PASSED > NOT_REQUIRED` 를 적용.

- ⭐ **`status_code = 'CONFIRMED'` 필터가 §0 #4 의 핵심**이다. `20260907174412` 가 `overall_judgment_code` 의 NOT NULL 을 풀어 **DRAFT 행은 판정이 비어 있을 수 있다**(부록 #21) — 필터가 빠지면 `null` 판정이 롤업에 섞인다.
- ⭐ **재검사 회차** — `uq_inspection_round (request, round)` 라 한 의뢰에 여러 회차가 있다. **CONFIRMED 최대 회차**만 센다. 빠지면 「불합격 뒤 재검사 합격」이 영원히 `REJECTED` 다(e2e #A-9).
- `oqcPassed`(배분) = **`required=false` 면 `true`**(계약 명시 「「검사를 안 거쳤다」가 「발행하면 안 된다」가 아니다」), 아니면 **그 LOT 축 판정 == `PASSED`**. ⇒ 「알려둘 것」 ⓕ.
- **통보 후보 F** — 라인에 검사를 매다는 칸이 0개라 우리가 축을 골랐다는 사실을 남긴다.

### 5-3. `packedQty` — **0 또는 배정 전량 둘뿐**

물리는 `shipment_lot_allocation.handling_unit_id` **한 개 nullable FK** 다. 부분 포장을 담을 자리가 없다.
⇒ `packedQty = handling_unit_id IS NULL ? 0 : allocated_qty` · `unpackedOnly` = `handling_unit_id IS NULL`.
⛔ **`handling_unit_content.qty` 로 세지 않는다** — 그 표는 `uq (hu, item, lot)` 라 **같은 (품목·LOT)의 배분 둘이 한 포장에 들어가면 수량이 합쳐져** 어느 배분 몫인지 못 가른다. 통보 후보 E.

### ① → **I-23**(출하 처리·확정·취소 + 재고 재등록)이 이 위에 선다
