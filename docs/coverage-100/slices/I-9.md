## 3. ⭐ `POST /logistics/shopfloor-receipts` — 이 슬라이스의 심장

### 3-1. 한 트랜잭션 순서

```
[tx 밖]  ① 본문 형식 검증(라인 1행 이상 · 수량 · 시각 형식 · 라인 중복)      → 400 모아 던짐
         ② 출고 헤더·라인·마스터 읽기(FK 그물 · 축마다 IN 한 번)             → 400 모아 던짐
         ③ varianceReasonCode 값 대조(assertCodeValues)                      → 400
         ④ plantId 를 W/O → production_plan → production_order 로 푼다        → 400 INVALID
         ⑤ numbering.next('SHOPFLOOR_RECEIPT', plantId, businessDate)         ⛔ $transaction «밖»
[tx 안]  ⑥ SELECT … FROM logistics.goods_issue WHERE goods_issue_id = ? FOR UPDATE
         ⑦ 그 출고에 이미 수령 전표가 있으면 400 STATE_LOCKED                 (§3-8)
         ⑧ INSERT shopfloor_receipt(status_code='REGISTERED', received_by=세션)
         ⑨ createMany shopfloor_receipt_line (variance_qty 는 안 넣는다 — GENERATED)
         ⑩ 같은 tx 에서 되읽어 상세(라인 포함)를 만든다                       → 201
```

⑤ 가 `$transaction` 밖인 근거는 `plan.md` §3 채번 칸 · I-2 R-2 · 선례 `material-issue-request.service.ts:62`.
⑥ 이 tx **안**인 근거는 §3-8. ⚠ 컨트롤러의 `runIdempotent` 가 이미 트랜잭션을 열고 있어(I-2 R-2 실측 정정) 요청당 동시 커넥션은 **2 로 main 과 같다**.

### 3-2. 헤더 검증 — ⓐⓑ

**ⓐ `goods_issue` 는 `POSTED` 만 받는다** — 400 `STATE_LOCKED`.
§2 0단계 선례가 답한다: `M-01-09` §8 #1 ⌜`M-01-08` 출고 확정이 `postImmediately: true` 라 **전표가 항상 전기완료**⌝ · `I-4.md` R-6 ⌜반품 전표도 항상 `POSTED` 로 태어난다⌝ · 상태 상수는 `goods-issue.service.ts:34`(`const POSTED = 'POSTED'`)·`:296`.
1단계 **가장자리**(등록만 된 출고·취소된 출고를 스캔했을 때만 갈린다) → 2단계 **기준 2**(거부하는 쪽) — 등록만 된 출고는 물건이 창고를 안 떠났고, `CANCELLED` 출고를 받으면 취소된 재고를 받은 것이 된다. 「업무를 없애는 거부」가 아니다(I-4 §5-3 의 단서에 안 걸린다).
⛔ 상수는 **복사하지 않는다** — `goods-issue.service.ts` 가 `POSTED` 를 `export` 하지 않으므로 이 도메인의 `shopfloor-receipt.constants.ts` 에 한 줄 두고 주석으로 출처를 적는다(도메인 간 import 금지 · `material-issue-request.constants.ts` 와 같은 모양).

**ⓑ `work_order_id`·`destination_location_id` 는 «존재만» 본다 — 대조하지 않는다.**
- W/O ↔ 출고 원천 체인: `goods_issue.source_document_type_code` enum **3값**(`PICKING_ORDER`·`GOODS_RECEIPT`·`DISPOSITION_DECISION` — 실측). 생산 투입은 `PICKING_ORDER` 하나이고, 거기서 W/O 에 닿으려면 `picking_order.source_document_id → material_issue_request.work_order_id` 로 **FK 없는 다형 2홉**을 타야 한다. ⚠ 그런데 **I-8 이 `picking_order` 를 만드는 오퍼레이션이 0건임을 확정했다**(문의 045) — 오늘 피킹 지시는 픽스처로만 선다. 체인을 필수로 걸면 「출고는 있는데 대조가 불가능」한 형상이 생긴다.
  ⇒ 1단계 가장자리 → 2단계 **기준 5**(새 개념 0) · I-4 §5-3 「업무를 없애는 거부는 안 쓴다」 ⇒ **대조 없음**. §8-3 ⓒ.
- 위치: `goods_issue.destination_type_code`/`destination_id` 짝(`ck_goods_issue_destination` — `20260901090000…:25-26` 「둘이 함께 널이거나 함께 값」)이 있으나 **둘 다 nullable** 이고 `GoodsIssueCreate` 에서도 **선택**이다(`goods-issue-rules.ts:34-35`). 도착지 없는 출고에 400 을 내면 그 갈래를 죽인다.
  또 「생산창고」를 가르는 `location_type_code` 값이 **없다**(§1-5 · 5값 중 없음) ⇒ **유형 검사도 안 한다.**
  ⇒ **존재만 본다**(`location.count()` — `material-issue-request.service.ts:157` 선례). §8-3 ⓓ.

**ⓔ 판정 — `issuedQty` 는 «대조»다, «덮어쓰기»가 아니다.**
1단계: 클라이언트 값이 출고 라인과 다를 때만 갈린다 → **가장자리**.
2단계 기준 1 동률(둘 다 원장·상태를 안 쓴다) → 기준 2 **거부하는 쪽** + 기준 4 **값을 조용히 도출하지 않는 쪽** — 둘이 같은 답을 낸다.
⇒ **다르면 400 `INVALID`.** 근거 보강: `M-01-09` §4-A 가 「출고 수량 = **읽기 전용 — 출고에서**」라 적었고, `variance_qty` 는 GENERATED 라 **클라이언트가 보낸 값이 차이의 분모**가 된다 — 조용히 덮어쓰면 화면이 본 차이와 저장된 차이가 갈린다. 되돌리기: 회신이 「덮어써라」면 검사 한 줄을 지우는 완화다.
3단계 흔적: 단위 테스트 `issuedQty 가 출고 라인과 다르면 400 INVALID // 설계 미정 — 문의 050`.

**ⓖ 판정 — 차이 0 인데 사유가 오면 «거부»한다.**
계약은 한 방향만 적었다(⌜차이가 0 이 아니면 필수⌝). 반대 방향은 침묵이다.
1단계 가장자리 → 2단계 **기준 2**(거부→허용은 완화, 허용→거부는 깨는 변경). 「업무를 없애는 거부」가 아니다 — `M-01-09` §5-6 이 ⌜차이 사유: **`variance_qty ≠ 0`일 때 노출**⌝ 라 적어 화면이 애초에 안 보낸다.
⇒ **400 `INVALID`**(새 코드 0). 선례 모양: I-6 의 `REMAINDER_DISPOSITION_NOT_ALLOWED`(계약이 두 방향을 다 적었던 자리) — 여기는 이름을 새로 짓지 않고 `INVALID` 로 간다(README §5 「새 error code 0」).
3단계 흔적: 단위 테스트 `차이가 0 인데 사유가 오면 400 INVALID // 계약 미기재 갈래 — 문의 049 와 함께 전달`.

## 5. 오프라인 큐 순서 — 서버 몫이 있나

`M-01-09` §5-1(결정 17 시나리오 2)이 셋을 적었고 그중 **2번이 서버에 닿는다**:

**이 슬라이스가 하는 것 / 하지 않는 것**

| | |
|---|---|
| 한다 | 입고가 먼저 닿으면 **400 `INVALID`**(없는 `goodsIssueId`·`goodsIssueLineId`) 로 거부한다 — 계약이 이 경로에 404 를 선언하지 않았다(§1-1). 출고가 나중에 거부되면 그 출고는 아예 안 생기므로 입고도 **영구히 400** 이고 데이터가 어긋난 채로 남지 않는다 |
| 하지 않는다 | ⛔ **큐 묶음(batch) 개념을 만들지 않는다** — 계약 본문·`Idempotency-Key` 어디에도 「선행 요청 키」를 실을 자리가 없다(`IdempotencyKey` 는 uuid 하나). ⛔ 「출고 거부 → 딸린 입고 회수」 를 서버가 밀지 않는다(서버→단말 푸시 축이 0건) ⇒ **C-2 건별 되돌리기의 순서 보장은 클라이언트 셸 몫**이다 |

⇒ 서버가 할 수 있는 최선이 「앞이 없으면 뒤를 400 으로 거부」뿐이고, 그것이 화면이 요구한 「함께 거부」와 **같은 결과를 내는지**를 설계팀이 확인해야 한다 → **문의 048**.

## 7. e2e — `test/logistics-shopfloor-receipt.e2e-spec.ts` 하나

### 7-1. 픽스처

접두어 상수 `const PREFIX = 'SRE2E'` + `LIKE 'SRE2E%'` 정리(`plan-integration.md` §0 규약 · `logistics-picking.e2e-spec.ts:29` 모양).
마스터 사슬은 피킹 e2e 의 것을 그대로 복제한다(`:520~612` — legal_entity → business_unit → plant → item/uom → warehouse → location → process → routing → production_order/plan → work_order → lot).
⭐ **출고는 «직접 INSERT» 한다** — `goods_issue(status_code='POSTED', source_document_type_code='PICKING_ORDER')` + `goods_issue_line` N행.
근거: `goods_issue_line.inventory_transaction_line_id` 는 **nullable**(`schema.prisma:784`) 이라 전기 없이도 `POSTED` 전표를 세울 수 있고, 이 스위트는 **원장을 쓰지 않아야** 「원장 무변화」 단언이 뜻을 갖는다(§3-4). `:pick` → `POST /goods-issues` 를 태우면 원장이 생겨 단언이 무의미해진다.

### 7-2. ⭐ 정리에서 **`TRUNCATE` 를 쓰지 않는다**

I-8 ④b-2 가 원장 정리에 `TRUNCATE inventory.inventory_transaction_line, inventory.inventory_transaction CASCADE` 를 썼고(`logistics-picking.e2e-spec.ts:672`), 그것이 **동시 실행 스위트의 원장을 함께 비우는** 저장소 차원 문제로 이미 적혀 있다(I-8 §11-3 미완 목록).
**이 스위트는 원장 행을 한 건도 만들지 않으므로 TRUNCATE 가 필요 없다** — 쓰면 남의 스위트만 망가뜨린다.
정리 순서(전부 `DELETE … WHERE … LIKE 'SRE2E%'` 또는 id 서브쿼리):
`shopfloor_receipt_line → shopfloor_receipt → goods_issue_line → goods_issue → inventory_balance → lot → work_order → production_plan → production_order → routing_operation/routing → process → location → warehouse → item/uom → plant → business_unit → legal_entity` · 그리고 `app.numbering_counter`/`numbering_rule` 의 `SHOPFLOOR_RECEIPT` 행은 **지우지 않는다**(다른 스위트와 공유하는 전역 자원 · 기존 관행).
