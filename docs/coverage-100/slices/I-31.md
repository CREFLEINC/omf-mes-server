### 0-1. 판정 절차와 멈춤 경계

0단계는 계약 본문·기존 도메인 규칙·현재 전표 선례의 인용이다. 그 인용으로 결정되지 않는 것만 1단계에서 **모든 정상 호출**에 영향을 주는 본길인지 특정 입력의 가장자리인지 나눈다. 본길이면서 계약도 침묵하면 해당 op를 유보한다. 전건 거부 handler를 달아 covered로 세지 않는다.

가장자리는 2단계의 **최초 적용 기준**을 쓴다: ① 재고·원장·상태 안 쓰기 → ② 명시 거부 → ③ 스키마 안 늘리기/필요하면 nullable → ④ 조용한 도출 안 하기 → ⑤ 새로운 개념 수가 적은 쪽. 3단계는 상수 이름·실제 테스트 이름·문의 흔적이다. 아래 §9가 그 기록이다. 형식만 인용하고 실제 적용 기준을 생략하지 않는다.

전체 멈춤은 **컬럼/테이블 삭제의 두 릴리스 규칙 위반 / 원인 불명 gate 3회 실패 / 두 계약을 동시에 충족할 수 없는 명시 모순** 세 가지뿐이다. 설계 문의·실제 데이터 미측정·미마감 성공과 마감 유보의 공존은 전체 멈춤이 아니다. 이번 위임은 계획까지만이므로 그 소유 종료는 루틴 중단이나 구현 완료가 아니다.

PageMeta는 `{page,size,total}` **세 칸 모두 required**다. 목록에서 optional인 page를 항상 채우고 totalCount도 같은 전체 건수로 낸다. 상세/쓰기 body에 `versionNo/version_no`를 추가하지 않는다. 상세GET2만 version ETag를 설정하고 쓰기는 다음 수정 전 상세 재조회다. Express의 content-hash ETag 가능성과 version ETag를 구분하여 ‘모든 쓰기 ETag 부재’를 오검증하지 않는다.

### 3-2. SQL 후보 A — 지시·trigger 확장/완화

아래는 리뷰 가능한 **전체 후보 DDL**이다. 실제 migration 경로의 타임스탬프는 **파일 생성 시점의 clock**으로 정하며 지금 실행하지 않는다. 병합 시각을 미리 예약하거나 가짜 날짜 이름을 쓰지 않는다. 컬럼/표 삭제·데이터 UPDATE·INSERT·seed·백필은 없다. 기존 이름이 정확한지 §3-5 pg_catalog 결과로 재확인하고 기존 제약이 있는 환경에서 IF EXISTS로 오류를 감추지 않는다.

R2의 reset=true 거부와 DDL의 nullable reset/snapshot 저장자리 추가는 별개다. 물리 준비가 reset 성공이나 허용 코드 의미의 권위가 되지 않으며 현재 신규 결과는 reset=false·snapshot null, 누계/lastPM 쓰기0이다. `completed_at`은 nonreset 미마감 구간 종료를 저장할 뿐 PM 완료/시행일/집계시각이 아니다.

Prisma는 physical 이름과 FK 이름을 실제 DB 기준으로 반영하고 order.trigger 관계를 배열로 바꾼다. app_user/equipment/mold/breakdown/order/item/spare/GI의 **역방향 relation 전건**을 추가한다. `SPARE_PART_REFERRERS`에 result_part, `EQUIPMENT_REFERRERS`·`MOLD_REFERRERS`에 result의 실제 FK를 추가하고 각 기존 e2e의 pg_constraint 대조까지 같은 변경 묶음에 둔다. 공용 정렬/전체 schema 포맷 변경은 하지 않는다. result의 target_id 다형을 고르면 이 참조카운트 구현도 달라지므로 별도 안으로 몰래 바꾸지 않는다.

### 3-4. 새 칸과 구행·응답의 관계

신규order는 required6/담당자/발행번호/issued actor/time, 신규result는 required5/명시target/note/boolean기본/버전/audit를 전부 채운다. 구행을 조회할 때 계획일이 null이면 scheduled_start_at·created_at·오늘을 쓰지 않는다. 구result의 target/note가 null이면 연결 order나 action_description으로 추측하지 않는다. 작업자→계정도 비유일·nullable worker.app_user 관계를 타서 고르지 않는다.

응답 required 결손/지원하지 않는 target enum/안전정수 밖의 ID·누계는 요청자 잘못이 아니라 `500 INTERNAL_ERROR`로 명시한다. 0·빈 문자열·임의 상태/순서·NULL강제출력·행 제외/목록 total감축으로 봉합하지 않는다. 단 `MaintenanceOrder.assigneeUserId`처럼 optional non-null 필드는 구 nullable이면 **생략**, baseDate/finishedAt처럼 nullable 필드는 null이다. DDL 성공과 과거 데이터까지 API 사용 가능함은 다른 인수 항목이다. **배포 전 사전조회의 required 결손이1행 이상이거나 구 writer가 결손행을 계속 생성하면 해당 환경의 관련 operation 활성화를 유보한다(R4·091).** 결손 환경만의 배포 제한이지 정상 개발 환경의 구현이나 DDL 전체 중단이 아니다.

### 3-5. root에게 요청한 B 전용 SELECT 전건

실행자/DB 식별/실행시각/HEAD를 함께 보관하고 반환된 수만 실측으로 쓴다. 이 초안 작성자는 한 번도 DB에 접속하지 않았다. 비밀번호·전체 사용자 이름/서술은 필요 없다. 아래 행 수/구조/코드/시간대는 계획 근거에 필요한 최소 데이터다. root 실행 결과는 §3-6이며, 새 migration 뒤 검사와 운영 배포 검사는 별도 단계다. 여기서는 **현재 컬럼만** 조회했다.


## 4. 조회와 응답 매핑

O1은 planned_date를 받은 date와 직접 비교하여 from/to 양끝 포함. O3은 **각 대상 공장 로컬 달력일**의 started_at UTC 경계 `[from 시작, to 다음 달력일 시작)`로 비교한다. I-30 R13의 `maintenance-calendar.ts`를 재사용하고 AT TIME ZONE/서버OS시간대/UTC상수/끝=시작+24h는 쓰지 않는다. 대상 공장의 zone이 잘못됐으면 명시 INTERNAL_ERROR이며 해당 행 제외/UTC fallback0이다.

targetType 없이 targetId만 있으면 EQUIPMENT.id와 MOLD.id 각각에서 맞는 대상을 **모두** 반환할 수 있다. 정수 하나로 타입을 추측하지 않는다. 두 타입이 겹치는 ID fixture를 둔다. 모든 조건은 AND, targetId의 대상별 분기만 OR다. 존재하지 않는 filter ID는 정상 빈목록이지 상세404가 아니다. statusCode는 코드 문자열을 그대로 정확 비교하되 알 수 없는 값 처리도 I-30 조회 선례와 정합 확인한다(저장 active검증을 과거 조회에 잘못 적용하지 않음).

공통 `pageRequest`를 재사용: 기본1/50, size최대200, 범위는 현재 helper의 clamp 선례를 따른다. AJV integer 실패를 임의 clamp하지 않는다. page×size가 안전정수 범위를 벗어나는 요청은 기존400 RANGE. 기간 역전은400 RANGE, field plannedTo/startedTo. 정렬은 계약 침묵이므로 지시 `(planned_date DESC, maintenance_order_id DESC)`, 실적 `(started_at DESC, maintenance_result_id DESC)` 고정·문의094 연계. NULL required 구행을 NULLS LAST로 숨기지 않고 §3-4 검사를 적용한다.

count와 페이지는 같은 WHERE를 사용하고 read transaction의 일관된 snapshot으로 읽는다. page 밖의 rows를 JS에서 잘라 count와 어긋나게 하지 않는다. 목록 selected parent IDs에 대해 item/trigger/line/part를 batch조회하여 N+1을 막는다. items는 sequenceNo+ID, trigger는 created_at+ID, result line/part는 내부 sequence 순. 세 배열 모두 계약상 optional이나 정상 새 행에서는 []도 명시한다.

Order 매핑: 번호←maintenance_order_no, 유형←order_type_code, targetId/code←해당 FK+마스터, 계획/기준←date문자열, 담당←새 assignee_user_id, 발행자/시각←새 issued_by/issued_at. EQUIPMENT itemName은 FK 마스터명, MOLD는 저장 free name. 둘을 받은 경우 EQUIPMENT는 마스터 정본명을 표시하고 입력 자유이름을 snapshot으로 승격하지 않는다. trigger에 axis가 null이면 optional key생략(enum-null 모순 회피), 두 count/snapshotNote는 nullable 그대로.

Result 매핑: order/breakdown FK는 입력으로 저장한 값만, finishedAt←completed_at ISO/null, note←result_note, performer←새 performed_by_user_id, outsourced/reset/closed는 새 행 explicit boolean·구 unknown은 optional 생략. before/after는 snapshot/null. parts.partName은 readOnly가 아니므로 제공된 입력을 그대로 보존하고 미제공은 optional 생략(마스터명 임의 snapshot0). goodsIssueNo/issuedAt는 연결 헤더 조인, 미연결이면 null. **part.issuedAt도 raw epochµs projection→동일 UTC ISO6**를 사용하며 native Date로 받아 µs를 절삭하지 않는다(R8). uomCode의 단일 원천/다중 단위는 §7에서 정한다.

제한 없는 자유문자열·line 수를 임의 길이/배열개수로 계약에 추가하지 않는다. 물리 varchar(200)/code_t(50)와 numeric(20,6)은 명시400 RANGE/INVALID 경계 테스트로 다룬다. required 숫자 int64를 무조건 Number()로 반올림하여 가짜 ID/샷수를 내리지 않는다.

### 5-2. PM 발행 후보의 명시적 선택

고정 문서만으로도 PM_DUE는 현재 도래 상태를 근거로 만든다. `mdm/mold/mold-derivation.ts:125`의 OR식/월말보정·공장 today와 seed를 0단계 선례로 삼는다. pmDue=false, 기준자료 부족, 폐기 툴이면422 INVALID/STATE_LOCKED. `PM_NEAR_THRESHOLD_PERCENT=90`은 이미 있는 조회 지표이며 **IMMINENT_DAYS나 새로운 일수 정책을 만들지 않는다**. 임박 요약 수정은 I-31 범위가 아니다.

위 도래 재판정·샷 snapshot 규칙은 **MOLD PM_DUE에만** 적용한다. 실제 EQUIPMENT `trigger-picker.tsx:44,:258`는 저장된 후보를 조회하지 않고 설비를 골라 PM_DUE를 직접 더하며 sourceId를 비운다. 이 정상 입력은 계약의 촉발 선언 그대로 받고 대상/보전 부여/기준일을 검증한다. 툴의 샷·lastPM 주기를 설비에 이식하거나 source가 없다고 가짜 점검기록을 생성하지 않는다. EQUIPMENT의 별도 PM 도래 재계산 정책이 필요하면 그 원천을 문의하며, 후기 MOLD 전용 문구를 근거로 기존 설비 입력 전체를 거부하지 않는다.

현재 코드도 BOTH가 함께 도래하면 SHOT을 반환하지만 ‘먼저 도달한 시각’ 이력은 없다. **기존 문의4/O-5의 잠정 SHOT 선례 유지**를 후보로 하며, 고정 후 대표SHOT 문구를 해결 회신으로 취급하지 않는다. pure PM facts 추출 시 이 판정을 개선했다며 바꾸지 않는다. 큰 bigint의 비교는 bigint로 하고 ratio 표시용 Number와 혼합하여 오판정하지 않는다.

snapshot 입력을 전부 무시하고 최신값으로 바꿔도 된다는 후기 문구는 채택하지 않는다. 권고 경계는 다음과 같다: 제공된 axis/count/guaranteed가 발행tx에서 잠근 현재 사실과 맞으면 보존; **다르면422 INVALID(각 trigger field)**로 재조회하게 한다. 생략된 snapshot은 nullable로 보존하고 서버가 임의 과거값을 채우지 않는다. 현재 도래 판정이 서도 snapshot을 클라이언트가 생략할 수 있다는 것은 계약 optional의 범위이며, 화면 필수축 요구와의 차이는 문의에 남긴다. source없는 PM을 가짜 source ID로 저장하지 않는다.

### 5-3. 채번·쓰기 순서

필수 maintenance_order_no는 `NumberingService`만 사용한다. 등록 후보 `MAINTENANCE_ORDER:'MO'`, 기존 기본패턴 `MO-{YYYYMMDD}-{SEQ4}`. 화면의 TMO/연간 예시는 계약이 형식을 확정한 것이 아니다. **기간키는 클라이언트가 준 plannedDate**, 공장은 실제 대상 plant_id다(코어 next가 이미 가진 업무날짜를 요구하는 선례). 서버수신일·baseDate로 바꾸지 않는다. 문의14/098에 추가하고 별도 결과번호는 만들지 않는다.

I-30 R14 순서를 그대로 확장한다: 멱등 context 먼저 → 기존 record 사전조회 → 이미 있으면 새 번호/대상상태 검증 없이 run 재생 → 없으면 tx밖에서 대상공장 사전조회·next 완료 → run의 **전달tx** 안에서 target/부여/source/계정/코드 최종 검증·INSERT. 사전읽은 공장이 달라지면 업무0/409 user. 번호만 결번일 수 있다. 멱등행이 사이에 사라져 번호 없이 callback이 실행되면 내부 제어오류로 롤백·tx밖 준비 후 재진입한다.

번호 UNIQUE의 P2002만 최초+3회 전체 run 재시도하며 실패한 tx 안에서 다음 번호 INSERT를 시도하지 않는다. 소진400 UNIQUE_VIOLATION. source/item/멱등 PK의 다른 충돌을 번호충돌로 삼키지 않는다. 정상 성공 재전송에는 채번0, 경합/검증실패에는 선채번 결번 허용. business+response+멱등 record 원자성과 번호연속성은 별개다.

### 6-1. 실적 입력과 정상 성공

### 6-2. 공통 잠금·트랜잭션 순서

업무 쓰기4개는 모두 `IdempotencyService.run(context, async tx => ...)`를 직접 사용한다. 공용 master-write는 callback tx를 버리므로 사용하지 않는다. I-30에서 실제 병합될 `maintenance-code-reference`·context·numbered helper가 있으면 같은 maintenance 안에서 재사용하고, 계획에만 있는 파일을 존재하는 dependency로 import하지 않는다.

지문은 정규 METHOD+실제 path 식별자, 원 요청 body, **인증 appUserId**를 포함한다. actor가 달라졌는데 같은 키면409 user. 없던 사번 헤더를 요구하지 않고 appUser/worker 조회 뒤에야 actor지문을 만들지 않는다. If-Match는 의미본문이 아닌 전제토큰이므로 기존 선례대로 지문과 분리하고 성공 replay는 최신 version/상태를 다시 검사하지 않는다. 변경본문·변경대상·변경actor는 재생되지 않는다. readOnly/미지원 부가키를 DB 쓰기에서는 제외하지만 raw request 지문을 조용히 정규화해 다른 요청을 같게 만들지 않는다.

공통 순서는 **필요한 EQUIPMENT/MOLD target FOR NO KEY UPDATE → 연결 order FOR UPDATE → result FOR UPDATE → 종류/ID 정렬 참조 FOR SHARE**다. O8은 immutable target/order를 사전 읽어 같은 순서로 잠그고 result를 최종 다시 읽는다. O6은 order만 잠그며 target를 뒤늦게 추가 잠금하지 않는다. 같은 tx의 판정 뒤 다른 tx를 새로 열거나 domain service로 우회하지 않는다. 아래 R6는 기존 writer와 FK 잠금의 실제 순서까지 대조한 프로토콜이다.

POST와 cancel은 같은 order잠금 안에서 상태·결과수를 확인한다. cancel이 먼저면 POST400; POST가 먼저면 cancel400. POST 두 건의 다른 키는 1:N 정상 nonreset 실적 두 건이 될 수 있다. reset의 오더당1회 성공 인수는 날짜 원천 해소 뒤 조건부다. 미래 마감이 구현되면 닫힘 조건/항목 갱신도 이 잠금 안에서 수행해야 한다. 지금은 result parent의 completed_at만 보고 order를 닫지 않는다.

### 6-3. POST reset — 현재 거부와 미래 성공을 구분

**현재 R2 확정**: `resetCounter=true`는 PM 날짜 원천/적용시점이 닫힐 때까지 **422 INVALID, field resetCounter**, `MAINTENANCE_RESET_POLICY='REJECT_UNRESOLVED_PM_DATE'`로 명시 거부한다(114). run replay 우선·공통 계약/헤더 guard 뒤, callback에서 실적/header/line/part/누계/lastPM/version/멱등완료 쓰기 전에 거부한다. 처음 멱등행도 callback 예외로 rollback한다. “누계만 치환하고201, 날짜는 그대로”라는 옛 초안은 철회했다. malformed 헤더의 공통 guard400과 이 정상형식 입력의 정책422는 별개다.

`resetCounter=false/생략`인 EQUIPMENT/MOLD의 미마감 기록·편집은 정상 본길이다. after값을 주면400 INVALID이며 값 버림0, before 부가키는 whitelist 밖이다. 정상 nonreset은 누계·lastPM·mold.version 쓰기0, 새 결과는 reset=false·before/after null이다. 과거 기록을 남기거나 고치는 것을 **대상 마스터가 현재 폐기됐다는 이유만으로 일괄 거부하지 않는다**(R3). 발행의 현재 사용 가능 상태 검증(§5-1)과 다른 경계다.

MOLD 비reset에 If-Match를 보내는 실제 client는 같은 mold ETag를 검사하되 current_shot_count를 바꾸지 않는다. 헤더 생략이면 계약대로 낙관검사를 건너뛰고 NO KEY UPDATE로 참조를 보호한다. EQUIPMENT 비reset에 If-Match를 보낸 경우의 토큰 원천은 고정 계약이 정의하지 않았으므로 명시400 INVALID 가장자리이며 아무 자원의 version과 우연히 같다고 통과시키지 않는다(093).

**날짜 원천·시점 해소 뒤만 여는 조건부 성공 인수**: MOLD 예방보전 order·현재 폐기 여부를 잠금 뒤 검사, If-Match 없으면422 REQUIRED/형식400/툴 stale409, after 필수·안전 비음수정수, before는 발행snapshot 아닌 저장 직전 누계, after0/비0 직접치환·오더당1회·mold.version 증가·최종 response/멱등 동시 commit. after>before를 임의로 거부하거나 음수 tool_usage·과거 사용행 삭제·보장타수 변경은 하지 않는다. 날짜의 원천/부분시행/역행/nonreset 효과도114에서 함께 닫혀야 한다. 이 성공 helper·경로·테스트를 현재 사용처 없이 먼저 병합하지 않는다.

I-33 tool_usage는 아직 실제 writer가 아니다. 미래 증분 writer는 같은 누계행의 원자 UPDATE와 version 증가로 낡은 reset 토큰이 새 사용량을 지우지 않게 해야 한다. **CAS/직접 DB version fixture PASS로 I-33 실제 writer의 완성·경합 인수를 대신하지 않는다.** 미래 reset 성공을 열 때 실제 증분/폐기 writer와 제어된 잠금 배리어로 오더당1회·재생0변경·증분 경합·폐기 후 최신 ETag reset 거부를 검증한다. 현재 E-R28은 reset=true의 전건0 거부이며 이 미래 성공 목록과 별개다.

### 8-2. PM 마지막 일자 — reset 반쪽 성공 철회

확정: W-05-03 §5-A는 시행일(date)이 마지막PM일자가 된다고 쓰고, §5-1은 master 현재값을 갱신하되 자기참조 체인을 두지 않는다. reset은 실적등록시·오더당한번이며 before는 현재 누계다. **계약 입력에는 별도 시행일/date가 없고 startedAt·finishedAt만 있다.** 실제client는 시작일을 offset 자정 startedAt로 변환한다. 이는 `localDate(startedAt, target.plant.timezone)` 후보의 구체 근거지만 `finishedAt`의 현지 날짜 또는 close서버시각을 골라도 된다는 근거는 아니다.

남은 정상 PM 범위: 나눠시행1:N에서 어느 실적을 PM 1회로 보는가, 부분정비/미마감에도 lastPM일자를 갱신하는가, 과거시행 입력이 현재기준을 되돌리는가, reset=false에도 날짜만 갱신하는가. 화면 요약 ‘리셋 시’와 필드 ‘시행일이 된다’가 시점을 하나로 닫지 않는다. 새 pm_date 입력을 계약에 추가하거나 plannedDate/baseDate/수신일로 빈 값을 메울 수 없다.
