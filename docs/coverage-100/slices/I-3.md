### 2-5. `businessDate`·`occurredAt` 은 저장하지 않는다 — 그러면 응답은 무엇을 주나

- **답: 아무것도 안 준다.** `InboundReceipt`·`InboundReceiptLine`·`InboundReceiptSplitResponse` **어느 응답 스키마에도 `businessDate`·`occurredAt` 칸이 없다**(전건 실측). 요청에만 있고 응답에는 없으므로 「무엇을 돌려주나」 문제가 성립하지 않는다.
- **0단계 선례**: `POST /trace/lots` 가 **똑같은 자리**에 서 있고 이미 구현돼 있다 — `lot.service.ts:assertWritable` 이 「⚠ 받아서 «형식만» 본다. 담을 칸이 없어 저장하지 않는다 — 서버가 수신 시각으로 다시 잡지 않는다는 C-8 을 지키려면 값을 지어내지 않는 편이 낫다(되돌림 §Z-4)」. `assertDay`·`assertInstant` 가 그 자리다.
- **판정**: 입하도 같다. 원장을 지나지 않으므로(`plan-integration.md` §3-1 I-3 「⛔ 없다. §Z-2 가 이미 판정했다 — 「원장을 지는 것은 입고다」」) `business_date` 를 실을 표가 없다. **형식만 검증하고 버린다.** 회신 15 의 설계팀 답(공유계약 `C-8-1` 세 갈래 — 「원장을 지나지 않는 쓰기는 싣지 않는다」)이 이 처리를 확인해 주었다.
- **쓰이는 자리 하나** — 채번의 `periodDate` 다. `numbering.next('INBOUND_RECEIPT', plantId, businessDate)` 로 넘긴다(입고가 `businessDate` 를 그대로 넘긴 선례 · `NumberingService.next` 주석 「⛔ 서버가 「오늘」로 다시 잡지 않는다」). ⇒ **값을 버리되 «날짜 축»으로는 쓴다.**
- ⚠ 「`businessDate` 미저장 건수 누적」은 `plan.md` §7 이 이미 「누적」 대상으로 잡았다 — I-3 이 **3 오퍼레이션**(등록·`:split` · ⛔ 차이 등록에는 두 칸이 아예 없다)을 더한다.

### 2-6. 마이그레이션 SQL 초안 — **A3 + V-inbound_variance 한 파일. forward-only · 추가·완화만.**

```sql
-- prisma/migrations/2026XXXXXXXXXX_inbound_receipt_lot_and_variance_reason/migration.sql
--
-- I-3(입하) 선행 마이그레이션. 추가 1 · 완화 1 · 삭제 0 — 두 릴리스 규칙 미해당.
--
-- ① A3 — logistics.inbound_receipt_line.lot_id
--    계약 `InboundReceiptLine.lotId` 가 앵커(x-source-column) 없이 선 자리다.
--    ⛔ 「lot.source_type_code='INBOUND_RECEIPT_LINE' AND lot.source_id = <라인>」 역조회로
--       대신할 수 «없다» — 세 가지 이유가 있다.
--       ⓐ trace.lot 에 (source_type_code, source_id) 유일 제약이 없어 역조회가 여러 행을
--          돌려줄 수 있는데 계약의 lotId 는 «단수»다.
--       ⓑ GET .../lines 의 labelIssued 필터가 「그 라인의 LOT 에 발행 기록이 있는가」다.
--          칸이 있으면 관계 필터 한 줄(lot -> document_issue_log)로 접히고, 없으면
--          다형 축(source_id)을 Prisma 관계로 못 태워 원시 SQL 로 내려가야 한다.
--       ⓒ 계약이 lotId 를 type:[integer,null] 로 적었다 — required 가 아니어도 «널로
--          내려야» 하므로 칸이 필요하다(I-2 R-7 이 approval_request_id 에서 같은 판정).
ALTER TABLE logistics.inbound_receipt_line
    ADD COLUMN lot_id bigint
        REFERENCES trace.lot(lot_id);

COMMENT ON COLUMN logistics.inbound_receipt_line.lot_id IS
    '이 라인으로 만들어진 자재 LOT. 사전부착 라인은 입하 등록과 같은 트랜잭션에서, '
    '미부착 라인은 POST /trace/lots(P-01-01)가 채운다. 계약 InboundReceiptLine.lotId.';

-- labelIssued·「LOT 이 붙은 라인은 못 지운다」 판정이 이 축으로 돈다.
CREATE INDEX ix_inbound_line_lot
    ON logistics.inbound_receipt_line(lot_id);

-- ② V-inbound_variance — reason_code 의 NOT NULL 해제
--    계약 InboundVarianceCreate 의 required 에 reasonCode 가 없고 설명이
--    「⛔ 선택이다 … 현장이 사유를 모를 때 오류 기록 자체가 막히면 안 된다」이다.
--    M-01-06 §6 도 「사유 미선택 — 막지 않는다」. README §5(물리가 계약을 따른다).
ALTER TABLE logistics.inbound_variance
    ALTER COLUMN reason_code DROP NOT NULL;
```

- ⛔ **FK 이름을 짓지 않는다.** `ADD COLUMN … REFERENCES` 는 Postgres 가 `inbound_receipt_line_lot_id_fkey`(Prisma 기본형)로 이름 짓는다 — I-2 의 `source_inbound_receipt_line_id` 와 같은 형태다(`fk_*` 로 지으면 `migrate diff` 가 드리프트를 낸다).
- ⛔ **인덱스 이름은 `@@index(map:)` 에 그대로 적는다** — 안 적으면 Prisma 가 `inbound_receipt_line_lot_id_idx` 를 기대해 드리프트가 난다.
- ⛔ **`plan.md` §4 행 N(`x-no-code-key` 16자리 `status_code` NOT NULL 해제)은 이 슬라이스에서 «걸지 않는다»** — §5-4 판정. 그 판정이 §0 #10 과 갈리는 자리라 §9 에 정정으로 올린다.
- **백필 0** — `lot_id` 는 새 칸이라 기존 행이 없다(`inbound_receipt_line` 은 e2e 픽스처 말고 실데이터가 없다).

## 3. P/O 귀속 — `purchase_order_line.received_qty`

### 3-1. 언제 올리나 (오퍼레이션별)

| 오퍼레이션 | `received_qty` | 근거 |
|---|---|---|
| `POST /logistics/inbound-receipts` | 라인의 `purchaseOrderLineId` 가 있으면 **`+= receivedQty`** | `AsnLine.receivedQty` 설명 「그 P/O 라인의 **누적 입하 수량**」 · `M-01-01` §5-2 「누적 입하량(`purchase_order_line.received_qty`)」 · §5-2-1 「`received_qty`(**누적·서버 갱신**)」 |
| `PUT …/{id}/lines`(치환) | **차분**: 옛 라인 집합의 `(po_line_id → Σqty)` 와 새 집합의 차이만큼 올리고 내린다. 삭제·수량 변경·귀속 대상 변경 셋 다 이 한 맵으로 처리 | 치환은 「요청에서 빠진 기존 행은 삭제한다」라 옛 기여분을 되돌리지 않으면 누적이 영원히 부풀어 오른다 |
| `PUT …/{id}`(헤더 수정) | **건드리지 않는다** — 본문에 라인이 없다 | 계약 |
| `POST …:split` | **정량분 라인만** 올린다. **초과분 라인은 `purchase_order_line_id` 가 NULL 이라 올릴 대상이 없다** | `W-01-03` §4-B 「초과분 라인 `purchase_order_line_id` = ⚠ **NULL** — P/O 비귀속」 |
| `POST …/variances` | **건드리지 않는다** — §4-3 | 계약이 한 마디도 안 했다 |
| 취소(되돌림) | **I-5 의 몫** | `plan-integration.md` §2 다형 취소 |

### 3-2. 잠금 순서 — ⭐ 이 슬라이스의 핵심 판정

**무엇이 문제인가.** I-2 의 `purchase-order.service.ts:replaceLines` 는 `received_qty` 를 **잠그지 않고 손검사한다** —
`tx.purchase_order_line.findMany({select:{received_qty}})` 로 읽고 `assertLinesFit` 이 `orderedQty + toleranceOverQty >= received_qty` 를 본다.
입하 등록이 같은 순간 `received_qty` 를 올리면 두 방향 모두 사고다.

| 순서 | 결과 |
|---|---|
| P/O 치환이 «옛» `received_qty` 를 읽고 발주를 낮춤 → 커밋 → 입하가 올림 | 입하 커밋에서 `ck_po_line_received` 위반 → **500**(CHECK 는 `PrismaClientUnknownRequestError` 라 공용 그물에 안 걸린다 — `prisma-error.ts` 주석) |
| 입하가 올림(미커밋) → P/O 치환이 옛 값을 읽고 통과 → 입하 커밋 → 치환 커밋 | 치환의 raw UPDATE 에서 같은 CHECK 위반 → **500** |

**⭐ 판정 — 입하 쓰기는 귀속 대상 라인의 «부모 `purchase_order` 행»을 `SELECT … FOR UPDATE` 로 먼저 잠근다.**

```
1. (트랜잭션 밖) 검증 → numbering.next(...)  ← I-2 R-2
2. $transaction 시작
3. 이 요청이 건드리는 purchase_order_id 를 «오름차순 정렬»해 한 문장으로 잠근다
     SELECT purchase_order_id FROM logistics.purchase_order
      WHERE purchase_order_id = ANY($1) ORDER BY purchase_order_id FOR UPDATE
4. 잠근 뒤 purchase_order_line 의 ordered_qty·tolerance_over_qty·received_qty 를 «다시» 읽는다
5. 손검사(§3-3) → 통과하면 received_qty increment
6. inbound_receipt / _line / trace.lot 을 쓴다
7. 커밋
```

- **왜 부모인가.** `replaceLines` 는 `tx.purchase_order.updateMany({where:{id, version_no}, data:{version_no:{increment:1}}})` 로 **부모 행에 배타 잠금을 이미 건다**(라인을 만지기 «전»에). 입하가 같은 부모 행을 잠그면 두 경로가 **같은 자물쇠**에서 직렬화된다 — 라인만 잠그면 치환의 «삭제 후 재삽입» 경로와 어긋난다.
- ⭕ **I-2 코드를 고치지 않는다.** 잠금 획득 순서가 양쪽 다 「부모 → 라인」으로 같다. 치환의 조건부 UPDATE 가 0행이면 잠금을 안 남기지만, 그때는 `assertUpdated(0)` 이 409 로 끝나 무해하다.
- **데드락 회피** — 한 입하가 여러 P/O 라인을 실을 수 있고 두 입하가 서로 다른 순서로 두 P/O 를 잡으면 교착한다. ⇒ **`purchase_order_id` 오름차순 한 문장**으로 잠근다(`ORDER BY … FOR UPDATE`). 라인은 따로 안 잠근다 — 라인은 언제나 부모를 거쳐서만 바뀐다.
- ⚠ **채번은 잠금 «전»이다**(I-2 R-2). 잠근 채로 채번하면 카운터 대기가 부모 잠금을 물고 늘어진다.
- ⚠ `:split` 도 같은 절차를 탄다 — 다만 정량분 쪽 라인만 잠금 목록에 들어간다.

### 3-3. `ck_po_line_received` 를 500 으로 안 새게 하는 손검사

```
CONSTRAINT ck_po_line_received CHECK (received_qty <= ordered_qty + tolerance_over_qty)
```

- 잠금 뒤 라인마다 `received_qty + Δ <= ordered_qty + tolerance_over_qty` 를 본다. 넘으면 **400 `QTY_EXCEEDS_ORDERED`**(field = `lines.{i}.receivedQty`).
- ⛔ **`Decimal` 로 비교한다** — `Number()` 로 바꿔 비교하면 `@db.Decimal(20,6)` 의 끝자리에서 판정이 갈린다(I-2 `assertLinesFit` 이 `Number()` 를 쓴 자리는 «반대 방향» 검사라 오차가 안전한 쪽으로 났다).
- ⛔ **정상 흐름에서는 이 400 이 안 나온다.** `M-01-01` §5-2 가 화면에서 「남은 예정 + `tolerance_over_qty`」로 판정해 초과면 `W-01-03` 으로 보낸다. 이 400 은 **화면을 거치지 않은 직접 POST** 의 그물이다.
- ⭐ 화면의 판정식과 서버의 CHECK 는 **같은 축**이다 — `M-01-01` §5-2 「「실입하 > 남은 예정 + 허용치」는 「누적 + 실입하 > 발주 + 허용치」와 **같은 식**이다」. 그래서 서버는 화면 규칙을 다시 발명하지 않고 CHECK 를 손으로 앞당길 뿐이다.

### 3-4. I-2 R-12 ② 「발주수량 < 초과분 수량」의 서버 대응

`W-01-11` §6 의 「발주수량 < 초과분 수량 → 인라인 오류」는 **화면 쪽 방어**이고, 서버 쪽 대응이 없었다.
이 슬라이스가 세우는 것은 **반대 방향의 자물쇠**다 —

| 방향 | 누가 막나 | 자리 |
|---|---|---|
| 「이미 받은 수량보다 «적게» 발주한다」 | I-2 `assertLinesFit`(`ERROR_CODE.RANGE`) | 이미 있다 |
| **「발주보다 «많이» 받는다」** | **I-3 `QTY_EXCEEDS_ORDERED`** | 이 슬라이스 |
| 두 방향이 **동시에** 일어난다 | **§3-2 의 부모 잠금** | 이 슬라이스 |

⇒ R-12 ② 는 **셋째 줄이 실체**였다 — 값 검사가 아니라 «경합»이 문제였다. 단독 요청 둘은 각자의 손검사로 이미 막힌다.

### 3-5. 입하가 P/O 승인 상태를 보는가 — **보지 않는다** (§2 절차)

- **0단계 선례**: 입하 계약 12건의 `description`·`x-*`·`requestBody` 전문에 **승인 문장이 0건**이다(실측). `InboundReceiptCreate.x-internal-note` 는 반대로 「⚠ **승인 절차 자체(누가·언제)는 아직 정해지지 않았다** — M-01-01 §8-4. 계약은 `approvalRequestId` 자리만 갖는다」라 적었고, `InboundReceipt.approvalRequestId` 는 「⚠ 무발주 예외 입하에는 «**별도 승인을 걸지 않는다**»(확정 2026-09-02 · omf-mes#348) … **이 자리를 채울 상신 오퍼레이션도 없다**」다.
- **1단계**: 모든 입하의 결과가 달라지므로 **본길**처럼 보인다 → 임의로 못 고른다 → **계약 문자 그대로**. 계약은 「보라」고 안 했다 ⇒ 보지 않는다.
- **2단계**(확인용): 기준 1「상태를 쓰지 않는 쪽」 · 기준 5「새 개념 0」 둘 다 같은 답.
- **I-2 §5-4 와 이어 붙는다**: 「승인이 끝난 뒤 P/O 는 아무도 안 옮긴다 … P/O 의 후속은 `W-01-03` 의 초과분 귀속인데 그것은 `inbound_receipt_line.purchase_order_line_id` 를 채우는 **I-3 의 일**이고, **입하 계약에 승인 확인 문장이 없다**」 — 실측으로 확인했다. **끊긴 자리는 그대로 끊긴 채 둔다**(문의 023 의 몸).
- ⇒ **`assertApproved` 를 부르지 않는다.** I-2 R-9 의 「첫 사용처는 I-4(`goods-issues:post`)」가 **유지**된다.
- **3단계 흔적**: e2e 이름 `입하 — 승인되지 않은 P/O 에도 입하가 붙는다(계약에 승인 문장이 0건이다 — 문의 023)`.

### 3-6. `source_inbound_receipt_line_id` 로 초과분 P/O 를 만드는 흐름 — **이 슬라이스가 아니다**

- `W-01-03` §5-5 「등록 후 분기 — [입고 진행] → **`W-01-11` 신규 P/O 등록** → 초과분을 그 P/O 에 귀속」 · §5-1 액션표 「신규 P/O 등록 | 등록 완료 후 | **없음 — 소관 이동.** `W-01-11` §5-3」.
- 서버 쪽은 **I-2 가 이미 다 세웠다** — `PurchaseOrderCreateInput.sourceInboundReceiptLineId` 가 실재하고(`purchase-order.service.ts:create`) A2 마이그레이션도 병합됐다.
- ⇒ I-3 은 **그 칸을 읽지도 쓰지도 않는다.** 다만 **e2e cleanup 순서**에는 걸린다(§6-4 · R-12 ①).

## 4. `:split` · 차이(variance)

### 4-1. `:split` — 무엇이 서고 무엇이 안 서나

| 항목 | 판정 | 근거 |
|---|---|---|
| 만드는 것 | `mode` 에 따라 `inbound_receipt` **1~2건** + 각 헤더의 라인 + 사전부착 라인의 LOT | 계약 응답 「mode 에 따라 1건 또는 2건」 |
| 트랜잭션 | **한 `$transaction`** — 부분 실패 없음 | 계약 `x-internal-note` · `W-01-03` §5-4 「둘 중 하나만 저장되면 안 된다」 |
| 정량분 라인 | `purchase_order_line_id` **채운다** → §3 귀속을 탄다 | `W-01-03` §4-B |
| 초과분 라인 | `purchase_order_line_id` **NULL** → 귀속 안 함 | `W-01-03` §4-B 「⚠ NULL — P/O 비귀속」 · 태그 「P/O 비귀속」 |
| 초과분 헤더 | `exception_type_code` 를 **요청이 준다**(서버가 `OVER_DELIVERY` 를 강제하지 않는다) | `SplitPart.exceptionTypeCode` 가 요청 칸이고 example 이 `OVER_DELIVERY` 일 뿐 enum 이 아니다 — §2 기준 4(조용히 도출하지 않는다) |
| `mode` ↔ `normal`/`excess` 정합 | **서버가 400 으로 막는다** — 계약이 「목 서버·검증기는 mode 와 어긋나는 조합을 통과시킨다」라 **가드가 못 막는 것을 스스로 적었다** | `x-internal-note` |
| 응답 | `{created: [...]}` — `mode` 순서대로(정량분 먼저, 초과분 뒤) | 계약이 순서를 안 적었다 → 요청 순서 그대로가 지어내지 않는 쪽 |

### 4-2. 원본 처분 — **원본은 저장된 적이 없다** (§2 0단계에서 끝난다)

`plan-api.md` S02 가 「`:split` 이 원 전표를 어떻게 두는가 … §2 1단계 = 본길이라 **계약 문자 그대로**(두 건을 새로 만들고 원본은 안 건드림) + 문의」로 초안을 잡았다. **실측 결과 문의가 필요 없다.**

- 요청 `InboundReceiptSplitRequest` 에 **원본을 가리키는 칸이 하나도 없다**(`mode`·`normal`·`excess`·`businessDate`·`occurredAt` 다섯이 전부).
- `W-01-03` §5-1 액션표: 「**취소** | 항상 | 원 도착으로 복귀 — **아직 아무것도 저장되지 않았다**」.
- `W-01-03` §4-A: 두 건의 `inbound_receipt_no` 가 「MES 채번」·「**별도 채번** — 노트B 「입하 번호 2건」」 ⇒ **총 2건**이지 3건이 아니다.
- 진입 경로가 `M-01-01`(모바일 입하 «검증» 중)이라 원 도착은 **화면의 미저장 초안**이다.

⇒ **판정: 원본 처분 로직이 없다.** 「안 건드림」이 아니라 **「건드릴 것이 없다」**이다. `plan-api.md` S02 의 문의 초안을 **철회**한다(§9 #3).
**3단계 흔적**: e2e 이름 `분리 — 요청이 원본 입하를 가리키지 않는다(원 도착은 저장된 적이 없다 — W-01-03 §5-1)`.

### 4-3. 채번 2회 — 트랜잭션 «밖» · 실패 시 번호 소모

- I-2 R-2 그대로: `$transaction` 을 **열기 전** `mode` 를 보고 필요한 만큼(1 또는 2) `numbering.next('INBOUND_RECEIPT', plantId, businessDate)` 를 부르고 **문자열만** 트랜잭션에 넘긴다.
- ⚠ **정량분과 초과분의 `plantId` 가 다를 수 있다**(`SplitPart` 마다 `plantId` 가 required 다). 각 part 의 `plantId` 로 각각 부른다 — 공장 지정 규칙이 갈릴 수 있다.
- ⛔ **입고의 `NUMBER_RETRY` 재시도 루프를 복사하지 않는다** — I-2 가 「카운터가 `INSERT … ON CONFLICT … RETURNING` 한 문장이라 동시 등록도 값이 안 겹친다」로 P/O 에서 이미 뺐다. 남는 위험(이관·수기로 심긴 `inbound_receipt_no`)은 P2002 → 400 `UNIQUE_VIOLATION` 으로 그대로 나간다.
- ⚠ **알려둘 것** — 트랜잭션이 굴러떨어지면 뽑아 둔 번호 1~2개가 **결번**이 된다. I-2 R-2 ③ 이 허용한 범위이고 `:split` 은 한 요청이 «둘»을 소모한다는 점만 다르다.

### 4-4. 차이(variance) — 무엇을 검증하고 무엇을 안 하나

| 물음 | 판정 | 근거 |
|---|---|---|
| 등록 대상 라인의 **상태 제약** | **없다 — 안 건다** | 계약이 한 마디도 안 했고, 라인 `status_code` 는 값 목록 자체가 없어(§5-4) 걸 축이 없다. §2 2단계 기준 3·5 |
| **유형** 검증 | `assertCodeValues(… groupCode:'INBOUND_VARIANCE_TYPE')` — 시드 3값 `SHORTAGE`·`ITEM_MISMATCH`·`UNREGISTERED_ITEM` | 계약 `x-code-key` + 시드(`seed.ts:427`) |
| **사유** 검증 | 값이 «있을 때만» `INBOUND_VARIANCE_REASON`(시드 5값) 검사. **없어도 통과** | 계약 「⛔ 선택이다」 · `M-01-06` §6 「사유 미선택 — 막지 않는다」 |
| `varianceQty` **상한** | ⛔ **안 건다** | 계약이 상한을 안 적었다. `M-01-06` §6 의 「차이(20 EA)보다 큰 수량을 등록할 수 없습니다」는 **인라인(화면) 오류**이고, 서버가 비교할 축이 무발주 라인에는 아예 없다(발주 수량이 없다). §2 2단계 기준 4(값을 조용히 도출하지 않는다) |

| 없는 라인에 등록 | **404**(계약 미선언) | I-2 R-1 과 같은 형태 — 「알려둘 것」 |

## 5. LOT · 상태기계

### 5-1. LOT — 누가 채우나

| 라인 | LOT 생성 시점 | `lot_id` 를 채우는 자리 |
|---|---|---|
| **사전부착**(`supplierLotMissing=false` · `supplierLotNo` 있음) | **입하 등록과 같은 트랜잭션** | I-3 의 등록 서비스 |
| **미부착**(`supplierLotMissing=true`) | 나중에 `POST /trace/lots`(`numberSourceCode=MES` · P-01-01) | **I-3 이 `lot.service.ts` 에 3줄을 더한다** — `sourceTypeCode='INBOUND_RECEIPT_LINE'` 이면 그 라인의 `lot_id` 를 같은 트랜잭션에서 채운다 |

- **되짚기 흐름은 이미 절반 서 있다** — `lot.source_type_code='INBOUND_RECEIPT_LINE'`·`source_id=<라인 id>` 를 `LotService.insert` 가 이미 쓴다(`SOURCE_TYPES = ['INBOUND_RECEIPT_LINE']` 로 닫혀 있다). A3 는 **반대 방향**을 잇는다(§2-6 ⓐⓑⓒ).
- ⭐ **누가 사전부착 LOT 을 만드는가** — `M-01-01` §5-4 가 2026-09-02(`omf-mes#354`)에 갈랐다: 「**사전부착 LOT 을 만드는 것은 이 화면이다 — `M-01-02` 는 «보완»이다** … 두 스펙이 같은 경로를 각자 자기 것으로 적고 있어 **같은 LOT 이 두 번 만들어질 수 있었다**(뒤엣것이 `UNIQUE(plant_id, lot_no)` 로 400 이 된다)」.
- **입하 등록이 LOT 에 넣는 값** — `lot_no` = 라인의 `supplierLotNo`(계약 `numberSourceCode=SUPPLIER` 축) · `item_id`·`uom_id` = 라인 · `plant_id` = 헤더 · `initial_qty` = `receivedQty` · `expiry_date` = 라인의 `expiryDate` · `lot_type_code` = **`MATERIAL`**(시드 `LOT_TYPE` 3값 `MATERIAL`·`PRODUCTION`·`PRODUCT` 중 자재 입하가 고를 수 있는 하나) · `status_code` = `INSPECTION_PENDING` · `lot_hold` 1행(`INCOMING_INSPECTION_WAIT` · `HELD`).
- ⛔ **`manufactured_at` 을 채우지 않는다.** 라인의 `manufactured_date` 는 `@db.Date` 이고 `lot.manufactured_at` 은 `timestamptz` 다 — 날짜를 시각으로 올리려면 타임존을 골라야 하는데 CLAUDE.md 가 「날짜 타임존 캐스팅 금지」다. §2 2단계 기준 4(값을 조용히 도출하지 않는다) ⇒ **비워 두고 날짜는 라인에 그대로 남긴다.** 「알려둘 것」.
- ⛔ **`POST /trace/lots` 를 HTTP 로 부르지 않는다.** 「입하·라인·자재 LOT 이 **한 트랜잭션**」이라 같은 `tx` 안에서 서야 한다. `LotService.insert` 는 자기 `$transaction` 을 열므로 **`createWithin(tx, …)` 를 뽑아 둘이 함께 쓴다**(`TraceModule` 이 `LotService` 를 export, `LogisticsModule` 이 import). 코어로 승격하지 않는다 — 사용처가 둘이고 `plan.md` §3 코어표에 LOT 등록이 없다(§9 #5).
- **`Lot.receiptDispositionCode`** — `plan-integration.md` §3-1 I-3 의 판정(「본길이 아니다 → 1단계 가장자리 → 3「스키마를 안 늘리는 쪽」 → **칸을 빼고 요청서에 남긴다**」)을 **그대로 유지**한다. 되돌림 §Z-5 가 이미 「응답에서 칸을 빼고 필터는 받지 않는다」로 서 있고 「필요한 답」도 보냈다. **I-3 은 이 값을 만들지도 읽지도 않는다.**

### 5-2. `inspection_required` — 서버가 채운다 (§2 절차)

- **계약**: 「이 라인이 수입검사 대상인지. 입하 라인 단위로 갈린다. **서버가 채운다 — 요청 스키마 `InboundReceiptLineUpsert` 에 이 칸이 없다.**」 실측 확인 — 요청 스키마에 없다.
- **0단계 선례**: 계약 `x-internal-note` 가 후보를 직접 지목했다 — 「판정 원천 미확정 — 미결 대장 M-01-01 #3(품목 속성·공급사·정책 중 미정). **계약에 이미 있는 후보는 `mdm-기준정보.json` `Item.inspectionRequired`**(default false · 「MES 확장 · W-01-01 IQC 대상 판정의 입력」)이고 W-06-05 §4 가 편집 화면을 둔다(근거 강도 [추정])」. 물리도 있다 — `mdm.item.inspection_required Boolean @default(false)`(실측).
- **1단계**: 모든 라인이 값을 가져야 하므로 **본길**. 그러나 계약 문자가 후보를 **하나만** 적었고 나머지 둘(공급사·정책)은 **물리에 칸이 없다** ⇒ 지어내지 않고 그 하나를 쓴다.
- **판정**: `inspection_required = item.inspection_required`(품목 승계). NULL 인 품목은 `false`(칸이 `@default(false)` NOT NULL 이라 NULL 이 없다).
- ⭕ **`W-01-03` §8 #3(초과분도 IQC 대상인가)이 함께 해소된다** — 초과분 라인도 같은 품목이라 같은 값이 나온다. 「승계할지 별도 판정할지」의 물음이 성립하지 않는다.
- **3단계 흔적**: 단위 테스트 `등록 — inspectionRequired 는 품목 마스터에서 읽는다(요청 스키마에 칸이 없다 — M-01-01 §8 #3)` + 코드에 `// 판정 원천 미확정 — M-01-01 §8 #3`.

### 5-4. `inbound_receipt_line.status_code` — 값 목록이 없다 (§2 절차 · ⚠ `plan.md` §0 #10 과 갈린다)

- **실측**: 물리 `status_code app.code_t NOT NULL`. 계약 `InboundReceiptLine.statusCode` 는 **required** 이고 `x-no-code-key` 가 「코드 그룹을 세우지 않는다 — **라인 진행은 `supplierLotMissing`·`labelIssued`·`inspectionRequired`·`lotId` 네 축이 이미 담는다**(A-21)」라 적었다. `M-01-01` §8 #1 도 「⚠ 라인은 아직 사전 키가 없다」.
- **0단계 선례**: `trace.lot_hold.status_code` 가 같은 자리였고 되돌림 §Z-3 이 「값 목록이 없다 → **`HELD` 를 넣는다** · ⛔ **판정은 이 값으로 하지 않는다**(`released_at IS NULL` 로만 가른다)」로 갈랐다. 상수 하나 + 「그 값으로 판정하지 않는다」가 이 저장소의 선례다.
- **1단계**: 모든 라인이 값을 가져야 하니 본길 — 그러나 계약이 「값으로 분기하지 않는다」(G-2)라 **어느 문자열이든 결과가 같다** ⇒ 가장자리로 읽는다.
- **2단계**: ⛔ **기준 3「스키마를 안 늘리는 쪽」이 `plan.md` §0 #10(nullable) 을 «지지하지 않는다»** — `NOT NULL` 해제도 스키마 변경이고, 무엇보다 **계약이 이 칸을 `required` 로 적었다.** 널이면 응답에 실을 값이 없고, 키를 생략하면 `required` 를 깬다(`plan.md` §5 규칙 7 「값 없는 칸 — 키 생략(널 금지)」이 required 칸에는 못 선다). ⇒ nullable 은 문제를 옮길 뿐 풀지 않는다.
  다음 기준 5「새 개념 수가 적은 쪽」 → **같은 도메인에 이미 시드된 문자열을 재사용한다**.
- **판정**: `status_code = 'REGISTERED'` 고정(`LOGISTICS_DOCUMENT_STATUS` 의 첫 값 · 부모와 같은 값). 마이그레이션 0. ⛔ **이 값으로 아무 판정도 하지 않는다** — 라인 진행은 계약이 적은 네 축으로만 읽는다.
- ⚠ **I-2 e2e 픽스처는 `'RECEIVED'` 를 넣었다**(`test/logistics-purchase-order.e2e-spec.ts:638`) — 픽스처이지 판정이 아니므로 **고치지 않는다**(그 스위트는 이 값을 읽지 않는다). I-3 의 새 e2e 는 `'REGISTERED'` 로 선다.
- **3단계 흔적**: 상수에 이름(`const LINE_STATUS = 'REGISTERED'`) + 주석 `// 값 목록 없음(x-no-code-key · A-21) — 이 값으로 판정하지 않는다`. 「알려둘 것」에 한 줄(§7-6).
- ⇒ `plan.md` §4 행 N 은 **이 슬라이스에서 걸지 않는다** · §0 #10 을 「계약이 `required` 로 안 적은 자리에만 선다」로 좁히자고 §9 에 올린다.

## 6. 횡단 · e2e 정리 순서

### 6-1. 403 게이트 — 등록 **3건**(5건 중 2건은 이미 있다)

`derived-permissions.ts` 실측 — 이미 있는 것: `POST /logistics/inbound-receipts`: `['M-01-01']`(:173) · `POST /logistics/inbound-receipts:split`: `['W-01-03']`(:174).
`manual-permissions.ts` 에 **새로 3건** — `plan-api.md` §5.3 ① 의 S02 행과 **정확히 같다**.

```ts
// `M-01-01` 입하 등록 — 도출표에 POST 만 들어왔다(§3 이 등록 액션만 적었다).
// 헤더·라인 수정은 같은 화면의 같은 자원이다(등록 폼 안의 라인 그리드 · §5-4).
'PUT /logistics/inbound-receipts/{inboundReceiptId}': ['M-01-01'],
'PUT /logistics/inbound-receipts/{inboundReceiptId}/lines': ['M-01-01'],
// `M-01-06` 입하 오류 등록 — 그 화면이 이 자원의 유일한 소유자다(계약 description 근거).
'POST /logistics/inbound-receipt-lines/{inboundReceiptLineId}/variances': ['M-01-06'],
```
- ⛔ **도출표와 겹치면 검사가 막는다**(`manual-permissions.ts` 머리 주석) — 위 셋은 도출표에 없다(실측).
- ⚠ 조회 넷도 도출표에 있으나(`GET /logistics/inbound-receipts`: `['M-01-02','P-01-01','W-01-10']` 등) **계약이 403 을 선언하지 않아 가드가 보지 않는다** — 무해, 지우지 않는다.
- ⛔ 등록이 없으면 `PermissionGuard` 가 던져 **500** 이 된다(F-6) — 구현과 **같은 PR**에 싣는다.

### 6-2. 멱등 — 쓰기 5건 전건

| 오퍼레이션 | `successStatus` |
|---|---|
| `POST /logistics/inbound-receipts` | `CREATED`(201) |
| `POST /logistics/inbound-receipts:split` | `CREATED`(201) |
| `POST …/variances` | `CREATED`(201) |
| `PUT …/{id}` | `OK`(200) — `runVersioned` |
| `PUT …/{id}/lines` | `OK`(200) — `runVersioned` |

⚠ **채번은 `runIdempotent` 트랜잭션 «안»에서 돈다**(I-2 R-10 ⓕ) — 업무 `$transaction` 밖이지만 멱등 기록 트랜잭션 안이라 요청당 커넥션 2다(main 과 같다). `:split` 은 그 안에서 `next()` 를 **둘** 부른다 — 커넥션 수는 그대로다(순차 호출).

### 6-3. If-Match 3건 · ETag 3건 — ⛔ 함정 둘

| 자리 | 판정 |
|---|---|
| `PUT …/{id}` · `PUT …/lines` = **필수** | `IfMatchVersion` 가드 그대로. **둘 다 부모 `inbound_receipt.version_no`** 를 본다 — 계약이 `PUT …/lines` description 에 「**잠그는 단위가 부모이기 때문이다**(B-1-1)」로 못박았다 |
| `PUT …/lines` 의 응답 ETag | ⛔ **안 내린다.** 계약이 헤더를 선언하지 않았다. **P/O 라인 치환은 내렸다** — 그쪽은 계약이 헤더를 선언했기 때문이다(I-2 §6-3). 같은 모양이라고 복사하면 안 되는 자리 |
| `PUT …/lines` 가 부모 `version_no` 를 **올리나** | ⭕ **올린다** — 라인이 바뀌면 부모 상세의 내용이 바뀌고, 다음 If-Match 는 부모 상세 GET 이 준다. 계약이 ETag 를 안 내리므로 **화면은 상세 GET 을 다시 돈다** — 「알려둘 것」 |
| `POST /logistics/inbound-receipts` 의 **「선택」** | 계약 `IfMatchVersionOptional` + `x-internal-note` 「**오프라인 대상 오퍼레이션이다** … **큐는 낙관적 잠금 토큰을 싣지 않는다**(C-9)」. ⛔ **새 자원을 만드는 POST 라 대조할 버전이 없다** — 가드는 `requirement()` 그대로 두고(조이지도 풀지도 않는다 · `plan.md` §5 규칙 3) **서비스는 값을 무시한다.** 있어도 400 을 내지 않는다 |
| `POST …:split` 에는 If-Match 가 **아예 없다** | 같은 오프라인 축인데 갈렸다 — 「알려둘 것」 |
| ETag 3 = `POST /inbound-receipts` 201 · `GET /{id}` 200 · `PUT /{id}` 200 | `setEtag(response, versionNo)`. ⛔ **본문 필드로 안 내린다**(A-4) |

### 6-4. `@Contract` · `X-Worker-No` · 그 밖

- `@Contract('METHOD /path')` 12건 전건. `:split` 은 `@Post('\\:split')` 형태(경로에 콜론 — I-2 `:request-approval` 선례).
- 409 봉투는 **기본 `ConflictResponse`** — 도메인 전용 넷(`Production`·`Quality`·`Shipment`·`StockReinstatement`)에 입하가 없다(실측).
- `X-Worker-No` 2건(등록·차이 등록) — 「누가 어느 단말에서」 덧붙임. **헤더가 없어도 400 을 내지 않는다**(`plan.md` §5 규칙 9). 주체는 계정 세션(`created_by`·`received_by`).
- ⚠ **`received_by` 를 무엇으로 채우나** — 요청 스키마 셋 어디에도 `receivedBy` 칸이 없고 응답에는 있다. §2 2단계 기준 4 → **계정 세션의 `app_user_id`**(주체는 계정 세션 · `plan.md` §5 규칙 9). `created_by` 와 같은 값이 된다 — 「알려둘 것」.
- `assertDay`/`assertInstant` 는 지금 `src/trace/lot/lot-rules.ts` 에 있다. ⛔ **도메인을 가로질러 import 하지 않는다** — 입고 선례대로 인라인 정규식 두 줄을 쓴다(CLAUDE.md 「CRUD 는 기존 모듈 패턴 복제」·「사용처 하나뿐인 추상화 금지」). 사용처가 넷째로 늘면 `common/master` 로 옮기는 것이 옳다 — 이번엔 아니다.

### 6-5. e2e 정리 순서 — 순환 FK (I-2 R-12 ① 인계)

**순환**: `purchase_order.source_inbound_receipt_line_id → inbound_receipt_line → purchase_order_line → purchase_order`.

⭐ **I-3 e2e 는 `sourceInboundReceiptLineId` 를 채운 P/O 를 만들지 않는다** — 그 흐름은 `W-01-11`(I-2)의 것이고 이 슬라이스 밖이다(§3-6). 그러면 순환이 «데이터에» 실재하지 않아 아래 한 방향 순서로 충분하다.

```
① logistics.inbound_variance         (inbound_receipt_line 자식)
② logistics.inbound_receipt_line     ← 여기서 lot_id 가 trace.lot 을 가리킨다
③ logistics.inbound_receipt
④ trace.lot_hold → trace.lot_external_identifier → trace.lot   ← ⭐ 입하 등록이 새로 만든다
⑤ logistics.asn_line → logistics.asn
⑥ logistics.purchase_order_line → logistics.purchase_order
⑦ mdm.item → mdm.partner → mdm.location → mdm.warehouse → mdm.plant → business_unit → legal_entity
⑧ app_user·role (P/O e2e 와 같은 꼬리)
```
- ⭐ **②가 ④보다 «먼저»다** — A3 로 `inbound_receipt_line.lot_id → trace.lot` FK 가 생기므로 LOT 을 먼저 지우면 FK 위반이다. **P/O e2e 에는 없던 순서**다.
- ⚠ **만약** 뒤에 이 스위트가 초과분 → 신규 P/O 흐름까지 e2e 로 잇게 되면, ② 앞에 한 줄이 더 필요하다:
  `UPDATE logistics.purchase_order SET source_inbound_receipt_line_id = NULL WHERE plant_id IN (…)`.
  (P/O 를 먼저 지우는 I-2 의 처방은 이 스위트에선 못 쓴다 — 입하 라인이 P/O 라인을 가리켜 P/O 를 먼저 못 지운다. **NULL 로 끊는 쪽이 두 스위트 모두에서 선다** — I-2 §8 PR ④ 주석보다 넓은 처방이다.)
- **P/O e2e 는 깨지지 않는다** — `test/logistics-purchase-order.e2e-spec.ts:804 cleanup()` 은 `PREFIX = 'POWE2E'` 의 plant 로만 좁히고, I-3 e2e 는 자기 PREFIX 를 쓴다. ⛔ 다만 그 스위트의 cleanup 은 `trace.lot` 을 **안 지운다** — I-3 이 A3 를 넣어도 그쪽은 LOT 을 안 만들므로 무해하다.
- **상수 충돌 실측** — 기존 둘은 `GRE2E`/`e2e-gr-probe`/`E2E_GR` 와 `POWE2E`/`e2e-po-write-probe`/`E2E_PO_WRITE`. I-3 은 **`IRE2E` / `e2e-ir-probe` / `E2E_IR`** 로 잡는다(겹침 0).
- ⚠ **브리프 전제 정정** — 「기존 입고 e2e 의 입하 픽스처」는 **없다.** `test/logistics-goods-receipt.e2e-spec.ts` 에 `inbound_receipt` 문자열이 0건이고(실측 grep), 입하 라인 픽스처를 세운 것은 **P/O e2e** 다(`inbound_receipt.create` + `inbound_receipt_line.create` — `status_code: 'RECEIVED'`). ⇒ **재사용도 대체도 없다.** I-3 은 자기 픽스처를 새로 세운다.
- **ASN 은 직접 INSERT** — 등록 경로가 계약에 없다(`x-internal-note` 「ERP 수신본이라 등록·수정·삭제가 없다」). `prisma.asn.create` + `asn_line.create`(P/O e2e:750 선례). `asn.status_code` 는 값 목록이 없으므로 픽스처가 아무 문자열이나 넣는다 — **우리 코드가 그 값을 읽지 않는다**(§2-1).
- ⛔ `numbering_counter` 는 지우지 않는다(I-2 R-10 ⓔ) — 번호 정규식은 `\d{4,}` 로 넓힌다.

### 7-2. 「작성중 상태에서만 허용한다」를 어떻게 구현하나

- 계약이 두 곳에 적었다(`PUT …/{id}` description · `x-internal-note` 「**확정·전기된 전표의 수정은 400 `STATE_LOCKED`**」).
- 「작성중」이 `LOGISTICS_DOCUMENT_STATUS` 4값에 **없다** ⇒ I-2 가 P/O 에서 이미 갈랐다 — 「값 목록에 「작성중」이 없어 `REGISTERED` 하나로 푼다」(`purchase-order.service.ts:update` 주석).
- **같은 판정을 복제한다**: `status_code !== 'REGISTERED'` 면 400 `STATE_LOCKED`.
- ⛔ **1차에 도달 불가능하다**(§5-3) — `REGISTERED` 밖으로 가는 오퍼레이션이 없다. ⇒ **e2e 로 못 세우고 단위 테스트로 세운다**(§8 PR ④ 단위 목록).

### 7-3. 계약에 있으나 담을 곳이 없는 칸 하나

`InboundReceiptCreate.deliveryNoteAttachmentId` — `x-source-column` 이 없는 유일한 요청 칸이고 `inbound_receipt` 에 자리가 없다.
**판정**: §2 2단계 기준 3(스키마를 안 늘리는 쪽) → **받아서 버린다**(400 을 내지 않는다). 첨부 자체는 I-34 이고 **바이너리 저장소가 없어 건너뛰는 오퍼레이션**이다(`plan.md` §6) — 칸을 만들어도 채울 값이 안 온다.
같은 자리의 OCR 파싱 결과도 계약이 「⚠ 담을 곳이 없다 … ✅ **계약 반영 완료** — 이슈 재발행(구 #75 대체)」로 **물음을 이미 세웠다**(`M-01-01` §8 #2) ⇒ 새 문의로 세우지 않는다. 「알려둘 것」.

### 7-4. ⭐ 계약이 안 적은 자물쇠 하나를 «건다» — 입고가 붙은 라인

- 계약은 「**LOT 이 이미 만들어진 라인은 지울 수 없다** — 400 `STATE_LOCKED`」만 적었다. 그런데 **수량 «수정»은 안 막고**, 미부착 라인(LOT 없음)은 삭제도 열려 있다. 그 사이 **입고가 그 라인을 소비했을 수 있다** — `goods_receipt_line.inbound_receipt_line_id` 가 실재하고 원장까지 갔다.
- **§2 1단계**: 「입고가 붙은 라인을 고칠 때만」 갈리므로 **가장자리**.
- **2단계 기준 2「거부하는 쪽」** — 거부→허용은 호환 완화, 허용→거부는 깨는 변경. 그리고 허용하면 **원장이 가리키는 근거가 사라진다**(되돌릴 수 없는 사고).
- **판정**: `goods_receipt_line` 이 붙은 입하 라인은 **삭제도 수량 변경도 400 `SUCCESSOR_EXISTS`**. 코드 이름은 I-2 가 이미 세운 것을 재사용한다(조회의 사유와 실행 오류가 같은 문자열 — `plan.md` §5 규칙 6).
- ⛔ **I-2 R-6 의 교훈을 그대로 복제한다** — 가드를 안 두면 FK 위반이 **500 으로 샌다**. 입하 라인의 자식은 셋이다: `inbound_variance` · `goods_receipt_line` · `purchase_order.source_inbound_receipt_line_id`. **셋 다 본다.**
- **3단계 흔적**: 코드에 `// 계약이 LOT 만 적었다 — 입고·차이·역참조 P/O 도 막는다(I-3.md §7-4)` + e2e 3줄.

### 7-5. 「알려둘 것」(번호 없음 · 다음 전달분 말미) — **8건 + 재수립 R-11 의 ⓘ~ⓡ 10건 = 18건**

ⓐ **`inbound_variance.reason_code` 의 `NOT NULL` 을 풀었다** — 계약이 「⛔ 선택이다」라 적었는데 물리가 필수였다. 데이터 모델 산출물에 반영이 필요하다.
ⓑ **`inbound_receipt_line.status_code` 에 `'REGISTERED'` 를 고정으로 넣는다** — 값 목록이 없고 계약이 `required` 라 널로 못 둔다. **이 값으로 아무 판정도 하지 않는다**(§5-4). `asn.status_code` 는 우리가 쓰지 않는다.
ⓒ **대상이 있는 쓰기 3건**(`PUT …/{id}` · `PUT …/lines` · `POST …/variances`)이 **404 미선언**인데 우리는 404 를 낸다(I-2 R-1 과 같은 형태 · 이번이 둘째).
ⓓ **`PUT …/lines` 는 200 에 ETag 를 안 내린다**(계약대로) — 화면이 다음 쓰기 전에 **상세 GET 을 다시 돌아야 한다**. P/O 라인 치환은 계약이 ETag 를 선언해 내리므로 **두 자원이 갈린다**.
ⓔ **`POST /logistics/inbound-receipts` 의 `If-Match`(선택)는 아무것도 안 한다** — 새 자원이라 대조할 버전이 없다. 같은 오프라인 축인 `:split` 에는 그 파라미터가 아예 없다.
ⓕ **`received_by` 를 계정 세션으로 채운다** — 요청 스키마에 칸이 없고 응답에는 있다. `created_by` 와 같은 값이 된다.
ⓖ **`lot.manufactured_at` 을 채우지 않는다** — 라인의 `manufactured_date` 는 date, LOT 은 timestamptz 라 타임존을 골라야 한다(CLAUDE.md 금지). 날짜는 라인에 남는다.
ⓗ **`inbound_receipt.approval_request_id` 와 `inbound_variance.approval_request_id` 는 1차 내내 빈다** — 계약이 「채울 상신 오퍼레이션이 없다」라 스스로 적었다(`InboundReceipt.approvalRequestId` · `M-01-01` §8 #4). 📨 데이터 모델 통지.
