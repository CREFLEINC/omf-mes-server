### 2-2. 왜 notification_event는 카탈로그가 아닌가

`occurred_at`과 aggregate가 유일 키의 일부이고 같은 event_type_code가 대상·시각별로 반복된다. event_name이 없고 title은 수신자별 notification에 있다. **발생 건수 0은 정의된 이벤트가 0이라는 뜻이 아니다.** DISTINCT(event_type_code), notification.title, payload를 이용해 목록이나 이름을 만들지 않는다. 이 표에 고정 이벤트를 시드하면 가짜 발생 기록이 생긴다.

### 2-3. 조건부 마이그: 기존 표의 이벤트 헤더 + 규칙 자식

정본 이벤트가 확정되고 §3 보류가 해소될 때만 적용한다. 기존 app_user_id·channel_code를 모두 nullable로 완화하고 둘 다 NULL인 행을 이벤트 헤더로 사용한다. 옛 사용자·채널 행은 둘 다 nonnull인 채 보존하며 신규 API가 조회·수정·삭제하지 않는다. 두 헤더 칸에 0, 관리자 계정, `SYSTEM` 사용자나 임의 채널 코드를 넣지 않는다.

Zalo와 version_no는 **헤더 1행**의 것이다. recipients가 0이어도 헤더는 남는다. 구독자의 수·현재 미리보기 인원·최종 저장자별로 토큰을 만들지 않는다. 기존 is_enabled는 신규 API의 의미로 읽지 않는다. 전용 카탈로그 테이블은 만들지 않는다(계약이 정의를 소유하고 편집 API가 없다).

## 3. 이벤트 정본과 보류 후보 3건

계약 GET 이벤트 description은 「발생 지점 표가 아직 비어 있다」고 적는다. 같은 operation의 x-internal-note는 사건명으로 고장·적정타수·P/O 변경·연계 실패·결재 도착의 발생 지점을 적지만 **eventCode 문자열은 미확정**이라고 명시한다. 검교정 만료 임박의 시간 트리거·임박 일수도 미확정이다. 이 둘은 정식 표와 내부 초안의 차이이므로 계약 모순으로 전 레인을 멈추지 않는다.

| 보류 후보 | 본길이 비는 이유 | 하지 않는 임의 선택 |
|---|---|---|
| GET events | required eventCode+eventName 목록의 코드 문자열 원천이 없음 | 사건명을 번역한 영문 코드, 한국어 사건명을 코드로 사용, 빈 배열을 「정의 0건」으로 반환, 발생이력 DISTINCT |
| GET subscriptions | 목록의 사건 행·초기 빈 수신자·이벤트 하나의 초기 토큰을 구성할 정본 이벤트 집합 없음 | 옛 사용자별 행을 이벤트 설정으로 합치기, 임의 eventCode마다 헤더 만들기, GET에서 데이터 생성 |
| PUT subscriptions | 어떤 eventCode의 설정을 허용하는지가 모든 성공 호출을 결정함 | 임의 문자열을 새 이벤트로 등록, 전건 400인 껍데기 핸들러를 구현 완료로 세기 |

README §2 **0단계**: 관련 코드·값 정의·확실한 권고안 없음 → **1단계 본길**, 계약도 문자열에 침묵하므로 해당 operation skip 후보. 통합자는 3관점 리뷰에서 이 범위를 확정한다. `plan-integration.md:438`의 「8건 전건 가능」과 차이가 있지만 통합 초안의 전망을 실제 원천 부재보다 우선하지 않는다.

알림 읽기는 저장된 event_type_code를 그대로 보여 줄 수 있고, preview는 eventCode를 아예 받지 않으므로 이 부재가 정상 경로를 막지 않는다. 다만 W-CO-03 제목의 eventName은 목록 경로가 보류돼 화면까지 완결되지는 않는다. API 5건 완료와 화면 완료를 구분한다.

보류 해소 조건: 권한 있는 정본에서 **코드↔이름 목록**을 확인하고 통합자가 R로 재개한다. 초기 행/토큰은 R-4의 가장자리 판정으로 처리하며 별도 회신을 필수로 기다리지 않는다. 발생기·검교정 배치·전화번호/전송기도 해소 조건이 아니다. 현재 a6a87e1 계약 갱신 금지는 유지한다. 코드 상수/시드를 미리 만들거나 외부 설계 저장소에 쓰지 않는다.

저장된 구독 헤더 SELECT 자체가 불가능한 것은 아니다. 보류 이유는 계약 소비 흐름인 이벤트 선택→미설정 개별 GET→최초 PUT을 위해 정본 이벤트와 미등록 입력을 가를 수 없다는 것이다. 저장행0을 전체 이벤트 설정0으로 정하지 않는다.

### 3-1. 보류 해소 뒤 적용할 GET/ETag/최초 PUT 후보

1. 코드 목록은 계약 확정값을 읽기 전용으로 제공한다. 업무 발생 이력은 조회하지 않는다.
2. 구독 전체 GET은 확정 이벤트별 설정을 반환한다. `@Res()`에서 JSON 직렬화 후 `response.type('application/json').status(200).end(...)`로 완료해 Express 자동 weak ETag까지 차단하고 Nest의 이중 전송을 피한다. 미등록 eventCode 응답도 같은 경계다. 알려진 단일 eventCode만 해당 version_no를 ETag로 반환하며 본문 versionNo는 없다. 전역 HTTP 설정은 바꾸지 않는다.
3. **정본에는 존재하지만 아직 설정이 없는 이벤트**는 recipients=[]·zaloEnabled=false·초기 토큰1로 읽는다. GET은 INSERT하지 않는다. `INITIAL_NOTIFICATION_SUBSCRIPTION_VERSION=1`은 DB 기본1·W-CO-11 기본 끔/0명 허용에 근거한 가장자리 선택(2단계①)이며 문의100에 기록한다.
4. 정본에 없는 eventCode 조회는 `{items:[]}`·이벤트 ETag 없음 후보(조회 404 미선언·하위 목록 선례). 저장은 400 INVALID(field eventCode). 정본 부재 자체와 「정본에 없는 입력」을 혼동하지 않는다.
5. 신규 PUT은 tx 안에서 헤더를 version1로 `INSERT ... ON CONFLICT ... DO NOTHING`한 뒤 동일 행을 잠그고 version을 검사해 version2로 저장한다. 둘 다 If-Match1인 최초 저장은 하나만 성공한다. 알림 수신자 0명이어도 헤더를 삭제하지 않아 토큰이 1로 되돌아가지 않는다.
6. GET의 헤더 version·Zalo·recipients는 한 SQL 스냅샷 또는 읽기 전용 RepeatableRead tx에서 함께 읽는다. 기본 격리의 여러 SELECT나 Prisma include만으로 한 스냅샷을 보장했다고 간주하지 않는다.
7. 이벤트 선택→개별 GET1→PUT→개별 GET2→새 키 다음 편집을 소비자 시나리오로 검증한다. 409도 개별 GET 후 사용자가 재편집한다. 응답 유실 재전송은 처음 키/본문을 유지한다.

## 4. 자신의 알림 조회·읽음·모두 읽음

### 4-1. 조회

모든 조건의 선두는 `recipient_user_id = currentSession(request).userId`다. 관리자가 호출해도 다른 사람의 알림을 합치지 않는다. 클라이언트 입력으로 userId를 받지 않는다. page·count에 같은 where를 적용하고 event 조인으로 발생 시각을 제한한다. unread-count는 **자기 미읽음 전체**이며 기간을 받지 않는다.

세션 주체가 없으면 명시적으로401이며 optional userId가 Prisma where에서 빠지는 경로를 허용하지 않는다. 현재 인증은 활성 app_user 세션만 받으므로 terminal-only도401이다. 계정 인증/단말 코어는 이 슬라이스가 변경하지 않는다.

### 4-2. 읽음 처리의 한 트랜잭션

가드(인증·계약·권한·멱등 헤더) → 세션 주체 고정 → §6의 멱등 tx → `UPDATE notification SET read_at=$now WHERE id=$id AND recipient_user_id=$actor AND read_at IS NULL` → 변경0이면 같은 tx에서 **id+actor** 존재 확인 → 있으면 이미 읽음이므로 성공, 없으면 404 → 멱등 완료 기록 → 204.

이미 읽은 행의 read_at을 다시 찍지 않는다. 다른 키로 다시 읽어도 최초 시각 보존. 같은 키는 저장 응답을 재생한다. 남의 알림은 없는 알림과 똑같이 404이며 권한 있는 계정도 예외 없다. 알림·발생 이력의 삭제와 title/message 변경은 0이다.

컨트롤러는 `@HttpCode(204)`를 선언하고 멱등 결과를 await한 뒤 void를 반환한다. DB null 재생도 raw body는 빈 문자열이다. IdempotentOutcome의 status/replayed/body를 계약 봉투로 노출하지 않는다. openable=false인 자기 알림도 이 경로와 배지 재조회가 가능하다.

### 4-3. 모두 읽음

같은 tx에서 `updateMany({where:{recipient_user_id:actor,read_at:null},data:{read_at:now}})`의 **실제 count**를 `readCount`로 반환한다. 미리 count한 뒤 UPDATE하지 않는다. 동시 단건 읽기/모두 읽기가 같은 행을 만나도 변경 건수는 중복되지 않는다. 최초 응답 12 이후 새 알림이 생겨도 **같은 키 재전송은 12**이고 새 알림을 읽지 않는다. 새 키는 남은 미읽음만 처리하며 0건도 200이다. 명령이 잠그는 UPDATE 대상 집합 이후에 발생한 알림까지 소급하려고 반복하지 않는다.

## 5. recipients:preview — 업무 저장 0, 응답 재전송 유지

### 5-1. 실제 관계와 필드

ROLE 후보 질의는 아래와 같다. USER 규칙 userId들을 같은 OR에 추가해 한 번에 user 목록을 구한다. 결과의 PK로 최종 중복 제거한다. 로그인 이름·작업자 이름·사업부 이름을 userName 또는 departmentName으로 대신 쓰지 않는다.

```sql
-- 의미를 보이는 SELECT. 실제 구현은 같은 OR/EXISTS를 Prisma 또는 매개변수 SQL로 표현.
SELECT u.app_user_id, u.user_name, u.is_active, d.department_name
  FROM app.app_user u
  LEFT JOIN mdm.department d ON d.department_id = u.department_id
 WHERE u.app_user_id = ANY($userIds)
    OR EXISTS (
      SELECT 1 FROM app.user_role ur
       WHERE ur.app_user_id = u.app_user_id
         AND (d.business_unit_id, ur.role_id) IN (/* ROLE 입력 쌍 */)
    )
 ORDER BY u.app_user_id;
```

`app_user`에는 business_unit_id가 없고 `user_role`에도 없다. 정상 계정의 소속 경로는 app_user.department_id → mdm.department.business_unit_id다. `user_data_scope`는 접근 범위이며 조직 소속이 아니다. worker.app_user_id는 선택·비유일이라 그쪽으로 우회하면 다른 의미와 중복이 생긴다. 부서 없는 사용자는 ROLE에 일치하지 않지만 USER로 직접 지정하면 포함한다. 부서 명칭은 department.department_name; 값 없음은 키 생략.

### 5-2. 검증과 비활성 후보 판정

1. ROLE/USER 조건부 짝을 먼저 검증하고 같은 규칙 중복을 검증한다. 잘못된 행은 정확한 `recipients[i].필드`를 가리키는 400이다.
2. 참조 사업부·역할·사용자는 실제 존재를 일괄 조회해 400 INVALID로 가른다. **존재하는 역할의 소속 사용자0명**은 유효한 규칙으로 users=[]다.
3. USER로 지정한 비활성 사용자를 제거하지 않는다. ROLE 전개에도 inactive 사용자를 포함해 `isActive:false`로 표시한다(계약이 해당 false 표시를 명시). `users`는 PK 중복 제거 전원, **`totalCount`는 isActive=true 인원수**로 R-5에서 확정한다. `countActiveRecipients`에 이름을 붙이며 계약 integer에 의미를 덧씌운 부분은 W-CO-11 §6의 「비활성 제외+표시」를 함께 충족시키는 해석임을 문의101에 기록한다.
4. 비활성 **역할/사업부/부서** 자체를 어떤 수신 차단으로 볼지는 계약이 말하지 않는다. 이미 존재하는 참조와 배정을 임의 제거하지 않고 app_user.is_active만 응답한다. 새로운 합성 활성 상태를 만들지 않는다. 이 미정은 문의에 명시한다.
5. `resolvedAt`은 이번 전개의 서버 UTC 시각. 사용자 목록은 한 SELECT의 스냅샷으로 구하고 시각과 결과를 같은 멱등 응답에 저장한다. 사용자/역할/소속이 바뀐 뒤에도 같은 키는 처음 결과, 새 키는 새 전개다.

구독 헤더·규칙·notification·notification_event·audit에는 0행 쓰기. **app.idempotency_record만 1건** 남는다. 계약의 「아무것도 저장하지 않는다」와 「같은 키에 같은 전개 결과」를 이 구분으로 지킨다(기존 plan-api.md:986). Zalo 요청값은 별도 전달을 일으키지 않으며 missingContactCount를 응답에 더하지 않는다.

전체 구독 GET의 개수는 규칙 수 `recipients.length`다. ROLE2+USER1이 같은 활성1명을 가리키면 규칙3·표시1·수신1이다. 비활성1명만 있으면 규칙1·표시1·수신0이다. 실제0명 경고는 preview 결과로 판단하고 특정 ROLE의0명은 그 규칙만 preview한다. 새 집계 필드나 사용자 활성의 합성 값을 만들지 않는다. ROLE/USER 반대 축 키는 null이 아닌 생략이다.

## 6. 멱등·잠금·구독 PUT 심장

### 6-1. 공용 래퍼 실측과 로컬 사용 경계

`common/master/master-write.ts:30`은 fingerprint에 method+path+body만 넣고 **query와 actor를 빼며**, `:34`는 `tx`를 무시한 `() => work()`를 부른다. `PrismaService`는 단순 PrismaClient이며 ALS 전달이 없다. 별도 서비스 `$transaction`을 열면 업무와 멱등 기록의 원자성을 보장하지 못한다.

**공용 파일을 고치지 않고**, I-28 4개 POST/PUT 경계가 기존 `IdempotencyService.run(context, tx => ...)`를 직접 사용한다. service는 전달받은 tx로만 DB를 호출하며 안에서 별도 `$transaction`을 열지 않는다. 이는 README의 멱등 의무를 지키는 구체적 구현 보정으로 R에서 확정한다.

```ts
// notification 영역의 경계에서 구성. 외부 입력을 보강한 뒤 실제 request.body를 바꾸지 않는다.
fingerprint: requestFingerprint(`${request.method} ${request.path}`, {
  actorUserId: session.userId,
  eventCode: normalizedEventCode, // PUT만 존재, 다른 operation에서는 undefined
  body: request.body,
})
// idempotency.run(context, (tx) => notificationService.readWithin(tx, ...))
```

같은 키·다른 actor 또는 eventCode 또는 body는 저장 결과를 노출하지 않고 공용 ConflictResponse 409다. If-Match는 지문에 넣지 않는다: 성공 뒤 토큰이 낡아져도 같은 요청키를 재전송하면 최초 결과가 돌아와야 한다. 성공 상태는 read=204, 나머지=200. 읽음은 undefined, preview와 PUT은 JSON 응답, read-all은 최초 count가 저장된다.

### 6-2. 구독 PUT 순서 — 보류 해소 뒤에만

| 순서 | 같은 멱등 tx 안의 처리 |
|---|---|
| 1 | 확정 카탈로그에서 eventCode 존재 확인(400 INVALID). 규칙 짝·중복·참조 검증. Zalo omission은 아래 후보 규칙 |
| 2 | NULL/NULL 헤더를 INSERT ON CONFLICT DO NOTHING로 확보. 조건은 부분 유일 인덱스와 동일하며 사용자·채널 옛 행은 제외 |
| 3 | eventCode+NULL/NULL 헤더를 `SELECT ... FOR UPDATE`로 잠금 |
| 4 | 잠긴 version_no와 If-Match 비교. 불일치 409 ConflictResponse `{conflictCause:'user',message}`. code 추가 없음 |
| 5 | 같은 헤더 자식 규칙 DELETE → createMany. ROLE은 user NULL, USER는 BU/role NULL. 순서가 의미 없는 집합이며 재조회는 recipient PK 순으로 고정 |
| 6 | 헤더 zalo_enabled 갱신·updated_at=now·version_no+1. 조건부 UPDATE의 version도 재확인 |
| 7 | 같은 tx에서 자식과 헤더를 읽어 NotificationSubscription 응답 조립 → 멱등 COMPLETED 기록 → 함께 커밋 |
| 8 | 200, **PUT 자체에는 ETag 미선언**이므로 setEtag를 호출하지 않는다. 다음 편집은 GET eventCode로 토큰을 받는다 |

새 헤더 INSERT 실패/토큰 충돌/자식 FK 실패/응답 저장 실패는 모두 롤백하므로 규칙 반쪽 상태·증가한 버전·고아 헤더·성공 멱등 기록이 남지 않는다. 최초 두 요청 경합은 DB 부분 유일과 헤더 잠금으로 직렬화한다. 같은 키는 멱등 PK가 한 번만 실행한다.

`zaloEnabled` 생략: 기존 헤더는 값 유지, 최초 미설정은 false 후보. 계약이 optional이고 명시적 false를 지원하므로 생략을 무조건 false로 덮으면 입력하지 않은 상태를 쓴다. README §2 가장자리→2단계 1번(상태를 안 쓰는 쪽). 이름 `zaloEnabledOmittedPreservesCurrentSetting`·문의로 흔적을 남긴다.

## 7. 오류·권한·모듈 파일

| 조건 | 상태·봉투 | 기존 code/field |

## 10. PR 분할 — 유사 파일 실제 줄 수로 예산 배정

숫자는 신규 코드가 이미 존재한다는 뜻이 아니라 **실제 읽은 기존 조각의 크기를 예산 기준으로 배정**한 것이다. 구현 시 diff 실측이 우선이며 줄을 접어 상한을 맞추지 않는다. 테스트 줄 수는 비테스트 예산에서 제외하지만 해당 응답 필드 단언을 같은 PR에 넣는다.

```sql
SELECT current_database(), current_user;
SELECT table_name,column_name,is_nullable,data_type,domain_name,column_default
FROM information_schema.columns
WHERE table_schema='app'
  AND table_name IN ('notification','notification_event','notification_subscription')
ORDER BY table_name,ordinal_position;
SELECT 'notification' AS name,count(*) FROM app.notification
UNION ALL SELECT 'notification_event',count(*) FROM app.notification_event
UNION ALL SELECT 'notification_subscription',count(*) FROM app.notification_subscription;
SELECT table_schema,table_name FROM information_schema.tables
WHERE table_name ILIKE '%notification%' ORDER BY 1,2;
SELECT tg.tgname,c.relname,pg_get_triggerdef(tg.oid)
FROM pg_trigger tg JOIN pg_class c ON c.oid=tg.tgrelid
JOIN pg_namespace n ON n.oid=c.relnamespace
WHERE n.nspname='app'
  AND c.relname IN ('notification','notification_event','notification_subscription')
  AND NOT tg.tgisinternal;
```

## 12. 마감 틀 — 통합자 작성

### 12-1. 조회 PR①에서 추가로 확인한 날짜 경계

`occurredFrom` 이상·`occurredTo` 미만은 DB의 마이크로초보다 세밀한 입력에서도 그대로 지킨다.
`new Date()`로 비교값을 만들면 밀리초 아래를 절삭하므로 사용하지 않는다. 저장 시각 x가
1µs 격자이므로 양 경계 q를 모두 `ceilµs(q)`로 바꾸면 `x >= q`와 `x < q`를 보존한다.
6자리 이하 소수는 보존하고, 이후 자릿수에 비영 값이 있을 때만 1µs 올린다.
초·일·월·년 이월과 Gregorian 윤년도 처리하며 저장된 발생 시각은 변경하지 않는다.

또한 고정 계약 검증기가 허용하는 소문자 t/z·단일 공백류 구분자·`+HHMM`·`+HH`는
Prisma가 받는 `T`·`Z`·`+HH:MM` 형태로 정규화한다. 공용 검증기의 입력 범위를 좁히지 않는다.
단위 테스트는 실제 ContractValidator를 거친 형식 조합을 검증하며, HTTP E2E는 µs 경계,
7~10자리 소수·익년 이월·offset·구분자에 대한 ID와 total을 함께 단언한다.
기대값을 구현 helper로 계산하지 않는다. 이 두 결함은 독립 코드 리뷰에서 발견했다.
