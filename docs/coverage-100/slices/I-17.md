**0단계 — 선례.** 계약 `InventoryTransaction.sourceDocumentTypeCode` 를 직접 파싱했다:

> `enum` ⭐ **5값**(선반영 뒤) = `GOODS_RECEIPT`·`GOODS_ISSUE`·`INVENTORY_ADJUSTMENT`·`STOCK_TRANSFER`·**`RECYCLE_ENTRY`**.
> 설명 원문: 「**A-10 다형 참조 판별자**이고 **값은 «대상 테이블 이름»이다** — `sourceDocumentId` 는 **그 표의 식별자**다.
> ⛔ 공통코드 그룹으로 받지 않는다 — … **가리킬 표가 늘면 계약을 고친다**. …
> ⚠ `STOCK_TRANSFER` 는 «재고를 움직이므로 원장을 남긴다»는 **추론**이다 — 다른 셋보다 **근거가 얕다**.」
> `x-code-key`: `CD-INVENTORY-TRANSACTION-SOURCE-DOCUMENT-TYPE`.

`plan.md` §5 **규칙 8** — 「**원장 판별자 4값** 고정. 투입·실적·출하는 원장 안 지남」. ⇒ **다섯째 값을 만들지 않는다**.

⭐ **같은 모양의 선례가 하나 있다 — 통보 059(적치)**.
`docs/design-inquiries/059-…md` 원문: 「판별자 값은 「대상 테이블 이름」인데 적치에는 `logistics.stock_transfer` 헤더가 **없다**.
… **후보 넷을 다 재었다** — `PUTAWAY_TASK` 다섯째 값은 **응답·질의 두 enum 이 닫혀 AJV 가 잡는다** ·
**`GOODS_RECEIPT` 로 쓰면 다형 취소가 한 문서에서 원장 2행을 만나 500 을 낸다** …」
결정: `STOCK_TRANSFER` 를 그대로 쓰고 `transaction_no` 의 `PT-` 접두어를 정본 판별 규칙으로 삼는다.

**1단계 — 본길이다**(모든 호출이 이 값을 쓴다). 계약 문자는 「대상 테이블 이름」인데 **네 표 중 어느 것도 이 전표가 아니다** ⇒ 계약 침묵 ⇒ **1-1단계**.

**1-1단계 — 묻는가 통보하는가.** MES 본질(재고 원장) **✓**. 바꾸는 비용 — ⓑ `block_ledger_header_mutation` 이
`status_code` 밖의 UPDATE·DELETE 를 막아 **이미 쌓인 행은 정정 불가**다. **그러나 059 와 같은 이유로 「식별은 된다」** —
아래 ③이 그 식별을 «양성»으로 세운다. 위험은 「구분 불가」가 아니라 「정정 불가」이고, 식별이 되는 한 실무는 성립한다.
⇒ **통보**(059 와 같은 판정).

> ⛔⛔ **이 절은 R-1 로 «폐기»됐다. 아래가 확정본이다.**
> 초안은 「`INVENTORY_ADJUSTMENT` 를 빌리고 `transaction_type_code='RECYCLE_ENTRY'` 로 양성 판별」이었고
> **3관점이 독립적으로 전부 기각**했다. 기각 근거 둘: ⓐ 계약이 「`transactionTypeCode` 를 따로 두지 않는다
> (L-2-1 · 2026-09-02 판정)」·「한 칸 더 두면 어긋났을 때 어느 쪽이 맞는지 판정할 수 없다」로 **이름 대며 금지**했다
> ⓑ `GET /inventory/transactions` 에 **`sourceDocumentId` 질의 축이 없어** 화면이 id 를 클라이언트에서 맞추므로,
> 빌린 값 아래서 id 가 겹치면 **조정 상세에 재생재 원장이 «유령»으로 붙는다**(접두어로 못 막는다).
> ⇒ **질의 213** 으로 올렸고 **ⓐ(enum 에 다섯째 값 추가)로 확정**됐다(2026-09-10 · 계약 사본 선반영 #572).

### 3-2. ⭐ 판별자 — **확정본**(질의 213 → ⓐ)

```
sourceDocumentTypeCode = 'RECYCLE_ENTRY'
sourceDocumentId       = recycle_entry_id
```

| 칸 | 값 | 근거 |
|---|---|---|
| `sourceDocumentTypeCode` | ⭐ **`'RECYCLE_ENTRY'`** | 계약 `InventoryTransaction.sourceDocumentTypeCode` enum 이 **5값**으로 열렸다(실측: `GOODS_RECEIPT`·`GOODS_ISSUE`·`INVENTORY_ADJUSTMENT`·`STOCK_TRANSFER`·**`RECYCLE_ENTRY`**). description 이 스스로 「**가리킬 표가 늘면 계약을 고친다**」라 적어 둔 그 경우다 |
| `sourceDocumentId` | `recycle_entry_id` | 같은 description — 「값은 «대상 테이블 이름»이고 `sourceDocumentId` 는 **그 표의 식별자**다」 |
| `transactionTypeCode` | **같은 값 `'RECYCLE_ENTRY'`** | ⛔ **판별에 «쓰지 않는다».** 선례 넷(입고·출고·조정·이동)이 전부 「판별자와 같은 값을 유형에도 쓴다」(`receipt-posting.ts:115` · `adjustment-posting.ts:141` · `transfer-posting.ts:134` · `putaway-posting.ts:47`) — 그 **모양만** 따른다 |

**왜 빌리지 않아도 되는가** — 유형 축이 갈리면 `(유형, id)` 가 **다시 유일**해진다. 빌릴 때 생기던 문제 셋이 전부 소멸한다:

| 빌릴 때의 문제 | ⓐ 에서 |
|---|---|
| `GOODS_RECEIPT` → `cancelable:true` + 「2행이면 throw」로 **입고 취소가 500** | ⛔ 해당 없음 |
| `INVENTORY_ADJUSTMENT` → I-14 의 병합된 e2e 가 `(유형,id)` 로 `toHaveLength(1)` 단언 · 화면 역조회 오염 | ⛔ 해당 없음 |
| `STOCK_TRANSFER` → 059 의 정본 규칙 후반부가 거짓이 된다 | ⛔ 해당 없음 |

⚠ **선반영 가드** `src/common/contract/contract-recycle-entry-enum.spec.ts` 가 응답·질의 두 축 enum 을 지킨다.
⛔ **빨개지면 지우지 말고 보고한다** — 설계 변동 공지에 안 실렸다는 뜻이다.

⭐ **`RECYCLE_ENTRY` 는 `LOGISTICS_DOCUMENT_TYPES` 9종에 없다** — 다형 취소·진행 조회가 이 값을 **아예 안 본다**(실측).
⇒ 취소를 여는 누구든 `document-type-registry.ts` 에 이 유형을 더하면 **그때 원장 2행 판정을 다시 재야 한다**(§13 ⓔ).

## §4. 서버가 정하는 칸 — 축 넷 (자리 ④)

### 4-1. 공장 축 — `warehouse.plant_id`

본문에 `plantId` 가 **없다**. `mdm.warehouse` 는 `plant_id` NOT NULL 이고 `InventoryPostingService.orgAxis()`(`:324-331`)가

**셋 다 같은 원천**을 쓴다. ⛔ 위치에서 풀지 않는다 — 위치는 창고의 자식이라 한 단계 더 멀다.
⭐ **위치가 그 창고 소속인지 검사한다**(400 `INVALID`) — 안 하면 잔액 차원이 두 창고에 걸쳐 어긋난다.

### 4-2. 상수 넷 — 값을 «지어내지» 않는다 (F-6)

| 칸 | 값 | 0단계 근거 |
|---|---|---|
| `recycle_type_code` | **`'RECYCLED'`** | ⭐ `MES_CATEGORY` 코드군에 **`NEW`·`RECYCLED` 두 값이 시드로 실재**한다(psql). 그리고 이 칸의 **옛 형제**가 바로 `item.recycle_type_code` 였고 `20260903100000_rename_item_mes_columns` 가 그것을 `mes_category_code` 로 개명했다 — **같은 값 영역**이다. ⇒ 새 코드 그룹 **0** |

⛔ **`source_document_type_code`·`source_document_id` 는 «둘 다 NULL»** — 공유계약 A-10(§2-2 ⓒ).

- `mdm.item.mes_category_code` 는 **nullable** 이고 `mdm.item` 은 **0행**(psql).
- 마이그 주석 원문: 「`mes_category_code` 는 신재와 재생재를 가르는 **MES 안쪽 구분**이다(DR-006 확정).

## §5. ⭐ LOT 코어 `createWithin` — 셋째 사용처 (자리 ③)

### 5-1. `sourceTypeCode` = **`'RECYCLE_ENTRY'`** — 추측이 아니다

세 겹으로 닫힌다:

1. 계약 `Lot.sourceTypeCode`(`logistics-01자재창고.json:11374`) — 「LOT 이 어디서 생겼나 — 입하 라인(`INBOUND_RECEIPT_LINE`) · **재생재 등록(`RECYCLE_ENTRY`)**. ⛔ 시스템 소유다」
2. 계약 `LotCreate.sourceTypeCode`(`:11613`) — 「⛔ **`RECYCLE_ENTRY` 는 이 경로로 오지 않는다** — 재생재 등록은
   `POST /logistics/recycle-entries` 가 **LOT 과 재고를 한 트랜잭션으로 만든다**(M-01-12 §5-2)」
3. 계약 `RecycleEntry.recycleEntryId`(`:13537`) — 「새로 만든 LOT 의 원천 참조가 이것을 가리킨다 — **원천 유형 코드는 `RECYCLE_ENTRY` 다**」
4. ⭐ **시드에 이미 있다** — `LOT_SOURCE_TYPE` 코드군 **3값**: `INBOUND_RECEIPT_LINE`·`RECYCLE_ENTRY`·`WORK_ORDER`(psql).
   ⇒ ⛔ **`lot-source.ts` 에 상수를 더하지 않는다** — 그 파일은 `WORK_ORDER` 하나뿐이고 「도메인 둘이 같은 문자열을 봐야 해서」 코어에 둔 것이다.
   재생재는 **보는 도메인이 하나**라 도메인 파일의 상수로 둔다(사용처 하나뿐인 추상화 금지 · CLAUDE.md).

### 5-2. ⭐ 코어를 **0줄** 고친다 — 역방향 칸은 호출자가 채운다

`lot-registry.service.ts:120-122`:
```ts
if (input.sourceTypeCode === INBOUND_RECEIPT_LINE) {
  await this.attach(tx, input.sourceId, lot.lot_id);   // inbound_receipt_line.lot_id 를 채운다
}
```
⇒ **재생재는 이 가지를 안 탄다.** `recycle_entry.lot_id` 는 호출자가 같은 `tx` 로 UPDATE 한다.
⛔ 코어에 두 번째 가지를 더하지 않는다 — 코어 주석이 스스로 「**이 원천만 역방향(라인 → LOT) 칸을 갖는다**」(`:20`)라 적었고,
가지를 더하면 CLAUDE.md 의 「코어 전용 PR ≤ 200」이 발동해 **PR 이 1 → 2** 가 된다.

**순서 불변식**(입하와 같은 모양 — 라인 → LOT → 라인 UPDATE):

```
$transaction 안:
  ① recycle_entry INSERT (lot_id = NULL)      ← lot.source_id 가 이 id 라 먼저 서야 한다
  ② registry.createWithin(tx, {... sourceTypeCode:'RECYCLE_ENTRY', sourceId: recycleEntryId}, appUserId)
  ③ tx.recycle_entry.update({ lot_id })        ← ①의 역방향
  ④ posting.post(tx, {...})                    ← lotId 가 정해진 뒤라야 라인이 선다
```

### 5-3. 코어가 «무조건» 하는 것을 그대로 받는다

`createWithin` 은 파라미터 없이 **셋을 고정**한다: `status_code = 'INSPECTION_PENDING'` ·
`lot_hold`(`reason_code = 'INCOMING_INSPECTION_WAIT'`) · `lockLotsWithin` 한 번.
코어 주석 `:93-97` — 「⭐ 화면이 보내지 않고 «서버가» 건다 … 부르는 이유는 **표식에 예외를 두지 않으려는 것**」.

⇒ **재생재도 검사 대기로 태어나고 보류가 하나 걸린다.** 옵션을 열지 않는다.
⚠ 이것이 「분쇄재를 바로 재투입한다」와 어긋난다고 판단되면 **코어에 파라미터가 생기고 자리 ③ 이 뒤집힌다** — 리뷰가 볼 자리다.
⭐ 다만 **재고 자체는 `AVAILABLE`** 이다(§3-3) — 보류는 LOT 표식이고 잔액 차원과 독립이다.

### 5-4. LOT 번호 — 서버가 매긴다(C-2)

`plan-uiux.md:1113` — 「⭐ **LOT 번호를 서버가 매긴다**(C-2) — 「번호는 저장 후 정해집니다」」.
`POST /trace/lots` 선례(`lot.service.ts:249-260`)를 그대로 복제한다:
`mesLotNo(plantId, businessDate, count+1)` — 접두어 `M{plantId 6자리}{YYYYMMDD}` 로 `lot.count` 를 세고 뒤에 난수 13자리.
⛔ 연속을 보장하지 않는다. 충돌은 **재시도 루프**가 받는다(입고 선례 `NUMBER_RETRY = 3`).
`lotTypeCode = 'MATERIAL'` — 계약이 「새 **자재** LOT」이라 적었고 `LOT_TYPE` 시드에 `MATERIAL` 이 실재한다(psql).

## §7. 횡단 — 멱등 · If-Match · ETag · 403 · 사번 · 상태기계

### 7-1. 멱등 · If-Match · ETag

- **멱등**: `runIdempotent(this.idempotency, request, HttpStatus.CREATED, () => …)` — 쓰기 전건 규칙(`plan.md` §5 규칙 2).
  ⛔ `FAMILY_CONFLICT_CODE` **다섯째 인자를 넘기지 않는다**(§1-4).
- **If-Match**: ⭐ **안 받는다.** `IfMatchVersionOptional` 이 «생성»에 붙어 있으나 **새 자원이라 대조할 버전이 없다**(C-9).
  직전 I-16 이 같은 자리에서 같은 판정을 했다(`handling-unit.controller.ts:79` — 「⛔ If-Match 는 안 받는다 — 새 자원이라 대조할 버전이 없다(C-9)」).
  가드(`optimistic-lock.guard.ts:28-63`)는 `requirement='optional'` 이라 **헤더가 없으면 통과**하고, 있으면 파싱해 `rememberIfMatch` 만 한다 —
  핸들러가 안 읽으므로 무해하다. ⚠ **단 형식이 틀리면(0·음수·비수치) 가드가 400 `INVALID` 를 낸다** — 새 자원인데 400 이 나는 자리이고 I-16 과 같다.
- **ETag**: ⛔ **`setEtag` 를 부르지 않는다** — 201 에 `headers` 가 **없다**(§1-1). `plan-uiux.md:262` 정정 대상.
