### 2-2. 귀속 — 저장칸 신설의 선례

`worker.app_user_id`는 nullable이고 UNIQUE가 아니다. 사번→계정이 없을 수 있고 계정→사번이 여러 개일 수 있다. 계정으로 왕복해 사번을 복원하는 설계는 성립하지 않는다. 계약 WorkerNo는 “로그인 없이 이 쓰기의 귀속”이라고 명시한다.

**0단계 선례**: `production.precheck_decision.worker_no` 마이그(`20260901100000…:26`, `:57`)는 계정 연결 없는 작업자의 헤더 문자열을 그대로 보관한다. 같은 형상으로 `breakdown.reporter_worker_no varchar(50)`을 추가하며 reported_by FK는 보존한다. **현재 HTTP는 활성 계정 세션 필수**이므로 reported_by·created_by·updated_by는 실제 호출 세션 계정이다. worker.app_user_id=NULL과 요청 세션 없음은 다르다. 사번은 새 칸만 읽고 worker계정으로 도출하지 않는다. terminal-only/세션없음은401이며 무로그인 현장 흐름은054의 공용 미지원 과제다.

점검은 이미 정확한 worker FK가 있으므로 새 사번 칸을 만들지 않는다. worker_no→worker_id를 찾아 inspected_by에 넣는다. 비활성·계정 없음·자격 없음은 별도 거부 근거가 없어 저장 가능하며, 사번의 존재는 확인한다(M-05-01 §8-6 자격 게이트 없음).

### 2-4. 과거 nullable 행·필수 응답·기존 root_cause

추가 컬럼을 nullable로 두는 것은 과거 행을 사실처럼 백필하지 않기 위해서다. 현재 DB는 0행이지만 운영도 0행이라고 추정하지 않는다. PR① 조회 활성화 전부터 아래 사전 SELECT를 실제 대상 DB에서 확인하고, 구 작성자가 결손 행을 계속 만들 수 있는지도 배포 담당이 확인한다. 마이그 PR까지 검사를 미루지 않는다.

```sql
-- 기존 실측표를 덮어쓰지 않는 추가 배포 검사. 결과는 구현/배포 시 실제 기록.
SELECT count(*) FROM maintenance.equipment_inspection
 WHERE inspected_at IS NULL OR inspected_by IS NULL OR judgment_code IS NULL
    OR judgment_code NOT IN ('PASS','FAIL');
SELECT count(*) FROM maintenance.equipment_inspection_result
 WHERE judgment_code IS NULL OR judgment_code NOT IN ('PASS','FAIL');
-- A15 적용 뒤 실행:
SELECT count(*) FROM maintenance.breakdown
 WHERE occurrence_state_code IS NULL OR reporter_worker_no IS NULL;
```

과거 점검의 inspected_at/inspected_by/judgment_code, 과거 고장의 occurrence_state_code/reporter_worker_no가 null이면 **required 응답을 만들 수 없다**. 선택 컬럼처럼 omitEmpty로 키를 빼거나 수신시각·계정로그인·ABNORMAL로 메우지 않는다. 뷰의 불변식 검사가 기존 INTERNAL_ERROR 봉투로 실패시키고 문의에 남기는 후보이며, 이 상태의 행이 조회될 운영 DB에서는 정상 서비스 가능한 배포로 승인하지 않는다. 데이터 보완 주체·계약 완화 중 하나가 필요하다. 목록의 해당 행을 조용히 제외하거나 total에서 빼지 않는다.

R-15 보완: 기간 조회의 NULL 시각은 SQL 날짜 조건으로 제거되기 전에 잡는다. 날짜 외 동일 관계 필터를 적용한 metadata 집계에서 NULL 시각이 하나라도 있으면 기간 소속을 판별할 수 없으므로 INTERNAL_ERROR다. NULL을 요청 기간에 포함한 것처럼 count하지 않는다. 다른 설비/유형/판정/기발행 등 명시 필터로 제외된 행은 영향을 주지 않으며 날짜 없는 미발행의 페이지별 매핑과 역전 빈집합은 유지한다. 추가 단언: `기간 양끝/미발행 한쪽기간의 NULL 시각은 page/count 전에500`, `무관한 조건의 NULL 시각은 조회를 막지 않음`.

헤더/라인의 OK·NG 등 enum밖도 같은 불변식 실패다. 이를 정상200 지원으로 세지 않는다. PUT/start 뒤 응답 매핑이 이 조건으로 실패하면 업무상태·감사·version·멱등기록이 함께 롤백돼야 한다. DB0행인 개발 환경의 구현 진행과 과거행이 있는 운영 배포 승인을 구분한다(091).

기존 `root_cause`를 새 `causeCode` 또는 `handlingNote`로 옮기는 백필은 0이다. DB 주석도 없어 둘 중 어느 의미인지 정할 근거가 없다. 구버전 행의 root_cause가 있어도 그대로 보존하고 새 handling 객체에 임의 노출하지 않는다. 새 cause_code에 이미 저장된 문자열은 조회 시 그대로 반환하며 **오늘의 마스터 존재 검사로 역사 조회를 막지 않는다**. PUT에서 생략은 유지·명시 null은 해제이고 비null 대입은 동일 문자열 재전송도 거부 후보다(§3-2). 그때 기존 저장값은 유지된다.

### 4-2. 고장 목록·보전 연결

기본 미처리=`status_code <> 'DONE'`, 정렬=`reported_at ASC,breakdown_id ASC`. `statusCode='DONE'`인데 openOnly 생략/true면 **빈 목록**이다. 완료 건 이력은 openOnly=false와 기간을 명시한다. 기간 필수 조건은 L-12 예외의 반대이므로 openOnly=false에서 reportedFrom/To 두 칸을 요구하는 후보다(094). withoutMaintenanceOrder와 openOnly는 독립이다.

-- 고장 미발행 여부: 두 실재 연결을 모두 읽는다. 지시 상태로 필터하지 않는다.
SELECT b.breakdown_id
  FROM maintenance.breakdown b
 WHERE NOT EXISTS (
   SELECT 1 FROM maintenance.maintenance_order_trigger t
    WHERE t.trigger_type_code = 'BREAKDOWN' AND t.source_id = b.breakdown_id

### 4-3. 상세 전용 비가동 합계

```sql
SELECT count(*)::int AS "linkedDowntimeCount",
       count(*) FILTER (WHERE ended_at IS NULL)::int AS "openLinkedDowntimeCount",
       COALESCE(sum(extract(epoch FROM ended_at - started_at))
         FILTER (WHERE ended_at IS NOT NULL), 0) AS "closedSeconds"
  FROM maintenance.equipment_downtime
 WHERE breakdown_id = $1;
```

상세에서만 이 쿼리를 실행한다. count는 열린 것 포함 전체, 합계는 닫힌 것만. 겹친 구간도 각 행을 합한다(계약 “합계”이며 OEE 합집합을 새로 만들지 않는다). 열린 구간을 현재시각까지 더하지 않고 고장의 reported_at/handled_at도 사용하지 않는다.

closedSeconds가 60으로 정확히 나뉘면 integer 분을 반환한다. **소수 분일 때 반올림 규칙이 계약·기존 구현에 없어 null**을 반환하는 후보다(허용된 `[integer,null]`, 1단계 가장자리→2단계 기준 4, 095). 0초는 알려진 0분이다. 이는 정확한 초를 저장하거나 분을 새 컬럼으로 저장하는 변경이 아니다. 리뷰에서 floor/round를 택하려면 그 0단계 선례나 판단 근거를 추가한다.

목록의 linkedDowntimeCount는 계약대로 **0**, minutes/openCount는 생략한다. 생성·수정·전이 성공 응답도 “상세 GET”이 아니므로 목록형 집계 규칙을 쓴다. 처리 내용의 최신 저장값은 모든 성공 응답에 포함하고, 새 집계값이 필요한 화면은 상세 GET을 다시 부른다. 이 구분을 조회 테스트가 단언한다.

후속 쓰기용 토큰도 반드시 상세 GET으로 갱신한다: **생성→GET→메모PUT→GET→start→GET**. PUT 응답으로 상세 집계/열린 비가동 경고를 덮지 않는다. 409는 입력을 보존하고 재조회 후 새 시도, 응답 유실은 같은키/본문 재전송으로 구분한다. 복수지시의null은 지시없음이 아니고 소수분null은0이 아니며 목록count0은 비가동없음의 증거가 아니다(093·095).

## 5. 트랜잭션·횡단 골격

### 5-1. 한 업무와 멱등 기록을 같은 tx에 둔다

**실측**: `master-write.ts:27`의 runIdempotent는 `IdempotencyService.run` 콜백의 tx를 버리고 `work()`를 부른다. `PrismaService`에는 ALS 등 주변 tx 전달 장치가 없다. 따라서 기존 도메인의 독립 `$transaction`을 그대로 복제하면 멱등 기록 저장 실패 뒤 업무만 남을 수 있다. 이 문제를 통합자에게 보고했으며 공용·다른 레인 파일은 수정하지 않는다.

I-30 쓰기는 **기존 IdempotencyService.run(context, async tx => …)**을 사용한다. 최종 업무검증·INSERT·UPDATE·응답 되읽기·멱등완료는 전달tx다. 번호준비용 사전조회는 아래의 명시적 예외이며 최종 업무검증을 대체하지 않는다. 중첩업무tx·새멱등코어는 만들지 않는다.

위 지문 재료는 R-5의 actor/worker까지 확장한다. `common/master/code-reference.ts:24`는 PrismaService를 받으므로 TransactionClient와 호환되지 않는다. 로컬 `maintenance-code-reference.ts`가 tx.code_value.findMany로 그룹·활성을 검증한다. this.prisma 우회나 as타입단언으로 같은tx 원칙을 감추지 않는다. context/코드검증은⑤에서 만들고⑥이 실제 재사용하며 해당 diff를 모두 예산에 포함한다.

**R-14는 초안의 tx내 채번을 철회한다.** numbering.service.ts:64~70은 풀고갈을 피해 tx전에 next를 완료하도록 경고한다. 같은 풀의 연결을 잡은 멱등tx들이 추가 연결을 기다릴 수 있으므로 「멱등1+채번1」은 안전성 근거가 아니다. 실제 장애 재현 주장이 아닌 코드 경로 판정이다. 계약:2982는 중복기록 금지이며 재생 카운터0/번호 연속을 요구하지 않는다.

O3/O6의 순서:

1. 전역가드와 run전 사번형식 검사 뒤 actor/worker 포함 context를 고정한다.
2. tx밖에서 해당 idempotency_record 존재만 확인한다. 있으면 새 설비조회/채번 없이 기존 run으로 넘겨 재생/충돌을 판정한다. private replay 로직은 복제하지 않는다.
3. 없으면 번호에 필요한 설비공장만 사전조회하고 **await Numbering.next를 완료한 뒤** run을 연다. 번호 문자열·준비 공장축만 업무tx로 넘긴다.
4. 전달tx로 사번/설비/코드/입력을 최종 검증하고 업무·응답·완료기록을 함께 커밋한다. 사전조회 뒤 다른 요청이 성공했으면 run이 앞 응답을 돌려주고 선채번 번호는 결번이다. 설비공장이 준비축과 달라졌으면 기존409 user로 거부·업무0, 번호만 소비한다.
5. 사전조회한 멱등행이 사라져 번호 미준비로 callback이 호출되면 로컬 `NumberPreparationRequired` 제어오류로 롤백하고 밖에서 번호를 준비해 다시 run한다. callback안 채번은 금지한다. 이 제어오류는 API에 노출하거나 새 ERROR_CODE로 등록하지 않는다.

정상 완료 재생은 현재 번호규칙 비활성화/설비정보 변경에도 최초 응답이다. 경합·업무실패·재시도의 선채번 결번은 허용한다. 번호까지 원자화하지 않고 업무+멱등만 원자성을 보장한다. 로컬 조율은 두 생성에서 실제 공유하는 `numbered-maintenance-write.ts`에 한정하며 ⑤/⑥ 예산에 포함한다.

번호 중복 P2002는 **해당 번호 유일키에 한정**해 잡아 멱등 run 전체를 재시도한다. 실패한 PostgreSQL tx 안에서 다음 INSERT를 시도하지 않는다. 선례는 `goods-receipt.service.ts:98`, `NUMBER_RETRY=3`(최초+3회 재시도)이다. 소진은 POST 선언에 맞춰 400 UNIQUE_VIOLATION으로 낸다. 라인 항목 중복·다른 FK 오류까지 재채번으로 삼키지 않는다.

### 5-2. 공통 오류 우선순위

전역 순서는 `app.module.ts:25`의 **인증→권한→계약 body/query/path→멱등 헤더→If-Match 헤더**다. 사번 존재 검사는 서비스에서 한다. 전역 실패가 업무 검증보다 앞서는 것은 이 계획에서 바꾸지 않는다.

### 6-1. O3 점검 등록 — 201

R-14에 따라 번호준비는 run밖에서 완료한다. 멱등콜백 안에는 다음 최종검증/업무만 들어온다.

## 7. 채번·알림·모듈 배치

### 7-1. 두 필수 번호

0단계: plan.md §0-3은 미등재 유형에 `{PREFIX}-{YYYYMMDD}-{SEQ4}` 공용 기본패턴을 확정했다. 계약 example은 InspectionNo=`EQI-2026-0088`, BreakdownNo=`MLF-2026-0088`이다. DB 두 번호는 NOT NULL UNIQUE이고 입력에는 번호가 없다. NumberingService.DEFAULT_PREFIX에는 이 둘이 없으며 전용 규칙도 0행이다.
