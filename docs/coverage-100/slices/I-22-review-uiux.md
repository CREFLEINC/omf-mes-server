### ⓻ ⭐ 「`PICKING` 함정 — 부분 배정은 영영 `PARTIALLY_ALLOCATED`」 → ⛔ **반증**(함정은 실재, 판정이 틀렸다)

**셋으로 갈라 잰다.**

**⑴ 「영영 머문다」는 틀렸다.** 계약 식은 `PICKED = P=A AND S=0` 이고 **`A=R` 을 요구하지 않는다.**
「뒤가 이긴다」로 `PICKED` 가 `PARTIALLY_ALLOCATED` 를 덮는다. ⇒ 갇히는 구간은
**`A<R` 이면서 `0<P<A`(피킹 «진행 중») 하나뿐**이다.
⛔ 계획안 **§5-1 ⚠⚠ 의 「아무리 피킹해도 머문다」는 자기 §9-3 ⓖ 와 모순**이다(ⓖ 가 맞다). → Nit 1.

**⑵ 그래서 「화면이 막히지 않는다」(§9-1 #2)는 «출하 확정»에 대해서만 맞다.**
그 진입 필터는 계약이 못박았다 — `pickingCompleteOnly` 의 description: 「⭐ **`W-04-04` 출하 처리의

아니라 수량 축이므로 **부분 배정 전량 피킹분도 정상으로 잡힌다.** ⇒ 이 자리는 ⭕. (계획안은 이 근거를
안 들었다 — 결론만 맞았다.)

**⑶ ⛔ 그런데 «막는 이유 배지»가 안 그려진다.** `W-04-04` §5-4:

> ⚠ **막힌 이유를 목록에서 보인다** — 「검사대기 ⛔」·「피킹중 ⛔」. G-3 을 **목록 수준으로** 올린 형태다.
> ⭐ **배지의 원천을 못박는다** — 「피킹중」은 `ShipmentRequest.shipmentProgressCode` = `PICKING` 이다.

`W-04-04` §3 목업이 `● SR-…0461 A사 **피킹중 ⛔**` 를 실제로 그린다.
`A<R` + 피킹 진행 중인 건은 `PARTIALLY_ALLOCATED` 를 내므로 **그 배지를 못 단다** — 대신 「부분 편성」이
뜨고, 운영자는 **`W-04-01` 로 가서 배정을 더 넣으려 한다**(실제로 해야 할 일은 `M-04-01` 로 가서 피킹을

`W-04-02` §5-4 가 「뭉치면 **왜 막히는지 목록에서 알 수 없다**」로 막으려 한 바로 그 실패 모양이다.

**⇒ 판정: 반증.** 「막히지 않는다」 → 「**출하 확정은 안 막힌다. 다만 상시 구조에서 차단 사유 배지가

## 3. 관점별 전수 점검표 — `plan-uiux.md` ↔ 계획안 ↔ 화면 명세

### 3-1. ⛔ **Blocker 1 — 목록 응답에 `lines` 가 없으면 «세 화면»의 유일한 수량 열이 빈다**

계획안은 `GET /logistics/sales-orders` 에 대해 **「목록은 `lines` 를 싣지 않는다」로 «명시적으로 정하고»**
e2e **S-3** 으로 잠갔다(`I-22.md:392`·`:666`). `GET /logistics/shipment-requests` 에 대해서는 **침묵**한다 —
그러면 저장소 선례(`src/logistics/purchase-order/purchase-order-query.service.ts:71` — 목록은 헤더,
단건만 `lines`)대로 **헤더만** 나간다. 계약도 `lines` 를 `required` 에 안 넣었다.

**그런데 화면 셋이 그 라인 합계를 «핵심 열»로 그린다.**

### 3-2. ⛔ **Blocker 2 — `oqcPassed` 축 ≠ 라인 검사 축 ⇒ 「합격인데 납품라벨을 못 뽑는」 영구 상태**

계획안 §5-2 안에서 두 파생이 **다른 축**을 쓴다.

```
라인 shippingInspectionStatusCode :  (LOT 축)  OR  (SHIPMENT_REQUEST 헤더 축)
배분 oqcPassed                    :  (LOT 축)  만
```

⇒ **OQC 를 헤더 대상(`target_type_code='SHIPMENT_REQUEST'`)으로 낸 작업지시**에서:

| 화면 | 그리는 값 | 결과 |
|---|---|---|
| `W-04-02` §4-A 「검사」 | 라인 축 → `PASSED` | 「✅ 합격」 |
| `W-04-04` §5-4 관문 ② | 라인 축 → 합격 | 출하 확정 통과 ⭕ |
| `P-04-02` §5-1 대상 목록 | `oqcPassed` → **LOT 축 결과 0건 → false** | ⛔ **「발행 불가 — OQC 판정이 나면 발행할 수 있습니다」** |

`P-04-02` §5-1 은 「납품라벨을 고르면 대상 목록이 **「합격」만 활성**된다」이고 §5-6 「**발행 취소 ⛔ 두지 않는다**」다.
⇒ 운영자는 **목록에서 합격을 보고, 출하는 확정되는데, 납품라벨만 영원히 못 뽑는다.** 이유는 어디에도 안 뜬다.
`W-04-02` §5-4 가 「**다섯을 셋으로 뭉치면 출하 확정에서 막힌다 — 왜 막히는지 목록에서 알 수 없다**」로
경고한 실패를 **다른 화면에서 재현**한다.

**⇒ 두 파생을 «같은 함수»로 통일한다.** `shipment-request-progress.ts` 가 라인 검사 상태를 내는
함수 하나를 갖고, `oqcPassed = (라인 판정 == PASSED)` 로 그 함수를 **재사용**한다(계약이 요구하는
`required=false → true` 만 앞에 둔다). ⭐ **PR 배치도 바뀐다** — 지금 `oqcPassed` 는 PR ⑦, 라인 롤업은
PR ③ 이다. **③ 으로 당겨야** 두 벌이 안 생긴다. e2e **A-6~A-9 와 L-23~L-30 이 같은 픽스처를 공유**해야
어긋남이 드러난다(지금은 파일이 갈려 있어 **둘 다 초록으로 어긋난다**).

### 3-3. ⛔ **Major 3 — `q`(납품라벨)를 계약이 «명시적으로 배제한» 축에 붙였다**

| **β** | 「합격인데 납품라벨을 못 뽑는」 상태가 생긴다 | 라인 검사 롤업은 LOT 축 + 헤더 축인데 `ShipmentLotAllocation.oqcPassed` 는 LOT 축뿐이다. 헤더 대상(`target_type_code='SHIPMENT_REQUEST'`) OQC 만 있는 출하는 `W-04-02` 「✅ 합격」·`W-04-04` 통과인데 `P-04-02` 대상 목록에서 영영 비활성이다. 서버가 두 축을 통일한다 |
| **γ** | `:pick` 의 409 가 네 사유를 코드 하나로 접는다 | `ShipmentConflictResponse` 에 `errors[]`·`field` 가 없어 Hold·가용·배정 초과·잔여 유효기간 넷이 `INVALID_STATE` 하나가 된다. `M-04-01` §6 이 요구하는 「보류 사유 표시」·「요구 180일 미달(실제 92일)」은 `message` 가 전부 져야 한다 |
| **δ** | 제품 피킹을 되돌릴 길이 «화면에도» 0 | `M-04-01` §5-7 이 「되돌림은 `W-01-13` 계열」이라 가리켰는데 `W-01-13` 은 **04 를 명시적으로 제외**하고 취소 가능 문서 3종(입하·입고·출고)에 피킹이 없다. 편성 취소도 계약 0건이라 잘못 집은 예약이 출하 전까지 못 풀린다(계획안 후보 **K** 를 이 근거로 보강) |
| **ε** | 목록 응답이 라인 3수량을 못 실으면 세 화면의 핵심 열이 빈다 | `ShipmentRequest` 에 합계 칸이 0개라 `W-04-02` §4-A 「요청/배정/출하」·`W-04-05` 드롭다운 「배정 500」·`M-04-01` ① 「배정 300 · 피킹 120」이 `lines` 없이는 못 선다. `ShipmentRequestLine.required` 에 `picks` 가 있어 목록이 라인을 실으면 예약 롤업이 페이지 전체로 번진다 |
| **ζ** | `q`(납품라벨)를 `handling_unit_no` 로 읽으면 계약이 갈라 둔 두 축이 겹친다 | 계약 `q` 가 「⛔ 포장은 `handlingUnitId` 를 쓴다」로 포장 축을 이미 배제했다. 납품라벨 번호를 담는 칸이 저장소 전체에 0개이고 `document_issue_log` 에도 발행 «번호» 칸이 없다(계획안 후보 **D** 를 이 근거로 교체) |
| **η** | 「미편성/부분편성/편성완료」 3상태 중 서버가 세우는 것은 하나뿐 | `W-04-01` §3 지시서 목록이 3상태 배지와 「N라인」을 그리는데, `unassignedOnly` 는 boolean 이고 `GET /logistics/shipment-requests` 에 `salesOrderId` 질의 축이 없어 되짚을 길도 없다 |
| **θ** | `M-04-01` §4-A 의 「피킹 수량 = `inventory_balance.picked_qty`」가 라인 축을 못 준다 | 그 컬럼은 (품목·LOT·창고) 차원이라 같은 LOT 을 집은 두 라인을 못 가른다. 라인별 「피킹 120」은 계약 `ShipmentRequestLine.pickedQty` 로만 난다 — 화면 문서의 출처 칸을 고쳐야 한다 |
| **ι** | 권장 외 LOT 을 집은 사유를 `:pick` 이 안 받는다 | `M-04-01` §5-5 가 「경고 후 통과 · 사유는 남지 않는다」로 닫혔음을 서버가 확인했다는 사실만 남긴다(§8 미결 1 해소와 같은 자리) |
