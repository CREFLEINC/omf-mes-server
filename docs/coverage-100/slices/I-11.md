### 1-3. 쓰기 6건 — 본문 스키마 실측

#### `POST /production/work-sessions` — `WorkSessionCreate`
required **2**: `workOrderId` · `startedAt`. 선택: `shiftId` · `equipmentId` · `moldId` · `workerIds[]`(⌜시작 시점 작업자⌝) · `controlOverride`.
- `startedAt` ⌜단말 시계가 정한다. **서버 수신 시각으로 덮지 않는다**(C-12)⌝.
- `shiftId` ⌜비우면 **서버가 정한다** — 시작 시각과 **요청을 인증한 단말의 공장**으로 교대 마스터를 풀어 넣는다 … 어느 교대에도 들지 않는 시각이면 **비운 채 기록**⌝ + x-internal-note ⌜단말→공장 경로 부재(omf-mes#262)는 그대로 남지만 이 처리로 화면이 막히지는 않는다⌝.
- `ControlOverride` = `reasonCode`(required · `CONTROL_OVERRIDE_REASON`) + `note`(선택). 설명 ⌜서버가 세션과 `work_session_event`(**통제 우회**)를 한 트랜잭션으로 만든다. **별도 액션을 두지 않는 이유는 「우회만 하고 세션을 안 여는」 상태를 없애기 위함**⌝.
- description ⌜**단말 게이팅(`can_start_work`)을 서버가 강제한다**⌝ · ⌜⛔ 오프라인 대상이 아니다 … ⛔ 셸의 outbox 에 담지 않는다 · ⛔ 큐 접수 202 를 두지 않는다⌝ · ⌜If-Match 는 선택이다 — **신규 생성이라 대조할 `version_no` 가 아직 없다**⌝.
- x-internal-note ⌜**409 `OPEN_SESSION_EXISTS` 는 같은 W/O 에 열린 세션이 이미 있다는 뜻**이다. `uq_work_session(work_order_id, session_no)` 가 물리적으로도 막는다⌝.

#### `POST …/{workSessionId}/events` — `WorkSessionEventCreate`
required **2**: `eventTypeCode` · `occurredAt`. 선택 `reasonCode`.
- ⭐ ⌜이 오퍼레이션으로 **단말이 적재하는 것은 구간 «안의» 사건인 STOP·RESUME 뿐**이다. 구간의 «경계»(START·END)와 통제 우회는 세션을 열고 닫는 오퍼레이션이 **같은 트랜잭션**으로 만든다 — 따로 보내지 않는다⌝.
- ⭐ ⌜**P-02-01(작업 시작)의 [재개]도 이 경로다** — 중단된 W/O 를 재개할 때 **새 세션을 열지 않고 같은 세션에 RESUME 을 적재**한다(G-16 보완). **⛔ `/production/work-orders/{workOrderId}:resume` 를 부르지 않는다**⌝.
  ⇒ **W/O 층 `:hold`/`:resume` 와 세션 층 STOP/RESUME 은 서로를 호출하지 않는다.** I-6 이 이미 반대 방향(`:hold` 가 세션을 안 건드린다)을 코드와 e2e 로 못박았다(`production-work-order.e2e-spec.ts:501` ⌜중단 — 세션의 `ended_at`·`status_code` 가 그대로다⌝). **이 슬라이스는 그 대칭을 지킨다** — events 가 `work_order.status_code` 를 건드리지 않는다(§6-4).
- ⌜유형별로 `reasonCode` 에 어느 코드 그룹을 쓰는지는 **공유계약 A-25**가 정한다⌝ → §5-3 대응표.
- `WorkSessionEventCreate` 설명 ⌜**사번은 본문이 아니라 X-Worker-No 헤더로 보낸다. 단말은 요청을 인증한 단말 토큰에서 서버가 푼다**⌝.

#### `POST …/{workSessionId}/workers` — `WorkSessionWorkerJoin`
required **2**: `workerId` · `joinedAt`. 선택 `workerRoleCode`. 설명 ⌜세션을 닫지 않고 사람을 더한다⌝.

#### `POST …/workers/{workSessionWorkerId}:leave` — `WorkSessionWorkerLeave`
required **1**: `leftAt`. 설명 ⌜떠난 시각을 찍는다. **행을 지우지 않는다** — 누가 언제까지 있었는지가 기록이다(B-4 의 정신)⌝.

#### `POST …/{workSessionId}:end` — `WorkSessionEnd`
required **1**: `endedAt`(⌜단말 시계. **시작보다 앞서면 400**⌝). 선택 `stopReasonCode`(**x-no-code-key** ⌜⛔ 이 칸을 «쓰지 않는다» … 값 목록을 못 정한 것이 아니라 «비우기로 정했다»(A-21·A-25)⌝).
- 설명 ⌜끝 시각을 찍어 구간을 닫는다. ⚠ 이 표는 `status_code` 를 함께 갖는다 — **끝 시각을 찍으면서 `status_code` 도 「종료」로 옮긴다**(G-16 보완)⌝.

#### `POST /production/precheck-decisions` — `PrecheckDecisionCreate`
required **5**: `workOrderId` · `equipmentId` · `decidedAt` · `controlLevelCode`(enum `BLOCK`·`WARN`·`OFF`) · `decisionCode`(enum `PASSED`·`BLOCKED`·`WARNED`·`OVERRIDDEN`). 선택 `basisInspectionId`(nullable) · `overrideReasonCode`(nullable).

### 2-2. 조건 ① 후보 셋 — 명시 판정

#### ⓐ `work_session.shift_id` NOT NULL ↔ 계약 「비운 채 기록」 — **⭕ 마이그 1건**

#### ⓑ `terminal_id` NOT NULL + 단말 토큰 부재 — **✕ 마이그 0** · ⭐ **I-10 공유 물음**
**사실 관계(전부 실측)**
1. 계약 `WorkSession.terminalId` 는 **required** 이고 `WorkSessionCreate` 에 **칸이 없다**. `P-02-01` §5-A ⌜단말 — ⛔ **화면이 보내지 않는다 — 서버 파생.** 요청을 인증한 **단말 토큰**에서 서버가 푼다(F-2) — ⛔ 화면이 토큰을 열어 읽지 않는다⌝.
2. 서버는 단말 토큰을 **이미 발급한다** — `terminal.service.ts:215` `{ sub: terminalId, typ: TOKEN_TYPE.TERMINAL, tv: token_version }` · TTL 365일 · **세션 쿠키와 같은 비밀키**.
3. **그러나 파싱하는 자리가 0이다** — `session-resolver.service.ts:54` 가 `typ !== SESSION` 이면 `null` 을 낸다. `Session`(`session.types.ts`)에 단말 칸이 **없다**. `authentication.guard.ts:24` 주석 ⌜**단말 토큰(POP·모바일)은 아직 없다.** 계약이 `terminalToken` 을 정의만 하고 `security` 를 어디에도 걸지 않아 어느 오퍼레이션이 단말용인지 계약만으로는 못 가른다⌝(실측 — `production-02*.json`·`mdm-*.json` 에 `securitySchemes` **0** · `app-공통.json` 에만 `terminalToken`(http bearer) 하나 · `security` 를 건 오퍼레이션 **0건**).
4. `material_consumption.terminal_id` 도 **NOT NULL** 이고 `MaterialConsumption.terminalId` 도 **required** 다 — **I-10 이 같은 벽을 만난다.**
5. 형제 선례는 **안 통한다** — `production_result.terminal_id` 는 **nullable** 이고 `ProductionResult.terminalId` 가 **required 밖**이라 I-7 이 「비운다」로 지나갈 수 있었다(`production-result.service.ts:137` 주석). 세션은 둘 다 반대다.

- **0단계 선례**: 없다(위 5).
- **1단계**: 모든 `POST /work-sessions` 가 이 값을 필요로 한다 → **본길**. ⇒ 「임의로 못 고른다. **계약 문자 그대로** + 문의.」
- **계약 문자**: 「요청이 실어 보낸 **단말 토큰**에서 서버가 푼다」. 계약은 그 토큰의 **전송 수단까지 적었다**(`terminalToken`: `type: http` · `scheme: bearer` · ⌜단말 등록 때 발급한 값을 **기기가 저장해 보낸다**⌝). 침묵한 것은 「그 토큰이 **인증**도 겸하는가」뿐이다(`security` 미부착).
- ⇒ **채택 — 「`Authorization: Bearer <단말 토큰>` 을 읽어 `terminal_id` 로 쓴다. 인증은 그대로 계정 세션이 진다.」**
  - 검증: 같은 비밀키로 서명 검증 → `typ === TOKEN_TYPE.TERMINAL` → `terminal` 행 존재 + `is_active` + `token_version === tv`. 하나라도 어긋나면 **400 `INVALID`**(`field: 'Authorization'` · 「재발급이 필요하다」).
  - 헤더가 없으면 **400 `REQUIRED`** — 값을 지어내지 않는다.
  - ⛔ **`AuthenticationGuard` 를 고치지 않는다.** 단말 토큰은 **`X-Worker-No` 와 같은 «귀속» 축**으로만 쓴다(사번이 사람을 귀속시키듯 토큰이 단말을 귀속시킨다). 인증 축을 바꾸면 「어느 오퍼레이션이 단말용인가」를 우리가 정하게 되고, 그것은 계약이 `security` 로 말하지 않은 것을 지어내는 일이다.

## 3. ⭐ `POST /production/work-sessions` — 이 슬라이스의 심장

### 3-1. 한 트랜잭션 순서

**tx 밖(선행)**
① 헤더 셋을 푼다 — `Idempotency-Key`(필수 · `runIdempotent` 가 쓴다) · `X-Worker-No`(없으면 **400 `REQUIRED`** · §3-7) · `Authorization: Bearer`(단말 토큰 → `terminalId` · §2-2 ⓑ) · `If-Match`(선택 · `ifMatchVersion(request)`).
② 단말 검증 — `terminal` 존재 · `is_active` · `token_version === tv`. 어긋나면 400 `INVALID`.
③ FK 존재 검증(400 `INVALID`) — `shiftId`(보냈으면) · `equipmentId` · `moldId` · `workerIds[]` 전건(`mdm.worker`). 배열 안 중복도 400 `INVALID`.
④ `controlOverride.reasonCode` → `assertCodeValues(…, 'CONTROL_OVERRIDE_REASON')`.
⑤ **채번 없음** — `session_no` 는 W/O 내 순번이라 `app.numbering_rule` 축이 아니다(§3-5). ⇒ I-2 R-2 의 「tx 밖 채번」 규약이 걸리지 않는다.

**tx 안(`this.prisma.$transaction`)** — `runIdempotent` 가 tx 를 넘겨주지 않으므로 서비스가 자기 `$transaction` 을 연다(I-9 R-10 · `idempotency.service.ts:67` → `master-write.ts:33`).

### 3-2. 게이팅 `can_start_work` — 판정 입력 세 표

```
work_order.routing_operation_id → planning.routing_operation.process_id   (실측 :2564)
mdm.terminal_process (terminal_id = 단말 토큰의 sub, process_id = 위)
  → can_start_work
```
- `P-02-01` §5-1 ⌜`terminal_process`(**이 단말 × 이 W/O 의 공정**)`.can_start_work = true`⌝ · ⌜행이 **없다** → 시작 불가 / 행은 있고 `false` → 동상⌝ ⇒ **행 부재도 거부**(`can_start_work ?? false` 가 아니라 `findUnique` 가 `null` 이면 거부).
- 봉투는 **403** — 계약 403 설명 ⌜**단말·권한 게이팅**에 막혔다⌝. `PermissionGuard`(계정 권한)와 **다른 축**이므로 가드가 아니라 서비스가 낸다. `ContractException(FORBIDDEN, [{scope:'screen', code: PERMISSION_DENIED, message:'이 단말은 이 공정의 작업을 시작할 수 없습니다.'}])`(화면 G-3 문구 그대로).
- `plan-uiux.md` 589행 ⌜플래그를 늘리지 않고 **기존 `can_start_work`·`can_input_result` 로만**⌝ — 이 슬라이스는 `can_start_work` **하나만** 본다. `:end`·events·workers·precheck 에는 **게이팅을 걸지 않는다**(`P-02-10` §5-1 ⌜작업 중단에 맞는 플래그가 8종에 없다 — **게이팅 없이 시작**하고 미매핑으로 기록⌝ · 계약도 그 셋에 `can_*` 를 안 적었다). 알려둘 것 ⓔ.

### 3-3. `shift_id` 도출 — 「시작 시각 + 단말의 공장」

- 본문에 `shiftId` 가 오면 **그 값을 쓴다**(존재 검증만). 계약이 칸을 열어 두었다.
- 없으면 서버가 푼다:
  1. `plantId = terminal.plant_id`(단말 토큰이 준 단말 · 계약 문자 「요청을 인증한 **단말의 공장**」 그대로) — ⛔ W/O 로 대체하지 않는다(`work_order` 에 공장 칸이 없고 `production_plan.production_order.plant_id` 2홉은 **nullable 사슬**이라 계약이 말한 축과 다르다 · I-9 §3-7 이 그 사슬을 쓴 것은 **채번**이라 축이 다르다).
  2. `plant.timezone_code` 로 `startedAt` 의 **공장 로컬 시:분**을 낸다 — `Intl.DateTimeFormat(…, { timeZone })`(선례 `operation-policy.service.ts:226` · `mold-derivation.ts:96`). ⛔ **날짜 타임존 캐스팅 금지**(CLAUDE.md) — SQL 로 캐스팅하지 않고 애플리케이션에서 시:분만 뽑는다.
  3. `mdm.shift(plant_id = 위, is_active)` 를 읽어 `start_time`·`end_time`·**`crosses_midnight`** 로 포함을 판정한다.
     - `crosses_midnight = false` → `start_time <= t < end_time`
     - `crosses_midnight = true` → `t >= start_time OR t < end_time`
     - **경계는 반열림**(시작 이상 · 끝 미만) — 공유계약 L-3 의 시각 기간 규약과 같은 결. 두 교대가 겹치면 **`start_time` 이 앞선 것**을 쓴다(정렬 한 줄 · 결정론).
  4. 어느 교대에도 안 들면 **NULL** — 세션을 막지 않는다(계약 명문).
- 단말의 공장에 `shift` 행이 0건이어도 **NULL**(막지 않는다).
- ⛔ **`work_order.planned_shift_id` 를 대신 쓰지 않는다** — 계약이 도출 축을 「시작 시각 + 단말의 공장」으로 못박았고 계획 교대는 다른 축이다(조용한 도출 금지).

### 3-4. `idempotency_key` — **두 벌을 다 쓴다**(I-7 방식 그대로)

`plan-integration.md` 309행이 ⌜`work_session.idempotency_key` 가 전역 UNIQUE 다 — `app.idempotency_record` 와 **이중이 되지 않도록 한쪽만** 쓴다⌝ 라 적었다. **I-7 이 이미 이 물음을 풀었다**:
- `production_result.idempotency_key` 도 **전역 `@unique`**(`schema.prisma:2830`)인데, I-7 은 컨트롤러에서 `runIdempotent` 를 감고(`production-result.controller.ts:73`) **컬럼에도 헤더 값을 그대로 넣었다**(`production-result.service.ts:145` 주석 ⌜헤더 값 «그대로» — **멱등 기록이 만료된 뒤의 재전송을 이 UNIQUE 가 둘째 그물로 막는다**⌝).
- ⇒ **같은 방식.** 「한쪽만」은 **판정 축이 둘이 되면 안 된다**는 뜻이고, 여기서는 판정을 `runIdempotent` 하나가 하고 컬럼은 **만료 뒤 둘째 그물**일 뿐이다. `P2002`(`uq_work_session_idempotency_key`)는 공용 Prisma 그물이 400 `UNIQUE_VIOLATION` 으로 옮긴다.
- `precheck_decision` 에는 그 칸이 **없으므로** `runIdempotent` 하나뿐이다.
- ⭐ 마이그레이션 `20260728020000` 의 주석이 이 판정의 근거를 이미 적어 두었다 — ⌜기존 「이미 진행 중」 409 로도 중복 세션은 막힌다. 그러나 그건 거부지 멱등이 아니다 … **멱등 키가 있어야 「그때 만든 그 세션」을 그대로 돌려줄 수 있다**⌝.

### 3-5. `session_no` — 채번 코어가 아니다

- `uq_work_session(work_order_id, session_no)` · CHECK `session_no > 0` · 계약 ⌜그 작업지시에서 세션을 «새로 열 때마다» 는다 … **⛔ 중단·재개로는 늘지 않는다**⌝.
- 전표 번호가 아니라 **부모 안의 순번**이라 `app.numbering_rule` 축이 아니다 — 선례가 실재한다: `production_result.result_sequence` 를 I-7 이 `MAX+1`(W/O 를 `FOR UPDATE` 로 잠근 뒤)로 채웠다(`production-result.service.ts:93-97`).
- ⇒ **`DEFAULT_PREFIX` 를 건드리지 않는다 · `numbering.service.ts` 무변경 · 결번 개념 없음.**
- 동시성: 1번의 `lockWorkOrder` 가 같은 W/O 의 두 요청을 직렬화하므로 `MAX+1` 이 안전하다(잠금 없이 하면 `uq_work_session` 이 런타임 충돌을 낸다).

### 3-6. ⭐ 세션 열기가 **precheck 를 읽지 않는다**

- 계약 `POST /precheck-decisions` 설명 ⌜통과·우회면 **이 기록 뒤에** `POST /production/work-sessions` 로 세션을 연다⌝ = **클라이언트의 호출 순서**다.
- `POST /work-sessions` 설명이 서버 몫으로 명시한 것은 ⌜**단말 게이팅(`can_start_work`)을 서버가 강제한다**⌝ **하나**이고, 통제는 ⌜통제 우회는 `controlOverride` 로 함께 보낸다⌝ 로 **본문 축**에 넘겼다.
- 화면도 같다 — `P-02-02` §5-9 ⌜**판정은 이 화면이 한다**⌝ · `P-02-01` §5-2 ⌜이 화면은 판정 결과를 **보이고** 통과 시 세션을 연다⌝ · F-5(게이트를 만드는 화면과 집행하는 화면을 나눈다).
- ⇒ **서버는 「최근 `BLOCKED` 판정이 있으면 거부」를 하지 않는다.** 그런 규칙을 넣으면 화면이 이미 내린 판정을 서버가 다시 내리는 것이고(판정 규칙 두 벌 — `P-02-02` §5-3 이 정확히 그것을 피했다), 「이력 없음 + WARN → 진행」이 서버에서 막힌다.
- ⭐ `controlOverride` 가 왔는데 그 W/O 가 **긴급이 아니면**? — 계약이 그 판정을 `POST /precheck-decisions` 의 x-internal-note 에만 적었다(`OVERRIDDEN` ⇒ `work_order_type_code`). §2 1단계 **가장자리**(우회를 보낸 요청에서만 갈린다) → 2단계 **기준 2(거부)** ⇒ **400 `INVALID`**(`field: 'controlOverride.reasonCode'` · 「긴급 작업지시에서만 우회할 수 있습니다」). 두 오퍼레이션이 **같은 판정**을 하는 편이 우회가 두 문으로 들어오는 것보다 안전하다(P-02-02 §5-8 ⌜아무 지시나 우회하면 통제가 무의미하다⌝). 알려둘 것 ⓕ.
- `controlOverride.note` — **담을 칸이 0**(`work_session_event` 에 메모 칸 없음 · `work_session.remarks` 는 세션 축이다) ⇒ **받아서 버린다**(I-6 `:cancel` 의 `note` 선례). 알려둘 것 ⓖ.

## 4. `POST …/{workSessionId}:end` — 세션 닫기

한 트랜잭션:
1. `SELECT … FROM production.work_session WHERE work_session_id = $1 FOR UPDATE` → 없으면 **404**.
2. `assertVersion`(If-Match 선택 · 세션의 `version_no`).
3. `assertTransition('production.work_session.status_code', 'work-session-end', row.status_code, BAD_REQUEST)` → `from: ['RUNNING','STOPPED']` → `ENDED`. 이미 `ENDED` 면 **400 `STATE_LOCKED`**.
4. `endedAt < started_at` 이면 **400 `RANGE`**(`field: 'endedAt'`) — DB CHECK `ck_work_session_dates` 를 손으로 앞당긴다(CHECK 위반은 `PrismaClientUnknownRequestError` 라 공용 그물에 안 걸린다 · `work-order-write.service.ts:88` 주석과 같은 이유).
5. UPDATE `work_session` — `ended_at` · `status_code='ENDED'` · `version_no+1` · `updated_by`. **`stop_reason_code` 는 건드리지 않는다**(계약 x-no-code-key ⌜비운다⌝ · A-25 확정 ②). 본문에 `stopReasonCode` 가 와도 **저장하지 않고 400 도 내지 않는다**(계약이 프로퍼티를 열어 두었으므로 거부하면 계약 유효 요청을 막는 것이다 — I-6 `:hold` 의 「받아서 저장하지 않는다」 선례). 알려둘 것 ⓚ.
6. INSERT `work_session_event` **END** — `occurred_at = endedAt` · `performed_by`=세션 사용자 · `terminal_id`=단말 토큰 · `reason_code` **없음**(A-25).
7. ⛔ **`work_order` 를 건드리지 않는다** — 계약이 `:end` 설명에서 W/O 를 한 번도 언급하지 않았고, `transitions.ts` 의 W/O 키에 「세션 종료」 액션이 없다. W/O 는 `IN_PROGRESS` 로 남고 `:close` 가 닫는다(`:close` 의 `from` 에 `IN_PROGRESS` 가 있다). ⇒ **세션 층 ≠ W/O 층**(`plan-integration.md` 308행).
8. ⛔ **참여 중 작업자의 `left_at` 을 자동으로 찍지 않는다** — 계약 침묵. §2 1단계: `:end` 마다 갈리므로 **본길** → 계약 문자 그대로 = 아무 말도 없으니 **쓰지 않는다**(기준 4 — 값을 조용히 도출하지 않는다). ⇒ 종료된 세션의 `GET …/workers?active=true` 가 사람을 계속 든다 → **문의 050+4**. 흔적: 단위 테스트 `:end 가 work_session_worker.left_at 을 찍지 않는다` `// 설계 미정 — 문의 050+4`.
9. 응답 200 `WorkSession`(되읽기) · **ETag 없음**.

## 5. `POST …/{workSessionId}/events` — 세션 사건 적재

### 5-1. 전이표에 더하는 것 — W/O 키 1 + **세션 키 신설**

```ts
// production.work_order.status_code  (기존 키 — 액션 하나를 더한다)
'work-session-start': { from: ['RELEASED', 'IN_PROGRESS'], to: 'IN_PROGRESS',
  sourceOperation: 'POST /production/work-sessions' },

// production.work_session.status_code  (신설 키 — 액션 셋)
'work-session-stop':   { from: ['RUNNING'],            to: 'STOPPED',
  sourceOperation: 'POST /production/work-sessions/{workSessionId}/events' },
'work-session-resume': { from: ['STOPPED'],            to: 'RUNNING',
  sourceOperation: 'POST /production/work-sessions/{workSessionId}/events' },
'work-session-end':    { from: ['RUNNING', 'STOPPED'], to: 'ENDED',
  sourceOperation: 'POST /production/work-sessions/{workSessionId}:end' },
```

- ⚠ **I-6 §8-6 854행은 `from: ['RELEASED']` 라 적었다. 이 계획은 `['RELEASED','IN_PROGRESS']` 로 넓힌다** — 근거: 계약 `sessionNo` 설명 ⌜세션을 **«새로 열 때마다»** 는다(작업 완료·교대 마감으로 `:end` 한 뒤 **다시 시작하는 경우**)⌝. 첫 세션을 `:end` 해도 W/O 는 `IN_PROGRESS` 로 남으므로(§4-7) **둘째 세션은 `IN_PROGRESS` 에서 열린다.** `['RELEASED']` 만 두면 계약이 명문으로 연 경로가 `transitions.ts` 에서 던진다. `to` 가 같은 값이라 **상태가 넓어지지 않는다**(`:release` 가 `from: ['PLANNED','CONFIRMED']` 로 같은 모양을 쓴 선례 · `plan-api.md` 818행). §10 #6 에 기록한다.
- ⛔ `SUSPENDED` 는 `from` 에 **넣지 않는다** — `P-02-01` §5-5 ⌜**작업 시작** \| 상태 = **배포** / **재개** \| 상태 = **중단** → 같은 세션에 `RESUME` 적재⌝ 이므로 중단된 W/O 에서 새 세션을 여는 경로는 계약·화면 어디에도 없다(기준 2 — 거부하는 쪽). ⇒ 400 `STATE_LOCKED`.
- ⭐ **유혹 9 에 걸리지 않는다**(`plan-integration.md` 668행) — 상태값을 지어내지 않았다. `WORK_SESSION_STATUS` 3값이 **시드·DB 에 실재**하고 A-25 전이표가 START·RESUME→진행 / STOP→중단 / END→종료를 **문장으로 확정**했다. `sourceOperation` 셋 다 계약에 실재한다(`document-state.spec.ts` 의 「계약에 실재한다」 단언 통과).
- ⛔ **세션의 탄생(`RUNNING`)은 전이가 아니다** — `from` 이 없는 자리라 표에 담을 수 없다(`logistics.goods_issue.status_code` 의 `postImmediately` 주석과 같은 판단).
- ⛔ **이력 표가 없다** → `transitionCode` 를 쓰지 않는다(LOT 축만 갖는 칸).
- `conflictStatus` = **400**(`HttpStatus.BAD_REQUEST`) — `work-order-transition.service.ts:71` 과 같다.

### 5-2. 유형별 처리

| `eventTypeCode` | 서버 | 세션 `status_code` |
|---|---|---|
| `STOP` | 액션 `work-session-stop` | `RUNNING` → `STOPPED` |
| `RESUME` | 액션 `work-session-resume` | `STOPPED` → `RUNNING` |
| `START`·`END`·`CONTROL_OVERRIDE` | ⛔ **400 `INVALID`**(`field: 'eventTypeCode'` · 「이 사건은 세션을 열고 닫는 오퍼레이션이 만듭니다」) | — |
| 그 밖의 문자열 | `assertCodeValues(…, 'WORK_SESSION_EVENT_TYPE')` → 400 `INVALID` | — |

- 계약 명문 ⌜이 오퍼레이션으로 단말이 적재하는 것은 **STOP·RESUME 뿐**⌝ ⇒ 셋을 막는 것은 **계약 문자 그대로**이지 좁히는 것이 아니다.
- ⭐ **`P-02-01` 의 [재개]도 이 경로다** — `RESUME` 을 적재하고 **새 세션을 열지 않는다**. 화면이 `:resume`(W/O)을 부르지 않는다(계약 ⛔ 명문 · 문의 035 가 이미 그 비대칭을 올려 두었다).

### 5-3. `reason_code` — A-25 대응표 그대로

| `event_type_code` | 그룹 | 사유 | 위반 시 |
|---|---|:-:|---|
| `START` | — | **비운다** | (단말이 못 보낸다) |
| `STOP` | `WORK_SESSION_EVENT_REASON`(7값) | **필수** | 없으면 **400 `REQUIRED`** · 그룹 밖이면 400 `INVALID` |
| `RESUME` | — | **비운다** | 오면 **400 `INVALID`**(`field: 'reasonCode'`) |
| `END` | — | 비운다 | (단말이 못 보낸다) |
| `CONTROL_OVERRIDE` | `CONTROL_OVERRIDE_REASON`(2값) | 필수 | (세션 열기가 만든다 — `controlOverride.reasonCode`) |

「`STOP` 사유 필수」는 **A-25 가 내린 판정**이다(화면 `P-02-10` §6 이 2026-08-23 에 ⓐ 차단으로 바꿨다 — ⌜목록에 `OTHER`(기타)가 있어 **차단해도 현장이 막히지 않는다**⌝). ⇒ 서버가 그대로 강제한다.

### 5-4. 나머지

- `occurred_at` = 본문 그대로(**단말 시계** · C-12 — 서버가 덮지 않는다). `recorded_at`(계약)은 **`created_at` DB 기본값**으로 낸다(§2-1).

- ⛔ **`work_order` 를 건드리지 않는다** — 계약 ⌜⛔ `/production/work-orders/{workOrderId}:resume` 를 부르지 않는다⌝ 의 대칭. I-6 이 반대 방향을 이미 못박았다.

### 6-2. `POST …/workers` — 참여

1. 세션 존재(404) → `FOR UPDATE` 불필요(세션 상태를 안 옮긴다) 하지만 **If-Match 대조를 위해 `version_no` 를 읽는다**.
   ⚠ If-Match 가 오면 세션 `version_no` 와 대조한다 — 그러나 **참여는 세션 행을 UPDATE 하지 않으므로 `version_no` 를 올리지 않는다**(계약이 `WorkSessionWorker` 응답에 `versionNo` 를 안 준다). 알려둘 것 ⓘ.
2. `workerId` 존재(400 `INVALID`).
3. `workerRoleCode` 가 오면 `assertCodeValues(…, 'WORK_SESSION_WORKER_ROLE')` · 안 오면 **칸을 안 넣는다**(물리 default `'OPERATOR'` · §2-2 ⓒ).
4. **중복 참여** — 같은 `worker_id` 가 이 세션에 `left_at IS NULL` 로 이미 있으면 **400 `STATE_LOCKED`**(「이미 참여 중인 작업자입니다」).
   §2 1단계 가장자리 → 기준 2(거부) · 봉투는 400(§1-6 · I-9 R-9 선례). 물리에 UNIQUE 가 없으므로 **애플리케이션 잠금**이다 — 동시 두 요청은 뒤가 통과할 수 있다. `work_session` 행을 `FOR UPDATE` 로 잠가 직렬화한다(세션 축 한 줄).
   ⭐ **떠난 사람의 재참여는 허용한다** — 계약 ⌜같은 사람이 다른 세션에서 다른 값을 가질 수 있다 — `joinedAt`·`leftAt` 이 붙은 «참여 구간»의 속성⌝ 이 구간 개념을 세웠고, 「행을 지우지 않는다」가 이력임을 못박았다.
5. **종료된 세션(`ENDED`)에 참여** → **400 `STATE_LOCKED`**(가장자리 → 기준 2). ⛔ 전이표를 타지 않는다(상태가 안 바뀐다) — 서비스 손검사.
6. `joined_at` = 본문(단말 시계) · `created_by` = 세션 사용자. 201 `WorkSessionWorker`.

### 6-3. `:leave` — 이탈

1. 세션 존재(404) · `work_session_worker` 존재 **그리고 그 세션 소속**(아니면 404 — 남의 세션의 참여 행을 경로로 물어도 못 찾게 한다).
2. **이미 `left_at` 이 있으면 400 `STATE_LOCKED`**(계약 ⌜행을 지우지 않는다⌝ — 두 번 찍지 않는다).
3. `leftAt < joined_at` → **400 `RANGE`**(CHECK `ck_work_session_worker_dates` 앞당김).
4. **종료된 세션에서도 이탈을 허용한다** — §4-8 이 자동 이탈을 안 찍기로 했으므로 사후 정리 경로를 닫으면 「영원히 참여 중」이 확정된다(기준 2 의 「거부」가 오히려 업무를 없앤다 — I-4 §5-3 단서).
5. UPDATE `left_at` 만. `version_no` 없음. 200 `WorkSessionWorker`.
6. If-Match 헤더 **없음**(계약) — 읽지 않는다.

### 6-4. 세 오퍼레이션 모두 **`work_order` 를 안 건드린다**

`work_session_event`·`work_session_worker` 는 W/O 상태 축과 무관하다. I-6 ⓟ(마감 뒤 UPDATE 를 트리거가 막는다)에 닿는 것은 **`POST /work-sessions` 하나뿐**이고 그 자리는 §3-1 3번이 앞서 막는다.

## 7. `POST /production/precheck-decisions` — 통제 판정 기록

### 7-1. 검증 순서

1. `X-Worker-No` 없으면 **400 `REQUIRED`** → `mdm.worker.worker_no` 에 없으면 400 `INVALID`(값을 저장하므로 존재를 본다).
2. `workOrderId`·`equipmentId` 존재(400 `INVALID`).
3. `basisInspectionId` 가 오면 `maintenance.equipment_inspection` 존재(400 `INVALID`) — ⭐ **표는 실재하고 0행이다**(`src/maintenance/` 모듈은 **없다** — I-30 몫). **FK 존재 검사만** 한다: 점검 유형·주기·종합 판정을 서버가 다시 보지 않는다(판정은 화면이 한다 · §7-3).
4. **`decisionCode` × `overrideReasonCode` 짝**
   | 경우 | 판정 |
   |---|---|
   | `OVERRIDDEN` + `overrideReasonCode` 없음 | **400 `REQUIRED`** |
   | `OVERRIDDEN` + `work_order_type_code ≠ 'EMERGENCY'` | **400 `INVALID`**(x-internal-note 명문) |
   | `OVERRIDDEN` 아님 + `overrideReasonCode` 있음 | **400 `INVALID`**(⌜`OVERRIDDEN` 일 때만 값이 있다⌝) |
   | `overrideReasonCode` 가 `CONTROL_OVERRIDE_REASON` 밖 | **400 `INVALID`**(`assertCodeValues`) |
5. `controlLevelCode` × `decisionCode` **12조합은 서버가 가르지 않는다**(§7-3).
6. INSERT — `decided_at`=본문(단말 시계) · `worker_no`=헤더 문자열 · `created_by`=세션 사용자. `runIdempotent` 하나(멱등 칸 없음 · §3-4). 201 `PrecheckDecision`. **ETag·If-Match 없음.**

### 7-2. 409 자리 — **도메인은 안 낸다**

계약이 409 를 선언했으나(`ProductionConflictResponse`) 이 표에는 `version_no`·유일 제약이 **하나도 없고** 「같은 판정을 두 번」이 업무적으로 정상이다(P-02-02 §5-9 ⌜**다시 확인** — 항상 · 판정을 다시 돌린다⌝). ⇒ **409 의 유일한 출처는 멱등 계층**이다(지문 불일치 · 처리 중 재전송). 없는 자리를 지어내지 않는다(I-9 §3-9 와 같은 처리).

### 7-3. `controlLevelCode` 를 **대조하지 않는다**

계약 응답 설명 ⌜**판정 시점에 적용된 통제 수준의 스냅샷** … 정책이 나중에 바뀌어도 이 기록은 바뀌지 않는다⌝ + 요청 설명 ⌜**화면이 읽은** 통제 수준. 적용 정책이 없으면 WARN⌝ ⇒ **화면이 읽은 값을 그대로 저장한다.** 서버가 `app.operation_policy` 를 다시 읽어 대조하면 ① 화면과 서버가 서로 다른 시점의 정책을 읽어 정상 요청이 400 이 되고 ② A-18(판정 근거가 움직이면 스냅샷)이 이 칸을 둔 이유가 사라진다. DB `operation_policy` **0행** 실측이라 오늘 대조를 켜면 `WARN` 밖 값이 전부 막힌다(본길). 알려둘 것 ⓒ.
