## 1. 계약 전건 읽기 표

### 1-1. 오퍼레이션·헤더·응답

| 오퍼레이션 | 멱등 | If-Match | Worker-No | ETag | 성공 | 그 밖 응답 | 제안 |
|---|---|---|---|---|---|---|---|
| `GET /trace/serial-numbers` | 없음 | 없음 | 없음 | 없음 | 200 `{items,page}` | 명시 없음 | 구현 |

근거: production 계약 `:4039`~`:4220`. POST 설명은 양품 N개→개체 N행, 서버 발번, 한 트랜잭션·전량 되돌림, 발행 기록 별도, 오프라인 큐는 연결 뒤 송신을 명시한다. 202·BatchResult·부분 성공을 만들지 않는다.

공용 헤더 전건(`:4221`~`:4265`):

- `Idempotency-Key`: `type:string, format:uuid, required:true`. 같은 키 재전송은 새 전표를 만들지 않는다. 이 계약은 `businessDate` 칸이 0이며 원장 영업일 키를 요구하지 않는다.
- `If-Match`: `type:string, required:false`. 없으면 검사를 생략. 제공된 값의 **대상 버전/GET 원천**은 이 POST 설명에 없다(§6-2).
- `X-Worker-No`: `type:string, maxLength:50, required:true`. 귀속용이며 인증이 아니다. `mdm.worker.worker_no`가 원천, 6자리 숫자 패턴은 **강제하지 않는다**.

### 1-5. 에러 봉투 전건

`ErrorResponse` required1 = `errors:ErrorItem[]`. ErrorItem required3 = `scope`, `code`, `message`; `scope` enum `field|screen`; 선택 `field:string`, `uniqueScope:string[]`. 400·403은 이 봉투다(`:4286` 이후).

## 2. 물리 대조와 마이그레이션 결론

### 2-1. 실물은 이미 있다 — 신설 표0, 현재 마이그0

`prisma/schema.prisma:3677`의 `trace.serial_number`는 scalar **11칸**:
`serial_number_id` identity PK · `serial_no varchar(150) NOT NULL UNIQUE` · `item_id NOT NULL FK` · `lot_id NOT NULL FK` · `status_code varchar(50) NOT NULL` · `produced_at? timestamptz` · `created_at/default clock_timestamp()` · `created_by? bigint` · `updated_at/default clock_timestamp()` · `updated_by? bigint` · `version_no/default1 CHECK >0`.

- B DB SELECT에서 제약5 = PK·전역 serial_no UNIQUE·item FK·lot FK·version CHECK. index2 = PK와 serial_no만. `lot_id` 인덱스는 없다.
- 비내부 trigger1 = UPDATE 때 `app.set_updated_at()`. 상태 자동 채움·개체수≤양품·품목=LOT품목 검사는 DB에 없다.
- `status_code`의 DEFAULT·컬럼 주석 모두 NULL. baseline `:2142`~`:2154`에도 기본값이 없다.
- 조회가 반환할 7칸은 전부 물리에 있다. 발번의 필수 상태값은 **칸 결손이 아니라 의미/값 원천 결손**이다. nullable 마이그는 required 응답을 못 채우므로 해결책이 아니다.
- `serial_component_relation`은 이 두 계약의 입력/출력/행위에 없다. S17의 「쓰는 표」 기재와 달리 **쓰기0**. 임의 조립 관계를 만들지 않는다.
- 발행기록·원장·LOT 생애/품질/홀드·W/O 상태 쓰기0. `created_by/updated_by`는 계정 id이며 사번을 이 칸에 넣지 않는다.

## 3. 즉시 구현 가능한 GET

`src/trace/serial-number/serial-number.controller.ts`·`serial-number-query.service.ts`·`serial-number-view.ts`를 둔다. `/trace` 경로이므로 production 모듈에 등록하지 않는다. controller에는 GET `@Contract` 하나만 단다.

조회 순서:

1. 계약 검증된 질의로 `where` 하나를 만든다. 모든 optional 필터는 `undefined`일 때만 생략한다.
2. `pageRequest`로 skip/take를 얻는다. 정렬은 **`serial_number_id ASC`** 고정으로 제안한다. nullable 생산시각 대신 발번된 개체 순서를 안정적으로 보여 준다(정렬 계약 없음, §9 판정).
3. 같은 where의 `findMany`와 `count`를 Prisma 배열 `$transaction`의 **RepeatableRead** 스냅샷에서 실행한다. 목록 응답 한 번의 `items`와 `total`이 동시 발번 때문에 서로 다른 시점을 세지 않게 한다. DB 쓰기 0·명시적 행 잠금 0이다.
4. 행을 §1-4 매퍼로 옮겨 `pagedResponse`를 반환한다. 조인 없이 개체 행의 값만 읽는다. 저장 상태는 알 수 없는 문자열이라도 보존한다.

시간 경계는 `serial-number-time-boundary.ts`의 로컬 순수 함수로 만든다. 실제 `notification-time-boundary.ts` 54줄의 검증된 계산을 재사용하되 app 도메인 import는 하지 않는다. T/t/단일 공백류·Z/z·±HH:MM/±HHMM/±HH를 정규화하고, 6자리 뒤 비영 소수는 **양 경계 모두 µs 격자로 올림**한 문자열을 Prisma 조건에 직접 전달한다. 저장 µs 격자에서 `x >= q`와 `x < q` 모두 이 변환이 동치다. `new Date`의 ms 절삭·Postgres 캐스트 반올림·6자리 단순 절삭은 금지한다. 응답 `producedAt`의 기존 Date 매핑과 필터 판정 정밀도는 별개이며, 이 helper는 저장 시각을 수정하는 함수가 아니다.

GET 전체에는 멱등·Worker-No·수동 권한 등록·비즈니스 ETag0. 기존 derived 권한표 `:142`에 GET이 있어도 `PermissionGuard`는 403 미선언이면 검사하지 않는다. 공용 인증 가드에 따른 세션은 계속 필요하다(현재 단말 토큰 단독 요청은 이 가드를 통과하지 못함).

P-02-05는 LOT 진척의 양품과 `GET /trace/serial-numbers?lotId=...`의 **필터 없는 전체 `page.total`**을 비교한다. 상태·검색·생산시각 필터가 걸린 total을 기발번 전체로 쓰면 안 된다. 두 GET 사이의 시점 차이는 남으며, 최종 허용 수량은 POST의 잠금 후 재집계만 확정한다. 새 미리보기/잔량 API는 만들지 않는다.

## 4. 조건부 채번 설계 — 상태 본길 해소 뒤 재수립할 권고안

### 4-1. 상태와 번호는 위임 근거가 다르다

번호는 POST `:4151`의 「번호는 서버가 매긴다」와 `:4215`의 「계약은 서버가 매긴다까지만 정하고 규칙을 정하지 않는다」, 화면 §8-2의 「서버 몫」으로 **판정 주체가 넘어왔다**. 상태에는 이 문구가 없다. 따라서 번호 형식 미정 자체만으로 GET/POST 전부를 유보하지 않는다.

현재 코어는 `NumberingService`라는 이름이며 `CoreNumberingService`가 아니다. 기본 유형13개에 SERIAL이 없고, 지원 토큰은 `{YYYYMMDD}`·`{YYMMDD}`·`{SEQn}`뿐(`:9`·`:133`). `{PLANT}`·`{LOT}`를 템플릿에 심으면 throw하며 자동 확장되지 않는다.

권고안은 **도메인에서 `P{plantId}-L{lotId}-{coreNumber}`를 조립**하고 `coreNumber`는 `next('SERIAL_NUMBER', null, periodDate)`로 얻는 것이다. `SERIAL_NUMBER:'SN'` 기본 접두어 한 줄만 별도 코어 PR에서 추가하고 기존 DAILY 카운터를 재사용한다. 공장 코드·lot_no는 변경/공장 중복이 가능하므로 숫자 식별자를 쓰며, 공장별 카운터 선택은 하지 않는다. 기존 전역 카운터+LOT 식별자가 유일성을 진다. 일반 형식만 제안하며 실제 발번 예시·규칙 행을 지금 만들지 않는다.

`periodDate` 후보는 본문 producedAt의 UTC 날짜, 생략 시 **요청 준비 시 한 번 잡은 UTC 날짜**다. 생산시각 컬럼을 채우는 것과 번호의 운영 날짜를 고르는 것은 별개다. 실패 재시도 동안 날짜를 유지한다. 기본 형식 최대 길이는 양의 bigint19자리 기준 **73자**이며 custom pattern 때문에150자를 넘으면 잘라 저장하지 않고 실패시킨다. 이 권고안·UTC 축·패턴 길이/비활성 규칙 오류는 상태 유보 해소 때 함께 재수립한다.

### 4-2. 전량 성공과 번호 연속성

계약이 보장하는 결과는 **`quantity=N`이면 개체 N행이 전부 생성되거나0행**이다. 번호 카운터의 무결번·동시 배치 사이 연속 구간·실패한 번호 재사용까지 명시적으로 보장하지 않는다. 화면 §9는 「개체 번호는 연속이어야」라고 적어 코어 결번 허용과 어휘가 다르므로 문의에 정확히 남긴다.

권고안은 N회의 `next()`를 순차 완료한 뒤 업무/멱등 tx를 연다. 전량 롤백 뒤 예약 번호가 소모되는 것은 허용하되, 개체 N개 중 일부만 커밋되는 것은 금지한다. `Promise.all` 1000회로 커넥션 풀을 채우지 않는다. 다른 배치가 채번 사이에 끼면 숫자는 연속하지 않아도 `issuedCount=N`이다. 무결번이 별도로 요구되면 이 권고안을 쓰지 않고 별도 코어 범위를 재수립한다.

중복 재시도는 기존 `NUMBER_RETRY=3` 선례를 따른다. `P2002` 중 **target이 serial_no인 경우만** 전체 rollback 뒤 전건 새 번호로 재시도한다. 멱등키 충돌·FK·설정 오류·타임아웃을 번호 충돌로 삼키지 않는다. 상한 소진은409 `DUPLICATE_KEY`. `skipDuplicates:true`는 부분 성공을 만들므로 금지한다.

## 5. 조건부 POST의 한 트랜잭션

### 5-1. LOT 양품 정본·사전 SQL

LOT 실적 정본은 **`production.production_result_lot_allocation.allocated_qty`**다. `production_result.good_qty`는 W/O 실적 헤더 축이며 한 실적이 여러 LOT에 나뉠 수 있다. 현재 `LotService.progressOf`·`LotCompleteService`와 같은 합을 쓴다. `good_qty` 헤더를 LOT마다 붙여 합하면 과대 발번한다.

```sql
-- 아래는 POST 재개 시 업무 tx 안에서 쓸 문장 전문(지금 실행하지 않음).
-- $1 = body.lotId. 잠금 문장과 집계 문장을 하나의 CTE로 합치지 않는다.
SELECT lot_id, plant_id, item_id, source_type_code, source_id, version_no,
       lifecycle_status_code, status_code, completed_at
FROM trace.lot WHERE lot_id=$1 FOR UPDATE;

-- 잠금을 얻은 뒤의 새 READ COMMITTED 문장으로 직전 발번 커밋을 본다.
SELECT uom_id, coalesce(sum(allocated_qty),0) AS allocated_qty
FROM production.production_result_lot_allocation WHERE lot_id=$1 GROUP BY uom_id;
SELECT count(*) AS issued_count FROM trace.serial_number WHERE lot_id=$1;
```

위 합은 아직 개체 수가 아니다. I-7은 요청 uomId를 배분에 저장하고 존재만 검증하므로 같은 LOT의 10 EA·2 BOX 또는 전부 KG도 가능하다(`production-result.service.ts:106`·`:181`). **개체 단위 대응/환산 정본이 입증된 집합만** good_qty로 계산한다. EA 문자열·base_uom 일치·decimalScale만으로 개체 단위를 정하지 않으며 item_uom_conversion의 존재만으로 목표 단위·유효일을 선택하지 않는다. 혼합/환산 불명 집합은 조건부400 INVALID(field=lotId), 업무/멱등 증가0으로 거부한다. 정상 허용 집합의 대응 원천조차 없으면 상태만 정해져도 POST를 재개하지 않는다. 기존 I-7 코드는 이 GET에서 변경하지 않는다.

단위가 해소된 뒤 Prisma `Decimal(good_qty).minus(issued_count).gte(quantity)`로 판정한다. 반올림/올림/number 부동소수 변환을 하지 않는다. 예: 개체 단위 배분합2.5·기발번1이면 quantity1은 허용, quantity2는400; 남는0.5를 개체1개로 바꾸지 않는다. 음수 잔량은0으로 덮어 고치지 않고 신규 발번을400으로 막는다.

배분 유일키는 **`(production_result_id, lot_id)`**이므로 동일 LOT에 여러 실적이 들어오는 것은 정상이고 전부 합한다. 같은 실적의 동일 LOT 중복은 DB uq가 막으며 I-7 입력 `assertAllocations`도 거부한다. `sum(distinct allocated_qty)`는 정상적인 같은 수량의 두 실적을 지우므로 쓰지 않는다. 배분합≤헤더 good_qty의 지연 트리거는 실적 단위 검사일 뿐 시리얼 상한을 대신하지 않는다.

### 5-2. 준비→멱등→LOT 잠금→배치→멱등 결과

| 순서 | 위치 | 하는 일 |
|---|---|---|
| 1 | tx 밖 | 계약·계정 기능 권한 가드. 사번 required/공백/길이 검사는 재생 전. actor/단말을 읽고 JSON 안전한 지문 생성. 완료된 동일 요청은 기존 run으로 결과 재생을 먼저 시도 |
| 2 | tx 밖 | 새 요청만 사번 존재, LOT 존재·품목·공장, 단말/공정 게이트를 읽고 기본 오류를 선검사. If-Match는 §6-2 재수립 판정을 적용 |
| 3 | tx 밖 | 번호 N개를 모두 준비. `NumberingService.next`는 **`IdempotencyService.run` 호출 전에 완료**. 실패 재시도도 이전 tx 종료 뒤 여기로 돌아옴 |
| 4 | 단 하나의 tx | `IdempotencyService.run(context, tx => commitWithin(tx,...))`. 이 tx가 idempotency IN_PROGRESS INSERT를 수행 |
| 5 | 같은 tx | LOT `FOR UPDATE`. 없음400. 준비 때 얻은 item/plant/source가 달라졌다면 prepared 번호를 쓰지 않고 전체 rollback, 밖에서 다시 준비. LOT 부모를 읽은 뒤 W/O를 추가 잠그지 않음 |
| 6 | 같은 tx | §5-1의 단위별 배분·개체 대응과 **상태/발행기록 여부로 좁히지 않은** 개체 count 재조회. 미확정 단위/잔량 초과400. 사번 존재·단말/공정 게이트도 전달 tx에서 최종 재확인 |

### 5-3. 동시성의 정확한 범위

- 다른 key·같은 LOT: 요청들이 같은 LOT 행을 직렬로 잠그고, 기다린 요청은 **잠금 획득 뒤 새 문장**에서 선행 개체 count를 본다. 두 요청이 각각 충분하다고 판정해 합계 상한을 넘지 않는다. 트랜잭션 시작 전 읽은 잔량·동일 CTE의 낡은 snapshot을 재사용하지 않는다.
- 같은 key: 멱등 PK 충돌을 기존 run이 처리한다. 한 번 성공한 결과를 재생하고 개체수를 늘리지 않는다. 키가 다르면 반복 발번이 합법이며 이미 만든 count만큼 남은 양품이 줄어든다.
- 서로 다른 LOT/공장: 업무 잠금은 독립이다. 번호 코어 카운터는 짧은 개별 DB 문장이고 업무 tx와 중첩하지 않는다.
- I-7 정상 등록은 W/O를 먼저 잠근 뒤 배분을 INSERT하고 L1을 수행한다. 이미 ACTIVE이면 L1은 LOT UPDATE를 생략한다(`lot-lifecycle.service.ts:59`); **LOT 잠금만으로 모든 배분 생산자를 막는다고 주장하지 않는다.** 현재 API의 배분은 양수 append라 동시에 추가되어도 잔량을 적게 볼 수 있을 뿐 과다 발번은 안 생긴다. 배분을 감소/삭제하는 새 경로는 같은 LOT 잠금과 시리얼 상한을 함께 지켜야 한다.
- I-7 정정은 새 실적만 만들고 배분을 수정/복사하지 않는다(`production-result-correct.service.ts:35`). 따라서 정정 뒤 W/O 양품과 LOT 양품은 달라질 수 있다(기존 문의044). I-26에서 header 잎 집계로 조용히 갈아타거나 기존 배분을 수정하지 않는다.
- 발번에 LOT·W/O 상태/버전 UPDATE를 추가하지 않는다. `FOR UPDATE`는 경쟁 개체수를 보호하기 위한 잠금이며 상태 전이가 아니다. 후속 코드가 다른 순서의 잠금을 요구하면 별도 재수립한다.

## 6. 횡단 계약·남은 가장자리

### 6-1. 멱등 래퍼의 실제 경계

`common/master/master-write.ts:24`는 fingerprint에 method/path·body만 넣고 `work:()=>Promise<T>`라 run이 제공하는 tx를 버린다. 서비스가 별도 `$transaction`을 열면 개체 commit 뒤 멱등 결과 기록 실패라는 틈이 생긴다. **I-26 POST는 이 래퍼를 사용하지 않고 공용 IdempotencyService를 직접 주입해 같은 tx를 받는다.** 공용 서비스/다른 레인 호출자는 수정하지 않는다.

fingerprint 권고안은 `requestFingerprint(operation, {body, query, actor:{appUserId,workerNo,terminalId}})`다. `app_user_id`는 저장만 될 뿐 기존 replay가 actor를 비교하지 않으므로 actor를 지문에 명시한다. POST의 계약 질의는0이지만 요청 query를 지문에서 빠뜨리지 않는다. `If-Match`는 요청 본문 식별이 아니라 조건부 토큰이므로 지문에 넣지 않고, 이미 성공한 재전송은 현재 잔량/버전보다 저장 결과 재생이 앞선다. 동등한 body 키 순서는 기존 stableJson이 정규화한다.

지문용 actor는 `{appUserId:number, workerNo:string, terminalId:string|null}`로 고정한다. `resolveTerminalId`의 실제 `bigint|null`은 `terminalId?.toString() ?? null`로 바꾸고 DB 검증에는 원래 bigint를 쓴다. `JSON.stringify(bigint)` 오류나 Number 정밀도 손실을 만들지 않는다. 지문을 위해 준비 객체/Prisma 객체 전체를 직렬화하지 않는다.

준비 전에 완료 응답을 재생하려면 로컬 조정자가 `idempotency_record` 존재를 선조회한 뒤 **최종 판정은 기존 run의 replay로** 위임한다. 선조회 뒤 기록이 삭제되어 run이 work를 부르는 경합에서는 로컬 `PrepareRequired` 표식으로 해당 tx를 rollback하고 준비를 tx 밖에서 다시 시작한다. 선조회가 없다고 판단했는데 상대 요청이 먼저 완료하면 준비 번호는 결번이 될 수 있지만 run이 저장 응답을 재생한다. 공용 replay 로직을 복제하거나 캐시 body를 무검증 반환하지 않는다. 이 조정자는 발번 사용처 하나에만 둔다.

기존 멱등 기록은 expires_at을72시간 뒤로 저장하나 run은 **만료시각 자체를 검사하지 않는다**(`idempotency.service.ts:66`). 기록이 실제 삭제되면 serial_number에는 별도 key/batch 축이 없어 재생을 복구할 수 없다. 새 영구 배치표·멱등키 컬럼을 선제 추가하지 않고 보존/삭제 정책의 한계로 문의한다. 「72시간 뒤 반드시 재발번한다」고 잘못 단정하지 않는다.

### 6-2. If-Match: 선택 여부와 토큰 원천은 별개

헤더 부재 허용/잘못된 형식400은 공용 가드가 이미 담당한다. **정상 형식의 헤더가 어느 행의 version인지 계약이 말하지 않는다.** GET 시리얼 목록에는 ETag가 없고 새로 만들 개체의 version1은 기존 수정 대상이 아니다. 본문의 LOT FK만 보고 lot.version_no를 상속하면 공유계약 B-1-1의 명시 규칙을 대신 결정하게 된다.

가장자리 제안: POST가 재개되더라도 원천 확정 전에는 **정상 형식 If-Match를 제공한 요청만400 `INVALID`(field=`If-Match`)로 거부**, 부재는 계약대로 허용. README §2 2단계 기준2(거부→허용은 완화)·4(원천을 조용히 도출하지 않음). 이는 선택 헤더의 사용 가능성을 줄이는 잠정 방침이므로 문의/재수립 대상이다. 형제 `material-return.controller.ts:52`의 「신규라 받되 무시」 선례도 함께 제시하되, 그것이 serial 계약의 빠진 원천 문장을 채웠다고 주장하지 않는다.

이 가장자리 제안과 관계없이 **현재 POST 전체는 상태 본길 때문에 미구현**이다. 유보 해제 시 If-Match 결론도 먼저 R-n으로 확정해야 한다. LOT 토큰 사용이 확정되면 비교는 LOT 잠금 뒤에 하고409 `VERSION_CONFLICT`·`currentVersion`·`conflictCause=user`를 내며, 토큰을 단순 개체수 잠금과 혼동하지 않는다.

## 7. 상태기계·발행기록 경계·배포 제한

신규 상태 축/전이/상태 이력 **0건**. `trace.lot.status_code` 품질과 `lifecycle_status_code` 생애, `serial_number.status_code`의 미정 축은 서로 다른 칸이다. LOT의 NORMAL/ACTIVE를 개체 초기값으로 복사하지 않는다. 코드 그룹 금지는 상태 필드 삭제/nullable 위임이 아니다.

GET 첫 페이지로 성공 배치를 재구성하지 않는다. I-26에서 발행기록을 쓰거나 실패 보상으로 개체를 삭제하지 않는다. 기록 성공 뒤 실물 인쇄 실패의 K-7 재발행은 I-27 경계다.

I-27은 대상 `SERIAL_NUMBER`·documentType `IDENTIFICATION_TAG`와 회차·발행기록을 받는다. PRINT/PDF/rendition은 별도 건너뜀 범위다. 현재 GET만 열면 저장된 개체 조회/복구 준비는 가능하지만 신규 발번 버튼까지 완결됐다고 보고하지 않는다. I-27의 LOT/기존 개체 대상 기록 경로는 I-26 POST 미구현과 별도로 범위를 재판정할 수 있다.

P-02-12의 긴급 생산도 정상 인식표 경로를 재사용하므로 POST 유보가 전파된다. derived GET 권한의 P-04-04는 실제 포장 단위/PACKING_LABEL 화면과 매핑이 다르므로 시리얼 소비자라고 단정하거나 공용 권한표를 수정하지 않는다. 빈 `items/total=0`은 저장 개체0이며 양품0·미발행 가능·미지원 상태를 대신 뜻하지 않는다.
