### R-3. §3-6 세 겹 — ②·③ 모순 해소: **③ 은 「이미 역처리됨 → `alreadyReversed:true`」 로 ②와 한 뜻이 된다** (integration 3 ⛔)

#### `POST …/{documentTypeCode}/{documentId}:cancel` — 취소 실행

- ⌜취소 실행. 승인이 끝난 요청만 받는다.⌝
- ⌜⭐ 서버가 후속 유무를 다시 판정한다 — 승인을 기다리는 사이에 후속이 생겼을 수 있고, 자동 실행이면 그것을 못 본다. 재판정에 걸리면 400(code=SUCCESSOR_EXISTS)이고 승인은 그대로 유효하다 — 새 요청을 다시 올리지 않는다(공유계약 J-8).⌝
- ⌜전기된 문서는 원장에 역트랜잭션을 만든다. 전기 전이었으면 상태만 바뀌고 원장에는 아무것도 생기지 않는다. 역처리가 재고 잔액을 음수로 만들면 400 이다.⌝
- ⌜승인 전이면 400 이다 — :post 가 승인 전이면 400 인 것과 같은 형태다.⌝
- 경로 파라미터는 `:request-cancel` 과 **글자 그대로 같다**(enum 3 · 같은 `x-code-key`).
- ⛔ **`requestBody` 가 없다.** `businessDate`·`occurredAt`·`remarks` 어느 것도 안 받는다 — 역트랜잭션의 영업일·시각·번호를 아무도 안 보낸다(§3-4·§3-5 · 문의 032).
- **응답 200** `CancelResult`.

## 3. 역트랜잭션 코어 — `InventoryPostingService.reverse()`

실측 전제: `src/core/inventory-posting/inventory-posting.service.ts` 는 **187줄 · public 메서드가 `post()` 하나**다. `reverse` 문자열 0건 — **이 슬라이스가 만든다**.

### 3-1. 시그니처 초안

```ts
// posting.types.ts 에 더한다
export interface ReverseInput {
  /** 되돌릴 원 트랜잭션. 파티션 키라 businessDate 가 짝으로 온다. */
  inventoryTransactionId: bigint;
  businessDate: string;          // 원 트랜잭션의 business_date (YYYY-MM-DD)
  /** 누가 되돌리는가 — 원장 created_by. */
  createdBy?: number;
  /** 역트랜잭션의 발생 시각. 취소 실행 시각을 호출자가 넘긴다. */
  occurredAt: Date;
}
export interface ReverseResult {
  inventoryTransactionId: bigint;   // 새로 만든 역트랜잭션
  transactionNo: string;            // → CancelResult.reversalTransactionNo
  businessDate: string;             // → CancelResult.reversalBusinessDate
  alreadyReversed: boolean;         // 멱등 재호출 흡수
}

// inventory-posting.service.ts
async reverse(tx: Prisma.TransactionClient, input: ReverseInput): Promise<ReverseResult>
```

- ⛔ **`transactionNo` 를 인자로 받지 않는다** — `post()` 는 받지만(호출자가 채번) 역트랜잭션의 번호는 **원 번호에서 파생**한다(§3-5). 호출자가 채번을 부르지 않으므로 「채번은 트랜잭션 밖」(I-2 R-2) 규칙에 걸리지 않는다.
- ⛔ **`businessDate` 를 «새로» 받지 않는다** — 원 트랜잭션의 것을 그대로 쓴다(§3-4).
- ⛔ **라인 목록을 받지 않는다** — 원 트랜잭션의 라인을 코어가 읽는다. 도메인이 「무엇을 되돌릴지」를 고르지 못하게 한다(부분 역처리 없음 — 계약이 부분 취소를 안 준다).
- `tx` 를 받는다 — 도메인 트랜잭션 안에서 돈다(`post()`·`createWithin()` 과 같은 모양).

### 3-2. 되돌리는 모양 — **부호가 아니라 `from`/`to` 를 뒤집는다**

물리가 `qty > 0` CHECK 를 걸었고 `post()` 도 음수 델타를 라인에 안 싣는다(`move()` 가 델타를 계산할 뿐 라인 `qty` 는 언제나 양수) ⇒ 선택지가 없다.

```
원 라인      qty=100  from=(W1,L1,GOOD,AVAILABLE)   to=null        (출고)
역 라인      qty=100  from=null                     to=(W1,L1,GOOD,AVAILABLE)

원 라인      qty=100  from=null                     to=(W1,L1,GOOD,AVAILABLE)   (입고)
역 라인      qty=100  from=(W1,L1,GOOD,AVAILABLE)   to=null

원 라인      qty=100  from=(W1,L1,…)  to=(W2,L2,…)  (이동)
역 라인      qty=100  from=(W2,L2,…)  to=(W1,L1,…)
```

- `ck_inventory_transaction_direction`(from·to 중 하나는 있어야 한다)은 뒤집어도 성립한다.
- `item_id`·`lot_id`·`uom_id`·`ownership_type_code`·`owner_partner_id`·`handling_unit_id` 는 **원 라인을 그대로 복사**한다.
- `line_no` 는 원 라인의 `line_no` 를 그대로 쓴다 — `uq_inventory_transaction_line` 이 헤더가 다르므로 안 깨지고, 원 라인과 1:1 로 대응해 읽기 쉽다.
- `from_qty_after_transaction`/`to_qty_after_transaction` 은 `post()` 와 같은 자리에 «역처리 뒤» 잔량을 싣는다.
- ⛔ **`inventory_transaction_line_id` 되짚기 칸(`goods_receipt_line`·`goods_issue_line`·`stock_transfer_line`)은 건드리지 않는다** — 원 라인을 가리킨 채로 둔다. 트리거가 원장 라인 UPDATE·DELETE 를 막고(§2-1), 그 칸은 「이 문서 라인이 «어느 원장 줄로» 들어갔나」의 기록이라 취소해도 사실이다(B-3 이력 불변). 역 원장으로 옮겨 쓰면 원 사실이 지워진다.

### 3-3. 헤더 칸 — 무엇을 복사하고 무엇을 새로 쓰나

### 3-4. `business_date` — 원 트랜잭션의 것 (⭐ 이 슬라이스의 가장 큰 §2 판정)

**문제**: `:cancel` 에 `requestBody` 가 없다. 그런데 역행은 `inventory_transaction` 에 들어가고 그 표는 `business_date NOT NULL` 이며 유일 제약 둘이 다 날짜를 물고 있다.

- **0단계 — 선례가 있다.** ⭐ **같은 규약의 둘째 구현(I-23 · S22)이 답을 적었다.** `contracts/shipment-04제품출하.json` 의 `ShipmentCancel` 은 `businessDate`·`occurredAt` **둘 다 required** 이고 그 설명이 ⌜영업일(발생일). **취소는 재고를 되돌리므로 원장을 지난다 — 유일 제약에 영업일이 들어 있다**(공유계약 C-8 · W-04-12 §5-8)⌝ 다. ⇒ **설계는 「취소가 원장을 지나면 영업일을 싣는다」를 이미 알고 있고, 01 의 `:cancel` 에서만 그것이 빠졌다.** 이것이 문의 032 의 본체다.
- **1단계**: 전기된 문서의 모든 취소가 영향을 받으니 **본길**이다 ⇒ 임의로 못 고른다. 계약 문자 그대로 + 문의.
- **계약 문자**: `CancelResult.reversalBusinessDate` ⌜역트랜잭션 영업일 — 원장 조회에 함께 쓴다⌝ — **서버가 «내려준다»**고만 적혔다. 즉 값을 «정하는 쪽»이 서버라는 것까지는 계약이 말한다.
- **2단계 · 갈래 둘**

| 갈래 | 나중에 뒤집는 비용 | 걸리는 기준 |
|---|---|---|
| ⓐ **원 트랜잭션의 `business_date`** | 낮다 — 값을 «읽어» 온 것이라 되돌리면 그만 | 기준 4 ⭕ (도출이 아니다) · CLAUDE.md ⭕ (⌜서버가 수신 시각으로 다시 잡지 않는다⌝) · 기준 2 ⭕ (§3-6 의 멱등키가 «같은 날짜»에서 돌아 이중 역처리를 DB 가 막는다) |
| ⓑ 취소 실행일(서버 시각) | 높다 — 원장 행에 남아 되돌릴 수 없다 | 기준 4 ✕ (⌜서버가 수신 시각으로 다시 잡지 않는다⌝를 정면으로 깬다) · 기준 2 ✕ (날짜가 달라져 `uq_inventory_idempotency` 가 이중 역처리를 못 막는다 — C-8 이 경고한 바로 그 구멍) |

- ⇒ **판정: ⓐ — `reversalBusinessDate = 원 트랜잭션의 business_date`.**
  ⭐ **부수 효과가 이 판정의 가장 강한 근거다** — 같은 영업일이면 `uq_inventory_idempotency (idempotency_key, business_date)` 가 `REVERSAL:{원 id}` 키로 **이중 역처리를 DB 차원에서 막는다**(§3-6). ⓑ 를 고르면 그 방어가 통째로 사라진다.
  ⚠ 대가: 이미 지난(회계상 마감됐을 수 있는) 영업일에 행이 하나 더 붙는다. 우리 모델에 원장 마감 개념이 없어(마감 표·마감 상태 0건 — 실측) 지금은 무해하다. 마감이 서면 뒤집을 자리다.
- **3단계 흔적**: 코드 주석 `// 역트랜잭션의 영업일은 원 트랜잭션의 것이다 — :cancel 이 businessDate 를 안 받는다(계약 실측). 서버가 수신 시각으로 다시 잡지 않는다(C-8 · CLAUDE.md). 04 ShipmentCancel 은 같은 행위에 businessDate 를 required 로 실었다 — I-5.md §3-4 · 문의 032` + 단위 테스트 이름 · **문의 032 갈래 ①**.
- `occurredAt` 은 다르다 — **취소 실행 시각(서버)** 을 쓴다. 그것은 「영업일을 다시 잡는 것」이 아니라 «새로 일어난 사건의 시각»이라 C-8 의 금지에 안 걸린다. `recorded_at` 이 이미 `clock_timestamp()` 인 것과 같은 성격.

### 3-5. `transactionNo` — `{원 번호}-R`

- **실측**: 오늘 `transaction_no` 는 **문서번호 그 자체**다 — `issue-posting.ts:154 transactionNo: header.goodsIssueNo` · `receipt-posting.ts:116 transactionNo: receiptNo`. 계약 example 의 `TX-2026-0011` 같은 별도 계열은 **한 번도 채번된 적이 없다**.
- `core/numbering` 의 `DEFAULT_PREFIX` 7값(`PO`·`GR`·`PT`·`NTC`·`AP`·`IR`·`GI`)에 `INVENTORY_TRANSACTION` 이 **없다**(실측) · `numbering_rule` 시드도 `PRODUCTION_RESULT` 하나뿐이다.
- **1단계**: 본길 · 계약 침묵. **2단계**: 기준 5「새 개념 수」 — 새 채번 유형 + 새 규칙 + 결번 관리를 세우는 쪽보다, **원 번호에서 파생**하는 쪽이 새 개념 0 이다. 그리고 원 행과 역 행이 1:1 이라 파생이 «도출»이 아니라 «식별»이다.
- **판정**: `transaction_no = ` `` `${원 transaction_no}-R` ``. 같은 영업일에서 `uq_inventory_transaction_no (transaction_no, business_date)` 를 안 깬다. 길이도 안전하다(`GI-20260906-0001` 16자 + 2 ≪ 100).
- ⛔ **채번 코어를 부르지 않는다** — 카운터를 소모하지 않으므로 「채번은 업무 트랜잭션 밖」(I-2 R-2) 규칙에 걸리지 않고, 롤백이 결번을 만들지도 않는다.
- **3단계 흔적**: 상수 `const REVERSAL_NO_SUFFIX = '-R'` + 주석 + 단위 테스트 · **문의 032 갈래 ②**.

### 3-6. 이중 역처리를 막는 세 겹 (I-4 §3-8 과 같은 모양)

| 겹 | 무엇이 막나 | 한계 |
|:-:|---|---|
| ① `runIdempotent` | 같은 `Idempotency-Key` 재전송을 앞의 응답으로 흡수 | 키가 다르면 안 막는다 |
| ② `reverse()` 선조회 + `uq_inventory_idempotency (REVERSAL:{원 id}, 원 영업일)` | 두 번째 역처리를 **같은 (키, 영업일)** 로 흡수 → `alreadyReversed:true`. ⭐ §3-4 ⓐ 판정 덕분에 **날짜가 절대 어긋나지 않아 C-8 구멍이 없다** | 「원 트랜잭션이 둘인 문서」에는 각각 걸린다(정상) |
| ③ **손검사** — `reversal_of_transaction_id = 원 id` 인 행이 이미 있으면 **400 `STATE_LOCKED`** | 유일 제약이 없는 자리를 코드가 대신 막는다 | 경합 시 ②가 UNIQUE 로 받는다 |
| ④ **상태 잠금** `document-cancel` `from:['CANCEL_REQUESTED']` | 두 번째 `:cancel` 은 상태가 `CANCELLED` 라 **400 `ALREADY_CANCELLED`** | — |

⇒ ⭐ **③이 코어의 몫이고 ④가 도메인의 몫이다.** ③은 e2e 로 도달하기 어렵다(④가 먼저 막는다) ⇒ **단위 테스트로 못박는다**(§9 PR ①).
- ⛔ **부분 유일 인덱스를 «걸지 않는다»** — 기준 3「스키마를 안 늘리는 쪽」. ②+③ 이 이미 막고, 인덱스를 걸면 「한 트랜잭션을 두 번 역처리하는 정당한 경우」(오늘은 없다)를 영구히 닫는다.

### 3-7. 잔액 갱신 순서 — I-4 R-1 의 7칸 오름차순 한 문장을 **코어 차원에서 한 번에**

I-4 R-12 ⓐ 가 넘긴 자리다(「입고 `postReceipt` 의 순서(ⓚ)를 코어 차원에서 한 번에 정한다」).

- **실측**: `post()` 는 라인 순서대로 `move()` 를 부르고 **선잠금이 없다**. 출고만 도메인(`issue-posting.ts` `lockBalances`)이 7칸 오름차순 한 문장으로 선잠근다. 입고(`receipt-posting.ts`)는 선잠금이 없다. ⇒ 입고 취소(역: 잔액 감소)와 출고가 같은 두 차원을 반대 순서로 잡으면 교착 가능(I-4 R-9 ⓚ 가 예고한 자리).
- **판정**: `reverse()` 는 **자기 안에서** 선잠금을 한다 — 원 라인 전건의 from·to 7칸 키(`legal_entity_id, business_unit_id, plant_id, warehouse_id, location_id, item_id, COALESCE(lot_id,0)`)를 **한 `VALUES` 목록으로 합쳐** `ORDER BY inventory_balance_id FOR UPDATE` 한 문장. I-4 R-1 ①②③ 을 글자 그대로 승계한다:
  - ① 교차곱 금지 — 행생성자 `IN (VALUES …)` 한 문장.
  - ② `to` 키(역행에서 «나가는» 쪽)도 같은 문장에 합친다.
  - ③ 같은 7칸 키의 라인이 둘이면 **합산**해 하한을 본다.
- ⛔ `post()` 는 **고치지 않는다** — 사용처가 이미 넷이고 diff 가 코어 PR ≤200 을 깬다. 대신 `reverse()` 안에 같은 불변식을 두고, 「입고도 선잠금하게 바꾼다」는 I-8(`plan-integration.md` §6-2 가 I-5 ∥ I-8 을 금지한 바로 그 파일)로 넘긴다 — §8 인계.

### 3-8. `NEGATIVE_BALANCE` — 코어가 «앞당겨» 막는다

- I-4 §3-3 이 「음수 금지는 코어가 아니라 도메인이다 — 트리거는 500 으로 샌다」로 갈랐다. **역처리는 반대다** — 되돌릴 수량을 도메인이 고르지 않고(§3-1) 코어가 원 라인에서 읽으므로 **검사도 코어가 한다**.
- 판정문: 선잠금으로 되읽은 잔액 행에서 7칸 키별 `available_qty` 를 보고, 역행의 «나가는 쪽»(from) 합계보다 작으면 **400 `NEGATIVE_BALANCE`**. `available_qty` 는 생성 컬럼인데 Prisma 타입이 `Decimal?` 이다 — `null` 이면 **던진다**(I-4 R-1 ③ 과 같은 처리 · 조용히 0 으로 대신하지 않는다).
- 잔액 행이 **0행**이면(그 차원이 통째로 사라졌다) 역시 400 `NEGATIVE_BALANCE` — 없는 자리에서 뺄 수 없다.
- ⛔ `mdm.item.negative_stock_allowed` 를 보지 않는다(I-4 §3-3 과 같다 — 트리거의 셋째 갈래는 `available_qty ≥ Σ` 가 전부 앞당겨 막는다).
- ⭐ **`ALREADY_CANCELLED` 가 아니라 `NEGATIVE_BALANCE` 인 자리**: 입고를 취소하려는데 그 재고가 이미 나갔다면 §4 의 후속 판정(LOT 축)이 먼저 `SUCCESSOR_EXISTS` 로 막는다. `NEGATIVE_BALANCE` 는 **후속 판정이 못 본 경로**(다른 문서가 같은 (위치·LOT) 잔액을 소비 — 예: 실사 조정)에서만 뜬다. 둘 다 필요하다.

### 3-9. 코어 PR ≤200줄에 들어가는가 — 들어간다(~140줄)

`reverse()` 본문 ~95 · 선잠금·합산 헬퍼 ~30(`issue-posting.ts` 의 `lockBalances` 와 «모양»만 같고 코드는 코어 안에 새로 둔다 — 도메인 파일을 import 하지 않는다) · `posting.types.ts` +~22 · `error-codes.ts` +~15(코드 3 + 주석). 합 **~162** ≤ 200. ✅

## 4. 후속 판정 — **함수 하나**

계약 요구: `cancelBlockedReasonCode` 5값이 ⌜`cancellable` 판정과 **같은 함수**여야 한다 — 화면이 미리 본 것과 실행 결과가 갈리면 그 화면이 틀린 안내를 한다⌝(`plan-api.md` §5.1-B).

### 4-1. 하나의 함수 · 세 호출자

```ts
// src/logistics/document-progress/cancel-eligibility.service.ts
export interface CancelEligibility {
  successorCount: number;
  successors: DocumentSuccessorRow[];   // 상세 GET 만 쓴다
  cancellable: boolean;
  cancelBlockedReasonCode?: CancelBlockedReason;
```

| 호출자 | 무엇을 읽나 | 어긋나면 |
|---|---|---|
| `GET /document-progress` (목록) | `cancellable`·`cancelBlockedReasonCode`·`successorCount`·`cancelApprovalRequestId` — 행마다 | 목록의 「후속」 열이 틀린다(`W-01-13` §3 ⌜「후속」 열을 목록에 둔다⌝) |
| `GET /document-progress/{type}/{id}` (상세) | 위 + `successors[]`(`withSuccessorRows:true`) | 상세의 후속 목록이 목록의 숫자와 갈린다 |
| `:request-cancel` · `:cancel` | 같은 함수 · `tx` 안에서 | 화면이 미리 본 것과 실행 결과가 갈린다(J-8 재판정) |

⭐ **`:cancel` 은 승인 뒤 «다시» 부른다** — 계약이 못박은 J-8 재판정이 이 한 줄이다. 요청 시점과 실행 시점의 판정이 **같은 코드**라 갈릴 수 없다.

### 4-2. 두 갈래 — 문서 하류 / 재고 사용

계약 `DocumentSuccessor` 는 ⌜앞 넷은 sourceDocument* 로 거꾸로 조회하는 «문서 하류»이고, 자재 투입은 … LOT 을 가리키는 «재고 사용»이다⌝ 라 적었다. ⛔ **그 문장을 글자 그대로 읽으면 `INVENTORY_TRANSACTION` 갈래가 «언제나 0» 이 된다.**

- 실측: `inventory_transaction.source_document_type_code` 는 계약 enum **4값**(`GOODS_RECEIPT`·`GOODS_ISSUE`·`INVENTORY_ADJUSTMENT`·`STOCK_TRANSFER`)이다. 어떤 문서의 원장을 `source_document_*` 로 역조회하면 **그 문서 «자신»의 전기 원장**이 잡힌다. 자기 자신을 빼면 남는 것이 0 이다.
- 그런데 계약이 그 문장의 **근거로 든 화면**은 다르게 적었다 — `W-01-13` §5-3 표: ⌜**재고 사용** | 그 입고가 만든 **LOT·수량이 이동·출고·투입에 쓰였는가 → 원장**⌝. 그리고 FR-IM-077 이 ⌜입고재고가 **이동**·출고·투입되지 않은 경우 입고를 취소할 수 있어야 한다⌝ 다 — 이동(`STOCK_TRANSFER`)이 만든 원장 행은 `source_document_type_code='STOCK_TRANSFER'` 라 **문서 하류 축으로는 영원히 안 보인다.**
- ⇒ **§2 0단계로 끝난다** — 계약이 스스로 인용한 화면 문장이 답이다. **`INVENTORY_TRANSACTION` 은 LOT 축이다.**

| 갈래 | 후속 유형 | 어느 표의 어느 칸 | 실측 |
|---|---|---|---|
| **ⓐ 문서 하류** | `GOODS_RECEIPT` | `goods_receipt.source_document_type_code`/`source_document_id` (**nullable**) | ⭕ |
| | `GOODS_ISSUE` | `goods_issue.source_document_type_code`/`source_document_id` (**NOT NULL**) | ⭕ |
| | `PICKING_ORDER` | `picking_order.source_document_type_code`/`source_document_id` (**NOT NULL**) | ⭕ |
| **ⓑ 재고 사용(LOT 축)** | `INVENTORY_TRANSACTION` | 이 문서가 «만든» LOT 을 실은 `inventory_transaction_line.lot_id` — 단 그 헤더의 `source_document_*` 가 이 문서가 «아닌» 것 | ⭕ |
| | `MATERIAL_CONSUMPTION` | `material_consumption.lot_id` (**BigInt NOT NULL** · FK `trace.lot`) — `source_document_*` 칸이 없다(실측) | ⭕ |

- **「이 문서가 만든 LOT」의 출처**: `INBOUND_RECEIPT` → `inbound_receipt_line.lot_id`(nullable · I-3 A3 가 세웠다 — `plan-api.md` 71행이 「후속 판정에 필요하다」고 예고한 그 칸) · `GOODS_RECEIPT` → `goods_receipt_line.lot_id`(NOT NULL).
- ⛔ **`GOODS_ISSUE` 에는 LOT 축을 적용하지 않는다.** 출고 라인의 LOT 은 출고가 «만든» 것이 아니라 이미 있던 것이라, LOT 축으로 세면 모든 출고가 영구히 취소 불가가 된다. 계약도 화면도 ⌜그 **입고**가 만든 LOT⌝ 라 적었다. §2 0단계.
  ⇒ 출고의 후속은 ⓐ 뿐이고, 실측상 `goods_issue` 를 `source_document_*` 로 가리키는 표가 없어 **대개 0** 이다. 그것이 FR-IM-078 ⌜아직 인수하지 않았거나 사용하지 않은 출고 건⌝ 과 어긋나지 않는다 — 출고의 「사용」은 하류 문서가 아니라 목적지 소비이고 계약이 그 축을 안 줬다. 「알려둘 것」.

### 4-3. 세지 않는 것 — 세 규칙

| # | 규칙 | 근거 |
|:-:|---|---|
| **①** | **자기 자신의 전기 원장을 빼다** — `inventory_transaction` 의 `(source_document_type_code, source_document_id)` 가 이 문서면 후속이 아니다 | 그 행은 이 문서 «자신»이다. 안 빼면 전기된 문서가 전건 취소 불가 |
| **②** | **취소된 후속은 세지 않는다** — 후속 문서의 `status_code = 'CANCELLED'` 면 제외 | 계약 ⌜취소하려면 이것들을 **역순으로 먼저 취소**해야 한다⌝ · `W-01-13` §6 ⌜먼저 이 2건을 역순으로 취소하세요⌝. 안 빼면 역순 취소가 **영원히 안 풀린다** — 본길이고 계약이 답했다(0단계) |
| **③** | **역처리로 상쇄된 원장 쌍은 세지 않는다** — 어떤 원장 행을 `reversal_of_transaction_id` 로 가리키는 행이 있으면 그 원 행도, 역 행도 후속이 아니다 | ②의 원장판. 출고를 취소하면 그 출고의 원장 두 줄이 상쇄돼 입고 취소가 열려야 한다 — M1 완료 조건이 요구하는 바로 그 경로 |

⚠ ③은 §3-3(역행이 `source_document_*` 를 복사한다) 때문에 **반드시 필요하다** — 없으면 취소가 자기 후속을 하나 만들어 다음 취소를 막는다.

### 4-4. 5값의 우선순위 — 계약이 안 줬다

- **1단계**: 두 조건이 동시에 참인 입력에서만 갈린다 ⇒ **가장자리**.
- **2단계**: 기준 5「개발 난이도가 낮은 쪽 — 새 개념 수」. 새 개념 0 이므로 **싼 판정부터**로 가른다. 그리고 화면 관점(G-3 ⌜비활성 사유는 「어떻게 풀 것인가」⌝)에서도 「풀 수 없는 것 → 이미 끝난 것 → 기다리면 되는 것 → 손으로 풀 것」 순이 맞다.
- **판정 순서**(먼저 걸리는 것이 이긴다):

| 순 | 코드 | 조건 | 읽는 것 |
|:-:|---|---|---|
| 1 | `TYPE_NOT_CANCELABLE` | `documentTypeCode` ∉ 3값 | **행을 안 읽는다** — 가장 싸다 |
| 2 | `ALREADY_CANCELLED` | `status_code = 'CANCELLED'` | 대상 행 1건 |
| 3 | `CANCEL_IN_PROGRESS` | `status_code = 'CANCEL_REQUESTED'` **또는** 열린(`PENDING`) `approval_request` 가 있다 | 대상 행 + `ix_approval_request_target` |
| 4 | `STATE_LOCKED` | `status_code` ∉ {`REGISTERED`,`POSTED`} | 대상 행(이미 읽음) |
| 5 | `SUCCESSOR_EXISTS` | ⓐ+ⓑ 합이 0 이 아니다 | **가장 비싼 조회 — 맨 뒤** |

- `cancellable = true` ⟺ 다섯 중 어느 것도 안 걸린다. 그때 `cancelBlockedReasonCode` 는 **키 생략**(`omitEmpty`).
- ⭐ **3 이 두 조건의 OR 인 이유**: 상태는 `CANCEL_REQUESTED` 인데 결재가 반려돼 열린 요청이 없는 경우가 실재한다(§6-5·문의 033). 그때도 `CANCEL_IN_PROGRESS` 로 막는 것이 옳다 — 되돌릴 경로가 없어 그 문서는 잠긴 상태이고, 화면은 결재함으로 안내한다.
- **3단계 흔적**: 우선순위를 `const BLOCK_ORDER` 배열 하나로 두고 주석 `// 계약이 5값의 우선순위를 안 줬다 — 싼 판정부터(§2 2단계 기준 5) · G-3 안내 순서와 같다(I-5.md §4-4)` + 단위 테스트 5줄.

### 4-5. 유형↔표를 어디서 읽나 — **등록부는 «검증»에, 매핑은 «코드»에**

`plan-integration.md` §9 #5 가 ⌜`app.entity_type_registry` 표가 이미 있다 — **거기서 읽는다**. 코드에 표를 박지 않는다⌝ 라 적었다. 실측이 그 문장을 **절반만** 지지한다.

- **실측 ①**: `entity_type_registry` 의 칸은 **넷뿐**(`schema_name`·`table_name`·`id_column_name`·`is_active`). `DocumentProgress` 를 채우려면 **문서번호 칸·일자 칸·상태 칸·버전 칸·라인 표·계획수량 칸·처리수량 칸** 일곱이 더 필요한데 **둘 자리가 없다**(§2-3).
- **실측 ②**: 9종 중 **4종이 등록부에 없다**(§1-4 ⓐ). 등록부만 믿으면 오늘 4종이 500 이다.
- **실측 ③**: 표 이름으로 동적 SQL 을 짜려면 `$queryRawUnsafe` 로 **식별자를 문자열 연결**해야 한다. 값은 `entity_type_registry` 에서 오지만 그 표를 쓰는 오퍼레이션이 이 저장소에 없어(관리 API 0건) **누가 그 값을 넣는지 통제가 없다** — 오늘은 시드뿐이지만 계약이 「고객이 늘린다」로 열릴 자리다.
- **§2 2단계**: 기준 5「새 개념 수」 — 동적 SQL 갈래는 «식별자 화이트리스트 + 9종 칸 이름 표 + 원시 SQL 조립기» 셋을 새로 만든다. 정적 매핑 갈래는 «표 하나»다. 기준 1「재고·원장·상태를 쓰지 않는 쪽」 무관. 기준 4「값을 조용히 도출하지 않는 쪽」 — 동적 SQL 은 등록부 값에서 SQL 을 도출한다.
- ⇒ **판정: 매핑은 코드의 정적 표 하나(`document-type-registry.ts`), 등록부는 «대조»에만 쓴다.**

```ts
// src/logistics/document-progress/document-type-registry.ts  (개념)
const DOCUMENT_TYPES = {
  PURCHASE_ORDER: { entityTypeCode: 'PURCHASE_ORDER', delegate: 'purchase_order',
    idColumn: 'purchase_order_id', noColumn: 'purchase_order_no', dateColumn: 'order_date',
    lineDelegate: 'purchase_order_line', plannedColumn: 'ordered_qty', processedColumn: 'received_qty',
    subTypeColumn: null, cancelable: false },
  …9종…
} as const;
```
- **부팅 시 1회 대조**(`OnModuleInit`): 9종 각각에 대해 `entity_type_registry` 에 `(schema_name, table_name)` 이 있는지 확인하고 **어긋나면 로그 경고**(던지지 않는다 — 등록부가 비어도 서비스가 뜬다). ⭐ 「유형이 늘 때 조용히 틀리는 것」(`plan-integration.md` §9 #5 의 걱정)을 이 대조가 잡는다.
- **시드 보강**: `prisma/seed.ts` `ENTITY_TYPES` 에 **7행을 더한다** — `MATERIAL_ISSUE_REQUEST`·`PICKING_ORDER`·`SUBCONTRACT_ISSUE`·`SUBCONTRACT_RECEIPT`(조회 9종) + `INVENTORY_TRANSACTION`·`MATERIAL_CONSUMPTION`(후속 5종 · `PICKING_ORDER` 는 위와 겹친다). ⚠ `uq_entity_type_table (schema_name, table_name)` 이 있으니 중복 없음을 확인한다. **마이그레이션이 아니다.**
- ⛔ **`$queryRawUnsafe` 로 식별자를 넣지 않는다.** 3단계 흔적: 파일 머리 주석 `// 유형↔표 매핑을 코드에 둔다 — entity_type_registry 는 칸이 넷뿐이라 DocumentProgress 를 못 채우고, 식별자를 SQL 로 흘리지 않는다. 등록부는 부팅 대조에만 쓴다(plan-integration §9 #5 · I-5.md §4-5)`.

### 5-2. 외주 2종 — FK 로 판다 (마이그 0)

`subcontract_issue`·`subcontract_receipt` 에는 문서번호·라인·수량 칸이 없다. **그런데 둘 다 NOT NULL FK 로 출고·입고에 매달려 있다**(`goods_issue_id` · `goods_receipt_id`, 각각 `uq_subcontract_issue`·`uq_subcontract_receipt`).

- **§2 1단계**: 이 두 유형의 모든 행이 영향받으니 본길처럼 보이나, **계약이 답을 갖고 있다** — `DocumentProgress` 의 required 칸을 채울 «다른 값이 없다»가 아니라, 그 문서의 실체가 곧 짝지어진 출고·입고다.
- **§2 2단계**: 기준 3「스키마를 안 늘리는 쪽」 ⇒ **FK 를 따라가 파생**. 기준 1(원장·상태 안 씀) ⭕.
- **판정**: `documentNo` = 짝 `goods_issue_no` / `goods_receipt_no` · `plannedQty`/`processedQty` = 짝의 라인 합계 · `documentDate` = 자기 `issued_at`/`received_at` · `statusCode`·`version_no` 는 자기 것.
- **3단계 흔적**: 매핑 표에 `derivedFrom: 'goods_issue'` 한 칸 + 주석 + 「알려둘 것」(외주 2문서에 번호·라인 칸이 없어 짝 전표에서 판다).
- ⚠ **오늘 두 표는 0행이다**(외주 오퍼레이션이 계약 커버리지 밖) ⇒ 목록이 언제나 빈다. e2e 는 픽스처를 직접 INSERT 해 형태만 못박는다.

### 5-3. 유니온이냐 유형별이냐 · 정렬 · 페이징

- ⭐ **`documentTypeCode` 가 required 라 유니온이 필요 없다.** 한 요청 = 한 유형 = 한 표다. ⇒ **유형별 Prisma 쿼리 하나**를 정적 매핑으로 고른다. `$queryRawUnsafe` 도 `UNION ALL` 도 없다.
- **페이징**: 그 한 표에서 `skip`/`take` — 표준 `pageRequest`/`pagedResponse` 재사용.
- **정렬**: 계약 침묵 ⇒ **§2 2단계 기준 5 + 0단계 선례**(P/O·입하·입고 전건이 「업무 일자 desc + PK desc」) ⇒ `{dateColumn} desc, {idColumn} desc`. 일자 칸이 없는 둘은 `created_at desc, id desc`.
- **필터**:
  - `statusCode` → `status_code` 등호.
  - `documentDateFrom`/`To` → `dateColumn` 범위(UTC 경계 · 위 「알려둘 것」).
  - `q` → `noColumn` `contains`(외주 2종은 짝 전표의 번호 — 조인 필터).
  - `itemId`·`lotId`·`warehouseId` → **라인 표 존재 필터**(`some`). ⚠ `lot_id` 가 라인에 없는 유형(`purchase_order_line`·`material_issue_request_line`)에서 `lotId` 를 주면 **결과 0** 이다(400 이 아니다 — 계약이 유형별로 필터를 안 갈랐다) → 「알려둘 것」. `warehouseId` 는 표마다 자리가 다르다(헤더 `warehouse_id` / `source_warehouse_id` / `from_warehouse_id` / 라인 위치 조인) — **매핑 표에 `warehouseFilter` 한 칸**으로 둔다.
  - `cancellableOnly=true` → ⛔ **DB 로 못 민다**(판정이 후속 조회를 포함한다). ⇒ **페이지를 뽑은 뒤 §4 함수로 걸러 낸다.** 그러면 페이지 크기가 요청보다 작아진다.
    §2 2단계 기준 5: 「후속을 SQL 서브쿼리로 밀어 넣는다」는 다섯 표를 상관 서브쿼리로 엮어야 하고 §4 의 「함수 하나」를 깬다 ⇒ **뒤에서 거른다**. `PageMeta.totalElements` 는 **거르기 «전»** 수를 낸다(계약이 접지 말라 했고 정확한 수를 알려면 전건 판정이 필요하다) → 「알려둘 것」 · 3단계 흔적으로 주석 한 줄.
- **N+1 방지**: 한 페이지(기본 50)의 문서 id 를 모아 §4 함수를 **묶음으로** 한 번 돌린다 — 다섯 후속 조회가 페이지당 5쿼리(행당 5쿼리가 아니다). 상세 GET 만 행 단위다.

### 5-4. `steps` — 상태 4값에 닿은 순간 (체인을 거슬러 오르지 않는다)

계약이 ⌜전표의 진행 상태와 «같은 값집합»이다⌝ 라 못박았다(§1-4 ⓗ). ⇒ 최대 네 줄이고, **알 수 있는 것만** 낸다.

| `stepCode` | `occurredAt` | `actorName` | `inventoryTransactionNo`·`businessDate` |
|---|---|---|---|
| `REGISTERED` | 대상 행 `created_at` | `created_by` → `app_user.user_name` | 생략 |
| `POSTED` | ⭐ **원장 행의 `occurred_at`** | ⛔ **생략** — `W-01-13` §3 목업 ⌜전기 08-06 09:14 (자동)⌝ · 계약 ⌜사람이 한 것이 아니면 비어 있다⌝ | 원장 `transaction_no`·`business_date` |
| `CANCEL_REQUESTED` | `approval_request.requested_at`(다형 축) | `requested_by` → 이름 | 생략 |
| `CANCELLED` | `document_cancellation.cancelled_at` | `cancelled_by` → 이름 | ⭐ **역행의** `transaction_no`·`business_date`(있으면) |

- ⛔ **`POSTED` 줄은 원장이 있을 때만 낸다.** 상태 이력 표가 없어(실측 0건) 「전기 시각」을 다른 데서 못 읽는다. `updated_at` 으로 근사하지 않는다 — §2 2단계 기준 4「값을 조용히 도출하지 않는 쪽」. ⇒ **입하는 `POSTED` 줄이 영원히 없다**(입하는 전기를 안 한다) → 「알려둘 것」.
- 정렬: `occurredAt` 오름차순(⌜시간순으로 보인다⌝).

### 5-5. `successors[]` — §4 함수가 준 행을 그대로

`successorNo` 는 유형별로 `goods_receipt_no`·`goods_issue_no`·`picking_order_no`·`transaction_no`·`consumption_no`. `qty` 는 ⌜이 문서에서 넘어간 수량⌝ — 후속 라인 중 **이 문서의 LOT/원천을 가리키는 라인의 합**. `screenId` 는 §5-1 과 같은 이유로 **키 생략**.

### 5-6. 모델 배분 — 조회 2건은 sonnet 가능한가

⭕ **가능하다 — 단 §4(판정 함수)가 «먼저» 서 있을 때만.** 판정이 이 슬라이스의 판단 밀도 전부이고, 그것이 별도 PR(②·opus)로 서면 조회 PR(③)은 「매핑 표를 보고 Prisma 쿼리를 짜고 매퍼를 쓰는」 복제 작업이 된다(README §4 「조회 GET·뷰·컨트롤러·기존 패턴 복제 = sonnet」). ⇒ **PR ③ = sonnet**.

## 6. 취소 요청·실행 — 상태기계와 어댑터

### 6-1. `transitions.ts` — 키 하나에 «더하고» 키 둘을 «연다»

실측(`src/core/document-state/transitions.ts` 160줄 · 등록된 키 **여섯**): `mdm.equipment` · `mdm.mold` · `planning.routing` · `trace.lot.lifecycle_status_code` · `app.approval_request` · **`logistics.goods_issue.status_code`**(`document-post` 한 줄뿐). ⭐ 그 파일 `:158` 에 **이미 주석이 있다** — 「I-5 가 이 키 안에 `document-request-cancel`·`document-cancel` 을 더한다 — 키를 다시 만들지 않는다」(I-4 R-2 가 남긴 자리).

```ts
'logistics.goods_issue.status_code': {
  'document-post':           { from: ['REGISTERED'], to: 'POSTED', … },       // I-4 — 그대로
  'document-request-cancel': { from: ['REGISTERED','POSTED'], to: 'CANCEL_REQUESTED',
      sourceOperation: 'POST /logistics/document-progress/{documentTypeCode}/{documentId}:request-cancel' },
  'document-cancel':         { from: ['CANCEL_REQUESTED'], to: 'CANCELLED',
      sourceOperation: 'POST /logistics/document-progress/{documentTypeCode}/{documentId}:cancel' },
},
'logistics.inbound_receipt.status_code': { /* 위 두 액션만 */ },   // ⭐ 새 키
'logistics.goods_receipt.status_code':   { /* 위 두 액션만 */ },   // ⭐ 새 키
```

- `from`/`to` 는 `plan-api.md` §5.1-A 표 그대로다.
- **`conflictStatus` 는 400** — I-4 §3-7 과 같은 판정(409 는 If-Match 저장 충돌 전용). 다만 던지는 코드는 §4-4 의 우선순위가 «먼저» 갈라 `ALREADY_CANCELLED`·`CANCEL_IN_PROGRESS`·`STATE_LOCKED` 중 하나가 나간다 — `assertTransition` 의 `STATE_LOCKED` 는 **경합으로 그 사이 상태가 바뀐 경우의 마지막 그물**이다.
- ⛔ **`transitionCode` 를 안 쓴다** — `trace.lot` 축만 갖는 칸이고 물류 축에는 값 목록이 없다(`work-order-cancel` 선례는 `L3` 를 갖지만 그것은 LOT 생명주기다).
- ⚠ **입하는 `POSTED` 에 도달하는 길이 여전히 없다**(I-3 §5-3 · 문의 026) ⇒ `from: ['REGISTERED','POSTED']` 중 `POSTED` 는 입하에서 **도달 불가**. 계약 문장대로 두고 좁히지 않는다.
- ⭐ **I-3 R-12 ⓑ 재판정 — §7-4 임시 자물쇠는 «걷지 않는다».** 그 자물쇠(입고가 붙은 입하 라인의 치환·삭제를 400 `SUCCESSOR_EXISTS` 로 막는다)를 걷는 조건은 「전기 완료 축이 서면」이었는데, **이 슬라이스가 여는 것은 취소 두 값이고 `POSTED` 축은 그대로 없다.** 자물쇠를 걷으면 026 이 지적한 구멍이 다시 열린다. ⇒ 유지 · I-5 는 그 파일을 안 건드린다.

### 6-2. `:request-cancel` 의 순서

```
① @Contract + PermissionGuard(403) + OptimisticLockGuard(If-Match 필수)
② runIdempotent(202) 로 감싼다
③ $transaction {
     ③-1 대상 행 조회 + version_no 대조 (없으면 404 · 어긋나면 409)
     ③-2 §4 함수 evaluate() → cancellable 이 아니면 400 (사유 코드 그대로)
     ③-3 approval.request(tx, {
            targetTypeCode: documentTypeCode,          // INBOUND_RECEIPT | GOODS_RECEIPT | GOODS_ISSUE
            approvalTypeCode: `${documentTypeCode}_CANCEL`,
            targetId, reason, requestedBy, approvalRequestNo })   // 번호는 ② 안에서 next() 로 받는다
     ③-4 상태 전이 document-request-cancel → CANCEL_REQUESTED · version_no +1
   }
④ 202 { approvalRequestId }
```

- **승인 유형 3값은 계약이 이름을 줬다** — `contracts/app-공통.json` 의 `approvalTypeCode` **enum 9값**에 `INBOUND_RECEIPT_CANCEL`·`GOODS_RECEIPT_CANCEL`·`GOODS_ISSUE_CANCEL` 이 있다(실측). `targetTypeCode` 는 **enum 8값**에 `INBOUND_RECEIPT`·`GOODS_RECEIPT`·`GOODS_ISSUE` 가 있다. ⇒ **`${documentTypeCode}_CANCEL` 이 세 값에 정확히 대응한다** — 지어내는 것이 없다. `W-01-13` §8 #4 도 ⌜유형(`approval_type_code`)은 `omf-mes#336` 이 8값으로 정했다(2026-09-01 · `INBOUND_RECEIPT_CANCEL`·`GOODS_RECEIPT_CANCEL`·`GOODS_ISSUE_CANCEL` 포함)⌝ 라 적었다.
- **`assertNoOpenRequest` 는 `request()` 안에서 이미 돈다**(실측 `approval.service.ts:102`) — `APPROVAL_IN_PROGRESS` 400. §4-4 의 `CANCEL_IN_PROGRESS` 가 **먼저** 걸러 대개 그 앞에서 끝난다(J-7). 둘 다 남긴다 — 경합 그물.

### 6-3. `:cancel` 의 순서 — ⭐ 이 슬라이스의 중심

```
① @Contract + PermissionGuard(403) + OptimisticLockGuard(If-Match 필수)
② runIdempotent(200)
③ $transaction {
     ③-1 대상 행 조회 (FOR UPDATE) + version_no 대조     → 404 / 409
     ③-2 approval.assertApproved(tx, documentTypeCode, documentId, `${documentTypeCode}_CANCEL`)
                                                          → 400 APPROVAL_IN_PROGRESS / APPROVAL_REQUIRED
     ③-3 ⭐ §4 함수 evaluate() 재판정                     → 400 SUCCESSOR_EXISTS (J-8)
     ③-4 document_cancellation INSERT
            previous_status_code = 지금 status_code
            reason_code = 'OTHER' · reason_detail = 승인 요청의 reason
     ③-5 previous === 'POSTED' 면 유형별 어댑터가 원장 역처리 + 부수효과(§6-4)
     ③-6 상태 전이 document-cancel → CANCELLED · version_no +1
   }
④ 200 CancelResult { …, reversed, [reversalTransactionNo], [reversalBusinessDate] }
```

- ⭐ **③-2 가 ③-3 «앞»이다** — 계약이 ⌜승인이 끝난 요청만 받는다⌝ 를 먼저 적었고, 승인 없이 부른 호출에 후속 사유를 알려 주는 것은 정보 누출이자 화면 안내를 어지럽힌다.
- ⭐ **③-3 이 ③-4 «앞»이다** — 재판정에 걸리면 **아무 흔적도 남기지 않는다**. 계약 ⌜승인은 그대로 유효하다 — 새 요청을 다시 올리지 않는다⌝ ⇒ `approval_request` 도 문서 상태(`CANCEL_REQUESTED`)도 **그대로**다. 트랜잭션이 통째로 롤백된다.
- ⭐ **③-5 가 ③-6 «앞»이다** — 역처리가 `NEGATIVE_BALANCE` 로 400 이면 상태도 안 옮긴다.
- `previous_status_code` 는 ③-1 에서 읽은 값(`REGISTERED` 또는 `POSTED`) — ⭐ `CancelResult.reversed` 를 가르는 것과 **같은 값**이라 두 곳이 갈릴 수 없다.
- ⌜전기 전이었으면 상태만 바뀌고 원장에는 아무것도 생기지 않는다⌝ ⇒ `reversed:false` + 두 nullable 칸 **키 생략**.

### 6-4. 유형별 어댑터 3 — 「원장 되돌림 = 코어, 나머지 = 어댑터」

| 유형 | 대상 표 / `version_no` | 원장 역처리 | 도메인 부수효과 |
|---|---|:-:|---|
| `INBOUND_RECEIPT` | `inbound_receipt` | ⛔ **없다** — 입하는 전기를 안 한다(`plan-api.md` S02 「posting 연결 없음」) ⇒ `reversed` 는 **언제나 false** | ⭐ **`purchase_order_line.received_qty` 되돌림** — I-3 R-12 ⓐ 불변식 그대로: 라인→부모 매핑을 트랜잭션 안에서 읽고 **부모 `purchase_order_id` 오름차순 `FOR UPDATE`** 한 문장(`IN (${Prisma.join(ids)}) ORDER BY … FOR UPDATE`) → `received_qty` `decrement` → **하한 0 손검사**(음수면 400 `RANGE`). 「`purchase_order_line` 을 쓰는 모든 경로는 부모 `purchase_order` 를 먼저 잠근다」 불변식 유지 |
| `GOODS_RECEIPT` | `goods_receipt` | ⭕ `previous='POSTED'` 면 | ⛔ **`putaway_task` 를 손대지 않는다**(아래) |
| `GOODS_ISSUE` | `goods_issue` | ⭕ 같음 | ⛔ 취소 3칸을 안 채운다(§2-4) · `approval_request_id`(I-4 의 폐기 품의)를 **안 덮는다**(§2-5) |

- **원 트랜잭션을 어떻게 찾나**: `inventory_transaction` 을 `(source_document_type_code, source_document_id) = (유형, id)` 로 조회 — `ix_inventory_transaction_source (source_document_type_code, source_document_id, business_date DESC)` 가 받는다. **§4-3 ③ 을 적용해 이미 역처리된 행은 제외**하고, 남은 것이 0행이면 `reversed:false`(전기 전) · 1행이면 그것을 `reverse()` · **2행 이상이면 던진다**(오늘 한 문서는 원장 하나다 — 조용히 첫 행을 고르지 않는다).
- **`putaway_task` 판정**: 입고 등록이 적치 지시를 만든다(I-4 §6-5 실측). 계약 `DocumentSuccessor` **5값에 `PUTAWAY_TASK` 가 없어** 후속으로 셀 수도, 응답에 실을 수도 없다. §2 2단계 기준 1「재고·원장·상태를 쓰지 않는 쪽」 ⇒ **손대지 않는다.** ⚠ 취소된 입고의 적치 지시가 남는다 → 「알려둘 것」(I-12 가 볼 자리).
- **LOT 처리(I-3 R-12 ⓒ)**: 입하 취소가 `inbound_receipt_line.lot_id` 가 가리키는 LOT 을 어떻게 두나.
  - LOT 이 «이미 쓰였으면» §4 의 LOT 축이 `SUCCESSOR_EXISTS` 로 **먼저 막는다** ⇒ 취소가 통과하는 것은 안 쓰인 LOT 뿐이다.
  - 그때 갈래 셋: ⓐ LOT 을 그대로 둔다 ⓑ `lot.status_code`/`lifecycle_status_code` 를 옮긴다 ⓒ `inbound_receipt_line.lot_id` 를 NULL 로 끊는다.
  - §2 2단계 기준 1「재고·원장·**상태**를 쓰지 않는 쪽」 ⇒ ⓑ 탈락. 기준 4「값을 조용히 도출하지 않는 쪽」 + B-3(이력 불변) ⇒ ⓒ 탈락(어느 LOT 이 이 입하에서 났는지가 지워진다). ⭐ **판정 ⓐ — 손대지 않는다.**
  - ⚠ `trace.lot` 의 폐기·무효 전이는 **`transitions.ts` 의 `trace.lot.lifecycle_status_code` 축**에 `work-order-cancel`(→`VOIDED`)만 있고 입하 취소용 액션이 없다 — 지어내면 F-6 에 걸린다. 이것이 ⓑ 를 못 고르는 두 번째 이유다.
  - **3단계 흔적**: 어댑터 주석 + 「알려둘 것」 + 문의 026 갈래에 한 줄 덧붙임(새 문의 아님 · I-3 R-12 ⓒ 를 여기서 닫는다).
- **I-3 R-12 ⓕ**(LOT 이 붙은 부착 라인 치환 ↔ `lot.initial_qty` 어긋남)는 **여기서 안 닫힌다** — 026 회신 대기 그대로 인계한다.

### 6-5. 승인 반려 뒤 — **되돌릴 경로가 없다** (문의 033)

- **실측**: `contracts/app-공통.json` 의 승인 경로 9개는 `GET/POST /app/approval-requests`·`{id}`·`:approve`·`:reject`·결재선 5. **철회·취소가 0건**이다. `W-01-13` §5-7 은 액션표에 ⌜취소 요청 철회 | 결재 진행 중 — ⚠ 상신자만 · 승인된 뒤에는 불가(J-6)⌝ 를 두었는데 **그 액션에 대응하는 오퍼레이션이 계약에 없다.**
- ⇒ `:reject` 뒤 문서는 `CANCEL_REQUESTED` 에 **영구히 갇힌다**. 그 상태에서는 `:post` 도(전이 `from:['REGISTERED']`), 재상신도(§4-4 3 이 `CANCEL_IN_PROGRESS` 로 막는다) 안 된다.
- **§2 1단계**: 반려된 모든 취소가 그렇게 되니 **본길**. **계약이 침묵** ⇒ 규칙대로라면 「건너뛴다」인데, 건너뛸 오퍼레이션이 «없다»(우리가 여는 두 오퍼레이션은 정상 경로다).
- **판정**: **계약 문자 그대로 구현한다** — `document-cancel` 은 `CANCEL_REQUESTED` 에서만 열리고, 되돌리는 전이를 **만들지 않는다**(전이표에 없는 액션은 던진다 — F-6 의 「귀찮음이 방어다»). ⇒ 반려된 문서가 잠기는 것은 **계약이 그렇게 생겼기 때문**이고, 우리가 지어낸 자물쇠가 아니다.
- **3단계 흔적**: `transitions.ts` 주석 `// 반려 뒤 CANCEL_REQUESTED 를 되돌리는 오퍼레이션이 계약에 없다 — 되돌리는 전이를 만들지 않는다(I-5.md §6-5 · 문의 033)` + 단위 테스트 `취소 — 반려된 요청의 문서는 CANCEL_REQUESTED 에 머문다(되돌리는 전이가 없다)` + **문의 033**.

## 7. 횡단

### 7-1. 403 게이트 — **추가 0건**

`derived-permissions.ts` 실측 — **네 오퍼레이션이 이미 전건 있다**:
```
:48  'GET  /logistics/document-progress':                                              ['W-01-13']
:49  'GET  /logistics/document-progress/{documentTypeCode}/{documentId}':              ['W-01-13']
:167 'POST /logistics/document-progress/{documentTypeCode}/{documentId}:cancel':        ['W-01-13']
:168 'POST /logistics/document-progress/{documentTypeCode}/{documentId}:request-cancel':['W-01-13']
```
⇒ **`manual-permissions.ts` 에 더할 것이 없다**(도출표와 겹치면 검사가 막는다). 계약이 403 을 선언한 것은 쓰기 2건뿐이고 GET 둘은 가드가 보지 않는다 — 도출표에 있어도 무해하다(I-4 §6-1 과 같은 처리).

### 7-2. If-Match 2 — ⛔ **토큰은 대상 문서의 `version_no`**

- 계약이 두 번(두 오퍼레이션 description) + `plan-uiux.md` U18(1151행)이 한 번 못박았다: ⌜이 응답이 아니라 **대상 문서 리소스의 상세 GET**(`/inbound-receipts/{id}` · `/goods-receipts/{id}` · `/goods-issues/{id}`)⌝.
- ⇒ 가드(`OptimisticLockGuard`)는 헤더를 «필수»로 파싱만 하고, **비교는 어댑터가 한다** — 어댑터가 「이 유형의 `version_no` 는 어느 표의 어느 칸인가」를 안다(§4-5 매핑 표의 `versionColumn`). 실제 비교는 `ifMatchVersion(request)` 값과 `updateMany({ where: { id, version_no } })` + `assertUpdated(count)` — I-4 §6-3·P/O `:request-approval` 선례와 같은 모양(`runVersioned` 는 못 쓴다 — ETag 미선언).
- **어긋나면 409 `ConflictResponse`**(계약 선언 · ⌜저장 충돌. 다시 읽어 오면 풀린다⌝).
- ⚠ **세 대상 표 모두 `version_no` 가 실재한다** — 마이그 불필요(§0 ⚠).

### 7-3. 멱등 2 — `runIdempotent`

| 오퍼레이션 | 헬퍼 | `successStatus` |
|---|---|---|
| `:request-cancel` | `runIdempotent` | `ACCEPTED`(202) · `@HttpCode(HttpStatus.ACCEPTED)` |
| `:cancel` | `runIdempotent` | `OK`(200) |

⚠ 조회 2건에는 안 붙인다(`plan.md` §5 규칙 2). ⛔ `runVersioned` 는 둘 다 못 쓴다(ETag 미선언).
⚠ **원장의 멱등키는 별개다** — `runIdempotent` 의 키는 클라이언트가 준 `Idempotency-Key` 이고, `reverse()` 안의 `REVERSAL:{원 id}` 는 원장 표의 것이다. 둘이 겹치지 않는다(§3-6 ①·②).

### 7-4. `@Contract` · 404 · 409 · `X-Worker-No` · `CANCEL_IN_PROGRESS` 의 상태

- `@Contract('METHOD /path')` **4건 전건**. `:cancel`·`:request-cancel` 은 `@Post(':documentId\\:cancel')` 형태(경로에 콜론 — I-2·I-3·I-4 선례).
- **404**: 계약이 **셋에 선언했다**(상세 GET · `:request-cancel` · `:cancel`). ⭐ **이 슬라이스는 404 미선언 자리가 없다** — I-2·I-3·I-4 가 매번 「알려둘 것」에 올리던 항목이 여기서는 안 생긴다.
  ⚠ 다만 **목록 GET 은 404 를 안 낸다** — 유형 enum 밖이면 400(계약 ⌜덮지 않는 문서 유형이면 여기로 온다⌝).
- **409 봉투**: 기본 `ConflictResponse`. 도메인 전용 넷(`Production`·`Quality`·`Shipment`·`StockReinstatement`)에 이 자리가 없다.
- **`X-Worker-No`**: 네 오퍼레이션 **전건 0**(실측). 주체는 계정 세션(`document_cancellation.cancelled_by`·`approval_request.requested_by`).
- ⭐ **`CANCEL_IN_PROGRESS` 를 400 으로 낸다** — `plan-api.md` §5.4 는 이 코드를 **409 · S22**(출하 `:confirm` 자리)로 적었다. 이 자리에서 400 인 근거 둘: ① 계약이 `:request-cancel` 400 설명에 ⌜취소 요청이 이미 진행 중이다⌝ 를 **다른 400 셋과 나란히** 적었다 ② `cancelBlockedReasonCode` enum 의 형제 넷이 전부 400 이고 「조회 사유 = 실행 오류」가 같은 문자열이어야 한다(`plan.md` §5 규칙 6). ⇒ **409 는 If-Match 저장 충돌 전용**(I-4 §3-7 과 같은 판정) → `plan-api.md` §5.4 행에 「S22 는 409 · S06 은 400」 주석을 다는 것을 §10 에 올린다.
- **`@db.Date` 캐스팅 금지**: 목록 `documentDateFrom`/`To` 는 대부분 `timestamptz` 를 자른다 ⇒ **UTC 경계**(입고·출고 선례) → 「알려둘 것」.

### 10-1. e2e 스위트 · 픽스처 · 정리 순서

**파일**: `test/logistics-document-progress.e2e-spec.ts` — 상수 `PREFIX='DPE2E'` / `LOGIN_ID='e2e-dp-probe'` / `ROLE='E2E_DP'`. 기존 전건과 겹침 **0**(실측: `GRE2E`·`GIE2E`·`IRE2E`·`POWE2E`·`ASNE2E`·`INVBAL`·`INVTX`·`LOTE2E`·`MDM*`·`POLICY`·`NOTICE-E2E`·`POST-E2E`·`E2E_*` 전건 대조).

**시퀀서**: `alphabetical-sequencer.js` 가 파일 이름 순이라 `logistics-document-progress` 는 **`logistics-goods-issue`·`goods-receipt` «앞»**이다. ⇒ 뒤 스위트의 픽스처를 못 쓴다(I-3·I-4 와 같은 결론) — **자기 픽스처를 새로 세운다**.

**잔액·원장을 세우는 법**(I-4 §6-5 처방 그대로)
- 입고 API(`POST /logistics/goods-receipts`)를 **부른다** — 원장·잔액·적치를 한 번에 세운다. 직접 INSERT 는 `inventory_balance` 트리거 때문에 차원 11칸을 손으로 맞춰야 한다.
- 출고는 `POST /logistics/goods-issues`(`postImmediately:true` · `sourceDocumentTypeCode='GOODS_RECEIPT'`)로 세운다 — J-8 e2e 의 「그 사이 생긴 후속」과 `NEGATIVE_BALANCE` e2e 의 「미리 빼 두는 잔액」이 같은 호출이다.
- 입하는 `POST /logistics/inbound-receipts` + P/O 픽스처(`received_qty` 되돌림 e2e 용).
- 결재선 3유형은 **`test/approval-request.fixture.ts` 의 `seedRoute(prisma, 'GOODS_RECEIPT_CANCEL', [approverId])`** 등으로 직접 심는다 — `prisma/seed.ts` 에 `approval_route` 시드가 **0건**이다(실측).
- 승인은 `POST /app/approval-requests/{id}:approve` 를 **부른다**(`test/app-approval-decision.e2e-spec.ts` 선례).
- 외주 2종은 `subcontract_order` → `subcontract_issue`/`subcontract_receipt` **직접 INSERT**(등록 오퍼레이션이 계약에 없다).

**cleanup 순서**(FK 방향 실측 · ⭐ **역행 자기참조를 먼저 끊는다**)
```
①  TRUNCATE inventory.inventory_transaction_line, inventory.inventory_transaction CASCADE
      ← 원장은 트리거가 UPDATE·DELETE 를 막는다(block_ledger_*_mutation) — TRUNCATE 뿐이다.
        ⭐ 복합 FK 자기참조(fk_inventory_transaction_reversal)도 TRUNCATE 가 한 번에 지운다
           — 역행을 먼저 DELETE 하는 순서를 «안 짜도 된다».
        CASCADE 가 goods_receipt_line·goods_issue_line·putaway_task 의 되짚기 칸을 함께 비운다.
②  DELETE app.document_cancellation        WHERE document_id IN (…) AND document_type_code IN (…)
③  DELETE inventory.inventory_balance      WHERE item_id IN (PREFIX 품목)
④  DELETE logistics.putaway_task           WHERE item_id IN (PREFIX 품목)
⑤  DELETE logistics.subcontract_receipt → subcontract_issue → subcontract_order
⑥  DELETE logistics.goods_issue_line → (UPDATE goods_issue SET approval_request_id = NULL) → goods_issue
⑦  DELETE logistics.goods_receipt_line → goods_receipt
⑧  DELETE logistics.inbound_variance → inbound_receipt_line → inbound_receipt   ← lot 보다 «먼저»(A3 FK)
⑨  DELETE trace.lot_hold → lot_external_identifier → trace.lot
⑩  DELETE logistics.purchase_order_line → purchase_order
⑪  DELETE app.approval_step → app.approval_request                 ← 요청·실행이 만든다
⑫  DELETE app.approval_route_step → app.approval_route             ← seedRoute 가 만든다
⑬  DELETE mdm.location → warehouse → item → partner → plant → business_unit → legal_entity
⑭  app_user·user_role·user_credential·idempotency_record · role_permission·role
```
- ⭐ **①이 이 스위트의 핵심이다** — 브리프가 걱정한 「복합 FK 자기참조 — 역행 먼저 지운다」는 **`TRUNCATE … CASCADE` 가 흡수한다**(원장은 애초에 DELETE 가 트리거로 막혀 있어 다른 길이 없다).
- ⭐ **⑧이 ⑨보다 «먼저»다** — `inbound_receipt_line.lot_id → trace.lot` FK(A3) 때문(I-3 §6-5 와 같은 순서).
- ⭐ **⑥의 `approval_request_id = NULL`** — `goods_issue.approval_request_id → app.approval_request` FK 를 먼저 끊는다(I-4 §6-5 ⑥ 와 같은 처방). ⚠ `inbound_receipt.approval_request_id` 도 같은 FK 를 갖는다 — ⑧ 앞에 한 줄 더 필요하다.
- ⛔ `app.numbering_counter` 는 지우지 않는다(I-2 R-10 ⓔ) — 번호 정규식은 `\d{4,}` 로 넓힌다.
- ⚠ `test/app-approval-decision.e2e-spec.ts:328` 의 `prisma.goods_issue.count()` 는 **한 테스트 안의 before/after 차분**이고 `--runInBand` 라 깨지지 않는다(I-4 §6-5 실측 그대로).
