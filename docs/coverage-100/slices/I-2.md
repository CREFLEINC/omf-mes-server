## ⭐ 0-재수립. 3관점 재검토 결정 (2026-09-06) — **아래 본문과 다르면 이 절이 정본이다**

재검토 원문: `I-2-review-api.md` · `I-2-review-uiux.md` · `I-2-review-integration.md`. 셋이 갈린 자리는 통합자(나)가 README §2 절차로 갈랐다. 본문에도 반영한 자리는 「재수립 R-n 반영」으로 표시했다.

### R-1. 계약 실측 정정 — **대상이 있는 쓰기 3건 전부 404 를 선언하지 않는다** (api 1 · 셋 중 유일한 사실 오류)
`jq` 재실측: `PUT …/{id}` = `200,400,403,409` · `PUT …/lines` = `200,400,403,409` · `…:request-approval` = `202,400,403,409` · **404 는 `GET …/{id}` 하나뿐**. §1-1 표가 `PUT …/{id}` 에 404 를 잘못 적었다 → 지웠다.
⇒ §7-4 셋째 행의 범위를 **셋으로 넓히고**(없는 P/O 에 쓰면 404 를 낸다 — 계약 미선언), 「알려둘 것」도 한 자리가 아니라 셋으로 적는다. 판정 자체(404 를 낸다)는 그대로 — `plan-api.md` §5.3 ④ 은 미선언 자리를 400 으로 접으라 하지 않았다.

### R-2. ⛔ **채번 카운터는 업무 트랜잭션 «밖»에서 돈다** — 시그니처에서 `tx` 를 뺀다 (api 3-a 채택 · integration G-3 의 처방은 기각)
갈린 자리: api 「밖」 vs integration 「안 + `$transaction(fn, { timeout: 15_000 })`」. **밖으로 간다.** 근거 넷 —
1. **롤백이 카운터를 되돌리면 재시도가 무의미하다.** `goods-receipt.service.ts:98` 의 재시도는 `$transaction` 을 **통째로 다시 연다**(실측) — 증가가 그 안이면 세 번 다 같은 번호를 뽑고 `ConflictException` 으로 끝난다. 하노이 이관 창(레거시 번호와 같은 날)이 **실제로 막힌다**. 이것이 §3-5 의 안전 논거였으므로 안쪽 안은 자기 근거를 무너뜨린다.
2. **행 잠금이 전표 커밋까지 간다.** `nextReceiptNo` 는 `postReceipt` 의 **첫 문장**(`receipt-posting.ts:63` 실측)이라 같은 (유형·영업일) 입고가 전기·잔액·적치까지 한 줄로 선다. Prisma 기본 트랜잭션 시한 5초를 넘기면 `P2028` 이고, 그것은 `isDuplicateNo` 가 아니라 **재시도 루프를 빠져나가 500** 이 된다(integration G-3 의 실측이 옳다). integration 은 시한을 15초로 늘려 덮자고 했으나, 그것은 **현행에 없던 실패 모드를 만들고 나서 완화하는 것**이다 — 잠금을 애초에 안 만드는 쪽이 새 개념이 적다(§2 2단계 기준 5).
3. **결번은 허용된다.** 계약이 번호의 형식도 연속도 요구하지 않는다(어느 응답도 `pattern` 없음 — `plan-api.md` §5.5). 「결번」과 「번호 재사용」은 값이 다르다 — 재사용은 두 전표가 같은 번호를 갖는 «사고»이고 결번은 흔적일 뿐이다. `count()+1` 이 지운 행 자리를 되돌려주던 결함이 사라지는 것이 이 코어의 목적이다.
4. **멱등 재전송은 영향이 없다**(integration 확인) — `runIdempotent` 가 저장된 응답을 먼저 돌려주므로 `work()` 자체가 안 돈다. 카운터는 밖이든 안이든 안 오른다.
⇒ 시그니처 `next(documentTypeCode, plantId, periodDate)`(§3-1 재수립 반영). ⛔ `$transaction` 시한은 **손대지 않는다** — 잠금을 안 만들므로 지금과 같다.
⇒ **부수 이득**: `NTC-` 이관이 「`create()` 를 `$transaction` 으로 감싼다」(integration G-4)가 아니라 **호출 한 줄 치환**이 된다.

### R-3. 규칙 조회·자동 생성 — `is_active` 는 조회 조건이 아니다 · `DO UPDATE … RETURNING` (integration G-2 + api 3-b 절충)
- ⛔ **`is_active = true` 를 조회 `WHERE` 에 넣지 않는다.** `uq_numbering_rule` 에 `is_active` 가 없어(실측) 비활성 행이 한 줄 있으면 조회는 실패하고 자동 생성은 유일 충돌로 막혀 **영영 규칙을 못 찾는다**(integration G-2-3). 대신 **찾은 행이 `is_active=false` 면 던진다**(F-6 과 같은 처리).
- ⛔ api 안(`DO UPDATE SET … is_active = true`)은 **기각** — 운영자가 일부러 내린 규칙을 조용히 되살린다(§2 2단계 기준 4).
- `DO NOTHING`(integration) 은 충돌 시 `RETURNING` 이 0행이라 재-SELECT 가 필요하다 ⇒ **`DO UPDATE SET updated_at = clock_timestamp() RETURNING numbering_rule_id`** 로 한 문장에 끝낸다(api 안의 절반만 취한다).
- `uq_numbering_rule` 은 **표현식 UNIQUE INDEX**(제약 아님 — baseline:2595)라 `ON CONFLICT ON CONSTRAINT` 를 못 쓴다. 표현식 추론이 서는지는 DB 없이 못 재므로 **PR ① 첫 실행에서 확인**하고, 안 서면 `INSERT … SELECT … WHERE NOT EXISTS` 로 접는다. 반면 §3-3 의 `uq_numbering_counter` 는 **진짜 CONSTRAINT**(baseline:2608)라 `ON CONSTRAINT` 가 그대로 선다.

### R-4. 상신 시 **대상 P/O 행을 잠근다** — `SELECT … FOR UPDATE`(호출자 몫) (api 4)
§4-2(부분 유일 인덱스 대신 조회)와 §6-3(`version_no` 를 안 올린다)이 **합쳐지면** 같은 If-Match 를 든 두 상신이 둘 다 통과한다 — 낙관적 잠금이 잡아 줄 수 있었던 자리를 스스로 비운다. 두 절이 따로 판정돼 이 합이 안 보였다.
⇒ 호출자(`purchase-order.service.ts`)가 트랜잭션 **첫 문장**에서 `SELECT … WHERE purchase_order_id = $1 FOR UPDATE` 를 건다. 스키마 0 · 계약 0 · 202/ETag 판정 그대로 · 되돌림 0. **코어가 아니라 호출자 몫**이다(코어는 대상 표를 모른다 — §4-1 유지).
⚠ uiux 는 「단일 사용자의 단일 버튼이라 이중 클릭뿐, 요청이 둘 서도 사고가 아니라 잡음」이라 했다 — 맞지만 잠금이 **공짜**이므로 채택한다. §4-2 의 3단계 흔적 주석을 이것으로 바꾼다.

### R-5. `schema.prisma` 관계 두 줄에 **`onDelete: NoAction, onUpdate: NoAction`** 을 적는다 (integration G-1)
Prisma 의 optional 관계 기본값이 `SetNull`/`Cascade` 라, 안 적으면 손 SQL 의 `REFERENCES …`(= NO ACTION)와 참조 동작이 갈려 `migrate diff` 가 드리프트를 낸다(integration 이 `migrate diff` 로 실측). 선례 `goods_issue.approval_request_id`(`schema.prisma:758`)가 그 형태다.
➕ 같은 선례는 `map:` 을 **안 붙였다** — 그래서 이름이 Prisma 기본형(`purchase_order_approval_request_id_fkey`)이 된다. baseline 이 만든 `fk_inventory_adjustment_approval` 류는 `map:` 으로 고정돼 있어 드리프트가 없다(실측) — **새 칸은 `map:` 을 붙이지 않는다**.
➕ 선례가 함께 깐 `ix_goods_issue_approval_request` 는 **안 깐다**(표시용 역참조지 조회 축이 아니다). 「선례와 달리 인덱스를 안 깐다」를 §2-5 에 한 줄 남긴다 — 다음 슬라이스가 베끼지 않게.

### R-6. 라인 삭제 가드는 **`inbound_receipt_line` + `asn_line` 둘을 본다** (api 7-1)
`asn_line.purchase_order_line_id` FK 가 실재한다(`schema.prisma` `asn_line` · `onDelete: NoAction` 실측). ASN 만 붙은 라인을 지우면 **FK 위반이 500 으로 샌다**(입고에서 이미 한 번 고친 자리 — 995c122). 코드는 `SUCCESSOR_EXISTS` 하나. 그 FK 에 인덱스는 **안 깐다**(1차 데이터량 · §2 기준 3) — 마이그레이션 주석 한 줄.

### R-7. 마이그레이션 선행 커밋을 **PR ③(sonnet) → PR ②(opus)** 로 옮긴다 (api 6)
README §4 모델 배분표가 「구현 — 코어(원장 쓰기·상태기계·posting·**마이그레이션**) = opus」다. ②가 ③보다 **앞**이므로 「A1 이 조회보다 먼저 선다」(integration·uiux 가 ③을 지지한 근거)는 그대로 지켜진다. 줄 수만 ② ~165 · ③ ~335 로 옮겨 가고 PR 수·순서·커버리지는 불변.
✏ 함께 정정 — 「조회가 실어야 하니 마이그가 앞선다」의 근거는 «required» 가 아니다(`PurchaseOrder.required` 7칸에 `approvalRequestId` 가 없다). **`type: [integer,null]` 이라 널로 내려야 하고, 그러려면 칸이 있어야 한다**(§6-4 판정).

⇒ **9 유형 · 7 오퍼레이션.** 계약이 그 셈을 직접 적었다(`CD-APPROVAL-TYPE`): 「값 집합의 정본은 화면이 아니라 «상신 오퍼레이션»이다 … ⚠ 본문 스키마로 세지 않는다 — 7개는 ApprovalRequestCreate 를 쓰지만 출하 취소만 ShipmentCancelRequest 를 쓴다(모양은 같다 · required=[reason])」.

**아홉 자리가 «글자 그대로 같게» 요구하는 것 넷** — 이것이 코어의 몸이다.
1. 「결재선이 없으면 400(code=`ROUTE_NOT_FOUND`)이다 — 상신할 곳이 없는 요청을 만들지 않는다」 (6자리에 같은 문장)
2. 「진행 중인 승인 요청이 이미 있으면 400 이다 — 한 전표에 살아 있는 요청은 하나다」 (4자리에 같은 문장 · 코드 이름은 계약이 **안 줬다** → `APPROVAL_IN_PROGRESS`(§1-5))
3. 「반려된 요청은 진행 중이 아니므로 다시 상신할 수 있고 그때는 새 요청이 만들어진다(공유계약 J-6)」 → **「진행 중」 = `PENDING` 만**. `REJECTED` 는 막지 않는다
4. 유형·대상 유형은 **서버가 채운다** — 「⛔ 화면이 고르는 값이 아니다 — 서버가 상신 오퍼레이션에서 채운다」(`CD-APPROVAL-TYPE`) · 「값은 «상신 오퍼레이션이 정한다» — 화면이 고르는 값이 아니라 서버가 채운다」(`CD-APPROVAL-TARGET-TYPE`)

⛔ **코어가 지지 «않는» 것 셋** — ① If-Match 판정(자리마다 토큰의 출처가 다르다 — P/O 는 자기 경로, 다형 취소는 대상 문서, 실적 정정은 아예 없다) ② 응답 모양(출하만 200 `Shipment`) ③ 주체 해석(`WorkerNo` 는 IQC 생략만). 셋 다 호출자 몫이다.

### 2-5. 마이그레이션 SQL 초안 — **A1·A2·M-b 한 파일. forward-only · 추가만.**

```sql
-- I-2 선행 커밋 · A1·A2·M-b (plan.md §4)
--
-- ── A1. 승인 요청 역참조 ────────────────────────────────────────────────────
-- 계약 `PurchaseOrder.approvalRequestId` 가 `x-source-column` 없이 서 있다(실측) —
-- 「승인 요청 식별자. 승인 진행 상태를 읽는 경로는 별도 계약에서 온다」. 응답 필수 칸은
-- 아니지만 화면(W-01-11 §5-6)이 「등록 → 승인 요청 → 승인 완료」를 한 줄로 보이므로
-- 이 칸이 없으면 상세를 두 번 부른다.
--
-- ⛔ 이 FK 는 «업무 승인 하나»만 담는다(plan.md §5 #12 · I-1 R-3) — P/O 의 취소 승인은
--    애초에 없다(§5-2). 승인 «판정»은 언제나 다형 축(target_type_code, target_id,
--    approval_type_code)으로 조회한다. 이 칸은 표시용 역참조다.
-- FK 제약 이름을 적지 않는다 — PostgreSQL 이 짓는 `purchase_order_approval_request_id_fkey`
-- 가 Prisma 기본형이다. `fk_*` 로 지으면 `migrate diff` 가 드리프트를 낸다(선례:
-- data_model_v4 의 `goods_issue.approval_request_id` 도 인라인 REFERENCES 다).
ALTER TABLE logistics.purchase_order
    ADD COLUMN approval_request_id bigint REFERENCES app.approval_request(approval_request_id);

COMMENT ON COLUMN logistics.purchase_order.approval_request_id IS
    '이 P/O 의 업무 승인 요청. 취소·특수 승인은 여기 담지 않는다(공유계약 A-10 다형 축이 정본). 근거: 계약 PurchaseOrder.approvalRequestId.';

-- ── A2. 초과 입하 분리에서 승계된 입하 라인 ─────────────────────────────────
-- 계약 `PurchaseOrderCreate.sourceInboundReceiptLineId` — 「초과 입하 분리에서 넘어온
-- 경우 승계된 입하 라인. 근거: W-01-03 §5-1」. 응답에는 없다(받기만 한다).
--
-- ⚠ 받아서 버릴 수도 있었다(선례: businessDate 미저장 · 대기 15). 저장을 고른 것은
--    W-01-03 이 「초과분 입하를 이 P/O 에 귀속」시키는 «되짚기»의 유일한 흔적이어서다 —
--    귀속은 inbound_receipt_line.purchase_order_line_id 가 지지만 그것은 «어느 라인에»
--    붙었는지만 말하고 「이 P/O 가 어느 초과분 때문에 생겼는가」는 어디에도 안 남는다.
ALTER TABLE logistics.purchase_order
    ADD COLUMN source_inbound_receipt_line_id bigint
        REFERENCES logistics.inbound_receipt_line(inbound_receipt_line_id);

COMMENT ON COLUMN logistics.purchase_order.source_inbound_receipt_line_id IS
    '초과 입하 분리(W-01-03)에서 승계된 입하 라인. 일반 발주는 비어 있다. 근거: 계약 PurchaseOrderCreate.sourceInboundReceiptLineId.';

-- ── M-b. ERP 발주번호 유일 (§I-48) ──────────────────────────────────────────
-- 계약 `erpPurchaseOrderNo` x-internal-note 원문: 「⚠ 유일 제약이 없다(실측) — 같은 ERP
-- 번호를 두 MES P/O가 가질 수 있다. 의도인지 누락인지 미확정 — 화면은 중복을 경고할 수
-- 있으나 «강제는 서버·DB 몫»이다. 근거: W-01-11 §6·§8-3 · omf-mes#75」
--
-- 부분 유일로 둔다 — PostgreSQL 은 UNIQUE 에서 NULL 을 서로 다르게 보므로 맨 UNIQUE 와
-- 결과는 같지만, WHERE 절이 「비어 있는 것은 세지 않는다」는 의도를 구조로 말한다.
-- ⚠ 지금 이 칸을 채우는 오퍼레이션이 계약에 «0건»이다(§7-3) — 다만 `계약-되돌림-mdm.md`
--    §X-1 이 「확정된 수신 대상은 품목·자재명세·조직·작업자·**구매발주** 다섯」을 인용하고
--    서버가 `PURCHASE_ORDER` 문자열을 이미 골라 두었다 ⇒ 「올 수도 있는 경로」가 아니라
--    «확정된 수신 대상»이다(재수립 R-9). 인덱스는
--    당분간 빈 집합 위에 선다. 그래도 지금 거는 것은, 02 P/O 수신 I/F 가 붙는 순간
--    중복이 «데이터로» 들어오면 되돌리는 비용이 인덱스보다 크기 때문이다.
CREATE UNIQUE INDEX uq_purchase_order_erp_no
    ON logistics.purchase_order (erp_purchase_order_no)
    WHERE erp_purchase_order_no IS NOT NULL;
```

- **삭제·NOT NULL 조임 0건** → 두 릴리스 규칙 미해당 → 멈춤 조건 아님.
- **`schema.prisma` 는 고친다** — 스칼라 2 + 관계 2 + 반대편 역참조 2 = **6줄**(부분 유일 인덱스는 I-1 A6 과 같은 이유로 못 적는다). `@default` 변경이 없으므로 `prisma generate` 는 **관계 타입 때문에** 돌린다.
- ⛔ **관계 두 줄에 `onDelete: NoAction, onUpdate: NoAction` 을 반드시 적는다**(재수립 R-5) — Prisma 의 optional 관계 기본값이 `SetNull`/`Cascade` 라, 안 적으면 위 손 SQL(`REFERENCES …` = NO ACTION)과 참조 동작이 갈려 `migrate diff` 가 드리프트를 낸다(integration 이 `migrate diff` 로 실측). 선례 `goods_issue.approval_request_id`(`schema.prisma:758`). ⛔ `map:` 은 **붙이지 않는다** — 그래야 이름이 Prisma 기본형(`purchase_order_approval_request_id_fkey`)이 된다(baseline 의 `fk_*` 들은 `map:` 으로 고정돼 있어 드리프트가 없다).
- ➕ **선례와 달리 인덱스를 안 깐다**(R-5) — `goods_issue` 는 `ix_goods_issue_approval_request` 를 함께 깔았으나 이 칸은 **표시용 역참조**이지 조회 축이 아니다(승인 판정은 다형 축 `ix_approval_request_target` 을 탄다). 다음 슬라이스가 베끼지 않도록 여기 남긴다.
- ➕ **`CONCURRENTLY` 를 쓰지 않는다** — Prisma 는 마이그레이션 파일을 한 트랜잭션으로 돈다. 대상이 0행이라 잠금 시간도 0이다.
- ⚠ **순환 FK 가 생긴다**(R-12 ①) — `purchase_order → inbound_receipt_line → purchase_order_line → purchase_order`. DDL 은 무해하나 **e2e 정리 순서**에 걸린다(`source_inbound_receipt_line_id` 를 채운 P/O 가 있으면 입하 라인을 먼저 못 지운다). §8 PR ④ cleanup 에 한 줄 + **I-3 계획안에 인계**.
- ⚠ **적용 전 중복 확인** — `uq_purchase_order_erp_no` 가 실패할 수 있다. `seed.ts`·e2e 에 `purchase_order` 행이 **0건**(실측 — `entity_type_registry` 등록 행 말고는 없다)이라 로컬·CI 는 안전. 하노이는 적용 직전:
  ```sql
  SELECT erp_purchase_order_no, count(*) FROM logistics.purchase_order
   WHERE erp_purchase_order_no IS NOT NULL GROUP BY 1 HAVING count(*) > 1;
  ```

### 3-3. 동시성 — **업무 트랜잭션 밖**에서 한 문장으로 올린다 (재수립 R-2 반영)

```sql
INSERT INTO app.numbering_counter (numbering_rule_id, period_key, last_value)
     VALUES ($1, $2, 1)
ON CONFLICT ON CONSTRAINT uq_numbering_counter
  DO UPDATE SET last_value = app.numbering_counter.last_value + 1,
                updated_at = clock_timestamp()
  RETURNING last_value;
```
- `uq_numbering_counter` 는 baseline:2608 의 **진짜 CONSTRAINT** 라(`CONSTRAINT … UNIQUE`) `ON CONFLICT ON CONSTRAINT` 가 그대로 선다 — 표현식 인덱스인 `uq_numbering_rule`(§3-4)과 갈리는 지점이다.
- 한 문장이라 **읽고-쓰는 창이 없다**. 이 문장은 **업무 트랜잭션 밖**에서 돌므로 행 잠금은 이 문장이 끝나면 바로 풀린다 — 전표 커밋까지 끌고 가지 않는다(R-2 ②). 그래서 `$transaction` 의 시한(Prisma 기본 5초)을 손대지 않아도 된다.
- **대가는 결번이다** — 전표가 롤백되면 그 번호는 버려진다. 계약이 연속을 요구하지 않고(`plan-api.md` §5.5), 「번호 재사용」(`count()+1` 의 결함)과 달리 결번은 사고가 아니다.
- **e2e 로 고정하는 법**: 같은 `businessDate` 로 입고 두 건을 **Promise.all** 로 던져 ① 번호 둘이 서로 다르고 ② 둘 다 성공하며 ③ **타임아웃(`P2028`)이 나지 않는 것**을 본다(지금 `count()+1` 은 같은 번호를 뽑아 하나가 유일 제약에 걸린다). 단위 테스트로는 못 잡는다 — 경합이 DB 안에 있다.

### 3-4. 규칙이 없는 문서 유형 — 기본값 `{PREFIX}-{YYYYMMDD}-{SEQ4}`

`plan.md` §0 #3 판정 그대로. **다만 카운터에는 `numbering_rule_id` FK 가 있으므로**(NOT NULL) 규칙 행 없이는 셀 자리가 없다 ⇒ 첫 사용에서 **규칙 행을 만들어 둔다**:

```sql
INSERT INTO app.numbering_rule (document_type_code, pattern, reset_cycle_code)
     VALUES ($1, $2, 'DAILY')
ON CONFLICT (document_type_code, COALESCE(plant_id, 0), COALESCE(lot_type_code, ''))
  DO UPDATE SET updated_at = clock_timestamp()
```

```ts
assertNoOpenRequest(tx: Tx, targetTypeCode: string, targetId: bigint, approvalTypeCode: string): Promise<void>;
```

`request()` 가 하는 일 다섯 — ① `assertNoOpenRequest` ② `selectRoute(tx, approvalTypeCode, businessUnitId)`(I-1 실재 · `ROUTE_NOT_FOUND`·`ROUTE_AMBIGUOUS` 를 그대로 던진다) ③ `numbering.next(tx, 'APPROVAL_REQUEST', null, today)` ④ `approval_request` 한 행(`status_code='PENDING'` · `requested_at = now()`) ⑤ `expandSteps(tx, routeId, requestId)`(I-1 실재).

- ⛔ **대상 문서를 건드리지 않는다** — `purchase_order.approval_request_id` 를 채우는 것은 **호출자**다. 코어가 9 도메인의 표를 알면 그게 두 번째 라우팅표가 된다(I-1 §3-4 가 콜백을 물리친 것과 같은 이유).
- 코어가 코어를 부른다(`ApprovalService` → `NumberingService`) — `ApprovalService` 는 이미 `DocumentStateService` 를 부른다(실측). 도메인 간 호출 금지는 `src/*/`(도메인) 사이의 규칙이다(`server-architecture.md` §1).
- `requested_at` 은 서버 시각이다 — `business_date` 축이 **아니다**(C-8 대상 3표에 `approval_request` 가 없다).

### 4-2. 「진행 중 요청은 하나」의 판정 — **조회로 한다** (§2 절차)

- **0단계 선례**: 없다. I-1 은 요청을 만들지 않았다.
- **1단계**: 「같은 순간에 두 상신」에서만 갈린다(순차 클릭은 조회가 잡는다) → **가장자리**.
- **2단계**: 기준 1 해당 없음(원장 안 씀) · 기준 2 해당 없음(**둘 다 거부한다** — 갈리는 것은 「인덱스로 거부」냐 「조회로 거부」냐다) · **기준 3 「스키마를 안 늘리는 쪽」이 걸린다** → **조회**.
  - 부분 유일 인덱스로 하면 `CREATE UNIQUE INDEX … ON app.approval_request (target_type_code, target_id, approval_type_code) WHERE status_code = 'PENDING'` 이 되고, 이는 **§0 조건 1(계획에 없던 마이그레이션)** 을 세운다.
  - 조회는 **I-1 A6 이 이미 깐 `ix_approval_request_target` 을 그대로 탄다**(§2-4) — 축이 이미 있다.
- **3단계 흔적**(재수립 R-4 반영): ① **호출자가 트랜잭션 첫 문장에서 대상 행을 잠근다** — `SELECT … WHERE purchase_order_id = $1 FOR UPDATE`. 코어 주석에는 「⚠ 동시 상신을 막는 것은 «호출자의 대상 행 잠금»이다 — 이 함수의 조회만으로는 같은 순간의 둘이 다 통과한다」 ② 단위 테스트 이름에 「대상 행 잠금은 호출자 몫이다」 ③ 되돌릴 때: 부분 유일 인덱스 한 줄(추가·부분) + 코드 무변경.
- ⛔ 잠금이 **왜 필요해졌나** — §6-3 이 `version_no` 를 안 올리기로 갈랐으므로 같은 If-Match 를 든 두 요청을 낙관적 잠금이 못 가른다. 두 절이 따로 판정돼 그 합이 안 보였다(재수립 R-4). 스키마·계약 변경 0이라 값이 싸다.

### 4-3. 「반려는 막지 않는다」

계약: 「반려된 요청은 진행 중이 아니므로 다시 상신할 수 있고 그때는 새 요청이 만들어진다(공유계약 J-6)」 ⇒ 판정은 `status_code = 'PENDING'` **하나**다. `APPROVED` 도 「진행 중」이 아니다 — 승인 끝난 P/O 에 다시 상신하면 새 요청이 선다. ⚠ 계약이 그것을 막지 않았으므로 **막지 않는다**(§2 1단계 「계약 문자 그대로」).

### 4-4. ⛔ `assertApproved` 는 I-2 에서 만들지 않는다

- **사용처가 0이다.** P/O 에는 `:post` 가 없다(오퍼레이션 7건 실측 — §1-1). 승인 뒤에 P/O 에서 일어나는 일이 계약에 **없다**(§5-2).
- 입하도 아니다 — `inbound-receipt*` 쓰기 오퍼레이션의 `description`·`x-internal-note` 에 「승인」이 **한 건도 없다**(jq 실측 0건). I-3 은 이 함수를 안 부른다.
- 첫 사용처는 **I-4**(`goods-issues:post`)와 I-14(`adjustments:post`)다 — `plan-api.md` §5.4 가 `APPROVAL_REQUIRED` 를 **S04·S07** 에 배정했다.
- ⇒ CLAUDE.md 「사용처 하나뿐인 추상화·선제적 레이어 금지」 + I-1 §3-4 의 같은 판정(「⛔ I-1 에서 만들지 않는다 — 사용처가 0이다」)을 그대로 따른다. **이름과 자리는 I-1 이 이미 적어 두었다** — I-4 가 채운다.

### 4-5. 코어 PR ≤200줄에 들어가는가

들어간다 — §8 PR ② 에서 **~130줄**. 채번 코어(PR ①)와 **별도 PR** 이다(`plan.md` §3 이 「채번과 별도」로 못박았다).

### 5-3. `:request-approval` 이 상태를 옮기는가 — **안 옮긴다** (§2 절차)

- **1단계**: 모든 상신 호출의 결과가 달라진다 → **본길처럼 보인다.** 그러나 계약 문자가 답을 준다 — 옮길 값이 목록에 **없다**(`LOGISTICS_DOCUMENT_STATUS` 4값에 「승인대기」가 없다). 지어내야만 옮길 수 있으므로 **옮기지 않는 쪽이 계약 문자 그대로**다.
- **2단계**(확인용): 기준 1 「상태를 쓰지 않는 쪽」이 첫 줄에서 걸린다 → 같은 결론.
- **판정**: 승인 진행은 `approval_request.status_code` 가 지고 P/O 는 `REGISTERED` 에 머문다. `plan-api.md` S01 초안과 **같다**.

### 5-4. 승인이 끝난 뒤 P/O 는 누가 옮기나 — **아무도 안 옮긴다**(J-8 상태 조회 갈래)

### 6-2. 멱등 — 쓰기 4건 전건

| 자리 | 감싸는 법 | 성공 상태 |
|---|---|---|

조회 3건에는 붙이지 않는다.

### 6-3. `If-Match` 3건 · ETag 4건 — ⛔ 함정 하나

- `If-Match` **필수 3**(선택 0). 가드 `requirement()` 판정을 그대로 믿는다.
- `PUT …/lines` 의 토큰은 **부모 `purchase_order.version_no`** 다 — 계약이 문장으로 적었고(§1-3) **응답 ETag 도 계약이 선언했다**. I-1 R-4 는 계약이 «선언하지 않은» 헤더를 선례로 냈지만, 여기서는 계약이 명시했으므로 「알려둘 것」이 아니다. 구현은 `runVersioned` + 부모 `version_no` 증가(선례 `approval-route.service.ts:202 replaceSteps`).
- ⛔ **함정 — `:request-approval` 은 `version_no` 를 올리지 않는다.**
  - 계약 202 응답에 **ETag 헤더가 없다**(실측). 올리면 화면이 새 토큰을 받을 길이 없어 **다음 `PUT` 이 영원히 409** 가 된다(상세 GET 을 다시 돌 때까지).
  - 그런데 이 오퍼레이션은 `purchase_order.approval_request_id` 를 **쓴다**(A1). 「쓰는데 버전을 안 올린다」는 어긋남이라 §2 로 가른다 — 1단계 가장자리(연속 쓰기에서만 갈림) → 2단계 기준 2 의 역: 화면을 막지 않는 쪽이 되돌리기 싸다(올리는 쪽으로 조이는 것은 나중에 가능, 푸는 것도 완화) → **안 올린다**.
  - 흔적: 서비스 주석 + e2e 이름 `상신 — 같은 If-Match 로 뒤이어 PUT 이 통한다(202 에 ETag 가 없어 버전을 올리지 않는다)` + **「알려둘 것」 ⓐ**(§7-5).
  - ⭐ **이 판정이 나머지 8 상신자에 그대로 복사된다** — 9 상신자 중 ETag 를 낼 수 있는 것은 200 `Shipment` 를 돌려주는 출하 취소 하나뿐이고 나머지는 전부 202 `ApprovalRequestRef` 다(§1-4). I-2 가 **첫 벌**이다(재수립 R-10 ⓐ).
  - ⛔ **대신 동시 상신은 대상 행 잠금(`FOR UPDATE`)이 막는다** — §4-2 와 이 절이 합쳐지면 낙관적 잠금이 비므로 호출자가 잠근다(재수립 R-4).
- ETag 4건은 `setEtag(response, versionNo)` — 본문 필드로 내리지 않는다(A-4).

## 7. 설계 미정 자리 — README §2 절차로 전건 판정

### 7-1. `approval_request` 에 결재선 식별자를 더할까 (문의 018 의 I-2 몫)
- **0단계**: I-1 §2-3 이 이미 판정했다 — 유형 축 근사, 칸을 더하지 않는다. 018 은 「**I-2 에서** nullable `approval_route_id` 를 더해 정확히 셀까」를 물었고 **회신이 없다**.
- **판정**: 더하지 않는다(기준 3). 회신이 오면 그때 한 줄 `ALTER TABLE … ADD COLUMN`(0행이라 백필 0). **기존 문의 018 — 새로 세우지 않는다.**

### 7-2. `reset_cycle_code` 가 `DAILY` 가 아닐 때
- **0단계**: 값 목록이 없다(`RESET_CYCLE` 그룹 폐기 · 시드 행 1건은 `DAILY`).
- **1단계**: 그런 규칙 행이 등재됐을 때만 갈린다 → **가장자리**.
- **2단계**: 기준 2 「거부하는 쪽」 → **던진다.** `transitions.ts` 의 F-6 과 같은 처리이고, 조용히 `DAILY` 로 접으면 「월 단위로 리셋한다」고 등재한 사람이 그 사실을 모른다.
- **3단계**: 코어 주석 + 단위 테스트 `채번 — DAILY 가 아닌 리셋 주기는 던진다(값 목록이 없다)`. 문의 대상 아님(등재하는 주체가 우리다).

### 7-3. `erp_purchase_order_no` 유일 제약 (§I-48 · M-b)
- **0단계**: 계약이 답을 반쯤 줬다 — 「의도인지 누락인지 미확정 — 화면은 중복을 경고할 수 있으나 **강제는 서버·DB 몫이다**」. 화면 §8-3 도 같은 문장에 「조정」 등급.
- **1단계**: 같은 ERP 번호가 두 번 들어올 때만 → **가장자리**. ⚠ 게다가 **지금은 아무도 이 칸을 못 채운다** — `PurchaseOrderCreate`·`PurchaseOrderUpdate` 스키마에 칸이 **없고**(실측) 화면도 「등록 폼은 이 값을 받지 않는다」(W-01-11 §4-A)라 적었다. 채우는 것은 「02 P/O 수신 I/F」인데 **그 인터페이스가 계약에 없다**.
- **2단계**: 기준 2 「거부하는 쪽 — 거부→허용은 호환 완화」가 먼저 걸린다 → **유일 제약을 건다**(부분 유일 · §2-5 M-b). 인덱스를 나중에 지우는 것은 완화이고, 중복이 데이터로 들어온 뒤 조이는 것은 데이터 정리를 부른다.
- **3단계**: 마이그레이션 주석 + **「알려둘 것」 ⓓ**(재수립 R-9 — ~~문의 024~~ 는 **철회**했다: `W-01-11` §8 #3 이 「강제는 서버·DB 몫 · ✅ 계약 반영 완료 · 이슈 재발행」으로, §8 #4 가 「도메인 02 스펙 작성 시 함께 본다」로 **물음도 일정도 이미 세워 두었다**) + e2e 는 못 쓴다(값을 넣는 경로가 없다) → 단위 테스트에서 Prisma 오류 매핑만 확인.
- ⭐ **근거 보강**(재수립 R-9) — 「그 인터페이스가 계약에 없다」는 절반만 사실이다. `계약-되돌림-mdm.md` §X-1: 계약 `InterfaceDefinition.targetCode` 가 「확정된 수신 대상은 품목·자재명세·조직·작업자·**구매발주** 다섯」이라 적었고 서버가 `PURCHASE_ORDER` 문자열을 이미 골라 두었다. ⇒ **오퍼레이션이 없을 뿐 「ERP 발주를 받는다」는 계약 층위에서 확정**됐고, 이것이 지금 유일 제약을 거는 가장 센 근거다(「올 수도 있는 경로」가 아니다).
