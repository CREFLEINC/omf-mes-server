1. **계약 읽기 표** — 7건 각각: 파라미터·본문 필드·응답·에러코드(계약이 이름 적은 것)·멱등/If-Match/ETag/403/`X-Worker-No`·`x-*` 노트. 추측 금지, 계약 문장 인용. `sourceDocumentTypeCode` 3값과 각 값의 `sourceDocumentId` 가 가리키는 표 · `destinationTypeCode` 값과 「자체 폐기면 비운다」 문장 · `:post` 본문(있다면 `businessDate`·`occurredAt`) · `:request-approval` 의 `approvalTypeCode` 결정 축(`GOODS_ISSUE_DISPOSAL` vs 다른 유형 — `reasonCode` 파생 G-31).
2. **물리 대조** — 계약 ↔ `goods_issue`·`goods_issue_line`. 없는 칸·다른 이름·제약. **M-c 실측 결론**(마이그 필요/불필요 — 필요하면 SQL 초안 · forward-only · 별도 선행 커밋). `goods_issue_spare_line` 이 이 7건에 걸리는지.
3. **원장 `:post`** — `posting.post()` 호출 모양(라인마다 `from` = 출발 창고·위치·품질상태·재고상태 / `to` = `LOCATION` 일 때만) · 어느 값이 라인에서 오고 어느 값이 헤더에서 오나 · **LOT 단위 차감**(`goods_issue_line.lot_id` 가 필수인가 · LOT 없는 품목) · 잔액 부족 400 코드 · 음수 금지의 자리(코어 vs 도메인) · `inventory_transaction_line_id` 되짚기 · `business_date` 출처(C-8 · 서버가 안 잡는다) · 상태 `REGISTERED → POSTED`(`transitions.ts` `document-post` 를 부른다 · `version_no` 범프 · 응답 ETag) · **멱등 재전송이 이중 전기가 되지 않는 구조**(`runIdempotent` + 상태 잠금 둘 다인지).
