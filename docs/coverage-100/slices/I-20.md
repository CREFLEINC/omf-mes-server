⛔ **`ix_lot_hold_released_at` 은 `schema.prisma` 에 «안 적는다»** — 부분 인덱스라 Prisma 가 표현하지 못한다. 실측 근거: 이미 있는 `ix_lot_hold_active(lot_id) WHERE released_at IS NULL` 도 모델에 없고 오늘 드리프트가 0 이다. ⚠ **반대로 `ix_lot_hold_held_at` 은 부분이 아니므로 «반드시» 모델에 적는다** — 안 적으면 `migrate diff` 가 `DROP INDEX` 를 낸다(`lanes.md` §2-3 게이트가 그 자리에서 깨진다).
⛔ `updated_at`·`updated_by` 를 더하지 않는다 — `runVersioned` 는 `version_no` 만 쓰고 해제자는 `released_by` 가 담는다.
✅ **추가·완화만 · 삭제 0 · 백필 0 · 순서 의존 0**(`lanes.md` §1-2).

### 2-5. 인덱스를 **더 걸지 않는 자리** — 근거

### 3-1. `POST /quality/lot-holds` — 201(배열)

```
1  (tx 밖) 본문 형식 — lots ≥1(RANGE) · lots≥2 인데 holdQty(INVALID) · holdQty↔uomId 짝(PAIR)
```

⭐ **순서 판정 셋**
1. **버전 대조(b)가 업무 게이트(c·d)보다 «먼저»다** — 0단계 선례 `inspection-confirm.service.ts`(「버전 대조가 상태 게이트보다 먼저다 — 형제 `:release`·`:close` 와 같은 순서」). 낡은 토큰으로 이미 보류된 LOT 을 건드리면 「다시 불러오라」가 먼저 나와야 한다.
2. **INSERT(e)가 전이(f)보다 먼저다** — 「`lot_hold` INSERT 와 `lot.status_code` UPDATE 는 한 트랜잭션이다 … 하나만 되면 재고가 안 막히거나 **막힌 이유가 없다**」(`:1845` · B-8). 이유가 먼저 서야 한다.
3. **하나라도 어긋나면 전체 거부** — 버전(계약 명문)뿐 아니라 **상태(f)도 같다**. `W-03-03` §6 이 「여러 LOT 중 하나라도 어긋나면 전체 거부」로 한 규칙만 적었으므로 두 축을 다르게 두지 않는다.

⚠ **`from` 이 가르는 자리** — C9 는 `from:['NORMAL']` 하나다(`transitions.ts:210`) ⇒ **검사 대기(`INSPECTION_PENDING`) LOT 에 클레임·리콜 재Hold 를 못 건다**(400 `STATE_LOCKED`). C10 은 `['NORMAL','INSPECTION_PENDING']` 이라 자기 전이가 허용되고 `lot_status_event` 행이 한 줄 남는다. 문의 **080**.

### 3-2. `POST …/{lotHoldId}:release` — 200 + ETag

> ⛔ **R-5 가 이 절을 다시 쓰게 한다** — 「열린 보류 재계수」가 `lot` 잠금 «밖»이라 동시성에서 깨진다(둘 다 안 옮겨 LOT 이 갇히거나, 열린 보류를 둔 채 `NORMAL` 로 간다). ⚠ **R-6: `releaseQty == hold_qty` 가 「잔량 0」 행을 만든다.** ⚠ **R-3: 400/409 를 단정하지 마라**(계약이 「횡단 단일안 소관」이라 적었다).


```
0  (tx 밖) assertCodeValues — releaseReasonCode/LOT_HOLD_RELEASE_REASON · targetLotStatusCode/LOT_STATUS
1  (tx 밖) 본문 — targetLotStatusCode ∈ {NORMAL, DEFECTIVE}(INVALID) · releaseQty > 0(RANGE)

      (`:confirm` 이 먼저 닫았을 수 있다 — §0 #2 ⓐ · 재로드해도 안 풀린다)
   d  releaseQty 가 있으면: hold_qty IS NULL(전량)이면 400 INVALID
                           releaseQty > hold_qty 면 400 RANGE
   e  코어 releaseWithin —
      원 행 UPDATE: released_at·released_by·release_reason_code·release_target_lot_status_code
                    ·remarks(있으면)·version_no + 1
      부분이면 잔량 행 INSERT: hold_qty = 기존 − releaseQty · 나머지 칸은 원 행 복사
```

## 4. 조회 6건

### 4-1. `GET /quality/lot-statuses` · `GET /quality/lot-status-summary` — **한 필터 빌더**

- 질의는 **원시 SQL** 이다(0단계 선례 `balance-query.ts`) — 접기(`CASE WHEN count(DISTINCT …) = 1`)와 `EXISTS`/`NOT EXISTS` 를 Prisma 로 못 쓴다.
- `FROM trace.lot l` 을 뿌리로 두고 `LEFT JOIN LATERAL` 셋: ⓐ 잔액 접기 ⓑ 열린 보류 집계(`SUM(hold_qty)`·`COUNT(*)`·`bool_or(hold_qty IS NULL)`) ⓒ `MAX(GREATEST(held_at, released_at))` + 그 시각의 `reason_code`.
- ⛔ **`heldQty` 는 `SUM(hold_qty)` 인데 전량 보류(NULL)가 섞이면 뜻이 다르다** ⇒ `fullyHeld=true` 면 `heldQty = onHandQty` 로 낸다. NULL 을 0 으로 접으면 「전량 보류인데 보류량 0」이 나온다(L-8).
- `sort` 6값 enum(`lotNoAsc`…`latestTransitionDesc`) · 기본 `latestTransitionDesc`. ⛔ 그 밖은 400 `INVALID`(L-4).
- **요약**은 `statusCode × lotTypeCode` 로 묶는다. ⛔ **셋을 합치지 않는다**(L-7). ⛔ **없는 조합의 칸을 0 으로 만들지 않는다** — 실제로 행이 있는 조합만 낸다(`plan-uiux.md:1073` 「4값에 없는 상태는 칸을 빼고 내린다」).
- `asOf` = 질의 시작 시각(서버). `outOfScopeCount` **생략**(§1-4).

### 4-2. `GET /quality/lot-status-transitions` — 화면이 전이표를 갖지 않는다

- `lotId` 로 `trace.lot` 한 건 → 없으면 404. `currentLotStatusCode` = 그 값.
- `transitions` = `TRANSITIONS['trace.lot.status_code']` 중 **`sourceOperation` 이 `POST /quality/lot-holds` 또는 `…:release` 인 넷**(C7·C8·C9·C10)만. ⛔ 검사 확정 넷(C4·C5·C6·C14)과 재등록은 **actionCode 가 없다** — 계약 enum 이 `RELEASE_HOLD`·`CREATE_HOLD` **둘뿐**이다(F-6: 액션을 지어내지 않는다).
- 각 행: `allowed = transition.from.includes(current)` · `targetLotStatusCode = transition.to` · `actionCode = sourceOperation === RELEASE ? 'RELEASE_HOLD' : 'CREATE_HOLD'`.
- ⭐ **`DEFECTIVE` 가 두 줄로 나온다**(C8 RELEASE_HOLD · C9 CREATE_HOLD) — 계약이 「목표 상태만으로는 가를 수 없다」(`:4410`)로 그것을 요구했다. **행을 상태로 묶지 않는다.**
- `blockedReason` — `allowed=false` 일 때만. 「지금 상태(불량)에서는 이 전이를 할 수 없습니다」 꼴.
- `note` — 전건 `allowed=false` 일 때만. 계약이 문장을 줬다: 「불량(Hold)은 발신 전이가 0이라 빈 드롭다운 대신 안내를 보인다」(`:4472` 인접) · `W-03-02` §5-5 「이 LOT은 더 전이할 수 없습니다 — 불량 처리는 생산실행에서 합니다」.
- `impact` — **CREATE_HOLD 행에만**(`:4424`). `openPickingCount` = `picking_line` 중 `picked_qty < planned_qty` 이고 소속 `picking_order.status_code` 가 종결이 아닌 건수 · `shippedQty` = `Σ goods_issue_line.issue_qty`. ⛔ **Release 행은 `null` 이다**(빈 객체가 아니다).

### 4-3. `GET /quality/lot-holds` · `…/{lotHoldId}` · `GET /quality/lot-hold-events`

- **목록** — `open` 기본 **true**. ⛔ `open=false` 는 필터를 «걸지 않는다»(계약 `:1725`). `lotNo` 정확히 일치. `heldFrom/To` 선택 쌍(§1-2 갈래 B).
- **상세** — `runVersioned` 가 아니라 조회지만 **`setEtag(version_no)`** 를 낸다(계약이 ETag 를 선언한 유일한 자리).
- **사건 목록** — 한 `lot_hold` 행을 **최대 두 사건**으로 펼친다.

| 사건 | 조건 | `occurredAt` | `actorId` | `releaseReasonCode` | `targetLotStatusCode` |
|:-:|---|---|---|---|---|
| `HELD` | 언제나 | `held_at` | `held_by` | **null** | `target_lot_status_code` |

  구현은 `SELECT … UNION ALL SELECT …` 한 문장 + 바깥에서 `ORDER BY occurred_at` · `LIMIT/OFFSET`.
  ⛔ **두 질의를 앱에서 합쳐 정렬하지 않는다** — `page.total` 과 다음 페이지가 어긋난다(계약이 `lot-statuses` 의 `transitionFrom` 설명에서 같은 함정을 이름 적었다).

  ⚠ `reasonCode` 필터는 **두 가지 다** `lot_hold.reason_code` 를 본다(해제 사건도 원 행의 등록 사유를 싣는다 · §1-4).
