### 3-5. `shopfloor_receipt_line_id` 서버 귀속 — **상한을 검사하지 않는다**

**귀속 규칙**: 이 W/O 의 수령 라인 중 `item_id = itemId AND lot_id = lotId` 인 것을 찾아 잇는다.
```
shopfloor_receipt_line WHERE shopfloor_receipt.work_order_id = ? AND item_id = ? AND lot_id = ?
  ORDER BY shopfloor_receipt_line_id DESC  →  첫 행 · 없으면 NULL
```
- **여럿이면 최신(PK 내림차순 첫 행)** — 1단계 가장자리 → 2단계 기준 5. 계약이 ⌜서버가 그 라인을 잇는다⌝ 라고만 적었고 어느 라인인지 안 적었다. 화면(§5-3)이 이 축을 ⌜무관⌝ 으로 못박아 **틀려도 업무가 안 갈린다**.
- **없으면 NULL** — 계약 ⌜비어 있어도 투입은 선다(출고 귀속 무관)⌝ · 화면 ⌜출고 귀속 없음 → 기록만⌝.
- ⛔ **`picking_line`·`goods_issue_line` 을 직접 읽지 않는다**(I-8 §9-4 인계 규약).

**⭐ 상한(`received_qty`)을 검사하지 않는다 — I-9 §9 가 남긴 물음의 답.**
§2 0단계: I-9 §9 가 ⌜수령 라인에 「소진량」 칸은 **없다** — 한 수령 라인을 여러 투입이 물어도 서버가 **누계를 못 센다**⌝ 라 못박았다.
1단계: 「누계 > `received_qty`」인 입력에서만 갈린다 → **가장자리**.
2단계 **기준 5**(새 개념 0) — 상한을 걸려면 ⓐ 「이 수령 라인을 문 투입의 합」을 매번 집계하고 ⓑ 귀속이 NULL 인 투입(계약이 정상으로 인정)은 어느 상한에도 안 걸리며 ⓒ `shopfloor_receipt_line_id` 에 **인덱스가 없어**(실측) 집계가 풀스캔이 된다. 즉 **반쪽 상한**이 되고, A-21 ⌜일부만 채워진 것이 빈 것보다 위험하다⌝ 에 걸린다.
보강: 화면 `P-02-03` 전문에 **「수령량을 넘지 못한다」류 문장이 0건**이다(grep). 있는 것은 반대 방향뿐이다 — §6 예외표 ⌜라인 수령 미달 | ⚠ 경고 — 수령량으로 진행하되 차이 사유 입력⌝.
⇒ **상한 검사 ✕.** 3단계 흔적: 단위 테스트 `수령량을 넘는 투입도 201 이다 // 설계 미정 — 문의 052 와 함께 전달`. §8-3 ⓗ.

### 3-7. `worker_id` · `terminal_id` — 주체 둘

### 3-8. `enteredQty`/`enteredUomId` — **환산하지 않는다**

물리 `ck_material_consumption_entered CHECK ((entered_qty IS NULL) = (entered_uom_id IS NULL))`(baseline `:1571-1572`).
CHECK 위반은 공용 그물에 안 걸려 **500 으로 샌다**(I-4 §3-3 · I-9 §2-3) ⇒ **서비스가 손으로 앞당겨 400 `PAIR`** 로 낸다(`error-codes.ts` 에 `PAIR` 실재 — I-3 A3 선례).

⚠ 화면 `P-02-03` §5-6 은 ⌜`input_qty` 는 **환산된 기준단위 값**이 된다. **환산은 서버가 한다**⌝ 라 적었으나 —
계약 `MaterialConsumptionCreate` 는 **`inputQty` 를 required 로 받는다**. 즉 화면이 이미 환산된 값을 보낸다.
1단계: 「`enteredQty`×환산율 ≠ `inputQty`」인 입력에서만 갈린다 → **가장자리**.

**§2 절차** — 1단계: 모든 반출의 결과가 갈린다 ⇒ **본길** → 임의로 못 고른다 ⇒ **계약 문자 그대로.** 계약은 이 전표에 날짜도, 목적 위치도, 원장 칸도, 도착 오퍼레이션도 주지 않았다 ⇒ **전기하지 않는다.**
2단계로 확인(방향 일치): 기준 1(재고·원장을 쓰지 않는 쪽) · 기준 2(안 전기하다가 전기하는 것은 완화 · 틀리게 전기한 불변 행은 못 지운다) · 기준 4(`businessDate`·목적 위치를 조용히 도출하지 않는 쪽) — **셋 다 같은 답**.

⇒ **`material_return_line.inventory_transaction_line_id` 는 영원히 NULL 이다.** 3단계 흔적: e2e 단언 `⛔ 반출이 inventory_transaction 을 만들지 않고 inventory_balance 가 그대로다 // 설계 미정 — 문의 051`.

**⚠ 멈춤 조건 3(계약끼리 모순) 판정 — 미발동.** 계약은 **스스로 모순되지 않는다**: 이 오퍼레이션의 어느 문장도 「원장을 지난다」라 적지 않았고, 날짜 칸이 없는 것과 원장 칸이 없는 것은 **서로 맞는다**. 어긋나는 것은 «물리 모델의 한 칸 + 통합 계획서의 추론» ↔ 계약이고, 그것은 §2 로 가르는 자리다(I-9 가 `plan-uiux.md` 의 「원장 ○ 이동」을 같은 방식으로 갈랐다). 물리 칸은 nullable 이라 고칠 것도 없다(README §5 「물리와 계약이 다르면 물리를 고친다」의 대상이 아니다).

### 4-5. `requested_at` — **서버 시각**(§Z-4 유형)

`material_return.requested_at timestamptz NOT NULL` · 계약 `MaterialReturn.requestedAt` **required(응답)** · `MaterialReturnCreate` 에 **칸 없음**.
§2 0단계: I-3·I-8·I-9 의 §Z-4 와 **같은 유형이지만 방향이 반대**다 — 거기는 「받았는데 담을 칸이 없다」(형식만 검증하고 버린다), 여기는 **「담을 칸이 있는데 받을 칸이 없다」**.
1단계 가장자리(값이 몇 초 다를 뿐 업무가 안 갈린다) → 2단계 기준 5.
⇒ **`requested_at = new Date()`(서버 수신 시각).**
⚠ **C-8 위반이 아니다** — C-8 이 실린 표는 셋뿐이고(`inventory_transaction`·그 파티션·`inventory_transaction_line` · CLAUDE.md) `material_return.requested_at` 은 `business_date` 가 아니다. 이 전표는 원장을 안 지난다(§4-4).
⇒ **회신 대기 15번 누적 +1** — I-9 가 **10** 으로 닫았고 이 오퍼레이션이 **11번째**다(방향이 반대인 첫 사례라 요청서 051 에 함께 적는다).
`received_at` 은 **NULL 로 태어나 영원히 NULL** — 채우는 오퍼레이션 0건(문의 051).
