## 2. 놓친 결함·사용자 흐름

### R-UX1 · Major — 전체 조회의 ETag는 호출 생략만으로 없어지지 않는다

- 근거: `docs/coverage-100/slices/I-28.md:200`은 `setEtag`를 안 부르는 것으로 설명한다. `contracts/app-공통.json:2049`는 전체 조회에서 **ETag를 내리지 않는다**고 명시한다.
- 실제 선례: `src/app.setup.ts:10`은 전역 필터/CORS만 구성하고, `test/production-production-result.e2e-spec.ts:175`는 기본 JSON 응답의 약한 내용 해시 ETag를 단언한다. 이는 새 DB 측정이 아닌 빠진 응답 경계다.
- 왜: 전체 이벤트 목록을 먼저 받은 운영자가 그 헤더를 저장 토큰으로 쓰면 숫자 version 토큰이 아니어서 실패한다. 본문 해시는 이벤트별 낙관적 잠금을 대체하지 않는다.
- 수정안: 조건부④에서 I-28 전체 구독 GET의 실제 응답에 ETag가 없도록 국소 응답 처리를 명시한다. 전역 Express 설정 변경은 요구하지 않는다. 단일 eventCode GET만 실제 숫자 토큰을 준다.
- PUT은 ETag **미선언**, 전체 GET은 **명시적 부재**다. PUT까지 일괄 헤더 억제로 범위를 넓히지 않는다. README §2 0단계의 계약 문언 적용이다.
- 필수 테스트: `전체 구독 GET의 HTTP 응답에는 약한 해시를 포함한 ETag 헤더가 없다`, `단일 이벤트 GET의 ETag를 그대로 If-Match로 저장할 수 있다`.

### R-UX2 · Minor — 최초 설정과 재편집은 토큰을 얻는 소비자 흐름까지 묶어야 한다

- 근거: `contracts/app-공통.json:2049`의 **이벤트 선택 뒤 단일 GET 재호출**, `:3574`의 조회 토큰 사용, 초안 `:201`·`:203`의 초기1/최초 PUT2, `:284`의 PUT 뒤 재조회; W-CO-11 `:162`·`:173`의 저장 충돌→다시 불러오기.
- 왜: 헤더가 없는 정본 이벤트를 단일 GET에서 통째로 빼면 최초 If-Match를 얻지 못한다. 저장 성공 후 같은 화면에서 다시 편집할 때도 PUT 본문에는 새 토큰이 없다. 개별 응답 테스트만으로 이 연결은 드러나지 않는다.
- 수정안: **정본 이벤트 선택→단일 GET 빈 규칙·false·토큰1→PUT 성공→단일 GET 토큰2→새 키로 다음 편집**을 한 시나리오로 고정한다. 전건 GET/preview 결과에서 토큰을 만들지 않는다.
- 초기1은 확정된 계약 상수가 아니라 `version_no` 기본1·공용 양수 토큰 선례를 사용한 권고다. 정본에 존재하지만 설정만 없는 입력은 가장자리이며, GET 쓰기0은 README §2 2단계①에 맞는다. `INITIAL_NOTIFICATION_SUBSCRIPTION_VERSION` 및 문의 흔적을 남긴다.
- 409 복구는 단일 GET으로 설정/토큰을 다시 받은 뒤 사용자가 재편집하는 흐름이다. 응답 유실 재전송은 처음 키/본문을 유지한다. 최초 충돌·실패 뒤에는 고아 헤더가 없어야 한다.
- 필수 테스트: `미설정 이벤트를 선택해 최초 저장하고 다시 조회한 토큰으로 두 번째 저장한다`, `두 운영자의 최초 저장 충돌 후 다시 불러온 토큰으로 재편집한다`, `최초 PUT 실패 뒤 GET은 초기 빈 설정과 초기 토큰을 유지한다`.

### R-UX3 · Major — 규칙 수·표시되는 사람 수·실제 수신 인원 수는 서로 다르다

- 근거: `contracts/app-공통.json:2022`는 이벤트 목록 수를 **recipients.length**로 정의한다. `:3451`은 중복을 접고 `:3513`은 비활성도 표시한다. W-CO-11 `:120`·`:168`·`:170`·`:171`은 실제 0명 경고와 비활성 표시를 요구한다. 초안 `:247`에는 users와 totalCount만 있고 좌측 목록 숫자의 의미가 빠졌다.
- 왜: ROLE 규칙1개에 사람0명, USER 규칙1개에 비활성1명인 경우 규칙 수는1이지만 실제 수신은0명이다. 반대로 ROLE2개+USER1개가 같은 활성1명을 가리키면 규칙3개·실제1명이다. 어느 수를 다른 수로 대체해도 화면 설명이 틀린다.
- 수정안: 전체 GET의 배열은 **규칙 그대로** 보존한다. preview의 users는 중복 없는 활성+비활성 목록, totalCount는 활성 사용자 수로 권고 확정하고 `countActiveRecipients`와 문의 흔적을 둔다. totalCount의 계약 문언은 아직 integer뿐임을 명시한다.
- README §2 0단계에서 화면의 「지금 받는 사람」과 비활성 제외/표시를 함께 읽은 해석이다. 목록의 `(규칙 수)`와 preview의 `N명`을 소비자 인계에서 구분하고, users.length나 규칙 수로 수신 가능 인원을 추정하지 않는다.
- 모든 이벤트의 실제 수신 인원/0명 경고는 전체 구독 GET만으로 알 수 없다. 화면이 필요로 하면 해당 규칙으로 preview를 호출한다. 기존 합집합 preview만으로 특정 ROLE의 0명을 구분할 수도 없으므로 개별 규칙 preview가 필요하다. 새 집계 필드를 발명하지 않는다.
- 비활성만 남은 경우 **totalCount=0, users는 비어 있지 않음**이 정상이다. 설정은 지우지 않고 경고하되 저장을 허용한다. 사업부/역할/부서 비활성으로 합성 isActive를 만들지 않는 초안은 유지한다.
- 필수 테스트: `규칙 한 개에 비활성 사용자만 있으면 users는 남고 totalCount는 0이다`, `ROLE 두 개와 USER 한 개가 겹치면 규칙은 3개이고 실제 수신은 1명이다`, `ROLE 단독 preview가 0명이어도 다른 규칙이 있는 합집합 preview와 모두 성공한다`.

### R-UX4 · Minor — openable=false는 알림을 읽을 수 없다는 뜻이 아니다

- 근거: `contracts/app-공통.json:1896`은 항목을 열 때 읽음, `:5034`·`:5039`는 화면 미정 시 생략/원본 코드 표시를 허용한다. W-CO-03 `:147`·`:149`는 읽음과 대상 이동을 별도 액션으로 둔다. 초안 `:338`·`:340`은 둘을 각각만 검증한다.
- 수정안: 화면 대응표가 없어 전건 false인 fallback을 유지하되, **항목 클릭→204→미읽음 목록/배지 재조회**는 정상 작동하도록 인계하고 묶어 검증한다. 알려진 targetTypeCode/targetId는 false여도 남겨 원본 대상 표시에 쓴다.
- W-CO-03 `:161`의 「대상이 더 이상 없습니다」는 삭제·폐기 사실이 확인될 때의 사유다. 화면 원천이 없다는 이유만으로 그 문구를 쓰면 살아 있는 설비도 삭제된 것으로 오인한다.
- enum 밖 과거 유형은 계약 `:5010`에 실을 수 없어 대상 쌍 생략을 유지한다(가장자리·2단계③). 다만 그 **원본 대상 유형을 화면에 보일 수 없는 손실**은 문의에 적는다. eventCode나 message를 변형해 대상 코드로 대신하지 않는다.
- `locationPath` 원천 부재는 생략을 유지한다. 위치 표시 미완과 대상의 부재를 같은 뜻으로 표시하지 않는다. 이 가장자리 때문에 정상 알림 목록 operation 전체를 보류할 근거는 없다.
- 필수 테스트: `대상 화면을 열 수 없는 자기 알림도 읽음 처리되고 미읽음 목록과 배지에서 빠진다`, `알려진 대상의 openable false는 targetTypeCode와 targetId를 보존한다`.

### R-UX5 · Minor — 기간 목록·셸 배지·모두 읽음의 범위와 재전송 뒤 상태를 연결한다

- 근거: `contracts/app-공통.json:1801`은 날짜 끝을 익일00:00으로 보내도록 명시한다. `:1866`은 셸 배지, `:1945`는 모두 읽음 액션이다. W-CO-03 `:163`의 최근1주는 화면 기본값이다. 초안 `:209`·`:219`의 전역 자기 unread/read-all 범위는 맞다.
- 수정안: 하노이 현지의 「그날까지」를 명시적 `+07:00` 익일00:00으로 보낸 사례를 단언한다. 같은 순간의 UTC/다른 offset 입력은 같은 결과이며, `.999`를 포함하고 정확히 to인 행은 제외해야 한다. 서버가 날짜/최근1주를 다시 만들지 않는다.
- 필터로 보이는1건 외에 다른 기간·이벤트의 자기 미읽음2건을 두어 read-all=3임을 고정한다. 셸 배지와 모두 읽음은 필터 전체건수와 다르다. 남의 알림은 제외한다.
- 동일 키 재전송의 readCount는 과거 응답이다. 응답 이후 도착한 새 미읽음은 재조회 시 남아야 하며 화면이 배지를 무조건0으로 만들거나 과거 count를 다시 빼지 않도록 인계한다. 관리웹 온라인 전제와 HTTP 재시도 멱등은 양립한다.
- 필수 테스트: `하노이 날짜 마지막 밀리초를 포함하고 익일 자정은 제외하며 동등한 offset은 같은 목록이다`, `필터 밖 자기 미읽음까지 read-all로 처리하고 남의 알림은 남긴다`, `read-all 응답 유실 재전송 뒤 새 미읽음은 목록과 배지에 남는다`.

## 3. 본길·보류·R 반영 제안

- **R-UX6 / #1 유지**: 계약 `app-공통.json:1980`·`:2004`, W-CO-03 `:193`, W-CO-11 `:205`가 정본 위치 확정과 코드 문자열 미확정을 구분한다. `plan-uiux.md:571`의 발생 훅 제외만으로 설정3건을 열 수는 없다. `:1216`의 코드 검증 불가와 README §2 1단계에 따라 이벤트 GET/구독 GET/PUT 보류를 유지한다.
- 발생 이력0·ROLE에 속한 사람0·받은 알림0은 각각 정상 빈 데이터다. 정본 코드 부재를 빈 이벤트 목록으로 성공 처리하지 않는다. preview는 eventCode가 없어 독립 구현 가능하다. 초안의 +5를 화면 완결로 확대하지 않는다.
- 알림 제목은 계약 `app-공통.json:4989`의 이벤트명 조회가 필요하다. 보류 시 **제목과 유형 선택 목록**이 미완이고, W-CO-11 `:156`·`:157`의 이벤트 선택→규칙 편집/preview도 실제 화면에서는 도달하지 못한다. 알림 발생기 제외도 함께 인계한다.
- `plan-uiux.md:572`의 사용자별 표 유지안은 `plan.md:23`의 이벤트 규칙 신설 결정과 맞지 않으므로 통합자가 정정한다. UIUX는 헤더+규칙의 의미를 지지하며 SQL/동시성 구현 확정은 통합 판정에 맡긴다.
- **R-UX1→조건부④**, **R-UX2→조건부④·⑤**, **R-UX3→③ 및 조건부④·⑤**, **R-UX4·5→①·②**로 테스트를 붙인다. 조회 응답 단언을 마지막 쓰기 PR로 미루지 않는다. 공용 파일은 자신의 등록만 변경한다.
