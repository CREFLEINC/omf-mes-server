## 2. 화면이 요구하는데 계획안에 없는 것

### U-1 ⭐ `P-04-04` ① 「발행 대기 목록」이 이 계획안으로 **한 열도 못 선다**

`P-04-04` §3:40-45 의 목록 4열(**원 포장 · 유형 · 새 포장 · 확정 시각**)과 §5-6:175 「대기 목록 조회 | 항상 — 상태 = 라벨 발행 대기」.

- **목록 자체가 없다.** 재포장 이벤트를 **HU 를 가로질러** 뽑는 오퍼레이션이 0이다 — `GET …/{handlingUnitId}/repack-events` 는 **path 전용**이고 질의 칸이 **0**(실측: 7 path 의 `parameters` 전수 — `GET` 목록만 7칸, 자식 GET 둘은 빈 배열). `GET /inventory/handling-units` 에는 「이벤트가 있는가」 축이 없고, 계획안 §5-5 가 **치환이 `status_code` 를 안 옮긴다**로 못 박아 상태로도 못 거른다. ⇒ POP 이 모바일이 넘긴 것을 **찾을 수 없다**(2단말 스택이 끊긴다 · `M-04-03` §5-1:112).
- **「유형」 열이 언제나 같은 값이다** — 계획안 §5-3 이 `repack_type_code` 를 `'RECONFIGURE'` 고정으로 판정했으므로 「분할/합병」(`P-04-04` §3:43-44)을 구분할 축이 사라진다.
- **「새 포장 n건」 열의 원천이 0이다** — 계획안 §5-3 이 「라인의 `handling_unit_id` 는 **전부 경로의 그 HU**」로 닫았고, 신규 포장은 `P-04-04` 에서 **뒤에** `POST` 로 생기므로(결정 13 · `P-04-04` §5-2) 이벤트가 원 포장↔새 포장을 **영영 못 잇는다**.

⇒ 계획안이 이미 적은 문의 143ⓑ(여러 HU)와 **다른 물음**이다(143 은 요청 모양, 이것은 **조회 축과 2단말 인계**). **문의 145 신설** 권고.

### U-2 중첩 포장의 **하위 조회 축이 0** — `P-01-02`·`P-02-09` 가 파렛트에서 오작동한다

`HandlingUnit` 응답에 `parentHandlingUnitId` 는 있으나(실측) **질의 축에 없고**, 상세 응답도 `{handlingUnit, contents[]}` 뿐이라 **자식 목록이 없다**. 그런데 화면은 계층을 전제한다 — `P-02-08` §5-3:112-116(팔레트→박스) · `P-04-01` §5-2:158-161.
파렛트가 카톤을 담으면 그 파렛트의 `handling_unit_content` 는 **비어 있다** ⇒ `P-01-02` §6:213 「파렛트에 LOT 0건 → ⛔ 차단」이 **정상 파렛트를 막고**, `P-02-09` §5-2:85 「내용물을 읽어 대상 후보를 만든다」가 **0건**이 된다. 계획안 §6-3 은 이 갈래를 안 봤다. **문의 145 에 함께** 싣는다.

### U-3 「빈 포장은 만들지 않는다」인데 **빈 HU 가 번호까지 달고 남는다**

화면 셋이 확정 «전»에 포장번호를 이미 보인다(`P-02-08` §3:38 `HU-2026-0804-0007` · `P-04-01` §3:50 `CTN-2026-0091`) ⇒ 계약 `x-internal-note`(부록 #16)대로 **`POST` 가 먼저 빈 HU 를 만드는 흐름**이다. 그런데 삭제 오퍼레이션이 **0건**(실측 7 path)이고 화면은 「내용물 0 → 확정 **비활성**」(`P-02-08` §6:157 · `P-04-01` §6:253)이라, **스캔만 하고 이탈하면 `OPEN` 고아 HU 가 번호와 함께 영구히 남는다.** 더 나쁜 것은 그 행이 `P-04-01` §5-2-1:172 의 **상위 포장 후보 목록**(`statusCode={포장 가능}` = `OPEN`)에 그대로 섞인다는 점이다. 계획안 §4-1·§10-3 어디에도 없다 → **「알려둘 것」 + 문의 142 에 한 줄**(잘못 확정한 포장뿐 아니라 **못 확정한 포장**도 갈 곳이 없다).

### U-4 `PUT …/contents` **빈 배열 허용**이 화면 둘과 정면으로 어긋난다

계획안 §5-1 은 「계약이 안 막았으니 허용」으로 갔으나, `M-04-03` §5-7:195 「재구성 확정 | 새 구성 유효 **AND 수량 합 = 원 수량 합**」 · §6:204 「수량 합 불일치 ⛔」 · `P-02-08` §6:162 「(재구성은) **수량 합 = 원 수량 합** 제약이 걸려 포장 밖으로 빼지 못한다 — **해체가 아니다**」가 셋 다 반대다. 허용하면 **화면이 닫아 둔 해체 경로가 API 로 열린다**(빈 `PACKED` 포장). 판정을 뒤집지는 않되(계약 문자 그대로가 맞다) ⇒ **§10-3 에 항목으로 올린다** — §5-1 이 「알려둘 것에 남긴다」고 약속했는데 **ⓐ~ⓞ 어디에도 없다**(누락).

### U-5 수량 상한을 **서버가 하나도 안 본다** — 오프라인 큐가 그 방어선을 지난다

화면 예외 둘이 상한을 건다 — `P-02-08` §6:158 「스캔 수량 > LOT 잔여 → 인라인 오류」 · `P-04-01` §6:251 「배분 잔여 초과 ⛔」. 계획안의 400 갈래(§3-3·§4-2·§5-6)에는 `qty > 0` 뿐이다. 원장을 안 지나므로(§3-5) 서버가 잔량을 못 보는 것은 맞으나, `M-04-03` §5-6:182 가 **오프라인 확정을 허용**하고 큐가 나중에 올라오므로 **화면 검증만이 유일한 방어선**이라는 사실이 계획안에 **한 줄도 없다**. → 「알려둘 것」 1건.

## 3. 계획안이 만드는데 화면에 없는 것 / 매핑 오류

- **U-6 `plan-uiux.md:396` 화면 매핑이 틀렸다.** `PUT …/contents` 의 화면을 「M-04-03,**P-04-04**」로 적었으나 `P-04-04` §5-6:173-183 액션 9건에 **구성 편집이 없다**(「구성 편집은 `M-04-03`」 · §1:23). `P-04-04` 가 부르는 것은 **`POST /inventory/handling-units`**(신규 발번 · §5-2:112)다. 계획안 §8-5 표가 그 매핑을 그대로 인용했다(판정 ④ 결론은 그대로 — 둘 다 POP).
- **U-7 `:pack` 소유 화면에 `P-04-01` 이 빠졌다.** `P-04-01` §5-6:240 「**포장 확정** | 내용물 ≥ 1 AND 유형 선택됨」 · §6:257 「낙관적 잠금 충돌 — `handling_unit.version_no`」가 **부모 버전을 올리는 쓰기**를 요구한다. `plan-uiux.md:399` 는 `:pack` 을 `P-02-08` 하나로 적었고 계획안 §8-5 가 그대로 받았다. 어느 쪽이든 POP 이라 400 판정은 안 바뀌지만 **e2e 의 「어느 화면 흐름을 재는가」가 바뀐다**.
- `P-04-01` §5-2-1:178-187 이 「부모 유무로 후보를 거르지 않는다」로 못 박았으므로 **`parentHandlingUnitId` 질의 축을 만들지 않은 것은 ✅ 맞다**(U-2 는 «자식» 축 이야기로 다르다).
- 화면이 물러난 자리(§8) 대조 — `P-02-08` §8-2·`P-04-01` §5-5(단말 게이팅 플래그 부재 → `can_input_result`)는 **서버 몫이 0**이고 `plan-uiux.md` §9 U22 가 이미 받았다. `P-04-01` §8 미결 4(계층 깊이)를 계획안 §4-4 가 「상한 0」으로 받은 것 ✅ 동의 — 화면도 깊이를 앞지르지 말라고 적었다(§5-2-1 ①).
