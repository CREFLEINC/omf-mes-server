### 3-3. 어느 칸을 얼마나

| 함수 | `inventory_balance` | `inventory_reservation` | 하한 검사(400 `NEGATIVE_BALANCE`) |
|---|---|---|---|
| `pick()` **예약 있음** | `reserved_qty −= Δ` · `picked_qty += Δ` · `version_no+1` | `consumed_qty += Δ` · Δ<0 이면 되돌림 | ⓐ Δ>0: `reserved_qty ≥ Δ` ⓑ Δ>0: `reserved_qty − released_qty − consumed_qty ≥ Δ`(`ck_reservation_qty` 를 앞당김) ⓒ Δ<0: `picked_qty ≥ −Δ` |
| `pick()` **예약 없음** | `picked_qty += Δ` · `version_no+1` | — | ⓐ Δ>0: **`available_qty ≥ Δ`**(트리거 갈래 1 을 앞당긴다 — `on_hand` 만 보면 500) ⓑ Δ<0: `picked_qty ≥ −Δ` |
| `consume()` | `picked_qty −= qty` · `version_no+1` | ⛔ **건드리지 않는다** — 예약은 피킹에서 이미 소진됐다(`plan-integration.md` §1-1 ⑦ 「예약 소진」은 피킹 자리다) | `picked_qty ≥ qty` |

- ⭐ **합이 변하지 않는다.** `pick()` 은 `reserved+picked` 를 그대로 두거나(예약 있음) `on_hand` 안에서만 올린다(예약 없음). `consume()` 은 `picked` 를 내리고 `on_hand` 는 `post()` 가 내린다 — 트리거 갈래 1(`on_hand ≥ reserved+picked+blocked`)이 어느 순간에도 깨지지 않는다.
- **한 문장 UPDATE + `RETURNING`** 으로 쓴다 — 조건을 `WHERE` 에 실어 **0행이면 400** 이다(먼저 SELECT 해서 비교하면 잠금 밖의 값을 보고 판정하게 된다). `move()` 가 원시 SQL 을 쓰는 이유(표현식 유일 인덱스)와 같은 이유로 여기도 `$queryRaw` 다.
- `Decimal` 로만 센다(`@db.Decimal(20,6)` · I-3 §3-3 교훈).
- Δ = 0 이면 **아무것도 하지 않는다**(불필요한 `version_no` 증가가 화면의 If-Match 를 낡게 만든다 — I-6 R-29 교훈).

### 3-4. 잠금 — I-4 R-1 의 7칸 오름차순을 그대로 탄다

- 코어 두 함수는 **행을 잠그지 않는다.** 호출자가 `lockBalancesInOrder()`(`balance-lock.ts:39`)로 이미 잠근 행을 UPDATE 한다.
  근거: `post()` 도 같은 규약이고(선잠금 뒤 `move()`), 두 곳에서 잠그면 순서가 갈려 교착 창이 열린다(I-4 R-1 ② · I-5 R-5).
- `:pick` 의 잠금 순서: **`picking_line`(FOR UPDATE) → `inventory_balance`(`lockBalancesInOrder`) → `inventory_reservation`(FOR UPDATE)**.
  한 라인이라 잔액 행은 하나이고, 예약 행은 그 뒤라 출고 경로(잔액만 잡는다)와 순환이 생기지 않는다.
- ⭐ **`consume()` 은 예약 행을 안 잡는다** — 그래서 출고 경로에는 예약 잠금이 없고, `:pick`(예약 뒤)과 `:post`(예약 없음) 사이에 교착이 성립하지 않는다.

### 3-5. ⭐ `consume()` 은 `post()` «안»이 아니라 `issue-posting.ts` 가 **손검사 «앞»**에서 부른다

**이것이 이 슬라이스에서 순서를 틀리면 정상 출고가 400 이 되는 자리다.**

`available_qty = on_hand − reserved − **picked** − blocked` 이므로, 피킹된 재고는 **가용에서 이미 빠져 있다**.
I-4 의 손검사(`issue-posting.ts:120-135`)는 `available_qty ≥ Σ issueQty` 를 보므로, 그대로 두면
**피킹을 마친 정상 출고가 언제나 400 `NEGATIVE_BALANCE`** 다(I-4 §7-2 가 「예약된 재고는 I-4 경로로 안 나간다 — `picked_qty` 로 옮긴 뒤에야 나간다」라 적은 문장의 실체).

| 갈래 | 판정 |
|---|---|
| ⓐ `post()` 안에서 돈다 | ⛔ **기각.** `post()` 는 입고·이동·조정이 함께 쓰는 «원장» 함수이고 피킹 라인을 모른다. 알게 하려면 `PostingInput` 에 피킹 축을 더해야 하는데 **새 개념 하나**(§2 2단계 기준 5) |
| ⓑ 손검사 «뒤», `post()` 앞 | ⛔ **기각.** 손검사가 이미 400 을 낸 뒤다 |
| ⓒ **잠금 뒤 · 0행/2행+ 판정 뒤 · 손검사 «앞»** | ⭕ **채택** |

**`postIssue()` 의 새 순서**(굵은 것이 I-8 이 더하는 줄):

```
assertLotNotBlocked                                   (그대로)
fromKeys/toKeys → lockBalances(7칸 한 문장, id 오름차순)  (그대로)
키별 0행/2행+ 판정 → row 확정                            (그대로)
⭐ picking_line_id 가 있는 라인 → posting.consume(tx, [{dimension: row 11칸, qty: issueQty}])
⭐ 손검사식을 `row.available_qty.plus(그 키에서 consume 한 합) ≥ Σ issueQty` 로 바꾼다
posting.post(...)                                     (그대로)
되짚기 UPDATE                                          (그대로)
```

- `available_qty` 는 생성 컬럼이라 **UPDATE 뒤에 다시 읽어야** 새 값이 나온다. 되읽기(왕복 +1) 대신 **우리가 방금 내린 양을 더한다** — 같은 트랜잭션에서 우리가 쓴 값이고 행은 잠겨 있다. 흔적 주석 한 줄.
- `consume()` 이 쓰는 11칸은 **잠근 그 행**의 것이다(품질·재고·소유 3칸은 계약이 안 싣는다 — I-4 §3-2 문의 031 과 같은 자리).
- ⚠ **피킹이 올린 행과 출고가 내리는 행이 다르면** `consume()` 이 `picked_qty ≥ qty` 에서 400 이다. 그것이 옳다 — 다른 위치의 피킹분을 여기서 소진할 수 없다. 흔적 주석 + 단위 테스트.
- ⛔ `material_issue_request_line.issued_qty` 는 여기서 **올리지 않는다** — 어느 요청 라인인지가 (요청, 품목)만으로는 유일하지 않다(같은 품목이 두 라인일 수 있다). 값을 조용히 도출하지 않는다(기준 4) → 문의 **046**.

### 3-6. `reverse()` — 소진된 피킹을 **되돌리지 않는다**

`reverse()`(`:105~`)는 원 라인의 `from`/`to` 를 맞바꿔 `on_hand` 만 되돌린다. `picked_qty` 는 건드리지 않는다.
⇒ 출고를 취소하면 **`on_hand` 는 돌아오고 `picked_qty` 는 돌아오지 않는다**(피킹 자체가 취소된 것이 아니므로 그것이 사실에 가깝다).
⚠ 다만 `picking_line.picked_qty` 는 남아 있고 재출고 경로가 `consume()` 을 다시 부르면 **두 번째 `consume()` 이 400** 이다.
§2 1단계: 취소된 피킹 출고를 다시 내보내는 갈래에서만 갈린다 → **가장자리** → 2단계 기준 1(재고·상태를 안 쓰는 쪽) ⇒ **`reverse()` 를 고치지 않는다**(코어 무변경).
⇒ 「알려둘 것」 + I-5 축 인계 한 줄. `reverse()` 파일을 안 여는 것이 「원장 코어를 고치는 두 슬라이스」 경고(`plan-integration.md` §6-2)를 피하는 길이기도 하다.

### 3-7. `reserve()` 를 **이 슬라이스에서 만들지 않는다**

- 계약은 ⌜출고요청 생성 시 걸리는 예약분⌝ 이라 적었으나, **어느 잔액 행에 거는지**(창고·위치·LOT·품질·재고·소유 6축)를 정할 근거가 어디에도 없다 — `material_issue_request` 는 «도착» 위치만 갖고 출발 창고를 모른다(§5-2).
- 사용처가 **0** 이면 CLAUDE.md 「사용처 하나뿐인 추상화 금지」에 정면으로 걸린다.
- 04 계약 실측이 첫 사용처를 준다 — `POST /logistics/shipment-requests/{id}/lines/{lid}:pick` ⌜⭐ 화면이 예약을 직접 쓰지 않는다 — **서버가 이 피킹의 결과로 `inventory_reservation` 을 걸고 푼다**(01 자재창고 계약 · `M-01-08` §5-5 와 같은 규약)⌝.
⇒ **`reserve()` 는 I-22 가 만든다.** `pick()`·`consume()` 의 시그니처를 이 슬라이스가 고정하고 인계한다(§9-4).

### 3-8. 「도메인이 `inventory_balance` 를 직접 UPDATE 하지 않는다」 감지 수단 — **트리거가 없다**

`plan.md` 106행이 「e2e 감지」라 적고 `plan-integration.md` §9 반박 2 가 「잔액 UPDATE 트리거로 감지」라 적었다.

⇒ §2 1단계 가장자리 · 2단계 기준 3(스키마를 안 늘리는 쪽) ⇒ **트리거를 만들지 않고 «정적 가드»를 둔다.**

### 6-2. 잔액 차원을 어디서 얻나

`// 예약을 거는 자리가 서버에 없어 오늘은 언제나 NULL 이다 — 문의 045(I-8.md §5)`.

### 6-4. 누적인가 대체인가 — **대체**

- 근거(0단계): `PickingLinePick.pickedQty` 의 `x-source-column` 이 **`picked_qty`** 이고, 200 응답이 같은 칸을 그대로 내리는 `PickingLine` 이다.
- 재전송은 멱등키가 흡수한다. **다른 값으로 다시 부르면 정정**이다(현장이 수량을 잘못 눌렀을 때의 유일한 정정 경로 — 계약에 `:unpick` 이 없다).
- Δ<0(줄이는 정정)은 ①의 잠금과 ③(이미 출고된 라인 400)이 지킨다 — 출고가 이미 `consume()` 한 뒤에는 못 줄인다.
- **부분 피킹은 허용된다** — `ck_picking_qty (picked_qty <= planned_qty)` 만 있고 하한이 없다. `M-01-08` §5-7 ⌜부분 출고로 처리하고 부족분을 남긴다⌝.

### 7-2. BOM 축 — **`production_plan.bom_id` 하나**로 간다

⇒ **`work_order → production_plan.bom_id`(NOT NULL) + 그 `bom.base_qty`.** 흔적 주석 + 「알려둘 것」 ⓓ(배포 뒤 계획의 BOM 이 바뀌면 shortage 가 선발행 스냅샷과 갈린다 — 계획의 BOM 을 바꾸는 오퍼레이션이 있는지는 I-24 가 안다).

### 7-4. 기출고 축 — `goods_issue_line`

계약 `issuedQty` ⌜**이 W/O 앞으로 출고된 수량의 합**⌝ 이 축을 말한다.

```sql
goods_issue_line gil
  JOIN goods_issue gi   ON gi.goods_issue_id = gil.goods_issue_id AND gi.status_code = 'POSTED'
  JOIN picking_line pl  ON pl.picking_line_id = gil.picking_line_id
  JOIN picking_order po ON po.picking_order_id = pl.picking_order_id
                       AND po.source_document_type_code = 'MATERIAL_ISSUE_REQUEST'
  JOIN material_issue_request mir ON mir.material_issue_request_id = po.source_document_id
 WHERE mir.work_order_id = ?
 GROUP BY gil.item_id
```
- `status_code='POSTED'` 만 — 취소된 출고는 세지 않는다(`CANCELLED` 는 원장이 되돌려졌다).

- `workOrderId` 없으면 400 `REQUIRED` · 없는 W/O 면 400 `INVALID`(계약이 404 를 선언하지 않았다).
