### 3-2. ⭐ 부호 → `from`/`to` 가름 — 「증/감이 한 트랜잭션에 섞인다」

`inventory_adjustment_line.adjustment_qty Decimal(20,6)` 은 **부호를 갖는다**(계약 ⌜증감 수량. 음수가 올 수 있다⌝ · example `−2.0`). 원장 라인은 **`qty > 0` CHECK**(DB 실측 `inventory_transaction_line_qty_check`)이고 방향은 `from`/`to` 가 말한다(`posting.types.ts:14-17` ⌜없으면 입고 / 없으면 출고⌝).

| 라인 | `PostingLine` |
|---|---|
| `adjustment_qty < 0`(감) | `qty = -adjustment_qty` · **`from` 만**(그 위치) · `to` 없음 |
| `adjustment_qty > 0`(증) | `qty = adjustment_qty` · **`to` 만**(그 위치) · `from` 없음 |
| `= 0` | ⛔ 도달 불가 — CHECK `adjustment_qty <> 0` 과 등록·치환의 400 이 앞서 막는다 |

- ⭐ **한 트랜잭션에 `from` 만 라인과 `to` 만 라인이 섞인다** — `writeLine()`(`inventory-posting.service.ts:174-204`)이 라인마다 독립으로 판단하므로 코어 무변경이다. `ck_inventory_transaction_direction (from_location_id IS NOT NULL OR to_location_id IS NOT NULL)` 도 둘 다 지난다.
- ⭐ **`lot_id` 가 nullable 이다** — I-4 는 `goods_issue_line.lot_id` 가 NOT NULL 이라 「LOT 없는 재고는 출고할 길이 없다」였다(I-4 §8 ⓒ). 조정은 그 길이 **있다**: `PostingLine.lotId` 를 `undefined` 로 두고 잔액 키는 `COALESCE(lot_id,0)` 로 잠근다(`balance-lock.ts:53` 이 이미 `lotId` 를 따로 내린다). ⇒ M-01-08 §8 #3 이 「조정」으로 남긴 자리가 **여기서 실제로 열린다**. 「알려둘 것」.
- ⛔ **부분 역분개를 만들지 않는다** — 조정을 되돌리는 오퍼레이션이 계약에 0건이다(§13 ⓒ · 문의 132).

### 3-3. ⭐ 잔액 차원 두 칸(+소유 축)의 원천 — **라인이 «저장한» 값을 쓴다**

`PostingEndpoint` 는 `{warehouseId, locationId, qualityStatusCode, inventoryStatusCode}` 4칸이고 `PostingLine.ownershipTypeCode` 는 **required** 다(`posting.types.ts:2-19`). 계약 조정 라인은 셋 다 **안 싣는다**.

**§2 판정** — 0단계 선례 둘이 갈린다:
- 입고는 **계약이 싣는다**(`GoodsReceiptLine.qualityStatusCode` — `receipt-posting.ts:552-553`이 본문 값을 그대로 넣는다).
- 출고·적치는 **잠근 잔액 행에서 되읽는다**(`issue-posting.ts:193-195` ⌜계약이 안 싣는 두 칸이라 «잠근 잔액 행»에서 되읽는다(문의 031)⌝ · `putaway-posting.ts:1190-1194`).

조정은 계약이 안 실으므로 **되읽기 쪽**이다. 그런데 물리 라인이 두 칸을 **NOT NULL 로 요구**하고 라인은 **등록·치환 시점에 INSERT** 된다 — 전기보다 훨씬 앞이다. 1단계: 모든 등록이 이 칸을 채워야 하므로 **본길**. 계약이 침묵하므로 권고안 + 문의(README §0).

⇒ **판정: 등록·치환이 잔액 행을 읽어 라인에 «저장»하고, `:post` 는 그 저장값을 그대로 싣는다.**

| 상황(등록·치환 시점 · 7칸 키로 조회) | 값 | 오류 |
|---|---|---|
| 1행 | 그 행의 `quality_status_code`·`inventory_status_code`·`ownership_type_code`(+`owner_partner_id`) | — |
| 2행 이상 | — | **400 `INVALID`**(field `lines[i].locationId`) 「재고 차원이 둘 이상이라 어느 것을 조정할지 정할 수 없습니다」 — I-4 `issue-posting.ts:133-139` 와 **같은 문구·같은 코드** |
| 0행 · 감(−) | — | **400 `NEGATIVE_BALANCE`** 「이 위치에 그 LOT 의 재고가 없습니다」 — `issue-posting.ts:127-131` 그대로 |
| 0행 · 증(+) | — | **400 `INVALID`** 「이 위치에 그 품목의 재고가 없어 어느 상태로 넣을지 정할 수 없습니다」 |

근거: §2 2단계 **기준 4**(값을 조용히 도출하지 않는 쪽 — `QUALITY_STATUS` 코드 그룹이 **DB 에 없어**(§1-5) 상수를 지어낼 근거가 0이다) + **기준 2**(거부하는 쪽 — 거부→허용은 호환 완화다).
⚠ **이 판정이 「빈 위치에 재고를 만드는 조정」을 막는다.** 화면 `W-01-12` §3 목업은 「장부 200 · 실물 180 · 차이 −20」처럼 **장부 행이 이미 있는** 경우만 그린다(실사·호퍼 실측 둘 다 그렇다). 그래도 되돌릴 값을 정하려면 설계 답이 필요하다 ⇒ **문의 130**.
⚠ **소유 축(`ownership_type_code`·`owner_partner_id`)은 라인에 «저장할 칸이 없다»** — 위 조회로 두 칸을 얻지만 라인에는 품질·재고 상태 둘만 저장하고, 소유 축은 **`:post` 가 잠근 잔액 행에서 다시 읽는다**(I-4 `issue-posting.ts:209-210` 과 같다). 잠금 뒤 값이므로 안전하다.
⚠ **전기 시점에 라인 저장값과 잔액 행의 두 칸이 달라졌다면?** 라인 저장값이 이긴다 — 「승인자가 본 것」이 원장에 나가야 한다(I-4 `assertNotApproved`(`goods-issue-update.service.ts:242-258`)가 같은 결로 승인 뒤 치환을 막는다). 그때 그 차원 행이 없으면 `move()` 의 `INSERT … ON CONFLICT DO NOTHING`(`inventory-posting.service.ts:269-282`)이 증(+)은 만들고, 감(−)은 §3-4 손검사가 400 으로 막는다.

### 3-4. 잔액 잠금과 손검사 — **I-4 R-1 을 그대로 · 음수재고만 갈린다**

```
잠금: (legal_entity_id, business_unit_id, plant_id, warehouse_id, location_id, item_id,
       COALESCE(lot_id,0)) IN (VALUES …) ORDER BY inventory_balance_id FOR UPDATE
```
- ⭐ **7칸 행생성자 한 문장**(I-4 R-1 ① · `balance-lock.ts:41-61` 의 `lockBalancesInOrder` 를 **그대로 부른다** — 조정은 `from`/`to` 가 한쪽뿐이라 I-4 처럼 두 벌을 합칠 일이 없다).
- ⭐ **키별 합산** — 같은 (위치·품목·LOT) 라인이 둘이면 라인별 검사가 둘 다 통과하고 둘째 UPDATE 가 트리거 500 이다(I-4 R-1 ③). 감(−)의 **합**으로 본다.
- ⛔ `posting.post()` 가 **자기도** `lockBalancesInOrder` 를 부른다(`:69`) — 같은 순서라 교착이 없다(I-5 R-5 가 같은 이유로 순서를 맞췄다).

**음수재고 3갈래** — ⭐ **I-4 와 갈리는 자리다.** `check_balance_qty()` 원문(DB 실측):

```
IF NEW.on_hand_qty >= 0 THEN
    IF NEW.on_hand_qty < reserved+picked+blocked THEN 예외
ELSE
    item.negative_stock_allowed 가 거짓이면 예외
    reserved+picked+blocked > 0 이면 예외
```

I-4 는 `negative_stock_allowed` 를 **무시**했다 — 계약 `GoodsIssueLineUpsert.issueQty` 가 「보유 수량 이하」로 **예외 없이 닫았기** 때문이다(`issue-posting.ts:155-156`). 조정 계약 `adjustmentQty` 에는 **그 문장이 없고**, 화면 `W-01-12` §6 이 ⌜**음수 재고가 되는 조정** — `item.negative_stock_allowed` 참이면 허용 · 거짓이면 트리거가 막는다⌝로 **직접 인정**한다. ⇒ §2 **0단계**(화면 확정문) — 트리거 세 갈래를 그대로 손검사로 앞당긴다.

| 조건(키별 · `after = on_hand − Σ감 + Σ증`) | 판정 |
|---|---|
| `after >= 0` 이고 `after < reserved + picked + blocked` | **400 `NEGATIVE_BALANCE`**(field `lines[i].adjustmentQty`) |
| `after < 0` 이고 `item.negative_stock_allowed = false` | **400 `NEGATIVE_BALANCE`** |
| `after < 0` 이고 `reserved + picked + blocked > 0` | **400 `NEGATIVE_BALANCE`** |

⛔ 트리거 위반은 `PrismaClientUnknownRequestError` 라 공용 그물에 안 걸려 **500 으로 샌다**(`prisma-error.ts` 머리 주석 · I-4 `goods-issue-rules.ts:91-92` 가 같은 이유로 손검사를 앞당겼다) — 그래서 세 갈래를 다 앞당긴다.

### 3-7. ⭐ 승인 완료 판정 — **다형 축으로 조회한다**

`plan.md` §5 규칙 **12** 원문: ⌜문서의 `approval_request_id` FK 는 **업무 승인 하나만**(`PURCHASE_ORDER`·`GOODS_ISSUE_DISPOSAL`·**`INVENTORY_ADJUSTMENT`**). … 승인 판정은 **언제나 다형 축**(`approval_request.(target_type_code, target_id, approval_type_code)`)으로 조회한다.⌝

### 3-8. 멱등 · 재전기 · 상태 · `adjusted_at`

- 컨트롤러 `runIdempotent(…, HttpStatus.OK, …)` ⇒ 같은 `Idempotency-Key` 재전송은 work() 자체가 안 돈다(`master-write.ts`).
- 다른 키로 재전기하면 ⑤ 가 400 `STATE_LOCKED`(`POSTED` 는 `from` 밖).
- 그래도 새어 들어오면 `posting.post()` 의 `uq_inventory_idempotency(idempotency_key, business_date)` 가 흡수하고 §3-5 의 `alreadyPosted` throw 가 잡는다. ⚠ **영업일이 다르면 흡수가 안 된다** — 상태 잠금만 남는다(I-4 R-2 와 같은 자리).
- **`adjusted_at = occurredAt`**(본문 값) — 계약 ⌜전기된 시각⌝ · 화면 §4-A ⌜**승인 후 전기 시점**⌝. ⛔ 서버 `now()` 를 지어 넣지 않는다(C-1 · 기준 4). 목록 필터 `adjustedAtFrom/To` 가 이 칸을 본다.
- `version_no` 는 **올린다**(상태를 옮기므로). 응답에 ETag 가 없어 다음 토큰은 상세 GET 이 준다(I-4 §6-3 과 같다).

### 3-9. `:post` 400·404·409 갈래 — 순서가 판정이다

`400 INVALID`(① 본문 형식 · **tx 밖이라 맨 앞**) → `404`(③) → `409`(④ If-Match) → `400 STATE_LOCKED`(⑤) → `400 APPROVAL_*`(⑥) → `400 LINE_REQUIRED`(⑦) → `400 INVALID`(⑧ 공장 둘) → `400 NEGATIVE_BALANCE`/`INVALID`(⑨).
⚠ ① 이 tx 밖이라 **「없는 전표 + 잘못된 businessDate」는 404 가 아니라 400** 이다. ⛔ 고치지 않는다 — I-4 와 같은 형상이고 e2e 이름으로 못 박는다(§10-3).

### 4-2. 순서와 갈래

1. `findUnique` 로 존재·상태 확인 — 없으면 **404**(계약 미선언이나 낸다) · `REGISTERED` 아니면 **400 `STATE_LOCKED`**(채번 «전»에 한 번 거른다 — 되풀이 상신이 AP 번호만 비운다 · `:179-180`).
2. 채번 `APPROVAL_REQUEST`(tx 밖 · `plantId=null` · 기간 키 = 서버 UTC 오늘).
3. tx: `lockHeader`(FOR UPDATE) → `version_no` 대조(**409**) → `REGISTERED` 재검사(**400 `STATE_LOCKED`**) → `approvals.request(...)` → FK 채움 → **202 `{approvalRequestId}`**.
4. 갈래: 결재선 0건·단계 0건 → **400 `ROUTE_NOT_FOUND`**(계약이 코드 이름을 직접 적었다) · 활성 결재선 둘 → 400 `ROUTE_AMBIGUOUS` · `PENDING` 이미 있음 → 400 `APPROVAL_IN_PROGRESS` · 반려 뒤 재상신은 **새 요청이 선다**(공유계약 J-6 · 계약 description 이 직접 적었다).

⛔ **상태를 «안 옮긴다»** — `plan-api.md:755` 마지막 줄 ⌜`:request-approval`(P/O·출고·**조정**) — **상태를 옮기지 않는다**⌝. 승인 진행은 `approval_request.status_code` 가 진다.
⛔ **`version_no` 를 «안 올린다»** — 202 에 ETag 가 없어 화면이 새 토큰을 받을 길이 없다. 올리면 다음 쓰기가 상세 GET 을 다시 돌 때까지 영원히 409 다(I-4 §6-3). ⛔ 그래도 «읽고 비교는» 한다 — 안 그러면 계약이 선언한 409 가 도달 불가능해진다.
⚠ 버전을 안 올리니 낙관적 잠금이 동시 상신을 못 가른다 — tx 첫 문장의 `FOR UPDATE` 가 그 자리다(I-2 R-4).

## 6. `PUT …/{id}/lines`(치환) — I-4 의 복제 + **ETag 하나가 다르다**

### 6-1. 전량 교체 의미

「요청에서 빠진 기존 행은 삭제한다」 · `inventoryAdjustmentLineId` 가 없으면 신규 행(계약 ⌜없으면 신규 행⌝). `goods-issue-update.service.ts:50-154` `replaceLines()` 를 그대로 복제한다.

### 6-2. `line_no` 재부여

### 6-3. 어느 상태까지 허용하나

| 잠금 | 판정 | 근거 |
|---|---|---|
| `status_code !== 'REGISTERED'` | **400 `STATE_LOCKED`** | 계약 ⌜**전기된 조정은 바꿀 수 없다** — 400 STATE_LOCKED⌝(description + `InventoryAdjustmentLineUpsert`) |
| `PENDING` 승인 요청 있음 | **400 `APPROVAL_IN_PROGRESS`** | `assertNoOpenRequest`(`approval.service.ts:102-120`) — 승인자가 본 것과 전기되는 것이 달라진다. 원장은 되돌릴 수 없다(⭐ 조정은 **취소 경로가 아예 없다** — §13 ⓒ · I-4 보다 더 강한 이유다) |
| `APPROVED` 요청 있음 | **400 `STATE_LOCKED`** | `assertNotApproved`(`goods-issue-update.service.ts:242-258`) — `assertApproved` 는 시각 순서를 안 봐 승인 뒤 바꾼 라인이 원장에 나간다 |

⭐ 화면 `W-01-12` §5-2 가 남긴 ⌜승인자가 무엇을 승인하는지 볼 수 없다⌝ 는 라인 표가 서면서 **해소된다**(화면 §8 #1 ✅). 위 두 잠금이 그 해소를 지킨다.

### 6-4. ⭐ `version_no` 와 ETag — **I-4 와 갈리는 한 자리**

계약 `PUT …/lines` 200 의 ETag 설명 원문: ⌜… **라인을 고치면 이 헤더의 값이 오르므로 다음 상태 전이(`:request-approval`·`:post`)는 이 값을 쓴다 — 상세 GET 을 다시 돌지 않는다.**⌝
⇒ ① 부모 `version_no` 를 **올린다**(`updateMany where version_no = $ifMatch` + `assertUpdated`) ② 새 값을 **`setEtag(response, version + 1)`** 로 내린다 ③ 본문은 `{items[]}`(`InventoryAdjustmentLineListResponse`).
⛔ I-4 는 같은 자리에 헤더가 미선언이라 안 내렸다(`goods-issue.controller.ts:107-111`) — **베끼면 빠뜨리는 자리다.**
⛔ `runVersioned` 를 쓰지 않는다 — 응답 본문이 자원 하나가 아니라 컬렉션이다. 컨트롤러가 `versionOf(request)`(`goods-issue.controller.ts:148-154`)로 가드가 파싱해 둔 값을 꺼내고 서비스가 «비교만» 한다.

### 6-5. 라인 두 상태 칸

치환도 등록과 **같은 헬퍼**로 잔액 차원을 다시 읽어 저장한다(§3-3). ⇒ `inventory-adjustment-rules.ts` 의 `resolveLineDimensions()` 하나를 등록·치환이 나눠 쓴다(I-4 `lineTargetErrors` 가 `'lines' | 'items'` 를 인자로 받은 것과 같은 모양 — 계약 본문 칸 이름이 다르다: 등록 `lines` · 치환 `items`).

### 10-5. 단위 테스트 — **9**

`adjustment-posting.ts`(순수 조립): ① 감(−) → `from` 만·`qty` 절댓값 ② 증(+) → `to` 만 ③ 증·감 혼재 배열의 라인 순서 보존 ④ `lotId` 널이면 `PostingLine.lotId` 를 **키에서 생략**한다 ⑤ `idempotencyKey` 가 `INVENTORY_ADJUSTMENT:{번호}` 다.

### 10-6. 전기 뒤 `inventory_balance` 기대값
