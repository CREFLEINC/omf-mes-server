## 1. 문의 032·033·034 가 새 문의인가 ✏

- **032 ✅ 유효 · 물음의 방향을 고친다.** 화면 실측 — **취소 다이얼로그에 영업일 입력 칸이 어느 쪽에도 없다**: `W-01-13` §7 DS 매핑 ⌜취소 요청 사유 | `Dialog` + `TextArea`⌝ 하나뿐이고, `W-04-12` §7(284행)도 글자 그대로 같다. 즉 04 의 `ShipmentCancel.businessDate` required 도 **사람이 넣는 값이 아니라 클라이언트가 원 문서에서 파생하는 값**이다 ⇒ I-5 §3-4 ⓐ(원 트랜잭션의 `business_date`)와 **같은 값**을 서버가 대신 읽는 것이다. C-8·026 과 겹치지 않는다(C-8 은 「서버가 수신 시각으로 다시 잡지 마라」이고 ⓐ 가 그것을 지킨다). ⇒ 문의는 「누가 옳은가」가 아니라 **「01 에 칸을 더할 것인가 / 04 의 required 를 서버 파생으로 낮출 것인가」** 로 적는다. §8 I-23 인계(두 자리를 한 번에 맞춘다)는 그대로 옳다.
- **033 ✏ 두 겹을 갈라야 한다.** ⓐ **결정 «전» 철회**(`W-01-13` §5-7 「취소 요청 철회」)는 **새 문의가 아니다** — `W-04-10` §5-7 ⌜품의 취소 ⛔ 두지 않는다 — **상신 철회 경로가 승인 계약에 없다**(01 요구서 §5-3)⌝ + 같은 스펙 §8 미결 5 「상신 철회 경로 없음 · 승인 계약 보강」이 **이미 열린 건**이다. W-01-13 §5-7 을 그 건의 **둘째 사용처**로 덧붙이는 것이 맞다(어느 쪽에 묻나 = 설계팀의 승인 계약 축). ⓑ **반려 «뒤» 복귀는 새 자리다** — `W-CO-09` §5-5 가 ⌜반려된 요청을 상신자가 고치려면⌝ · J-6 ⌜번복은 **새 요청**⌝ 으로 **재상신을 전제**하는데, I-5 §4-4 순위 3(상태 `CANCEL_REQUESTED` **또는** 열린 요청)이 재상신을 **영구히** 막는다. 화면 전제와 정면 충돌이다. ⇒ **033 은 ⓑ 로 좁혀 올린다**(제목에서 「철회」를 빼고 인용만 한다).
- **034 ⛔ 문의가 아니라 물리 정정이다.** README §5 명문 ⌜물리 모델과 계약이 다르면 **물리를 고친다**⌝. 화면·계약 어디에도 취소 사유 «코드» 축이 없다(다이얼로그는 `TextArea` 하나 · 목록에 사유 열 없음 · `ApprovalRequestCreate` 는 `reason` 1칸 `minLength:1`). 그리고 상수 `'OTHER'` 는 **나중에 「취소 사유별 집계」가 서면 전건 오염**이다 — 설계가 같은 함정을 이미 세 번 기록했다(`W-04-05` §8-1 `expediteReason` · `M-04-04` §8-1 · 공유계약 `I-41` 「자유 텍스트라 **집계가 안 된다**」). ⇒ **`document_cancellation.reason_code` 를 nullable 로 낮추고(선행 마이그 1건) `reason_detail` 만 채운다**가 화면 관점의 답이다. ⚠ 이것이 서면 §0 조건 ①(마이그레이션)이 **✕ → ⭕** 로 뒤집힌다 — §2 참조.
- **「알려둘 것」 12건 중 문의로 올릴 것 2건**: **ⓚ**(출고 후속이 실측상 언제나 0)는 **P0 요구 FR-IM-078**「아직 인수하지 않았거나 **사용하지 않은** 출고 건」을 서버가 「언제나 취소 가능」으로 답한다는 뜻이라 통지 수준이 아니다. **ⓛ**(P/O 후속 미집계)은 목록 「후속」 열이 P/O 에서 **항상 「없음」**이라 FR-IM-086 진행현황 열이 거짓을 말한다. 둘 다 화면 열의 의미가 바뀌는 자리다.
- §9-1 판정표의 §2 절차 적용: #4 는 위 034 로 재판정 · #8(5값 우선순위)을 「1단계 가장자리」로 본 것은 §4 판정 U-5(아래) 때문에 **본길에 걸친다**. 나머지 18건의 절차 적용은 화면 관점에서 어긋남 없다.

- 화면이 보는 것은 `CancelResult` 의 `reversalTransactionNo`·`reversalBusinessDate` 둘과 §5-7 액션 **「원장 보기」**뿐이다. §3-4(원 영업일)·§3-5(`{원 번호}-R`)가 그 두 칸을 채워 **원장 조회 키(번호+영업일)가 성립**한다 — 원장 PK 가 `(id, business_date)` 라 영업일 없이는 「원장 보기」가 못 선다. ✅
