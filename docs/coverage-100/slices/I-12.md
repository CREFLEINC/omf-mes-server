### 1-1. 횡단 4축 — 실측(python · `contracts/logistics-01자재창고.json`)

## 3. ⭐ `POST …/{putawayTaskId}:complete` — 이 슬라이스의 심장

### 3-1. 한 트랜잭션 순서

```
[tx 밖]  ① X-Worker-No 부재/공백 검사 → 400 REQUIRED                          (§7-4)
         ② 사번 존재 확인(mdm.worker.worker_no) → 400 INVALID · ⛔ 저장하지 않는다 (§9-1 #4)
         ③ 본문 형식은 계약 가드가 본다(required 3 · date · date-time · int64)
[tx 안 · 컨트롤러의 runIdempotent 가 연 트랜잭션과 «다른» 트랜잭션 — 입고 선례]
         1  SELECT … FROM logistics.putaway_task WHERE putaway_task_id = ? FOR UPDATE   → 없으면 404
         2  If-Match 가 있으면 version_no 대조                                  → 409 ConflictResponse
         3  assertTransition('logistics.putaway_task.status_code',
                             'putaway-complete', status_code, 400)             → 400 STATE_LOCKED  (§6)
         4  goods_receipt_line → goods_receipt 를 되읽는다
              (plant_id · warehouse_id · status_code · line.inventory_transaction_line_id)
         5  취소된 입고 검사: goods_receipt.status_code ∈ {CANCEL_REQUESTED, CANCELLED}
                                                                                → 400 STATE_LOCKED  (§3-8)
         6  actualLocationId 그물: mdm.location 존재 · is_active · warehouse_id = 목적 창고
                                                                                → 400 INVALID       (§3-3)
         7  ⭐ 권장 판정 2×2                                                     → 400              (§3-4)
         8  입고 원장 라인 되읽기 — inventory_transaction_line 의 to_* 4칸 +
              ownership_type_code · owner_partner_id · handling_unit_id         → 없으면 400 STATE_LOCKED
         9  posting.post(tx, { … from = ⑧ 복제 · to = actual_location · qty = task_qty })
                                                                                → 400 NEGATIVE_BALANCE (§3-7)
        10  UPDATE putaway_task SET actual_location_id · status_code='COMPLETED'
              · completed_at = occurredAt · inventory_transaction_line_id
              · version_no = version_no + 1 · updated_by                        (§3-9)
        11  같은 tx 에서 되읽어 PutawayTask 를 만든다                           → 200 (ETag 없음)
⛔ 없는 단계: 채번(§3-6 ⓒ) · 권장 위치 재계산(§Z-11) · 혼적·수용량 검사(§9-1 #6)
              · location_type_code 검사 · lot 상태 검사 · 알림 적재
```

- ⭐ **`runIdempotent` 안에서 서비스가 자기 `$transaction` 을 다시 연다** — 입고(`goods-receipt.service.ts:110-112`)·I-10 §3-1 과 같은 형상이고, 요청당 동시 커넥션은 2다. 새로 만드는 규약이 아니다.
- ⑤⑥⑦ 을 ⑨ «앞»에 두는 이유는 I-5 §6-4 와 같다 — 원장을 쌓기 전에 업무 거부를 끝낸다(400 이면 상태도 안 옮긴다).
- ⑧ 을 ⑨ 앞에 두는 이유: `from` 끝점 4칸을 «지어내면» 입고가 세운 잔액 행과 다른 차원을 깎아 400 `NEGATIVE_BALANCE` 가 난다. **복제만이 안전하다.**

### 3-2. `FOR UPDATE` 를 «건다» — I-10 과 갈리는 지점

I-10 은 `FOR UPDATE` 를 안 걸었다(INSERT 만 하고 판정 대상 행이 없었다). 여기는 **읽고 판정하고 그 행을 UPDATE 한다** — 두 요청이 같은 지시를 동시에 완료하면 상태기계가 옛 값을 본다. 선례는 `lot-complete.service.ts:117-124`(`lockLot`). 잠금 순서는 `putaway_task` 한 행 → `post()` 안의 잔액 행(코어가 id 오름차순으로 한 번에 잠근다 · `balance-lock.ts`)이라 **교착 창이 없다**(다른 도메인이 `putaway_task` 를 잠그는 자리가 0건 — grep 실측).

### 3-3. `actualLocationId` 그물 — 세 검사

### 3-5. 원장 라인의 두 끝점 — ⓓ

```
from  ← 입고 원장 라인의 to_* 를 «그대로» 복제
        goods_receipt_line.inventory_transaction_line_id
          → inventory_transaction_line.{to_warehouse_id, to_location_id,
                                        to_quality_status_code, to_inventory_status_code}
          + {ownership_type_code, owner_partner_id?, handling_unit_id?}
to    ← { warehouseId: location.warehouse_id(= goods_receipt.warehouse_id · §3-3 셋째 검사),

          qualityStatusCode  : from 과 «같은» 값,
          inventoryStatusCode: from 과 «같은» 값 }
qty   ← putaway_task.task_qty     (라인 1건 · 분산 적치는 이 슬라이스 밖 · §9-1 #9)
```
- `from_location_id` 는 `putaway_task.from_location_id`(= 입고 라인의 `destination_location_id`)와 **같아야 한다** — 다르면 입고가 세운 잔액이 아닌 곳을 깎는다. 되읽은 값과 대조해 어긋나면 **던진다**(업무 오류가 아니라 우리 결함 · `receipt-posting.ts:158-161` 의 「라인 수가 다르면 던진다」와 같은 등급).
- ⭐ 품질·재고 상태를 **바꾸지 않는다** — 적치는 물건을 옮길 뿐 판정하지 않는다. 바꾸면 `uq_inventory_balance_dim` 의 다른 차원으로 넘어가 「적치했더니 검사 대기가 정상이 됐다」가 된다.
- `handling_unit_id` 복제는 I-16(취급 단위) 인계 — 오늘은 입고가 안 채우므로 언제나 `undefined` 다.

#### ⭐ ⓐ `sourceDocumentTypeCode` — §2 절차 전문

**0단계 — 선례.**
- `plan-integration.md` 120행이 통합 정본으로 **`STOCK_TRANSFER`** 를 배정했다(「`POST …:complete`·`:complete-temporary` — from `from_location_id` · to `actual_location_id` · `STOCK_TRANSFER`」). §3-1 I-12(316행)도 같다.
- `plan-uiux.md` U14 판정(581·1174행): 「`stock_transfer` 는 창고 간(from ≠ to)만 받는다. **위치 이동은 적치(U10)로 흡수**한다」 — 창고 «안» 이동의 원장 자리를 적치로 몰아준 것이 이미 통합 판정이다.
- ⭐ **I-10 §4-4 의 반대 선례** — `MATERIAL_RETURN` 이 enum 4값 밖이었을 때 I-10 은 **판별자를 늘리지 않고 「원장을 아예 안 지난다」로 물러났다**(`plan-integration.md` 660행 유혹 1). 여기서는 그 탈출구가 없다 — 계약 `PutawayTask.actualLocationId` 가 「**재고 잔액의 위치 축이 이 값을 따른다**」로 원장을 요구하고, 입고가 이미 하역장에 잔액을 세워 두었다.

**1단계 — 본길.** 두 오퍼레이션의 **모든 호출**이 이 값을 쓴다 ⇒ 본길. 「임의로 못 고른다. 계약 문자 그대로 + 문의.」

**계약 문자가 둘로 갈린다.**
- (i) `enum: [GOODS_RECEIPT, GOODS_ISSUE, INVENTORY_ADJUSTMENT, STOCK_TRANSFER]` — **닫힌 집합**. 다섯째 값을 쓰면 `GET /inventory/transactions` 응답이 자기 계약을 못 지난다(`test/inventory-transaction.e2e-spec.ts` 가 AJV 로 응답을 검증한다). `inventory-transaction.service.ts:20` 의 `SourceDocumentType` 유니온도 4값이고, 질의 필터가 그 유니온이라 **다섯째 값은 걸러낼 수도 없다**(응답 칸은 `string` 이라 새기는 통과한다 — 조용히 새는 모양).
- (ii) 「값은 «**대상 테이블 이름**»이다 — `sourceDocumentId` 는 그 표의 식별자다. **가리킬 표가 늘면 계약을 고친다**」 — `STOCK_TRANSFER` 는 `logistics.stock_transfer` 를 뜻한다(`document-type-registry.ts:68` · `entity_type_registry` 시드 1335행). 적치에는 그 헤더가 없다.

**후보 넷을 전부 재어 본다.**

| 후보 | 어긋나는 것 | 재는 값 |
|---|---|---|
| **`STOCK_TRANSFER` + `sourceDocumentId = putaway_task_id`** | (ii) — 가리키는 표가 거짓 | ⭐ **채택** |
| `PUTAWAY_TASK`(다섯째 값) | (i) — enum 이 닫혀 있다 · 우리 e2e 가 계약 위반을 잡는다 · 유혹 1 이 「계약을 고쳐야 는다」로 금했다(I-10 이 이미 그 판정을 따랐다) | ✕ |
| `GOODS_RECEIPT` + `sourceDocumentId = goods_receipt_id` | ⭐ **이미 선 기능을 깬다** — I-5 다형 취소가 원 트랜잭션을 `(source_document_type_code, source_document_id)` 로 찾고 「**2행 이상이면 던진다**」(`I-5.md` §6-4). 입고 전기 1행 + 적치 1행 = 2행 ⇒ 입고 취소가 죽는다 | ✕ |
| 서버가 `stock_transfer` 헤더를 만든다 | `plan-uiux.md` 1174 「창고 간만」과 충돌 · I-13 영역 침범 · 새 개념 넷(전표·번호·상태·사유) — §2 2단계 기준 5 | ✕ |

⇒ **판정: `STOCK_TRANSFER` + `sourceDocumentId = putaway_task_id` · 문의 059+1 로 계약을 고쳐 달라 한다.**
**3단계 흔적**: `putaway-posting.ts` 의 상수에 이름(`SOURCE_DOCUMENT_TYPE`)과 「⚠ 설계 미정 — 문의 059+1」 주석 · e2e 단언 이름에 「⚠ 판별자는 STOCK_TRANSFER 이고 sourceDocumentId 는 stock_transfer 가 «아니다»」.

⚠ **남는 위험 — 식별자 공간이 겹친다.** I-13 이 서면 같은 `STOCK_TRANSFER` 아래 `putaway_task_id` 와 `stock_transfer_id` 두 공간이 섞여, `(STOCK_TRANSFER, 5)` 가 둘을 가리킬 수 있다.
- **오늘은 터지지 않는다** — `document-type-registry.ts:68` 의 `STOCK_TRANSFER` 는 `cancelable: false` 라 다형 취소가 그 조회를 돌리지 않는다(실측).
- **I-13 이 이동 취소를 열면 터진다.** §11 인계 ① 에 못 박고 059+1 의 본문에 싣는다.

### 3-7. ⓔ 잔액 부족 — **그대로 400 `NEGATIVE_BALANCE`**

`post()` → `move(delta = -qty)` → `inventory_balance` UPDATE → `trg_inventory_balance_qty`(BEFORE INSERT OR UPDATE · `check_balance_qty()`) 가 음수를 막는다(psql 실측).
`plan-api.md` 1061행이 「⚠ 지금은 DB 트리거가 **500 으로 샌다** — 잡아서 이 코드로 바꾼다」라 적었고 **I-4 가 그 변환을 이미 세웠다**(첫 사용처). ⇒ 이 슬라이스는 **코드를 더하지 않고** 그 그물을 그대로 탄다. e2e 로 400 임을 못 박는다(§8-3).
일어나는 형상: 입고 뒤 같은 하역장 위치에서 출고·이동이 먼저 나가 잔액이 `task_qty` 보다 적을 때.

### 3-8. ⓕ 취소된 입고의 적치 지시 — **400 `STATE_LOCKED` 로 «먼저» 막는다**

`document-cancel-execute.service.ts:100-103` 이 「⛔ `putaway_task` 를 안 건드린다 — ⚠ **취소된 입고의 적치 지시가 남는다**」라 적었고 `I-5.md` §6-4 가 「**I-12 가 볼 자리**」로 넘겼다.

- **왜 `NEGATIVE_BALANCE` 로 충분하지 않은가.** 입고 취소가 역처리하면 하역장 잔액이 0 이 되어 ⓔ 로도 걸리는 «것처럼» 보인다. 그러나 `inventory_balance` 는 **차원 키**(창고·위치·품목·LOT·품질·재고상태·소유)이지 전표 키가 아니다 — **같은 LOT 이 같은 하역장으로 다시 입고되면 잔액이 채워지고, 취소된 지시가 «남의 물건»을 조용히 옮긴다.** 그물이 새는 자리다.
- §2 1단계: 가장자리(취소된 입고에서만 갈린다) → 2단계 **기준 2(거부하는 쪽)**. 거부→허용은 완화다.
- ⇒ `goods_receipt.status_code ∈ {CANCEL_REQUESTED, CANCELLED}` 이면 400 `STATE_LOCKED`, 「취소된 입고의 적치 지시입니다」. 값은 시드 `LOGISTICS_DOCUMENT_STATUS` 4값이고 상수를 새로 짓지 않는다.
- ⛔ **지시의 `status_code` 를 옮기지 않는다**(「취소됨」 값이 `PUTAWAY_TASK_STATUS` 3값에 없다 · F-6) — 막기만 한다. 남은 지시를 «닫는» 길은 계약에 0건이라 **059+3** 으로 묻는다.

### 3-9. UPDATE 와 응답

```
UPDATE logistics.putaway_task
   SET actual_location_id = ?, status_code = 'COMPLETED',
       completed_at = <occurredAt>, inventory_transaction_line_id = ?,
       updated_by = ?, version_no = version_no + 1
 WHERE putaway_task_id = ?            -- ① 에서 FOR UPDATE 로 이미 잡았다
```
- `completed_at = occurredAt`(클라이언트 값). **서버 시각이 아니다** — 계약 `occurredAt` 이 「단말에서 행위가 일어난 시각」이고 오프라인 큐가 몇 시간 뒤에 닿는다. 0단계 선례: `lot-complete.service.ts:95`(`completed_at: new Date(body.occurredAt)`). §9-1 #3.
- `version_no` 를 올린다 — 행이 바뀌었으므로 다음 `GET …/{id}` 의 ETag 가 따라간다. (두 POST 는 dead end 라 되쓸 자리가 없지만, 토큰을 옛 값으로 두면 상세를 든 다른 화면이 낡은 채로 통과한다.)
- 200 응답은 같은 tx 에서 되읽은 `PutawayTask` 하나. ⛔ **`setEtag` 를 부르지 않는다**(계약 미선언 · §1-1).

## 4. `POST …/{putawayTaskId}:complete-temporary`

### 4-1. 뼈대는 §3 과 «같다»

①~⑥ · ⑧~⑩ 이 글자 그대로 같고, 갈리는 것은 셋뿐이다.
| 자리 | `:complete` | `:complete-temporary` |
|---|---|---|
| ⑦ 권장 판정 | 2×2(§3-4) | ⛔ **하지 않는다**(§4-2) |
| ⑦′ 사유 검증 | 없음 | `reasonCode` ∨ `remarks` 「적어도 하나」 + 코드 그룹 대조(§4-3) |
| ③ 전이 액션 | `putaway-complete` → `COMPLETED` | `putaway-complete-temporary` → `COMPLETED_TEMPORARY` |
| ⑩ UPDATE | 위 + — | 위 + `reason_code`·`remarks` |

### 4-2. 권장 판정을 **하지 않는 근거**

ⓐ 계약 `PutawayTaskCompleteTemporary` 에 `confirmedNoRule` 칸이 **없다**(실측) — 권장이 없는 품목을 통과시킬 손잡이가 아예 없으므로, 권장 강제를 걸면 그 품목이 임시 적치도 못 한다.
ⓑ `M-01-05` §5-2-1 의 흐름도가 「권장과 다름 → ⛔ 저장 불가 · **임시 적치가 필요하면 → `M-01-07` 경로**」로 **임시를 권장 강제의 «탈출구»로 세웠다.** 탈출구에 같은 자물쇠를 걸면 `M-01-05` 의 차단이 dead end 가 된다.
ⓒ `M-01-07` §6 「임시 위치도 포화 → ⚠ **경고만**」 · 「혼적 제약 → ⚠ **임시 위치에는 적용하지 않는다**」.
⇒ §2 **0단계(계약 + 화면 문자)** 로 끝난다. 판단이 아니다.

### 4-3. 사유 — 「적어도 하나」

| 입력 | 판정 |
|---|---|
| `reasonCode` 있음(그룹 안) | 통과 · 저장 |
| `remarks` 있음(공백 아님) | 통과 · 저장 |
| 둘 다 | 통과 · 둘 다 저장 |
| 둘 다 없음/공백 | **400 `REQUIRED`** · `field: reasonCode` · 「사유 코드와 비고 중 하나는 있어야 합니다」 |
| `reasonCode` 가 그룹 밖/비활성 | **400 `INVALID`** — `assertCodeValues(prisma, [{ field:'reasonCode', value, groupCode:'PUTAWAY_TASK_TEMPORARY_REASON' }])` · ⛔ **tx 밖**(잠글 필요 없는 마스터 조회 · `lot-complete.service.ts:53-55` 선례) |

⚠ `M-01-07` §6 이 「사유 미선택 — **막지 않는다**」라 적었으나 그것은 **화면의 필수 표시** 이야기이고, 계약 오퍼레이션 설명이 「사유 코드와 비고 중 **적어도 하나는 있어야 한다**」로 명문이다. 계약이 이긴다(§5-5 액션 활성 조건도 「사유 선택 **또는** 비고 입력」이라 같은 규칙이다).

### 4-4. 두 오퍼레이션을 **한 서비스 함수의 모드 분기**로 둔다

- 갈리는 것이 셋뿐이고(§4-1) 나머지 아홉 단계가 «글자 그대로» 같다. 두 함수로 쪼개면 원장 쌓기·끝점 복제·전이·UPDATE 가 두 벌이 되고, 한쪽만 고치는 사고가 정확히 그 자리에서 난다.
- CLAUDE.md 의 「사용처 하나뿐인 추상화 금지」에 걸리지 않는다 — **사용처가 둘**이다.
- 모양: `putaway-complete.service.ts` 에 `complete(taskId, body, ctx, mode: 'NORMAL' | 'TEMPORARY')` 하나. 분기 셋만 `if (mode === 'TEMPORARY')`.
- 컨트롤러는 핸들러 둘(계약 경로가 둘이므로 `@Contract` 도 둘).

### 5-1. `GET /logistics/putaway-tasks`

```ts
where = {
  ...filter('assigned_worker_id', assignedWorkerId),
  ...filter('lot_id', lotId),
  ...filter('status_code', statusCode),
  ...(temporaryOnly === true ? { status_code: 'COMPLETED_TEMPORARY' } : {}),   // ⚠ 아래
  ...(warehouseId  === undefined && goodsReceiptId === undefined ? {} : {

```

- ⭐ **`statusCode` 와 `temporaryOnly` 가 겹치면 AND 로 겹친다** — 객체 전개로 뒤가 앞을 덮으면 조용히 한쪽이 사라지므로 `AND: [...]` 로 명시한다. 모순되면 **빈 목록**(400 이 아니다). 0단계 선례 — 모든 목록이 질의 축을 AND 로 겹친다(`goods-receipt.service.ts:53-64` 등). 계약이 배타를 안 적었다.

- 정렬: 계약 침묵. `M-01-05` §4-A 가 `priority_no` 를 「**목록 정렬**」이라 적었다(0단계 화면 문자) + PK 로 안정화. ⛔ `completed_at desc` 가 아니다 — 이 목록의 첫 손님은 «대기 중» 지시다.
- 403: 계약이 선언하지 않았고 `PermissionGuard` 는 선언한 자리만 센다 — `derived-permissions.ts:62` 의 `['M-01-05','M-01-07']` 는 그대로 두고 손대지 않는다.
