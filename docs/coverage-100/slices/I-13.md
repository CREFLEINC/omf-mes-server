## 3. ⭐ 2단 전기 — 이 슬라이스의 심장

### 3-0. 먼저 못 박을 것 — **문서 1건 · 원장 전기 2회 · 트랜잭션 2개**

계약 `StockTransfer` x-internal-note(`:14081`) 원문: 「한 행에 `shipped_at`·`received_at` 이 둘 다 있다 — **두 문서가 아니라 한 문서의 두 전이다**(02-URL동작규약 §2-4)」.
물증은 `stock_transfer_line` 이 `issue_transaction_line_id`·`receipt_transaction_line_id` **두 칸**을 가진 것이다(`schema.prisma:1457-1458`).

⭐ **두 전기가 «한» 트랜잭션에 드는 자리는 없다.** 반출은 `POST` 의 트랜잭션, 도착은 `:arrive` 의 트랜잭션이다 — 그 사이에 **작업자가 물건을 들고 이동하는 시간**이 있다(`M-01-10` §3-1 「몇 분에서 수십 분」). 각 오퍼레이션은 `posting.post()` 를 **정확히 한 번** 부른다.

```
[POST /logistics/stock-transfers]            ── 트랜잭션 A ──
   전표·라인 INSERT + post() 1회
     from = {출발 창고, from_location, Q, I}          ← 잠근 잔액 행에서 되읽는다
     to   = {도착 창고, to_location,  Q, IN_TRANSIT}  ← ⭐ 재고 상태 축만 갈아 끼운다
   status_code = 'REGISTERED' · shipped_at = occurredAt
   issue_transaction_line_id 되짚기

        … 물건이 이동한다(분~수십 분 · 오프라인 큐가 그 사이를 담는다) …

[POST …/{id}:arrive]                          ── 트랜잭션 B ──
   post() 1회
     from = {도착 창고, to_location, Q, IN_TRANSIT}   ← ⭐ A 가 남긴 원장 라인의 to_* 복제
     to   = {도착 창고, 실제 위치,   Q, I}            ← ⭐ A 의 from_inventory_status_code 로 되돌린다
   received_at = occurredAt · 전량이면 status_code = 'POSTED'
   receipt_transaction_line_id 되짚기
```

`Q` = `quality_status_code` · `I` = `inventory_status_code`. **둘 다 서버가 «고르지» 않는다** — A 는 잠근 잔액 행에서, B 는 A 가 남긴 원장 라인에서 되읽는다(§1-5 · QUALITY_STATUS 그룹이 0건이라 고를 값 자체가 없다).

### 3-2. 반출(A)의 두 끝점

```
from ← 잠근 잔액 행에서 되읽는다 (issue-posting.ts:120-146 과 «같은» 모양)
        { warehouseId: from_warehouse_id,
          locationId : line.from_location_id,
```

- ⭐ **`from` 을 지어내지 않는다.** `lockBalancesInOrder` 가 7칸으로 잠근 행이 **둘 이상**이면(품질·재고 상태·소유가 갈린 잔액) 어느 것을 낼지 계약이 안 준다 ⇒ **400 `INVALID`**(`issue-posting.ts:131-136` 「설계 미정 — 문의 031」 그대로 복제 · 새 문의를 열지 않는다). 0행이면 400 `NEGATIVE_BALANCE`.

### 3-3. 손검사와 잠금 순서 — **코어를 안 고친다**

`posting.post()` 가 첫 `move()` «앞»에서 라인 전건의 `from`·`to` 잔액 행을 `inventory_balance_id` 오름차순으로 **한 문장에** 잠근다(`inventory-posting.service.ts:66-69` → `balance-lock.ts:41-61`). I-4 R-1 ①②·I-5 R-5 가 세운 규약이라 **이 슬라이스가 더할 것이 없다**.

다만 **음수 하한 손검사는 호출자 몫**이다(코어는 「잠글 뿐 판정하지 않는다」 · `balance-lock.ts:36-37`). 그래서 `transfer-posting.ts` 가 `issue-posting.ts:96-165` 를 복제한다:
1. `lockBalances` 로 `from` 키 전건을 잠근다.
2. **키별 «합계»로** 요구량을 센다 — 같은 (위치·품목·LOT) 라인이 둘이면 라인별 검사는 둘 다 통과하고 둘째 UPDATE 에서 트리거가 500 을 낸다(I-4 R-1 ③).
3. `available_qty` 와 견준다 — 모자라면 400 `NEGATIVE_BALANCE`.
4. 그 뒤에 `posting.post()` 를 부른다.

⛔ `pick()`·`consume()` 을 부르지 않는다 — 이동은 피킹 축이 아니다(`header.sourceDocumentTypeCode !== 'PICKING_ORDER'` 갈래 · `issue-posting.ts:251`).
⛔ `item.negative_stock_allowed` 를 보지 않는다 — 출고와 같은 가름(계약이 「보유 수량 이하」로 닫았다).
⚠ 도착(B)의 `from` 은 **반출이 세운 잔액**이라 잔액이 모자랄 수 없다 — 그래도 같은 손검사를 태운다(부분 도착 뒤 잔여를 누가 먼저 빼 갔을 수 있다 · 400 `NEGATIVE_BALANCE`).

### 3-4. ⭐ `IN_TRANSIT` 행의 `location_id` — §2 절차 전문

`inventory.inventory_balance.location_id` 는 **NOT NULL**(baseline `migration.sql:1097` 실측)이고 `uq_inventory_balance_dim` 의 축이다. 이동 «중»에는 물건이 어느 위치에도 없다.

- **0단계 선례** — ⓐ `plan-integration.md:325` 초안 판정: 「2단계 기준 3 → **도착 위치를 미리 쓴다**(`to_location_id`)」. ⓑ `stock_transfer_line.to_location_id` 는 **NOT NULL** 이라 반출 시점에 이미 값이 있다(계약 `StockTransferLineUpsert.toLocationId` required). ⓒ 「위치 없음」을 표현할 자리가 물리에 0건이다 — `location` 마스터에 「가상 위치」 개념도 없다(`mdm.location` 실측: `location_type_code` 값 목록 0건).
- **1단계** — 모든 반출 호출이 이 값을 쓴다 ⇒ **본길**. 「계약 문자 그대로 + 문의」인데 **계약이 침묵**한다(원장 끝점 4칸이 계약 어디에도 안 실린다).
- **2단계** — 후보 셋을 잰다.

| 후보 | 새 개념 | 어긋나는 것 | 판정 |
|---|:-:|---|---|
| **`to_location_id`(계획 도착 위치)** | 0 | 「아직 도착 안 했는데 도착 위치에 잔액이 선다」 — 다만 `inventory_status_code='IN_TRANSIT'` 가 그것을 말한다 | ⭐ **채택** |
| `from_location_id`(출발 위치) | 0 | 출발 위치의 잔액이 «줄었는데 다시 늘어» 같은 행이 0 이 되고 옆에 `IN_TRANSIT` 행이 선다 — `M-01-04`(자재 위치 확인)가 출발 위치에 아직 물건이 있는 것처럼 그린다 | ✕ |

⇒ **`to_location_id` 를 쓴다.** 2단계 **기준 3**(스키마를 안 늘리는 쪽)·**기준 5**(새 개념 0). 초안과 같은 결론이고, 절차를 다시 밟아 확인했다.

**3단계 흔적**: `transfer-posting.ts` 의 상수·주석에 「⚠ 이동 중 위치 = 계획 도착 위치. `inventory_balance.location_id` 가 NOT NULL 이라 「위치 없음」을 담을 자리가 없다(문의 124)」 · e2e 이름 14·26 에 세 지점 단언.

### 3-6. 되짚기 — `createManyAndReturn` 순서에 기대지 않는다(I-24 R-7)

`posting.post()` 는 **넘긴 배열 순서대로** `line_no` 를 매긴다(`inventory-posting.service.ts:86-88` — `for (const [index, line] of input.lines.entries())` → `writeLine(…, index + 1)`). 이것은 «반환 순서» 추정이 아니라 **코어가 명시한 규약**이다.

```ts
const ledger = await tx.inventory_transaction_line.findMany({
  where: { inventory_transaction_id: posted.inventoryTransactionId,
           business_date: new Date(`${businessDate}T00:00:00.000Z`) },

  select: { inventory_transaction_line_id: true },

if (ledger.length !== postedLines.length) throw new Error(...);   // 우리 결함이다
```

⚠ **도착에서는 «전기한 라인만» 짝짓는다** — `receivedQty = 0` 인 라인은 원장 라인이 없으므로 `postedLines`(0 을 걸러낸 배열)와 짝짓고, 걸러진 라인의 `receipt_transaction_line_id` 는 **널로 둔다**.

### 4-3. 채번 — `DEFAULT_PREFIX` 에 **`ST` 한 줄**

`app.numbering_rule` **3행**(psql 실측 — `PRODUCTION_RESULT`·`WORK_ORDER`·`MATERIAL_ISSUE_REQUEST` · 전부 `plant_id IS NULL`)이라 `STOCK_TRANSFER` 규칙은 **미등재**다. `numbering.service.ts:120` 이 기본 패턴 `{PREFIX}-{YYYYMMDD}-{SEQ4}` 로 규칙 행을 스스로 만들지만, `prefixOf()` 가 `DEFAULT_PREFIX` 에 없는 유형을 **던진다**(`:152-161` 「접두어를 지어내지 않는다」).

```ts
/** 규칙 미등재 — `ST-{YYYYMMDD}-{SEQ4}`. 계약 example `ST-2026-000260` 은 접두어만 준다(I-13 §4-3). */
STOCK_TRANSFER: 'ST',
```

- **한 줄 추가**(`numbering.service.ts:9-29` · GI·SR·MC·MR·PP 다섯이 같은 모양으로 이미 서 있다).
- 기간 키 = **`businessDate`**(호출자가 준 날짜 · 형제 물류 전표 전건이 같다 — `goods-receipt.service.ts:107`·`goods-issue.service.ts:72`·`material-issue-request.service.ts:62`·`shopfloor-receipt.service.ts:72`).
- `plantId` = **`from_warehouse.plant_id`** — 물류 전표 다섯이 전부 공장을 넘긴다(위 실측). ⚠ I-24 R-6 이 W/O 를 `null` 로 통일한 이유(「같은 유형을 부르는 자리가 둘이라 공장 규칙이 등재되면 카운터가 갈린다」)는 **여기 없다** — `STOCK_TRANSFER` 를 부르는 자리가 이 한 곳뿐이다(grep 실측).
- **재시도**: `stock_transfer_no` 가 `@unique` 다 ⇒ `goods-receipt.service.ts:101-121` 의 `for(attempt)` + `isDuplicateNo(error)` 루프를 **그대로 복제**한다(I-2 R-2). 채번은 **`$transaction` 을 열기 «전»**(`numbering.service.ts:62-64` — 안에서 부르면 커넥션을 둘 쥐어 `P2024`).
- ⛔ **원장 번호를 따로 채번하지 않는다** — 전표 번호를 그대로 쓴다(입고·출고·적치 3선례 · §3-1).
- 문의 14(채번 규칙 없는 표) 표에 **`stock_transfer_no`(`ST-`) 한 행**을 더한다(기존 문의 · 신설 아님).

### 4-5. 멱등 · If-Match · ETag · 403

- **멱등**: `runIdempotent(this.idempotency, request, HttpStatus.CREATED, …)`(`goods-issue.controller.ts:83-85` 선례). 원장 쪽은 **결정적 키**가 둘째 그물이다(§3-1).
- **If-Match 는 «선택»**이라 컨트롤러가 `runVersioned` 를 **못 쓴다**(`putaway-task.controller.ts:44-45` 가름). ⭐ 그런데 **새 자원이라 대조할 버전이 없다** — `goods-issue.controller.ts:73` 「⛔ If-Match 는 「선택」이라 꺼내지 않는다 — 새 자원이라 대조할 버전이 없다」와 **같은 판정**. ⇒ **읽지도 대조하지도 않는다.** e2e 23 으로 「실어도 통과한다」를 못 박는다.
- **ETag**: `setEtag(response, 1)` — 계약 201 `headers.ETag` 실측(「낙관적 잠금 토큰 — 이 행의 `version_no`. 다음 쓰기의 If-Match 에 그대로 담는다. **본문 필드로는 내리지 않는다**」).
- **403**: `derived-permissions.ts:188` 에 **이미 있다**(`['M-01-10']`) — 등록 0줄(§9-5).

## 5. `POST …/{stockTransferId}:arrive` — 도착 확정 · **200**

### 5-1. 한 트랜잭션 순서

```
[tx 밖]  ① X-Worker-No 그물(§4-2 ①)
         ② lines.length === 0 → 400 LINE_REQUIRED
[tx 안 · runIdempotent 안]
         1  SELECT … FROM logistics.stock_transfer WHERE stock_transfer_id = ? FOR UPDATE
                                                        → 없으면 404 (§7-3)
         2  If-Match 가 «있으면» version_no 대조                → 409 ConflictResponse(user)
         3  ⭐ received_at IS NOT NULL 이면                     → 400 STATE_LOCKED  (§5-3)
         4  라인 되읽기 + 본문 대조 — 남의 라인 · 중복          → 400 INVALID
         5  receivedQty > shipped_qty                           → 400 RANGE
         6  toLocationId 재정의가 오면 위치 그물 셋(§4-2 ⑤)     → 400 INVALID
         7  반출 원장 라인 되읽기(issue_transaction_line_id → to_* 4칸 + 소유·취급단위)
                                                                → 없으면 던진다(우리 결함)
         8  postTransferArrive(tx, posting, …)  — receivedQty > 0 인 라인만 (§3-5)
                                                                → 400 NEGATIVE_BALANCE
         9  UPDATE stock_transfer_line SET received_qty · to_location_id(재정의분)
              · receipt_transaction_line_id                     (line_no 자리 짝짓기 · §3-6)
        10  전량 도착이면 assertTransition('logistics.stock_transfer.status_code',
                                          'transfer-arrive', locked.status_code, 400) → POSTED
            부분 도착이면 상태를 그대로 둔다                     (§5-3 · plan-api.md:752)
        11  UPDATE stock_transfer SET received_at = occurredAt · status_code(위)
              · updated_by = 세션 · version_no = version_no + 1
              WHERE stock_transfer_id = ? AND version_no = <잠글 때 읽은 값>
              0행이면 assertUpdated(0)                          → 409 (잠금 밖 경합의 마지막 그물)
        12  같은 tx 에서 되읽어 StockTransferDetailResponse
[응답]   200 · ⛔ setEtag 안 부른다(계약 미선언)
```

- ③⑤⑥ 을 ⑧ «앞»에 두는 이유는 I-5 §6-4·I-12 §3-1 과 같다 — **원장을 쌓기 전에 업무 거부를 끝낸다**(400 이면 상태도 안 옮긴다).
- ⑦ 을 ⑧ 앞에 두는 이유: 끝점을 지어내면 반출이 세운 잔액이 아닌 차원을 깎는다(§3-5).
- ⭐ **`FOR UPDATE` 를 «건다»** — 읽고 판정하고 그 행을 UPDATE 한다. 두 요청이 같은 전표를 동시에 도착시키면 ③ 이 옛 값을 본다(`I-12.md` §3-2 · `goods-issue-update.service.ts:224-238` `lockHeader`). 잠금 순서는 `stock_transfer` 한 행 → `post()` 안의 잔액 행(코어가 id 오름차순 · `balance-lock.ts`)이라 **교착 창이 없다**.

### 5-2. 라인 매칭 — 네 갈래

| 형상 | 처리 |
|---|---|
| 본문에 실린 라인이 이 전표의 것이 아니다 | 400 `INVALID`(field `lines[i].stockTransferLineId`) — `assertOwnLines` 복제(`goods-issue-update.service.ts:281-289` 「짚는 행이 «없으면» 조용한 사고가 된다」) |
| 같은 `stockTransferLineId` 를 두 번 실었다 | 400 `INVALID` — `assertNoDuplicate` 복제(`:264-275`) |
| 본문에 «안» 실린 라인 | 안 건드린다(`received_qty` 그대로) — 계약 「도착 수량을 «기록할» 라인」 |
| `toLocationId` 재정의 | 위치 그물 셋을 지나면 **`stock_transfer_line.to_location_id` 를 갱신**하고 원장 `to.locationId` 로 쓴다. ⚠ 원장의 `from` 은 **반출 원장 라인**에서 오므로 계획 위치 그대로다(§3-4 ⭐) — 두 값이 달라도 잔액이 어긋나지 않는다 |

### 5-3. ⭐ 부분 도착과 재도착 — §2 절차 전문

**물음 셋을 가른다.**

**ⓐ 부분 도착(`receivedQty < shippedQty`)을 막나?** → **막지 않는다.** 0단계 — 계약이 **명시적으로 허용**한다(`:5710`·`:14090` 「반출한 수량 **이하**만 받을 수 있다」) + 물리 CHECK `received_qty <= shipped_qty` + `M-01-10` §6 「이동 중 분실·손상 — 도착 수량 < 반출 수량으로 표현되나 사유가 없다」. **재량 없음.**

**ⓑ 부분 도착이 상태를 옮기나?** → **안 옮긴다**(`REGISTERED` 유지). 0단계 — `plan-api.md:752` 전이표가 통합 정본으로 「부분 도착은 상태를 안 옮긴다 — 전량에서만 `POSTED`」라 적었다. 2단계 **기준 1**(상태를 안 쓰는 쪽)도 같은 답이다.

**ⓒ 둘째 `:arrive` 를 받나?** → ⭐ **안 받는다. 400 `STATE_LOCKED`.**

- **0단계** — 계약이 침묵한다(되풀이 호출을 한 줄도 안 적었다). `StockTransferArrive.lines[].receivedQty` 는 `x-source-column: received_qty` 로 **칸에 직접 대응**할 뿐 누적인지 설정인지 말하지 않는다. 이미 구현된 전표 중 같은 축(부분 처리를 되풀이하는 확정)은 **0건**이다(적치·출고·입고 전부 1회 확정).
- **1단계** — 둘째 호출에서만 갈린다 ⇒ **가장자리**.
- **2단계** — 후보 둘.

| 후보 | 새 개념 | 재는 값 |
|---|:-:|---|
| **거부**(`received_at IS NOT NULL` → 400 `STATE_LOCKED`) | **0** | 기준 2 「거부하는 쪽 — 거부→허용은 호환 완화」. 원장 규약이 그대로 선다: `transactionNo = ST-…-A` 한 벌 · 결정적 멱등키 한 벌(§3-1) |
| 허용(누적 또는 설정 + 델타 전기) | **2** — 「도착 회차」 · 「회차별 원장 번호·멱등키」 | 기준 5(새 개념 수)에 걸린다. 게다가 `receivedQty` 가 «그 회차의 양»인지 «누계»인지 계약이 안 갈라 **또 하나의 미정**을 낳는다 |

⇒ **거부.** ⚠ **대가**: 부분 도착한 전표는 `REGISTERED` 인 채 `received_at` 이 차 있고 잔여 수량이 `IN_TRANSIT` 차원에 남는다 — **닫는 길이 계약에 0건**이다(취소도 없다 · §11 #2). 이것은 적치의 dead end(문의 060)와 **같은 형상**이라 **문의 124** 로 올린다.
**3단계 흔적**: 상수·주석에 「⚠ 설계 미정 — 문의 124」 · e2e **29·30**(부분 도착이 `REGISTERED` 로 남는다 · 둘째 `:arrive` 는 400) · 단위 ④.

### 5-4. 멱등 · If-Match · ETag · 403

- **멱등**: `runIdempotent(…, HttpStatus.OK, …)`.
- **If-Match 는 «선택»** — 있으면 대조하고(409 `ConflictResponse` · `conflictCause='user'`) 없으면 건너뛴다(C-9 · `putaway-task.controller.ts:73-85` `contextOf` 의 `version: ifMatchVersion(request)` 선례).
- **ETag 를 안 내린다**(계약 200 `headers` 0건) — `plan-uiux.md:253` 의 「ETag」는 요청 `If-Match` 다(§13-1 #4).

### 6-2. 판정 — **자물쇠까지만 구현한다**

§2 1단계 **본길**(모든 호출) → 계약 문자 그대로 구현한다. 계약 문자가 「400 `STATE_LOCKED`」이므로 **그것이 유일한 출구**다.

```
[tx 안 · runIdempotent 안]
  1  SELECT status_code, shipped_at, version_no FROM logistics.stock_transfer
       WHERE stock_transfer_id = ? FOR UPDATE                 → 없으면 404 (§7-3)
  2  If-Match(필수) 대조 — 어긋나면 409 ConflictResponse(user)  ← 부모 토큰(계약 원문)
  3  ⭐ shipped_at IS NOT NULL 이면 400 STATE_LOCKED(field 'items')
       ⚠ 오늘 이 갈래를 «반드시» 지난다 — 반출 전 상태를 만드는 오퍼레이션이 0건이다(문의 123)
  4  (도달 불가) 치환 — 쓰지 않는다
```

- ⛔ **치환 본체(`LINE_NO_SHIFT` 밀어두기·`assertOwnLines`·`assertNoDuplicate`·삭제/생성/갱신)를 짓지 않는다** — `CLAUDE.md` 「사용처 하나뿐인 추상화·선제적 레이어 금지」·「불가능한 시나리오의 에러 처리 금지」. 도달 가능해지면 그때 `goods-issue-update.service.ts:50-153` 를 복제한다(§13 ⑥).
- ⭐ **③ 을 ② «뒤»에 둔다** — I-12 R-6 과 같은 순서(잠금 → 토큰 → 상태). If-Match 가 필수라 토큰이 어긋나면 409 가 먼저다. e2e 36 이 그 순서를 못 박는다.
- **`version_no` 를 «안 올린다»** — 치환이 일어나지 않으므로 바뀌는 것이 없다. (도달 가능해지면 부모 버전을 올린다 — `goods-issue-update.service.ts:139-145` 「라인이 바뀌면 부모 상세의 내용이 바뀐다」.)
- **ETag 를 안 내린다**(계약 미선언) · **`X-Worker-No` 를 안 받는다**(계약 미선언 — 관리웹 축이다).
