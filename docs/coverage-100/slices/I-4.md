### R-1. ⛔ §3-4 잠금 SQL 을 다시 쓴다 — 교차곱 제거 · `to` 행도 같은 문장 · 차원별 합산 (integration 3-①②③)
- **①** `(plant,warehouse,location,item) = ANY(…) AND COALESCE(lot_id,0) = ANY(…)` 는 라인 1 의 위치와 라인 2 의 LOT 을 짝지어 잠근다 — 라인이 둘 이상이면 §3-2 의 0행/1행/2행+ 판정이 뭉개진다. **7칸 행생성자 한 문장**으로:
  `WHERE (legal_entity_id,business_unit_id,plant_id,warehouse_id,location_id,item_id,COALESCE(lot_id,0)) IN (VALUES (…),(…)) ORDER BY inventory_balance_id FOR UPDATE`. 되읽은 행을 **라인별 7칸 키로 다시 그룹지어** 행 수를 센다.
- **②** `destination_type_code='LOCATION'` 이면 `to` 잔액 행이 선잠금 밖이라 `move()` 가 순서 밖에서 잡는다 — A→B·B→A 동시 출고가 정확히 §3-4 가 막으려던 교착이다. ⇒ **`to` 의 7칸 키(도착 창고·위치 + 같은 품목·LOT)를 같은 `VALUES` 목록에 합쳐 한 문장으로 잠근다.** `to` 키는 잠금용일 뿐 행 수 판정을 안 한다(0행이면 `move()` 의 `INSERT … ON CONFLICT DO NOTHING` 이 만든다 — 넣는 방향이라 §3-4 마지막 ⛔ 와 충돌 없음). `LOCATION` 을 범위 밖으로 미루는 대안(integration ⓑ)은 **기각** — 계약 `destinationTypeCode` 「생산 투입은 위치」 · `M-01-08` §5-6 이 현장 최다 갈래다(uiux 3).
- **③** 같은 (위치·품목·LOT) 라인이 둘이면 라인별 손검사가 둘 다 통과하고 둘째 UPDATE 가 트리거 500 이다 ⇒ **7칸 키별로 `issueQty` 를 합산해** `available_qty >= Σ` 를 본다. `available_qty` 는 생성 컬럼인데 Prisma 타입이 `Decimal?` 이다 — `null` 이면 **던진다**(조용히 0 이나 손계산으로 대신하지 않는다).
- `check_balance_qty()` 세 갈래(baseline `20260727000000`:2831~)를 `available_qty ≥ Σ` 가 전부 앞당겨 막는다는 integration 실측으로 §3-3(`negative_stock_allowed` 무시)은 **그대로 선다**.

## 3. 원장 `:post` — `posting.post()` 호출 모양

### 3-1. 라인마다 `from` 만, `to` 는 `LOCATION` 일 때만

`core/inventory-posting/posting.types.ts` 실측 — `PostingLine.from` 없으면 입고, `to` 없으면 출고. 입고(`receipt-posting.ts:135`)는 `to` 만 싣는다. **출고는 그 거울상**이다.

```
posting.post(tx, {
  businessDate,                          // ← 요청 본문(C-8) · 서버가 다시 안 잡는다
  occurredAt: new Date(occurredAt),      // ← 요청 본문(C-1)
  transactionTypeCode: 'GOODS_ISSUE',
  transactionNo: goodsIssueNo,           // 전표 번호를 그대로 원장 번호로(입고 선례)
  statusCode: 'POSTED',
  plantId,                               // ← warehouse.plant_id 로 푼다(헤더에 plant_id 가 없다)
  sourceDocumentTypeCode: 'GOODS_ISSUE', // ⭐ 원장 판별자 4값(plan.md §5 #8) — 전표의 sourceDocumentTypeCode 가 아니다
  sourceDocumentId: Number(goodsIssueId),
  idempotencyKey: `GOODS_ISSUE:${goodsIssueNo}`,
  createdBy: appUserId,
  lines: lines.map((line) => ({
    itemId: line.item_id, lotId: line.lot_id, qty: line.issue_qty, uomId: line.uom_id,
    from: { warehouseId: header.source_warehouse_id,   // ← 헤더
            locationId: line.source_location_id,       // ← 라인
            qualityStatusCode: balance.quality_status_code,     // ← ⚠ 잔액 행에서(§3-2)
            inventoryStatusCode: balance.inventory_status_code },
    // to 는 destinationTypeCode === 'LOCATION' 일 때만. PARTNER·DISPOSAL_SITE·비움이면 없다
    ...(header.destination_type_code === 'LOCATION'
        ? { to: { warehouseId: <그 위치의 창고>, locationId: header.destination_id,
                  qualityStatusCode: ..., inventoryStatusCode: ... } }
        : {}),
    ownershipTypeCode: balance.ownership_type_code,
    ...(balance.owner_partner_id === null ? {} : { ownerPartnerId: ... }),
  })),
})
```

| 값 | 출처 |
|---|---|
| `from.warehouseId` | **헤더** `source_warehouse_id` |
| `from.locationId` | **라인** `source_location_id` |
| `from.qualityStatusCode`·`from.inventoryStatusCode`·`ownershipTypeCode`·`ownerPartnerId` | ⚠ **어디에도 없다 → 잔액 행에서 되읽는다**(§3-2) |
| `to` | **헤더** `destination_type_code === 'LOCATION'` 일 때만. `PARTNER`·`DISPOSAL_SITE`·비움이면 **없음** — `plan-integration.md` I-4 가 적은 그대로 |
| `qty`·`itemId`·`lotId`·`uomId` | **라인** |
| `businessDate`·`occurredAt` | **요청 본문** |

⛔ **`to` 가 `LOCATION` 일 때의 창고**를 헤더가 안 준다. `mdm.location` 에서 `warehouse_id` 를 읽는다(`location.warehouse_id` 실재). 입고가 「목적지는 그 창고의 위치여야 한다」를 손검사한 것(`goods-receipt.service.ts:227-231`)의 반대 방향이다 — 여기선 도착 창고를 «도출»하므로 검사가 아니라 조회다.

### 3-2. ⭐ `from` 의 두 칸이 계약에 없다 — 잔액 행에서 되읽고, 모호하면 400

`uq_inventory_balance_dim` 은 11칸 차원이다(`inventory_balance` 실측). 출고 라인이 주는 것은 그중 **6칸**(le/bu/plant 는 창고에서 · warehouse · location · item · lot). 남는 셋(`quality_status_code`·`inventory_status_code`·`ownership_type_code`+`owner_partner_id`)을 **계약이 안 싣는다.**

- **§2 0단계** — 선례 없음. 입고는 라인이 실어 보내고(`GoodsReceiptLineCreate.qualityStatusCode`·`inventoryStatusCode`), 소유 구분은 서버가 `OWNED` 로 골랐다(문의 016). 출고는 «이미 있는 행»을 깎는 것이라 고르는 것이 아니라 **찾는 것**이다 — 입고의 처방이 그대로 안 온다.
- **§2 1단계** — 잔액 행이 한 벌뿐이면 답이 데이터로 정해진다. 둘 이상일 때만 갈린다 ⇒ **가장자리**.
- **§2 2단계 기준 2(거부하는 쪽)** — 서버가 하나를 고르면 «어느 품질 상태의 재고를 냈는가»가 조용히 정해지고, 그것은 원장에 남아 되돌리기 비싸다.

**판정** — `(le,bu,plant,warehouse,location,item,lot)` 7칸으로 `inventory_balance` 를 잠그고 읽는다.
| 결과 | 응답 |
|:-:|---|
| 1행 | 그 행의 `quality_status_code`·`inventory_status_code`·`ownership_type_code`·`owner_partner_id` 를 그대로 `from` 에 싣는다 |
| 0행 | 400 **`NEGATIVE_BALANCE`**, field `lines[i].lotId` — 「이 위치에 그 LOT 의 재고가 없습니다」 |
| 2행 이상 | 400 **`INVALID`**, field `lines[i].lotId` — 「재고 차원이 둘 이상이라 어느 것을 낼지 정할 수 없습니다」 + `// 설계 미정 — 문의 031` |

- ⛔ **새 에러 코드를 만들지 않는다** — §2 2단계 기준 5(새 개념 수가 적은 쪽).
- ⛔ **LOT 없는 잔액(`lot_id IS NULL`)은 출고할 길이 없다** — `goods_issue_line.lot_id` 가 NOT NULL 이고 계약도 required 다. M-01-08 §8 #3 이 같은 것을 「조정」으로 남겼다 ⇒ §8 판정표 ⓒ(문의 아님 — 화면이 이미 안다).
- ⭐ **`to` 쪽 두 칸**(도착이 `LOCATION` 인 경우)은 **`from` 과 같은 값을 쓴다** — 창고 안/사이 이동에서 품질·재고 상태가 바뀌는 축이 계약에 없다(`GoodsIssueCreate` 에 칸 0). §2 2단계 기준 4(조용히 도출하지 않는 쪽) — 값을 «바꾸지» 않는 것이 도출을 안 하는 쪽이다.

### 3-3. 음수 금지의 자리 — **코어가 아니라 도메인이다. 트리거는 500 으로 샌다**

```
-- baseline 20260727000000:2831~2861
CREATE OR REPLACE FUNCTION inventory.check_balance_qty() ... BEFORE INSERT OR UPDATE
  IF NEW.on_hand_qty >= 0 THEN
      IF NEW.on_hand_qty < NEW.reserved_qty + NEW.picked_qty + NEW.blocked_qty THEN RAISE ... check_violation
  ELSE
      SELECT i.negative_stock_allowed ...  IF NOT COALESCE(v,false) THEN RAISE '음수재고 미허용 품목' ... check_violation
```
- `ERRCODE = check_violation` ⇒ Prisma 는 **`PrismaClientUnknownRequestError`** 를 던지고 `prisma-error.ts` 는 `PrismaClientKnownRequestError` 만 본다 ⇒ **500**. 그 파일 머리 주석이 못박은 자리다: 「⛔ CHECK 위반은 여기 오지 않는다 … 서비스가 짝 검사를 빠뜨린 «우리» 버그」.
- `InventoryPostingService` 안에도 음수 검사가 **없다**(`inventory-posting.service.ts` 전문 실측 — `move()` 는 UPDATE 만 한다).
- ⇒ **판정: 손검사를 도메인(`issue-posting.ts`)이 진다.** 코어를 늘리지 않는다 — `plan.md` §3 이 `posting.reverse()` 의 `NEGATIVE_BALANCE` 를 **I-5 코어 PR** 로 잡아 두었고, 여기서 코어를 먼저 늘리면 I-5 와 같은 파일을 두 슬라이스가 고친다(`plan-integration.md` §6-2 ⛔ 「원장 코어를 «고치는» 두 슬라이스」).
- **검사식**: `available_qty(= on_hand − reserved − picked − blocked) >= issue_qty`.
  ⛔ `on_hand_qty` 만 보면 안 된다 — 트리거 첫 갈래가 「`on_hand < reserved+picked+blocked`」도 막는다. 예약이 걸린 재고를 출고하면 `on_hand` 는 양수인데 그 조건에 걸려 **500** 이다. (`available_qty` 는 생성 컬럼으로 이미 있다 — 실측.)
  ⛔ **`Decimal` 로 비교한다**(I-3 §3-3 교훈 · `@db.Decimal(20,6)`).
- 넘으면 **400 `NEGATIVE_BALANCE`**, field `lines[i].issueQty`.
- ⚠ `item.negative_stock_allowed = true` 인 품목은 트리거가 음수를 허용한다 — 그래도 **서버는 막는다**. §2 2단계 기준 2(거부하는 쪽) + 계약 `GoodsIssueLineUpsert.issueQty` 「보유 수량 이하」가 예외를 안 뒀다. 흔적: `// item.negative_stock_allowed 를 보지 않는다 — 계약이 「보유 수량 이하」로 닫았다(I-4.md §3-3)` ⇒ §8 판정표 ⓓ.

### 3-4. 잠금 순서 — I-3 §3-2 의 불변식을 잔액 축으로 옮긴다

⚠ **재수립 R-1 이 아래 4번 SQL 을 대체한다** — 7칸 행생성자 `IN (VALUES …)` 한 문장 · `to`(LOCATION) 키 합집합 · 키별 합산 검사. 아래 `= ANY(…)` 두 줄은 교차곱이라 쓰지 않는다.

손검사만 하면 두 동시 출고가 둘 다 통과하고 두 번째 UPDATE 에서 트리거가 500 을 낸다.

```
1. (트랜잭션 밖) 검증 → (등록 경로면) numbering.next(...)     ← I-2 R-2
2. $transaction 시작
3. goods_issue 헤더를 SELECT … FOR UPDATE (상태·버전 재확인)
4. 이 요청이 건드리는 잔액 행을 «차원 오름차순 한 문장»으로 잠근다
     SELECT inventory_balance_id, quality_status_code, inventory_status_code,
            ownership_type_code, owner_partner_id, on_hand_qty, reserved_qty, picked_qty, blocked_qty
       FROM inventory.inventory_balance
      WHERE (plant_id, warehouse_id, location_id, item_id) = ANY(...)
        AND COALESCE(lot_id,0) = ANY(...)
      ORDER BY inventory_balance_id
      FOR UPDATE
5. 행 수 판정(§3-2) → available_qty 손검사(§3-3)
6. posting.post(tx, …)   ← move() 의 UPDATE 가 «이미 잠긴» 행을 만진다
7. goods_issue_line.inventory_transaction_line_id 되짚기(§3-5)
8. 상태 전이 + version_no 범프(§3-7)
9. 커밋
```
- **왜 오름차순 한 문장인가** — 두 출고가 서로 다른 순서로 두 잔액 행을 잡으면 교착한다(I-3 §3-2 와 같은 처방 · `ORDER BY … FOR UPDATE`).
- **왜 헤더를 먼저 잠그나** — `PUT …/lines` 도 헤더를 잠그므로(§4-4) 「헤더 → 잔액」 한 방향이면 치환과 전기가 같은 자물쇠에서 직렬화된다.
- ⚠ **채번은 잠금 «전»이다**(I-2 R-2) · `:post` 는 채번을 안 한다(번호는 등록에서 이미 났다).
- ⚠ DB 에 `inventory.lock_balance(...)` 헬퍼 함수가 있으나(baseline:3225) **행마다 한 번 도는 모양**이라 라인 N 개면 왕복 N 회다. 위 한 문장을 쓴다 — 함수를 쓰지 않는 이유를 주석에 남긴다.
- ⛔ **`ON CONFLICT DO NOTHING` 으로 0행을 만들어 두지 않는다** — 없는 행을 만들면 「재고가 없다」가 「0 이 있다」로 바뀌어 §3-2 의 0행 판정이 사라진다. 입고 쪽 `move()` 가 그 INSERT 를 하는 것은 «넣는» 방향이기 때문이다.

### 3-5. `inventory_transaction_line_id` 되짚기 — 입고와 같은 모양

`receipt-posting.ts:146-170` 그대로: posting 이 라인 순서대로 `line_no` 를 매기므로 `orderBy: { line_no: 'asc' }` 로 읽어 자리로 짝짓고, 개수가 다르면 트랜잭션을 던져 되돌린다(「조용히 어긋나느니」). ⛔ `business_date` 를 `new Date(\`${businessDate}T00:00:00.000Z\`)` 로 맞춰 파티션 키를 함께 건다.

### 3-6. `business_date`·`occurred_at` 출처 — C-8

- `businessDate`: **요청 본문**(`PostRequest.businessDate` · 「근거: 공유계약 C-8」). 서버가 수신 시각으로 다시 잡지 않는다.
- `occurredAt`: **요청 본문**(`PostRequest.occurredAt` · C-1). ⚠ 입고는 `receiptDatetime` 을 `occurredAt` 으로 썼는데(별도 칸이 없어서) 출고는 **본문이 직접 준다** — `issued_at` 을 쓰지 않는다.
- ⛔ 도출 함수를 만들지 않는다(CLAUDE.md 「도출 규칙(야간조 경계)은 설계 미정」).
- 형식 검증: `/^\d{4}-\d{2}-\d{2}$/` + `Date.parse` (입고 `goods-receipt.service.ts:156-161` 선례) — 400 `INVALID`.

### 3-7. 상태 `REGISTERED → POSTED` — `transitions.ts` 에 축을 «새로 연다»

실측: `src/core/document-state/transitions.ts` 에 등록된 축은 **다섯**(`mdm.equipment` · `mdm.mold` · `planning.routing` · `trace.lot.lifecycle_status_code` · `app.approval_request`). **`logistics.goods_issue.status_code` 는 없다.** `DocumentStateService.assertTransition` 은 미등록 (칸,액션)을 **던진다**(F-6).

⇒ I-4 가 이 축의 **첫 줄**을 등록한다(`plan-api.md` §5.1 A 표의 `document-post` 행 그대로):
```
'logistics.goods_issue.status_code': {
  'document-post': { from: ['REGISTERED'], to: 'POSTED',
                     sourceOperation: 'POST /logistics/goods-issues/{goodsIssueId}:post' },
},
```
- **`conflictStatus` 는 400** — `:post` 의 400 은 `ErrorResponse`, 409 는 `ConflictResponse` 이고 계약이 「지금 상태에서는 안 된다」를 어디에 뒀는지가 자리마다 다르다(`document-state.service.ts` 주석). 계약 `GoodsIssueLineUpsert` 가 **「전기된 전표의 라인은 바꿀 수 없다 — 400 `STATE_LOCKED`」**로 400 을 명시했으므로 같은 축의 `:post` 재전기도 **400 `STATE_LOCKED`** 로 맞춘다. 409 는 If-Match 저장 충돌 전용이다(공유계약 G-1 · `error-codes.ts` 주석).
- **취소 두 전이(`document-request-cancel`·`document-cancel`)는 I-5 가 같은 표에 더한다** — I-4 는 열지 않는다(사용처 0).
- **`version_no` 범프**: `updateMany({ where: {goods_issue_id, version_no}, data: { status_code: 'POSTED', version_no: {increment:1}, updated_by } })` + `assertUpdated(count)`.
- **응답 ETag**: 계약이 `:post` 200 에 헤더를 **안 선언**했다 ⇒ **안 내린다**(I-3 §6-3 선례) → 「알려둘 것」.
- `PUT …/lines` 는 상태를 **안 옮긴다** — `REGISTERED` 에서만 허용하고 부모 `version_no` 만 올린다.
- `:request-approval` 은 상태를 **안 옮긴다** — `plan-api.md` §5.1 A 표 마지막 줄(「⛔ 상태를 옮기지 않는다」) · `LOGISTICS_DOCUMENT_STATUS` 4값에 「승인대기」가 없다.

### 3-8. 이중 전기가 되지 않는 구조 — **세 겹이고, 셋 다 필요하다**

| 겹 | 무엇이 막나 | 한계 |
|:-:|---|---|
| ① `runIdempotent` | 같은 `Idempotency-Key` 재전송을 앞의 응답으로 흡수 | 키가 «다르면» 안 막는다 |
| ② `posting.post()` 의 선조회 + `uq_inventory_idempotency (idempotency_key, business_date)` | 같은 `(GOODS_ISSUE:번호, 영업일)` 재전기를 흡수해 `alreadyPosted:true` | ⛔ **영업일이 다르면 «다른 키»다** — 자정을 넘긴 오프라인 재전송이 두 행을 만든다(C-8 이 경고한 바로 그 구멍) |
| ③ **상태 잠금** `document-post` `from:['REGISTERED']` | 두 번째 `:post` 는 상태가 `POSTED` 라 **400 `STATE_LOCKED`** — 영업일이 달라도 막는다 | 없음 |

⇒ **①+③ 둘 다** 건다(브리프 물음의 답: 「`runIdempotent` + 상태 잠금 둘 다」). ②는 코어가 이미 하는 것이고 여기서 «기대지 않는다».
⭐ **③이 정본이다** — `plan.md` §5 규칙 3(If-Match 필수)이 함께 걸려 두 번째 호출은 낡은 토큰으로도 409 를 받는다. 셋이 겹쳐야 오프라인 큐(C-9)에서 안전하다.
⚠ `transaction_no` 도 `uq_inventory_transaction_no (transaction_no, business_date)` 라 같은 한계를 갖는다 — ③이 없으면 영업일만 바꿔 두 원장 전표가 선다.

### 3-9. `postImmediately` — 한 트랜잭션 안에서 등록 + 전기

계약: 「참이면 등록과 동시에 전기한다. **두 번 호출로 나누면 오프라인 큐에 중간 상태가 남는다**」 · `x-internal-note` 「`postImmediately` 는 「화면이 한 버튼이면 오퍼레이션도 하나」 규칙(02-URL동작규약 §2-2)을 한 리소스에서 지키기 위한 것이다. **세 화면의 버튼 구조가 서로 다르다.**」

| 화면 | 보내는 값 | 근거 |
|---|:-:|---|
| `M-01-08` 자재출고 피킹 | **true** | `M-01-09` §8 #1 「`M-01-08` 출고 확정이 `postImmediately: true` 라 전표가 항상 전기완료」 |
| `W-01-05` 공급사 반품 | **true**(재수립 R-6 확정) | `derived-permissions.ts:170` `:post` 소유가 `W-01-06`·`W-04-10` 뿐 · §5-7 유일 액션 [반품 처리] · §5-1 「반품 = 전표+라인+`inventory_transaction`」 |
| `W-01-06`·`W-04-10` 폐기 | **false** | 「승인 완료 후에만 출고」(§5-5 · REQ-PR-0028) |

- **구현**: `postImmediately === true` 면 **등록과 같은 `$transaction` 안에서** §3-1~§3-7 의 전기 함수를 부르고 `status_code` 를 `POSTED` 로 «만든다». ⛔ 이때 `document-post` 전이를 부르지 않는다 — 입고와 같은 자리다(`plan-api.md` §5.1 A 표 「(전기와 동시) (없음) → `POSTED` … `REGISTERED` 에 머무는 자리가 없다」). `from` 이 없는 전이라 표에 담을 수 없다.
- **승인 게이트**: `postImmediately=true` 로 오면 그 전표에는 승인 요청이 있을 수 없다(방금 만들었다) ⇒ 게이트가 «언제나» 통과한다. ⛔ **폐기 출고를 `postImmediately=true` 로 보내면 승인을 건너뛴다** — 계약이 막지 않았다 ⇒ 문의 030 갈래 ③.
- **응답**: 둘 다 201 `GoodsIssueDetailResponse` + ETag. 전기했으면 `statusCode: 'POSTED'`.

## 4. 승인 판정 — `assertApproved` 코어

### 4-1. 시그니처 — I-1 이 이름을 적어 둔 자리를 채운다

`src/core/approval/approval.service.ts` 실측: `request`·`assertNoOpenRequest`·`selectRoute`·`expandSteps`·`currentStep`·`approve`·`reject` 일곱뿐. **`assertApproved` 는 없다** — I-1 §3-4 가 이름만 적고 「⛔ I-1 에서 만들지 않는다 — 사용처가 0이다」, I-2 §4-4 가 「첫 사용처는 **I-4**(`goods-issues:post`)와 I-14」로 미뤘다.

```ts
/**
 * 「승인 전이면 400」의 자물쇠. 대상 문서의 `:post` 가 부른다 — 승인은 자물쇠만 풀고(J-8)
 * 실행은 여기서 «읽어» 가른다(I-1.md §3-4 상태 조회 갈래).
 * ⛔ 대상 표의 approval_request_id FK 를 보지 않는다 — 정본은 다형 축이다(plan.md §5 #12).
 */
async assertApproved(
  tx: Tx, targetTypeCode: string, targetId: bigint, approvalTypeCode: string,
): Promise<void>;
```
- **인자에 `approvalTypeCode` 가 반드시 있다** — I-1 R-2 축 그대로. `goods_issue` 는 두 유형을 탄다(`GOODS_ISSUE_DISPOSAL` 업무 승인 · `GOODS_ISSUE_CANCEL` 취소 승인). 유형을 안 받으면 I-5 의 취소 품의를 I-4 가 「승인됐다」로 읽는다(`plan.md` §5 #12 가 막으려는 바로 그것).
- **조회 축**: `(target_type_code, target_id, approval_type_code)` — I-1 A6 이 깐 `ix_approval_request_target` 이 받는다(`schema.prisma:102`).
- **판정**(`approval_request.status_code` 3값 실측 — `PENDING`·`APPROVED`·`REJECTED` · `transitions.ts` `app.approval_request.status_code`):

| 그 축의 행 | 응답 |
|---|---|
| 0건 | ⭕ **통과** — 「승인을 타지 않은 출고」다(§4-2) |
| `APPROVED` 가 하나라도 있다 | ⭕ 통과 |
| `PENDING` 만 있다 | 400 **`APPROVAL_IN_PROGRESS`** — 「기다려라」 |
| `REJECTED` 만 있다 | 400 **`APPROVAL_REQUIRED`** — 「다시 올려라」(J-6 「번복은 새 요청」) |

- ⛔ **`assertNoOpenRequest` 와 대칭이지 반대가 아니다** — 그쪽은 `PENDING` 하나만 보고 400 을 내고, 이쪽은 `APPROVED` 를 찾는다. 한 함수로 합치지 않는다(뜻이 다르고 호출자가 다르다).
- ⚠ **`APPROVED` 판정에 시각 순서를 안 본다** — 한 전표에 살아 있는 `PENDING` 은 하나뿐이고(`assertNoOpenRequest`) `APPROVED` 는 종결이라, 「승인된 뒤 다시 상신했고 그것이 반려됨」이면 통과한다. 계약이 그 경우를 안 적었다 ⇒ §8 판정표 ⓔ.

### 4-2. ⭐ 「승인이 필요한 전표」를 무엇으로 가르나 — **S04 초안을 기각한다**

`plan-api.md` S04 초안: 「계약이 `reasonCode` → 결재선 파생(G-31)이라 적었다 → **결재선이 그 유형·사업부로 존재하면 승인 필수**로 읽는다」.

**⛔ 기각 근거 셋(전부 실측)**
1. **`businessUnitId` 가 8자리 전부 `null` 이라 「그 사업부로」가 사라진다**(문의 022 · `approval.service.ts:request` 주석). 남는 것은 「`GOODS_ISSUE_DISPOSAL` 활성 결재선이 있는가」 하나인데, 그것은 **전표와 무관한 전역 조건**이다 ⇒ 결재선을 한 벌 등록하는 순간 **생산 투입 출고(M-01-08)까지 전부 400** 이 된다. M-01-08 §5-8 은 「출고 확정」에 승인 조건이 **없다**.
2. **`reasonCode` 로 가르려 해도 「폐기」를 가리키는 값이 없다.** 시드 `GOODS_ISSUE_REASON` 5값 = `IQC_FAIL`·`OVER_RECEIPT`·`DEFECT_AFTER_RECEIPT`·`WRONG_SHIPMENT`·`OTHER`(`seed.ts:574-583`) — 계약 `reasonCode` 설명도 같은 5값이다. **폐기가 없다.** 그런데 `seed.ts:387-388` 은 「⛔ 폐기는 출고 *유형*이 아니라 기타출고의 *사유*다. `issue_type_code=OTHER` 로 두고 `reason_code` 로 가른다 — **승인 게이트도 유형이 아니라 사유를 보고 건다**」라 적었고 계약 `issueTypeCode` 설명도 같다. ⇒ **게이트를 걸 축이 데이터에 없다.**
3. `issueTypeCode='OTHER'` 로 대신 가르는 안도 계약 문자에 어긋난다 — 위 문장이 「유형이 아니라 사유를 보고」라 명시했다.

**⭕ 채택 — 「그 전표에 `GOODS_ISSUE_DISPOSAL` 승인 요청이 하나라도 있으면 승인을 타는 전표다」**

§2 **0단계 선례**(판단이 아니라 계약 문장 인용):
> `GoodsIssue.approvalRequestId`: 「이 출고가 어느 승인 요청에서 나왔는지 되짚는 식별자. **비어 있으면 승인을 타지 않은 출고다.** 폐기 출고 화면이 이 값으로 승인을 보이고, **승인 없이 나간 건을 가려낸다.**」

계약이 ⓐ 승인을 안 탄 출고가 존재함을 인정하고 ⓑ 그것을 «사후에 화면에서 가려낸다»고 적었다 ⇒ **서버가 사전에 전건을 막는 축이 아니다.**
구현: `:post` 는 언제나 `assertApproved(tx,'GOODS_ISSUE',id,'GOODS_ISSUE_DISPOSAL')` 를 부르고, 그 축에 행이 0건이면 통과한다(§4-1 표 1행).

| 화면 | 흐름 | 결과 |
|---|---|---|
| `M-01-08`·`W-01-05` | 상신 안 함 → `:post`(또는 `postImmediately`) | 통과 — 원장 out |
| `W-01-06`·`W-04-10` | `POST`(false) → `:request-approval` → 결재함 승인 → `:post` | `PENDING` 이면 400 `APPROVAL_IN_PROGRESS` · `APPROVED` 면 통과 |

- ⛔ **FK `approval_request_id` 를 판정에 쓰지 않는다** — `plan.md` §5 #12(「승인 판정은 언제나 다형 축으로 조회한다 — I-5 가 I-4 의 품의 흔적을 덮지 않게」). FK 는 `:request-approval` 이 채우고 응답이 실어 내리는 «표시용»이다(P/O `purchase-order.service.ts:320` 선례와 같은 모양).
- **남는 구멍 둘** → 문의 030: ① 폐기 출고를 상신 없이 `:post` 하면 그냥 나간다 ② `postImmediately=true` 면 상신 자체가 불가능하다(§3-9).
- **3단계 흔적**: `// 「승인이 필요한 전표」를 가르는 축이 데이터에 없다 — 상신 흔적으로 가른다(I-4.md §4-2 · 문의 030)` + e2e `전기 — 상신하지 않은 출고는 승인 없이 전기된다(계약 「비어 있으면 승인을 타지 않은 출고다」)`.

### 4-3. 문의 022 와의 맞물림 — 결재선 없는 사업부의 폐기 출고는 전기되나

- `:request-approval` 은 `selectRoute(tx,'GOODS_ISSUE_DISPOSAL', **null**)` 로 부른다(022 판정 · `approval.service.ts` 주석 「⚠ P/O 만 전표 값을 준다. 나머지는 `null`(공통본)」). ⇒ **사업부 축이 실제로 안 선다.** 전 사업부 공통본이 없으면 400 `ROUTE_NOT_FOUND`(계약 명시).
- **질문의 답**: 결재선이 아예 없으면 `:request-approval` 이 400 이라 승인 요청이 생기지 않고, 그러면 §4-2 판정에 따라 **`:post` 는 통과한다** — 폐기 출고가 승인 없이 나간다. 화면(W-01-06 §6)은 「결재선이 없다 → ⛔ 상신 차단 … `W-06-15` 에서 먼저 정의한다」로 사람을 막지만 **API 는 안 막는다**. ⇒ 문의 030 갈래 ①과 같은 뿌리.
- ⚠ **022 의 권고안 ② 는 실측상 성립하지 않는다** — 요청서가 「전표 라인 품목의 `item.business_unit_id`(자재/제품)로 판단한다」를 권고안으로 적었으나 **`mdm.item` 에 `business_unit_id` 칸이 없다**(`awk '/^model item/,/^}/' | grep business_unit` → **0건**). 사업부 축은 `mdm.item_bu_item_map`(품목 «대응표»)뿐이다. ⇒ 022 는 **갈래 ④(사업부 축을 쓰지 않는다 · 공통본만)** 로 가고, 이 정정을 「알려둘 것」에 싣는다(§8). ⛔ 요청서 파일은 이 슬라이스에서 고치지 않는다(구현 시).

### 4-4. 승인 대기 중 라인 치환 — **막는다**(계약 밖 자물쇠 하나)

- 계약은 **`POSTED` 만** 막았다(`GoodsIssueLineUpsert` 「전기된 전표의 라인은 바꿀 수 없다 — 400 `STATE_LOCKED`」). 승인 대기(`REGISTERED` + `PENDING`) 중 치환은 열려 있다.
- ⛔ 그러면 **승인자가 본 것과 전기된 것이 달라진다** — 10개를 승인했는데 100개가 나간다. 원장은 되돌릴 수 없다(역트랜잭션은 I-5 다).
- **§2 1단계**: 「승인 대기 중에 라인을 고칠 때만」 갈린다 ⇒ **가장자리**. **2단계 기준 2(거부하는 쪽)** — 거부→허용은 호환 완화.
- **판정**: `PUT …/lines` 는 그 전표에 `GOODS_ISSUE_DISPOSAL` `PENDING` 요청이 있으면 **400 `APPROVAL_IN_PROGRESS`**(코드 재사용 — `plan.md` §5 규칙 6 「조회의 사유와 실행 오류가 같은 문자열」).
- ⚠ **I-2 의 023 판정과 갈린다** — P/O 는 같은 구멍을 «열어 둔 채» 문의로 올렸다(023 갈래 ③). 갈리는 이유: **P/O 에는 `:post` 가 없어 승인 뒤에 일어나는 일이 계약에 0건**이고(I-2 §5-2), 출고는 승인 뒤 «원장»이 움직인다. 되돌림 비용이 다르다. 이 차이를 §8 판정표 ⓕ 에 적고 문의 030 본문에 인용한다.
- **상신 뒤 `:post` 전에 라인이 바뀌면 승인이 무효인가** — **계약이 말하지 않는다.** 위 자물쇠로 API 경로에서는 일어날 수 없으므로 «재판정을 만들지 않는다»(§2 2단계 기준 5 — 새 개념 0). 흔적: 문의 030 갈래 ②.

`assertApproved` 본체 ~30 + 주석 ~15. `ERROR_CODE.APPROVAL_REQUIRED` 한 줄. 단위 테스트는 별도. ⇒ PR ②(§9)에서 **비테스트 ~45줄** — CLAUDE.md 「코어는 전용 PR, diff ≤ 200」을 크게 밑돈다.

### 5-2. 「단일 지점」은 실재하는데 **비어 있다**

결정 10 의 정본은 `lot.status_code` 문자열 집합이 아니라 **판정유형별 통제표**다.

### 5-3. 재판정 — §2 절차

- **0단계 선례** — 있다. ⓐ 계약이 판정의 단일 지점을 `JudgmentTypeControl.blocksIssue` 로 못박았고 그 표가 실재한다. ⓑ 그 표가 비어 있다 ⇒ **오늘의 데이터가 내는 답은 「막는 것이 없다」**이다. ⓒ 화면은 갈래마다 반대를 요구한다(§5-1).
- **1단계** — 「보류·불량 LOT 을 출고할 때만」 갈린다 ⇒ **가장자리**(통합의 판단과 같다).
- **2단계** — 기준 2(거부하는 쪽)가 먼저 걸리지만, **거부가 계약이 정의한 업무(폐기·반품)를 없앤다.** README §2 2단계의 기준은 「나중에 뒤집는 비용이 싼 쪽」이고, «업무를 없애는 거부»는 뒤집기 전까지 그 오퍼레이션을 못 쓰게 만들어 비용이 가장 크다. 다음 기준 4(조용히 도출하지 않는 쪽) → **상태 문자열 집합을 서버가 지어내지 않는다.** 그 다음 기준 5(새 개념 수) → **새 상수 집합 0.**

**⭕ 판정 — I-4 는 LOT 상태로 차단하지 않는다. 대신 통제표를 «읽는다».**
```
1) trace.lot.status_code 를 읽어 그 값의 code_value 를 찾고
2) mdm.judgment_type_control 에 그 code_value 의 행이 있고 blocks_issue = true 면 400 STATE_LOCKED
3) 행이 없으면 통과한다  ← 오늘은 언제나 이쪽이다(JUDGMENT_TYPE 값 0개)
```
- ⛔ **문자열 집합(`{DEFECTIVE,SCRAPPED,INSPECTION_PENDING}`)을 코드에 박지 않는다** — `transitions.ts` 머리 주석이 세운 원칙(「코드에 상태 문자열을 박으면 값이 확정될 때 찾아 고칠 수 없다」)과 같다.
- ⚠ **`lot.status_code`(LOT_STATUS 4값)와 `JUDGMENT_TYPE` 은 같은 코드 그룹이 아니다.** `judgment_type_control.lot_status_code` 가 둘을 잇는 칸이다(판정유형 → 도달 LOT 상태). 값이 오면 그 칸으로 역인덱스를 만든다. **오늘은 그 매핑도 비어 있다** ⇒ 2)의 조회가 늘 0행이다. 흔적: `// JUDGMENT_TYPE 값 목록이 0개라 오늘은 아무것도 막지 않는다 — 결정 10 의 단일 지점은 mdm.judgment_type_control 이다(I-4.md §5-3)`.
- ⭐ **I-20 이 정본으로 바꿀 것이 「집합을 넓히는 것」이 아니라 「표를 채우는 것」이 된다** — `plan-integration.md` 374행(「I-20 이 잠정 판정을 정본으로 바꾼다」)의 실체가 여기서 갈린다. §10 에 싣는다.
- ⚠ **`M-01-08` 의 「보류 LOT 스캔 차단」은 I-8 이 «피킹»에서 진다**(`blocks_picking` 축). I-4 의 `:post` 는 이미 피킹된 것을 내보내는 자리라 축이 다르다. 이 경계를 §7 인계에 적는다.
- ⚠ `trace.lot_hold` 는 보지 않는다 — 「LOT 재고 상태(보류→가용)」와 「의심자재 보류 기록」은 다른 축이고 뒤의 것은 `W-03-02` 소관이다(입고 `receipt-posting.ts` 머리 주석 · 회신 2026-09-05 · 되돌림 §Z-8). W-01-05 §5-5 도 「반품해도 Hold 는 유지된다」라 적었다.

### 6-4. `@Contract` · `X-Worker-No` · 404 · 409 봉투

- `@Contract('METHOD /path')` **7건 전건**. `:post`·`:request-approval` 은 `@Post(':goodsIssueId\\:post')` 형태(경로에 콜론 — I-2·I-3 선례).
- **`X-Worker-No` 는 등록 1건뿐**(`WorkerNoOptional` — jq 실측). 헤더가 없어도 400 을 내지 않는다(`plan.md` §5 규칙 9). 주체는 계정 세션(`created_by`·`updated_by`).
- **404**: 계약이 선언한 것은 **상세 GET 하나**다. 대상이 있는 쓰기 3건(`PUT …/lines`·`:post`·`:request-approval`)과 `GET …/lines` 는 **404 미선언인데 우리는 404 를 낸다** — I-2 R-1·I-3 과 같은 판정, 「알려둘 것」.
- **409 봉투**: 기본 `ConflictResponse`. 도메인 전용 넷(`Production`·`Quality`·`Shipment`·`StockReinstatement`)에 출고가 없다.
- **`@db.Date` 캐스팅 금지**: 목록의 `issuedAtFrom`/`issuedAtTo` 는 `issued_at timestamptz` 를 자른다 ⇒ **UTC 경계**(입고 `receiptDateWhere` 선례 · 「하노이 06:00 출고가 전날에 잡힌다」) → 「알려둘 것」.
- **정렬**: 계약 침묵 ⇒ `issued_at desc, goods_issue_id desc`(입고·P/O 선례).

### 6-5. e2e 픽스처 · 정리 순서

**파일**: `test/logistics-goods-issue.e2e-spec.ts`. 상수 `PREFIX='GIE2E'` / `LOGIN_ID='e2e-gi-probe'` / `ROLE='E2E_GI'` — 기존 전건과 겹침 **0**(실측: `GRE2E`·`POWE2E`·`IRE2E`·`ASNE2E`·`INVBAL`·`INVTX`·`POST-E2E`·`LOTE2E`·`E2E_PUTAWAY` …).

**⭐ 입고 e2e 픽스처는 «재사용하지 않는다».** 근거 셋(I-3 이 같은 결론을 냈다):
1. `logistics-goods-receipt.e2e-spec.ts` 는 `PREFIX='GRE2E'` 로 자기 조직·품목·창고를 세우고 `cleanup()` 이 그 접두어로만 지운다(:574-613) — 스위트 사이에 공유하는 자원이 없다.
2. `alphabetical-sequencer.js` 가 파일 이름 순으로 돌린다 ⇒ `logistics-goods-issue` 가 `logistics-goods-receipt` **앞**이다. 뒤 스위트의 픽스처를 앞에서 쓸 수 없다.
3. ⚠ **GR 스위트의 `cleanup()` 첫 줄이 `TRUNCATE inventory.inventory_transaction_line, inventory.inventory_transaction CASCADE` 다**(:575) — `goods_issue_line.inventory_transaction_line_id` FK 때문에 **CASCADE 가 `logistics.goods_issue_line` 까지 비운다**. 우리 스위트가 먼저 끝나므로 무해하지만, **역순으로 돌면 조용히 깨진다** — 시퀀서 고정에 기대는 자리라 주석으로 남긴다.

**잔액을 세우는 법** — 출고는 잔액이 있어야 전기된다.
- ⭕ **입고 API(`POST /logistics/goods-receipts`)를 «부른다»** — 이미 구현·초록이고 원장·잔액·적치를 한 번에 세운다. LOT·위치·품목을 우리 PREFIX 로 만들고 그 API 로 잔액을 올린다. 직접 INSERT 보다 낫다: `inventory_balance` 는 트리거가 지키는 표라 손으로 넣으면 차원 11칸을 우리가 맞춰야 하고, 그것이 §3-2 가 읽는 바로 그 값이다.

## 7. I-23 · I-8 인계 모양

### 7-1. I-23(출하)이 재사용할 **데이터 모양** 타입의 자리

`plan-integration.md` 399~400행: 「⭐ `POST /logistics/shipments` 가 서버 내부에서 `goods_issue` 를 만들고 전기한다 — **I-4 의 서비스를 도메인 간 호출로 부르지 않는다** … **shipment 가 `posting.post()` 를 직접 부르고 `goods_issue` 를 만든다.** 새 코어를 만들지 않는다. 대신 `goods_issue` 를 만드는 «데이터 모양»은 **I-4 의 타입을 재사용한다**.」

**판정 — 타입만 export 한다. 서비스는 export 하지 않는다.**

| 무엇 | 자리 | I-23 이 |
|---|---|---|
| `GoodsIssueHeaderWriteInput` · `GoodsIssueLineWriteInput`(순수 인터페이스) | `src/logistics/goods-issue/issue-posting.ts` 에서 `export` | **`import type` 한다** |
| `postIssue(tx, posting, input, …)` 함수 | 같은 파일 `export` | ⛔ **안 부른다** — 부르면 shipment 가 goods-issue 의 «동작»을 타게 된다 |
| `GoodsIssueService`(Nest `@Injectable`) | `goods-issue.service.ts` | ⛔ **안 부른다**(아키텍처 §1) |

- **「타입만이면 규칙에 걸리는가」 — 걸리지 않는다.** `server-architecture.md` §1 이 금지한 것은 「도메인이 다른 도메인의 **service** 를 부르지 않는다」이다. 인터페이스는 런타임 의존이 아니고(SWC 가 `import type` 을 지운다) DI 그래프에 선이 생기지 않는다. 선례: `receipt-posting.ts` 가 `GoodsReceiptCreate`·`GoodsReceiptLineCreate` 를 export 하고 `goods-receipt.service.ts`·컨트롤러가 나눠 쓴다 — 같은 도메인 안이지만 **모양은 같다**.
- ⚠ **경계선** — I-23 이 `postIssue()` 를 부르고 싶어지면 그때가 「코어로 올릴 때」다. `plan-integration.md` 가 §2 2단계 기준 5 로 **안 올린다**고 이미 판정했으므로, I-4 는 **`postIssue()` 를 `issue-posting.ts` 안에 두고 `src/core/` 로 올리지 않는다.**
- **인계 문장**: 「I-23 은 `import type { GoodsIssueHeaderWriteInput, GoodsIssueLineWriteInput } from '../goods-issue/issue-posting'` 만 한다. `goods_issue` INSERT 와 `posting.post()` 호출은 shipment 가 자기 파일에 다시 적는다.」

### 7-2. I-8(피킹)이 같은 등록 경로를 타는가 — **탄다**

- `sourceDocumentTypeCode='PICKING_ORDER'` 는 `GoodsIssueCreate` 의 enum 3값 중 하나이고, `goods_issue_line.picking_line_id` 가 **이미 있다**(nullable · W-01-05 §5-4 「nullable 이라 성립한다 — 같은 테이블이 두 경로를 받는다」).
- ⇒ **I-8 은 새 등록 경로를 만들지 않는다.** `M-01-08` 이 `POST /logistics/goods-issues`(`postImmediately:true`)를 그대로 부른다.
- **I-8 이 더하는 것 셋**: ⓐ `picking_order`/`picking_line` 을 만드는 경로 ⓑ `posting` 의 `reserved_qty`·`picked_qty`(코어 확장 — `plan.md` §3) ⓒ **`blocks_picking` 축의 LOT 차단**(§5-3 · `M-01-08` §6 「보류 LOT 스캔 → 차단」).
- ⚠ **I-4 는 `picking_line_id` 를 «받아 저장만» 한다** — 계약 `GoodsIssueLineUpsert.pickingLineId` 가 선택 칸이고, FK 검증(존재하는 `picking_line` 인가)만 한다. 피킹 수량과의 대조(`ck_picking_qty`)는 I-8 몫이다. 흔적 주석 한 줄.
- ⚠ **예약 축을 안 건드린다** — `inventory-posting.service.ts` 머리 주석 「⛔ `reserved_qty`·`picked_qty` 는 건드리지 않는다 … 별도 코어다」. I-4 의 §3-3 손검사가 `available_qty`(예약을 뺀 값)를 보므로 **예약된 재고는 I-4 경로로 나가지 않는다** — I-8 이 `picked_qty` 로 옮긴 뒤에야 나간다. 이 순서를 인계에 적는다.
