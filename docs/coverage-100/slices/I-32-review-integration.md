## M1 — 이미 확정된 집계 규칙과 조건부 미정을 한 본길로 묶었다

**[Major] 초안:319,453~466,526,691~706.** 화면은 다음을 이미 확정했다.

- `W-05-08:146~163`은 “확정 — 거르지 않는다. 별도 줄로 나눈다”이며 일반 사유에 경미 건을 섞으면 평균이 뜻을 잃는다고 설명한다. 계약:4513도 actual에 포함하면서 줄을 나누라고 한다. 따라서 **경미를 일반 사유행과 분리할지**는 새 미정이 아니다. `minorStop*`로 별도 값을 내고 가짜 reasonCode는 만들지 않는다.
- `W-05-08:250~260`은 폐지 사유를 **미분류로 묶되 원본 코드 표시**로 확정했다. 원본 코드가 존재하는 폐지 행의 표시 정책과 reason 자체가 null인 과거행의 표현 결손을 분리한다. 전자는 새 문의가 아니다.
- `W-05-08:304`는 minor 정책이 **공장 단위면 충분**하다고 명시한다. ITEM/PROCESS를 설비·작업에서 새로 추론할 필요가 없다. 정책의 유효일·복수 공장/기간에 다른 threshold가 걸리는 경우만 남긴다. 기본5는 미설정일 때뿐이며 0/음수를5로 바꾸지 않는다.

**최소 수정:** §7/§9의 위 세 자리를 0단계 해소로 바꾸고 S11~13 기대값을 고정한다. 남은 비중·평균은 계약 예시(2320분/31건=74.8, 2320/7680≈30.2%)와 화면 산식을 먼저 대조한다. 일반 사례까지 “분모 미정”으로 확대하지 않는다.

기간 경계·분 정밀도도 별개다. **기간 안에서 시작하고 끝나는 정수분 구간**은 선택/clip/반올림 후보가 같은 결과다. 시작 전부터 이어지는 구간, 기간 밖으로 나가는 구간, 소수분, 열린 작업세션, 복수 threshold만 갈리면 README §2의 **가장자리**이며 해당 조건의400 명시 거부를 검토할 수 있다. 이 사례만으로 정상 query 전체가 본길 결손이라고 결론내리지 않는다. 목록의 started_at 선택은 유지한다.

O2 보류는 이들을 걷어낸 뒤 **남는 계산 정의**로 좁힌다. 달력의 정상 계획구간을 어떤 교대로 구성하여 HOLIDAY/PARTIAL에서 차감하는지, 완료 보전을 어떤 엔티티·완료일로 세는지는 현재 연결 자료만으로 단일 SQL을 확정하기 어렵다. 단순 “I31 미구현”·“DB0행”은 보류 근거가 아니다.

검증 추가: `경미는 actual에 포함되고 일반 사유행 건수와 분리된다`, `폐지 사유는 미분류 표시와 원본 코드를 함께 보존한다`, `일반 정수분 자료는 경계자료 거부 정책과 독립하여 계산된다`.

## M2 — PUT/close의 구체적인 상태잠김400보다 일반422를 우선했다

**[Major] 초안:359~363,397~408,581~589.** 계약 `equipment-05설비툴.json:1908,1990`은 두 오퍼레이션에서 **“업무 규칙 위반(상태 잠김·참조 존재)은 … 400”**이라고 명시한다. 일반적인 `422: 업무 규칙에 걸린다`가 이 구체 문구보다 좁은 규칙이라는 초안 해석은 성립하지 않는다. I30 R-7도 같은 원리로 구체400을 우선했다.

**최소 수정:** O6에서 DONE/미등록 상태의 고장을 새로 연결하는 STATE_LOCKED는400, O5의 이미 종료된 행 STATE_LOCKED도400 후보로 통합한다. O4의 중복open은 구체400 문구가 없으므로422를 유지한다. close400 응답표 누락은 입력/헤더400 누락과 함께 문의에 남긴다. 미래/역전 등 다른 조건은 각 operation의 구체 문구에 맞춰 별도로 판정하며 422 전부를400으로 바꾸지 않는다.

검증 추가: `POST 중복open422와 PUT 완료고장 새연결400은 다른 봉투다`, `close 재생은200이고 다른키의 이미닫힘은400 STATE_LOCKED다`. 뒤 검증은 O5 시각 규약 해소 후 활성화한다.

## 1·2·3축을 지탱하는 근거

물리 `schema.prisma:4147`은 사번/메모/version 칸이 없고 reason nullable, type NOT NULL이다. `closed_by`는 app_user FK다. 초안의 forward-only 추가·완화, 백필0, 최초사번과 계정 분리, nullable workSessionId 유지가 맞다. 구데이터1행 때문에 전체 코드 구현을 멈추지 않고 **해당 환경 배포**를 제한한다. 조회·수정 매퍼 실패는 내부 결손으로 실패시키되 그 행을 목록에서 숨겨 total을 바꾸지 않는다.

P05:91,119~144 및 공유계약 C12:1862~1930은 단말 시각 보존·같은 시계의 시작/종료를 전제한다. O5 계약:1925의 “지금”은 서버 처리시각이라는 명문이 아니고, requestBody 부재는 단말시각을 금지한다는 명문도 아니다. 오프라인 종료10:05/도착10:30에서10:05를 복원할 입력이 없다. **발생시각 전달 규약 또는 명시적인 서버시각 예외**가 최소 해소다. PUT을 O5의 대체로 삼으면 필수 If-Match가 다른 오프라인 계약을 바꾸므로 그렇게 완료 처리하지 않는다.

P05:186~190의 끝≥시작·겹침허용·중복시작금지와 초안 잠금은 정합한다. 없는 open행을 잠그는 대신 항상 존재하는 equipment행으로 직렬화하는 선택이 맞다. 길이0·맞닿음은 overlap에서 제외하고 모든 필터를 page 전에 적용한다. 기존 연결이 DONE이 된 뒤 메모만 고치는 길은 유지한다. I30:426~447은 breakdown만 잠그고 설비/비가동을 쓰지 않아 현재 계획끼리 역순 잠금은 없다. I31이 새로 설비를 잠그는 쓰기를 만들면 같은 순서를 인계해야 한다.

## 4축의 실제 의존성과 집계 단위

- `work-session.service.ts:74`는 equipment 생략을 null로 저장한다. `schema.prisma:2986`의 실제 세션을 합하며 `work_order_resource_assignment:4540`의 복수 계획배정 JOIN으로 증폭시키지 않는다. STOPPED여도 ended_at=null이면 열린 세션이다. 무장비 세션은 조업시간 포함·설비별 제외·별도 건수라는 계약:4552를 유지한다.
- `I-30.md:324~339`의 연결 비가동은 **고장별 닫힌 원본행 합**, I32 actual은 **설비별 union**이다. 전자가 후자보다 커도 오류가 아니다. 같은 고장에60분과30분의 중첩 구간을 연결해 I30=90분, I32=60분을 단언한다. 고장완료·보전마감·작업 STOP/RESUME로 비가동을 자동 생성/종료하지 않는다.
- `maintenance_order`에는 DONE 상태·유형·대상이 있고 `maintenance_result`에는 완료시각과 order FK가 있다(`schema:4210~4264`). **재료는 실재한다.** 계약 Result.closed는 “지시를 마감했는지”이며 finishedAt은 nullable(`equipment:4003,4062`). W05-06:214~222는 지시 마감과 개별 실적을 구별한다. 여러 실적/지시없는 실적을 단순 row count로 세지 말고, 완료 건의 엔티티·기간 시각을 I31 인계에서 확정한다.
- 지시없이 완료한 고장은 DONE/completed_at을 읽고 직접 FK와 BREAKDOWN 트리거 **둘 다 부재**여야 한다. 취소지시도 발행흔적이다. I30 완료 보류는 기존 DONE 데이터가0이라는 근거가 아니다.

## 5축 — 원자성·소유·예산과 Minor

`IdempotencyService.run:56~90`은 전달tx에서 업무와 응답 저장을 함께 커밋한다. `master-write.ts:24,35`는 tx를 전달하지 않으므로 로컬 createWithin/updateWithin을 직접 연결하는 계획이 맞다. actor/worker 지문, If-Match 지문 제외, 재생 전 형식·재생 뒤 업무 존재 검증을 구분한다. 응답 매퍼와 멱등 완료 실패 rollback 테스트를 P3/P4에 모두 둔다.

현재 `AppModule`은 인증→권한→계약→멱등→토큰 순서다. X-Worker-No는 인증 대체가 아니다. POST/close는 derived P05-02에 있고 PUT은 자신의 manual행만 추가한다. 조회403을 새로 만들지 않는다. 현장 로그인 생략·CORS 제한은 배포 노트에 남겨 API4건을 POP 전체 완료로 보고하지 않는다.

**[Minor N1] 초안:307.** 유효하지 않은 plant.timezone_code는 사용자의 날짜 입력 오류가 아닌 내부 설정 결손이다. I30:278의 INTERNAL_ERROR와 맞추고, 기간 없는 openOnly 조회는 TZ를 불필요하게 평가하지 않는다. 검증: `잘못된 공장TZ는 내부 결손이며 기간없는 open목록은 독립이다`.
