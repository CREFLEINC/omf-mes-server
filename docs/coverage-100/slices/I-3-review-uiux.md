ⓙ **`:split` 이 차량번호를 버린다.** `W-01-03` §4-A 는 「두 건 모두 `M-01-01` 의 헤더 구조를 **그대로 쓴다**」인데 `SplitPart` 에 `vehicleNo` 가 없다(§1-3 이 실측만 하고 처분을 안 적었다). **초과 분리로 간 도착은 차량번호가 통째로 없어진다.**

ⓚ **오프라인 큐가 두 호출을 못 잇는다.** `M-01-06` 은 `M-01-01` 등록 응답의 **라인 id** 를 경로에 담아야 부를 수 있는데(`POST /inbound-receipt-lines/{id}/variances`) 두 화면 모두 §6 이 「큐잉」이다. 앞 요청의 서버 생성 id 를 뒤 요청이 참조하는 규약이 계약에 없다. ⇒ `M-01-01` §8 #5 가 「오프라인 규약은 검증된 적 없다 · **4차에서 본격 검증**」으로 물음과 일정을 이미 세웠으므로 **새 문의로 올리지 않는다**(I-2 024 와 같은 처분).

⛔ 취향이라 뺀 것: PR 안의 파일 쪼개기 · 목록 응답이 id 만 내리고 이름을 안 내리는 것(저장소 전반의 축) · `W-01-09` 「품목 검색」이 `itemId`(id)라 자유 텍스트가 아닌 것(클라이언트 몫) · U5 조회 3행의 화면 열이 도출표와 다른 것(GET 은 403 미선언이라 무해).
