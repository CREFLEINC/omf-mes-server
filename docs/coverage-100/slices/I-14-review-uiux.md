## 2. 화면이 요구하는데 계획안에 없는 것 — **3건**(전부 「알려둘 것」 감)

1. ⭐ **「장부 · 실물」 두 열의 원천이 조정 7건 «밖»이다.** 화면 §3 ②·§5-4 는 ⌜장부 200 · 실물 180 · 차이 −20⌝ **3열**을 UI 형태로 못박았는데(⌜✅ 옳은 UI⌝), 서버 라인이 싣는 것은 **차이 하나**(`adjustmentQty`)다. ⇒ 실사 경유는 `GET /inventory/counts/{id}/lines`(`system_qty`·`counted_qty`·`variance_qty` — **I-15 몫**), 직접 등록은 `GET /inventory/balances`(구현됨)로 화면이 두 열을 «따로» 채운다. ⭐ **권한 문제는 없다** — 두 오퍼레이션 다 계약이 **403 을 선언하지 않아** 가드가 보지 않는다(`permission.guard.ts:37-40` · balances 응답 `['200','400']` 실측). ⚠ 다만 **전기 뒤에 다시 열면 「장부」가 이미 바뀐 값**이라 화면이 상신 당시 수를 복원할 수 없다(라인에 장부 수량을 저장하는 칸이 없고 `inventory_transaction_line_id` 도 응답에 안 싣는다 · §11-3 ⓒ). ⇒ **§11-3 에 ⓛ 한 줄**.
2. **전기 버튼의 활성 조건을 조정 응답만으로 못 푼다.** 화면 §5-6 ⌜전기 — **승인 후**(또는 승인 불요 시 상신 즉시)⌝ 인데 `InventoryAdjustment` 8칸에는 `approvalRequestId` 만 있고 **승인 «상태»가 없다** ⇒ 화면이 승인 계약(U1 `GET /app/approval-requests/{id}`)을 따로 부른다. 서버는 `:post` 에서 400 `APPROVAL_IN_PROGRESS`·`APPROVAL_REQUIRED` 로 막으므로 안전하지만, **버튼을 회색으로 만들 값이 이 슬라이스에 없다.** ⇒ **§11-3 에 ⓜ**.
3. **「결재선이 있으면 상신 · 없으면 즉시 전기」 분기를 미리 알 길이 없다**(화면 §5-3 마지막 · §5-5 호퍼 권고). 조정 7건에 결재선 조회가 없어 화면이 U1 `GET /app/approval-routes` 를 먼저 보거나, `:request-approval` 의 **400 `ROUTE_NOT_FOUND` 를 분기 신호로 쓴다** — 후자는 사용자에게 **오류 토스트로 보인다**(화면 §3 ⌜⚠ 결재선 조회 불가⌝ 가 이미 같은 자리를 적었다). ⇒ **§11-3 에 ⓝ** · 문의 **030** 에 한 줄로 붙인다(새 문의 아님).

## 3. 계획안이 만드는데 화면에 없는 것 — **0건**(전건 대응 확인)

`PUT …/lines` = §5-6 「라인 추가·수정 — 직접 등록 시」 + §7 DS ⌜편집 그리드(c)⌝ ⇒ §9-4 의 권한 2줄 근거 **✅ 정확**. `:request-approval` = 「조정 상신」 · `:post` = 「전기」 · 조회 3 = ②표·「처리 이력」 탭. ⚠ **목록 필터 4축(`statusCode`·`reasonCode`·`inventoryCountId`·`adjustedAt*`)만 화면 §3 에 입력 UI 가 없다** — 「처리 이력」 탭 안이 미상세라 **만들되 화면 갱신 대상**(§11-3 ⓐ 옆에 반 줄).

## 4. 목록 필터·정렬·집계 열

- **정렬 `created_at desc, id desc` ✅ 동의** — `adjusted_at` 은 **전기 시점**이라(화면 §4-A ⌜승인 후 전기 시점⌝) 미전기 전표가 NULL 이고, 「처리 이력」 탭이 **방금 상신한 건을 못 본다**. 근거가 화면 쪽에서도 선다.
- **집계 열 요구 0** — `W-01-12` 에 요약 카드가 없다(`W-01-04` §3 의 「계획 120·카운트 38·차이 6」 은 **실사 화면 몫**). ⇒ 새 집계 오퍼레이션을 만들지 않는 판정에 동의(`plan-uiux.md` §9-4 T 와 같은 결).
- ⛔ **`plan-uiux.md:275` 의 「`GET /inventory/adjustments` → W-01-12,**W-06-06**」은 오탐이다** — 계약 실측상 `W-06-06` 은 `statusCode` **설명문** ⌜고객이 W-06-06 에서 이 값을 편집하면 안 된다⌝ 안에서만 나오고, `W-06-06-공통코드조직작업자마스터.md` 에 조정 언급이 **0건**이다(전문 grep). 화면 식별자 정규식이 설명문까지 긁은 자리다. ⇒ **내 계획서 쪽 수정**(권한·구현 영향 0).

## 5. 「실사 결과에서 불러오기」가 무엇을 부르는가 (I-15 인계)

`GET /inventory/counts/{inventoryCountId}/lines`(계약 실재 · 200 만 선언) 로 **차이 라인을 읽어 화면이 조정 라인으로 옮긴다** — 조정 7건 밖이고 **I-15(U16) 몫**이다. ⇒ §13 ⓐ 는 옳으나 ✏ **두 가지를 더한다**: ⓐ 이 버튼이 부르는 오퍼레이션 이름을 §13 ⓐ 에 적을 것(구현자가 「조정 쪽에 불러오기 API 가 필요한가」를 다시 묻지 않게) ⓑ **I-15 가 늦으면 화면 §3 ① 라디오의 «실사 결과에서» 한쪽이 통째로 빈다** — `plan-uiux.md:623` 이 적은 그대로다. §12-1 #15 의 「서버는 저장만 하므로 선다」는 **서버 관점에서만 참**이라 배포 노트에 한 줄이 필요하다.

## 8. 화면 명세가 **낡았다** — 설계팀 통지 대상(§13 에 행 추가 권고)

`W-01-12` **§4-B**(⌜조정 라인 — 담을 테이블이 없다 · 위치·품목·LOT ⛔ 없음⌝) · **§5-1 A-11 표**(⌜라인별 사유 ⛔ 불가⌝) · **§5-2 해법 3안**(⌜①로 실사 경유, 직접 등록은 **②「미확정 수불 트랜잭션」**⌝) · **§5-6**(⌜사유 선택 — 라인당 ⚠ **저장 자리 없음**⌝) 넷이 전부 **라인 표 부재**를 전제한다. 물리·계약 둘 다 라인과 `reason_code`(NOT NULL)를 갖는 지금 ⇒ ⛔ **클라이언트가 §5-2 ②안대로 「미확정 수불 트랜잭션」을 구현하면 승인 전에 재고가 움직인다**(결정 08 위반). 화면 §8 #1 이 「✅ 해소 2026-09-02」로 **미결 표만** 닫았고 본문 넷은 그대로다. ⇒ 계획안 §2-3(계약 `x-internal-note` 3건 낡음)과 **같은 뿌리이고 대상이 화면 쪽**이다.
✏ 또 하나 — 화면 §8 #3 은 ⌜프론트가 **`ADJUST_REASON`** 으로 고정해 두었고 실제 그룹은 `INVENTORY_ADJUSTMENT_REASON` … **⛔ 변경 통지 대상**⌝ 이라 적었다. 서버 값 목록은 시드 5행으로 닫혔으므로 §11-2 의 「문의 아님」 판정에 **✅ 동의**하되, **「알려둘 것」에 한 줄이 필요하다** — 클라이언트가 그 이름을 고치지 않으면 사용자는 **사유 드롭다운이 빈 채**로 만난다(서버는 오류를 내지 않는다).
