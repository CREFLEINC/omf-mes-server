- LOT·SERIAL_NUMBER·GOODS_ISSUE_LINE은 확정 FK 원천이 있어 생략/null 요청을 원천으로 채우는 **0단계 선례**가 있다. nonnull이 다르면422 PAIR. HU는 내용물이 단일 LOT여도 null을 유지한다(화면 명시). HU/MOLD/LOCATION에 nonnull lotId를 보내면422 PAIR(가장자리 최초2-②). 검사 결과는 요청FK가 있는 경우만 연결하고 없으면null; 인접 LOT·최근 검사로 찾지 않는다.
- `mdm.item.serial_control_type_code`는 물리에 있으나 고정 Item 계약16562행은 **코드 그룹·값·boolean을 정하지 않는다**. 이 칸의 NONE을 인식표 제외/허용 규칙으로 쓰지 않는다. P-02-05 §8-5의 ‘전 품목 대상으로 시작’ 선례를 적용할 수 있으나 개체별 불량 판정 공백은 해소되지 않는다.
- LOT 품질 상태·생명주기·작업hold 세 축은 분리한다. 생산완료는 completed_at이고 ACTIVE나 NORMAL의 동의어가 아니다. 재고 blocked_qty로 라벨 자격을 정하지 않는다.
- 기존 goods-issue `assertLotNotBlocked`는 judgment_type_control.blocks_issue를 쓰며 **프린트 자격 플래그가 아니다**. blocks_issue/blocks_shipment를 발행 차단으로 재사용하지 않는다. 품질 값을 DEFECTIVE/SCRAPPED로 거르는 것이 자재/출고/성적서까지 참이라는 근거는 없다.
- 기존 serial의 상태 문자열을 바꾸거나 양품 수량만큼 낮은 serial ID를 골라 ‘양품 개체’로 추정하지 않는다. I-26 문의104(상태)·105(수량/단위)·044(정정 배분)의 한계와 I-27 발행 자격 질문을 구분해 root가 중복 통합한다.

## 5. GET 목록·상세·summary 설계

1. 목록은 회차를 합치지 않고 페이지를 낸다. `issued_at DESC, document_issue_log_id DESC` 고정 정렬. 최신을 시간 동률에서도 정한다. 날짜 경계는 I-26/알림의 **>= from, < to** 선례를 따르고 date-time을 일자로 바꾸지 않는다. query 경계는 µs 이상 소수 자리도 보존하는 로컬 helper(기존52~54줄) 사용, `new Date`로 입력을 ms로 자르지 않는다. 이 선택은 문의 ‘조회 가장자리’에 최초0단계 선례로 기록한다.
2. row/count/대상 이름은 같은 RepeatableRead snapshot. 대상별 그룹 조회 최대7회로 묶고, 200행당 target 조회200회는 하지 않는다. 없는 상세만404. LOT 필터는 저장 `document_issue_log.lot_id` 기준이다. HU 내용물 역조회를 자동 추가하지 않음: 현재 내용물은 발행 당시와 다를 수 있고 화면이 다중LOT에는 FK를 비우라고 확정했다. 이 누락 범위는 문의/배포 노트로 전달한다.
3. target 필터 없이도 과거 기록은 전부 보인다. target FK가 없는 과거행은 명시한 fallback으로 표시하되 enum 밖 document/target 또는 required printOutcome 결손은 **목록·상세 응답 활성화 hold** 대상이다. 그런 행을 숨기거나 PENDING으로 대체하지 않는다. 단 summary의 `lastPrintOutcome`은 선택 nullable이므로 구행 NULL도 count/seq/time을 보존하고 `null`로 정상 반환한다.
4. summary는 입력에 ordinal을 붙여 `targetIds` **전건, 원래 순서, 중복 multiplicity**를 보존한다. DB 조회는 distinct id 집합, 응답은 원래 배열 map. `[2,1,2]`이면 세 행(2,1,2); 그룹마다 중복 발행을 한 것처럼 세지 않는다. uniqueItems가 없고 ‘요청 전건’이 명시되어 최초0단계 문자대로다.
5. 미존재 target도 이 조회의 뜻은 ‘해당 키의 발행기록 개수’이므로 **issueCount0**(기록도 없을 때)로 반환한다. 대상 존재 증명 API가 아니다. 삭제된 대상에 이력이 있으면 count를 숨기지 않는다. 계약의404 미선언·요청 전건 문자를 따르며 문의에 이 의미를 적는다.
6. count는 조건에 해당하는 **로그 행 수**이지 max(issue_seq)가 아니다. documentType 지정 시 그 축만; 미지정이면 전체 문서종류의 로그를 센다. 마지막행은 `issued_at DESC,id DESC`의 한 행이고 lastIssueSeq/lastIssuedAt/lastPrintOutcome은 **동일 행**에서 가져온다. 문서종류끼리 max(seq)·max(time)·max(outcome)를 각각 조합하지 않는다. count0은 lastIssueSeq/lastIssuedAt/lastPrintOutcome null로 명시한다.
7. summary 1000건은 집계/최신행을 한 SQL 또는 고정 쿼리 수로 처리한다. timestamp를 문자열 원문 정렬하거나 Number ID만으로 issued_at 순서를 대체하지 않는다. 정본에 없는 page/size/issuedFrom/printOutcome 필터를 추가하지 않는다.
8. P2에는 summary 경로 전용 middleware를 함께 둔다. guard 전에 scalar `targetIds`만 `split(',')`하고 query 사본을 `Object.defineProperty`로 고정한다. `AppDomainModule.configure`에서 GET `app/document-issues/summary`에만 등록하며 `api` prefix를 중복하지 않는다. middleware는 응답·오류를 만들지 않고 missing은 그대로 둔다. 빈 token을 거르지 않으며, 중복·순서를 보존한다. 이미 배열인 repeated-key 입력은 기존 validator에 그대로 맡기고 배열 원소 안의 CSV를 추가 분해하지 않는다. controller/pipe 전처리나 공용 contract serializer 수정으로 바꾸지 않는다.

## 6. 발행 POST — 부분 정상 지원 심장

I-26 POST의 미완과 별개로 이 operation은 §0 지원표에 따라 진행한다. LOCATION을 포함한 확정 정상 가지를 열고, 미정 입력군은 이름 있는 정책으로 명시 거부한다. TOOL_LABEL만 R3의 writer 조율·보완·경합 회귀가 끝날 때까지 조건부 거부한다. 일부 입력군의 미정을 이유로 항상 422인 handler를 만들지 않는다.

| 순서 | 경계 | 처리 |
|---|---|---|
| 1 | tx 밖 | 계약/계정 기능권한→사번 형식→실제 계정·검증된 terminalId를 해석. 결과를 JSON 안전한 지문으로 작성 |
| 2 | 기존 run | IdempotencyService.run(context, tx=>issueWithin(tx,...)). 같은 key는 현재 자격·사유 상태 재검사보다 **저장 응답 재생 우선** |
| 3 | 같은 tx | `(targetTypeCode,targetId)` 중복을422 INVALID로 거부. 정렬된 처리복사본과 원본 ordinal을 분리. 중복 소거/같은 요청에서seq 두 번 증가0 |

잠금 순서는 실제 writer 그래프를 따른다. GI는 초기 line→header를 탐색에만 쓰고, 헤더 ID 오름차순 `FOR NO KEY UPDATE` → 잠근 헤더 안에서 line/FK 재조회 → LOT ID 오름차순 `FOR NO KEY UPDATE` 순이다. 다른 헤더나 LOT으로 바뀌었으면 부분 역행하지 않고 전체 run을 재시도한다. LOT 직접 대상은 LOT ID 오름차순, HU는 HU ID 오름차순, LOCATION은 LOCATION ID 오름차순으로 각각 `FOR NO KEY UPDATE`한다. GI-HU는 존재하는 content 최소 1행을 `FOR SHARE`로 잠가 최종 재확인까지 비어 있지 않음을 보존하되, PACKING_LABEL+HU에는 비어 있음 조건을 추가하지 않는다.

CoA는 초기 result→request→LOT 후보를 읽고 LOT ID 오름차순 `FOR NO KEY UPDATE` → request ID 오름차순 `FOR SHARE` → result ID 오름차순 `FOR NO KEY UPDATE` 뒤 경로·`CONFIRMED`·`confirmedAt`을 다시 확인한다. 초기 경로와 다르면 전체 run을 재시도한다. 타입별 SQL 식별자는 고정 whitelist이며 입력을 식별자에 보간하지 않는다. 구현 직전 최신 main의 GI line 삭제/LOT 변경, HU content, CoA 최종 confirm, mold code 변경 writer 그래프를 다시 확인한다. 새 역순 writer가 있으면 해당 가지의 소유 조율과 R 보완을 먼저 하며, 보지 않은 writer를 회귀 PASS라고 쓰지 않는다.

TOOL_LABEL은 별도 선행 PR에서 기존 코드 수정 writer를 `mold 잠금 → 현재 참조/발행 검사 → CAS` 한 트랜잭션으로 바꾸고, 두 writer의 양쪽 barrier 순서를 검증한 뒤에만 활성화한다. 발행 쪽에서 mold version만 올리는 우회는 하지 않는다. 사용자 조율 응답 전에는 이 writer를 수정하지 않고, `TOOL_LABEL_WRITER_READY=false` 가지의 422만 유지한다. PENDING/FAILED 이력도 코드 잠금 count에 포함한다.

부모 잠금·MAX·INSERT·mapper는 유형별 batch로 처리해 대상당 N 쿼리를 만들지 않는다. 원본 ordinal과 지문 순서를 보존한다. 동일 대상 동시 최초발행은 사유가 없으면 한 건만 201이고 다음 건은 422, 유효 사유가 있으면 seq1/2가 된다. 원인이 확인된 경로 변동, SQLSTATE 40001·40P01, 정확히 발행 회차 유일키 충돌만 실패한 트랜잭션 전체를 처음부터 최대 3회 실행한다. 실패 트랜잭션 안에서 문장만 재시도하거나 일반 P2002·검증422·프로그램 오류·500을 숨기지 않는다. 재시도 소진은 `ConflictException('user', message)`의 기존 409 `ConflictResponse`를 사용하며 이 응답에는 `conflictCause`와 `message`만 있고 code 필드는 없다. 존재하지 않는 `ERROR_CODE.CONFLICT`를 만들지 않는다.

N=1000은 Prisma 기본 5초 안에서 전량 성공·중간 실패·응답 저장 실패·재생과 고정 쿼리 상한/전체 시간을 실측한다. 원인 없이 공용 timeout을 늘리지 않는다. 새 전역 잠금표·번호 카운터·상태 전이 코어를 만들지 않으며 seq에는 `NumberingService`를 호출하지 않는다.

사유의 `effective_from/to`는 계약이 평가일·타임존을 정하지 않았으므로 새 날짜 gate를 만들지 않고 기존 활성 플래그만 사용한다. 유효기간 규약은 별도 질문으로 남긴다. 과거 이력의 사유명은 현재 코드가 inactive여도 표시하며, 과거 표시와 새 발행 자격을 섞지 않는다.

## 7. report-print·귀속·멱등

**report**: `IdempotencyService.run`이 넘긴 tx에서 해당 로그를 `FOR UPDATE`로 잠근다. 없으면 404, 알려진 결과가 PENDING이 아니면 422 STATE_LOCKED, FAILED에 사유가 없으면 422 REQUIRED다. 기존 NULL outcome은 ‘모르는 저장값’이므로 이미 보고된 상태로 바꾸지 않고 Error 500으로 드러낸다. 결과·보고 시각·보고자 계정/사번을 저장하고 같은 DocumentIssue view를 만든 뒤, run이 200 응답을 저장한다. print_reported_at은 **물리 인쇄 발생 시각이 아니라 서버의 보고 접수 시각**이다(본문에 시각 없음). printed_at이라는 이름으로 실물 인쇄 시각처럼 취급하지 않는다.

- FAILED의 failureReason null/생략/공백은422 REQUIRED. SUCCEEDED에 비어 있지 않은 failureReason이 오면422 INVALID(가장자리2-②, 정상완료사유 거부 선례 `lot-rules.ts:104`); 조용히 버리지 않는다. 빈 사유는 null로 표현한다. report 프린터 상태를 바꾸거나 상위LOT·개체·로그회차를 옮기지 않는다.
- 같은 key·동일 본문은 이미 보고되었어도 저장된 200 응답을 재생한다. 다른 key의 두 번째 보고는 422다. 다른 key의 동시 요청은 row 잠금으로 승자 1건을 보장한다. 실패 결과를 SUCCEEDED로 수정하는 길은 없으며 새 발행 회차로 처리한다.
- `issued_by`와 응답 issuedBy는 계정 FK다. worker.app_user_id는 nullable이므로 그 값으로 발행 계정을 대체하지 않는다. **A9에 issued_worker_id, print_reported_worker_id, print_reported_by를 nullable로 추가**한다. 최초 사번을 보고 사번으로 덮지 않는다. 계정 없는 단말 인증 지원은 공용 문의054 소관이며, 이 슬라이스에서 가드를 우회하지 않는다.
- POST WorkerNoOptional: 계정 요청의 사번 생략은 정상이며 issued_worker_id=null이다. 사번이 있으면 존재를 확인하고 저장한다. 검증된 단말 token이 있으면 사번 필수이고, report는 계정 요청도 사번 필수다. 사번을 인증으로 승격하거나 재직/활성/6자리 제한을 새로 추가하지 않는다. 인증·토큰 검증은 replay보다 먼저 하고, 업무 자격·사유·worker 존재 검사는 callback tx 안에서 한다.
- 지문은 `requestFingerprint(method+' '+actualPath,{body,query,actor:{appUserId,workerNo:rawHeader??null,terminalId:resolvedId?.toString()??null}})` 형태로 고정한다. path에는 실제 로그 ID가 들어간다. JSON에 bigint를 그대로 넣지 않는다. actorId만 멱등 행에 저장하면 replay가 비교하지 않으므로 지문에 넣어야 한다. 동일 key의 사번/단말/계정 변경은 409로 거부한다. 원본 targets 순서도 응답의 일부이므로 정렬된 본문으로 지문을 만들지 않는다.
- 기존 `runIdempotent`는 tx를 버리는 callback이므로 사용하지 않는다. 공용 IdempotencyService.run을 직접 사용하고 callback의 tx 밖 Prisma 조회나 별도 transaction은 만들지 않는다. `notification-write.controller.ts`가 현재 선례다. 공용 멱등 소스 변경은 0이다.
- 멱등 보존 72h는 expires_at 값일 뿐, 현재 run은 만료 시각을 검사하지 않는다. 기록이 실제 삭제되면 로그에 요청 key가 없어 재생 복구가 불가능하다. 새 영구 배치표를 만들지 않고 문의106/107 및 공용 보존 질문에 root가 통합한다.

## 9. A9 SQL 전문·A10 보류 후보 — 미실행

### 9-1. A9: 인쇄 결과3 + 귀속3 = nullable6 확정안

별도 선행 마이그 커밋으로 분리한다. 기존 12칸·유일키·CHECK는 유지하고 추가만 한다. DEFAULT/UPDATE/DELETE/backfill은 0이다. 과거 행의 NULL을 ‘보고 전’으로 정의하지 않는다. Prisma 상태 문자열은 String? @db.VarChar(40), 시각은 DateTime? @db.Timestamptz(6), FK는 BigInt?와 역관계가 필요하다. FK 이름은 PostgreSQL/Prisma 기본형을 사용한다.

```sql
-- I-27 A9 확정안. 구현 PR 전 사전조회·환경별 writer 확인 뒤 실행.
ALTER TABLE app.document_issue_log
  ADD COLUMN print_outcome_code varchar(40),
  ADD COLUMN print_failure_reason varchar(500),
  ADD COLUMN print_reported_at timestamptz(6),
  ADD COLUMN issued_worker_id bigint REFERENCES mdm.worker(worker_id)
    ON DELETE NO ACTION ON UPDATE NO ACTION,
  ADD COLUMN print_reported_worker_id bigint REFERENCES mdm.worker(worker_id)
    ON DELETE NO ACTION ON UPDATE NO ACTION,
  ADD COLUMN print_reported_by bigint REFERENCES app.app_user(app_user_id)
    ON DELETE NO ACTION ON UPDATE NO ACTION;

ALTER TABLE app.document_issue_log
  ADD CONSTRAINT ck_document_issue_print_outcome
  CHECK (print_outcome_code IS NULL OR
         print_outcome_code IN ('PENDING','SUCCEEDED','FAILED')),
  ADD CONSTRAINT ck_document_issue_print_report
  CHECK ((
    (print_outcome_code IS NULL AND print_reported_at IS NULL
      AND print_failure_reason IS NULL AND print_reported_worker_id IS NULL
      AND print_reported_by IS NULL)
    OR (print_outcome_code = 'PENDING' AND print_reported_at IS NULL
      AND print_failure_reason IS NULL AND print_reported_worker_id IS NULL
      AND print_reported_by IS NULL)
    OR (print_outcome_code = 'SUCCEEDED' AND print_reported_at IS NOT NULL
      AND print_failure_reason IS NULL AND print_reported_worker_id IS NOT NULL
      AND print_reported_by IS NOT NULL)
    OR (print_outcome_code = 'FAILED' AND print_reported_at IS NOT NULL
      AND nullif(btrim(print_failure_reason),'') IS NOT NULL
      AND print_reported_worker_id IS NOT NULL AND print_reported_by IS NOT NULL)
  ) IS TRUE);

COMMENT ON COLUMN app.document_issue_log.print_outcome_code IS
  '인쇄 결과. 신규 발행만 명시 PENDING; NULL은 과거 결과 미확인이고 PENDING으로 간주하지 않는다.';
COMMENT ON COLUMN app.document_issue_log.print_reported_at IS
  '인쇄 결과를 서버가 접수한 시각. 실물 인쇄 발생시각을 도출하지 않는다.';
COMMENT ON COLUMN app.document_issue_log.print_failure_reason IS
  'FAILED 결과의 필수 실패 사유. 성공 결과에는 NULL.';
COMMENT ON COLUMN app.document_issue_log.issued_worker_id IS
  'X-Worker-No로 확인한 최초 발행 귀속 작업자. issued_by 계정FK와 별개.';
COMMENT ON COLUMN app.document_issue_log.print_reported_worker_id IS
  '결과 보고 X-Worker-No 귀속 작업자. 최초 발행 사번을 덮지 않는다.';
COMMENT ON COLUMN app.document_issue_log.print_reported_by IS
  '인쇄 결과를 보고한 인증 계정. issued_by 최초 발행 계정과 별개.';
```

SQL의 3값 논리 때문에 결과 분기 전체를 `(...) IS TRUE`로 감쌌다. 계획 검증 테스트는 ‘과거 결과/보고 칸이 모두 NULL이면 허용’, ‘NULL outcome + nonnull report는 거부’, ‘PENDING + 보고 정보는 거부’, ‘FAILED + 공백 사유는 거부’, ‘보고 완료 + 귀속 누락은 거부’를 포함한다. SQL 확정안의 정적 검토이며 아직 DB 성공으로 표기하지 않는다.

### 9-2. A10: 기존 계획5칸을 보존한 보류 후보
