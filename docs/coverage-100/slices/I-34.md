## 3. ⛔ 건너뜀 3건 — 계약·물리로 재확인 (루틴 끝 보고에 실린다)

> README §0: 「**DB 안에서 끝나는 것만** 구현한다. 바이너리 저장소·실제 외부 전송·프린터/PDF 가 필요한 오퍼레이션은 건너뛰고 루틴 끝에 목록으로 보고한다.」
> 아래는 **인용이 아니라 이 계획안이 직접 잰 것**이다.
> ⛔ **사유는 「파일 업로드라 못 한다」가 아니다**(재수립 R-4) — 이 저장소는 파일 업로드를 **이미 한 자리 구현해 두었다**. 사유는 **「읽고 버림 vs 보관」**이다.

### 3-0. ⭐ 왜 「파일 업로드」 자체는 사유가 아닌가 (R-4 · 이 문단이 보고서에 그대로 실린다)

`POST /mdm/molds:import` 는 **이미 구현돼 있다** — `mold.controller.ts:142` 가 `@UseInterceptors(FileInterceptor('file', { limits: { fileSize: MAX_UPLOAD_BYTES } }))` 로 multipart 를 받는다. 그러므로 「NestJS 가 못 받는다」·「계약 검증기가 multipart 를 못 본다」는 **건너뜀 사유가 아니다**(검증기가 multipart 본문을 스키마로 안 보는 것은 사실이지만, 그것은 검증 범위의 문제이지 구현 가능성의 문제가 아니다).

⭐ **갈리는 축은 파일의 «수명»이다.** 그 코드 자신이 계약 주석을 인용해 갈라 적어 두었다(`mold.controller.ts:135-138`):

> 「엑셀 대장 올리기. 전 계약에서 처음 두는 파일 올리기 경로다 — **첨부와 «다른 자리»다**(**첨부는 보관되는 파일이고 이것은 읽고 버리는 입력이다** · 계약 x-internal-note).」

- `molds:import` — 바이트를 **읽고 버린다**. 파싱 결과만 `mdm.mold` 행이 된다. **DB 안에서 끝난다.**
- 첨부 3건 — 바이트를 **보관해야 한다.** 보관 위치를 가리키는 칸이 `storage_key varchar(500) **NOT NULL**` 이고, **그 값의 출처가 DB 밖이다.** 저장소가 없으면 키를 **지어내야** 하고, 지어낸 키는 §2 2단계 기준 4(값을 조용히 도출하지 않는다)에 정면으로 걸린다. 그리고 그 키로는 아무것도 못 꺼낸다.

⇒ **건너뜀 사유 한 줄**: **「보관할 바이너리 저장소가 DB 밖이라, `storage_key` 에 넣을 값을 서버가 지어내는 수밖에 없다.」**
