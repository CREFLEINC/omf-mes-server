**⛔⛔ 결정타 — `ck_..._distinct`**
계약의 **대표 경로가 취급 단위 «하나»짜리 사건**이다. `PUT …/{handlingUnitId}/contents` 는 한 HU 의 구성을 치환하고 그 치환이 이벤트를 만든다.
그 사건의 HU 는 **하나** ⇒ `source = target` ⇒ **CHECK 위반으로 INSERT 가 실패한다.**
그리고 헤더 두 칸(1 source → 1 target)은 `MERGE`(N source → 1 result)를 **구조적으로 못 담는다** — 계약이 그 축을 **라인**(`HandlingUnitRepackEventLine.handlingUnitId` required)에 두었다.

    --    ⛔ 지금 안 만들면 forward-only 라 «그 사이 기록된 이력은 영구 복구 불가»다.
    --    응답에는 싣지 않는다(계약 라인에 칸이 없다) — 서버가 채우고 서버만 읽는다. 통보 165.
    uom_id_before       bigint      NULL REFERENCES mdm.uom(uom_id),
    uom_id_after        bigint      NULL REFERENCES mdm.uom(uom_id),
    created_at          timestamptz NOT NULL DEFAULT clock_timestamp(),

## §3. ⭐ `POST …/{handlingUnitId}:pack` — 포장 확정

계약 description: 「포장 단위와 내용물 N행을 **한 트랜잭션**으로 **확정한다**(공유계약 B-8). **내용물이 비면 400 이다. 이미 확정된 포장은 409 다.** ⛔ 라벨·인식표 출력은 이 오퍼레이션 밖이다 … 오프라인 대상이다(공유계약 C-9). 근거: `P-02-08` §5-6」

### 3-1. 갈래 순서 — **가드가 핸들러보다 먼저 돈다**(V-7)

```
가드   ① 인증 → 권한 403 → 계약 본문 검증 → Idempotency-Key → If-Match 형식
          · contents 0건 ······················ 400 RANGE      (field `contents`)
          · qty <= 0 ··························· 400 RANGE      (field `contents[i].qty`)
          · required 누락(businessDate·occurredAt) 400 REQUIRED
          · date/date-time 형식 위반 ············ 400 INVALID
          · If-Match 는 «선택» — 없으면 그냥 통과
핸들러 ② X-Worker-No 없음/공백 → 400 REQUIRED · 없는 사번 → 400 INVALID (§8-3)
       ③ 요청 배열 안 (itemId, lotId) 중복 → 400 UNIQUE_VIOLATION   ← tx «밖»(본문만 본다)
       ④ 채번 없음 — 이 액션은 번호를 만들지 않는다
tx     ⑤ ⭐ SELECT … FROM inventory.handling_unit WHERE handling_unit_id = $1 FOR UPDATE
          없으면 404                                    ← ⭐ 자리 ② · I-27 과 «같은 순서»
       ⑥ status_code === 'PACKED' → 409 {conflictCause:'user', message: PACK_ALREADY_PACKED}
       ⑦ If-Match 가 «있으면» version_no 대조 — 어긋나면 409 {…, message: PACK_STALE_TOKEN}
       ⑧ FK 존재 검사 — item·lot·uom·location (없으면 400 INVALID · field 지정)
       ⑨ handling_unit_content DELETE(그 HU 전건) → INSERT N행 (전량 치환)
       ⑩ handling_unit UPDATE — status_code='PACKED'
                              · location_id = 본문에 «있으면» 그 값(없으면 유지)
                              · updated_by = 세션 userId · updated_at · version_no + 1
       ⑪ ⛔ 재포장 이벤트를 만들지 않는다(§3-4)   ⑫ ⛔ 원장을 부르지 않는다(§3-5)
후     ⑬ 200 HandlingUnitDetailResponse · ⛔ setEtag 안 부른다(계약 미선언)
```

- ⭐ **⑤ 가 `SELECT … FOR UPDATE` 여야 하는 이유가 «둘»이다.** ⓐ If-Match 가 선택이라 `UPDATE … WHERE version_no` 로는 오프라인 큐 요청을 잠글 문장이 성립하지 않는다. ⓑ ⭐ **병합된 `document-issue-simple-lock.ts:101-113` 이 같은 행을 `FOR NO KEY UPDATE` 로 잠근 뒤 `handling_unit_content` 를 `FOR SHARE` 로 잠근다.** 부모→자식 순서를 맞추지 않으면 발행과 포장이 교착한다.
- ⭐ **⑥ 이 ⑦ 보다 먼저인 것이 판정이다.** 확정된 포장에 낡은 토큰으로 다시 쏘면 「다시 읽어 오면 풀린다」(409 stale)가 **거짓말**이 된다. 계약 `ConflictResponse` 에 `code` 칸이 없어 봉투로는 못 가르므로(V-9) **`message` 를 상수 둘로 갈라** e2e 가 그 문자열을 단언한다.
- 전체를 `runIdempotent(this.idempotency, request, HttpStatus.OK, () => …)` 로 감싼다(`putaway-task.controller.ts:52-60` 형).
  ⚠ `runIdempotent` 는 `work` 에 `tx` 를 **안 넘긴다**(`master-write.ts:41`) — 서비스가 자기 `$transaction` 을 연다.

### 3-2. ⭐ `status_code` 값의 원천 — 상수 **둘** (자리 ④)

**사실 다섯**

1. `handling_unit.status_code` 는 `app.code_t` **NOT NULL** 이고 **CHECK 도 DEFAULT 도 없다**(psql).
2. 계약이 코드 그룹을 **영영 세우지 않겠다**고 닫았다(`x-no-code-key` 원문 — 질의 파라미터와 스키마 두 곳).
3. 그런데 같은 계약이 「**이미 확정된 포장은 409 다**」를 요구한다 ⇒ 「확정 전/후」를 가릴 축이 데이터에 있어야 한다.
4. `HandlingUnit.required` 에 `statusCode` 가 있다 ⇒ **nullable 로 못 물러선다**.
5. ⭐ **그리고 저장소에 이미 세 번째 값이 있다** — `test/logistics-stock-transfer.e2e-spec.ts:1314` 가 `status_code: 'ACTIVE'` 로 HU 픽스처를 만든다(S-11).

**판정** — README §2 1단계 본길 → 2단계 **기준 3**(칸이 이미 있다 · 마이그 0) · **기준 4**(값에 이름을 붙여 한 파일에 모은다).

## §4. `POST /inventory/handling-units` — 등록(201)

```
가드   ① 403 → 계약 검증(handlingUnitTypeCode required · qty exclusiveMinimum) → Idempotency-Key
핸들러 ② X-Worker-No (400 REQUIRED / INVALID)
       ③ handlingUnitTypeCode 를 assertCodeValues(HANDLING_UNIT_TYPE) 로 대조 — 없으면 400 INVALID
       ④ contents 안 (itemId, lotId) 중복 → 400 UNIQUE_VIOLATION
       ⑤ ⭐ 채번 — numbering.next('HANDLING_UNIT', null, <서버 UTC 날짜>) · ⛔ $transaction «밖»
tx     ⑥ parentHandlingUnitId 가 있으면 존재 확인 + 순환 검사(§4-3)
       ⑦ warehouse·location·item·lot·uom 존재 확인 — 없으면 400 INVALID(field 지정)
       ⑧ handling_unit INSERT — status_code = HU_STATUS_OPEN · created_by/updated_by = 세션 userId
       ⑨ contents 가 있으면 handling_unit_content INSERT N행
후     ⑩ 201 + HandlingUnitDetailResponse + ⭐ ETag(version_no = 1)
```

### 4-1. ⭐ 멱등 재전송이 ETag 를 잃지 않게 (V-8)

`runIdempotent` 는 `outcome.body` 만 돌려주고 `setEtag` 를 **안 부른다**. 계약은 201 에 ETag 를 «선언»했고 응답 본문에 `version_no` 가 없으므로, 그대로 두면 **재전송 응답에서 ETag 를 만들 원천이 사라진다.**
⇒ **work 의 반환을 `{ versionNo, view }` 로 만들어 캐시 본문에 버전을 실은 뒤** 컨트롤러가 `setEtag` 하고 `view` 만 내린다. `idempotency_record.response_body` 가 JSON 이라 그대로 되살아난다(`idempotency.service.ts:130-137`).
⛔ `runVersioned` 자체는 못 쓴다 — `POST` 에 If-Match 가 아예 없어 `master-write.ts:62` 가 던진다.

```ts
const { versionNo, view } = await runIdempotent(
  this.idempotency, request, HttpStatus.CREATED, () => this.units.create(body, contextOf(request)),
);
setEtag(response, versionNo);
return view;
```

**e2e 24 가 「재전송 응답에도 ETag 가 온다」를 단언한다.**

### 4-2. ⭐ 채번 — `DEFAULT_PREFIX` 에 **한 줄**

`handling_unit_no` 는 `business_no_t NOT NULL UNIQUE` 인데 계약 본문에 원천이 0이고 화면이 「MES 채번 · 자동」이라 적었다. `DEFAULT_PREFIX` 에 `HANDLING_UNIT` **없다**(현재 21종) · `app.numbering_rule` 에도 **0행**(13행 중 없음 · S-3).

```ts
// src/core/numbering/numbering.service.ts DEFAULT_PREFIX
/** 규칙 미등재 — `HU-{YYYYMMDD}-{SEQ4}` · 계약 example `HU-2026-000058` 은 형식만 준다.
 *  기간 축은 «서버 시각 UTC 날짜» — `HandlingUnitCreate` 에 날짜 칸이 0개다(통보 144ⓒ).
 *  `plantId` 는 null — `inventory.handling_unit` 에 공장 축이 0개다. */
HANDLING_UNIT: 'HU',
```

- ⭐ **기간 축**: `next()` 의 `periodDate` 는 「호출자가 이미 가진 날짜」인데 `HandlingUnitCreate` 에 `businessDate` 가 **없다** ⇒ **서버 시각의 UTC 날짜**. 0단계 선례 — I-10 `MATERIAL_RETURN`·I-14 `INVENTORY_ADJUSTMENT`(`numbering.service.ts:29·40` 주석).
  ⚠ 하노이(UTC+7) **00:00~07:00 발행이 전날 번호를 받는다** — 이미 통보 144ⓒ 로 나갔다. 새로 열지 않는다.
- ⛔ 채번은 **`$transaction` 을 열기 «전»에** 부르고 문자열만 넘긴다(`numbering.service.ts:83-89` 주석 — 커넥션 둘을 쥐면 `P2024`). **결번은 허용한다.**
- ⭐ **S-4 — `DEFAULT_PREFIX` 충돌 조율은 불필요하다.** `ST`·`IA`·`NC` 가 이미 병합돼 남은 것은 `HU` 한 줄뿐이다.

### 4-3. `parent_handling_unit_id` — 순환 방지는 **서버 몫**

물리 CHECK 는 `parent <> self` **하나뿐**이라 **A→B→A 를 안 막는다**(psql 원문).
⇒ 등록 시 부모 사슬을 위로 타고 올라가며 자기 자신을 만나면 400 `INVALID`.
- 깊이 상한은 **두지 않는다** — `P-04-01` §8 미결 4(포장 계층 깊이)가 미정이고, 기준 2 로 「거부」를 고르면 열려 있어야 할 3단을 막는다 ⇒ 기준 1로 **상한 0**.
- 무한 루프 방어로 **반복 200회 상한**만 두고 넘으면 500 이 아니라 400 `INVALID`.
- ⚠ 등록 시점의 부모는 **아직 자기 자신을 자식으로 갖지 않으므로** 사슬은 반드시 유한하다 — 200회 상한은 「데이터가 이미 순환인 경우」의 방어다.

### 4-4. `warehouse_id`·`location_id` · `status_code`

- 둘 다 nullable 이고 계약도 `["integer","null"]` ⇒ **비운 채 만들 수 있다. 서버가 기본값을 도출하지 않는다**(기준 4).
- `status_code` 초기값 = `HU_STATUS_OPEN`.
- ⚠ **404 를 선언하지 않았다** — 없는 부모/창고/위치는 **400 `INVALID`** 다(I-3·I-5 선례와 같은 가름).

## §5. `PUT …/{handlingUnitId}/contents` — 구성 치환(200)

### 5-1. 전량 교체 의미

계약: 「구성 **전체 치환** 항목. **요청에서 빠진 기존 행은 삭제한다.** 근거: 공유계약 A-5」.
`items` 는 required 이나 **`minItems` 가 없다** ⇒ **빈 배열이면 전건 삭제**다. 계약이 `minItems` 를 `:pack` «에만» 건 것을 **명시 신호**로 읽는다(통보 143ⓓ 로 이미 나갔다 · ⭐ 새 부작용은 통보 163 ⓓ).

### 5-2. ⭐ 한 트랜잭션 순서 — 부모를 «먼저» 잠근다 (자리 ②)

```
가드   ① 403 → 계약 검증(items required · qty exclusiveMinimum) → Idempotency-Key → If-Match 형식(선택)
핸들러 ② X-Worker-No (400 REQUIRED / INVALID)
       ③ 요청 배열 안 (itemId, lotId) 중복 → 400 UNIQUE_VIOLATION      ← tx 밖
tx     ④ ⭐ SELECT … FROM inventory.handling_unit WHERE handling_unit_id=$1 FOR UPDATE  ← 부모
          없으면 404(계약 미선언 · 서버가 낸다)
       ⑤ If-Match 가 «있으면» version_no 대조 — 어긋나면 409 {conflictCause:'user'}
       ⑥ ⭐ 잠근 «뒤»에 치환 «전» 구성을 읽는다 — handling_unit_content WHERE handling_unit_id=$1
          (⛔ ④ 보다 먼저 읽으면 두 치환이 겹칠 때 앞의 결과를 못 보고 qty_before 를 잃는다)
       ⑦ FK 존재 검사 — item·lot·uom (없으면 400 INVALID · field 지정)
       ⑧ handling_unit_content DELETE(그 HU 전건) → INSERT N행
       ⑨ ⭐ 재포장 이벤트 1건 + 라인 N행(§5-3)
       ⑩ handling_unit UPDATE — version_no + 1 · updated_at · updated_by
          ⛔ status_code 는 «안 옮긴다»
후     ⑪ 200 HandlingUnitContentListResponse{items[]} · ⛔ setEtag 안 부른다(계약 미선언)
```

⚠ **정정(PR ⑤ 마감 · 계획 수준) — ⑦ 이 tx «안»이어야 할 근거는 서지 않는다.** 참조 확인은
`item`·`lot`·`uom` 행을 **잠그지 않는다** — `findMany` 로 세기만 하므로 tx 밖에서 재는 것과 보장이
같고, 그 사이 참조가 지워지는 경합의 실제 그물은 **물리 FK** 다(그것이 없으면 500 으로 샌다).
⇒ 「트랜잭션 안이라 안전하다」는 문장은 사실이 아니다. ⛔ **그렇다고 코드를 옮기지 않는다** —
오늘 tx 안에서 도는 것이 틀린 것도 아니고(같은 커넥션 한 번 왕복일 뿐이다) 옮기면 diff 만 는다.
`:pack` 도 같은 자리를 tx 안에 두어 두 경로를 나란히 뒀다(§3-1 ⑧).

⭐ **④ → ⑧ 의 부모→자식 순서가 I-27 `lockUnits`(`document-issue-simple-lock.ts:101-113`)와 같다** — 그쪽은 `handling_unit` `FOR NO KEY UPDATE` → `handling_unit_content` `FOR SHARE` 다. 순서를 뒤집으면 오늘 병합된 발행 경로와 **교착한다.** 이것이 자리 ② 다.

### 5-3. ⭐ 재구성 이력 — «언제나» 남긴다 (자리 ⑤)

계약 원문에 **조건절이 없다**: 「⭐ 결정 13 되살림(2026-08-30) — **이 치환은 서버가 `HandlingUnitRepackEvent`(헤더) + Line(수량 변경 전/후)을 함께 기록한다.**」

**헤더 한 건**(치환 1회 = 1행)

| 칸 | 값 |
|---|---|
| `repack_type_code` | ⭐ **`'RECONFIGURE'` 고정** — 요청 본문 3종 전수에 그 칸이 «없다»(통보 143ⓐ). ⛔ 수량 모양으로 `MERGE`/`SPLIT` 을 추론하지 않는다(기준 4) |
| `performed_by` | 계정 세션 `userId`(`plan.md` §5 규칙 9) |
| `occurred_at` | **서버 시각** — 요청 본문에 `occurredAt` 이 없다(⛔ `:pack` 과 다르다) |

**라인 생성 규칙** — 치환 «전» 맵 `(item_id, lot_id) → {qty, uom_id}` 와 «후» 맵의 **합집합**을 돈다.

| 경우 | `role_code` | `qty_before` | `qty_after` | ⭐ `uom_id_before` | ⭐ `uom_id_after` |
|---|:-:|---|---|---|---|
| 전에 있었고 후에도 있다 | `RESULT` | 전 qty | 후 qty | 전 uom | 후 uom |
| 전에 없고 후에 생겼다(최초 채움 포함) | `RESULT` | **0** | 후 qty | **NULL** | 후 uom |
| 전에 있었고 후에 빠졌다 | `SOURCE` | 전 qty | **0** | 전 uom | **NULL** |

- ⭐ **`uom_id_before`·`uom_id_after` 는 R-2 의 자리다.** `uq_handling_unit_content` 가 `(handling_unit_id, item_id, lot_id)` 라 **같은 (item, lot) 의 단위만 바뀌는 치환**(`10 EA` → `10 BOX`)이 성립하는데, 이 두 칸이 없으면 그 사건이 이력에 **`qty_before === qty_after` 「변화 없음」으로만** 남는다. 응답에는 **안 싣는다**(계약 라인에 칸이 없다). ⇒ **통보 165** · **단위 12** 가 그 자리를 잰다.
- ⛔ **변화 없는 줄도 남긴다**(`qty_before === qty_after`) — 계약이 「변화가 있을 때만」을 안 적었고 「그 시점의 구성 전체」가 이력으로 더 쓸모 있다(기준 4). ⚠ 부작용은 통보 144ⓑ 로 이미 나갔다.
- `line_no` 는 **1부터** · 정렬은 **`(role_code DESC, item_id ASC, lot_id ASC)`** — `'SOURCE' > 'RESULT'` 라 DESC 가 SOURCE 를 위로 올린다.
- ⭐ **`qty` 비교는 `Decimal` 로 한다** — `app.qty_t` 는 `numeric(20,6)` 이라 `Number()` 로 접으면 소수 여섯째 자리에서 판정이 갈린다(`inbound-receipt-update.service.ts:180-182`). **단위 7 이 그 자리를 잰다.**
- ⛔ 다른 HU 를 안 건드리므로 라인의 `handling_unit_id` 는 **전부 경로의 그 HU** 다 — 합병은 클라이언트가 `PUT` 을 여러 번 쏘는 모양이 된다(통보 143ⓑ · 145).

### 5-4. If-Match 는 **부모 버전** · 5-5. 재고·상태·응답

- **If-Match**: 계약이 「If-Match 에 담을 토큰은 부모 자원 `GET …/{handlingUnitId}` 200 의 ETag」라 못 박았다. 선택이라 없으면 건너뛴다.
- **재고**: 안 옮긴다 — §3-5 와 같은 근거.
- **`version_no`**: **올린다(+1)** — 잠금 단위가 부모이므로 자식을 바꿨는데 부모 토큰이 안 늙으면 두 치환이 서로를 덮는다.
- **`status_code`**: **안 옮긴다** — 치환은 확정도 해제도 아니다. ⇒ ⭐ **`PACKED` 인 HU 도 치환된다**(200 · 통보 143ⓓ · e2e 30).
- **응답**: `{items[]}` · ⛔ **ETag 안 붙인다**.

### 5-6. 400·409 갈래표

| 조건 | 어디서 | 봉투 | 코드 |
|---|:-:|---|---|
| `items` 키 자체가 없음 | 가드 | 400 | `REQUIRED` |
| `qty <= 0` | 가드 | 400 | **`RANGE`** |
| `X-Worker-No` 없음 / 없는 사번 | 핸들러 | 400 | `REQUIRED` / `INVALID` |
| `(itemId, lotId)` 중복 | 핸들러 | 400 | `UNIQUE_VIOLATION` |
| FK 미존재 | tx | 400 | `INVALID` |
| **HU 없음** | tx(잠금) | ⚠ **404 미선언 → 404 를 낸다** | — |
| If-Match 어긋남 | tx | **409** | `{conflictCause:'user'}` |
| **`PACKED` 인 HU** | — | **200**(막지 않는다) | — |
