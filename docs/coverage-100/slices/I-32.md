```sql
   OR version_no<=0;
```

required 결손이 1행 이상이거나 구 작성자가 결손행을 계속 만들면 해당 환경의 O1/O3/O4/O6 배포를 제한한다(R1). 정상 환경의 구현 자체를 중단하지 않는다. 기존 µs 값이 있다는 사실은 배포 차단 사유가 아니며 R2의 동일 projection으로 정상 보존한다. 임의 백필은 이 마이그의 일부가 아니다. 권위 있는 이관 원천을 나중에 승인받으면 별개 계획으로 한다. 새 기본 사번을 넣거나 created_by와 worker_id 값이 우연히 같은 것을 매핑 근거로 쓰지 않는다.

## 4. 조회·시각·정수분의 구체 규칙

### 4-1. 기간과 시각 보존

O1의 기간은 이름/문언에 맞게 **started_at** 기준이다. 설비 공장의 timezone_code마다 로컬 달력일 경계를 instant로 변환해 WHERE에 넣는다. 입력 date나 저장 시각의 날짜를 바꾸지 않는다. 양끝 date 포함이므로 상한은 To의 익일 0시다. 날짜 역경계 P0는 **I-30 소유**다(R7/R13). 별도 담당자의 helper가 병합된 뒤 실제 함수·오류를 확인해 재사용하며, 확인 전 import 이름을 발명하거나 I-32에서 중복 구현하지 않는다.

설비 미지정 전체 조회는 공장별 경계 조건을 OR로 합한다. 요청 date의 형식/역전은 400 INVALID/PAIR다. 반면 **저장된 timezone 결손·잘못된 zone·유효한 경계를 만들 수 없는 내부 자료는 500 INTERNAL_ERROR**다. UTC로 대체하거나 호출자 잘못으로 돌리지 않는다(R7). `openOnly=true`이고 기간이 없으면 TZ를 평가하지 않는다. 상세도 로컬 날짜 필터가 없어 TZ를 평가하지 않는다. true 예외에서도 기간 쌍을 보내면 같은 필터를 적용한다.

정렬은 openOnly=true: started_at ASC,id ASC(오래 열린 것 먼저), 나머지: started_at DESC,id DESC다. 반환 원본 구간을 자르거나 병합하지 않으며 count와 page에 동일 필터를 사용한다.

**R2/R14 — PostgreSQL timestamptz(6)의 µs 정밀도를 보존한다.** 입력은 계약 Ajv 형식 검증 뒤 정수초와 소수µs를 별도 해석하여 정확한 UTC instant로 정규화한다(세부 문법·표현 범위는 아래 R14). 원문 전체를 Date로 읽어 소수부를 절삭하지 않는다. 소수 6자리까지 보존하고 짧으면 0을 채운다. 6자리 뒤가 전부 0이면 같은 instant이므로 허용하고 0만 걷는다. **소수 정밀도에서는 7번째 이후 비영 숫자만 400 RANGE**이며, 윤초·UTC 응답 연도 범위는 R14의 별도 제약이다. PG가 받는 UTC 문자열을 `$n::timestamptz`에 바인딩하며 입력 문자열 연결·SQL `AT TIME ZONE`은 사용하지 않는다.

목록·상세·잠금·쓰기 RETURNING·최종 view 조회의 모든 시각 projection은 `((extract(epoch FROM ts)*1000000)::bigint)::text`다. 원칼럼을 Prisma/native Date로 받아 성공 응답을 만들지 않는다. 시작/종료의 epoch µs 문자열을 JS BigInt로 받고, 종료 null은 그대로 둔다. **음수도 floor한 ms와 0..999 µs 나머지**로 나눈 뒤 UTC ISO 소수 6자리로 만든다. 원본 offset 모양이 달라도 동일 instant를 보존하면 된다.

```ts
// 응답 복원 의사코드: Date에 원칼럼/소수부 있는 입력을 넘기지 않고 분리된 정수 ms만 사용한다.
const epochUs = BigInt(epochUsText);
let ms = epochUs / 1000n;
let remainderUs = epochUs % 1000n;
if (remainderUs < 0n) { ms -= 1n; remainderUs += 1000n; }
const utcIso6 = new Date(Number(ms)).toISOString()
  .replace(/(\.\d{3})Z$/, `$1${remainderUs.toString().padStart(3, '0')}Z`);
```

통합자의 전용 DB **합성 SELECT 검증 전달값**: `2026-09-06T03:00:00.123456Z`와 `2026-09-06T10:00:00.123456+07:00`는 모두 `1788663600123456`, `1969-12-31T23:59:59.999999Z`는 `-1`이다. 이 편집자가 재실행한 값이 아니다. -1은 ms=-1, 나머지=999로 복원되어야 한다. 기존 µs 행도 같은 정상 경로로 조회하며 배포 제한을 걸지 않는다.

**R3 — 미래 인라인 검사는 화면의 단말 로컬 now 책임이다.** 서버는 유효 instant·µs 표현 범위·ended>=started만 검증한다. 서버보다 5분 빠른 단말의 "지금"도 그대로 보존한다. 서버 수신 now로 미래를 거부하거나 허용 오차·보정 헤더를 만들지 않는다. 직접 HTTP로 미래값을 보내면 서버가 이를 미래라는 이유만으로 차단하지 못한다는 한계와 화면 소관을 문의에 남긴다.

#### R14 보완 — Ajv 허용 형식과 PostgreSQL 입력 문법은 같지 않다

통합자 추가 실측: 고정 Ajv는 `2016-12-31T23:59:60.1Z`, `0000-01-01T00:00:00Z`, `2026-09-07T00:00:00+23:59`를 모두 통과시킨다. Prisma의 date-time 필터는 이 셋을 받아들이지만 **문자열을 raw SQL `$n::timestamptz`로 보내면** 각각22008·22008·22009가 난다. 상수 SELECT의 결과이며 업무행/설정 변경0이다. `23:59:60Z`는 PG가 익일00:00으로 접고, `0001-01-01T00:00:00Z BC`는 정상1BC로 받는다. 그러므로 단순 구분자/offset 모양만 바꿔 바인딩한다는 앞의 초안 설명을 아래로 보완한다.

P0t는 입력의 달력·시/분/정수초·숫자offset을 해석해 **정수초 epoch와 소수µs를 별도 유지**하고, 최종 epochµs를 PG가 받는 UTC문자열로 만든다. 원문 전체를Date로읽어소수부를잃은뒤복원하지않는다. 정수초 구성에Date를사용한다면 setUTCFullYear로0~99년특례를피하고µs는BigInt로끝까지별도보존한다. PG의0년부재는ISO0→1BC로표기만변환하며instant는불변이다. 큰offset도먼저정확한UTC로옮기므로PG의offset입력상한으로정상instant를거부하지않는다.

윤초(second>=60)는 PG가 별도순간/길이를보존하지못하므로 **400 RANGE**로명시거부하고익일로접지않는다(특정입력가장자리②·④). UTC정규응답이계약4자리연도밖이되는입력도400 RANGE다. 기존DB행의UTC표현이응답범위를벗어나면내부500이며숨김0이다. 이범위검사는현대날짜만허용하는임의업무기간제약이아니다. 수치µs초과외의두표현제약을109에남긴다.

추가 P0t단언: `year0000은1BC SQL표기로같은epoch를보존`, `+23:59도정확한UTC로정규화`, `윤초/소수윤초를조용히익일로접지않음`, `UTC연도경계밖은입력400/과거매핑500`, `전체정규화후음수epoch와µs보존`. 원문SQL직접바인딩만테스트하지말고실제바인딩문자열의상수SELECT왕복도구현검증에포함한다. R14는추가통합실측으로발견한계획보완이며독립3리뷰가미리발견했다고쓰지않는다.

### 4-2. 길이와 코드 표시

`durationMinutes`는 epoch BigInt의 `endedUs-startedUs`가 `60000000n`으로 정확히 나뉘면 정수, 그렇지 않으면 null이다. open도 null이다. 저장 시각을 분경계로 자르지 않는다. I-30 §4-3/문의095와 같은 nullable 정수 선례다. **O2 actual/operating은 required integer라 이 null 해법을 복사하지 않는다.** 정수분 정상 사례는 계산 가능하며 소수분 자료의 변환/거부는 R9의 가장자리다.

사유 이름은 페이지의 코드를 한 번에 조회한다(N+1 금지). **폐지/누락 사유는 미분류 표시와 원본 reasonCode를 함께 유지**한다(R8, 재질문 0). 원본 null을 `OTHER`로 바꾸거나 가짜 코드를 만들지 않는다. 코드 원문 자체가 없는 과거행은 required 결손 문제로 별도 처리한다.

### 4-3. 겹침목록의 SQL 전문 후보

아래는 **기간/설비/사유필터 후보집합을 먼저** 고른 뒤, 같은설비 전체구간에서 겹치는 짝을 찾는 형태다. 다른사유와 겹쳐도 사유필터 때문에 겹침이 사라지지 않는다. `end=null`은 비교상 상한없음이지만 실제길이를 만들지 않는다. 길이0은 겹침으로 세지 않으며 맞닿은끝=시작도 교차가 아니다.

```sql
SELECT d.equipment_downtime_id,d.equipment_id,d.breakdown_id,d.reason_code,
       d.remarks,d.recorded_by_worker_no,d.version_no,
       ((extract(epoch FROM d.started_at)*1000000)::bigint)::text AS started_epoch_us,
       ((extract(epoch FROM d.ended_at)*1000000)::bigint)::text AS ended_epoch_us
FROM maintenance.equipment_downtime d
WHERE EXISTS (
  SELECT 1 FROM maintenance.equipment_downtime other
  WHERE other.equipment_id=d.equipment_id
    AND other.equipment_downtime_id<>d.equipment_downtime_id
    AND (d.ended_at IS NULL OR d.ended_at>d.started_at)
    AND (other.ended_at IS NULL OR other.ended_at>other.started_at)
    AND (other.ended_at IS NULL OR d.started_at<other.ended_at)
    AND (d.ended_at IS NULL OR other.started_at<d.ended_at)
)
-- 여기에 bound parameter의 공장별 started_at 기간·equipmentId·reasonCode·openOnly를 AND.
ORDER BY d.started_at DESC,d.equipment_downtime_id DESC
LIMIT $1 OFFSET $2;
```

이 SQL의 WHERE를 count에도 그대로 쓴다. raw string에 입력값을 이어붙이지 않고 Prisma.sql/태그바인딩을 사용한다. open↔closed도 목록의 겹침표시에 포함하는 판정은 명시미정 가장자리로 §9에 기록한다. O2의 "한 번만 센" 경고는 실제sum에 포함된 닫힌구간끼리의 겹침이므로 이 필터와 항상 같은count라고 주장하지 않는다.

## 5. `:close` 유보의 정확한 범위(R4/R5)

O5는 "진행 중인 구간을 지금 시각으로 끝낸다", "오프라인 큐", "If-Match 선택"을 동시에 말하며 **requestBody가 없다**(`equipment-05설비툴.json:1920`). C-12와 P-05-02 §5-2는 단말이 시작과끝을 찍고 서버가 덮지 않는다고 한다. 생성은 단말10:00, 오프라인 종료버튼10:05, 서버도착10:30이면 **10:05는 요청 어느 곳에도 없다**. 서버now10:30을 넣으면25분을 추가하고, startedAt+임의길이를 넣으면 발명이다.

**R4로 O5 유보가 확정됐다.** "지금"만으로 서버 처리시각을 뜻한다고 확정할 근거는 없고, requestBody가 없다고 해서 단말시각 입력을 금지했다고 읽지도 않는다. 현재 입력 안에 필요한 발생시각이 없다는 **본길 원천 결손**이다. 최소 해소 조건은 다음 중 설계/통합자가 택한 하나다: ① 종료 발생시각을 계약 입력으로 전달하는 규약, ② O5의 지금이 서버 처리시각임을 확정하고 offline 길이 왜곡/혼합시계 예외를 명시하는 결정. If-Match를 optional로 맞추는 것만으로는 해소되지 않는다. 고정 계약을 갱신하거나 임의 입력을 추가하지 않는다.

종료시각 원천이 확정된 뒤의 조건부 순서는 다음과 같다(현재 실행/등록 0).

1. 실제 session의 활성 actorUserId 필수 → Worker-No 형식검사 → IdempotencyService.run의 재생/업무 tx. 신규 업무라면 전달 tx로 worker 존재를 확인한다. 계정 미연결 worker도 허용하며 성공 재생 때 현재 worker 상태는 다시 검사하지 않는다.
2. 대상id로 equipment_id를 읽음(없으면404) → 설비행 FOR UPDATE → downtime행 FOR UPDATE·재읽음.
3. If-Match가 있을 때만version대조; 어긋나면409 ConflictResponse(user). 없으면 대조없이 다음단계.
4. 이미 닫혔으면 **400 STATE_LOCKED**(R5). 같은 키의 성공 재생은 이 단계에 오지 않으며 다른 키의 중복 close는 종료시각을 바꾸지 않는다.
5. 확정 규약의 종료 instant를 µs 문자열로 정규화한다. ②의 명시 서버시각 예외가 채택될 때만 잠금 뒤 서버 clock을 한 번 읽는다. 유효 instant·정밀도·ended>=started를 검사하고 역전은 400 PAIR다. 서버 수신 now와 비교하는 별도 미래 검사 0. ended_at, closed_by=필수 actorUserId, closed_by_worker_no, version+1을 함께 쓴다.
6. 같은 tx의 µs 최종 projection으로 Downtime 필수값·view를 검증 → 멱등 완료 → 200. 원칼럼 Date를 반환하는 우회 경로는 없다. 매퍼/멱등 실패는 종료·버전·귀속 모두 rollback한다.

O5 응답표에는 400이 없지만 기존 헤더 guard는 400을 내고, 409 설명은 업무 상태 잠김을 **구체적으로 400**이라고 적는다. **R5는 일반적인 422 설명보다 이 구체 문언을 우선했다.** 이미 닫힘은 400 STATE_LOCKED로 확정하고 400 응답 목록 누락은 문의에 남긴다. 오류 봉투를 다시 미정으로 되돌리지 않는다. O5 유보 이유는 R4의 종료 발생시각 원천이다.

## 6. 등록·수정 한 트랜잭션 순서

### 6-1. 공통 잠금과 귀속

설비 행을 잠그는 이유는 **아직 존재하지 않는 open 행을 SELECT해도 틈을 잠글 수 없기 때문**이다. O4/O6와 향후 O5는 모두 `equipment → downtime` 순서로 통일한다. equipment_id는 수정 본문에 없어 API 내에서 불변이다. O6는 id로 설비를 알아낸 뒤 설비 잠금→대상 재읽음·행 잠금을 수행한다. 삭제/외부 변경이면 404/충돌로 재판정한다. 한 장비의 동시 open Create는 하나만 성공하고 나머지는 명시 업무 오류다. 서로 다른 장비는 같은 잠금을 공유하지 않는다.

```sql
SELECT equipment_id,plant_id FROM mdm.equipment
WHERE equipment_id=$1 FOR UPDATE;
SELECT equipment_downtime_id,equipment_id,breakdown_id,reason_code,remarks,
       recorded_by_worker_no,version_no,
       ((extract(epoch FROM started_at)*1000000)::bigint)::text AS started_epoch_us,
       ((extract(epoch FROM ended_at)*1000000)::bigint)::text AS ended_epoch_us
FROM maintenance.equipment_downtime
WHERE equipment_downtime_id=$2 FOR UPDATE;
SELECT equipment_downtime_id FROM maintenance.equipment_downtime
WHERE equipment_id=$1 AND ended_at IS NULL
  AND equipment_downtime_id<>$2;
```

O4에서 `$2` 비교는 없다. 비활성 설비를 무조건 거부하는 새 정책은 만들지 않는다. **모든 쓰기의 actorUserId는 실제 session의 활성 계정으로 필수**다(R11). 부재를 nullable 감사값으로 기록하지 않으며 worker의 계정 연결 여부와는 다르다. 계정 권한은 현재 PermissionGuard로 검사한다. P-05-02의 can_input_result 잠정 포섭은 단말 공정 축의 필요 여부가 별도 미정이며 계정 검사만으로 그 게이팅까지 충족했다고 주장하지 않는다. 입력 equipment를 단말 equipment로 덮지 않는다.

### 6-2. O4 Create — 201

1. 실제 session의 활성 actorUserId를 확인하고 계약 pipe로 required 3칸·타입·date-time을 검사한다. WorkerNo 없음/공백/max 50 초과는 run 전에 400. 사번 숫자 형식은 강제하지 않는다.
2. actorUserId·Worker-No 원문을 포함하는 지문으로 `IdempotencyService.run` 실행. 성공 재생이면 최초 응답을 내며 업무 현재값 재검증으로 재생을 막지 않는다.
3. 전달 tx로 worker 존재와 DOWNTIME_REASON 활성 코드를 조회한다. 6개 값을 enum으로 닫지 않는다. 없음/폐지는 400 INVALID.
4. 설비 존재와 실제 공장을 확인하고 설비 행을 잠근다. 없는 설비는 400 INVALID(O4에 404 미선언).
5. Ajv가 허용한 시각을 R14의 정확한 UTC·µs 문자열로 정규화하고 SQL 바인딩·epoch projection으로 유효 instant·ended>=started를 검증한다. 역전은 두 필드 PAIR, 물리 6자리 뒤 비영 값·윤초·UTC 응답 연도 범위 밖은 RANGE. 0분과 서버보다 빠른 단말 시각은 허용하며 수신 now 미래 비교는 없다(R2/R3).
6. endedAt이 없을 때만 기존 open을 검사하여 422 STATE_LOCKED. **이미 open이 있어도 과거 닫힌 구간 입력은 허용**한다. 닫힌 겹침도 허용하며 경고 응답 칼럼은 발명하지 않는다.
7. breakdownId가 nonnull이면 동일 설비·RECEIVED/HANDLING 고장인지 확인한다. 없으면 400 INVALID, 설비 불일치는 400 PAIR, **O4의 완료/미등록 상태 새 연결은 422 STATE_LOCKED**다(R5). 새 연결의 판단이 바뀌지 않도록 고장 행도 FOR UPDATE로 대조하며 장비→비가동→새 고장 순서를 따른다. I-31의 역순 잠금 여부는 인계한다(R6).
8. INSERT: equipment, reason, started, ended, breakdown, remarks, recorded_by_worker_no, created_by. downtime_type=null. ended를 받은 닫힌 생성의 closed_by는 실제 계정이다(작성과 종료가 동시에 일어나는 입력). started/ended를 서버 now로 보완하지 않는다.
9. 같은 tx의 µs 최종 projection과 설비/코드 조회로 필수값·view를 검증 → 멱등 완료 → 201. RETURNING 원칼럼 Date로 바로 응답하지 않는다. 고장/W/O/작업세션/보전/재고/알림 쓰기 0.

### 6-3. O6 Update — 200

1. 실제 session의 활성 actorUserId 필수, 계약 pipe·멱등 필수·If-Match 필수 guard. Worker-No는 추가로 강제하지 않는다.
2. run(tx) → 대상 사전조회 404 → 설비 잠금 → 대상 행 잠금 404 → version 대조 409(user).
3. 생략/명시 null을 구분한다. reason을 보냈을 때만 활성 등록값을 검증한다. 메모만 수정할 때 과거 폐지 사유를 현재 활성값으로 바꾸라고 강제하지 않는다.
4. endedAt nonnull은 µs 문자열로 정규화한 뒤 기존 시작 epoch µs와 대조한다. 서버 now와의 미래 비교는 없다. **startedAt/equipment/최초 사번/created_*는 불변**.
5. **닫힌 행+endedAt:null은 400 STATE_LOCKED로 재개 거부**(R6). 열린 행+null은 open 유지, 생략은 현재 종료 유지다.
6. 연결 nonnull 변경은 동일 설비·열린 고장을 검증하고 null은 해제한다. **O6의 완료/미등록 상태 새 연결은 400 STATE_LOCKED**로 O4의 422와 다르다(R5). 기존 연결을 생략하면 고장이 그 사이 DONE이어도 메모/시각 수정을 허용한다.
7. `UPDATE … WHERE id=$id AND version_no=$version`, data 허용 4칸·version+1, 0행이면 409. endedAt이 변경되며 닫히는 경우 closed_by=실제 계정. reason/remarks 변경만이면 기존 closed_by를 유지한다.
8. 같은 tx의 µs 최종 projection·필수값·view 검증 → 멱등 완료 → 200. 성공 후 신버전이 필요하면 O3 재조회. 상태전이 코어·별도 status 축은 추가하지 않는다.

동일 설비 open 중복 방지는 열린 신규 입력에만 적용한다. **모든 비가동 INSERT를 기존 open이 있을 때 거부하는 안은 채택하지 않는다.** 화면이 금지한 "새로 시작"보다 넓게 과거 입력을 막게 된다. 반대로 닫힘→열림을 나중에 허용하면 반드시 같은 설비 잠금·기존 open 검사를 함께 열어야 한다.

### 6-4. 쓰기 SQL 전문 후보 — 전달 tx 안에서만 실행

아래 SQL은 §6의 검증·잠금을 통과한 입력만 받는다. 시작/종료는 Date가 아닌 **정규화한 문자열을 바인딩**한다. 목록·상세·잠금과 같은 µs projection을 RETURNING에도 적용한다. 필요한 설비/사유 표시값을 최종 조회할 때도 같은 전달 tx와 projection을 사용한다. raw RETURNING의 native Date로 성공시키는 예외 경로는 없다.

```sql
-- Create: $1 equipmentId, $2 reasonCode, $3 startedAt, $4 endedAt/null,
-- $5 breakdownId/null, $6 remarks/null, $7 workerNo, $8 필수 actorUserId.
INSERT INTO maintenance.equipment_downtime
  (equipment_id,reason_code,started_at,ended_at,breakdown_id,remarks,
   recorded_by_worker_no,created_by,closed_by,downtime_type_code)
VALUES ($1,$2::app.code_t,$3::timestamptz,$4::timestamptz,$5,$6,$7,$8,
        CASE WHEN $4::timestamptz IS NULL THEN NULL ELSE $8::bigint END,NULL)
RETURNING equipment_downtime_id,equipment_id,reason_code,
          breakdown_id,remarks,recorded_by_worker_no,version_no,
          ((extract(epoch FROM started_at)*1000000)::bigint)::text AS started_epoch_us,
          ((extract(epoch FROM ended_at)*1000000)::bigint)::text AS ended_epoch_us;

-- Update: $1 id, $2 IfMatch version; $3/$5/$7/$9는 각각 필드의 존재 flag.
-- $4 reasonCode, $6 endedAt/null, $8 breakdownId/null, $10 remarks/null,
-- $11 필수 actorUserId. null과 생략을 COALESCE 하나로 합치지 않는다.
UPDATE maintenance.equipment_downtime
SET reason_code=CASE WHEN $3::boolean THEN $4::app.code_t ELSE reason_code END,
    ended_at=CASE WHEN $5::boolean THEN $6::timestamptz ELSE ended_at END,
    breakdown_id=CASE WHEN $7::boolean THEN $8::bigint ELSE breakdown_id END,
    remarks=CASE WHEN $9::boolean THEN $10::text ELSE remarks END,
    closed_by=CASE WHEN $5::boolean AND $6::timestamptz IS NOT NULL
                        AND ended_at IS DISTINCT FROM $6::timestamptz
                   THEN $11::bigint ELSE closed_by END,
    version_no=version_no+1
WHERE equipment_downtime_id=$1 AND version_no=$2
RETURNING equipment_downtime_id,equipment_id,reason_code,
          breakdown_id,remarks,recorded_by_worker_no,version_no,
          ((extract(epoch FROM started_at)*1000000)::bigint)::text AS started_epoch_us,
          ((extract(epoch FROM ended_at)*1000000)::bigint)::text AS ended_epoch_us;
```

INSERT는 기본 version=1을 사용한다. UPDATE 0행은 잠금 뒤에도 version 충돌로 처리한다. actor 없는 요청을 nullable 감사값으로 저장하지 않으며 사번으로 계정을 만들어 채우지도 않는다(R11). 본문이 빈 객체인 PUT은 계약 required가 0이므로 허용하고 version은 1 증가한다. 별도의 무변경 최적화나 400 REQUIRED는 추가하지 않는다.

## 7. Summary 원천·계산·최소 해소 조건

### 7-1. 판정: 빈 DB와 미정은 별개

현재 work_session/비가동/보전/캘린더가 0행이어서 오늘 숫자가 0일 수 있다는 것은 **집계 알고리즘이 정해졌다는 증거가 아니다**. API를 빈 환경에서만 맞는 형태로 등록하지 않는다. 아래 표에서 닫힌 산식은 그대로 준비하고, 본길/명시 미정은 조건부 계획으로 남긴다.

**정상 경로는 이미 계산 가능하다(R9).** 한 공장·한 설비에서 기간 안에 완전히 들어오는 닫힌 세션 09:00~17:00이면 operating=480분이다. 같은 설비 비가동 10:00~11:00와 그 안의 10:15~10:45이면 원본 raw합은 90분, actual union은 60분, availability는 87.5%다. 열린/무장비 자료가 없고 모든 값이 정수분이면 관련 가장자리가 발생하지 않는다. 두 행을 같은 고장에 연결했을 때 **I-30 연결합=90, I-32 union=60**이라는 차이를 테스트한다(R12). 이는 설계 예시이지 DB 실측이 아니다.

**O2 유보 근거는 R10의 두 본길 정의로 한정한다.** 날짜×설비 정상계획구간/적용 산식과 완료보전 엔티티·완료일·범위가 정의되면, 나머지 가장자리에서 명시 거부로 정상 경로를 열 수 있는지 각각 재판정한다. I-31 API 미구현, DB 0행, 열린세션 또는 소수분 하나를 근거로 전체 본길을 유보하지 않는다. 반대로 정의가 없는 planned/완료보전 값을 0이나 상시 생략으로 숨기는 핸들러도 만들지 않는다.

### 7-2. 합집합·겹침 계산 SQL 전문(계산부와 교차기간 가장자리 분리)

이 SQL은 선택을 마친 `selected(equipment_downtime_id,equipment_id,reason_code,s,e)` CTE를 입력으로 받는 **계산부 설계**다. 기간 안의 정상 구간은 원본 s/e를 그대로 쓰며, 교차기간은 R10 해소 뒤 R9의 명시 거부/clip 판단을 별도로 적용한다. s/e는 SQL 내부에서만 timestamptz로 계산하고 애플리케이션에는 정확한 µs 정수 문자열을 낸다. open은 e=null이다.

```sql
WITH selected AS (
  SELECT equipment_downtime_id,equipment_id,reason_code,
         started_at AS s,ended_at AS e
  FROM maintenance.equipment_downtime
  -- 공장/설비 범위와 기간 조건을 바인딩한다.
  -- 교차기간 자료의 명시 거부/clip 여부는 R9의 후속 가장자리 판정을 따른다.
), closed AS (
  SELECT * FROM selected WHERE e IS NOT NULL
), ordered AS (
  SELECT *,max(e) OVER (
    PARTITION BY equipment_id ORDER BY s,e,equipment_downtime_id
    ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING
  ) AS previous_max_end FROM closed
), islands AS (
  SELECT *,sum(CASE WHEN previous_max_end IS NULL OR s>previous_max_end
                    THEN 1 ELSE 0 END) OVER (
    PARTITION BY equipment_id ORDER BY s,e,equipment_downtime_id
  ) AS island_id FROM ordered
), merged AS (
  SELECT equipment_id,island_id,min(s) AS s,max(e) AS e
  FROM islands GROUP BY equipment_id,island_id
)
SELECT COALESCE((SELECT sum((extract(epoch FROM e-s)*1000000)::bigint)
                 FROM merged),0)::text AS union_microseconds,
       (SELECT count(*) FROM selected WHERE e IS NULL) AS open_count,
       (SELECT count(*) FROM closed a WHERE a.e>a.s AND EXISTS (
          SELECT 1 FROM closed b
          WHERE b.equipment_id=a.equipment_id
            AND b.equipment_downtime_id<>a.equipment_downtime_id
            AND b.e>b.s AND a.s<b.e AND b.s<a.e
       )) AS overlapping_rows;
```

`lag(e)` 하나만 보면 큰 구간 안에 짧은 구간 여럿이 들어간 경우 섬이 갈라지는 오류가 생겨 previous **max**를 쓴다. 맞닿은 구간은 union 길이에는 같게 병합할 수 있지만 overlap 경고는 엄밀 부등호라 0이다. 서로 다른 설비의 동시간대는 둘의 시간을 각각 센다.

닫힌 세션 Σ의 원천 SQL은 다음과 같다. 열린 세션의 처리/거부는 별도 가장자리이며 시각은 원칼럼 Date로 반환하지 않는다.

```sql
SELECT ws.work_session_id,ws.equipment_id,ws.work_order_id,ws.terminal_id,
       ws.status_code,
       ((extract(epoch FROM ws.started_at)*1000000)::bigint)::text AS started_epoch_us,
       ((extract(epoch FROM ws.ended_at)*1000000)::bigint)::text AS ended_epoch_us,
       t.plant_id AS terminal_plant_id,e.plant_id AS equipment_plant_id,
       e.production_line_id
FROM production.work_session ws
JOIN mdm.terminal t ON t.terminal_id=ws.terminal_id
```

장비배정표를 여기에 JOIN하면 한 W/O의 복수 배정이 세션을 복제하므로 합이 늘어난다. 실제 equipment_id가 있는 행만 equipment 묶음에 넣으며 null 행은 원본 session id로 한 번만 센다. session끼리 겹침이 있어도 계약은 Σ이므로 downtime union으로 바꾸지 않는다.

### 7-3. minor 정책

MINOR_STOP_THRESHOLD_MINUTES의 **공장 단위 적용과 미설정 기본5는 R8 확정**이다. 제공된 plant·business unit과 전역 ALL 후보만 기존 우선순위로 평가한다. 기존 전역 순위는 ITEM→PROCESS→PLANT→BUSINESS_UNIT→ALL이지만 I-32는 ITEM/PROCESS를 추론하지 않아 그 두 범위의 정책을 끼워 넣지 않는다. 유효기간은 포함 경계, 동순위는 effective_from DESC,id DESC다. 도메인 서비스를 직접 import하지 않는다.

일반 사유와 minor는 **별도 줄**로 나누며 actual 합계에는 둘 다 포함한다. 폐지 사유는 미분류 표시와 원본 code를 함께 보존하고 UNKNOWN 같은 코드도 만들지 않는다. 이 세 가지는 문의를 다시 만들지 않는다. 남는 것은 정책 평가 기준일, 여러 공장/기간의 복수 threshold를 한 scalar에 표시하는 방법, clip 전후/겹친 minor 시간의 처리다. 모두 해당 조건의 가장자리로 R10 해소 뒤 각각 재판정한다.

현행 정책 검증은 MINOR_STOP에 양수 제약을 추가하지 않는다(`assertValues`는 환산비율에만 >0 검사). 따라서 설정 0/음수를 보면 default 5로 바꾸지 않는다. `<0`으로 0건을 내는 것이 문언상 가능하더라도 업무 의미를 별도 문의한다. **기본 5는 값이 없는 경우만**이다.

### 7-4. 계획비가동의 재료는 있음·환산 규칙은 미완

W-05-09 §5-4:164는 "정상 조업시간은 교대가 정한다"고 적었다. mdm.shift의 start/end/crosses_midnight는 실재 재료다. **남는 본길은 날짜×설비에 어떤 정상 계획 구간을 적용하고 그 구간에서 계획 비가동을 어떻게 산출하는가**다. 교대 선택·설비 적용과 WORKING/HOLIDAY/PARTIAL·날짜 행 누락의 산식을 정해야 정상 plannedDowntimeMinutes가 하나로 정해진다. WORKING/HOLIDAY를 근거 없이 0/1440으로 환산하지 않는다.

**과거 수정 때문에 집계가 바뀌는 것은 W-05-09 §6이 허용한다**(R10, 통합자 원문 대조). 그러므로 불변 적용 이력/과거 스냅샷을 필수 원천으로 요구하지 않는다. 기존 effective의 production_line 부모→plant 해석, applicationOf의 날짜 필터 부재, applyCalendar의 옛 적용 삭제는 구현 참고 사실이지 그 자체로 O2를 유보할 근거가 아니다. PARTIAL을 교대마다 배분하는 새 정책도 필요 조건으로 추가하지 않는다. 최소 조건은 **날짜×설비 정상 구간 선택·적용과 그에 대한 계획 정지 산식**이며, 캘린더/이력 서비스를 I-32가 대체 구현하지 않는다.

### 7-5. 보전 건수·고장 완료·비가동 효과 분리

`CORRECTIVE/PREVENTIVE`는 계약 enum이고 고장이 하나라도 있는 트리거 조합은 CORRECTIVE다. 그러나 완료 건수를 `maintenance_order DONE distinct수`로 셀지 `완료 maintenance_result행수`로 셀지, 완료일을 어느 기록에서 가져올지, 설비/툴과 지시 없는 실적을 범위에 어떻게 귀속할지는 정의가 필요하다. **완료 엔티티·완료일·범위가 R10의 두 번째 본길**이다. 현재 result 제약과 미래 계약의 nullable 차이는 구현 시 대조하되 I-31 API 병합 자체를 원천 정의나 필수 선행 조건으로 삼지 않는다. 정의된 원천이 기존 DB에 있으면 그것을 읽을 수 있고, 새 원천이 필요하면 소유자가 마련할 최소 조치를 별도 인계한다.

지시없는완료고장은 **breakdown.status_code='DONE' 및 completed_at의공장기간**을후보원천으로잡고다음두관계의부재를읽는다. 이는I-30정본§4-2와일치하며취소지시도발행흔적이라존재로본다.

```sql
SELECT count(*) AS closed_without_order_count
FROM maintenance.breakdown b
WHERE b.status_code='DONE' AND b.completed_at >= $1 AND b.completed_at < $2
  AND NOT EXISTS (SELECT 1 FROM maintenance.maintenance_order o
                  WHERE o.breakdown_id=b.breakdown_id)
  AND NOT EXISTS (SELECT 1 FROM maintenance.maintenance_order_trigger t
                  WHERE t.trigger_type_code='BREAKDOWN' AND t.source_id=b.breakdown_id);
```

실제구현에는공장별기간/설비범위를반영한다. 고장접수reported_at·처리시작started_at으로완료건수를잡지않는다. I-30완료가보류됐다고기존DB의DONE행이논리적으로없다고가정하지않고,0을고정하지않는다.

## 11. 인계·실측 부록

### 11-1. 인계

I-30에는 FK 연결의 원본 행수/닫힌 raw합/열린 건수 변동만 인계한다. 같은 고장의 중첩 60분+30분이면 **I-30 연결합=90분, I-32 설비별 union=60분**이다(R12). 고장완료 원천(090)은 I-32가 해결하지 않는다. 분단위 정밀도는 기존095와 맞추되 nullable duration과 required summary를 구분한다. 날짜 helper는 I-30 담당자의 병합 뒤 실제 함수만 재사용한다.

I-11의 equipment null 세션을 계획장비로 메우지 않으며 STOPPED도 ended=null이면 열린 세션이라는 사실만 승계한다. 열린세션 가장자리를 I-11 종료 동작 변경으로 우회하지 않는다. I-31에는 완료 엔티티/완료일/설비·툴 범위와 직접FK+trigger를 인계하되 API 병합을 그 정의와 혼동하지 않는다. **equipment→downtime→새 breakdown의 역순 잠금 여부**도 인계한다(R6). I-29에는 실제 세션 분모와 계획 교대 분모가 다른 지표이며 OEE 곱/성능/양품률은 I-32 범위가 아님을 인계한다.
