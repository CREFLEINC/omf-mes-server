## 0. 결론과 반드시 지킬 불변식

1. 대상은 계약의 실사 **6 오퍼레이션 전부**다. 완료 시 커버리지 기여는 **+6**이다.
2. 실사 자체는 재고 원장을 쓰지 않는다. `POST :close`도 잔액을 고치지 않는다. 차이는 I-14 조정이 전기한다.
3. `POST /inventory/counts`는 창고 장부의 `on_hand_qty`를 서버가 스냅샷해 라인을 만든다.
4. 물리에 없는 `counted`를 `inventory.inventory_count_line.counted boolean NOT NULL DEFAULT false`로 추가한다. `counted_by`나 수량 0으로 미실사를 추정하지 않는다.
5. 블라인드 실사의 미실사 라인은 `systemQty`를 생략하고 `countedQty=0`, `varianceQty=0`으로 마스킹한다. 실제 수량 제출 뒤에는 차이를 보여준다.
6. 위치별 PUT은 **그 위치의 전량 치환**이다. 본문에서 빠진 기존 라인은 삭제하지 않고 미실사로 되돌린다. 장부 스냅샷 `system_qty`는 보존한다.
7. 마감은 `COMPLETED`가 아니고 `IN_PROGRESS`이며, 미실사 0건이고, 차이 라인마다 **POSTED 조정 라인**이 있을 때만 된다.
8. 모든 쓰기는 멱등 처리한다. PUT의 If-Match는 선택, close는 필수다. 계약이 선언하지 않은 PUT/close 응답 ETag는 내리지 않는다.
9. `raw/`와 다른 레인 파일은 건드리지 않는다. 계약 사본도 갱신하지 않는다.

|---|---|:-:|:-:|:-:|:-:|
| `GET /inventory/counts` | 창고·계획일 From/To·유형·상태·진행중만·page/size | — | — | — | — |
| `GET /inventory/counts/{id}` | 경로 id | — | — | **200** | — |
| `GET /inventory/counts/{id}/lines` | 위치·품목·미실사만·차이만·page/size | — | — | — | — |
| `POST /inventory/counts` | 유형·창고·계획일·blindCount | ✓ | — | **201** | ✓ |
| `PUT /inventory/counts/{id}/lines` | 위치·영업일·발생시각·라인 전체 | ✓ | **선택** | — | ✓ |

- 목록 응답은 `{items,page}`, 상세은 `{inventoryCount,summary}`, 라인도 `{items,page}`다.

- 조회의 잘못된 숫자·날짜 질의는 공용 관례대로 400을 내지만 계약은 조회 400을 선언하지 않았다. 기존 통보 186 범주에 더한다.

## 2. 물리 모델 결정

### 2-1. 추가 마이그레이션 1건

```sql
ALTER TABLE inventory.inventory_count_line
  ADD COLUMN counted boolean NOT NULL DEFAULT false;
```

- 추가만 하고 기존 행은 `false`로 안전하게 해석한다. 과거 행을 임의로 실사 완료로 백필하지 않는다.
- Prisma 모델에도 `counted Boolean @default(false)`를 반영한다.
- `counted_at`은 물리 NOT NULL이므로 미실사 행에도 스냅샷 생성 시각을 저장하되, 계약 설명대로 `counted=false`이면 의미 없는 값이다.
- 인덱스는 추가하지 않는다. 주요 조회는 부모 FK와 기존 `(inventory_count_id,line_no)` 유일 인덱스를 타고, `counted` 단독 선택도는 낮다.

### 2-2. 스냅샷 차원

`inventory_count_line`이 표현할 수 있는 차원은 `(location,item,lot,uom)`뿐이다. 따라서 개시 시 같은 창고의
`inventory_balance.on_hand_qty`를 이 네 축으로 합산한다. 품질·재고상태·소유·파트너·취급단위·조직 축은 라인에 담을 수 없어 합친다.

- 합계가 0인 묶음은 만들지 않는다.
- 음수 묶음이 하나라도 있으면 회신 전에는 전체 생성을 400으로 거부한다. 누락·0 절단은 하지 않는다. 실제값 보존에는 물리 도메인과 계약을 함께 바꿔야 하므로 질의 276으로 결정받는다.
- `line_no`는 `(location_id,item_id,lot_id NULLS FIRST,uom_id)` 안정 정렬 뒤 1부터 부여한다.
- 새 현장 라인은 같은 네 축의 **현재** `on_hand_qty` 합계를 `system_qty`로 삼고, 없으면 0이다.
- 한 PUT 안의 네 축 중복은 400 `UNIQUE_VIOLATION`이다. 물리 유일 제약은 추가하지 않는다.

## 3. 조회 규칙

### 3-1. 목록

- `plannedDateFrom` 포함, `plannedDateTo` 포함으로 `date` 컬럼을 비교한다.
- `inProgressOnly=true`면 `status_code='IN_PROGRESS'`를 강제한다. 함께 온 다른 `statusCode`가 다르면 결과 0건이다.
- 기본 정렬은 `planned_date DESC, inventory_count_id DESC`다.
- 공용 페이지 규칙 기본 1/50, 상한 200을 쓴다.

### 3-2. 상세 요약

요약은 페이지와 무관하게 DB 전체 라인으로 센다.

| 값 | 계산 |
|---|---|
| `plannedCount` | 전체 라인 수 |
| `countedCount` | `counted=true` 수 |
| `uncountedCount` | `counted=false` 수 |
| `varianceCount` | `counted=true AND variance_qty<>0` 수 |
| `closable` | 아래 우선순위 결과가 없음 |

차단 사유 우선순위는 다음과 같다.

1. `status=COMPLETED` → `ALREADY_CLOSED`
2. `status<>IN_PROGRESS` → `STATE_LOCKED`
3. 미실사 존재 → `COUNT_REMAINING`
4. 차이 라인 중 POSTED 조정 라인이 없는 행 존재 → `VARIANCE_UNADJUSTED`
5. 그 밖 → `closable=true`, 사유 `null`

`POSTED` 판정은 I-14가 추가한 `inventory_adjustment_line.inventory_count_line_id`와 부모
`inventory_adjustment.status_code='POSTED'`를 함께 본다. 등록·승인중 조정은 완료로 세지 않는다.

### 3-3. 라인 목록과 블라인드

- 정렬은 `line_no ASC, inventory_count_line_id ASC`다.
- `uncountedOnly`는 새 `counted=false`, `varianceOnly`는 `counted=true AND variance_qty<>0`다.
- `itemCode/itemName/lotNo/locationCode`는 조인해 내린다.
- 블라인드이면서 미실사면 `systemQty`를 생략하고 수량·차이는 0으로 마스킹한다. 이 결정은 계약 required 목록과 설명문 모순을 통보 273에 남긴다.

## 4. 쓰기 규칙

### 4-1. 실사 개시 POST

1. 유형 코드는 `INVENTORY_COUNT_TYPE` 활성 코드로 검증한다.
2. 창고 존재를 확인하고 창고의 `plant_id`를 채번 범위로 쓴다.
3. `INVENTORY_COUNT` 기본 접두어 `IC`, `plannedDate`를 기간키로 채번한다.
4. 헤더 상태는 동작 이름 그대로 `IN_PROGRESS`로 시작한다. `PLANNED`는 외부 적재·과거 행 조회를 위해 허용하되 이 API가 만들지 않는다.
5. 채번은 트랜잭션 밖에서 하고 헤더와 스냅샷 라인은 한 트랜잭션에 저장한다. 번호 충돌은 최대 3회 재시도한다.
6. 빈 창고는 라인 0건인 진행중 실사를 정상 생성한다. 다만 마감은 즉시 가능하다.
7. 응답은 상세+요약, 실제 `version_no` ETag다.

### 4-2. 위치별 라인 치환 PUT

잠금 순서: 실사 헤더 `FOR UPDATE` → 선택 If-Match 대조 → 상태 판정 → 위치와 기존 라인 → 참조·코드 검증 → 치환 → 헤더 버전 증가.

- `COMPLETED`는 400 `STATE_LOCKED`; `PLANNED`는 첫 정상 치환에서 `IN_PROGRESS`로 옮긴다.
- 본문 `locationId`와 각 라인의 `locationId`는 같아야 하고 위치는 실사 창고 소속이어야 한다.
- id가 있으면 해당 실사·해당 위치의 기존 라인이어야 한다. 없는 id는 새 라인이다.
- 기존 라인은 `system_qty`와 `line_no`를 보존하고 제출 수량·사유·시각·행위자만 갱신한다.
- 빠진 기존 라인은 `counted=false`, `counted_qty=0`, `variance_reason_code=null`, `counted_by=null`로 되돌린다.
- 차이가 0이 아니면 활성 `VARIANCE_REASON`이 필수이고, 차이가 0이면 사유를 받지 않는다.
- `businessDate`와 최상위 `occurredAt`은 형식만 검증하고 저장하지 않는다. 각 라인의 `countedAt`이 실사 시각의 정본이다.
- `X-Worker-No`가 있으면 작업자를 검증하고 연결된 `app_user_id`를 `counted_by`에 쓴다. 헤더가 없으면 세션 사용자다. 작업자에 계정 연결이 없으면 `counted_by=null`을 허용한다.
- 같은 키 재생은 같은 응답이며 버전을 다시 올리지 않는다. 다른 키의 동시 요청은 헤더 잠금으로 직렬화한다.

### 4-3. 마감 POST

잠금 순서: 헤더 `FOR UPDATE` → 필수 If-Match → §3-2 차단 사유 재계산 → 상태를 `COMPLETED`로 갱신하며 버전 증가.

- 실패 코드는 요약의 사유 문자열과 같다: `ALREADY_CLOSED`, `STATE_LOCKED`, `COUNT_REMAINING`, `VARIANCE_UNADJUSTED`.
- `businessDate`는 원장 없는 작업의 공용 규칙대로 검증만 하고 저장하지 않는다.
- 성공 응답은 새 상세이지만 ETag는 계약 미선언이라 내리지 않는다. 다음 토큰이 필요하면 상세 GET을 다시 부른다.

## 5. 권한·오류·응답

- `manual-permissions.ts`에 정확히 두 줄을 추가한다.
  - `PUT /inventory/counts/{inventoryCountId}/lines`: `M-01-11`
  - `POST /inventory/counts/{inventoryCountId}:close`: `W-01-04`
- 숫자·날짜·참조·코드 오류는 400 `INVALID`, 필수 사유는 `REQUIRED`, 중복 차원은 `UNIQUE_VIOLATION`이다.
- 존재를 계약이 선언한 상세 GET은 404다. 라인 GET·PUT·close도 기존 형제 규칙대로 없는 부모에 404를 내지만 계약 미선언임을 통지한다.
- `ERROR_CODE`에 마감 사유 3개(`COUNT_REMAINING`, `VARIANCE_UNADJUSTED`, `ALREADY_CLOSED`)를 추가한다. `STATE_LOCKED`는 기존 값을 쓴다.

## 6. 구현 PR 분할

계획 PR을 제외한 구현은 **5개**로 나눈다. 원안 3개보다 늘린 이유는 물리 변경, 조회 집계, 스냅샷, 오프라인 치환, 마감 동시성이 각각 독립 실패면을 갖기 때문이다.

| 순서 | 범위 | 완료 게이트 |
|:-:|---|---|
| ① | `counted` 마이그·Prisma·에러코드·권한·번호 접두어 | Prisma validate/generate, 해당 공용 단위 |
| ② | 뷰·조회 3건·요약 | 단위 + 조회 E2E + 계약 커버리지 +3 |
| ③ | 개시 POST·장부 스냅샷 | 단위 + POST E2E + 커버리지 +1 |
| ④ | 위치별 PUT | 단위 + PUT E2E + 커버리지 +1 |
| ⑤ | close·마감 판정·문서 마감 | 단위 + close E2E + 관련 회귀 + 커버리지 +1 |

각 PR은 `origin/main`을 fetch/merge한 뒤 게이트를 다시 돌리고 **merge commit**으로 병합한다. 다음 PR은 새 main에서 시작한다.

## 7. 테스트와 뮤테이션 표

### 7-1. 단위 시험

- 목록 7개 질의의 독립 매핑, 포함 날짜 경계, 정렬 2축, 페이지 상한.
- 요약 5수치와 차단 사유 우선순위 5갈래.
- 블라인드 미실사 마스킹과 실사 완료 뒤 차이 노출.
- 스냅샷 네 축 합산, 0합 제외, 안정 lineNo.
- PUT 잠금 순서, 선택 버전, 빠진 행 미실사 복귀, 신규 행 systemQty 계산, 중복·사유 검증.
- 사번 있음/없음/계정 미연결 3갈래.
- close가 POSTED 조정만 인정하고 헤더 버전을 한 번 올림.

### 7-2. E2E 핵심

- 6 오퍼레이션 정상·권한·404·400·409를 계약 선언에 맞춰 검증한다.
- 개시가 실제 잔액 여러 차원을 `(location,item,lot,uom)`로 합치고 원장을 안 건드린다.
- 블라인드 응답이 미실사 장부를 누설하지 않는다.
- PUT 빈 배열이 해당 위치를 미실사로 되돌리고 다른 위치는 보존한다.
- 선택 If-Match 없음은 통과, 낡은 값은 409, 동일 멱등키 재생은 단일 저장이다.
- 차이 0, 차이+POSTED 조정, 차이+REGISTERED 조정을 각각 마감한다.
- I-14 회귀와 함께 실행하고 `TRUNCATE … CASCADE`를 쓰지 않는다.

### 7-3. 반드시 RED여야 하는 변이

1. 목록 2차 정렬 제거, 날짜 상·하한 연산자 뒤집기.
2. `counted` 대신 `counted_by` 또는 `counted_qty`로 미실사를 판정.
3. 블라인드에서 `systemQty` 또는 미실사 실제 variance 노출.
4. 스냅샷을 `available_qty`로 바꾸거나 품질상태별 라인을 따로 생성.
5. PUT의 누락 행을 그대로 두기, 다른 위치까지 미실사로 돌리기, 기존 `system_qty` 덮기.
6. 새 라인의 시스템 수량을 항상 0으로 두기.
7. `varianceReasonCode` 필수 조건을 반대로 적용.
8. If-Match 선택을 필수로 바꾸기 또는 supplied version 대조 제거.
9. 마감에서 REGISTERED 조정을 POSTED로 인정하거나 조정 헤더 상태를 안 보기.
10. 마감 사유 우선순위를 뒤집거나 버전을 안 올리기.
11. 멱등 callback 밖에서 업무 쓰기 수행.
12. 실사 쓰기에서 재고 원장·잔액을 변경.
