### 3-4. ⭐ `work_order_dependency` 의 원천 — **`routing_operation_dependency` 를 옮긴다**

**갈림**: ⓐ `operation_seq` 이웃 체인 N−1 쌍을 서버가 만든다 / ⓑ `planning.routing_operation_dependency` 행을 그대로 인스턴스로 옮긴다.

§2 **0단계 선례** — ⓑ 를 가리키는 실측이 셋이다. ① 표 `planning.routing_operation_dependency` 가 실재하고 `dependency_type_code` 4값 코드 그룹(`ROUTING_OPERATION_DEPENDENCY_TYPE`)까지 시드돼 있다. ② 계약이 `PUT /planning/routings/{routingId}/operation-dependencies` 를 두었고 **이미 구현돼 있다**(`routing-operation.service.ts:145-180` — I-1~I-2 시기). ③ `routing-revision.service.ts:125-129` 가 Rev 를 뜰 때 **의존 행을 복제한다** — 마스터가 그 축을 «관리한다»는 증거다.

### 3-6. 멱등과 재확정

- 컨트롤러가 `runIdempotent(this.idempotency, request, HttpStatus.OK, …)` 로 감싼다 ⇒ **같은 `Idempotency-Key` 재전송은 work() 자체가 안 돌아** 새 전개가 없다(계약 원문 그대로). e2e 가 `work_order` 수 불변으로 잰다.
- **다른 키로 재확정**하면 ⑦ 이 400 `STATE_LOCKED` 로 막는다(`CONFIRMED` 는 `from` 밖).

### 3-7. `:confirm` 400·404·409 갈래 — 순서가 판정이다

`404`(⑤ 계획 없음) → `409`(⑥ If-Match) → `400 STATE_LOCKED`(⑦) → `400 LINE_REQUIRED`(② · **tx 밖이라 ⑦보다 앞이다**).
⚠ ② 가 tx 밖이라 「확정된 계획 + 공정 0건」이면 `LINE_REQUIRED` 가 먼저 난다. ⛔ 고치지 않는다 — 공정 0건 Routing 은 Rev 확정을 못 지난 것이라 도달하기 어렵고, tx 안으로 옮기면 채번을 tx 안에서 부르게 된다. e2e 이름에 순서를 못 박는다(§8-3).

2. tx 밖 채번 `PP`(`planDate`·`plantId` — 계획의 P/O 를 먼저 읽어 공장을 얻는다. 없는 P/O 면 여기서 **400 `INVALID`**(field `productionOrderId`) — ⛔ 404 를 안 낸다(계약이 404 를 선언하지 않았다)).
3. `prisma.production_plan.create` — `status_code:'DRAFT'` · `split_of_plan_id`·`split_reason_code` 는 있을 때만 · `created_by`/`updated_by` = 세션.
4. FK 부재(`bomId`·`routingId`·`uomId`·`plannedLineId`)는 공용 Prisma 그물이 400 으로 낸다.
5. **201 `ProductionPlan`** · ⛔ `setEtag` 안 부른다(201 에 ETag 미선언 — 실측).

⭐ **합계 검증(계획 합 vs P/O 수량)을 서버가 하지 않는다** — `W-02-02` §5-2 가 「**합계 제약이 없다** · DB 가 검증하지 않는다 · 초과=ⓑ경고 · 미달=ⓒ표시만 · **화면 책임**」이라 직접 적었다. §2 기준 4.
⭐ **원본 계획 수량을 줄이지 않는다** — `W-02-02` §5-7 「원본 계획을 골라 **새 계획을 만든다**」 + §5-2 의 합계 화면 책임. 서버가 줄이면 화면이 못 되돌린다(기준 1 — 상태를 안 쓰는 쪽).
⭐ `splitOfPlanId.sourcePlanId` 가 **다른 P/O 의 계획**이어도 막지 않는다(계약 침묵 · 기준 4) — 「알려둘 것」.

### 4-2. `PUT …/{productionPlanId}` — 200

`FOR UPDATE` → `ifMatchVersion` 대조(409) → **`status_code='DRAFT'` 가 아니면 400 `STATE_LOCKED`**(계약 「확정 전에만 고칠 수 있다」 + `statusCode` 설명이 400 을 이름으로 적었다) → `assertCodeValues` 없음(본문에 코드 칸이 0) → `optional()` 여섯 칸 UPDATE + `version_no+1` → 200.
⛔ `plannedLineId`·`remarks` 만 명시적 null 을 받는다 — `workOrderUpdateData()` 와 같은 `optional(...)` 조각.
⛔ **상태 잠금이 If-Match 보다 «뒤»다** — I-12 R-6 과 같은 순서(잠금 → 토큰 → 상태). ⚠ 계약이 순서를 안 적었다 ⇒ e2e 로 못 박는다.

### 4-3. `DELETE …/{productionPlanId}` — 204 · **물리 삭제**

- 계약 x-internal-note 원문: 「확정 전 생산 계획은 아직 문서가 아니라 **편집 중인 초안**이라 **물리 삭제**를 둔다 … 확정 뒤에는 W/O 가 매달려 있어 **404 가 아니라 409** 로 막는다」.
- 순서: `FOR UPDATE`(404) → `ifMatchVersion`(409 `VERSION_CONFLICT`) → `status_code !== 'DRAFT'` 면 **409 `INVALID_STATE`** → `prisma.production_plan.delete` → **204**.
- ⭐ **FK 두 개가 남는다**: ⓐ `work_order.production_plan_id`(`onDelete: NoAction`) — `DRAFT` 계획엔 W/O 가 없으니 안 걸린다. ⓑ **A11 자기 FK** — 이 계획을 원본으로 삼은 분할 계획이 있으면 DELETE 가 FK 위반(P2003)으로 튄다. ⇒ 공용 Prisma 그물이 400 을 내는데 계약 DELETE 에 **400 이 없다**. **손으로 먼저 본다**: 자식 계획이 있으면 **409 `SUCCESSOR_EXISTS`**(기존 코드 — 「후속 문서가 있다」와 같은 뜻) · 봉투는 `ProductionConflictResponse`.
- 컨트롤러는 `runIdempotent(…, HttpStatus.NO_CONTENT, …)` — 선례 `DELETE /production/work-orders/{id}/resource-plans/{id}`(`work-order.controller.ts:229-238`).

### 4-4. `GET` 2건

- 목록: `where` 4축 AND(모순은 빈 목록 · 400 아니다 — I-12 §9-1 #14 선례) · 정렬 `plan_date asc, production_plan_id asc` · `pagedResponse`.
- 상세: `findUnique` → 없으면 404 → `setEtag(response, row.version_no)`.
- 뷰 `production-plan-view.ts` — `omitEmpty()` 로 값 없는 칸 키 생략. ⛔ `splitOfPlanId` 를 **안 싣는다**(계약 응답에 없다).

## 5. P/O 조회 2 + `:acknowledge` + `:resync`

### 5-1. 파생 두 칸 — 페이지 단위 집계 2쿼리

목록·상세가 같은 뷰를 쓴다. 페이지의 `production_order_id` 목록을 얻은 뒤 **2회**만 더 돈다(행마다 세지 않는다 — `plan.md` §5 규칙 10 「집계는 서버가」).

```sql
-- expandedWorkOrderCount
SELECT p.production_order_id, count(*)::int AS n
  FROM production.work_order w
  JOIN planning.production_plan p ON p.production_plan_id = w.production_plan_id
 WHERE p.production_order_id IN (…) GROUP BY 1;

-- plannedWorkOrderCount — 계획별 Routing 공정 수의 «합»
SELECT p.production_order_id, COALESCE(sum(oc.cnt), 0)::int AS n
  FROM planning.production_plan p
  LEFT JOIN (SELECT routing_id, count(*) AS cnt
               FROM planning.routing_operation GROUP BY 1) oc
    ON oc.routing_id = p.routing_id
 WHERE p.production_order_id IN (…) GROUP BY 1;
```

- 행이 없으면 **0**(⛔ 키 생략이 아니다 — 계약 「0 이면 계획이 아직 없다」가 뜻을 갖는다 · `W-02-01` §6 이 `W/O 0/0` 과 `0/N` 을 다른 업무 상태로 그린다).
- ⛔ 취소된 W/O 를 빼지 않는다 — 계약 「이 P/O 아래 **생성된** W/O 수」(기준 4).

### 5-2. `unacknowledgedOnly` — 「확인된 것」의 여집합

계약: 참이면 ⓐ `acknowledgedAt` 이 비었거나 ⓑ `lastChange.receivedAt > acknowledgedAt` — **또는**다.
⇔ **「`acknowledged_at >= last_change_received_at` 인 확인 행이 하나도 없는 P/O」**.
Prisma 는 두 표의 «칸끼리» 비교를 못 태운다 ⇒ **후보를 좁힌 뒤 id 필터를 얹는다**(`work-order-list-where.ts` 의 `releasable` 선례 · 「서비스가 후보 집합을 좁힌 뒤 `work_order_id` 필터를 얹는다」).

```sql
-- 「확인됨」 집합
SELECT DISTINCT a.production_order_id
  FROM production.production_order_acknowledgement a
  JOIN planning.production_order o USING (production_order_id)
 WHERE a.acknowledged_at IS NOT NULL
   AND (o.last_change_received_at IS NULL OR a.acknowledged_at >= o.last_change_received_at);
```
→ `where.production_order_id = { notIn: ids }`.
⚠ 확인 행이 있는 P/O 만 담기므로 오늘 집합 크기는 «확인한 건수»다 — 그래도 무한히 자랄 수 있는 축이라 §11 ⑥ 에 후속(서브쿼리 raw 전환)을 남긴다.

### 5-3. `includeChildren` — 루트로 페이지를 세고 하위를 붙인다

1. `where`(필터 전건) **AND `parent_production_order_id IS NULL`** 로 `total` 을 세고 한 페이지의 **루트 id** 를 뽑는다.
2. 재귀 CTE 로 그 루트들의 **하위 전건**을 뽑는다.

```sql
WITH RECURSIVE t AS (
  SELECT production_order_id, parent_production_order_id, bom_level
    FROM planning.production_order WHERE production_order_id = ANY($1)
  UNION ALL
  SELECT c.production_order_id, c.parent_production_order_id, c.bom_level
    FROM planning.production_order c JOIN t ON c.parent_production_order_id = t.production_order_id)
SELECT production_order_id FROM t;
```
3. 루트+하위 전건을 한 번에 읽고 `bom_level asc, production_order_id asc` 로 낸다(계약 「트리는 `parentProductionOrderId`·`bomLevel` 로 만든다 · 기본 표시는 전체 펼침」).
4. `page.total` = **루트 수** · `items.length` ≥ total 일 수 있다 — 계약이 그렇게 적었다.
⛔ 거짓·미지정이면 이 갈래를 아예 안 탄다(평면 목록).
⚠ 하위에는 필터를 **다시 걸지 않는다** — 계약 「필터·`page`·`size`·`total` 은 «루트 P/O» 기준」.

### 5-4. `lastChange` — `withLastChange=true` 일 때만

- `receivedAt` = `production_order.last_change_received_at`. **널이면 `lastChange` 키 자체를 생략**(계약 「변경을 한 번도 받지 않은 P/O 는 켜도 이 칸이 없다」).
- `changedFields` = `production_order_change_field` 행을 **`ORDER_QTY` → `DUE_DATE` → `STATUS_CODE` 고정 순**으로 정렬(코드에 배열 상수 하나 · DB `ORDER BY` 로 못 낸다).
- 한 행 → 한 항목:

| 계약 칸 | 값 |
|---|---|
| `field` | `field_code` 그대로(계약 enum 3값) |
| `label` | 상수 3(`수량`·`납기`·`상태`) — 계약 「계약이 표시명까지 내려 준다」 |
| `beforeText` | `ORDER_QTY`→`before_order_qty` 십진 문자열(**단위 안 붙인다**) · `DUE_DATE`→`YYYY-MM-DD` · `STATUS_CODE`→**상태 표시명** |
| `afterText` | 지금 P/O 행의 짝(`order_qty`·`due_date`·`status_code`) — 계약 「P/O 행에는 이미 변경 후 값이 반영돼 있다」 |
| `beforeQty` | `ORDER_QTY` 일 때만 `before_order_qty` · 나머지는 **`null`**(계약이 `[number,null]` 로 널을 명시) |

- 상태 표시명: `mdm.code_value`(그룹 `PRODUCTION_ORDER_STATUS`)의 `code_name`. **못 찾으면 코드 문자열 그대로**(막지 않는다 — 기준 1). 페이지 전체의 상태 코드를 한 번에 읽는다(행마다 조회 금지).
- ⛔ **행이 0건이면 `changedFields: []`** — 계약 「빈 배열일 수 있다 … 열거한 세 항목 «밖»이 바뀐 경우다」(컬럼 주석이 같은 말을 한다).

### 5-5. `POST …:acknowledge` — 200

**tx 안**(멱등 래퍼 안):

| # | 하는 일 |
|:-:|---|
| ① | `SELECT … FROM planning.production_order WHERE production_order_id=$1 **FOR UPDATE**`(404) — `version_no`·`last_change_received_at`·`status_code` 를 쥔다 |
| ② | `ifMatchVersion` 대조 — 어긋나면 **409 `VERSION_CONFLICT` · `conflictCause='erpSync'`**(계약 「409 가 나면 … 「ERP 가 다시 보냈다」」) |
| ③ | `last_change_received_at IS NULL` 이면 **400 `STATE_LOCKED`**(§2-3) |
| ④ | 본문 400 넷 — ⓐ `PROCEED` + 배열 비지 않음 · ⓑ 영향 W/O 아님 · ⓒ 중복 `workOrderId` · ⓓ 세 칸 모두 없음. ⛔ **전부 tx 안**이다(ⓑ 가 DB 를 읽는다) |
| ⑤ | **영향 W/O 집합** = `work_order WHERE production_plan.production_order_id = $1`(⭐ 직접 칸이 없다 — 계획 경유. `work-order-list-where.ts:57` 이 같은 축을 쓴다). ⛔ 취소·마감 여부로 좁히지 않는다(계약 침묵) |
| ⑥ | 조정 건별 `UPDATE production.work_order SET …, version_no = version_no + 1 WHERE work_order_id=$i **AND version_no=$본문versionNo**` — 0행이면 **409 `VERSION_CONFLICT` · `conflictCause='user'`**(⭐ `W-02-06` §6 이 원인을 갈랐다). 「하나라도 어긋나면 전체 거부」는 트랜잭션이 진다 |
| ⑦ | `decisionCode='APPLY'` 면 **조정되지 않은 영향 W/O 에 `po_mismatch = true`**(계약 원문). ⭐ `PROCEED` 는? — 「강행 시 불일치 플래그」(`W-02-06` R09 · §5-2)라 **`PROCEED` 는 영향 W/O 전건**에 세운다 |
| ⑧ | 확인 행 upsert(§2-3) |
| ⑨ | ⛔ **`production_order.status_code` 를 옮기지 않는다** · ⛔ `version_no` 도 올리지 않는다 — `plan-api.md` 830행 「P/O 상태는 **ERP 수신이 옮긴다** · `:acknowledge` 는 판정만 기록」. ⇒ **If-Match 토큰이 그대로 유효하다**(같은 P/O 를 두 번 확인할 수 있다 · 「알려둘 것」) |
| ⑩ | 200 `ProductionOrder`(파생 3칸 새 값 포함) · ETag 미선언이라 안 내린다 |

⛔ **취소 반영은 안 한다** — 계약 「중단·취소 반영의 W/O 취소는 이 본문에 싣지 않는다 — `:cancel` 을 건별로」. `:cancel` 은 I-6 이 이미 구현했다(선발행 슬롯 전건 폐번 · DR-007).
⛔ **P/O 가 `CANCELLED` 여도 400 을 내지 않는다** — 취소야말로 확인해야 할 변경이다(`W-02-06` §3 목록의 셋째 줄이 「중단(취소)」다). §2 기준 1.

### 5-6. `POST …:resync` — 202 · 아웃박스 한 줄

- **부분 건너뜀**(`plan-api.md` 707행 · `plan.md` §6): 202 접수 + `integration.integration_message` 한 줄까지. 전송기 없음.
- 순서: 존재 확인(404) → `prisma.$transaction` 에서 `outbox.enqueue(tx, …)` → **202 · 본문 없음**(계약이 202 에 content 를 안 줬다).
- 값:

| 칸 | 값 | 근거 |
|---|---|---|
| `interfaceCode` | 상수 **`'IF-PO-RESYNC-REQUEST'`** | `IF_WO_CLOSE='IF-WO-CLOSE-SEND'`(`outbox.service.ts:21`) · 계약 example `IF-GR-SEND` 형식. `interface_definition` 0행이라 정의 행을 만들지 않는다(기존 문의 **#66**) |
| `messageKey` | **`outboxMessageKey(IF_PO_RESYNC, productionOrderNo) + ':' + Idempotency-Key`** | ⭐ I-6 은 「버전을 안 붙인다」였는데 그건 **한 W/O 가 평생 한 번 마감**하기 때문이다. 재동기는 **몇 번이고 다시 요청하는 것**이라 문서번호만으로 잠그면 둘째 요청이 조용히 사라진다(`enqueue` 가 `alreadyQueued` 로 흡수). 같은 멱등키 재전송은 `runIdempotent` 가 이미 흡수하므로 이 키로 「요청 1건 = 행 1건」이 정확히 선다 |
| `targetTypeCode` | `'PRODUCTION_ORDER'` | `INTERFACE_TARGET` 5값 밖이나 그룹이 열려 있다 — I-6 이 `'WORK_ORDER'` 로 같은 선례를 만들었다(`work-order-close.service.ts:19`) |
| `targetId` | `productionOrderId` | |
| `payload` | `{ productionOrderNo, erpOrderNo, requestedAt }` | ⛔ 서버가 값을 해석하지 않는다 |

- ⚠ `direction_code='OUTBOUND'` 인데 **뜻은 「우리가 ERP 에 다시 보내 달라고 «요청»한다」**다 — 나가는 메시지가 맞다. 「알려둘 것」.
