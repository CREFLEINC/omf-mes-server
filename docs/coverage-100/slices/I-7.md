### 1-4. 파생 스키마 — `ProductionResult` · `LotLifecycleHistoryEvent` · `Lot`

- ⚠ `shiftId` 는 **선택**이다 ⇒ D1 뒤 NULL 이면 **키를 생략**한다(`omitEmpty` · `plan.md` §5 규칙 7).

#### ⓑ `LotLifecycleHistoryEvent` — required **5**

`lotLifecycleHistoryId`·`lotId`·`toLifecycleStatusCode`·`transitionCode`·`changedAt`. 선택: `lotNo`(조인)·`fromLifecycleStatusCode`(⌜최초 전이(L1)는 null 이다⌝)·`sourceDocumentTypeCode`·`sourceDocumentId`.

⭐ `sourceDocumentTypeCode` 가 **enum 3값**이고 전이별 대응을 계약이 못박았다:

| 전이 | `sourceDocumentTypeCode` |
|:-:|---|
| L1 대기→활성(첫 실적) | **`PRODUCTION_RESULT`** |
| L2 대기→폐번(마감) | **`WORK_ORDER_CLOSING`** |

### 2-3. `status_code` — **D1 에 얹지 않는다.** 상수다

- `plan.md` §0 #10 이 이미 갈랐다: ⌜`x-no-code-key` 16자리 `status_code` NOT NULL 은 **해제(nullable)** … ⚠ **계약이 응답에 `required` 로 적은 자리에는 안 선다**(널이면 실을 값이 없다) — 그 자리는 **상수**(I-3 재수립 R-9)⌝.

### 2-4. ⚠ I-6 PR ⑥ 과의 조율 — 같은 함수 두 자리

`:close`(I-6 PR ⑥, 병합 전)의 누적 양품과 I-7 이 정하는 **정정 누계 규칙**(§5-3)이 **같은 정의**여야 한다(계약 ⌜조회와 마감이 다른 값을 내면 안 된다⌝). 실측상 오늘 `work-order-query.service.ts` 의 집계 **세 자리**(`:111` 요약 · `:123` 목록 · `:193` 상세)가 **전 행을 그냥 더한다**.
⇒ I-7 PR ② 가 그 세 자리에 「정정된 원본을 뺀다」를 넣고, I-6 PR ⑥ 이 `:close` 에서 **같은 함수**를 부른다. 두 PR 이 겹치지 않게 **I-7 은 I-6 이 전건 병합된 뒤 시작한다**(`plan.md` §1 41행의 「선행 I-6」 그대로).

### 4-1. 한 트랜잭션 순서

### 4-2. 채번 — `$transaction` **밖**

```ts
const productionResultNo = await this.numbering.next('PRODUCTION_RESULT', null, periodDate);
```
- **규칙이 등재돼 있다**: `PR-{YYMMDD}-{SEQ4}` · `DAILY` · `plant_id NULL`(psql 실측). ⇒ `DEFAULT_PREFIX` 에 손대지 않는다(`numbering.service.ts:9-21` diff 0).
- **`plantId` 는 `null` 을 넘긴다.** 규칙이 전역본 하나뿐이고 `rule()` 이 `OR: [{plant_id}, {plant_id: null}]` 로 찾는다(`numbering.service.ts:89-93`). ⭐ **공장을 도출하지 않는다** — `production_result` 에 `plant_id` 칸이 없고, `work_order` 에도 없어 도출하려면 `production_plan → production_order.plant_id` 를 두 번 조인해야 한다(I-6 R-7). 선례가 정확히 이 모양이다: `purchase-order.service.ts:288-297` ⌜`approval_request` 에 공장 축이 없어 공장 지정 규칙을 찾지 않는다⌝. §2 2단계 **기준 5**(개념 수).
- **`periodDate` = `occurredAt` 의 UTC 날짜**(`occurredAt.toISOString().slice(0,10)`). ⛔ 서버가 「오늘」로 다시 잡지 않는다 — `numbering.service.ts` 의 `@param periodDate` 주석이 ⌜호출자가 이미 가진 날짜를 그대로 준다 … 공유계약 C-8 과 같은 이유⌝ 라 적었고, `occurredAt` 은 계약 required 라 언제나 있다. 오프라인 큐가 하루 뒤 재전송해도 **같은 날 번호**를 받는다.
- ⚠ **하노이(UTC+7) 00:00–07:00 의 실적은 «전날» 번호를 받는다** — `purchase-order.service.ts:290-292` 가 AP 번호에 대해 이미 적어 둔 것과 같은 자리다. `production_result` 는 `business_date` 를 안 싣는 표라 C-8 위반이 아니다. → §9-3 ⓔ
- ⛔ 실패 시 **결번**이 남는다 — 허용한다(I-2 R-2 · `plan.md` §3 채번 칸).

### 4-3. `worker_id` — `X-Worker-No` 가 유일한 원천

**계약 문자**(`components.parameters.WorkerNo`): `required: true` · ⌜없으면 **서버가 거부한다**. 값은 작업자 사번(전역 유일) … 원천 컬럼은 `mdm.worker.worker_no`⌝.
**화면**(`P-02-04` §4): ⌜작업자 — ⛔ 화면이 보내지 않는다 — **서버 파생**. 귀속 헤더 `X-Worker-No`(사번)에서 서버가 푼다(D-5). ⛔ 작업자를 고르는 칸을 두지 않는다(사용자 확정 2026-08-18)⌝.
**물리**: `worker_id bigint NOT NULL REFERENCES mdm.worker`.

⇒ **§2 0단계에서 닫힌다** — 세 자료가 같은 말을 한다.

| 갈래 | 결정 |
|---|---|
| 헤더 없음 | **400 `REQUIRED`**(field=`X-Worker-No`) — 서비스가 손으로 본다(가드가 헤더를 안 본다 · §1-1) |
| 헤더 값이 `mdm.worker.worker_no` 에 없음 | **400 `INVALID`**(field=`X-Worker-No`) |
| 그 worker 가 비활성(`is_active=false`) | 막지 않는다 — 계약이 안 적었고 `is_active` 는 마스터 운영 축이다(기준 2 를 여기까지 늘리지 않는다). → §9-3 ⓕ |
| ⛔ `mdm.worker.app_user_id` 로 세션 사용자에서 «도출» | **하지 않는다** — 칸은 실재하지만(`schema.prisma:2332`) 계약이 헤더를 required 로 못박았고, 도출은 §2 2단계 **기준 4**(값을 조용히 도출하지 않는 쪽)가 금한다 |

⚠ **`plan.md` §5 규칙 9 와 어긋나는 «예외»다.** 규칙 9 는 ⌜`X-Worker-No` 41건은 「누가 어느 단말에서」 **덧붙임**. 헤더가 없어도 400 을 내지 않는다(관리웹이 헤더 없이 부르는 것이 정상)⌝ 인데, 이 오퍼레이션은 헤더가 **덧붙임이 아니라 유일한 주체 원천**이고 부르는 화면 넷(`P-02-03`·`P-02-04`·`P-02-12`·`P-04-03` · `derived-permissions.ts:232`)이 **전부 POP 단말**이다. 규칙 9 의 근거(관리웹)가 서지 않는다. ⇒ 규칙 9 에 **각주 한 줄**을 단다(§11 #8). 실제로 계약이 `:correct`·`:request-approval` 에서 헤더를 «걷어낸» 것이 이 가름의 증거다 — 관리웹이 부르는 둘만 걷혔다.
**주체는 여전히 계정 세션이다**(`created_by` = `currentSession(request).userId` · `notice.controller.ts:150` `actorOf` 선례). `worker_id` 는 «귀속»이고 `created_by` 는 «주체»다 — 두 칸이 다르다.

### 4-4. `idempotency_key` — 헤더 값 그대로

`production_result.idempotency_key varchar(150) NOT NULL UNIQUE` 는 `app.idempotency_record`(`runIdempotent`)와 **이중**이다. 실측:

- 도메인 표에 `idempotency_key` 를 든 표는 넷뿐이고(`inventory_transaction`(+`business_date` 복합) · `material_consumption`:2635 · `production_result`:2830 · `work_session`:2998 · `inspection_result`:3384) **구현된 것은 `inventory_transaction` 하나**다. 그것은 «파생 키»(`issue-posting.ts:162` `${SOURCE_DOCUMENT_TYPE}:${goodsIssueNo}`)를 쓴다.
- ⇒ **도메인 표에 헤더 값을 그대로 담는 선례는 아직 0건**이고, `production_result` 가 첫 자리다.
- **판정**: 계약 `IdempotencyKey` 의 x-internal-note 가 ⌜**이 도메인의 유일 제약은 전역 UNIQUE(idempotency_key)** 라 `business_date` 를 함께 쓰지 않는다⌝ 라 «이 칸»을 직접 가리킨다. 화면도 같다 — `P-02-04` §5-3 ⌜`production_result` 에 `idempotency_key varchar(150) NOT NULL UNIQUE` 가 있다. 이는 **클라이언트가 생성해 outbox 에 담고 재전송 시 서버가 중복을 흡수**하는 설계다⌝. ⇒ **헤더 값을 그대로 넣는다**(§2 0단계).
- 이중이어도 **부딪히지 않는다** — `IdempotencyService.run` 이 `idempotency_record` 를 먼저 보고 재전송을 흡수하므로 도메인 UNIQUE 까지 오지 않는다. 그 UNIQUE 는 **둘째 그물**이다(멱등 기록이 만료(72h)된 뒤의 재전송을 막는다).
- ⚠ `:correct` 가 만드는 행은 **자기 헤더 값**을 넣는다(원본과 다른 키다).

### 4-5. 다섯 수량 · 배분 검증

| 검사 | 응답 | 근거 |
|---|---|---|
| 어느 하나라도 음수 | 400 `INVALID`(field=`goodQty` 등) | `app.qty_t CHECK (>= 0)` 를 앞당겨 막는다(도메인 CHECK 는 500 으로 샌다) |
| 다섯 합 = 0(전부 생략 포함) | 400 `INVALID` | `ck_production_result_nonzero` · `P-02-04` §6 |
| 생략된 칸 | **0**(DB 기본값) | `P-02-04` §4 ⌜`defect_qty`·`hold_qty`·`scrap_qty`·`rework_qty` 는 이 화면에서 입력받지 않는다 … 기본값 0 으로 저장⌝ |
| `allocatedQty ≤ 0` | 400 `INVALID` | `CHECK (allocated_qty > 0)` |
| 같은 `lotId` 두 번 | 400 `INVALID`(`UNIQUE_VIOLATION` 이 아니다 — 요청 안의 중복은 입력 오류다) | `uq_production_result_lot` |
| `lotId` 가 이 W/O 의 슬롯이 아님 | 400 `INVALID` | `lot.source_type_code='WORK_ORDER' AND source_id=workOrderId` |

| **`Σ allocatedQty` = `goodQty` 인가** | ⛔ **검사하지 않는다** | 계약이 안 적었다. 화면은 한 LOT 만 보낸다(`P-02-04` §4 ⌜대상 LOT — 진입 시 선택⌝ 단수). §2 2단계 기준 2 를 계약 문자 위로 올리지 않는다 — 검사를 나중에 «거는» 것이 «푸는» 것보다 쉽다고 보기 어렵고(화면이 이미 다르게 보낼 수 있다), 무엇보다 **무엇과 비교할지 계약이 침묵**한다(`goodQty`? 다섯 합?). → §9-3 ⓖ |
| 잔여수량 초과 | ⛔ **막지 않는다** | `P-02-04` §6 ⌜**초과 생산은 허용**(✓확정 QA #27) → 차단하지 말고 확인 후 진행⌝ · `P-02-06` §5-4 R27 |

### 4-6. If-Match — 받되 **대조할 것이 없다**

계약 `IfMatchVersionOptional`: ⌜오프라인에서도 쓰는 오퍼레이션에서는 선택이다 — 없으면 낙관적 잠금 검사를 건너뛴다⌝.
형제 오퍼레이션 `POST /production/work-sessions` 의 description 이 «무엇의» 버전인지를 스스로 답했다(실측): ⌜**If-Match 는 선택이다 — 신규 생성이라 대조할 `version_no` 가 아직 없다**(공유계약 C-9 의 큐 조항과는 «무관»하다)⌝.

⇒ **판정**: 실적 등록은 «태어나는» 행이라 대조 대상이 없다. 그러나 이 요청이 잠그는 유일한 행은 `work_order` 이고 ⑥에서 이미 `FOR UPDATE` 로 잡는다 ⇒ **토큰이 오면 `work_order.version_no` 와 대조**한다(`assertVersion(locked, version)` — I-6 이 이미 만든 함수 재사용 · `work-order-write.service.ts:81-85`). 없으면 건너뛴다.
⚠ 이 선택은 «호환 완화 방향»이다 — 대조를 안 하다가 하는 것은 깨는 변경이므로 **처음부터 대조한다**(기준 2). 400 이 아니라 409 `VERSION_CONFLICT` 다.
⛔ `runVersioned` 를 쓰지 않는다 — `master-write.ts:48-51` 이 `undefined` 면 `throw new Error` 라 500 이 된다(I-6 §8-3 가 같은 이유로 배제했다).

## 5. `POST …/{id}:correct` — 정정

### 5-1. 한 트랜잭션 순서

```
[ 밖 ]  ① 가드 · 403 · ⛔ If-Match 없음 · ⛔ X-Worker-No 없음
        ② 채번  productionResultNo (원본과 같은 규칙 · periodDate = 원본 occurred_at 의 날짜)
[ $transaction ]
        ③ 원본 SELECT … FOR UPDATE                      (없으면 404)
        ④ 원본이 이미 «정정본»이면?  → §5-4
        ⑤ 정정 후 다섯 수량 = 본문에 있으면 그 값, 없으면 «원본 값 승계»
        ⑥ 합 0·음수 손검사                               (400 INVALID)
        ⑦ 등급 판정 — 다섯 중 하나라도 원본과 다르면 A급  (§5-5)
        ⑧ A급이면 승인 게이트                            (400 APPROVAL_REQUIRED / APPROVAL_IN_PROGRESS)
        ⑨ result_sequence = MAX+1  (원본의 work_order 아래)
        ⑩ INSERT production_result  (corrects_production_result_id = 원본 · 나머지 칸은 원본 승계)
[ 커밋 ]  201 ProductionResult   ⛔ ETag 없음 · ⛔ 원본을 UPDATE 하지 않는다 · ⛔ 배분을 안 만든다
```

⛔ **원본의 `version_no` 를 올리지 않는다** — 계약 ⌜원본을 고치지 않는다(G-18)⌝ · x-internal-note ⌜If-Match 를 받지 않는다 — 원본 실적을 고치지 않으므로 **잠글 것이 없다**⌝.
⛔ **`work_order` 를 잠그지 않는다** — ③이 원본을 잠그고 ⑨의 `MAX+1` 은 같은 W/O 의 다른 실적과 경합할 수 있다. ⇒ ③ 뒤에 **`lockWorkOrder(tx, 원본.work_order_id)` 도 부른다**(잠금 순서: 원본 → W/O 는 두 자물쇠라 교착 위험 → **W/O 를 먼저 잠근다**. I-4 R-1 「잠금 오름차순」의 이 도메인판: `work_order` → `production_result`). ⇒ ③을 **`lockWorkOrder` → 원본 `FOR UPDATE`** 로 뒤집는다.

### 5-2. 새 행이 받는 값

| 칸 | 값 | 근거 |
|---|---|---|
| `corrects_production_result_id` | **원본 id** | 계약 |
| `work_order_id`·`work_session_id`·`uom_id`·`result_source_code`·`occurred_at`·`worker_id`·`equipment_id`·`mold_id`·`shift_id`·`terminal_id` | **원본 승계** | 본문이 주지 않는데 NOT NULL 이 넷이다. 정정은 «같은 사건»의 보정이라 사건 칸이 바뀔 이유가 없다 |
| 다섯 수량 | 본문 값, 없는 칸은 **원본 값** | §5-3 |
| `result_sequence` | `MAX+1` | `uq_production_result_seq` |
| `production_result_no` | 새 번호 | 새 전표다 |
| `status_code` | `'CONFIRMED'`(§2-3) | |
| **`correct_reason_code`** | 본문 `reasonCode` | ⭐ **D2** |
| `remarks` | 본문 **`note`** | ⚠ 계약이 이름을 달리 적었다(`note` ↔ `remarks`) → §9-3 ⓗ |
| `idempotency_key` | **이 요청의 헤더 값** | §4-4 |
| `created_by` | 세션 사용자 | x-internal-note ⌜정정한 사람은 인증 주체로 남는다⌝ |
| `lotAllocations` | ⛔ **만들지 않는다** | `ProductionResultCorrect` 에 칸이 없다. 원본 배분도 «복사하지 않는다» — 복사하면 `:complete` 의 누적 양품이 두 배가 된다(§5-6 · 문의 044) |

⛔ **L1 을 부르지 않는다** — 배분이 없으므로 옮길 슬롯이 없다. `moveWithin` 을 빈 배열로 부르지도 않는다(사건이 아니다).

### 5-3. ⭐ 정정본은 «대체값»이다 — 그리고 누계에서 원본을 뺀다

**물음**: 정정 행의 다섯 수량은 «정정 후 값»인가 «차이값(상쇄)»인가.

**계약이 둘 다 적어 두었다** — 그래서 §2 절차를 탄다.
- `WorkOrderProgress` description: ⌜쪽과 무관하며 **정정(상쇄) 실적이 반영된 값**이다⌝ · `goodQty`: ⌜양품 합계 — **`production_result.good_qty` 의 합**⌝ ⇒ 「전 행을 더하면 정정이 반영된다」로 읽힌다(= 차이값).
- `POST` 실적의 x-internal-note: ⌜A급(**상쇄 트랜잭션** + ERP 역분개성 재송신)⌝.
- `W-02-05` §4-D: ⌜**정정 수량 5칸** — ⭐ 이 다섯 칸이 **등급 판정의 입력**이다 — 서버가 본다⌝ ⇒ 서버가 「수량이 **바뀌는가**」를 보려면 **원본과 대조**해야 하고, 그러려면 본문 값이 «정정 후 값»이어야 한다(차이값이면 「0이 아닌가」를 볼 뿐 원본이 필요 없다).

**⛔ 그리고 물리가 한쪽을 «불가능»으로 만든다**: `app.qty_t CHECK (VALUE >= 0)`(baseline:59-60) — 다섯 수량 칸에 **음수를 넣을 수 없다.** ⇒ 「양품 150 → 100」을 −50 행으로 담는 길이 **물리적으로 없다.**
(대안: `app.signed_qty_t` 로 도메인을 바꾸는 마이그 — ⛔ 하지 않는다. 원장 판별자를 늘리지 않는 것과 같은 이유로 §2 2단계 **기준 1·3**을 정면으로 어기고, 다섯 칸의 도메인을 바꾸면 `:close`·달성률·검사·ERP 가 전부 음수를 다뤄야 한다.)

**판정 — §2 1단계 «본길»**(모든 정정이 누계를 바꾼다) → 계약이 침묵하지 않고 **서로 어긋난다** → 0단계 선례로 닫고 문의를 낸다:

> `ProductionResult.statusCode` 의 `x-no-code-key` 전문 — ⌜정정은 상태를 바꾸는 것이 아니라 «새 행»으로 남긴다(`corrects…Id` 가 원본을 가리킨다). **원본인지 정정본인지는 그 칼럼으로 판정한다**(A-21 · L-2-1 · **2026-09-02 판정**)⌝

⇒ **결정**
1. 정정 본문의 다섯 수량은 **정정 후 값(대체값)**이다.
2. 누계는 **정정된 원본을 뺀 합**이다:
```sql
SUM(...) FROM production.production_result pr
 WHERE pr.work_order_id = ?
   AND NOT EXISTS (SELECT 1 FROM production.production_result c
                    WHERE c.corrects_production_result_id = pr.production_result_id)
```
Prisma 로는 `where: { corrected_by_production_results: { none: {} } }`(관계 이름 실측 — `schema.prisma:2839`).
3. **정정의 정정(체인)도 이 한 줄로 닫힌다** — 잎(아무도 안 가리키는 행)만 세어진다.
4. 「상쇄」는 **회계적 결과**로 성립한다 — 순효과가 정정 후 값이고, ERP 재송신이 상쇄 전표로 나간다(`W-02-05` §5-4 규칙 3).

⇒ **`work-order-query.service.ts` 세 자리(`:111`·`:123`·`:193`)에 이 `where` 를 넣는다.** 정의가 갈리지 않게 **한 상수**(`ACTIVE_RESULT_WHERE`)로 뽑아 `src/production/work-order/work-order-progress.ts` 에 둔다 — `:close`(I-6 PR ⑥)도 그것을 부른다(§2-4).
→ **문의 042**(§9-1 #2).

### 5-4. 정정의 정정 — 허용한다

계약이 금하지 않았고 `corrects_production_result_id` 가 자기참조라 물리도 막지 않는다. §2 1단계 가장자리 → 2단계 **기준 3**(스키마를 안 늘리는 쪽 — 체인을 막으려면 「정정본인가」 축을 하나 더 봐야 한다) + §5-3 의 잎 규칙이 체인을 이미 옳게 센다. ⇒ **허용**. 단위 테스트로 못박는다(⌜정정의 정정도 잎 하나만 세어진다⌝).

### 5-5. A급 판정과 승인 게이트

**판정식**(잠정 · `plan-integration.md` 271행 · `plan-api.md` S16 초안과 같다):
```
A급  ⇔  { goodQty, defectQty, holdQty, scrapQty, reworkQty } 중
        본문이 «준» 칸 하나라도 원본 값과 «다르다»
B급  ⇔  다섯 칸이 전부 원본과 같다(= 사유·비고만 고친다)
```
- 근거: `W-02-05` §5-8 등급표 — A급 = ⌜수량 조정 · 양품↔불량 재분류 · …⌝ / B급 = ⌜불량코드 · 처분구분 · 비가동 사유 · 작업자/설비 귀속 정정⌝. **본문이 담는 것은 사유·비고·수량 5칸뿐**이므로(계약 실측) 서버가 볼 수 있는 A/B 의 경계는 **수량이 바뀌는가** 하나다. `plan-integration.md` 가 ⌜계약이 「수불에 영향」이라 적은 것의 가장 좁은 해석이고, 넓히는 것은 호환 완화다⌝ 로 이미 같은 결론을 냈다.
- ⚠ B급 예시(불량코드·처분구분·귀속)를 **담을 칸이 본문에 없다** ⇒ 실무상 B급 정정은 「사유만 바꾸는 정정」뿐이다. `W-02-05` §5-8 이 스스로 ⌜B급 정정 항목의 전수 목록은 아직 확정되지 않았다 … 📄 기록만⌝ 이라 적었다. → §9-3 ⓘ

**승인 게이트 — `:correct` 가 진다**(계약 400 + `W-02-05` §5-8 흐름도 실측):
```
[ 정정 저장 ] POST …:correct
   ├─ 201  B급이다 → 정정 실적이 덧붙는다. 끝
   └─ 400  A급인데 승인된 요청이 없다 → 「승인 상신」 대화상자
```
⛔ **`ApprovalService.assertApproved` 를 그대로 쓸 수 없다** — 그 함수는 ⌜요청이 **0건이면 통과**한다⌝(`approval.service.ts:141-` · I-4 R-4 문의 030). A급인데 상신을 한 번도 안 했으면 **통과해 버린다.** 계약은 그 자리를 400 으로 못박았다.
⇒ **도메인 안에 짧은 판정을 둔다**(코어를 고치지 않는다 — `assertApproved` 는 「승인을 탔으면 확인」이고 이쪽은 「승인이 **필수**」라 뜻이 반대다):
```ts
const requests = await tx.approval_request.findMany({
  where: { target_type_code: 'PRODUCTION_RESULT', target_id: 원본id,
           approval_type_code: 'PRODUCTION_RESULT_CORRECT' },
  select: { status_code: true },
});
if (requests.some(r => r.status_code === 'APPROVED')) return;                 // 통과
if (requests.some(r => r.status_code === 'PENDING'))  throw 400 APPROVAL_IN_PROGRESS;
throw 400 APPROVAL_REQUIRED;                                                  // 0건·반려 포함
```
- **다형 축**이다 — `plan.md` §5 #12 ⌜`PRODUCTION_RESULT_CORRECT` 는 FK 를 쓰지 않는다⌝. `production_result` 에 `approval_request_id` 칸이 없다는 실측과 정확히 맞는다.
- 조회 인덱스는 I-1 A6 이 깐 `ix_approval_request_target` 이다.
- ⚠ **승인 한 건이 정정 몇 건을 여는가**를 정하는 축이 데이터에 없다 — 승인을 한 번 받으면 그 뒤 A급 정정이 몇 건이든 통과한다. 계약이 안 적었고 「소진」을 세려면 승인↔정정 연결 칸이 필요하다(없다). **계약 문자 그대로 두고 문의**. → **041** ⓑ

### 5-6. 배분·LOT 누계는 정정을 못 따라간다

`:complete` 의 누적 양품은 `Σ production_result_lot_allocation.allocated_qty` 인데(§3-3), `:correct` 는 배분을 만들지도 고치지도 않는다(계약 스키마에 칸이 없다). ⇒ **양품을 정정해도 LOT 누계는 그대로다.** W/O 누계(§5-3)만 따라간다.
⛔ 배분을 «서버가 알아서» 비례 조정하지 않는다 — §2 2단계 **기준 4**(조용히 도출하지 않는 쪽). 계약이 준 칸이 없다. → **문의 044**.

### 8-4. `X-Worker-No` 2 · 404 · 400 vs 409 · 409 봉투
- `X-Worker-No`: `POST` 실적은 **필수**(§4-3) · `:complete` 는 **받되 담을 칸이 없다** — `lot` 에도 `work_order` 에도 작업자 칸이 없다. ⇒ **읽지 않고 버린다.** ⚠ 계약은 `required: true` 다. 헤더가 없어도 400 을 내는가? → **낸다**(계약 문자 그대로 · 기준 2). 저장은 안 하지만 「거부한다」는 계약 문장은 저장 여부와 무관하다. → §9-3 ⓜ
- **404**: 계약 선언 4건(단건 GET·`:correct`·`:request-approval`·`:complete`). `POST` 실적은 **404 미선언**인데 `workOrderId` 가 없으면 **404 를 낸다**(I-2·I-3·I-4·I-6 이 같은 자리에서 그렇게 했다 · 「알려둘 것」).
- **400 vs 409**: 409 는 **둘뿐** — If-Match 저장 충돌(`VERSION_CONFLICT`) · 멱등 재전송 충돌(`IdempotencyService`). 업무 거부는 전부 400(I-5 R-9 · I-6 §8-4).
- **409 봉투**: 생산 4건은 `ProductionConflictResponse`(`code` required) → `ConflictException(cause, msg, { code: 'VERSION_CONFLICT' })`(I-6 R-8 이 이미 넣었다 · `conflict.exception.ts:36` 실측). ⚠ **`:complete` 만 `ConflictResponse`**(01 파일) → `extra` 없이 던진다 — 봉투가 오늘과 글자 그대로 같다.
- `@Contract` 데코레이터 **7건 전건**.
