## 3. 툴 증분 — 입력 사실과 현재 누계를 섞지 않는다

### 3-1. 값·참조·시간 검증

O3는 mold/work_order 실재를 tx에서 검사하고 worker는 원문 X-Worker-No로 `mdm.worker.worker_no`를 조회해 recorded_by에 저장한다. 세션 계정을 worker로 추정0·6자리 정규식 추가0. 없는 외래 ID는400 INVALID, 공백 필수 사번은400 REQUIRED. 폐기 툴은 화면의 저장 거부 선례로422 STATE_LOCKED. 비활성은 마스터 선택 숨김과 같은 축이지 폐기와 같지 않으므로 is_active=false만으로 새 업무 거부를 만들지 않는다.

workOrder가 존재한다는 것과 특정 툴의 배정이 유효하다는 것은 다르다. 고정 Create는 둘의 FK를 받지만 작업지시 상태/배정/수량상한을 지정하지 않는다. planned_mold_id 일치만 강제하면 교체·공용 툴을 막을 수 있어 R2는존재검사만유지한다. 공장 일치·작업자권한·단말공정 귀속을 새 인증 모델로 도출하지 않는다(054/091 인계). 누계/생산수량/작업지시 상태를 작업지시에서 자동 갱신하지 않는다.

shotCount는 1..9007199254740991 안전 정수, 현재 누계와 합산결과도 안전 비음수 정수 범위여야 한다. bigint로 더한 뒤 Number로 내기 전 검사하며 DB bigint의 넓은 범위가 JSON number 정확성을 보증하지 않는다. 요청 초과는400 RANGE, 저장된 현재 누계가 이미 API 범위 밖이면500 INTERNAL_ERROR(입력 탓으로 바꾸지 않음). 누계가 guaranteedShotCount를 넘거나 guaranteed가 null인 것은 화면 경고/미설정 표시이고 저장 차단 사유가 아니다.

CONVERTED는 conversionBaseQty/Ratio 모두 양수·유한·numeric(20,6)에 **무손실 저장** 가능해야 한다. 둘 중 없는 값은400 REQUIRED/PAIR, 6자리 초과 소수 또는 정수14자리 초과는400 RANGE. DIRECT는 둘 다 생략/null 정상; 숫자를 명시한 DIRECT는 서로 다른 사실축이므로 버리지 않고400 INVALID로거부한다(R1). ratio>1은 화면 경고일 뿐 서버 거부0. cavity_count를 다시 곱하거나 나누지 않는다.

**R1 — 입력 권한이 최초 근거다(0단계).** 고정 P-05-01 §5-2는 정하는 것은 화면의 증분, 반영하는 것은 서버의 누적이라고 명시하고 Create는 shotCount를 required로 받는다. 서버는 제출된 양의 안전 정수와 환산 근거를 보존하며 **곱으로 재계산·치환·엄격 일치 거부0**이다. P-05-01/W-05-01의 base×ratio 산식과 달리 반올림 규칙 자체는 미정이다. 실제 client `tool-usage/conversion.ts`의 Math.round는 임시 소비자 정책이지 승인된 서버 산식이 아니다. base1×ratio0.6·제출shot1도1과근거를그대로남긴다. 현재 `app.operation_policy` 재조회·cavity 재곱으로 오프라인 입력을 바꾸지 않는다. `CONVERSION_SHOT_POLICY='PRESERVE_SUBMITTED'`, 문의119에 입력권한과 미정 반올림을 분리해 남긴다. 종전 ‘최초④로 보존을 선택’ 문구는 철회한다.

occurredAt은 단말의 순간을 저장하고 과거/미래를 현재 서버시각으로 clamp하지 않는다. 기간 GET은 I-30 실제 calendar helper를 사용하되 server TZ에 기대지 않는다. 저장·조회는 **병합된 I-32 계획 R2/R14**의 timestamptz(6) µs 보존 규칙에 맞춘다. 6자리 뒤 전부0이면 같은 순간으로 허용, 비영소수는400 RANGE. 입력 정수초 epoch와 µs를 별도로 해석해 PG지원 UTC문자열로 바인딩한다. JS Date로 원문 소수를 먼저 절삭하지 않는다. ISO year0000은PG1BC표기로, +23:59같은큰offset은정확한UTC로정규화한다. 윤초/소수윤초 및 UTC응답연도0000..9999밖은400 RANGE, 과거저장값표현불가는500이다(109).

모든 조회·잠금·RETURNING·최종응답은 `((extract(epoch FROM ts)*1000000)::bigint)::text`로 읽고 BigInt 음수floor/나머지를 보존해 UTC ISO 소수6자리로 만든다. 관측 observedAt·서버 cumulativeAsOf/clearedAt에도 같은 정확한 projection을 적용한다. 원래 offset 모양이 아니라 동일순간이 정본이다. root가 I32 R15로 `src/maintenance/maintenance-instant.ts`의 `parseMaintenanceInstant`/`maintenanceInstantFromEpoch`·epochMicroseconds/utcIso/sqlTimestamp를 확정했다. P0t 예산150·구현 중/미병합이며 실제 병합 확인 전 import0·복제0이다. 달력일과 순간 helper는 다른 책임이다.

### 3-2. 동일 tx와 I-31 리셋 경합

O3 실행 순서는 **공통 인증/계약/헤더 → actor+rawworker 포함 지문 → IdempotencyService.run 재생 판단 → tx 안 worker/FK확인 → mold FOR NO KEY UPDATE → 폐기/범위 확인 → tool_usage INSERT → mold current_shot_count 가산·version_no+1·updated_by → 같은 시점 response → 멱등 COMPLETED**다(R2). 감사 actor와 작업자 귀속을 구분한다. 계수 UPDATE는 `current_shot_count = current_shot_count + delta`를 사용하며 읽은 누계로 무잠금 덮어쓰기0. updated_at trigger가 만든 시각을 반환해 cumulativeAsOf로 쓴다.

**root R2 잠금 근거와 실제 회귀 원문**:

root는 work-session.service.ts54,69~75(W/O FOR UPDATE→moldFKINSERT),work-order-write.service.ts174,189,212(W/O잠금→planned_mold FKUPDATE)실물을직접읽었다. O3의 mold FOR UPDATE→tool_usage의W/O FK는역순대기가가능하다. NO KEY UPDATE는비키누계/version writer끼리직렬화하면서production FK의KEY SHARE를허용한다([PostgreSQL16공식Table13.3](https://www.postgresql.org/docs/16/explicit-locking.html#LOCKING-ROWS)). TOOL_USAGE_REFERENCE_LOCK_COMPATIBILITY 이름과실제2connection/barrier회귀2건으로검증한다. 코드분석이지이미재현한PASS가아니다. work_order선잠금추가대안은비선택(강도완화만으로고리를끊고새검증축없음).

I-31 초안의 최초 §6/§8/인계·실제 reset 소비자를 읽은 사실과 그 뒤의 root R결정을 구분한다. **현재 I31 R2는 resetCounter=true를422 INVALID/field resetCounter로 전건쓰기0 거부**하며 nonreset 미마감 정상경로를 유지한다(114). R13에 따라 지금은 두증분·MDM CAS·reset거부의 누계/이력/version 무변경을 검증한다. 실제 reset 성공이 재개된 뒤에만 아래 교차 성공 회귀를 활성화한다. 고정계약의 툴 ETag 원천과 현재 client가 토큰을 보낸다는 사실은 성공 구현의 증거가 아니다.
