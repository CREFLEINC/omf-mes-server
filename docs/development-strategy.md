# MES 개발 전략 — 시스템 분할과 구현 순서

> 작성일: 2026-08-04
> 배경: 스키마(128개 테이블) 설계는 완료된 상태에서, 구현을 어떤 단위로 쪼개어 어떤 순서로 진행할지에 대한 전략 기록.
> 갱신(2026-08-26): 데이터 모델 v4 적용으로 논리 172개(물리 174개, 11 스키마) 테이블로 늘었다.
> 아래 "128개"는 2026-08-04 시점 스냅샷이며 전략 자체는 유효하다. 상세: [`docs/data-model/`](data-model/).

## 현재 상태 (2026-08-04 기준)

- Prisma 스키마 128개 모델 설계 완료 — "무엇을 만들지"는 스키마에 이미 있다.
- 구현 완료/진행: `auth`, `access`, `master-data`(거의 전 영역), `pop`(작업시작·생산실적 시작).
- 남은 것은 범위 정의가 아니라 **구현 순서의 전략**이다.

## 원칙 1. 레이어(수평)가 아니라 전표 흐름(수직)으로 자른다

"재고 모듈 전체 → 품질 모듈 전체" 식으로 도메인 하나를 통째로 끝내는 방식은 MES에서 실패하기 쉽다. 어떤 도메인도 혼자서는 동작을 검증할 수 없기 때문이다. 재고는 입고가 있어야 쌓이고, 입고는 발주가 있어야 생긴다.

대신 **자재가 공장을 통과하는 물리적 흐름 하나를 얇게 끝까지 뚫는 것**(tracer bullet)을 첫 목표로 잡는다:

```
purchase_order → goods_receipt → lot 생성 → material_issue →
work_order → production_result → (완제품 lot) → inventory_balance 반영
```

이 한 줄이 돌면 시스템의 뼈대 — 전표 상태전이, 재고 원장, lot 생성/소비, 채번 — 이 전부 한 번씩 검증된다. 각 전표는 처음엔 최소 필드·해피패스만으로 충분하다. ASN, putaway, picking, 검사 같은 가지들은 이 줄기가 선 뒤에 붙이는 게 훨씬 쉽다.

## 원칙 2. "단단함"이 필요한 코어는 소수다 — 거기에 설계·테스트를 집중한다

테이블(v4 기준 172개)이 전부 같은 난이도가 아니다. 대부분은 코어를 둘러싼 CRUD이고, 시스템의 견고함은 아래 4~5개 코어가 결정한다.

### 재고 원장 (posting engine)

`inventory_transaction` / `inventory_balance`. 입고·출고·생산실적·조정·이동 **모든 재고 변동이 단 하나의 posting 서비스를 통과**하게 만든다.

- 불변식: `balance = 트랜잭션의 합`
- 이게 여러 코드 경로로 흩어지는 순간 재고가 안 맞기 시작하는데 원인을 못 찾게 된다.
- `inventory_reservation` 차감도 여기서만 일어난다.

### Lot 계보

`lot`, `lot_relation`, `production_result_lot_allocation`. 소비 lot → 생산 lot 연결이 **실적 저장과 같은 트랜잭션 안에서 원자적으로** 기록되어야 추적성이 성립한다.

### 전표 상태기계

모든 전표(PO, GR, work_order, shipment…)의 상태전이를 표로 먼저 정의하고, 전이 검증을 공통 패턴으로 강제한다. "DRAFT인 채로 입고 처리됨" 같은 구멍이 MES 버그의 주범이다.

### business_date / shift 판정

자정을 넘는 교대(`shift.crosses_midnight`) 때문에 타임존 캐스팅으로는 구할 수 없다(CLAUDE.md 참고). 유틸 함수 하나로 격리하고 자정 교차 케이스를 유닛 테스트로 못 박는다. 각 서비스가 제각기 계산하면 반드시 어긋난다.

```
실적 timestamptz → plant.timezone_code 로 로컬 시각 변환
→ 그 로컬 시각이 속한 shift 판정 (start_time/end_time/crosses_midnight)
→ 그 shift 가 시작된 로컬 날짜 = business_date
```

### 정정/취소 경로

현장은 반드시 잘못 입력한다. 각 전표마다 "취소·역분개(reversal)를 어떻게 하나"를 해피패스와 **같이** 설계한다. 원장에 역방향 트랜잭션을 쌓는 방식(수정 불가, append-only)이 안전하다. 나중에 붙이려면 전 전표를 다시 뜯게 된다.

### 테스트 예산 배분

코어들은 유닛 테스트를 두껍게, 나머지 CRUD는 e2e 한두 개로 가볍게 — 같은 비율로 배분한다.

## 원칙 3. "빠짐없이"는 머리가 아니라 표로 보장한다

시스템 전체를 인지적으로 다 담을 수 없는 게 정상이다. 담으려 하지 말고 체크리스트를 외부화한다.

- **전표 × 상태 매트릭스**: 전표 종류를 행으로, `생성/승인/실행/부분완료/완료/취소/정정` 을 열로 놓고 각 칸을 "구현됨/불필요/미구현"으로 채운다. 이 표가 곧 진척표이자 누락 감지기다.
- **재고 변동 이벤트 목록**: 재고를 움직이는 모든 사건(입고, 불출, 실적, 불량 격리, 반품, 실사 조정, 이동, 외주 출고…)을 나열하고 각각이 posting 서비스에 어떤 트랜잭션 유형을 남기는지 1:1 매핑한다. **이 표에 없는 경로로 balance 가 바뀌면 안 된다.**
- 이 표들은 `docs/` 에 커밋해 유지한다 — 세션이 바뀌어도 "어디까지 왔고 뭐가 남았나"를 즉시 복원할 수 있다.

## 원칙 4. 개발 단위는 사람의 검토 대역폭이 정한다

에이전트(AI)가 개발을 수행하면 생산 속도가 검토 속도를 압도한다. 해법은 속도를 줄이는 게 아니라 **검증 지점을 앞당기고, 단위를 "리뷰 가능한 diff"로 강제**하는 것이다. 규칙 자체는 CLAUDE.md(개발 단위 규칙·코드 작성 규칙)에 있고, 여기에는 근거를 남긴다.

### 코드보다 계약을 먼저 리뷰한다

작업을 3단계로 나누고 단계 사이에서 멈춘다:

1. **계획/설계** — 상태전이표, 불변식, 처리 순서. 산문 반 페이지.
2. **계약** — 인터페이스 시그니처, DTO, 마이그레이션 SQL, 테스트 이름 목록.
3. **구현** — 계약을 채우는 코드.

800줄 구현을 읽는 것보다 30줄 계약을 읽는 게 더 정확한 검증이다. 1~2단계에서 잘못을 잡으면 3단계는 거의 기계적이지만, 3단계에서 처음 보면 설계 오류를 diff 속에서 발굴해야 한다.

### 리뷰 예산은 코드 종류별로 차등 배분한다

- **코어 로직** (posting engine, lot 계보, business_date, 상태기계): 한 줄씩 정독. 전용 PR, diff 200줄 이하.
- **CRUD/보일러플레이트**: 기존 모듈과 패턴이 같은지만 확인. 정독하지 않는다.
- **테스트 코드**: 실질적 리뷰 표면. 구현을 코드로 검증하는 대신 **테스트가 주장하는 행동 목록이 완전한지**를 검증한다. 테스트가 불변식을 못 박지 못하면 구현이 깔끔해도 반려.

### PR 은 "전표 체인의 한 마디" 단위로 자른다

M1 tracer bullet 도 한 PR 로 만들면 수천 줄이다. 자연스러운 절단면:

```
PR-1: 마이그레이션 + posting 서비스 인터페이스 + 테스트 스켈레톤
PR-2: posting 서비스 구현 + 유닛 테스트   (코어 — 정독 대상)
PR-3: goods_receipt 전표 + posting 연결 + e2e
PR-4: material_issue 전표 + e2e
...
```

각 PR 은 "머지해도 시스템이 깨지지 않는 최소 단위"이며 혼자 e2e 하나를 통과한다. 마이그레이션을 별도 선행 PR 로 두는 것은 forward-only 제약 때문에도 필요하다.

### 코드 규모도 검토 가능성에 맞춘다

- 주석은 코드에서 유추할 수 없는 도메인 정보·반직관적 선택의 이유에만 쓴다.
- 과설계 금지 — 사용처가 하나뿐인 추상화, 아직 없는 요구를 위한 레이어를 만들지 않는다. 두 번째 사용처가 생겼을 때 추상화한다.
- 함수 ~50줄, 파일 ~300줄은 분리를 검토할 신호. 판단 기준은 "리뷰어가 한 번에 읽고 이해할 수 있는가".

## 마일스톤 (현재 코드 기준)

| 단계 | 범위 | 비고 |
|---|---|---|
| **M1 — tracer bullet** | PO → GR → 불출 → 실적 → balance 한 줄 | posting 서비스와 lot 생성이 여기서 태어난다. pop 이 만드는 실적이 원장·lot 에 연결되는 것이 완성 조건 |
| **M2 — 실행 보강** | work_session, 자재 소비/loss/반납, handover | POP 시나리오가 현장에서 실제로 돌아가는 수준 |
| **M3 — 품질** | 검사 요청/결과, 불량, nonconformance → lot hold | 원장·출하와 연동 |
| **M4 — 출하** | SO → shipment → GI, lot allocation | |
| **M5 — 주변부** | 실사, ASN/putaway/picking 고도화, 외주, 승인 워크플로, 시리얼 | |

각 마일스톤의 완료 기준: **취소 경로를 포함한 전표 체인이 e2e 테스트로 통과.**
