## A. 먼저 — 저희 쪽 정정 3건

### A-1. `WORK_ORDER_STATUS` 7값을 저희가 근거 없이 만들어 뒀습니다

`#61` 에서 "확정된 적이 없으니 임의로 만들지 말아 달라"고 하신 그 그룹인데, 저희 시드에 이미 있었습니다.

```
prisma/seed.ts:410   WORK_ORDER_STATUS
  PLANNED · RELEASED · IN_PROGRESS · HOLD · COMPLETED · CLOSED · CANCELLED  (7값)
```

`342a414` 계약 7벌을 다시 전수 확인했고 말씀대로입니다 — 그룹명 `WORK_ORDER_STATUS` **0건**, 값 집합을 고정한 enum 도 **0건**입니다. (`RELEASED` 가 잡히길래 확인했더니 `quality-03품질.json › LotHoldEvent.eventTypeCode` 의 `HELD`/`RELEASED` 로, 보류 사건 코드였습니다.)

**저희가 만든 값이라 폐기하겠습니다.** 다만 `production.work_order.status_code`(`02:5614`)가 **NOT NULL** 이라 값 없이는 작업지시를 만들 수 없습니다 — D-1 에서 다시 여쭙습니다.

### A-2. 확인 이력을 담을 표가 이미 있습니다 — 알려드리지 않았습니다

`#63` 에서 `production_order.acknowledged_at`/`acknowledged_by`/`acknowledge_decision_code` 3칸을 요청하셨는데, 전용 표가 이미 있습니다.

```
02:5499   production.production_order_acknowledgement
  production_order_acknowledgement_id · production_order_id · acknowledgement_type_code
  · upstream_version · received_at · acknowledged_at · status_code · details(jsonb)
  · integration_message_id
```

**컬럼 3칸으로 평탄화할지, 이 표를 쓸지 판정을 부탁드립니다.** 저희 판단으로는 기존 표가 맞아 보입니다 — ERP 수신 이력과 `integration_message_id` 연결까지 담고 있어 확인이 여러 번 일어나도 이력이 남습니다. 컬럼으로 내리면 마지막 확인만 남습니다.

덧붙여 `production-02생산실행.json › ProductionOrderAcknowledge` 의 요청 본문은 `decisionCode` + **`reason`** 2필드입니다. `#63` 은 3칸만 드셨는데 `reason` 도 담을 자리가 필요합니다.

### A-3. 출하 시간대를 저희가 이미 다른 형태로 커밋해 뒀습니다

`#62`-5 에서 `SHIPMENT_TIME_SLOT`(`MORNING`·`AFTERNOON`·`NIGHT`) 신설을 확정으로 알려주셨는데, 저희는 `#41` 회신을 기다리는 동안 **시각 범위 2칸으로 이미 만들어 뒀습니다.**

```
02:2966   logistics.shipment_request
  ship_time_slot_start · ship_time_slot_end   (time without time zone)
  CONSTRAINT ck_shipment_request_time_slot
    CHECK (end IS NULL OR start IS NULL OR end > start)
```

**코드값 3종으로 바꾸겠습니다.** 확인 하나만 부탁드립니다 — 현재 CHECK 가 `end > start` 라 **자정을 넘기는 슬롯을 담지 못합니다.** `NIGHT` 가 야간 교대(예: 22:00~06:00)를 뜻한다면 시각 범위로는 애초에 표현이 안 됐던 것이고, 코드값 전환이 그 결함까지 같이 푸는 셈입니다. `NIGHT` 의 실제 시간대 정의를 알려주시면 좋겠습니다.

### ⛔ B-2. `trace.lot_hold_release` 도 테이블이 아니라 요청 본문입니다 — 그대로 받으면 기존 행이 깨집니다

`#63` 이 **"이번 재정리 유일의 파괴적 변경"**으로 표시한 항목입니다.

```
quality-03품질.json › LotHoldRelease   (required: targetLotStatusCode, releaseReasonCode)
  targetLotStatusCode · releaseQty · releaseReasonCode · remarks
```

해제 오퍼레이션의 **입력 DTO** 입니다. `release_reason_code` "선택 → 필수"는 이 DTO 의 required 이동이지 컬럼 NOT NULL 이 아닌 것으로 읽었습니다.

저희 물리는 보류와 해제를 한 표에 담습니다:

```
02:6626   trace.lot_hold
  ... held_by · held_at NOT NULL
      released_by · released_at · remarks · release_reason_code   ← 전부 nullable
  CONSTRAINT ck_lot_hold_release CHECK (released_at IS NULL OR released_at >= held_at)
  02:10282  CREATE INDEX ix_lot_hold_active ... WHERE released_at IS NULL
```

**`release_reason_code` 를 NOT NULL 로 올리면 아직 해제되지 않은 보류 행이 전부 깨집니다.** 해제 전에는 사유가 없는 것이 정상입니다. 기존 CHECK 를 확장하는 쪽으로 보고 있습니다:

```sql
CONSTRAINT ck_lot_hold_release_reason
  CHECK (released_at IS NULL OR release_reason_code IS NOT NULL)
```

**"해제된 행에는 사유가 반드시 있다"**가 의도하신 바가 맞습니까? `remarks` 필수→선택은 저희가 이미 nullable 이라 변경 없습니다.

### B-6. `WAREHOUSE_TYPE` — 계약 안에서 값이 서로 어긋납니다

`#62`-4 에서 4값(`MATERIAL`·`PRODUCT`·`SPARE_PART`·`GENERAL`)을 주셨는데, **`342a414` 계약 자신이 다른 목록을 적고 있습니다.**

```

  "isExternal 을 대체하지 않고 보완한다 — 창고 유형(자재·제품·반제품·상품·생산) 축과
```

여기 열거된 **자재·제품·반제품·상품·생산 5종**이 저희 시드와 정확히 대응합니다:

```
prisma/seed.ts:245   WAREHOUSE_TYPE
  MATERIAL(자재) · SEMI(반제품) · PRODUCT(제품) · MDSE(상품) · PRODUCTION(생산)
```

그리고 같은 파일의 `Warehouse.warehouseTypeCode` 는 이렇게 적혀 있습니다:

**즉 계약은 `WAREHOUSE_TYPE` 을 고정 목록이 아니라 G-31 고객 마스터로 규정합니다.** 그런데 `#62` 는 4값을 고정 목록처럼 지정하셨고, 그 4값에는 `isDefect` 설명이 든 반제품·상품·생산이 빠져 있고 대신 `SPARE_PART`·`GENERAL` 이 들어 있습니다.

여쭙습니다:

1. **`#62`-4 의 4값과 `isDefect` 설명의 5종 중 어느 쪽이 정본입니까?**
2. G-31 고객 마스터가 맞다면 **초기 시드값일 뿐이고 고객이 `W-06-06` 에서 바꾼다**는 뜻으로 이해하면 됩니까? 그렇다면 저희는 현재 7값을 그대로 두고, `DEFECT`·`REWORK` 만 `is_defect` 축(`02:4675`)으로 옮기며 정리하겠습니다.

`#47`(`is_defect`)이 닫힌 것을 확인했고, `342a414` 에서 `Warehouse.isDefect` 에 `x-source-column: is_defect` 가 붙은 것도 확인했습니다 — 그쪽은 양쪽 다 착지했습니다.
