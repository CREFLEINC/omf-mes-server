## 2. 물류 취소가 리소스 축에서 유형 축으로 옮겼다

```
- POST /logistics/inbound-receipts/{id}:request-cancel · :cancel
- POST /logistics/goods-receipts/{id}:request-cancel · :cancel
- POST /logistics/goods-issues/{id}:request-cancel · :cancel
+ POST /logistics/document-progress/{documentTypeCode}/{documentId}:request-cancel · :cancel
    documentTypeCode = INBOUND_RECEIPT · GOODS_RECEIPT · GOODS_ISSUE
```

계약이 이유를 적었다 — 「유형이 늘어도 화면이 유형↔리소스 표를 갖지 않게 하려는 것」
(공유계약 `A-10` 보강 · `omf-mes#352`). 파생 조회 뷰에 동사를 붙인 것이라 **리소스 축
규약의 의도적 예외**다.

⚠ **M1 tracer bullet 계획이 이 위에서 다시 그려져야 한다.** 완료 기준이 「취소 경로를 포함한
전표 체인 e2e」인데(`docs/development-strategy.md`), 그 취소 경로가 방금 하나로 합쳐졌다.
승인 후 실행 시점에 **서버가 후속 유무를 다시 판정**하고 걸리면 `400 SUCCESSOR_EXISTS`
라는 것도 이번에 계약에 실렸다(공유계약 `J-8`) — 상태기계 설계에 미리 얹는다.

## 3. 공유계약 v5.1 → v5.2 (조항 156)

- ⛔ **`screenId` 를 채울 표가 없다.** `ApprovalTarget.screenId`·`DocumentTarget.screenId`·
  `DocumentProgress.screenId` 셋 다 **화면 식별자**(`W-01-10` 꼴)를 요구하는데, 대응표가
  채운 것은 **리소스 경로**(`/logistics/goods-receipts/{id}` 꼴)다. 판별자 → 화면 식별자
  대응은 저장소 어디에도 없다. **물러난 길이 계약에 이미 있다** — 「서버가 열 화면을 정하지
  못하면 이 키를 생략한다(**널을 보내지 않는다**)」. 세 자리를 구현할 때 그대로 따른다.
- `LATE_ENTRY_ALLOWED_HOURS` 예시가 철회됐다 — 2026-08-31 확정(`omf-mes#61`)이 **사후 입력
  시간 임계값을 두지 않기로** 했다. 우리 시드에 이 키가 없어 지울 것은 없다.

## 5. 공지 감시가 꺼져 있었다 — 이번 라운드의 진짜 발견

`pnpm workflow:bootstrap` 이 회차를 `null` 로 뱉고 있었다. 설계팀이 `design/wiki/handover/` →
`design/wiki/progress/` 로 폴더를 옮겼는데 `bootstrap.mjs` 가 옛 경로를 봤고, **못 찾은 것을
정보성 한 줄로만 알렸다.** 규칙 5 의 감시가 조용히 꺼진 채로 회차 91 → 98 이 지나갔다.

고친 방식 — 후보 경로를 여럿 두고, **클론이 있는데도 하나도 못 찾으면 실패로 끝낸다.**
표 모양이 바뀌어 회차를 못 읽을 때도 같다. 「감시가 꺼진 것」을 성공으로 보고하지 않는다.
