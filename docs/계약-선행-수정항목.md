# 개발팀 선행 수정 항목 — 계약 사본을 당길 때 반영할 것

`contracts/` 는 설계 저장소의 **읽기 전용 사본**이다. 그런데 현장 결정이 먼저 떨어져 **서버가
계약보다 앞서 나간 자리**가 생긴다. 그 자리를 여기 적는다.

⛔ **`pnpm contracts:update` 를 돌리기 «전»에 이 문서를 읽는다.** 적어 두지 않으면, 새 사본에
그 칸이 없을 때 **아무도 모르는 채로 서버와 계약이 어긋난 상태로 굴러간다.**

> **이 문서와 `docs/coverage-100/계약-사본-당길-때.md` 는 다르다.**
> 저쪽은 **마감된 루틴(2026-09-10 종료)의 기록**이다 — 그 루틴이 설계팀에 청한 것들이 실려 올 때
> 빼야 할 가드 목록이고, 닫힌 문서라 **덧붙이지 않는다.**
> 이 문서는 그 뒤로 **계속 열려 있는 장부**다. 앞으로 생기는 선행 항목은 전부 여기 쌓는다.

## ⛔ 사본을 «고치지» 않는다 — 2026-09-13 에 실제로 그렇게 됐다

`contracts/` 를 직접 편집하면 다음 `pnpm contracts:update` 가 **조용히 지운다.** 그런데 그 사실을
알려 줄 도구가 없었다 — `contracts:check` 는 사본을 설계 **최신**과 대조해서, 「설계가 움직였다」와
「우리가 고쳤다」가 **같은 빨간불**이었다.

그 사이 사본 5벌이 고정 커밋(`a6a87e1`)에서 **120자리** 벌어져 있었다. 전수 조사(2026-09-13):

| 커밋 | 무엇 | 판정 |
|---|---|---|
| `bad2e95` | `RECYCLE_ENTRY` enum 선반영 | ✅ **본보기다** — 근거·위험·가드 spec 까지 커밋에 적었다 |
| **#610** | 클라이언트 전달본 **생성기 출력**을 `logistics-01자재창고.json` 에 덮어썼다 | ⛔ **사고** — 2026-09-13 에 도려냈다 |
| #610 | 자재·물류 스키마 파생 | ⚠ 기록 0 → **P-4** 로 연다 |
| #623 | 현장 단말·업무 파생 | ⚠ 기록 0 → **P-5** 로 연다 |

생성기 사고로 사본에 들어와 있던 것(`security` 90 · `x-omf-server-implementation` 90 ·
`401` 90 · `x-omf-known-differences` 5 · `securitySchemes.omfSession` · `info.version`)은 **설계
저장소에 고정본·최신본 양쪽 다 0건**이고 서버도 읽지 않아 전부 지웠다. 계약 검증 가드는 **요청
(body·query·params)만** 본다.

⇒ **`pnpm contracts:drift`** 를 만들었다. 사본을 **고정 커밋**과 대조해 「우리가 고쳤나」만 본다.

| 명령 | 질문 |
|---|---|
| `pnpm contracts:check` | 사본 ↔ 설계 **최신** — 「설계가 움직였나」 |
| `pnpm contracts:drift` | 사본 ↔ 설계 **고정** — 「우리가 고쳤나」 |

⛔ 사본을 고친 자리는 **여기에 항목을 열고**, 가능하면 `bad2e95` 처럼 **값이 사라지면 빨개지는
spec** 을 함께 둔다(`src/common/contract/contract-recycle-entry-enum.spec.ts`).

## 적는 규칙

서버가 계약에 **없는 것을 받거나 내리기 시작하면** 그 즉시 항목을 하나 연다. 한 항목에 넷을 적는다.

1. **무엇을 앞서 나갔나** — 계약에 없는 칸·동작
2. **코드 자리** — 사본이 바뀌면 따라 움직일 파일
3. **왜** — 그 결정의 근거(사용자 결정 · 통보 번호 · 이슈)
4. **사본을 당길 때** — ⓐ 실려 왔다 ⓑ 안 실려 왔다 ⓒ 다르게 실려 왔다, 세 갈래로 할 일

번호는 **`P-`**(선행, preceding) 접두를 쓴다 — `docs/계약-되돌림-mdm.md` 의 `Y-`·`Z-` 와 섞이지
않게 한다.

항목은 계약에 실려 정리되면 **지우지 않고 «닫는다»** — 제목에 `(닫힘 YYYY-MM-DD · 계약 <sha>)` 를
붙이고 「사본을 당길 때」 절만 지운다. 지워 버리면 **왜 그렇게 갔는지가 사라진다.** 되돌림 문서가
해소된 항목도 「정한 것」으로 남기는 것과 같은 이유다.

## P-1. 사용자 등록이 비밀번호를 받는다 — `AppUserCreate.password`

**무엇.** 계약 `AppUserCreate` 에는 비밀번호 칸이 없다. 서버는 **선택 칸 `password` 를 받고**,
받으면 그 값으로 자격을 만들고 **강제 변경을 걸지 않는다**(`must_change_password = false`).
안 받으면 임시 비밀번호를 뽑아 **201 응답에 한 번만** 싣는다(`temporaryPassword`).

그래서 201 응답도 계약과 다르다 — 계약은 `AppUser`, 서버는 `AppUser` + `temporaryPassword`.

| 코드 자리 | 무엇 |
|---|---|
| `src/app/access/app-user.service.ts` | `AppUserCreate.password` · `AppUserCreated` · `readPassword()` · `MIN_PASSWORD_LENGTH = 8` |
| `src/app/access/app-user.controller.ts` | `create()` 가 `actorId` 를 넘긴다 |
| `scripts/client-api/build-implementation-baseline.mjs` | `applyMdmPatches()` — 전달본에 이 칸을 그려 넣는 패치 |
| `test/app-user.e2e-spec.ts` | 비밀번호 4건(임시 발급 · 직접 지정 · 8자 미만 400 · 타입/`null`) |

**왜.** 사용자 결정 2026-09-12. 그 전에는 등록이 `app_user` 행만 만들어, 관리자가
`:reset-password` 를 따로 누르기 전까지 **로그인이 안 되는 계정이 정상 상태로 남았다.** 그 증상은
계정 존재를 숨기는 401 과 구분되지 않아 관리자가 원인을 짚지 못한다. PR #613.

⚠ **지금 이 칸은 계약 검증 가드가 보지 못한다.** 계약에 없는 속성이라 `contract-validator` 를
그냥 지나친다(ajv 에 `removeAdditional` 이 없고 계약에 `additionalProperties: false` 도 없다).
그래서 `readPassword()` 가 **유일한 문지기**다 — 타입·길이를 거기서 막는다.

**사본을 당길 때**

- **ⓐ `password` 가 실려 왔다** — ⛔ **먼저 `minLength` 가 «함께» 왔는지 본다.**
  - **왔다** — 길이·타입 검사를 **계약 가드에 넘긴다.** `readPassword()` 에는 「`null` 을
    「안 보냈다」로 읽는」 정규화만 남기고 `MIN_PASSWORD_LENGTH` 를 지운다.
    ⭐ 이때 #613 리뷰의 Minor ① 도 같이 사라진다 — 지금 서버는 `.length`(UTF-16 단위)로 세어
    `'😀😀😀😀'`(8) 를 통과시키는데, ajv 는 코드 포인트로 세어(4) 거절한다. 가드에 넘기면
    기준이 하나가 된다.
  - **안 왔다** — ⛔ **`MIN_PASSWORD_LENGTH` 를 지우지 마라.** 칸만 생기고 길이 제약이 없으면
    지우는 순간 **길이 검증이 조용히 사라진다.** 타입만 가드에 넘기고 길이는 그대로 둔 뒤,
    「계약에 최소 길이를 넣어 달라」를 설계팀에 올린다.
- **ⓑ 안 실려 왔다** — **아무것도 지우지 마라.** `readPassword()` 가 여전히 유일한 문지기다.
  이 항목을 그대로 둔다.
- **ⓒ 다르게 실려 왔다**(이름이 다르다 · 필수다 · 조합 규칙이 붙었다) — 계약을 따른다. 서버가
  만든 이름을 고집하지 않는다.

**201 응답**은 세 갈래 모두에서 따로 본다. 계약이 `AppUser` 를 그대로 두면 `temporaryPassword` 는
**계약에 없는 응답 칸**으로 남는다 — 그 사실을 이 항목에 계속 적어 둔다.

## P-2. 로그인 응답이 강제 변경 표시를 싣는다 — `Session.mustChangePassword`

**무엇.** 계약 `Session` 에 칸이 없다. 서버는 **불리언 `mustChangePassword` 를 «언제나» 싣는다** —
`POST /app/sessions` 와 `GET /app/sessions/current` 양쪽 모두.

| 코드 자리 | 무엇 |
|---|---|
| `src/auth/session.types.ts` | `mustChangePassword: boolean` (선택 아님) |
| `src/auth/session.service.ts` | `build()` 가 `user_credential` 을 include 해 값을 푼다 |
| `scripts/client-api/build-implementation-baseline.mjs` | `applyAppPatches()` — 전달본에서 `required` 로 승격 |
| `test/auth.e2e-spec.ts` | 「강제 변경 표시를 세션이 그대로 싣는다」 |

**왜.** 서버는 이 값을 **이미 계산하고 있었는데**(`credential.service.ts`) 계약에 칸이 없어 응답에
싣지 못했다. 그래서 화면이 임시 비밀번호 사용자를 비밀번호 변경으로 보낼 근거가 없었다. 부재를
「모른다」로 읽을 자리를 만들지 않으려고 **선택이 아니라 필수**로 두었다(공유계약 G-9).

**사본을 당길 때**

- **ⓐ 실려 왔다** — 계약이 `required` 에 넣었는지 확인한다. **선택으로 왔으면 서버가 더 엄격한
  것이고 그대로 두어도 된다** — 다만 전달본 생성기의 `required` 승격 패치는 지운다.
- **ⓑ 안 실려 왔다** — 그대로 둔다. 화면이 이 값에 매여 있으므로 **빼면 안 된다.**
- **ⓒ 이름이 다르게 왔다** — 계약 이름으로 바꾸고 클라이언트에 알린다(전달본을 다시 뽑는다).

## P-3. 자재 입하 LOT 이 계약보다 엄격하다 — 여섯 가지 제약

**무엇.** `#610`(FR-001) 이 입하에서 나는 자재 LOT 에 **계약에 없는 제약**을 더했다.

| 제약 | 자리 | 계약은 |
|---|---|---|
| `initialQty` = 입하 라인 `received_qty` | `lot.service.ts:323` | `exclusiveMinimum: 0` 뿐 |
| `itemId`·`uomId`·`plantId` = 입하 라인의 값 | 〃 `:320`·`:326`·`:329` | 제약 없음 |
| `lotTypeCode` = `MATERIAL` 만 | 〃 `:332` | `LotCreate` 에 제한 없음 |
| 제품코드·공급사 성분은 **구분자 5칸 형식**(제품코드\|수량\|날짜\|공급사\|번호 · 64자 이하) | `lot-number.ts` `materialMesLotNo()` | `MLOT #16` 이 「구분문자 없음」을 **확정**(2026-07-27)으로 적어 뒀다 — 이 형식은 그 확정 문구와 다르다(통보 277 · 되돌림 §Z-1) |
| 사전부착 공급사 LOT 번호는 **같은 구분자 5칸 형식** + **제품코드·공급사가 입하 라인과 일치** | `inbound-receipt-rules.ts` · `inbound-receipt-split.service.ts` | `supplierLotNo` 는 `maxLength: 100` 문자열, 형식·일치 검증 없음 |
| 검사 대상 품목은 **확정 IQC 기준이 정확히 하나** | `lot-registry.service.ts:227` | 계약에 그런 선행조건 없음 |

**왜.** 자재 LOT 번호가 품목·수량·일자·공급사를 **번호 안에 담는다**(모바일 스캔 화면의 정본
형식). 34자리 숫자였을 때는 그 자릿수에 안 들어가는 마스터 코드가 번호를 만들 수 없었다
(#620) — 통보 277 이 구분자 5칸으로 바꿔 마스터 코드를 원본 그대로 담게 했다. 사전부착 번호의
제품코드·공급사 일치 검사는 **틀린 라벨이 조용히 통과하는 것을 막는다**는 새 판단이다. 나머지
넷은 「LOT 이 입하 라인을 그대로 반영해야 한다」는 기존 판단 그대로다.

⚠ **이 제약들은 계약에 적히지 않았고, `#610` 병합 시 기록도 남지 않았다.** 그래서 기존 e2e
64건이 조용히 빨개진 채로 `main` 에 들어갔다(#617). 이 항목은 그 뒤늦은 기록이다.

**사본을 당길 때**

**✅ 결정됐다(2026-09-14 · 통보 277)** — 더는 #620 을 기다리지 않는다. 구분자 5칸 형식으로
서버가 이미 바뀐다(브랜치 `feat/material-lot-qr-label`). 계약 사본을 당길 때는:

- **ⓐ 같은 형식이 계약에 실려 왔다** — 서버 검사를 계약 가드에 넘길 수 있는 것만 넘긴다.
  `MLOT #16` 의 「구분문자 없음 ✓확정」 문구가 설계 쪽에서도 개정됐는지 먼저 확인한다.
- **ⓑ 안 실려 왔다(옛 34자리·「구분문자 없음」 그대로)** — 계약과 서버가 다른 채로 남는다.
  `x-internal-note` 로 이 괴리를 적어 두고, 서버 구현은 통보 277 대로 유지한다 — **되돌리지
  않는다.** 이미 만들어진 신형식 LOT 이 있으면 되돌릴 방법이 없다(라벨이 실물에 찍혀 있다).
- **ⓒ 다르게 실려 왔다**(예: 구분자를 다른 문자로, 칸 순서를 다르게) — 그 차이만큼 서버를
  따라가되, 이미 만들어진 LOT 의 소급 변환은 하지 않는다. e2e 픽스처(품목·공급사 코드·
  공급사 LOT 번호)를 **함께** 고친다. 이 셋은 형식에 매여 있어 계약이 바뀌면 반드시 같이 움직인다.

**e2e 픽스처가 이 형식에 매여 있다** — `test/trace-lot.e2e-spec.ts` ·
`test/logistics-inbound-receipt.e2e-spec.ts` · `test/logistics-document-progress.e2e-spec.ts` 의
`ITEM_CODE`·`SUPPLIER_CODE`·`supplierLotNoOf()`.

## P-4. 입하 라인이 「공급사 LOT 라벨 부착 여부」를 받는다 — `supplierLotLabelAttached`

**무엇.** `#610` 이 **계약 사본에 직접 써넣었다.** 설계 저장소에는 고정본 `a6a87e1` 에도,
**최신본에도 0건**이다(실측 2026-09-13).

| 자리 | 무엇 |
|---|---|
| `InboundReceiptLine` | `+ supplierLotLabelAttached` · **`required` 변경** |
| `InboundReceiptLineUpsert` | `+ supplierLotLabelAttached` |
| `GET /logistics/inbound-receipts` | 질의 파라미터 `+ supplierLotLabelAttached` |
| `GET /logistics/inbound-receipts/{id}/lines` | 〃 |
| `InboundReceiptCreate.description` | 설계 원문의 `supplierLotMissing` 서술을 **`supplierLotLabelAttached` 기준으로 다시 썼다** |

⛔ 「생략하면 `supplierLotMissing` 의 반대값으로 읽는다」는 하위호환 규칙도 **서버가 정한 것**이다.
계약에는 그 문장이 없다.

**코드 자리** — `src/logistics/inbound-receipt/inbound-receipt-rules.ts` ·
`test/logistics-inbound-receipt.e2e-spec.ts` · `test/logistics-document-progress.e2e-spec.ts`

**왜.** `#610`(FR-001) 이 「라벨이 붙었는가」와 「공급사 LOT 번호가 없는가」를 **다른 축**으로 갈랐다.
그 판단 자체는 타당하다 — 라벨이 붙었는데 번호를 못 읽은 경우와 애초에 라벨이 없는 경우는 현장에서
다른 일이다. 다만 **계약에 청하지 않고 사본을 고쳤고, 기록도 남기지 않았다.**

⚠ **2026-09-12 에 이 항목 때문에 판단이 한 번 어긋났다.** `#617` 을 볼 때 이 칸이 「설계팀 계약에
정의돼 있다」고 보고했는데 **틀린 말이었다.** 사본만 보고 정본을 안 봤기 때문이다 — 그때는
`contracts:drift` 가 없었다. 선택된 갈래(ⓐ, e2e 를 서버 규칙에 맞춘다)는 결과적으로 유효하나,
근거는 「계약이 그렇게 정했다」가 아니라 **「서버가 그렇게 정하고 사본에 적었다」**이다.

**사본을 당길 때**

## P-6. 사용자 상세 조회의 타인 접근 금지 — `GET /app/users/{appUserId}` 403

**무엇.** 계약 사본은 이 조회에 403 을 선언하지 않는다. 권한 가드가 이를 건너뛰어 로그인한
권한 없는 사용자가 타인의 이름·이메일 등 상세를 읽을 수 있었다. 서버는 본인 상세를 허용하고,
타인 상세에는 사용자 관리 권한 `W-CO-02` 를 요구한다. 없으면 `PERMISSION_DENIED` 403 이다.
개인정보 응답은 `Cache-Control: private, no-store` 로 보내며, 과거 ETag 의
`If-None-Match` 는 304 재사용 없이 현재 200 본문으로 답한다. 수정용 ETag 는 유지한다.

**코드 자리** — `src/app/access/app-user.controller.ts` 의 `get()` 접근 검사·캐시 헤더와
`test/app-user.e2e-spec.ts` 의 관리자/권한 없는 계정/본인/무인증·조건부 요청 검사.
클라이언트 `apps/web/src/screens/users-roles/screen.tsx` · `load-error-banner.tsx` 는
목록이 403 이면 상세·역할·범위를 숨기는 같은 화면의 연계 지점이다.

**왜.** FR-001 v2 실제 관리자 화면에서 권한 없는 A 계정이 B 계정 상세를 읽었다
(2026-09-13). 별도 A 세션의 실제 API 도 200 을 재현했다. 계약 403 미선언으로
`PermissionGuard` 가 검사하지 않았고, 상세 응답의 ETag `1` 은 초기화 전 브라우저 캐시와
재사용되어 이전 사용자 상세가 나타나기도 했다. 사용자 관리 화면의 권한은 기존 `W-CO-02` 다.
`GET /app/sessions/current` 는 본인 세션 조회이므로 바꾸지 않는다.

**사본을 당길 때**

- **ⓐ 403 이 실려 왔다** — 새 계약의 권한과 응답 형태를 확인한다. `PermissionGuard` 가
  `W-CO-02` 를 요구하도록 매핑하면 본인 상세까지 선차단하는 충돌이 생긴다. 본인 허용을
  먼저 검증하고, 명시 검사를 보존하거나 동등한 분기 구조로 옮긴다. 캐시·조건부 요청
  검사는 유지한다.
- **ⓑ 안 실려 왔다** — 이 경로의 명시 검사를 지우지 않는다. 설계팀에 403 제약을 청한다.
- **ⓒ 다른 제약으로 왔다** — 타인 상세의 실제 허용 범위를 설계·사용자와 대조하고
  런타임 검사와 회귀 테스트를 함께 조정한다.

## P-7. FR-007 MOBILE 단말 등록 완료 확인 — 현재 토큰 세대

**무엇.** 설계 사본 `mdm-기준정보.json`에는 단말의 가동 상태와 토큰 발급 시각만
있으며 기기 등록 완료 상태가 없다. 서버는 `mdm.terminal`에
`registered_token_version`/`registration_confirmed_at`을 추가하고, Terminal
목록·상세 응답에 `registrationStatusCode` (`UNREGISTERED`/`REGISTERED`) 및
`registrationConfirmedAt` (현재 세대의 확인 시각 또는 null)을 내린다. 현재 발급
세대와 일치할 때만 등록으로 보므로 재발급은 미등록으로 돌아간다. 가동 상태
`statusCode`는 그대로 둔다.

**신설 오퍼레이션.** `POST /mdm/terminals/{terminalId}:confirm-registration`은 빈
본문과 UUID `Idempotency-Key`를 받는다. 관리자 쿠키가 아닌 현재 세대의 활성
MOBILE 단말 Bearer 토큰만 허용한다. JWT 서명·만료·종류, DB의 단말/공장/코드/세대,
URL의 단말 ID를 검증한다. 실패는 401이며 등록 행을 바꾸지 않는다. 같은 세대의
재호출은 첫 확인 시각을 보존하고 200으로 같은 상태를 돌린다. 단말 기기가 QR
검증과 해당 공장 작업자 명부의 로컬 저장을 끝낸 직후 이 호출을 하고, 성공 후
로컬 등록 상태로 전환한다. 응답은 `terminalId`, `tokenVersion`,
`registrationStatusCode: REGISTERED`, `registrationConfirmedAt`이다.

**코드 자리.** `src/mdm/terminal/terminal.controller.ts`/`terminal.service.ts`,
`src/auth/authentication.guard.ts`의 등록 오퍼레이션 전용 분기,
`src/auth/terminal-token.ts`, Prisma migration, 관련 회귀 테스트. 모바일·웹은
이 선행 응답 필드와 경로를 타입으로 한정해 사용한다. 사본에 없는 `@Contract`
오퍼레이션을 꾸며 등록하면 계약 실재성 검사가 깨지므로, 정본 반영 전에는 명시적
전용 메타데이터와 전역 인증 가드의 엄격한 분기를 쓴다. 요청 헤더·빈 본문은
컨트롤러에서 검사한다. 기기 상태 조회는 기존 관리자 조회 권한 그대로다.

**왜.** FR-007 초기 실제 화면에서 새 MOBILE 단말을 만들고 QR을 발급해도
관리웹에 RUNNING만 보였다. 발급만으로는 기기가 QR을 읽고 명부를 저장했는지
확인할 수 없다. 두 상태를 합치면 미등록 기기가 등록 완료로 잘못 표시된다.

**사본을 당길 때**

- **ⓐ 실려 왔다** — 신설 경로의 인증·요청·응답과 Terminal 두 필드가 같음을
  확인하고 전용 분기를 표준 계약 가드/생성 타입으로 옮긴다. 401과 세대 경합,
  멱등·등록 표시 회귀는 보존한다.
- **ⓑ 안 실려 왔다** — 이 경로와 응답 필드가 사본에서 사라지지 않게 선행
  구현을 유지하고 설계팀에 반영을 요청한다.
- **ⓒ 다르게 실려 왔다** — 토큰 발급과 기기 완료를 구분하는 목적 및 실제 모바일
  호출 시점을 대조해 결정한다.

## P-8. FR-002 v2 자재 LOT 라벨 TSPL 렌디션 — 배포 POP RAW 출력

**무엇.** 설계 사본 `GET /app/document-issues/{documentIssueLogId}/rendition`의
`format`은 `png|pdf`이고 200 응답에도 TSPL이 없다. 현장 POP Electron은 RAW
출력을 위해 `format=tspl`을 요청한다. 서버는 정확히 이 경로의 `tspl` 질의만
선행 수용하고 `MATERIAL_LOT_LABEL` 발행 기록의 품목 코드·MES LOT 번호·수량·
발행 회차를 CRLF TSPL 명령으로 반환한다(`application/vnd.tspl`). 기존 `png`/기본값은
`image/png` 그대로다. 미지원 문서의 TSPL·구현되지 않은 PDF는 422로 거절하며
PNG를 다른 형식으로 위장하지 않는다. 출력 문자열은 제어문자·비ASCII·따옴표·
역슬래시를 거절해 명령과 바코드 값이 바뀌지 않게 한다.

**배치(2026-09-14 개정).** 계약은 라벨 배치를 정하지 않는다. 클라이언트 업데이트 없이
새 LOT 번호(통보 277)가 표준 라벨로 찍히도록, tspl·png 모두 클라이언트 개발 목업
(`omf-mes-client` `tools/mock/label-tspl.mjs` `renderLotTspl`)의 80×30mm 좌표·글자 크기·
줄임 규칙을 따른다(POP 셸은 바이트 시그니처 `SIZE `/PNG 만 본다). 목업과 다른 곳은
셋이다 — 2D 코드는 DMATRIX `L1|…` 묶음 대신 **QR 에 LOT 번호 그대로**, 품명 줄 없음(277
결정 5), 날짜 줄 오른쪽에 `ISSUE NO.`. 수량은 반올림 없이 천 단위 구분 + 단위 코드,
일시는 공장 시간대 `YY-MM-DD HH:mm`(제조일시가 없으면 발행 일시). png 는 639×240(203dpi).

**코드 자리.** `src/app/document-issue/document-issue.controller.ts`,
`document-issue-rendition.service.ts`, `material-lot-tspl.ts`, `material-lot-label.ts`,
`material-lot-label-layout.ts`,
`src/common/contract/contract-validation.guard.ts`의 정확한 경로 보정 및 회귀.
클라이언트는 `apps/web/src/patterns/pop-label-rendition.ts`에서 Electron 셸일 때
TSPL·미리보기일 때 PNG를 요청하고, 배포 모드 호출 잠금은 서버 실제 지원에 맞춰
클라이언트 담당이 조정한다. 사본 자체는 직접 수정하지 않는다.

**왜.** FR-002 v2 재검토에서 현 서버가 `format`을 무시하고 항상 PNG를 반환함을
확인했다. 배포 POP는 TSPL 바이트를 RAW 통로로 보내므로 이 상태에서는 MIME과
실제 바이트가 어긋나 라벨 출력 흐름을 진행할 수 없다. 실물 인쇄 성공은 이번
소프트웨어 렌디션 지원만으로 주장하지 않는다.

**사본을 당길 때**

- **ⓐ 실려 왔다** — 질의 enum·`application/vnd.tspl` 응답과 이 선행 동작을 대조하고
  정확한 경로 보정을 표준 계약 검증으로 옮긴다. PNG·TSPL·거절 회귀는 유지한다.
- **ⓑ 안 실려 왔다** — P-8 경계와 회귀를 보존하고 설계팀에 반영을 요청한다.
- **ⓒ 다르게 실려 왔다** — 클라이언트의 Electron RAW 인쇄 형식과 실제 응답 바이트를
  대조해 양쪽을 함께 조정한다.

**무엇.** 설계 사본에 없는 `GET /mdm/terminals/{terminalId}/accessible-screens`를
POP 현재 세대 Bearer 전용으로 선행 추가한다. 활성 POP가 자기 단말 ID와 공장·
토큰 세대가 일치할 때만 `{ "screenCodes": ["P-01-01"] }`을 반환한다. 이
`P-01-01`은 이미 해당 공장 POP로 자재 LOT·라벨 API 사용이 허용된 화면이다.
관리자 `/app/sessions/current`는 계정 세션 전용 그대로이고, 이 응답을 계정
권한으로 위장하지 않는다. 생산 등 다른 화면 코드는 공정 매핑 플래그와 화면
권한의 관계가 별도로 정의될 때까지 반환하지 않는다. 응답은 `private, no-store`다.

**코드 자리.** `src/auth/terminal-registration-operation.ts`,
`src/auth/authentication.guard.ts`, `src/mdm/terminal/terminal.controller.ts`,
단위·E2E 회귀. 클라이언트 POP의 화면 이동 조회를 이 경로로 바꾼다. 설계 사본
`contracts/*.json`은 직접 수정하지 않는다.

**왜.** POP는 사번 귀속 단말 토큰으로 움직이는데 화면 후보 조회가 계정 쿠키의
`GET /app/sessions/current.permissions`를 사용해 401을 받고 메뉴가 비활성화됐다.
등록·공정·설비 설정과 별도인 화면 접근 오류다.

**사본을 당길 때**

- **ⓐ 실려 왔다** — 자기단말·활성·공장·현재 토큰 세대와 반환 코드 범위를 대조해
  표준 계약 경계로 옮긴다. 타단말·타공장·MOBILE·이전 세대·무토큰 회귀를 유지한다.
- **ⓑ 안 실려 왔다** — 이 좁은 응답과 회귀를 보존하고 설계팀에 반영을 요청한다.
- **ⓒ 다르게 실려 왔다** — 실제 POP 작업 시작 권한과 공정 매핑을 근거로 화면별
  정책을 정의한 뒤 서버·클라이언트 후보를 함께 조정한다.

## 당기기 «전»에 돌릴 것

```bash
pnpm contracts:drift         # ⛔ 사본을 우리가 고친 자리. 여기 뜨는 것이 지워질 것들이다
```

위 목록과 이 문서의 `P-` 항목이 **맞아떨어지는지** 본다. 문서에 없는 자리가 뜨면 **당기기 전에
항목을 연다** — 당긴 뒤에는 무엇이 있었는지 알 길이 없다.

## 당긴 뒤 반드시 돌릴 것

```bash
pnpm contracts:drift         # 이제 비어야 정상이다 (P- 항목 ⓑ 로 남긴 것 빼고)
pnpm contracts:generate      # contracts/*.json → src/contracts/<slug>.d.ts
pnpm typecheck
pnpm test -- contract        # 계약 대조 unit spec 들
pnpm test:e2e -- contract     # ⛔ 잊기 쉽다 — contract-validation·contract-int64-range 는 e2e 다
pnpm test:e2e -- app-user auth
```

⭐ **전달본 생성기를 잊지 마라.** `scripts/client-api/build-implementation-baseline.mjs` 의
`applyMdmPatches()`·`applyAppPatches()` 는 **계약에 없는 칸을 그려 넣는** 패치다. 계약이 그 칸을
정식으로 실어 오면 패치가 **중복으로 덮어쓴다** — 조용히 우리 설명이 계약 설명을 이긴다.
ⓐ 갈래에서는 해당 패치를 **지우고** 전달본을 다시 뽑는다.

⚠ 전달본을 다시 뽑을 때 `SERVER_COMMIT` 은 **`main` 에 남는 커밋**이어야 한다. 이 저장소는 PR 을
squash 로 병합해 작업 브랜치 해시가 사라진다 — 그 상수 옆 주석에 적어 두었다(#613 → #614).
