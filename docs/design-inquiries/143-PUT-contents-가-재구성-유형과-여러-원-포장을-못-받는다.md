# 143. `PUT …/contents` 가 재구성 «유형»도 «여러 원 포장»도 `remarks` 도 못 받는다 — 그리고 빈 배열이 `:pack` 불변식을 사후에 깬다

| 칸 | 내용 |
|---|---|
| 걸리는 오퍼레이션 | `PUT /inventory/handling-units/{handlingUnitId}/contents` · `POST /inventory/handling-units/{handlingUnitId}:pack`(ⓒⓓ) |
| 구현 상태 | **구현 예정(I-16 · 계획만 병합됨 · 오늘 코드 0줄)** |
| 판정 | ⓐⓑ `coverage-100/README.md` §2 **2단계 기준 4**(값을 조용히 도출하지 않는다 — 수량 모양으로 `MERGE`/`SPLIT` 을 추론하지 않는다) · ⓒ **`plan.md` §5 규칙 7**(담을 칸 0 → 형식만 보고 버린다) · ⓓ **1단계 계약 문자 그대로**(계약이 `minItems` 를 `:pack` 에만 걸었다 = 명시 신호 → 허용) |
| 되돌릴 때 | ⓐⓑ 요청 스키마가 유형·여러 HU 를 실으면 서비스 한 자리 + 라인 생성 규칙. ⓒ `remarks` 칸을 열면 마이그 한 줄. ⓓ 거부로 바꾸면 400 한 갈래(허용→거부는 **깨는 변경**이라 지금 정해야 한다) |

## 무엇이 문제인가

ⓐ **응답은 재구성 «유형»을 required 로 요구하는데, 요청에 그 칸이 없다.** `HandlingUnitRepackEvent.repackTypeCode` 는 required 이고 enum 3값(`MERGE`·`SPLIT`·`RECONFIGURE` · `x-code-key: CD-REPACK-TYPE`)인데, 이 슬라이스 7 오퍼레이션의 요청 본문 3종(`HandlingUnitCreate`·`HandlingUnitContentUpsert`·`HandlingUnitPack`) **어디에도 그 칸이 없다**(전수 실측). 그런데 화면은 작업자에게 셋을 고르게 한다 — 「원 포장 스캔 → **재구성 유형 선택(합병/분할/재구성)** → 새 구성 편집 … → 재구성 확정」(`M-04-03-포장재구성스캔.md:11`). ⇒ **작업자가 고른 유형이 서버에 도달하지 않는다.**

ⓑ **합병(원 포장 여럿)을 한 요청에 담을 자리가 없다.** 경로가 `{handlingUnitId}` 하나이고 본문은 그 HU 의 구성 배열뿐이다. 그런데 화면은 라인 축으로 출처가 남는다고 적었다 — 「⚠ **합쳤다고 말한다** — 조용히 합치면 **어느 포장에서 얼마가 왔는지**를 못 본다. `HandlingUnitRepackEventLine`의 `roleCode=SOURCE` 행들이 그 출처를 남긴다(§5-2)」(`M-04-03-포장재구성스캔.md:173`). 한 요청이 한 HU 만 다루면 이벤트 라인의 `handling_unit_id` 는 **전부 경로의 그 HU** 가 되어, **`SOURCE` 로 남을 다른 포장이 없다.**

ⓒ **`HandlingUnitPack.remarks` 를 담을 칸이 물리에 없다.** 계약은 그 칸을 받는다(`contracts/logistics-01자재창고.json:8845` — 「비고」). `inventory.handling_unit` 13칸 전수에 `remarks` 가 없다(`prisma/schema.prisma:414-439`). ⇒ 받고 버린다.

ⓓ **빈 배열 `PUT` 이 `:pack` 이 세운 불변식을 사후에 깬다.** 계약은 `:pack` 에만 `minItems: 1` 을 걸고(`contracts/logistics-01자재창고.json:8829`) description 에 「포장 단위와 내용물 N행이 한 트랜잭션으로 확정된다(공유계약 B-8) — **내용물 없이 확정할 수 없다**」라 적었다(`:8825`). 반면 `HandlingUnitContentUpsert` 는 「구성 **전체 치환** 항목. **요청에서 빠진 기존 행은 삭제한다.** 근거: 공유계약 A-5」이고 `minItems` 가 없다(`:1448` 경로의 요청 배열). ⇒ 빈 배열을 보내면 **내용물 없는 `PACKED` 포장**이 만들어져, 확정 시점에 막아 둔 상태가 나중에 그대로 생긴다. 화면 셋은 반대다 — 「**재구성 확정** | 새 구성 유효 AND **수량 합 = 원 수량 합**」(`M-04-03-포장재구성스캔.md:195`) · 「수량 합 불일치 | ⛔」(`:204`) · 「**수량 합 = 원 수량 합** 제약이 걸려 포장 밖으로 빼지 못한다 — **해체가 아니다**」(`P-02-08-포장작업.md:162`). 즉 **허용하면 화면이 닫아 둔 해체 경로가 API 로 열린다.**

## 지금 서버는

- **아직 없다.** 계획이 정한 동작은 아래와 같다.
- ⓐ 이벤트 헤더의 `repack_type_code` 를 **`'RECONFIGURE'` 고정**으로 쓴다. 수량 모양(줄어듦=분할, 늘어남=합병)으로 유형을 **추론하지 않는다**.
- ⓑ 라인의 `role_code` 는 치환 전/후 구성을 비교해 서버가 도출한다(전에 있었고 후에 빠진 줄 = `SOURCE` · 나머지 = `RESULT`). 그래서 라인의 `handling_unit_id` 는 전부 경로의 그 HU 다. 화면이 그리는 「합병」은 클라이언트가 **`PUT` 을 여러 번** 쏘는 모양이 되고, 그러면 이벤트도 여러 건으로 흩어진다.
- ⓑ 참고 — 같은 `(itemId, lotId)` 가 요청 배열 안에 둘이면 서버는 **합치지 않고 400 `UNIQUE_VIOLATION`** 을 낸다. 화면이 말하는 「80 에 60 을 더해 140 이 됩니다」(`M-04-03-포장재구성스캔.md:205`)는 클라이언트가 보내기 «전»에 하는 일로 두었다.
- ⓒ `remarks` 는 형식만 보고 버린다(`businessDate`·`occurredAt` 도 같다 — 이 오퍼레이션들은 원장을 지나지 않아 담을 칸이 없다).
- ⓓ 빈 배열을 **허용한다**(전건 삭제). 화면 근거는 있다 — 「분할 잔량 0 | ⚠ **허용** — 전량을 새 포장으로 옮기는 것도 재구성이다」(`M-04-03-포장재구성스캔.md:206`). 다만 그 결과 빈 `PACKED` 포장이 남는다.

⇒ **묻는 것**: ⓐ 재구성 유형과 ⓑ 여러 원 포장을 요청에 실을 것인가(실지 않으면 이벤트의 `repackTypeCode` 는 영구히 한 값이고 합병 출처가 안 남는다) · ⓒ `remarks` 를 저장할 칸을 열 것인가, 아니면 계약에서 뺄 것인가 · ⓓ 빈 배열 `PUT` 을 허용하는가 거부하는가(허용→거부는 나중에 못 바꾼다).
