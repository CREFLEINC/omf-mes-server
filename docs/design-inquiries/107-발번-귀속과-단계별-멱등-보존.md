# 107. 발번 귀속의 저장과 발행 단계별 멱등 보존

> **서버팀 결정·통보 예정(2026-09-09):** 실제 로그인 계정은 `created_by`, 작업자는 필수 `X-Worker-No`의 마스터 존재 검사, 단말은 실제 토큰과 `terminal_process.can_print_label` 권한 검사로 귀속한다. 현재 스키마에 작업자·단말 영구 칸을 추가하지 않고 계정·사번·단말을 멱등 지문에 포함한다. 기존 멱등 기록이 보존되는 동안 원 응답을 재생하며, 영구 배치표나 별도 삭제 후 복구 규약은 만들지 않는다. 발번과 발행기록은 서로 다른 키를 유지한다.

|---|---|
| 대상 | I-26 발번·I-27 발행기록 연결, 사번/단말 귀속·멱등 기록 삭제 뒤 복구 |
| 상태 | 서버팀 결정 완료·I-26 POST 반영 중. 인증/CORS 공용 수정 및 새 영구 배치표0 |

## 귀속과 실제 인증

필수 X-Worker-No는 귀속용이며 최대50자다. 6자리 강제나 계정과 worker의 연결을 새로 요구하지 않는다. 현재 활성 계정 세션은 별도로 필요하다(기존 문의054). serial_number에는 worker_id/terminal_id가 없고 created_by는 app_user FK다.

로컬 지문에는 계정·사번·단말을 포함해 다른 주체의 응답 재생을 막는다. 실제 terminalId bigint는 지문에서 문자열/null로 바꾸며 Number 변환을 하지 않는다. **지문 해시는 행위자 사번/단말의 영구 저장을 대신하지 않는다.**

**발번한 개체의 귀속 사번·단말을 나중에 복원해야 하는지와, 필요하다면 어느 기록을 정본으로 삼는지 알려 달라.** 임의 컬럼·감사 FK 재해석은 하지 않는다.

단말 기능은 생산 LOT→W/O→공정의 실제 can_print_label 구성을 확인하는 후보이며 임의 첫 공정을 고르지 않는다. 브라우저 교차 오리진의 Authorization/X-Worker-No는 현재 CORS 허용 목록에 없어 동일 오리진 경로와 구분한다. 이는 공용 담당 배포 과제다.

## 두 단계의 키와 보존 한계

① 발번 응답 N개를 ② document-issues의 **단일 targets N개 요청**으로 넘긴다. 두 단계는 서로 다른 키를 쓰고 각 단계의 키·본문·귀속은 재전송 동안 유지한다. ① 응답 유실은① 동일 키, ② 응답 유실은② 동일 키로 원래 회차를 재생한다. 발행기록 실패 때문에 새 개체를 만들거나 성공 배치를 GET 첫 페이지로 재구성하지 않는다.

기존 IdempotencyService는 expires_at을72시간 뒤로 저장하지만 **그 시각을 직접 검사하지 않는다**. 따라서 ‘72시간 후 자동 재발번’이라고 단정할 수 없다. 다만 기록이 실제 삭제되면 시리얼 행에 키/배치 축이 없어 최초 응답을 복원하지 못한다.

**현장 큐의 최대 재전송 기간과 멱등 기록의 실제 삭제 정책, 삭제 뒤 같은 키 요청의 복구 책임을 정해 달라.** 그전에는 영구 배치표를 선제 추가하지 않고 기존 기록 보존 범위에서만 재생을 보장한다. 이 질문은 I-27 기록 성공 후 응답 유실을 새 재발행으로 처리해도 된다는 뜻이 아니다.
