# 103. 알림 재전송의 주체·이벤트 격리와 공통 오류

| 칸 | 내용 |
|---|---|
| 걸리는 오퍼레이션 | 알림 read/read-all · recipients:preview · 조건부 subscriptions PUT — `POST /app/notifications/{notificationId}:read` · `POST /app/notifications:read-all` · `POST /app/notification-subscriptions/recipients:preview` · `PUT /app/notification-subscriptions` |
| 구현 상태 | **구현 예정(I-28 R-6·R-8). 공용 runner 수정0** |
| 판정 | 0단계 인증/멱등 기존 계약과 IdempotencyService tx 경계를 사용. query/actor 결손은 로컬 경계에서 보정하며 새 상태·오류 코드를 발명하지 않음 |
| 되돌릴 때 | 공용 runner가 개선되면 동일한 주체/질의/tx 보장을 확인한 뒤 로컬 경계만 통합. 외부 오류 계약 보완은 계약 소유자가 수행 |

> ⭐ **「걸리는 오퍼레이션」 칸의 경로는 2026-09-10 레인 A(통합자)가 채웠다** — 이 요청서가 스스로 적어 둔
> 슬라이스 이름에서 고정 계약(`contracts/`)의 경로를 편 것이고, **주제를 새로 판정하지 않았다.**
> 전달 색인이 이 칸으로 도메인을 읽는다(`scripts/design_inquiries/build_delivery_index.py`).

`common/master/master-write.ts:30,34`는 method/path/body만 지문에 넣고 tx를 callback에 전달하지 않는다. 단순 PrismaClient에는 숨은 tx 전달이 없다. 그대로 쓰면 다른 사용자의 응답 재생·PUT query충돌·업무와 멱등 완료기록 분리가 가능하다.

I-28은 공용 파일을 바꾸지 않고 기존 `IdempotencyService.run(context, tx => work)`를 직접 사용한다. fingerprint는 method/path + actorUserId + PUT eventCode + body, If-Match는 제외한다. 업무와 멱등 기록은 같은 tx로 커밋한다. 같은키 다른주체/이벤트/본문은409이고 응답을 노출하지 않는다.

현재 인증 주체는 활성 app_user 세션이다. 세션 없음·terminal-only는401이고 undefined 주체가 where에서 빠지지 않는다. read는 최초/재생/이미읽음 모두204 무본문이다. preview는 업무표0쓰기이지만 최초 전개 응답을 멱등표에 보존한다.

**계약 검토 요청: 개별 성공/오류 선언에서 빠진 공통 인증401·멱등 헤더400·충돌409를 공통 정책으로 명시할 것인가?** 예컨대 read-all에는 개별 오류가 없고 preview에는409가 없지만 공통 계층의 응답은 필요하다(`app-공통.json:1890,1939,3445,3678`). 기존 ErrorResponse/ConflictResponse를 사용하고 enum을 늘리지 않는다. 이것을 이유로 정상4쓰기 전체를 보류하지 않는다.

알려둘 것: read-all은 화면 기간/이벤트 필터 밖의 자기 미읽음까지 바꾼다. 같은키의 readCount는 과거 응답이며 그 뒤 도착한 알림은 남는다. 배지를 무조건0 또는 과거 count만큼 다시 차감하면 안 된다.

흔적: `I-28.md` §6·R-6·R-8. 각 쓰기 주체409·대상409·완료기록 실패 롤백·재시도, read204 rawbody, read-all 재전송 뒤 새 unread 단언에 문의103 주석을 둔다.
