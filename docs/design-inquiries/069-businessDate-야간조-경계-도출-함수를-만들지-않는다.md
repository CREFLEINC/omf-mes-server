# 69. `businessDate` 의 야간조 경계 도출 규칙이 없다 — 도출 함수를 만들지 않는다 (문의 15 후속)

| 칸 | 내용 |
|---|---|
| **구분** | ⭐ **통보**(§2 1-1 — 2026-09-08 규칙) · 회신을 기다리지 않는다 |
| 걸리는 오퍼레이션 | **횡단** — 원장을 지나는 전건 — `inventory_transaction`·그 파티션·`inventory_transaction_line` 을 쓰는 모든 전기 |
| 구현 상태 | **구현함 — 클라이언트가 보낸 `businessDate` 를 그대로 쓴다. 서버가 도출하지 않는다** |
| 판정 | `coverage-100/README.md` §2 1-1 — **본질(회계 기간)이지만 「안 만드는 쪽」은 데이터를 안 쌓는다** ⇒ 비용 낮음 ⇒ **통보** |
| 되돌릴 때 | 야간조 경계 규칙이 오면 **도출 함수를 그때 만든다.** 그때까지 쌓인 값은 전부 클라이언트가 보낸 값이라 **규칙을 소급 적용해 재계산할 수 있다**(원장 행은 못 고치지만, 어느 행이 어느 규칙으로 들어왔는지 `occurred_at` 으로 재구성된다) |

## 결정

**`business_date` 는 클라이언트가 보낸다. 서버가 수신 시각으로 다시 잡지 않는다**(공유계약 C-8 · `CLAUDE.md`).
⛔ **야간조 경계 도출 함수를 만들지 않는다.**

## 왜

- 서버가 수신 시각으로 다시 잡으면 **자정을 넘긴 오프라인 재전송이 이중 전기**가 된다(C-8 의 원래 근거).
- 야간조 경계 규칙(예: 「06:00 이전은 전날 영업일」)은 **회계 기간 규칙**이다. 도출 함수를 만드는 순간
  **우리가 그 규칙을 정한 것**이 되고, 그 값으로 원장이 쌓이면 **되돌릴 수 없다**.
- 반대로 **안 만들면 아무 값도 쌓이지 않는다** — 클라이언트가 보낸 값이 그대로 남을 뿐이다.
  ⇒ 「안 만드는 쪽」이 §2 2단계 기준 1·4 를 동시에 만족한다.

## 설계팀이 답을 줄 때 필요한 것 하나

> **「하노이 야간조에서 영업일 경계를 몇 시로 보는가」**

그 한 줄이면 도출 함수가 선다. 그때까지는 클라이언트가 보내는 값이 정본이다.
