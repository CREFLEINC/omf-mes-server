# 45. 피킹 지시(`picking_order`/`picking_line`)를 만드는 오퍼레이션이 계약에 0건이고, 예약을 «거는» 자리도 같이 없다 — `M-01-08` 은 반쯤 열리고 M2 체인의 「피킹」 마디가 서버로 이어지지 않는다

| 칸 | 내용 |
|---|---|
| 걸리는 오퍼레이션 | `GET /logistics/picking-orders` · `GET …/{pickingOrderId}` · `POST …/lines/{pickingLineId}:pick` · `GET /inventory/reservations` |
| 구현 상태 | **구현함(I-8 · 조회 2·`:pick`·예약 목록은 계약대로 · 지시 생성·예약 생성·LOT 선출은 지어내지 않았다)** |
| 판정 | `coverage-100/README.md` §2 1단계 **본길**(피킹 없이는 자재 출고가 안 선다) · 계약이 오퍼레이션을 안 줬다 → 2단계 **기준 4**(서버가 배정 축을 지어내지 않는 쪽) — `plan-uiux.md` 579행이 같은 판정 |
| 되돌릴 때 | ① 「서버가 `:release`/요청 발행 때 지시를 만든다」면 `POST` 없이 자동 생성 — 출발 창고·LOT·위치를 고를 규칙(ⓑ·ⓒ)이 먼저 와야 한다 ② 「화면이 `POST /logistics/picking-orders` 로 만든다」면 계약 추가 + 컨트롤러·서비스 1벌(~200) ③ 예약은 답이 온 자리(요청 생성 시 / 지시 생성 시 / 생산오더)에서 코어 `reserve()` 를 만든다(I-8 §3-7 에 보류) |

## 무엇이 문제인가

`contracts/logistics-01자재창고.json` 의 `/logistics/picking-orders*` 는 목록·상세·`:pick` **셋뿐**이다. **`POST /logistics/picking-orders` 가 없다.** `M-01-08` §5-1 표도 「피킹 지시 생성 — ⚠ 누가 만드는지 미정(§8-1)」이 그대로다. DB 실측(2026-09-07): `picking_order`·`picking_line`·`inventory_reservation` 전부 **0행**.

지어낼 수도 없다 — 배정 축이 세 겹으로 빈다.

- ⓐ **출발 창고** — `material_issue_request` 에도 `work_order` 에도 없다. `picking_order.warehouse_id` 가 그것인데 그 행을 만드는 일이 지금 물음이다.
- ⓑ **예약의 차원** — 계약 `InventoryBalance.reservedQty` 는 ⌜출고요청 생성 시 걸리는 예약분⌝(근거 `M-01-08` §5-5)인데, 요청은 «품목·수량·도착 위치»만 갖는다. `picking_line.lot_id`·`location_id` 는 NOT NULL 이고 `reserved_qty` 는 11칸 차원을 요구한다 — 요청 생성 시점엔 걸 «자리»가 없다.
- ⓒ **선출(FEFO/FIFO)** — 계약은 **이미 배정된 라인의 표시 순위**(`PickingLine.pickSequenceRank`)로만 적었다. 「무엇을 골라 라인을 만드는가」는 어디에도 없다. `M-01-08.md:238-239` 는 위반 경고·강제 차단(REQ-PR-0010 확정)을 말하고, 물리엔 `operation_policy`·`item.shelf_life_days`·`fifo_policy_code` 가 실재하나 계약은 0 이다. `pickSequenceRank` 의 모집단도 같은 뿌리다 — 품목당 라인 하나인 지시에서는 언제나 1 이라 「고를 수 있었던 것들 사이」로 읽히는데, 그 모집단이 곧 ⓒ 의 답이다.
- ⓓ **결품 시** — `M-01-08` §5-7 이 「[결품 시] → (U-A1)」로 보내는데 (U-A1) 이 미정의다.
- ⓔ **예약 원천** — `InventoryReservation.sourceDocumentTypeCode` 는 지금 `PRODUCTION_ORDER` 하나다(`W-02-01` §5-4 가 세운 축). 04 계약의 `:pick` 이 「이 피킹의 결과로 예약을 걸고 푼다」로 자기 근거(`M-01-08` §5-5 ⌜출고요청 생성 시 예약⌝)를 잘못 인용했다 — 01 vs 04 의 충돌이 아니라 **04 의 인용 오류**로 읽었다. 번호를 매기는 쪽도 없다(`numbering.service.ts` `DEFAULT_PREFIX` 에 `PICKING_ORDER` 없음 · `plan-api.md:1092` 「출고요청이 만든다」는 틀린 문장).

⇒ 오늘 `M-01-08` 은 **반쯤 열린다**(`plan-uiux.md` §9-1 #7) · `GET /inventory/reservations` 는 **언제나 빈 목록** · `plan.md` §2 M2 체인 ⌜`:release` → **피킹** → 출고 → 생산창고 입고⌝ 의 «피킹» 마디가 서버 오퍼레이션으로 이어지지 않는다. `:pick` 은 e2e 픽스처의 직접 INSERT 로만 도달한다.

## 지금 서버는

- 조회 2·`:pick`·`GET /inventory/reservations` 는 계약 그대로. 코어 `pick()`/`consume()` 은 있고 **`reserve()` 는 없다**(I-8 §3-7 — 거는 자리가 정해지면 그때).
- `:pick` 은 `picking_line.inventory_reservation_id` 가 NULL 이면 「예약 없음」 갈래로 `picked_qty` 만 올린다 — 오늘은 언제나 그쪽이다(흔적 주석 `picking-pick.service.ts`).
- 지시 생성·예약 생성·LOT 선출 — **없다.** 답이 오면 위 「되돌릴 때」 ①~③.

흔적: `docs/coverage-100/slices/I-8.md` §5·§3-7·R-22 · `picking-pick.service.ts:49`(⛔ 예약을 걸지 않는다)·`:150`(예약 NULL 갈래) · `material-issue-request.service.ts:44`(요청 발행이 예약·지시를 만들지 않는다) · 「알려둘 것」 ⓕ(`pickSequenceRank` 모집단) 는 이 문의로 흡수.
