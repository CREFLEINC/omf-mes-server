# 23. P/O 의 `status_code` 를 `REGISTERED` 밖으로 옮기는 오퍼레이션이 없다 — 그래서 상신 뒤가 잠기지 않는다

| 칸 | 내용 |
|---|---|
| 걸리는 오퍼레이션 | `POST /logistics/purchase-orders` · `PUT /logistics/purchase-orders/{id}` · `PUT …/{id}/lines` · `POST …/{id}:request-approval` · `GET /logistics/purchase-orders?statusCode=`(I-2 · 7건 중 5건) |
| 구현 상태 | **구현함(계약 문자 그대로)** — 등록은 `REGISTERED` 로 서고 상신은 상태를 옮기지 않는다. `transitions.ts` 에 `logistics.purchase_order.status_code` 축을 **등록하지 않는다**(전이가 0건) |
| 판정 | §2 1단계 = 본길처럼 보이나 **계약 문자가 답을 준다**(옮길 값이 목록에 없다 → 지어내야만 옮길 수 있다) · 2단계 기준 1(상태를 쓰지 않는 쪽)도 같은 결론 · 3단계 흔적: e2e `상신 — P/O 의 status_code 는 REGISTERED 그대로다` |
| 되돌릴 때 | 전이가 정해지면 `transitions.ts` 에 축 한 벌 + 그 전이를 일으키는 오퍼레이션(없으면 계약 추가). 기존 행은 전부 `REGISTERED` 라 백필이 「전기된 것을 골라내는」 일이 된다 — 지금은 골라낼 기준도 없다 |

## 무엇이 문제인가 — 갈래 셋

`purchase_order.status_code` 의 값 목록은 확정됐다(`LOGISTICS_DOCUMENT_STATUS` 4값 · `registry-system` · 사용자 결정 2026-09-02 · `W-01-11` §4-A 도 같다). **그런데 그 값으로 옮기는 길이 없다.**

**① `POSTED` 에 도달할 경로가 계약에 없다.** P/O 7 오퍼레이션에 `:post` 가 없다(전수 실측). 승인이 끝나도, 초과분이 그 P/O 에 귀속돼도 상태는 `REGISTERED` 그대로다. `W-01-13`(물류 문서 진행현황 · FR-IM-086 「P/O …의 처리상태와 수량을 조회」)의 P/O 행은 **1차 내내 「등록」 한 값**만 보인다.
※ 취소 두 값(`CANCEL_REQUESTED`·`CANCELLED`)은 **묻지 않는다** — `W-01-13` §6 이 「취소 경로가 없는 유형은 버튼 비활성 + `cancelBlockedReasonCode=TYPE_NOT_CANCELABLE`」로 이미 답했고 계약도 「취소 실행 경로가 있는 것은 입하·입고·출고 3종뿐」이라 적었다.

**② 화면의 상태 드롭다운이 서버로 갈 길이 없다.** `W-01-11` §4-A 는 상태를 **필수 ✅ · 입력 「선택」**으로 그렸는데, 쓰기 스키마 둘(`PurchaseOrderCreate`·`PurchaseOrderUpdate`)에 `statusCode` 칸이 **없다**(실측). 계약은 반대로 「`purchaseOrderNo` 와 `statusCode` 는 서버가 정한다」라 적었다. 화면에서 그 드롭다운을 **지우는가**?

**③ 상신한 P/O 를 잠그는 축이 없다.** 계약 `PUT` 은 「작성중 상태에서만 허용한다」인데 상태가 `REGISTERED` 밖으로 못 가므로 **이 가드가 아무것도 막지 않는다**. 여기에 `:request-approval` 이 202 를 돌려주며 ETag 를 안 내려 `version_no` 도 올리지 않으므로(낙관적 잠금도 안 걸린다), **승인 대기 중에 헤더·라인을 얼마든지 고칠 수 있다.**
그리고 결재함은 그것을 못 본다 — `W-CO-09` §5-2 「대상 상세를 그리지 않는다」 · 목록의 업무 값은 `reason` 하나 · 「대상 화면에서 보기 ↗」는 8 유형 전건 비활성(문의 019). ⇒ **승인자가 본 것과 승인된 것이 달라질 수 있고, 다르다는 사실이 어느 화면에도 나타나지 않는다.**

## 지금 서버는

- 등록 시 `REGISTERED` 고정 · 상신은 상태를 안 옮긴다 · 수정 가드는 「`REGISTERED` 가 아니면 400 `STATE_LOCKED`」로 두되 1차에서는 늘 통과한다.
- 승인 진행은 `app.approval_request.status_code`(`PENDING`·`APPROVED`·`REJECTED`)가 진다.

## 요청

1. **`POSTED` 로 옮기는 주체·시점**을 정해 주십시오 — 승인 완료인가, 초과분 귀속(W-01-03)인가, 아니면 P/O 는 1차에서 `REGISTERED` 만 쓰는 것이 맞는가(그렇다면 `W-01-13` 의 상태 열 문구를 그렇게 적겠습니다).
2. **`W-01-11` §4-A 의 상태 드롭다운**을 읽기 전용으로 바꾸거나 지워 주십시오(계약이 서버 소유로 못박았습니다).
3. **승인 대기 중 수정을 막을지** 정해 주십시오. 막는다면 값이 하나 더 필요합니다(예: 상신 시 `POSTED` 가 아닌 별도 값) — 지금 4값으로는 「상신했다」를 표현할 자리가 없습니다.

우리 권고안(회신이 없으면 이대로 갈 값): **1 = P/O 는 `REGISTERED` 만 쓴다 · 2 = 읽기 전용 · 3 = 막지 않는다.** 이유: 값을 지어내지 않는 쪽이고(§2 2단계 기준 4), 나중에 값이 정해지면 전이표 한 벌과 가드 한 줄로 조일 수 있습니다(허용→거부는 깨는 변경이지만, 이 자리는 「승인 중 수정」이라는 예외 경로라 현장 데이터가 쌓이기 전에 조이는 편이 쌉니다).
