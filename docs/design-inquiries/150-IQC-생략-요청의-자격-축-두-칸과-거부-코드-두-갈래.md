# 150. `:request-iqc-skip` 의 「자격 축」을 서버가 **두 칸**으로 정했고, 거부 코드가 **둘로 갈린다**

> 계약이 「**입하돼 수입검사 대기인** LOT 에 대해」라고 산문으로만 적고, **그 조건을 어기는 요청의 응답을 한 줄도 적지 않았다.** 모든 호출이 이 갈래를 지나므로 비워 둘 수 없다.

| 칸 | 내용 |
|---|---|
| **구분** | ⭐ **통보**(§2 1-1 — 2026-09-08 규칙) · 회신을 기다리지 않는다 |
| 걸리는 오퍼레이션 | `POST /trace/lots/{lotId}:request-iqc-skip` |
| 구현 상태 | **구현 예정(I-18 · 계획 PR 만 · 오늘 코드 0줄)** — 계획서 `docs/coverage-100/slices/I-18.md` §0 자리 1 · §3-1 ⓑ · §4-3 표 8·9행 |
| 판정 | `coverage-100/README.md` §2 **1단계 가장자리** → **0단계 선례**(같은 자원의 형제 `POST /trace/lots/{lotId}:complete` 가 «똑같은 두 축»을 이미 갈라 놓았다) → **2단계 기준 2**(거부하는 쪽으로 판정 — 거부→허용은 호환 완화라 되돌리기 싸다) |
| 되돌릴 때 | 「아무것도 안 본다」로 오면 서비스에서 **판정 두 줄 삭제** + e2e 2건 삭제(≈ −25줄). 「보류까지 봐야 한다」로 오면 조건 한 줄 + e2e 픽스처가 보류 축을 세워야 해 ≈ +40줄. **코드만 바뀌고 마이그레이션·스키마는 어느 쪽이든 0** |

## 무엇이 문제인가

계약이 자격을 **산문으로만** 적었다.

- `contracts/logistics-01자재창고.json:6508` — 「**입하돼 수입검사 대기인** LOT 에 대해 … 요청을 만들기만 하고 한도는 승인자가 정한다. 결재선이 없으면 400(code=`ROUTE_NOT_FOUND`)이다」.
- 그런데 **그 조건을 어긴 요청의 응답이 없다.** 이 오퍼레이션의 `responses` 는 202·400·403·409 넷인데, 400 의 `description` 은 결재선·본문 축만 적고 「입하 LOT 이 아니다」·「수입검사 대기가 아니다」를 **한 줄도 적지 않았다**.

「입하돼」와 「수입검사 대기」는 물리에서 **서로 다른 두 칸**이다.

- 「입하돼」 → `trace.lot.source_type_code`. 입하 사슬로 태어난 LOT 은 `'INBOUND_RECEIPT_LINE'` 이다.
- 「수입검사 대기」 → `trace.lot.status_code`. `LOT_STATUS` 4값(`NORMAL`·`DEFECTIVE`·`INSPECTION_PENDING`·`SCRAPPED`) 중 `'INSPECTION_PENDING'` 이고, 등록 코어가 입하 LOT 을 그 값으로 세운다(`src/core/lot/lot-registry.service.ts:24`·`:87`).

⇒ 두 칸이므로 **거부 사유도 둘**이다. 화면(`M-01-13` POP)이 「이 LOT 은 입하 LOT 이 아닙니다」와 「이미 검사가 끝났습니다」를 구분해 보여야 하는데, 계약은 그것을 가를 축을 주지 않았다.

## 지금 서버는

**아직 없다.** 계획이 정한 동작은 다음과 같다.

- 대상 LOT 을 `FOR UPDATE` 로 잠근 «뒤» **두 칸을 따로 본다**(경합 몫이라 잠금 뒤가 맞다).
- ⭐ **두 축의 코드가 다르다** — 같은 자원의 형제가 이미 그렇게 갈라 놓았기 때문이다:

| 위반한 칸 | 응답 | 형제의 선례 |
|---|---|---|
| `source_type_code !== 'INBOUND_RECEIPT_LINE'` | **400 `INVALID`** | `src/trace/lot/lot-complete.service.ts:66-69` — `:complete` 가 「생산 LOT 만」을 원천유형으로 갈라 `ERROR_CODE.INVALID` 를 낸다 |
| `status_code !== 'INSPECTION_PENDING'` | **400 `STATE_LOCKED`** | 같은 파일 `:71-73` — 상태 위반은 `STATE_LOCKED` |

  `:complete`(생산 LOT 완료)와 `:request-iqc-skip`(입하 LOT 검사 생략)은 **같은 자원의 거울**이다. 한쪽이 「생산 LOT 만」을 원천유형으로 막는다면 다른 쪽의 「입하돼」도 같은 축·같은 코드다.

- ⛔ **열린 보류(`lot_hold.reason_code='INCOMING_INSPECTION_WAIT'`)는 보지 않는다.** 등록 코어가 입하 LOT 에 그 보류를 걸지만(`lot-registry.service.ts:96-104`), 검사 확정(`:confirm`, I-19)이 그 보류를 **닫는다**. 보류를 자격 축에 넣으면 「검사 «중»이라 보류가 이미 닫힌」 정당한 LOT 이 막힌다.
- ⛔ **대상 행에는 아무것도 안 쓴다** — `trace.lot` 에 `approval_request_id` 칸이 없고, `plan.md` §5 규칙 12 가 「`IQC_SKIP` 은 FK 를 쓰지 않는다 — 정본은 다형 축」으로 이미 못 박았다.
- 새 `ERROR_CODE` 는 **0건**이다. 둘 다 실재하는 코드다.

## ⇒ 알리는 것

1. **자격은 두 칸(`source_type_code` + `status_code`)이고 둘 다 본다.** 보류 유무는 안 본다.
2. **거부 코드가 갈린다** — 입하 LOT 이 아니면 400 `INVALID`, 수입검사 대기가 아니면 400 `STATE_LOCKED`. 화면은 이 둘로 문구를 가르면 된다.
3. 계약에 되돌릴 것: `:request-iqc-skip` 의 **400 description 에 이 두 갈래를 한 줄씩** 적어 주시면 서버 판정과 계약 문자가 같아진다.
