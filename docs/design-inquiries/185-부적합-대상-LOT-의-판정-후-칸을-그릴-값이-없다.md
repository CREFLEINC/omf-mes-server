# 185. 부적합 대상 LOT 의 **「(판정 후)」 칸을 그릴 값이 없다** — `qualityStatusBefore/AfterCode` 가 언제나 같다

**구분: 통보**(회신을 기다리지 않는다 — 계약 문자대로 구현했고, 그 결과 화면 한 칸이 죽습니다)

| 칸 | 내용 |
|---|---|
| 걸리는 오퍼레이션 | `POST /quality/nonconformances`(등록) · `GET /quality/nonconformances/{nonconformanceId}`(상세 · `lots[]`) |
| 구현 상태 | **구현 예정(I-21 PR ⑥)** — 계획서 `docs/coverage-100/slices/I-21.md` §1-4-1 · §3-1 |
| 판정 | §2 **1단계 본길** → **계약 문자를 먼저 따른다**(「부적합 등록 «전»/«후»」) · **2단계 기준 1**(상태를 안 쓰는 쪽) |
| 되돌릴 때 | 처분 판정 저장이 `nonconformance_lot.quality_status_after_code` 를 **UPDATE 하는 한 줄** |

## 무엇이 문제인가

`NonconformanceLot` 은 두 칸을 **둘 다 required** 로 요구합니다:

| 칸 | 계약 설명 |
|---|---|
| `qualityStatusBeforeCode` | 「부적합 등록 **«전»** 의 LOT 품질 상태」 |
| `qualityStatusAfterCode` | 「부적합 등록 **«후»** 의 LOT 품질 상태」 |

그런데 **부적합 등록은 LOT 을 옮기지 않습니다.** 계약이 등록 전이를 어디에도 적지 않았고(`POST /quality/nonconformances` 설명·`W-04-07` 전체), LOT 을 옮기는 것은 **처분 판정 저장**입니다(`quality-03품질.json:2460`).

⇒ **두 칸이 언제나 같은 값**이 됩니다(등록 시점의 `trace.lot.status_code`).

## ⚠ 화면 한 칸이 죽습니다

`W-03-10` §3 목업 ② 가 **그 두 칸으로 전/후 화살표**를 그립니다:

```
대상 LOT     LOT-…0088  320 EA   불량 → (판정 후)
```

⇒ 우리 구현에서는 그 자리가 **「불량 → 불량」**이 됩니다.

`quality.nonconformance_lot` 은 **기록 전용 표**입니다(감사 칸 `created_at`·`created_by` 뿐 · `updated_at` 없음 · `version_no` 없음). 처분 판정이 그 칸을 나중에 갱신하는 것은 **계약 문자와 어긋납니다** — 계약이 「등록 «전»/«후»」라 적었지 「처분 «전»/«후»」라 하지 않았습니다.

## ⇒ 우리가 정한 것

- **등록 시점의 `lot.status_code` 를 두 칸에 «그대로» 넣습니다.** 계약 문자 그대로입니다.
- ⛔ **처분 판정이 그 칸을 갱신하지 않습니다** — 기록 전용 표이고 계약 문자가 「등록」을 가리킵니다.
- ⛔ **등록이 LOT 을 옮기지도 않습니다** — 계약에 근거가 0이고 §2 2단계 기준 1(재고·원장·상태를 안 쓰는 쪽)입니다.

## 📨 정해 주십시오 — 셋 중 하나

1. **화면을 고친다** — `W-03-10` ② 의 「(판정 후)」를 **처분 결정 목록**에서 그린다(그 목록은 이미 상세에 옵니다). ⇒ 서버 변경 **0**.
2. **칸의 뜻을 「처분 전/후」로 바꾼다** — 그러면 처분 판정 저장이 `quality_status_after_code` 를 **UPDATE** 해야 하고, 그 표가 **기록 전용을 벗어납니다**(감사 칸이 필요합니다).
3. **칸을 하나 늘린다** — `disposition_status_after_code` 같은 자리를 두면 등록 이력과 처분 결과가 둘 다 남습니다.

⚠ **부분 처분이면 2·3 도 한 값으로 안 담깁니다** — 160 재작업 + 40 폐기면 도착이 둘입니다(**통보 089 §6**). 두 물음은 함께 보셔야 합니다.
