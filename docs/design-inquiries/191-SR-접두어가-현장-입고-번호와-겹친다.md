# 191. 출하작업지시 번호 접두어 **`SR` 가 현장 입고 번호와 겹친다** — 두 계약 example 이 둘 다 `SR-` 다

**구분: 통보**(회신을 기다리지 않는다)

| 칸 | 내용 |
|---|---|
| 걸리는 오퍼레이션 | `POST /logistics/shipment-requests`(04) · `POST /logistics/shopfloor-receipts`(01 · **이미 배포됨** · I-9) |
| 구현 상태 | **구현 예정(I-22 PR ⑤)** — `SHIPMENT_REQUEST: 'SR'` 을 `DEFAULT_PREFIX` 에 더한다 |
| 판정 | §2 **0단계**(계약 example 이 형식을 준다) — 계약 문자를 따른다 |
| 되돌릴 때 | 접두어 한 글자. 다만 **이미 발번된 번호는 데이터로 남습니다** — 그래서 미리 알립니다 |

## 실측

| 표 | 계약 example | 접두어 |
|---|---|:-:|
| `logistics.shipment_request.shipment_request_no` | `SR-2026-0813-0108` | **SR** |
| `logistics.shopfloor_receipt.shopfloor_receipt_no` | `SR-2026-000077` | **SR** |

`src/core/numbering/numbering.service.ts:24` 에 **`SHOPFLOOR_RECEIPT: 'SR'` 이 이미 있습니다**(I-9 가 계약 example 대로 넣었습니다).
저장소의 기본 패턴은 `{PREFIX}-{YYYYMMDD}-{SEQ4}` 이고 카운터는 **문서 유형별**이므로, 같은 날 둘 다 첫 건이면 **`SR-20260909-0001` 이 두 표에 하나씩** 생깁니다.

DB 는 막지 않습니다 — `business_no_t` UNIQUE 가 **표마다** 걸려 있어 제약 위반이 아닙니다. 막히는 것은 **사람**입니다: 현장에서 「SR-20260909-0001」을 말하면 그것이 출하작업지시인지 현장 입고인지 알 수 없습니다.

## ⇒ 우리가 정한 것

**계약 문자를 따릅니다** — 04 는 `SR-{YYYYMMDD}-{SEQ4}` 를 씁니다. 이미 배포된 I-9 의 접두어를 바꾸면 **발번된 번호와 새 번호의 규칙이 갈리므로** 그쪽은 손대지 않습니다.
예약 번호는 **`RS`** 입니다 — 01 계약 `InventoryReservation.reservationNo.example = 'RS-2026-000144'` 가 근거입니다.

## 📨 알려 드리는 것 — **문의 14(채번 규칙 없는 표) 표에 두 행을 더해 주십시오**

| 표 | 우리가 쓰는 형식 | 기간 축 |
|---|---|---|
| `logistics.shipment_request` | `SR-{YYYYMMDD}-{SEQ4}` | **`requestedShipDate`**(클라이언트가 보낸 날짜 — C-8) |
| `inventory.inventory_reservation` | `RS-{YYYYMMDD}-{SEQ4}` | ⚠ **서버 UTC 날짜**(`:pick` 본문에 날짜 칸이 0개 — 문의 197) |

⭐ **접두어를 겹치지 않게 정해 주시면 그대로 따르겠습니다.** 겹침을 푸는 값은 `numbering_rule` 한 행이라 배포 없이 바뀝니다.
