# 124. 부분 도착한 이동을 닫는 길이 0 이고 잔여가 「운송중」 차원에 영원히 남는다 — 게다가 그 전표가 미완 목록에서 사라진다

| 칸 | 내용 |
|---|---|
| **구분** | **통보** — 재도착 거부는 완화가 싸고, 잔여는 조정으로 턴다(데이터 소실 0) |
| 걸리는 오퍼레이션 | `POST /logistics/stock-transfers/{stockTransferId}:arrive`(부수: `GET /logistics/stock-transfers?inTransitOnly=true`) |
| 구현 상태 | **미구현**(I-13 PR ③ 예정) — 반출 등록과 조회 3건만 병합됐다(`main`) |
| 판정 | `coverage-100/README.md` §2 1단계 **가장자리**(둘째 `:arrive` 호출에서만 갈린다) → 2단계 **기준 2**(거부하는 쪽) + **기준 5**(새 개념 0 vs 2 — 「도착 회차」·「회차별 원장 번호·멱등키」) |
| 되돌릴 때 | 「재도착을 열라」면 `received_at IS NOT NULL` 자물쇠 한 줄 삭제 + **델타 전기**와 회차별 번호·멱등키 규약 신설(원장 축이라 코어 PR) · 「잔여를 조정으로 털라」면 서버 변경 0 |

## 무엇이 문제인가

ⓐ 계약이 부분 도착을 **명시적으로 허용한다** — `StockTransferArrive.description` 「도착 확정. **반출한 수량 이하만 받을 수 있다.** 근거: M-01-10 §5-6」(`contracts/logistics-01자재창고.json:14083` · path `:5710`), `receivedQty` 의 `minimum` 은 **0** 이다. 물리 CHECK 도 `ck_stock_transfer_qty CHECK (shipped_qty <= requested_qty AND received_qty <= shipped_qty)` 로 그것을 받는다(`prisma/migrations/20260727000000_baseline_physical_model_v3/migration.sql:2215-2217`).
ⓑ 그런데 **되풀이 호출을 계약이 한 줄도 적지 않았다.** `receivedQty` 는 `x-source-column: received_qty` 로 칸에 직접 대응할 뿐 **그 회차의 양인지 누계인지** 갈라 주지 않는다. 반면 통합 계획서 전이표 초안은 「부분 도착은 상태를 안 옮긴다 — `received_qty` **합**이 담고 전량에서만 `POSTED`」라 **누적 재도착을 전제**했다(`docs/coverage-100/plan-api.md:762` — 3관점 재검토 R-3 이 「계약 근거가 0」으로 확인해 그 뒤 절반을 지웠다). 계약과 계획서 초안이 갈렸고, **가른 근거가 계약에 없다**.
ⓒ 서버는 §2 절차로 **한 번만 받기로** 했다(둘째 `:arrive` = 400 `STATE_LOCKED`). ⚠ 그 **대가**: 부분 도착한 전표는 `REGISTERED` 인 채 `received_at` 이 차 있고 **닫을 오퍼레이션이 0건**이다 — 취소도 없다(문의 **120**).
ⓓ 남은 수량은 `inventory_balance` 의 `{도착 창고, 계획 도착 위치, IN_TRANSIT}` 차원에 남는데 **그 위치는 서버가 골랐다** — `inventory.inventory_balance.location_id` 가 **NOT NULL** 이라(`baseline/migration.sql:1097`) 「위치 없음」을 담을 자리가 물리에 없고, `mdm.location` 에 「가상 위치」 개념도 없다. 계약은 원장 끝점 4칸을 요청·응답 어디에도 싣지 않아 화면이 이 위치를 **보지도 고르지도 못한다**.
ⓔ 화면이 같은 구멍을 이미 적었다 — `M-01-10` §8 #6 「**이동 중 분실·손상** 🟠 — 도착 < 반출로 표현되나 **사유 축이 아직 없다**(되살리기 잔여 · §I-41 계열)」(`.design-reference/…/screens/01/M-01-10-재고이동불량반출.md:256-265`).
ⓕ ⭐ **부분 도착한 전표가 미완 목록에서 «사라진다».** 화면 §5-4 는 「화면 진입 시 **미완 이동(반출됨·미도착)을 먼저 보인다**」를 되찾기의 **유일한 수단**으로 규정했다(같은 파일 `:191-205`). 그런데 목록의 `inTransitOnly` 축은 `shipped_at IS NOT NULL AND received_at IS NULL` 이고(계약 정의 그대로 · `stock-transfer-query.service.ts`), 부분 도착이 `received_at` 을 채우므로 **그 전표는 미완 목록에서 빠진다**. ⇒ 닫는 길이 없는 데다 **찾는 길까지 없다**.

## 지금 서버는

- `:arrive` 는 아직 열려 있지 않다. 열 때의 계획: `received_at IS NOT NULL` 이면 **400 `STATE_LOCKED`** · `receivedQty > shipped_qty` 이면 **400 `RANGE`**(field `lines[i].receivedQty`) · 본문에 안 실린 라인은 안 건드린다 · `receivedQty = 0` 인 라인은 원장 라인을 만들지 않는다.
- 전량 도착일 때만 `REGISTERED → POSTED` 로 옮긴다(전이 하나).
- 반출 전기는 이미 병합됐고 잔액을 `{도착 창고, 라인의 `to_location_id`, `IN_TRANSIT`}` 에 세운다(`src/logistics/stock-transfer/transfer-posting.ts:26,158-161`).

⇒ **묻는 것**: 재도착(둘째 `:arrive`)을 열 것인가 — 열면 `receivedQty` 가 **회차분인지 누계인지** 계약이 갈라 주어야 한다 · 열지 않으면 남은 `IN_TRANSIT` 잔여를 **재고 조정으로 털게 할 것인가**, 그리고 부분 도착 전표를 되찾을 목록 축(분실 사유 축 포함)을 세울 것인가.
