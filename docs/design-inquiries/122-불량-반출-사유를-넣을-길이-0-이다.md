# 122. 불량 반출 사유를 넣을 길이 0 이다 — 응답에는 `reasonCode` 가 있는데 요청에는 없다

| 칸 | 내용 |
|---|---|
| 걸리는 오퍼레이션 | `POST /logistics/stock-transfers` · `GET /logistics/stock-transfers` · `GET …/{stockTransferId}` · `GET …/{stockTransferId}/lines` |
| 구현 상태 | **구현·병합함**(`main`) — `reasonCode` 를 **받지 않고**, 응답에는 물리 값(오늘은 언제나 널)을 그대로 싣는다 · `remarks` 는 뷰에서 뺐다 |
| 판정 | `coverage-100/README.md` §2 1단계 **가장자리**(`transferTypeCode='DEFECT_RETURN'` 호출에서만 갈린다) → 2단계 **기준 3**(스키마를 안 늘린다)·**기준 4**(값을 조용히 도출하지 않는다) |
| 되돌릴 때 | 「열라」면 `StockTransferCreate` 에 `reasonCode`(+`remarks`) 프로퍼티 추가 · 서버는 저장 한 줄 · 마이그 **0**(칸이 이미 있다) · 시드에 `STOCK_TRANSFER_REASON` 값 필요 |

## 무엇이 문제인가

ⓐ 계약과 화면이 **사유 칸의 «동작»을 값에 걸었다.** `StockTransfer.transferTypeCode.description` 원문(`contracts/logistics-01자재창고.json:13973`): 「재고 이동 유형 — 일반 이동(NORMAL) · 불량 반출(DEFECT_RETURN). ⭐ M-01-10 §4 가 「**불량 반출일 때만 사유 칸을 연다**」로 «동작»을 이 값에 걸었다 — 값이 늘면 화면 분기가 따라가지 못한다.」
ⓑ 그런데 `StockTransferCreate` 프로퍼티는 **10개**이고 그중 `reasonCode` 가 **없다**(실측: `transferTypeCode`·`fromBusinessUnitId`·`toBusinessUnitId`·`fromWarehouseId`·`toWarehouseId`·`requestedAt`·`businessDate`·`occurredAt`·`lines` — `contracts/…:14141`). 응답 `StockTransfer` 프로퍼티 12에는 **`reasonCode` 가 있다**(`contracts/…:13973`). ⇒ **읽기 전용 칸**이 됐다 — 화면이 고를 수는 없고 볼 수만 있다.
ⓒ 그 `reasonCode` 의 description 은 정반대로 **쓰기를 전제한다** — 「재고 이동 사유 — 불량 반출·분실 사유를 코드로 받는다. ⭐ 「불량 반출이 몇 건인가」를 세려면 자유 텍스트가 아니라 코드 축이어야 한다(공유계약 §I-41 · omf-mes#84)」(같은 자리).
ⓓ 물리 칸 `logistics.stock_transfer.reason_code`·`remarks` 는 실재하지만(`prisma/schema.prisma:1432-1433`) **재고 재등록(04)** 을 위해 선 칸이고, 그 마이그레이션 주석이 「이동이 이 표의 본래 쓰임이다 — **재등록만 사유를 싣는다**」라 직접 적었다(`prisma/migrations/20260901110000_stock_transfer_reason_remarks/migration.sql:20`).
ⓔ 값 목록도 비어 있다 — 시드 `STOCK_TRANSFER_REASON` 은 그룹만 있고 `values: []` 다(`prisma/seed.ts:1235-1238` · psql 실측 값 0행). `x-code-key: CD-STOCK-TRANSFER-REASON` 이 가리킬 값이 오늘 하나도 없다.
ⓕ `remarks` 는 요청·응답 **둘 다에 없다** — 이 6건은 그 칸을 읽지도 쓰지도 못한다.
ⓖ 화면은 이 구멍을 이미 세 번 올렸다 — `M-01-10` §4-B 「⚠ **사유 컬럼이 없다.** `goods_receipt`·`goods_issue`는 `reason_code`를 갖는데 `stock_transfer`는 `transfer_type_code`뿐이다」(`.design-reference/…/screens/01/M-01-10-재고이동불량반출.md:102`) · §9 3번 「**「사유를 기록한다」가 확정인데 컬럼이 없는 곳이 늘고 있다** — `putaway_task`(적치 사유 · `M-01-07`)에 이어 `stock_transfer`」(`:271`) · §8 #4 「**자재 불량 반출의 사유를 담을 자리가 없다** — `defect_record`는 `work_order_id NOT NULL`이라 생산 불량 전용 … `M-01-07` §5-1과 묶어 이슈」(`.design-reference/…/screens/01/M-01-10-재고이동불량반출.md:256-265`) · `W-04-11` §5-5 가 omf-mes#84 의 「세 번째 사용처」로 적었다.

## 지금 서버는

- `POST /logistics/stock-transfers` 는 `reasonCode`·`remarks` 를 **받지 않는다**(계약 프로퍼티에 없으므로 스키마를 늘리지 않았다) — 알 수 없는 칸이 와도 조용히 버린다.
- `transferTypeCode` 는 `STOCK_TRANSFER_TYPE` 값 목록 대조만 한다(없으면 400 `INVALID`) — `DEFECT_RETURN` 이라고 사유를 요구하지 **않는다**(`src/logistics/stock-transfer/stock-transfer.service.ts:204`).
- 응답 뷰는 `reasonCode: row.reason_code` 를 그대로 싣는다(`stock-transfer-view.ts:63`) — 이 6건으로 만든 전표는 **언제나 널**이다. `remarks` 는 응답 스키마에 없어 뷰에서 뺐다(`stock-transfer-view.ts:8`).

⇒ **묻는 것**: `StockTransferCreate` 에 `reasonCode`(+`remarks`)를 열 것인가 — 열면 `DEFECT_RETURN` 일 때 필수로 조일 것인가 · 그리고 `STOCK_TRANSFER_REASON` 초기값 목록을 누가 정하는가(시드가 비어 있어 오늘은 고를 값이 0개다).
