# 140. 재포장 이벤트를 담을 표가 계약에 없다 — 「데이터 모델 담당에게 통지 — 기다리지 않는다」가 세 곳에 그대로 살아 있어 서버가 표 둘을 신설했다

| 칸 | 내용 |
|---|---|
| **구분** | **통보** — 계약 `x-internal-note` 가 「데이터 모델 담당에게 통지 — **기다리지 않는다**」로 세 곳에 적었다. 그 문장이 곧 통보 지시다 |
| 걸리는 오퍼레이션 | `PUT /inventory/handling-units/{handlingUnitId}/contents` · `GET /inventory/handling-units/{handlingUnitId}/repack-events` |
| 구현 상태 | **구현 예정(I-16 · 계획만 병합됨 · 오늘 코드 0줄 · 마이그레이션도 아직 없다)** |
| 판정 | `coverage-100/README.md` §2 **0단계 선례** — `plan.md` §0 #7 「물리가 계약을 따른다」(`Printer.status` 선례) · README §5 「물리 모델과 계약이 다르면 물리를 고친다」 |
| 되돌릴 때 | 「기존 표를 쓰라」면 마이그 1파일을 버리고 라인 4칸 추가 + 헤더 NOT NULL 3칸 완화 + CHECK 1건 삭제 + `moved_qty` CHECK 완화 = **물리 변경 9건**(그중 CHECK 삭제는 두 릴리스 규칙에 걸린다). 「신설이 맞다」면 되돌릴 것 0 |

## 무엇이 문제인가

ⓐ **계약이 저장처를 서버에 넘겼고, 그 문장이 세 곳에 그대로 있다.** 원문 그대로:

- `contracts/logistics-01자재창고.json:1448`(`PUT …/contents` description) — 「⭐ 결정 13 되살림(2026-08-30) — 이 치환은 서버가 HandlingUnitRepackEvent(헤더) + Line(수량 변경 전/후)을 함께 기록한다. 신규 발번·새 라벨 대상은 이 이벤트가 아니라 POST /inventory/handling-units(P-04-04)가 별도로 만든다. **저장 테이블은 데이터 모델 담당에게 통지 — 기다리지 않는다.** 근거: M-04-03 §5-2」
- `contracts/logistics-01자재창고.json:1542`(`GET …/repack-events` description) — 「… 누가·언제·왜 재구성했는지와 수량 변경 전/후를 담는다. **저장 테이블은 데이터 모델 담당에게 통지 — 기다리지 않는다.** 근거: M-04-03 §5-2」
- `contracts/logistics-01자재창고.json:8726`(`HandlingUnitRepackEvent` 스키마 description) — 「포장 재구성 사건 헤더 … **저장 테이블은 데이터 모델 담당에게 통지 — 기다리지 않는다.** 근거: M-04-03 §5-2」

ⓑ **이름이 비슷한 기존 표는 계약 모양을 못 담는다.** `inventory.handling_unit_reconfiguration(+_line)` 과 칸을 전수 대조한 결과(`prisma/migrations/20260826000000_data_model_v4/migration.sql:520-546` · `prisma/schema.prisma:3980-4021`):

- 라인 필수 6칸(`contracts/logistics-01자재창고.json:8770`) 중 **4칸이 없다** — `handling_unit_id`·`role_code`·`qty_before`·`qty_after`(`migration.sql:539-545`).
- 헤더 NOT NULL 3칸이 **계약에 원천 0** — `reconfiguration_no`(UNIQUE · 채번 규칙도 없다)·`source_handling_unit_id`·`target_handling_unit_id`·`reason_code`(`migration.sql:527-531`).
- ⛔ 결정적인 것은 CHECK 다 — `CONSTRAINT ck_handling_unit_reconfiguration_distinct CHECK (source_handling_unit_id <> target_handling_unit_id)`(`migration.sql:534-535`). 계약의 **대표 경로가 취급 단위 «하나»짜리 사건**(`PUT …/contents` 는 한 HU 의 구성을 치환한다)이라 `source = target` 이 되어 **INSERT 가 구조적으로 실패한다.** 화면도 같은 말을 한다 — 「분할 잔량은 원 포장 번호를 그대로 씁니다」(`M-04-03-포장재구성스캔.md:159`).
- 헤더의 `source`→`target` 두 칸으로는 **합병(원 포장 여럿)을 못 담는다** — 화면이 라인 축임을 명시했다: 「`HandlingUnitRepackEventLine`의 `roleCode=SOURCE` 행들이 그 출처를 남긴다」(`M-04-03-포장재구성스캔.md:173`).

ⓒ **재사용하면 계약에 없는 NOT NULL 칸을 영구히 지어내야 한다.** `handling_unit_reconfiguration_line.uom_id bigint NOT NULL REFERENCES mdm.uom` 인데 계약 라인에 `uomId` 자체가 없고(`:8770` required 6칸 — `handlingUnitId`·`roleCode`·`itemId`·`lotId`·`qtyBefore`·`qtyAfter`), `moved_qty CHECK (moved_qty > 0)` 는 「변화 없는 줄」과 「전량을 옮긴 원 포장의 잔량 0」을 못 담는다.

## 지금 서버는

- **아직 아무것도 없다.** I-16 7 오퍼레이션은 계획만 병합됐고 코드·마이그레이션이 0이다. DB 실측 — `inventory.handling_unit` 0행 · `handling_unit_content` 0행 · `handling_unit_reconfiguration` 0행 · `handling_unit_reconfiguration_line` 0행.
- 계획이 정한 동작: **표 둘을 신설한다** — `inventory.handling_unit_repack_event`(헤더 4칸) + `inventory.handling_unit_repack_event_line`(라인 9칸) + 인덱스 1(마이그 1파일 · `CREATE` 2 · `INDEX` 1 · **삭제 0 · 백필 0**).
- 기존 `handling_unit_reconfiguration(+_line)` 은 **지우지도 고치지도 않는다** — 0행이고 `src/`·`test/` 참조 0건이라 삭제할 이유가 없고, 삭제는 두 릴리스 규칙이다. 「업무가 서면 그때 쓸 표」로 남긴다. 그 결과 **영원히 빈 표 둘**이 물리에 남는다.
- 계약에 없는 칸은 **`line_no` 하나만** 만든다(정렬 축 — 계약이 `lines` 배열 순서를 요구하는데 정렬 칸이 없으면 반환 순서가 보장되지 않는다). `uom_id`·`reason_code`·`_no` 는 만들지 않는다.

⇒ **묻는 것**: 재포장 이벤트의 저장 표를 «신설»한 것이 맞는가 — 아니면 `handling_unit_reconfiguration(+_line)` 을 계약 모양으로 고쳐 쓰라는 뜻이었는가(그 경우 `ck_handling_unit_reconfiguration_distinct` 삭제와 `uom_id`·`reason_code`·`source/target` 네 칸의 처리를 함께 정해 주셔야 한다).
