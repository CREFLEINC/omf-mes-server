# 114. 툴 PM 시행일과 누계 리셋의 원자성

| 칸 | 내용 |
|---|---|
| 걸리는 오퍼레이션 | POST `/maintenance/results`의 resetCounter=true, MOLD PM 시행 |
| 구현 상태 | 계획 확정·구현 전. reset=true만422 INVALID/field resetCounter·업무 전체0, nonreset 미마감 본길 유지 |
| 판정 | 0단계 고정 W-05-03 날짜+누계 결합효과→1단계 reset 분기→2단계 최초① 상태 전건0 후② 명시거부 |
| 되돌릴 때 | 시행일·부분/역행/nonreset 효과 확정 뒤 R·날짜/누계 같은tx·실제 writer 경합 인수로 정상 reset 성공 추가 |

고정 W-05-03 §5-A/§5-1은 시행일(date)을 마지막PM일자로 쓰고 누계도 갱신한다고 정한다. API 입력에는 독립 시행일이 없고 startedAt/finishedAt만 있다. 지시:실적은1:N, 부분정비와 마감은 별개다. 초안의 **누계만 치환하고 last_pm_date는 그대로 둔201 성공안은 독립3리뷰 뒤 철회**했다.

실패 예: DATE/BOTH 툴에서 지난 마지막PM 날짜를 유지한 채 샷0만 저장하면 성공 뒤에도 날짜축 도래가 남는다. 오더당1회 리셋은 이미 소비되고 PUT에 시행일/reset 정정 칸도 없다. 단순 ‘화면 미완’ 표기는 반쪽 상태 커밋을 해결하지 못한다.

**확인 요청:** 시행일의 요청 원천은 무엇인가? 시작/종료와 같은 경우 공장 로컬일 기준을 명시해 달라. 나눠시행1:N 중 어느 시점에 날짜를 갱신하며, reset=false·미마감/종료시각 입력만 있는 실적에도 효과가 있는가? 과거 시행 기록이 현재 기준일을 되돌리는가? 날짜·누계·실적을 함께 저장하는 정확한 경계를 정해 달라.

MAINTENANCE_RESET_POLICY='REJECT_UNRESOLVED_PM_DATE'. 해소 전 reset=true 입력은 result/parts/lines/current_shot_count/last_pm_date/version/멱등완료를 전부 쓰지 않는다. 새 pmDate/body/header·서버오늘·MAX/CLAMP·planned/baseDate 도출0. nonreset 기록의 finishedAt는 수행구간 종료값일 뿐 PM 시행완료를 선언하는 값이 아니다. PM완료 인수는 미완으로 유지한다.

현재 client의 시작일은 브라우저 offset 자정이며 공장 날짜를 입증하지 못한다. UTC 응답을 문자열 앞자리로 표시하는 문제도 별도 **094** 인수에 남긴다. 서버 instant 보존은109/I32 R14를 따른다.

재개 조건부 인수: 실제 직전누계 before/요청 after 치환·오더당1회·날짜+누계+버전 같은tx·DATE/BOTH 차기도래·부분/소급/nonreset 효과·I33 실제증분 경합·폐기 후 최신ETag도 상태잠김·성공키 재생의 무증분. 구현되지 않은 reset 성공 테스트를 현재PASS로 세지 않는다.
