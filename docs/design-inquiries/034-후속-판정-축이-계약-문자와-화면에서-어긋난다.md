# 34. 후속 판정 축이 계약 문자와 화면에서 어긋난다 — ① `INVENTORY_TRANSACTION` 은 문서 하류(계약)인가 LOT 축(화면)인가 ② 출고의 「사용하지 않은」을 가를 축이 enum 에 없다 ③ P/O 의 후속(입하)이 enum 에 없다

| 칸 | 내용 |
|---|---|
| 걸리는 오퍼레이션 | `GET /logistics/document-progress`·`/{documentTypeCode}/{documentId}`(`successors[]`·`successorCount`·`cancellable`·`cancelBlockedReasonCode=SUCCESSOR_EXISTS`) · `:request-cancel`·`:cancel`(같은 함수로 재판정) — 스키마 `DocumentSuccessor.successorTypeCode` enum 5값 |
| 구현 상태 | **구현함(① LOT 축 · ②③ 계약 문자 그대로)** — `INVENTORY_TRANSACTION` 후속은 「이 문서가 만든 LOT 을 실은 원장 행」으로 센다(화면 `W-01-13` §5-3 · FR-IM-077). 출고의 후속은 문서 하류만이라 실측상 대개 0 · P/O 는 후속 열이 항상 「없음」. 회신을 기다리지 않는다 |
| 판정 | `coverage-100/README.md` §2 **0단계** — ①은 계약이 스스로 근거로 인용한 화면 문장(⌜그 입고가 만든 LOT·수량이 이동·출고·투입에 쓰였는가 → 원장⌝)이 답이다. 다만 **계약 문자와 계약이 인용한 화면이 어긋날 때 어느 쪽이 이기는지**는 슬라이스가 닫을 자리가 아니라 문의한다. ②③은 **계약 침묵**(enum 에 값이 없다) — 값을 지어내지 않는다 |
| 되돌릴 때 | ①이 「문서 하류가 맞다」로 오면 LOT 축 쿼리 한 자리를 `source_document_*` 역조회로 바꾼다(그러면 이동이 만든 원장은 영영 안 보인다 — 아래). ②③은 enum 에 값(예: `PICKING_ORDER` 밖의 소비 축 · `INBOUND_RECEIPT`)을 더해 주면 매핑 표에 행 하나씩 |

## 무엇이 문제인가

### ① `INVENTORY_TRANSACTION` 갈래 — 계약 문자대로면 언제나 0 이다

계약 `DocumentSuccessor.successorTypeCode` 설명: ⌜앞 넷(`GOODS_RECEIPT`·`GOODS_ISSUE`·`PICKING_ORDER`·`INVENTORY_TRANSACTION`)은 `sourceDocument*` 로 거꾸로 조회하는 «문서 하류»이고, 자재 투입은 원천 문서가 아니라 LOT 을 가리키는 «재고 사용»이다⌝.

실측: `inventory_transaction.source_document_type_code` 는 enum 4값(`GOODS_RECEIPT`·`GOODS_ISSUE`·`INVENTORY_ADJUSTMENT`·`STOCK_TRANSFER`)이고, 어떤 문서의 원장을 `source_document_*` 로 역조회하면 **그 문서 «자신»의 전기 원장**이 잡힌다. 자기 자신을 빼면 0 이다. 즉 계약 문자대로 구현하면 「입고 재고가 이동·출고됐는가」를 원장에서 영영 보지 못한다.

그런데 계약이 그 문장의 근거로 든 화면 `W-01-13` §5-3 은 ⌜**재고 사용** | 그 입고가 만든 **LOT·수량이 이동·출고·투입에 쓰였는가 → 원장**⌝ 이고, FR-IM-077 은 ⌜입고재고가 **이동**·출고·투입되지 않은 경우 입고를 취소할 수 있어야 한다⌝ 다. 이동(`STOCK_TRANSFER`)이 만든 원장 행은 `source_document_type_code='STOCK_TRANSFER'` 라 문서 하류 축으로는 절대 안 보이고, **LOT 축**(`inventory_transaction_line.lot_id` 가 이 문서가 만든 LOT 이고 헤더의 `source_document_*` 가 이 문서가 아닌 행)으로만 보인다.

### ② 출고의 「사용하지 않은」(FR-IM-078) 을 가를 축이 enum 에 없다

FR-IM-078 ⌜아직 인수하지 않았거나 **사용하지 않은** 출고 건⌝ 만 취소 가능이어야 한다. 그런데 출고에 LOT 축을 적용할 수 없다 — 출고 라인의 LOT 은 출고가 «만든» 것이 아니라 이미 있던 것이라, LOT 축으로 세면 **모든 출고가 영구히 취소 불가**가 된다. 출고의 「사용」은 하류 문서가 아니라 목적지(공정·외주처)의 소비인데, 그 축이 enum 5값에 없다. 실측상 `goods_issue` 를 `source_document_*` 로 가리키는 표도 없다 ⇒ **전기된 출고는 언제나 취소 가능**으로 보인다.

### ③ P/O 의 후속(입하)이 enum 에 없다

FR-IM-086 은 P/O 진행에 「후속」 열을 요구하지만 `INBOUND_RECEIPT` 가 enum 에 없어 P/O 의 후속은 항상 「없음」이다(`inbound_receipt.purchase_order_id` 는 실재한다 — 셀 수는 있으나 담을 값이 없다).

## 지금 서버는

후속 판정은 **함수 하나**(조회·상신·실행 세 호출자가 같은 결과를 본다).

| 갈래 | 후속 유형 | 무엇을 센다 |
|---|---|---|
| 문서 하류 | `GOODS_RECEIPT`·`GOODS_ISSUE`·`PICKING_ORDER` | 각 표의 `source_document_type_code`/`source_document_id` 가 이 문서 |
| 재고 사용(LOT 축) | `INVENTORY_TRANSACTION` | 이 문서가 만든 LOT(`inbound_receipt_line.lot_id`·`goods_receipt_line.lot_id`)을 실은 `inventory_transaction_line` — 헤더의 `source_document_*` 가 이 문서가 «아닌» 것 |
| | `MATERIAL_CONSUMPTION` | `material_consumption.lot_id` |

세지 않는 것: 자기 자신의 전기 원장 · `status_code='CANCELLED'` 인 후속 · 역처리로 상쇄된 원장 쌍. `GOODS_ISSUE` 에는 LOT 축을 적용하지 않는다. P/O 는 매핑 행이 없어 후속 0.

흔적: 매핑 표 주석 `// INVENTORY_TRANSACTION 은 LOT 축이다 — 계약 문자(문서 하류)대로면 언제나 0 (I-5.md §4-2 · 문의 034)` · 단위 테스트 `후속 — 입고가 만든 LOT 을 이동이 실으면 INVENTORY_TRANSACTION 후속이다(source_document 축이 아니다)` · `후속 — 출고에는 LOT 축을 적용하지 않는다`.

## 요청

1. **① `INVENTORY_TRANSACTION` 후속의 축을 확정해 주십시오** — 계약 문자(문서 하류 · `sourceDocument*` 역조회)와 계약이 인용한 화면(LOT 축)이 어긋납니다. 화면대로면 계약 설명 문장을 ⌜앞 셋은 문서 하류, `INVENTORY_TRANSACTION`·`MATERIAL_CONSUMPTION` 은 LOT 축⌝ 로 고쳐 주십시오.
2. **② 출고의 「사용」을 무엇으로 봅니까?** 목적지가 공정이면 자재 투입(`material_consumption`)·외주면 외주 입고 등 축이 있어야 FR-IM-078 이 섭니다. 축을 주시면 enum 값과 함께 매핑 행을 더합니다. 없으면 「전기된 출고는 후속 없음」이 그대로 섭니다.
3. **③ P/O 후속에 `INBOUND_RECEIPT` 를 enum 에 더할 뜻입니까?** 더해 주시면 `inbound_receipt.purchase_order_id` 로 셉니다.

우리 권고안(회신이 없으면 이대로 갈 값): **① LOT 축 · ②③ enum 그대로(값을 지어내지 않는다).** ①을 문서 하류로 뒤집는 것은 쿼리 한 자리라 싸지만, 그러면 FR-IM-077 의 「이동」이 영영 안 보이므로 권하지 않습니다.
