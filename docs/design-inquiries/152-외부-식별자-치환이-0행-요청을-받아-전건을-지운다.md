# 152. 외부 식별자 치환이 **0행 요청**을 받아 전건을 지운다 — 그리고 `lotExternalIdentifierId` 가 매 치환마다 갈린다

> 같은 저장소의 형제 치환(`PUT /logistics/goods-issues/{id}/lines`)은 **0행을 400 으로 막았다.** 여기서 갈리는 이유는 «등록 쪽 계약의 대칭이 반대»이기 때문이다.

|---|---|
| **구분** | ⭐ **통보**(§2 1-1 — 2026-09-08 규칙) · 회신을 기다리지 않는다 |
| 걸리는 오퍼레이션 | `PUT /trace/lots/{lotId}/external-identifiers` · `GET /trace/lots/{lotId}/external-identifiers` · (파생) `GET /trace/lots/{lotId}` |
| 구현 상태 | **구현 예정(I-18 · 계획 PR 만 · 오늘 코드 0줄)** — 계획서 `docs/coverage-100/slices/I-18.md` §0 자리 3 ⓒ · §4-1(1번) · §4-2 |
| 판정 | `coverage-100/README.md` §2 **1단계 가장자리** → **2단계 기준 3**(스키마·개념을 늘리지 않는다 — 막으려면 계약에 없는 「최소 1행」 개념을 서버가 새로 만들어야 한다) **· 기준 5**(새로 만드는 개념 0 · 나중에 조이는 방향으로 되돌릴 수 있다) |

## 무엇이 문제인가

ⓐ **계약이 `minItems` 를 안 걸었고, 문장은 전건 삭제를 포함한다고 읽힌다.**

- `PUT …/external-identifiers` 의 본문은 `LotExternalIdentifierUpsert[]` 이고 **`minItems` 가 없다**.
- description 이 「**요청에서 빠진 기존 행은 삭제한다**」라 적었다(`contracts/logistics-01자재창고.json:6209-6285`). 요청이 0행이면 「전부 빠진 것」이므로 전건 삭제다 — 문장을 그대로 읽으면 그렇게 읽힌다.

ⓑ **형제 치환은 0행을 막았는데, 그 근거가 여기에는 없다.**

- `PUT /logistics/goods-issues/{id}/lines` 는 0행을 400 으로 막는다(`src/logistics/goods-issue/goods-issue-update.service.ts:56-60`). 그런데 그 근거는 **등록 쪽 계약이 「최소 1행」이라 적었기 때문**이다 — 라인 없는 출고 전표는 성립하지 않는다.
- 여기 등록(`LotCreate.externalIdentifiers`)은 **선택 배열**이다. 즉 **외부 식별자가 0건인 LOT 은 처음부터 정상**이다. 대칭이 반대라 형제의 근거를 그대로 옮길 수 없다.

ⓒ **덤 — 치환이 `lotExternalIdentifierId` 를 매번 갈아 치운다.**

- 계약 `LotExternalIdentifierUpsert` 는 required 2 · 프로퍼티 4 인데 **id 칸이 없다**(`:11761`). 즉 요청이 「이 행을 고쳐라」를 가리킬 수단을 주지 않았다.
- 물리 유일 인덱스는 **5칸 표현식**이라(`(lot_id, identifier_type_code, COALESCE(partner_id,0), COALESCE(external_system_code,''), external_identifier)` · baseline `migration.sql:1082-1089`) 자연키 diff 를 하려면 서버가 그 표현식을 손으로 재현해야 하고, 그렇게 해도 계약이 「빠진 행은 삭제한다」라 적어 결과는 같다.
- 이 표를 참조하는 **자식이 0개**다(`prisma/schema.prisma:3601-3614` — 역관계 0) ⇒ id 가 갈려도 참조 무결성은 안 깨진다. 깨지는 것은 **그 id 를 캐시한 클라이언트**뿐이다.

## 지금 서버는

**아직 없다.** 계획이 정한 동작:

- **0행 요청을 받는다.** `deleteMany` 로 전건을 지우고 `{ items: [] }` 를 200 으로 돌려준다.
- 치환은 **전삭제 + 전삽입**(`deleteMany` → `createMany`)이다. 그래서 `lotExternalIdentifierId` 는 매 치환마다 갈린다.
- **요청 «안»의 5칸 중복은 400 `UNIQUE_VIOLATION` 으로 앞당겨 막는다.** 표현식 유일 인덱스라 P2002 의 `meta.target` 이 비어 공용 그물에 안 걸리고, 손검사가 없으면 500 으로 새거나 조용히 N→N−1 이 된다(`purchase-order.service.ts:341-350` 이 같은 사고를 한 번 고쳤다). ⚠ `partnerId` 만 다른 두 행은 **통과**한다(`COALESCE(partner_id,0)` 축).
- 치환은 부모 `trace.lot.version_no` 를 **올린다** — 응답에 ETag 선언이 없어 다음 If-Match 토큰은 상세 GET 이 준다(0단계 선례 `goods-issue-update.service.ts:46-47`).
- 반환 정렬은 `lot_external_identifier_id asc` 로 **명시 고정**한다(계약에 `sort` 가 없다 · 상세 GET 과 같은 정렬).

## ⇒ 알리는 것

1. **0행 요청을 허용한다** — 전건 삭제로 처리한다. 등록이 선택 배열이라 「식별자 0건 LOT」이 정상 상태이기 때문이다.
2. **`lotExternalIdentifierId` 는 치환마다 갈린다** — 계약이 `Upsert` 에 id 칸을 두지 않아 다른 길이 없다. 클라이언트는 그 id 를 **캐시하지 않는 것**을 전제로 만들어 주십시오.
3. 계약에 되돌릴 것(택일): ⓐ 0행을 막으려면 `minItems: 1` 을 걸어 주십시오(서버는 한 줄로 조인다) ⓑ id 를 보존해야 하면 `LotExternalIdentifierUpsert` 에 `lotExternalIdentifierId?` 를 열어 주십시오(그러면 diff 치환으로 바꾼다 · ≈ +60줄).
