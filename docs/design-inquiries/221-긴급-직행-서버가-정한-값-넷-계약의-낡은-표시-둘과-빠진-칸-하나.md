## ⓐ 서버가 정한 값 — 긴급 직행이 만드는 «제품 입고»

계약(`shipment-04제품출하.json` `ShipmentCreate.expedited` `:2897-2902`) — 「참이면 서버가 **제품 입고 전표와 입고 전기**를 같은 트랜잭션에서 함께 만든다 — 화면이 01 계약을 따로 부르지 않는다. **입고 유형·원천 문서 유형은 서버가 정한다**」.

| 칸 | 값 | 근거 |
|---|---|---|
| `goods_receipt.receipt_type_code` | **`PRODUCT`** | 같은 설명 「제품입고(PRODUCT)로 확정됐고(2026-08-31 · G-32 등록부 `RECEIPT_TYPE`)」 · 시드 `RECEIPT_TYPE` 4값에 실재 |
| `goods_receipt.source_document_type_code` | **`SHIPMENT`** | `GoodsReceipt.sourceDocumentTypeCode` enum 4값에 실재(→ `logistics.shipment`) |
| `goods_receipt.source_document_id` | **`shipment_id`** | A-10 — 짝 id 는 판별자가 가리키는 표의 식별자 |
| 입고 창고 | 본문 `warehouseId` | 같은 설명 「장부상 입고 창고는 본문의 warehouseId 다」 |

⛔ 「`SHIPMENT` 는 반품 클레임 입고(`W-04-06`) 전용이다」는 **오독**이다 — A-10 규약상 값의 뜻은 «가리킬 표의 이름»이고, 괄호 속 `W-04-06` 은 그때 알려진 사용처다.

### 같은 트랜잭션 안의 판정 — 알려 두는 것

| 자리 | 정한 것 | 왜 |
|---|---|---|
| 품질 게이트 | ⛔ **건너뛰지 않는다** — 배분 LOT 이 Release 가 아니면 400 · **어떤 행도 쓰기 전**(맨 앞) | 계약 「품질 게이트는 건너뛰지 않는다(결정 10)」 |
| 순서 | 게이트 → 출하 헤더 → **입고 전기** → 출고 원천 해소 → 출고 전기 | 긴급 직행의 재고는 «방금 입고한 LOT» 이라 잔액 행이 없다 — 뒤집으면 출고 원천 해소가 0행으로 400 이다 |
| 적치 지시 | ⛔ **만들지 않는다** | 창고 경유를 건너뛰는 경로다 — 물건이 곧바로 나간다 |
| 출고의 피킹 소진 | **돌지 않는다** | 피킹을 건너뛰어 `picked_qty` 가 0 이다 — 평시처럼 소진하면 긴급 본길이 **언제나 400** 이었다(구현 중 발견) |
| `expediteReason` | 참이면 **필수 · 400 `REQUIRED`** | 계약 `required` 에는 없고 설명(A-12)에만 있다 — 물리 `ck_shipment_expedite` 가 같은 짝을 보지만 그쪽이 내면 500 이다 |
| 채번 | 입고 번호는 긴급일 **때만** 뽑는다 | 평시에 뽑으면 결번만 는다 |
| 취소 | 역전기 **둘** — 출고 역이 먼저, 입고 역이 나중 | 통보 220 |

## ⓑ ⛔ 계약에 남은 **낡은 표시 둘** — 지워 주십시오

| 자리 | 문구 | 모순 |
|---|---|---|
| `logistics-01자재창고.json` `GoodsReceipt.sourceDocumentTypeCode` `x-no-example`(`:8076`) | 「값 목록이 **아직 확정 전**이다(omf-mes#145) — 확정 전에는 예시를 지어내지 않는다」 | 같은 칸이 **enum 4값**을 이미 닫았다 |
| `shipment-04제품출하.json` `ShipmentCreate.expedited` 설명 · `x-internal-note`(`:2900` · `:2902`) | 「원천 문서 유형의 **값 목록만 아직 확정 전**이다(omf-mes#145)」 · 「`receiptTypeCode`·`sourceDocumentTypeCode` 의 값 목록 미확정 — 추적 omf-mes#145·#213」 | 위와 같다 — 그리고 `receiptTypeCode` 는 같은 설명이 「확정됐다」고 적었다 |

⇒ 읽는 사람이 「아직 못 쓰는 값」으로 받아들인다. enum 이 정본이면 표시 둘을 지우고, 표시가 정본이면 enum 을 열어 주십시오.

## ⓒ ⛔ `StockReinstatementConflictResponse` 에 `conflictCause` 칸이 **없다** — 더해 주십시오

| 스키마 | `conflictCause` |
|---|:-:|
| `ShipmentConflictResponse`(형제 · `W-04-12`) | ⭕ 있다 |
| `StockReinstatementConflictResponse`(`:3831`~) | ⛔ **없다** |

서버의 409 봉투는 **공용**이라(`src/common/errors/conflict.exception.ts:48` · `:55`) 언제나 `conflictCause` 를 싣는다. 스키마가 `additionalProperties` 를 막지 않아 응답 검증은 통과하지만, 화면은 **선언되지 않은 칸**을 믿고 쓸 수 없다 — `VERSION_CONFLICT`(다른 사용자가 먼저 고쳤다)와 업무 거부를 가르는 칸이다. 구현이 이 간극을 컨트롤러 주석에 적어 두었다(`stock-reinstatement.controller.ts:28`).

📨 형제와 같게 `conflictCause` 를 더해 주십시오. 스키마 `x-internal-note` 의 「`ShipmentConflictResponse` 의 enum 을 넓히지 않고 따로 만들었다」는 **`code` enum** 이야기이고, 칸 모양까지 달리하려던 것은 아니라고 읽었다.

## ⓓ 입고 «위치» — 계약이 칸을 안 줬고, 물리는 NOT NULL 이다

긴급 직행 본문에는 **위치 칸이 0개**다. 창고의 `management_level_code` 로 가른다 — 재고 재등록(통보 222 ⓒ)과 **같은 해소기**다(`src/logistics/destination-location.ts:26-35`).

| 관리 수준 | 판정 |
|---|---|
| `WAREHOUSE` | 그 창고의 활성 위치가 «정확히 하나»면 그것 · 0·2+ → 400 `RANGE`(`warehouseId`) |
| 그 밖(`ZONE`·`RACK`·`CELL`) | ⛔ **400 `REQUIRED`(`warehouseId`)** — 위치를 받을 칸이 없으니 긴급 직행은 «창고 단위로 관리하는 창고»로만 나간다 |

📨 셀 단위 창고에서도 긴급 직행을 해야 한다면 `ShipmentCreate` 에 입고 위치 칸을 주십시오. 오면 해소기의 인자 하나다.
