# 093. 고장 start의400 문언과 ETag 재조회

| 칸 | 내용 |
|---|---|
| 걸리는 오퍼레이션 | POST `/maintenance/breakdowns/{breakdownId}:start-handling` · 점검/고장 쓰기·조회 |
| 구현 상태 | R-6·R-7대로 구현 예정, 새 오류코드0 |
| 판정 | 0단계 구체 계약문언 우선: 상태잠금400, ETag미선언과 헤더금지 구별 |
| 되돌릴 때 | 계약 응답표 보완. 실제 상태정책 변경이면 호출부와 상태/재조회 테스트 수정 |

`equipment-05설비툴.json:790`은 상태잠금을400이라고 명시하지만 start 응답표에는403/404/409/422만 있고400은 없다. :779의422는 포괄 업무규칙이다. 서버는 구체문언대로400 STATE_LOCKED, version불일치는409 ConflictResponse를 낸다. 헤더/잘못된path의 공용400과 생성POST의 멱등409도 개별표에 빠져 있다.

**요청: 상태잠금400과 공통 인증/헤더/멱등 오류를 응답표에 정합하게 반영해 달라.** 응답 미등재는 절대금지로 읽지 않는다(기존 plan.md:207 선례). 어느 계약도 구현할 수 없는 모순으로 루틴전체를 멈추지 않는다.

고장 상세:506의 ETag만 버전이다. 생성·PUT·start 및 점검 응답의 ETag미선언은 **새버전토큰 미발행**이지 Express의 자동 weak 내용해시까지 금지한 것이 아니다. 전역 ETag설정을 바꾸거나 본문versionNo를 신설하지 않는다.

소비자는 생성→상세GET→메모PUT→상세GET→start→상세GET으로 다음 토큰과 집계를 얻는다. 내용해시를 If-Match로 쓰거나 쓰기응답의 목록형count0으로 열린 비가동 경고를 지우지 않는다. 409는 입력보존/재조회 후 새시도, 응답유실은 같은키/본문 재전송이다.

흔적: E-B21/E-B22, E-I08, 연속GET/PUT/start와 내용해시≠버전 단언에 문의093.
