# 106. 시리얼 발번의 번호 연속성과 선택 If-Match 조건

| 칸 | 내용 |
|---|---|
| 대상 | POST `/trace/serial-numbers`의 번호 정책·선택 If-Match |
| 상태 | 현재 POST 유보. 아래는 재개 전 통합 R로 확정할 권고안이며 구현된 규약이 아님 |
| 판정 | 번호 결정 주체는 서버로 위임됨. If-Match 대상 원천은 별도 가장자리 미정 |

## 번호 정책: 위임 범위 안의 권고안

계약은 서버가 번호를 매긴다고 하고 serial_no는 전역 UNIQUE다. quantity=N이면 개체 N행 전량 성공 또는0행이며, 발행기록은 별도 요청이다. 반면 P-02-05 §9는 ‘연속’이라는 표현을 쓴다.

권고안은 기존 NumberingService의 전역 `SERIAL_NUMBER:'SN'` 번호 앞에 `P{plantId}-L{lotId}-`를 붙이는 것이다. 기간은 producedAt의 UTC 날짜, 생략 시 준비 단계의 UTC 날짜를 한 번 고정한다. 이는 생산시각을 채우는 동작이 아니다.

번호 N개는 업무·멱등 tx 밖에서 순차 준비한다. 업무 실패 뒤 **예약 결번**과 다른 성공 배치의 끼어듦은 가능하지만, 개체 일부만 커밋하는 부분 성공은 없다. 번호 충돌만 한정 재시도하며 모든 오류를 재채번하지 않는다. 별도 코어 PR≤200으로 처리한다.

**화면의 ‘연속’이 무결번 또는 배치별 연속 구간을 반드시 요구하는지 확인해 달라.** 그렇다면 위 권고안을 확정하지 않고 코어 범위를 다시 세운다. 서버 위임 자체를 회신 대기 조건으로 추가하는 것은 아니다.

## 선택 If-Match: 버전의 대상이 없다

계약은 헤더가 없으면 검사를 생략하도록 하지만, 어느 자원 버전을 비교하는지 명시하지 않는다. 시리얼 목록에는 ETag가 없고 신규 개체의 version1도 기존 수정 대상이 아니다. LOT FK라는 이유로 부모 토큰을 상속하지 않는다.

**이 헤더가 가리키는 자원/GET 원천이 있는지, 아니면 신규 생성으로 받아도 비교하지 않는 자리인지 확인해 달라.** 기존 material-return 신규 생성에는 받되 무시하는 선례가 있다.

현재 재개 전 권고안은 정상 형식 헤더 제공 건만400 INVALID로 거부하는 가장자리 경계이며, 위 무시 선례와 비교한 최종 R이 필요하다. 생략 허용·형식 오류400은 이미 공용 가드 규칙이다. 원천을 지어내거나 If-Match를 필수로 바꾸지 않는다.
