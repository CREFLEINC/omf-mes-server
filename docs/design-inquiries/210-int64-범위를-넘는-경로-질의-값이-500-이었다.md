# 210. int64 **범위를 넘는 경로·질의 값**이 500 이었다 — 계약이 `format: int64` 를 적어 둔 자리 1456곳

**구분: 통보**(회신을 기다리지 않는다) · ⭐ **문의 074 · 통보 186 · 통보 201 과 «묶어» 보십시오** — 넷 다 「400 미선언인데 서버가 400 을 낸다」이고, **이 건만 원인이 다릅니다**(기간 규칙이 아니라 «계약이 이미 적어 둔 정수 범위»입니다).

| 칸 | 내용 |
|---|---|
| 걸리는 오퍼레이션 | **구현된 210건**(GET 169 · POST 36 · PUT 2 · DELETE 3) — 계약이 `format: int64` 를 적었고 `400` 을 «안» 적은 전건. 경로만 143 · 질의만 66 · 둘 다 1 |
| 구현 상태 | **구현함** — 공용 계약 검증기 한 자리(`contract-validator.ts`) · 컨트롤러·서비스 변경 0 |
| 판정 | §2 **2단계 기준 2**(거부하는 쪽 — 거부→허용이 호환 완화) · **0단계 선례 = 통보 186 · 통보 201 · 문의 074** |
| 되돌릴 때 | `int64` format 을 다시 무연산으로 등록하면 원래대로 — 한 줄 · e2e 19건 |

## 무엇이 났나

`GET /inventory/handling-units/99999999999999999999` 이 **500** 이었습니다. `INTERNAL_ERROR` 봉투가 나갔고, 계약은 그 자리에 200·404 만 선언했습니다.

⭐ **계약 487 오퍼레이션 중 `500` 을 선언한 것은 «0건»입니다**(python 실측). 500 은 어디서도 계약이 허용한 응답이 아닙니다.

원인은 취급 단위가 아니라 **정수 검증이 통째로 없다**는 것이었습니다.

| 층 | 1e20 을 받으면 |
|---|---|
| 계약 검증 가드(ajv) | `type: integer` 통과 — `Number.isInteger(1e20)` 이 **참**이다. `format: int64` 는 **무연산으로 등록**돼 있었다 |
| `ParseIntPipe`(70파일) | `parseInt` 이 `1e20` 을 돌려주고 `NaN` 이 아니라 통과 |
| `numeric()`(13파일 · 바이트까지 동일한 복사본) | `Number.isInteger(parsed) && parsed >= 0` 통과 |
| Prisma | int8 로 접지 못해 던진다 → **500** |

⇒ **네 층이 모두 통과시켰습니다.** PR #485 리뷰가 취급 단위 3자리에서 찾았지만, 같은 구멍이 **210 오퍼레이션**에 있었습니다.

## ⇒ 우리가 정한 것

- **계약 검증 가드의 `int64` format 을 «실제 범위 검사»로 바꿉니다.** 무연산 등록을 그만두고 `-(2^63) ≤ v < 2^63` 을 봅니다. 경로·질의 전건이 여기서 **400 `INVALID`** 로 걸립니다.
- ⭐ **이것은 새 규칙이 아니라 «계약이 이미 적은 것»의 이행입니다.** 계약이 그 자리 **1456곳**을 `format: int64` 로 적었고, 물리 id 컬럼 **756개가 전부 `BigInt`(int8)** 입니다. 서버가 계약의 범위 선언을 안 지켜 500 이 났던 것입니다.
- ⚠ **다만 경계는 int64 구간이 «아니라» 양쪽이 열린 `(-2^63, 2^63)` 입니다.** int64 자체는 하한이 닫힌 `[-2^63, 2^63-1]` 인데, Prisma 가 `|v| >= 2 ** 63` 을 ⌜Expected BigInt, provided Float⌝ 로 던집니다(실측 — PostgreSQL 은 `(-9223372036854775808)::bigint` 를 정상 수용하므로 **DB 가 아니라 Prisma 층의 제약**입니다). 그래서 **`-(2^63)` 은 «유효한 int64 인데도» 400 으로 거절**합니다 — 안 막으면 배정도로 그 값이 되는 유효 int64 **513개**가 그대로 500 이 됩니다.
- ⛔ **한 자리에서만 고칩니다.** `ParseIntPipe` 70파일도, `numeric()` 13복사본도 건드리지 않았습니다 — 가드가 파이프보다 **먼저** 돌아서 그 뒤는 이미 안전한 값만 봅니다. 「사용처 하나뿐인 추상화 금지」이므로 새 파이프·새 데코레이터를 만들지 않았습니다.
- ⛔ **본문에는 걸지 않았습니다.** I-28 이 이미 자기 규칙으로 본문 정수를 막고 있고(`recipients[].userId` → 400 `RANGE`), 그 자리는 **설계 미정 · 문의 번호 배정 대기(I-28 R-11)** 입니다. 공용 자리가 다른 슬라이스의 미결 판정을 덮으면 `RANGE` 를 받아 온 클라이언트가 말없이 `INVALID` 를 받습니다. 신고된 결함도 경로·질의뿐입니다.
- ⛔ **`page` 는 다른 자리·다른 코드입니다** — 아래.

## ⚠ 곁가지 하나 — `page` 는 계약이 `format: int64` 를 «안» 적었다

`?page=99999999999999999999` 도 **500** 이었는데 원인이 다릅니다. 계약이 `page` 를 `type: integer` **로만** 적어(`format` 없음) 위 검사가 지나갑니다. `skip = (page-1)*size` 가 부풀어 Prisma 가 못 접었습니다. `page` 를 받는 GET 은 **93건**(구현 79)입니다.

⇒ **`pagination.ts` 에서 400 `RANGE`** 로 막습니다. 이것도 우리가 «새로 고른» 답이 아닙니다 — `document-issue`·`maintenance/order`·`maintenance/result` **세 조회 서비스가 이미 같은 판정을 각자 베껴** 두고 있었습니다(`!Number.isSafeInteger(page.skip)` → 400 `RANGE`). `skip` 을 만드는 자리가 `pageRequest()` 하나뿐이라 그리로 모았습니다. `size` 는 `MAX_SIZE` 로 이미 잘려 이 문제가 없습니다.

## ⚠ 한 PR 안에서 코드가 «둘»로 갈린 이유

같은 「수가 범위를 넘었다」인데 **경로·질의 id 는 `INVALID`**, **`page` 는 `RANGE`** 입니다. 지어낸 것이 아니라 **양쪽 다 저장소가 이미 고른 답을 그대로 따른 결과**입니다.

| 자리 | 코드 | 따른 선례 |
|---|:-:|---|
| 경로·질의 id(int64 초과) | `INVALID` | `validation-error.mapper.ts` — 「형식 위반(타입·enum·format·pattern)은 `INVALID` 하나로 모은다」 |
| `page`(안전 정수 초과) | `RANGE` | `document-issue`·`maintenance/order`·`maintenance/result` 세 조회 서비스가 이미 쓰던 값 |

⚠ 계약이 이 제약을 `format: int64` 가 아니라 `maximum` 으로 적었다면 **같은 표가 `RANGE` 를 냈을 것**입니다(`RANGE_KEYWORDS` 에 `maximum` 이 있습니다). 즉 코드가 갈린 것은 업무 규칙 차이가 아니라 **계약이 제약을 어느 키워드로 적었는가**의 차이입니다.

⇒ 저희가 임의로 통일하지 않았습니다. 같은 매퍼가 「화면은 `field` 와 `message` 로 읽지 코드를 세분해 분기하지 않는다」라 적어 두어 화면에 미치는 차이가 없고, 한쪽으로 맞추면 **이미 `RANGE` 를 받아 온 세 조회의 클라이언트**나 **`INVALID` 규칙 전체** 중 하나가 말없이 바뀝니다. **어느 쪽으로 통일할지 정해 주시면 그대로 맞추겠습니다.**

## 📨 알려 드리는 것

**① 계약에 `400` 응답을 적어 주십시오** — 위 210건과 `page` 를 받는 93건입니다. 지금은 계약에서 만든 클라이언트에 400 분기가 없어 화면이 목록 대신 「알 수 없는 오류」를 봅니다. ⭐ **문의 074 · 통보 186 · 통보 201 과 묶어 보시면** 「계약이 제약을 적고(또는 설명하고) `400` 을 안 적는」 패턴이 **네 도메인에서 반복**된다는 것이 보입니다. 한 번에 고치실 수 있습니다.

**② `page`·`size` 에도 `format: int64` 와 `maximum` 을 적어 주십시오.** 지금 `maximum` 은 `size` **3자리에만** 있습니다(`pagination.ts` 주석 — 서버가 전건에 200 을 걸어 둔 상태입니다).

**③ ⚠ 2^53 초과 구간은 «막지 않았습니다».** `9007199254740993` 같은 값은 배정도로 옮기며 `...992` 로 반올림돼 **다른 id 를 조회하고 404** 가 됩니다. 500 이 아니고, 계약이 int64 를 허용한 이상 거절할 근거가 없어 그대로 둡니다. 다만 **계약이 id 상한을 2^53 으로 좁혀 주시면** 그 조용한 어긋남이 사라집니다. id 는 채번값이라 실무에서 닿지 않는 구간입니다.
