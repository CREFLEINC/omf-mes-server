# 30. 폐기 출고의 승인 게이트를 걸 축이 데이터에 없다 — 화면은 「계약이 전건을 막는다」로 읽었고 서버는 «상신한 전표»만 막는다

| 칸 | 내용 |
|---|---|
| 걸리는 오퍼레이션 | `POST /logistics/goods-issues/{goodsIssueId}:post` · `POST /logistics/goods-issues`(`postImmediately=true`) · `PUT …/{goodsIssueId}/lines` |
| 구현 상태 | **구현함(§2 절차 1단계 가장자리 → 2단계 기준 5 「새 개념 0 · 조이는 방향으로 되돌릴 수 있다」)** — `:post` 는 그 전표에 `GOODS_ISSUE_DISPOSAL` 승인 요청이 **하나라도 있으면** 승인 상태를 읽어 가르고(`PENDING` → 400 `APPROVAL_IN_PROGRESS` · `REJECTED` 만 → 400 `APPROVAL_REQUIRED`), **0건이면 통과**한다. `PUT …/lines` 는 `PENDING` 이 있으면 400 `APPROVAL_IN_PROGRESS` |
| 판정 | `coverage-100/README.md` §2 0단계 — 계약 `GoodsIssue.approvalRequestId` 「**비어 있으면 승인을 타지 않은 출고다.** 폐기 출고 화면이 이 값으로 승인을 보이고, **승인 없이 나간 건을 가려낸다**」가 「승인을 안 탄 출고」의 존재를 인정하고 그것을 «사후에 화면에서» 가려낸다고 적었다 ⇒ 서버가 사전에 전건을 막는 축이 아니다. 어느 전표가 승인을 타야 하는지는 **계약이 세운 축(`reasonCode`)의 값이 아직 없어** 상신 흔적으로 대신 가른다 |
| 되돌릴 때 | ① 「폐기」 `reasonCode` 값이 오면 `assertApproved` 호출 자리의 판정 한 줄(`I-4.md` R-4 주석 자리)을 「그 사유면 승인 요청이 반드시 있어야 한다」로 조인다 — 사유→승인 필수 여부는 상수가 아니라 데이터(`judgment_type_control.requires_approval` 과 같은 모양)로 둔다 ③ 「서버가 강제하라」면 등록 서비스에 거부 한 줄(`reasonCode` 가 승인 사유인데 `postImmediately=true` 면 400) |

## 무엇이 문제인가

계약과 시드가 **승인 게이트의 축을 「사유」로 못박았다.**

- 계약 `GoodsIssue.issueTypeCode`: 「⛔ 폐기는 출고 *유형*이 아니라 기타출고의 *사유*다. `issue_type_code=OTHER` 로 두고 `reason_code` 로 가른다 — **승인 게이트도 유형이 아니라 사유를 보고 건다**」(`seed.ts:387-388` 도 같은 문장).
- `W-04-10` §4-B 「출고 유형: 기타출고(`OTHER`) 고정 — 폐기는 유형이 아니라 **사유**다(✓확정 2026-08-31). 승인 게이트도 사유를 보고 건다」.

그런데 **그 축에 「폐기」를 가리키는 값이 없다.** `GOODS_ISSUE_REASON` 은 계약·시드 모두 5값 — `IQC_FAIL`·`OVER_RECEIPT`·`DEFECT_AFTER_RECEIPT`·`WRONG_SHIPMENT`·`OTHER`(`seed.ts:574-583`). 계약 `GoodsIssue.reasonCode` 는 「⭐ 고객이 늘린다 — 위 값은 초기 시드다(G-31)」라 적었으므로 **없는 것이 아니라 아직 안 실린 것**이다.

한편 화면 셋은 「계약이 전건을 막는다」로 읽었다.
- `W-04-10` §5-4 「01 계약이 이미 그렇게 썼다 — `POST /logistics/goods-issues/{id}:post` 는 **승인 전이면 400**」 · §6 「승인 전 출고 시도 → ⛔ 400 — **계약이 막는다**」
- `W-01-06` §6 「승인 없이 출고 시도 → ⛔ 차단(REQ-PR-0028)」

서버가 「승인 전」을 가르려면 «이 전표는 승인을 타야 한다»를 먼저 알아야 하는데, 그것을 알 축(사유 값)이 데이터에 없다. 대안 둘을 실측으로 기각했다(`I-4.md` §4-2).
1. 「`GOODS_ISSUE_DISPOSAL` 활성 결재선이 있으면 승인 필수」 — 결재선 선택의 사업부 축이 8자리 전부 `null`(문의 022)이라 **전표와 무관한 전역 조건**이 된다. 결재선을 한 벌 등록하는 순간 생산 투입 출고(`M-01-08`)까지 전부 400 이다.
2. 「`issueTypeCode=OTHER` 면 승인 필수」 — 위 계약 문장(「유형이 아니라 사유를 보고」)과 정면으로 어긋난다.

## 지금 서버는

**상신 흔적으로 가른다.** `:post` 는 언제나 `assertApproved(tx, 'GOODS_ISSUE', id, 'GOODS_ISSUE_DISPOSAL')` 를 부르고, 그 다형 축(`approval_request.target_type_code·target_id·approval_type_code`)에

| 행 | 응답 |
|---|---|
| 0건 | 통과 — 「승인을 타지 않은 출고」(계약 문장 그대로) |
| `APPROVED` 하나라도 | 통과 |
| `PENDING` 만 | 400 `APPROVAL_IN_PROGRESS` |
| `REJECTED` 만 | 400 `APPROVAL_REQUIRED` |

그래서 **남는 구멍**이 셋이다.

**① 「고아 전표」** — `W-04-10` §5-7 「승인 요청은 한 버튼이 두 호출이다」: `POST /logistics/goods-issues`(`postImmediately=false`) 로 전표를 먼저 만들고 `:request-approval` 로 상신한다. 첫 호출(201)이 성공한 뒤 둘째가 400 `ROUTE_NOT_FOUND`(결재선 없음 — `W-01-06` §6 「결재선이 없다 → 상신 차단 · `W-06-15` 에서 먼저 정의한다」)면 **승인 요청 0건짜리 `REGISTERED` 폐기 전표가 남고, API 는 그 `:post` 를 연다.** 화면은 《③ 승인 후》 구획을 잠그지만 서버는 안 막는다. 문의 022(결재선의 사업부 축)와 같은 뿌리다.

**② 상신 뒤 라인이 바뀌면 승인이 유효한가** — 계약은 `PUT …/lines` 를 `POSTED` 에서만 막았다(`GoodsIssueLineUpsert` 400 `STATE_LOCKED`). 승인 대기 중 치환이 열려 있으면 10개를 승인했는데 100개가 나가고, 원장은 되돌릴 수 없다. **서버는 `PENDING` 이 있으면 치환을 400 `APPROVAL_IN_PROGRESS` 로 막았다**(§2 2단계 기준 2 · 거부→허용은 호환 완화). ⚠ 문의 023(P/O 상신 뒤 잠금)과 **반대 판정**이다 — P/O 는 `:post` 가 없어 승인 뒤에 일어나는 일이 계약에 0건이고, 출고는 승인 뒤 «원장»이 움직인다. 되돌림 비용이 달라 갈랐다. 「승인된 뒤 `:post` 전에 라인이 바뀌면 승인이 무효인가」는 위 자물쇠로 API 경로에서 일어날 수 없어 **재판정을 만들지 않았다.**

**③ `postImmediately=true` 는 승인을 건너뛴다** — 등록과 전기가 한 트랜잭션이라 상신할 틈이 없다. 화면은 `postImmediately=false` 로만 보내지만(`W-04-10` §5-7 · `W-01-06` 2026-08-16 정정) 큐·다른 호출자가 `true` 를 보내면 폐기 사유의 출고가 승인 없이 전기된다. **서버는 지금 거부하지 않는다** — 거부할 사유 값(①의 축)이 같은 이유로 없다.

흔적: `assertApproved` 호출 자리 주석 `// 계약이 세운 축(reasonCode)의 값이 아직 없어 상신 흔적으로 대신 가른다 — 값이 오면 이 자리를 바꾼다(I-4.md R-4 · 문의 030)` + e2e `전기 — 상신하지 않은 출고는 승인 없이 전기된다(계약 「비어 있으면 승인을 타지 않은 출고다」)`.

## 요청

1. **「폐기」를 가리키는 `GOODS_ISSUE_REASON` 값을 정해 주십시오**(`DISPOSAL` 등 — 코드값과 표시명). 그리고 **「어느 사유가 승인을 타는가」를 코드 상수가 아니라 데이터로 두는 것**에 동의해 주십시오 — `mdm.judgment_type_control.requires_approval` 이 같은 모양이라, 값이 늘어도 코드를 안 고칩니다. 서버는 그 표시가 오면 «그 사유면 승인 요청이 반드시 있어야 한다»로 `:post` 를 조입니다(①의 고아 전표가 닫힙니다).
2. **상신 뒤 라인 치환을 서버가 막은 것(②)이 의도와 맞습니까?** `PUT …/lines` 를 부르는 화면은 실측 0건이라(`M-01-09` §8 #1 「라인 치환은 쓸 수 없다」 · `W-01-06` §5-7 · `W-04-10` §5-6 액션표) UI 비용은 없습니다. 맞다면 계약 `GoodsIssueLineUpsert` 400 문장에 「승인 대기 중」 한 줄을 더해 주십시오.
3. **폐기 사유의 출고에 `postImmediately=true` 가 오면 서버가 400 으로 거부해야 합니까(③)?** 1 의 값이 오면 거부할 수 있습니다. 거부한다면 코드는 `APPROVAL_REQUIRED` 로 갑니다.

우리 권고안(회신이 없으면 이대로 갈 값): **상신 흔적으로 가른다 · 치환은 막는다 · `postImmediately` 는 거부하지 않는다.** 셋 다 «조이는 방향»으로 되돌릴 수 있고(통과→거부는 새 값이 오는 순간 한 줄), 반대로 지금 전건을 막으면 생산 투입 출고까지 멈춥니다.
