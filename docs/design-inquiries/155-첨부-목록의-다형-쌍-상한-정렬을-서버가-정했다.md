# 155. 첨부 목록이 다형 쌍을 **독립 필터 둘**로 걸고, 상한과 정렬을 서버가 정했다 — 계약이 「**한 대상**」이라 «단수»로 적고도 위반 응답을 선언하지 않았다

> ⚠ **「계약이 침묵한다」가 아니다.** `GET /app/attachments` 의 description 은 **「한 대상에 붙은 첨부를 낸다.」**라 **단수로** 적혀 있다. 그런데 그 단수를 **위반했을 때의 응답이 한 자리도 선언돼 있지 않다**(선언 응답 `200` 하나). 문장과 응답 선언이 서로 다른 것을 말한다 — 그래서 이 통보를 낸다.
> ⚠ 그리고 **같은 다형 쌍(`targetTypeCode`,`targetId`)을 쓰는 오퍼레이션 셋의 계약이 셋 다 다르다.**

| 칸 | 내용 |
|---|---|
| **구분** | ⭐ **통보** — 계약이 선언하지 않은 400 을 서버가 만들지 않는다 · 계약에 없는 상한을 지어내지 않는다. 회신을 기다리지 않는다 |
| 걸리는 오퍼레이션 | `GET /app/attachments` · (대조) `GET /app/document-issues` · `GET /app/approval-requests` |
| 구현 상태 | **구현 예정(I-34 · 계획 PR 만 · 오늘 코드 0줄)** — 계획서 `docs/coverage-100/slices/I-34.md` §0 자리 1·2·3 · §4 F3·F4·S1·S2 · §6-1 |
| 판정 | `coverage-100/README.md` §2 — ⓐ **1단계 본길** → **0단계 선례**(같은 모듈 `src/app/approval/approval-request.service.ts:149-150` 이 400 미선언 형제를 독립 필터 둘로 이미 구현) ⓑ **1단계 본길** → **0단계 선례 셋**(질의 축 0 · `page`/`size` 0 인 구현된 컬렉션 GET 이 이미 서 있다) ⓒ **가장자리** → 0단계 선례 셋(시각 칸 있는 목록은 시각 desc + PK desc) |
| 되돌릴 때 | ⓐ 「짝을 강제하라」로 오면 **계약이 400 을 «선언»해 주십시오** — 서버는 서비스 앞에 분기 한 줄 + e2e 2건이면 된다(≈ +15줄). 지금 우리가 400 을 만들면 **계약에 없는 응답**이 서버에만 생긴다. ⓑ 상한이 필요하면 **계약에 `page`·`size`·`PageMeta` 를 열어 주십시오**(공용 헬퍼가 있어 ≈ +10줄). ⓒ 정렬이 화면 소관이면 상수 한 줄과 e2e 배열 단언만 바뀐다 |

## 무엇이 문제인가

### ⓐ 다형 쌍의 «짝 강제» 여부 — 같은 쌍을 쓰는 계약 셋이 서로 다르다

| 오퍼레이션 | 계약 문장 | 400 선언 | 구현 |
|---|---|:-:|---|
| `GET /app/document-issues` | **「targetId 와 함께 준다. 하나만 주면 400 이다」**(`contracts/app-공통.json:1099`) | **있다** | 미구현 |
| `GET /app/approval-requests` | 「targetId 와 **함께 쓴다**」(`:612~`) | **없다** | ⭐ **독립 필터 둘**(`src/app/approval/approval-request.service.ts:149-150`) |
| **`GET /app/attachments`** | **「한 대상에 붙은 첨부를 낸다.」**(단수) | **없다** | (이 슬라이스) |

- 세 오퍼레이션이 **같은 물리 다형 쌍**(`target_type_code`, `target_id`)을 쓰는데 **계약의 강제 수준이 셋 다 다르다.** 문장만 보면 첨부는 document-issues 쪽(단수·짝 전제)에 가깝고, **응답 선언**만 보면 approval-requests 쪽(400 미선언)과 동형이다.
- 서버는 **응답 선언**을 따랐다. 이유는 하나다 — 이 저장소는 **「계약이 선언하지 않은 응답을 서버가 만들지 않는다」**를 이미 규약으로 못 박았다. 권한 가드가 같은 규약의 반대편을 지킨다: 계약이 403 을 선언하지 않은 자리에서 403 을 내면 계약과 어긋난다(`src/common/permissions/permission.guard.ts:37-41`).

**그 대가**: `?targetId=1001` 만 주면 **창고 1001 의 첨부와 공지 1001 의 첨부가 섞여서 온다.** 다형 id 는 유형이 다르면 같은 숫자가 다른 것을 가리키므로, 유형 없는 id 필터는 **의미가 겹친 목록**을 낸다. ⛔ 서버가 이것을 막지 않는다 — 막으려면 계약에 없는 400 을 만들어야 한다. 대신 **e2e 가 이 섞임을 «사실»로 단언해** 나중에 조용히 바뀌지 않게 고정한다.

### ⓑ 상한이 하나도 없다 — 전건을 낸다

- 계약에 **`PageMeta` 가 없고** 응답은 `{ items }` 하나다(required `items`). 질의는 `targetTypeCode`·`targetId` **둘뿐이고 둘 다 선택**이다. **`page`·`size` 도, 기간 칸도 없다.**
- 형제 `GET /app/document-issues` 는 `page`·`size` 를 갖는다(`:1052~`). 첨부만 없다.
- ⇒ **질의를 하나도 안 주면 전건이 나간다.** 서버가 `take: N` 을 넣지 않는다 — 넣으면 화면은 「전부」로 읽고 **잘린 줄 모른다**.
- 이것은 이 저장소에서 **처음이 아니다.** 질의 축 0 · `page`/`size` 0 인 **구현된** 컬렉션 GET 이 이미 서 있다: `GET /mdm/judgment-type-controls` · `GET /app/permissions` · `GET /integration/outbound-item-settings`(같은 모양이 9건까지 있다). 그중 `judgment-type-control.service.ts:44-61` 은 `findMany`(take 없음) + `{ items }` + 2키 `orderBy` 로 **첨부가 세우려는 모양 그대로**다.
- ⚠ **오늘의 위험은 0 이다** — 첨부 표에 **writer 가 0줄**(`POST` 가 이번 릴리스 밖)이고 DB **0행**이다. 계약이 준 상한도 작다: 창고 도면은 `drawingAttachmentId` 가 **스칼라**(1장) · 고장 사진은 계약이 **「최대 세 장」**. ⇒ **위험은 `POST` 가 열리는 릴리스로 미뤄진다.**

### ⓒ 정렬을 계약이 한 글자도 안 적었다

- `sort` 파라미터가 없고 description 에도 순서 언급이 없다. 그런데 목록은 **어떤 순서로든 나간다** — 정하지 않으면 DB 가 정하고, 그 순서는 릴리스마다 바뀔 수 있다.
- 서버 기본: **`uploadedAt` 내림차순 + `attachmentId` 내림차순.** 같은 모듈의 형제들과 같은 관행이다(`notification-query.service.ts:42` — `occurred_at desc, notification_id desc` · `notice.service.ts:138` — `start_date desc, notice_id desc`).
- **2차 키(`attachmentId desc`)를 반드시 둔다** — 같은 초에 올라간 두 첨부의 순서가 흔들리면 화면 목록이 새로고침마다 뒤바뀐다.

## 지금 서버는

**아직 없다.** 계획이 정한 동작:

- `targetTypeCode`·`targetId` 를 **각각 독립인 선택 필터**로 건다. 준 것만 `where` 에 넣고, **둘 다 없으면 조건 `{}`** 다(조건을 지어내지 않는다).
- **`take` 를 넣지 않는다.** 공용 페이지 헬퍼(`src/common/pagination`)를 부르지 않는다 — 그 헬퍼의 기본값은 `DEFAULT_SIZE = 50` 이고, 습관으로 부르면 **51건째부터 조용히 잘린다.**
- 정렬은 **`uploaded_at desc, attachment_id desc`** 로 명시 고정한다.
- 없는 대상은 **404 가 아니라 `200 { items: [] }`** 다 — `targetId` 는 경로가 아니라 **필터 축**이고, 계약이 404 를 선언조차 하지 않았다. ⚠ 그래서 응답에서 **「대상이 없다」와 「첨부가 없다」가 구분되지 않는다.**
- enum 밖 `targetTypeCode`(예: `BREAKDOWN`)와 정수 아닌 `targetId` 는 **계약 검증 가드가 400** 을 낸다(질의·경로는 `coerceTypes: true`). 서비스가 다시 막지 않는다.
- 응답에 **`storageKey`·`checksumSha256` 을 싣지 않는다** — 계약 `Attachment` 에 그 칸이 없다.

## ⇒ 알리는 것

1. **`targetTypeCode`·`targetId` 는 독립 선택 필터 둘이다** — 하나만 줘도 400 이 아니다. **`targetId` 만 주면 유형이 섞인 목록이 온다.** 화면은 **둘을 함께 주는 것**을 전제로 만들어 주십시오.
2. **페이지네이션이 없어 전건이 나간다** — 서버가 상한을 지어내지 않는다. 상한이 필요하면 계약이 먼저 열어야 한다.
3. **정렬은 `uploadedAt` desc + `attachmentId` desc 다** — 계약에 없어 서버가 결정론성 확보용으로 정했다. ⚠ **표시 순서가 화면 소관이면 알려 주십시오** — 같은 화면(`W-CO-04`)의 공지 표시 순서가 「§8 미결 5 — 권고 단계이지 확정이 아니다」로 열려 있다(`app-공통.json:2277`). 화면 규칙이 서면 그쪽을 따른다.
4. 계약에 되돌릴 것(택일·전부 선택): ⓐ 짝을 강제하려면 **`GET /app/attachments` 에 400 을 선언**해 주십시오(문장만 단수인 지금 상태로는 서버가 400 을 만들 근거가 없다) ⓑ 상한이 필요하면 **`page`·`size`·`PageMeta`** 를 열어 주십시오 ⓒ ⭐ **같은 다형 쌍을 쓰는 셋(`attachments`·`document-issues`·`approval-requests`)의 강제 수준을 한 벌로 맞춰** 주십시오 — 지금은 셋이 다 달라서, 화면이 「이 쌍은 이렇게 부르면 된다」를 한 번에 배울 수 없다.
