# 162. 재고 이동이 진행 조회에서 「전기 완료」로 **먼저** 그려지고, 적치와 겹친 판별자는 **전표 번호로만** 갈린다

> ⚠ **다섯 다 「오늘 서버가 정하고 구현한 것」이다.** 회신을 기다리지 않는다.
> ⭐ 이 문의는 **C 대역(120~149)의 통보 `059`·`123`·`124` 와 `031` 을 «가리키기만» 한다** — 그 본문은 한 글자도 고치지 않았다.

## 무엇이 문제인가

### ⓐ 통보 **059** 의 판별 규칙을 서버가 처음 구현했다 — 다만 식은 「PT- 거부」가 아니라 「이 전표의 번호로 양성 판별」이다

- 적치가 재고 이동과 **같은 판별자**로 원장을 쌓는다 — `putaway-posting.ts:18` `SOURCE_DOCUMENT_TYPE = 'STOCK_TRANSFER'` · `:53` `sourceDocumentId: move.putawayTaskId`. ⇒ `(STOCK_TRANSFER, N)` 이 **두 표의 N** 을 뜻한다.
- I-13 이 `stock_transfer` 행을 처음 세우므로 **오늘부터 실재하는 겹침**이다. `putaway_task_id === stock_transfer_id` 인 순간 `GET /logistics/document-progress/STOCK_TRANSFER/{id}` 가 **남의 적치 원장**을 `POSTED` 줄로 그린다(번호·영업일·발생시각 셋 다 남의 값).
- 059 는 판별 규칙을 **`transaction_no LIKE 'PT-%'` = 적치 · `NOT LIKE 'PT-%'` = 재고 이동**으로 정했다.
- ⛔ **서버는 그 규칙을 «거부 목록»으로 구현하지 않았다** — 거부 목록은 **같은 판별자를 쓰는 쪽이 늘 때마다 자란다**(셋째가 생기면 조용히 뚫린다). 대신 **이 전표가 남기는 번호로 양성 판별**한다:
  `transaction_no: { in: [<이 전표의 stock_transfer_no>, <그 번호>+'-A'] }`.
- 그래도 **안전한 근거는 접두 검색이 아니다** — 같은 `where` 가 이미 `source_document_type_code` + **`source_document_id`** + `reversal_of_transaction_id: null` 로 행을 좁힌다(`document-progress-query.service.ts:227`). 그 위에서 **이동 원장 번호가 정확히 둘로 «구성상» 닫혀 있다**(`ST-…` 반출 · `ST-…-A` 도착 — `transfer-posting.ts:28,136,303`).
- ⛔ **`putaway-posting.ts` 는 한 줄도 고치지 않았다** — 이미 쌓인 원장 행은 트리거가 정정을 막는다(059 가 못박은 자리 · `trg_inventory_transaction_immutable` 은 BEFORE DELETE OR UPDATE 만 건다).
- ⛔ **다른 여덟 유형에는 축을 안 얹었다** — 겹칠 자리가 0이고, 얹으면 새 개념이 아홉 배로 는다.

### ⓑ `GET /inventory/transactions?sourceDocumentTypeCode=STOCK_TRANSFER` 는 **여전히 둘을 섞어 낸다**

- 문서진행 조회만 갈랐다. 원장 목록 조회는 적치·이동을 **가르는 질의 축이 0**이다.
- 가르는 유일한 단서는 **응답의 `transactionNo` 문자열**(`PT-` / `ST-`)뿐이라 **클라이언트가 문자열로 가른다.**
- ⚠ **오늘부터 실제로 섞인다**(I-13 병합 시점). `I-12.md` §9-3 이 예고한 자리이고 059 와 짝이다.
- ⇒ 질의 축(예: `documentSubTypeCode` 또는 `transactionNoPrefix`)을 계약에 세울지는 **설계 몫**이다. 서버는 계약에 없는 필터를 지어내지 않았다.

### ⓒ 진행 조회의 `POSTED` 줄이 «반출» 원장이다 — 화면에는 이렇게 보인다

> `W-01-13` 물류 문서 진행현황 상세에서, **반출만 끝난** 재고 이동이 **「전기 완료」 줄을 이미 가진 채** 그려진다. 같은 화면의 상태는 **`REGISTERED`** 이고 처리 수량(`processedColumn: 'received_qty'`)은 **0** 이다 — 사용자는 「전기 완료인데 처리 수량이 0이고 상태는 등록」인 한 줄을 본다. **도착 뒤에도** POSTED 줄의 번호·영업일은 **반출** 원장 것이다(`orderBy: { occurred_at: 'asc' }` 라 첫 원장을 집는다).

- 뿌리는 **한 문서가 원장을 «둘» 남기는 첫 사례**라는 것이다(반출 `ST-…` · 도착 `ST-…-A`). I-5 가 세운 「원장 행이 있으면 POSTED 줄」 규약이 **처음 어긋난다.**
- ⛔ **서버가 규약을 뒤집지 않았다** — I-5 의 판정을 이 슬라이스가 바꿀 자리가 아니다. e2e 가 **현재 동작을 못박는다**(「진행 조회의 POSTED 줄은 반출 원장이다」).
- ⇒ 설계가 답할 것은 **「그대로 두라」 / 「두 줄로 갈라라」**(반출·도착을 각각 한 줄로) 둘 중 하나다. 어느 쪽이든 조회 코드만 바뀐다.
- ⚠ 같은 뿌리의 자리 하나 — **부분 도착의 잔여**를 터는 유일한 길이 재고 조정이다(**문의 124** 의 dead end).

### ⓓ `PUT …/lines` 를 **자물쇠까지만** 구현했고, 통보 123 이 안 적은 널 갈래는 **명시적 파열(500)** 로 닫았다

- **하는 것**: 부모 전표를 `SELECT … FOR UPDATE` 로 잠그고 → 없으면 404 → `version_no` 가 If-Match 와 다르면 409 → `shipped_at` 이 차 있으면 **400 `STATE_LOCKED`**.
- **안 하는 것**: 본문 `items` 를 **한 칸도 읽지 않는다**(빈 배열도 안 본다 — 형제 출고는 `LINE_REQUIRED` 로 막는데 여기는 «일부러» 뺐다. 치환 본체가 없어 볼 이유가 0이다) · 라인을 만들지도 고치지도 지우지도 않는다 · 부모 `version_no` 를 올리지 않는다 · ETag 를 내리지 않는다.
- 근거는 **통보 123 이 예고한 그대로**다 — 반출 전 상태를 만드는 오퍼레이션이 계약 487건에 **0건**이고(`POST` 가 생성·반출을 한 번에 하며 `x-internal-note` 가 `:depart` 를 없앴다), 치환 본체는 **호출자가 0인 코드**다.
- ⭐ **123 이 안 적은 자리** — 「`shipped_at IS NULL`」 갈래. 여기서 400 을 «같이» 내면 **「`shipped_at` 을 아예 안 읽고 무조건 400」 구현과 모든 테스트가 같아져** 자물쇠가 조용히 사라져도 아무도 못 본다. ⇒ **`throw new Error('반출 전 재고 이동 전표가 실재한다 — 계약 전제가 깨졌다(문의 123).')`** 로 닫았다(응답은 `INTERNAL_ERROR` 한 줄 · 던진 문장은 로그에만 남는다). 501 은 쓰지 않았다 — 계약 응답 선언 밖의 «정상» 코드를 새로 여는 것이고 저장소 선례가 0이다.
- ⭐ **규칙 문장 — `stock_transfer` 를 만드는 «모든» 오퍼레이션은 `shipped_at` 을 반드시 채운다.** 안 채우면 위 파열이 **운영 500** 으로 터진다. 특히 **`POST /logistics/stock-reinstatements`**(재고 재등록 · 미구현)가 `received_at` 만 채우면 그 전표에 화면이 `PUT …/lines` 를 부르는 순간 500 이다. 근거는 계약 04 의 `x-internal-note` 가 재등록의 산출물을 «이동 문서»로 부른 자리다.
- ⚠ **409 의 「다시 읽어 오면 풀린다」가 이 오퍼레이션에서는 거짓이다.** 계약이 400 을 「고쳐야 풀린다」, 409 를 「다시 읽어 오면 풀린다」로 갈라 적었는데(C7 · `ErrorItem.code` 설명 C17 · 공유계약 G-1), 여기서는 **어긋난 토큰으로 온 호출이 409 를 받고 재조회해도 다시 400 `STATE_LOCKED`** 를 받는다. 400 조건이 **오늘 존재하는 모든 전표에 언제나 참**이기 때문이다(형제 출고의 400 조건은 일부 전표에만 참이라 이 문제가 없다). 순서(404 → 409 → 400)는 형제 둘·RFC 9110 선행조건 평가 순서를 따라 **그대로 두었고**, e2e 가 「409 뒤 재조회 → 같은 호출이 400」을 못박는다. **G-1 의 예외 자리로 알린다.**

### ⓔ `PUT …/lines` 의 403 소유 화면 `M-01-10` 은 **근거가 있다** — 문의 123 ⓕ 의 「근거 없는 등록」이 닫힌다

- `manual-permissions.ts:260` 이 이 오퍼레이션에 `['M-01-10']` 를 등록해 두었고(I-13 PR ① · 커밋 `852294a`), 그 주석과 **문의 123 ⓕ** 는 「부르는 화면이 0건이라 **잠정**·**근거 없는 등록**」이라 적었다.
- ⭐ **근거가 저장소 안에 있었다** — `docs/coverage-100/plan-uiux.md:852`(§5-3)가 **「물류 자식 치환 PUT 7 건은 전부 부모 자원 GET 의 ETag 를 If-Match 로 쓰므로 «부모의 화면이 곧 이 오퍼레이션의 화면»이다」**라는 **규칙**을 세우고 `stock-transfers` 라인에 **`M-01-10`** 을 붙였다. 형제 7건(`inbound-receipts` 헤더·라인 · `purchase-orders` 헤더 · `goods-issues` 라인 · `adjustments` 라인 · `lots/external-identifiers`)이 **같은 규칙으로** 붙었다.
- ⇒ **「근거 없는 등록」이 아니다 — UI/UX 정본이 규칙으로 부여한 것이다.** 문의 123 ⓕ 가 열어 둔 물음(「소유 화면을 지정해 403 근거를 준다」)은 **이 규칙으로 닫힌다.** ⛔ 123 본문은 C 대역이라 고치지 않았고, 이 문의가 가리킨다.
- ⚠ 함께 알린다 — **「부르는 액션이 0건」과 「소유 화면은 `M-01-10`」이 동시에 참**이다. `plan-uiux.md:254` 는 이 오퍼레이션의 화면 칸을 「—」로 적었고 `M-01-10` §5-6 액션 7종에 「라인 편집」이 없다. 이 슬라이스가 연 6 오퍼레이션 중 **화면이 부르지 않는 것은 `PUT …/lines` 하나**다.

## 지금 서버는

- **아직 없다(I-13 PR ④ 미착수).** 계획이 정한 동작: 진행 조회의 `STOCK_TRANSFER` 갈래에만 **번호 축 하나**(양성 판별 · ≈9줄) · `PUT …/lines` 는 **잠그고 404 → 409 → 400** 까지만 · 널 갈래는 **명시적 파열(500)** · 본문 `items` 는 **한 칸도 안 읽는다**.
- 마이그레이션 **0** · `schema.prisma` **0줄** · 새 `ERROR_CODE` **0**(500 갈래의 `INTERNAL_ERROR` 는 표 밖 상수) · 코어 파일(`transitions.ts`·`error-codes.ts`) **0** · 권한표 **0줄**(이미 등록돼 있다) · 적치 코드 **0줄**.
- e2e 가 반대 갈래를 반드시 지켜본다 — 「**`shipped_at` 이 널인 전표는 500 으로 터진다**」(이 단언이 없으면 「무조건 400」 구현과 모든 테스트가 같아진다) · 「**같은 id 의 `PT-` 원장을 안 집는다**」(축이 지워지면 즉시 빨개진다) · 「**POSTED 줄은 반출 원장이다**」(ⓒ 의 현재 동작 고정).

⇒ **알리는 것**: ⓐ 059 의 판별 규칙을 **양성 판별로** 구현했고, ⓑ 원장 **목록** 조회는 여전히 적치와 이동을 섞어 내며(질의 축 0), ⓒ 진행 조회가 **반출만으로 「전기 완료」 줄을 세우고 도착 뒤에도 반출 원장을 집으며**, ⓓ `PUT …/lines` 는 **자물쇠까지만**이고 널 갈래는 **500 으로 파열**하며 **409 의 「다시 읽으면 풀린다」가 이 자리에서는 거짓**이고, ⓔ 그 오퍼레이션의 **403 소유 화면 `M-01-10` 에는 근거가 있다**(123 ⓕ 가 닫힌다). 다섯 다 되돌리는 비용이 작다.
