## 이 전달분을 읽는 법

요청서는 **174건**이다. 다 읽으실 필요는 없다.

| 먼저 | 무엇 |
|---|---|
| **§0** | **답이 와야 서는 자리 — 5건.** 이것만 막고 있다 |
| §7 | 횡단 — 채번·시드·화면 통지. **짧고 대부분 「값 하나만 주시면」이다** |
| §8 | 배포 노트 — 현장에 미리 알릴 것 |

⛔ **레인(A·B·C·A2)으로 묶지 않았다.** 레인은 우리 사정이고, 레인 C 가 멈춘 뒤 슬라이스가
인계되면서 **같은 주제가 두 대역에 갈렸다**(취급단위 = 140~145 + A2 몫 · 출하지시 = 190~208 ·
재생재 = 213~216). **주제로 묶었다** — 레인은 추적용으로 끝 칸에만 남긴다.

## §7. 횡단 — 값 하나씩만 주시면 되는 것들

### 7-1. 채번 표(최초 문의 **14**)에 더할 세 행

구현된 접두어를 **실측**해 적는다(`src/core/numbering/numbering.service.ts`).

| 문서 | 컬럼 | 접두어 | 기간 축 |
|---|---|:-:|---|
| 재고 이동 | `stock_transfer_no` | **`ST`** | `ST-{YYYYMMDD}-{SEQ4}`(계약 example 은 접두어만 준다) |
| 재고 조정 | `inventory_adjustment_no` | **`IA`** | 서버 UTC 날짜 — 본문에 날짜 칸이 0개다(통보 135) |
| 취급 단위 | `handling_unit_no` | **`HU`** | 서버 UTC 날짜 — `HandlingUnitCreate` 에 날짜 칸이 0개다(통보 144ⓒ) |

⚠ 뒤 둘은 **하노이(UTC+7) 00:00–07:00 등록이 전날 번호를 받는다.** 본문에 날짜 칸이 없어
서버 시각 말고 쓸 축이 없다. 날짜 칸을 열어 주시면 바꾼다.

### 7-2. 시드·코드사전 — 5건

|:-:|---|---|:-:|
| 1 | `LOT_HOLD_RELEASE_REASON` | ⛔ **시드 4값에 없는 `INCOMING_INSPECTION_PASSED` 를 서버가 쓰고 있다.** 「1회차 수입검사 합격」에 맞는 값이 4값에 하나도 없는데 `ck_lot_hold_release_reason` 이 사유를 강제한다(질의 087). ⚠ `lot-hold-events` 화면이 열리면 **표시명이 빈 칸으로 나간다** | ⭐ |
| 2 | `PRODUCTION_RESULT_CORRECT_REASON` | 그룹은 있는데 **값이 0개**다(`values: []`) — 실적 정정 사유 드롭다운이 빈다 | |
| 3 | `LATE_ENTRY_REASON` | 같은 모양 — **값 0개** | |

### 7-3. 화면 통지 — 3건

설계 화면과 서버가 어긋나는 자리다. **회신은 필요 없고, 화면 정본을 고쳐 주시면 된다.**

- `W-02-04` — 전달사항(`handoverNote`)을 **저장하지 않는다**(담을 칸이 계약·물리 양쪽에 없다)
- `W-02-05` — 이월 라디오가 서버 축과 안 맞는다
- `W-02-08` — 달성률 **정렬은 400** 이다(계약 「정렬 키는 제한한다」 L-4 · 허용 키는 응답이 가진 넷) · 세션 열 부재

### 7-4. 헤더 규약 — 요청서 셋 (색인 §7)

| # | 무엇 |
|:-:|---|
| **069** | `businessDate` 의 **야간조 경계 도출 규칙이 없다** — ⛔ 도출 함수를 만들지 않는다. 클라이언트 값을 그대로 쓴다 |
| **242** | 같은 `X-Worker-No` 인데 **어떤 오퍼레이션은 없는 사번을 막고 어떤 것은 통과시킨다**(16 대 7). ⚠ 오프라인 큐가 옛 사번으로 재전송하면 **한쪽에서만 영영 안 들어간다** |
| **243** | 사번 **50자 초과**를 여섯은 `RANGE`, **설비 고장 하나만 `INVALID`** 로 낸다 |

⛔ 셋 다 **동작을 안 바꿨다** — 바꾸면 현장 응답이 바뀌는 자리라 정해 주셔야 한다. 그때까지
갈림 자체는 `worker-no.spec.ts` 가 **세고 있어** 조용히 달라지지 않는다.

### 7-5. ⭐ 클라이언트 개발팀에 전해 주십시오 — 지금 고칠 수 있는 것

> **재고 조정 화면의 사유 드롭다운이 빈 채로 보입니다.**
> 프론트가 코드 그룹을 **`ADJUST_REASON`** 으로 하드코딩했는데, 계약·서버·시드가 모두 쓰는 실제
> 그룹은 **`INVENTORY_ADJUSTMENT_REASON`** 입니다(`prisma/seed.ts:604` ·
> `inventory-adjustment-rules.ts:14` 실측). 그룹 코드만 바꾸면 값이 채워집니다.

⚠ 이 한 건은 **설계 판정이 아니라 클라이언트 수정**이다. 회신 대기 더미에 섞이지 않게 따로 뒀다.

## §8. 배포 노트 — 현장에 미리 알릴 것

「고쳐 달라」가 아니라 **「이렇게 동작하니 알고 계시라」**는 것들이다.

| # | 무엇 |
|:-:|---|
| 1 | **결재함**이 `openable=false` 다 — 목록은 보이나 해당 화면으로 못 넘어간다(대상 화면이 계약에 없다) |
| 2 | **`M-01-13`** 은 계정 세션이 필요하다 — 단말 토큰만으로는 안 선다 |
| 3 | **라벨 POP 8화면**이 발행 경로를 공유한다 |
| 4 | **프린터 상태가 `OFFLINE` 고정**이다 — 실제 상태를 받을 축이 없다 |
| 5 | **반쯤 열리는 화면 셋** — `M-01-08` · `M-01-10` · `W-02-05` |
| 6 | ⭐ **자재 반출분은 재고 수불에 안 잡힌다**(통보 051) — 실사 때 **라인 재고가 장부보다 적게 나오는 원인**이다. 반출 기록은 온전해 소급 전기는 가능하다 |
| 7 | **W/O 단위 계보**(회신 052 반영분) |
| 8 | ⭐ **이동 중(`IN_TRANSIT`) 품목은 조정·실사 차이 닫기가 오늘 400** 이다 |
| 9 | ⭐ **불량 반출 사유가 저장되지 않는다**(질의 **122** 대기 — 요청 스키마에 칸이 없다). 화면이 받는 값이 **어디에도 안 남는다** |
| 10 | **재고 조정 사유 드롭다운이 빈다** — 7-5 참조(클라이언트 수정) |

### 8-1. 「승인 없이 나간 폐기 출고」를 세는 질의 (통보 **030** 딸림)

서버는 **「상신 흔적이 있는 전표만」** 승인을 강제한다(계약 `GoodsIssue.approvalRequestId` 가
「승인 없이 나간 건을 **사후에** 가려낸다」로 그 존재를 이미 인정했다). ⭐ 회신이 「전건 차단」으로
와도 **소명할 목록이 나오도록** 질의를 확보해 둔다:

```sql
SELECT gi.goods_issue_id, gi.goods_issue_no, gi.posted_at
  FROM logistics.goods_issue gi
 WHERE gi.status_code = 'POSTED'
   AND NOT EXISTS (SELECT 1 FROM app.approval_request ar
                    WHERE ar.target_type_code = 'GOODS_ISSUE'
                      AND ar.target_id = gi.goods_issue_id
                      AND ar.approval_type_code = 'GOODS_ISSUE_DISPOSAL');
```

## §9. 안 만든 것 — 5건 + 부분 3

계약 오퍼레이션 **487** 중 **482 를 만들었다**. 나머지 다섯은 **못 만든 것이 아니라 «안» 만든 것**이고,
사유가 각각 다르다.

| 오퍼레이션 | 왜 |
|---|---|
| `POST /app/attachments` · `GET /app/attachments/{id}/content` · `POST /maintenance/breakdowns/{id}/attachments` | **파일 저장소가 이번 범위 밖**이다 — 바이너리를 어디에 둘지(로컬·객체 저장소·경로 규약)가 정해지지 않았다. 첨부 «메타»는 이미 다른 오퍼레이션이 다룬다 |
| `GET /app/document-issues/{id}/rendition` | 같은 이유 — 렌더링 산출물의 저장·수명 규약이 없다 |
| `GET /app/dashboard-summary` | **집계 대상이 되는 도메인이 다 서야** 뜻이 있는 화면이라, 마지막까지 미루다 **이번 범위에서 뺐다**(2026-09-10 결정) |

**부분 건너뜀 셋** — 오퍼레이션은 서지만 일부 축이 빈다:

| 자리 | 안 한 부분 |
|---|---|
| `:resync` | 재송신 «축»이 없다 — 무엇을 다시 보낼지 정하는 규약이 계약에 없다 |
| `work-orders:close` · `shipments:confirm` | **아웃박스 적재까지**만 한다 — 그 뒤 실제 송신은 연동 몫이다 |
| `zaloEnabled` | **칸만** 받는다 — 실제 Zalo 발송 경로가 없다 |

## 채우는 규칙

1. **§0~§6 은 손대지 않는다** — `python3 scripts/design_inquiries/build_delivery_index.py` 가 만든다.
   요청서를 더하거나 「구분」을 바꾸면 다시 돌린다. `--check` 로 낡았는지 본다.
2. **요청서에 `**구분: 질의|통보**` 한 줄을 넣어라** — 넣으면 색인이 저절로 잡는다. 안 넣으면 §9 에 남는다.
3. **답이 온 질의는 그 파일에 「회신」 절을 더하고 구분을 통보로 내린다**(213 이 그 본보기다).
   그러면 §0 에서 저절로 빠진다.
4. **§7·§8 은 손으로 쓴다** — 판정이 들어가는 자리라 기계가 못 만든다.
