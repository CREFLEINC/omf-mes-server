# 119. 툴 증분 환산과 누계 귀속

| 칸 | 내용 |
|---|---|
| 걸리는 오퍼레이션 | POST `/maintenance/tool-usages`, GET 목록·상세의 선택 누계 쌍 |
| 구현 상태 | I-33 R1/R2/R13 계획 확정·구현 전. 제출 증분을 보존하고 같은 tx에서 툴 누계/version을 갱신 |
| 판정 | 0단계 P-05-01의 화면 증분 결정/서버 누적 반영과 required shotCount. DIRECT 환산값은 가장자리② 거부. 과거 선택 누계는③ 칼럼 추가0·④ 도출0 |
| 되돌릴 때 | 환산 반올림/입력 정책과 누계 이력 요구가 확정되면 해당 소비자와 저장·응답 규칙만 보완. 기존 제출 이력 재계산0 |

고정 P-05-01 §5-2와 Create의 required shotCount에 따라 **화면이 정한 양의 안전 정수 증분**과 환산 근거를 보존한다. `CONVERSION_SHOT_POLICY='PRESERVE_SUBMITTED'`는 미정이라 임의 선택한 값이 아니라 입력 권한의0단계 근거다. CONVERTED의 base·ratio는 양수 numeric(20,6)에 손실 없이 담아야 하고, DIRECT에 숫자 환산 근거를 보내면 `DIRECT_CONVERSION_POLICY='REJECT_VALUES'`·400 INVALID로 거부할 계획이다.

**확인 요청:** base×ratio가 소수인 경우 화면이 shotCount를 결정하는 반올림/절사·최소증분 규칙과 표현 정밀도를 정해 달라. 현재 client `tool-usage/conversion.ts:87`의 Math.round는 실제 소비자 구현이지 승인된 서버 정책으로 간주하지 않는다. 예를 들어 base3×ratio0.5에서 제출 shotCount=2이면 서버는2와3/0.5를 그대로 남긴다. 곱을 엄격 대조해 거부하거나 현재 operation_policy·cavity를 다시 곱해 오프라인 증분을 바꾸지 않는다.

툴 비키 누계+version을 `FOR NO KEY UPDATE`로 직렬화하고 같은 tx에 이력·updated_by·최신누계/cumulativeAsOf 응답·멱등완료를 묶는다. occurredAt은 현장 발생시각, cumulativeAsOf는 master 갱신 기준시각이라 서로 대체하지 않는다. production의 실제 W/O잠금→mold FK 작성자와 FK KEY SHARE 호환성을 배리어 테스트로 확인할 계획이다. 계획상 잠금 분석을 실측 PASS로 보고하지 않는다.

GET에는 당시 누계 snapshot이 없으므로 선택 cumulativeShotCount/cumulativeAsOf 쌍을 생략한다(`TOOL_USAGE_HISTORY_CUMULATIVE='OMIT'`). SUM(과거이력)이나 현재master를 각 과거 행의 당시 누계처럼 반환하지 않는다. **시점별 과거 누계가 필요하다면 reset/정정 사건을 포함해 어떤 정본 이력으로 재구성할지 확인해 달라.** 선택칸을 채우기 위한 snapshot칼럼2를 선제 추가하지 않는다.

I-31의 resetCounter=true는 날짜 원천 미정 때문에 현재 전건422·쓰기0이다(114). 누계만 리셋하고 PM 날짜는 미반영한 반쪽201은 하지 않는다. 정상 nonreset 보전과 툴 증분 동시성은 현재 인수 범위, reset 성공과의 교차 검증은114 해소 뒤 조건부다. 입력 µs/SQL 표현은109, 귀속·동일 tx는096, 숫자 무손실 경계는097과 연계한다.

흔적: I-33 E-T01/07/08/12~15/18/19, DIRECT 부적합 전건 rollback·두 증분의 누계합/version·기존 MDM CAS·실제 production FK 경합·동일키 재생. 계약 a6a87e1 고정, 생산실적·원장·자동PM·기존 이력 수정0이다.
