# 131. 조정 라인의 실사 원천 칸이 물리에 없고, 그 칸에 실사 마감 판정이 달려 있다 — 계약 `x-internal-note` **넷**이 낡았다

| 칸 | 내용 |
|---|---|
| 걸리는 오퍼레이션 | `POST /inventory/adjustments` · `PUT /inventory/adjustments/{id}/lines` · `GET /inventory/adjustments/{id}/lines` |
| 구현 상태 | **미구현** — 조회 3건만 병합됐고(`main`) 등록·치환은 아직 없다. 마이그레이션도 아직 안 나갔다 |
| 판정 | `coverage-100/README.md` §2 **1단계 가장자리**(실사에서 불러온 라인에만 붙는다) → 2단계 **기준 4**(계약이 정의한 값을 조용히 버리지 않는 쪽). 기준 3(스키마를 안 늘림)도 「늘려야 하면 nullable」이라 nullable 추가를 막지 않는다 |
| 되돌릴 때 | 「칸을 두지 않는다」면 마이그 한 건을 되돌린다(두 표 다 0행이라 백필 0). 다만 I-15 실사 마감 판정이 헤더 축으로 물러선다 |

## 무엇이 문제인가

**ⓐ 계약이 요청·응답 둘 다에 정의한 칸이 물리에 없다.**
`InventoryAdjustmentLine.inventoryCountLineId` — ⌜실사 차이에서 불러온 경우의 원천 라인⌝(`contracts/logistics-01자재창고.json:9900-9908`) · `InventoryAdjustmentLineUpsert.inventoryCountLineId`(`:9981-9988`). 물리 `inventory_adjustment_line` 은 14칸인데 그 이름이 **0건**이다(`prisma/schema.prisma:4023-4048` · DB `information_schema.columns` 실측).

**ⓑ ⭐ 계약 `x-internal-note` **넷**이 「이 표는 아직 없다」로 남아 있다 — 표는 실재한다.**
전부 같은 문장이다 — ⌜`inventory_adjustment_line` 은 물리 모델에 **아직 없다**. #88 회신으로 신설이 확정됐고 이 계약은 다른 전표의 라인과 같은 형태로 먼저 정의한 것이다 — 조정 대상⌝.

| 자리 | 줄 |
|---|---|
| `POST /inventory/adjustments` | `contracts/logistics-01자재창고.json:190` |
| `PUT /inventory/adjustments/{id}/lines` | `:361` |
| `InventoryAdjustmentLine`(응답 스키마) | `:9949` — 여기에만 ⌜**라인 사유를 담을 자리도 함께 확정돼야 한다**(W-01-12 §5-1)⌝ 가 붙어 있다 |
| `InventoryAdjustmentLineUpsert`(요청 스키마) | `:10028` — 위 문장은 **없다** |

실측으로는 표도 `reason_code`(NOT NULL · `schema.prisma:4034`)도 이미 있다. **빈 것은 `inventory_count_line_id` 하나뿐이다** — 노트가 「표 전체가 없다」라고 적어 두어 그 하나를 가린다.

**ⓒ 헤더 축만으로는 실사 마감을 판정할 수 없다.**
헤더에는 `inventory_count_id` 가 있다(`schema.prisma:467`). 그런데 실사 마감 조건은 라인 축이다 — `W-01-04-재고실사.md:212` ⌜**실사 마감** — **미실사 = 0** AND **차이 = 0 또는 조정 완료**(§5-5)⌝. 헤더 축만으로는 화면 `W-01-12` §3 ①이 그린 「차이 **6건**」 중 **4건만 조정한 상태**를 가를 수 없다.

**ⓓ 값을 버리면 화면이 되읽기를 기대한 자리가 빈다.**
계약이 이 칸을 **응답에도** 두었으므로 화면은 「이 조정 라인이 어느 실사 라인에서 왔는가」를 되읽을 수 있다고 본다. 서버가 요청에서 받아 버리면 응답에 채울 원천이 사라진다.

**ⓔ ⭐ 두 화면이 서로를 선행으로 요구한다 — 순환이다.**
`W-01-12-재고조정.md:227` 은 ⌜실사가 마감되지 않음 → **⛔ 차단** — `W-01-04`에서 마감 후⌝ 라 적었고, `W-01-04-재고실사.md:212` 는 반대로 ⌜마감 = … 차이 = 0 **또는 조정 완료**⌝ 라 적었다(같은 문서 `:249` 미결 #3 ⌜차이가 있을 때 조정 없이 마감할 수 있나 — 마감 차단으로 시작⌝). **조정은 마감 뒤에, 마감은 조정 뒤에**다. 어느 쪽도 서버가 강제할 수 없다 — 그래서 서버는 실사 마감 여부를 **검사하지 않기로** 했다(`inventoryCountId` 는 FK 존재만 본다). 이 순환은 두 화면 중 하나를 고쳐야 풀린다.

## 지금 서버는

- **아직 없다.** 등록·치환이 미구현이라 이 칸을 받는 코드가 0 이고, 물리 칸도 아직 없다.
- 계획된 동작은 **칸을 더하는 것**이다 — `inventory_adjustment_line.inventory_count_line_id BigInt?` + FK(`inventory_count_line`) + 인덱스 1. 두 표 다 0행이라 백필이 없다. 선례는 I-24 R-1(`production_plan.split_reason_code`)·I-7 D2(`production_result.correct_reason_code`) — **계약이 정의한 칸을 물리에 더한 자리**들이다.
- 실사 마감 여부는 **검사하지 않는다**(위 ⓔ).

⇒ **묻는 것**: 조정 라인에 실사 원천 칸을 두는 것을 계약이 인정하는가 · 실사 마감의 「조정 완료」를 **라인 축**으로 잴 것인가(그리고 ⓔ 의 순환에서 어느 화면 문장을 고칠 것인가).

「알려둘 것」으로 함께 보내는 것(문의 아님): 계약 노트 넷(ⓑ)은 회신 없이도 지울 수 있는 **문서 정정**이다 — 표·`reason_code` 는 실재하고, 화면 `W-01-12` §8 #1 은 「✅ 해소 2026-09-02」로 **미결 표만** 닫았지 본문 §4-B·§5-1·§5-2·§5-6 은 아직 「라인 표 없음」 전제로 남아 있다.
