# 076. 부분 보류 한도의 **「보유 수량」**을 무엇으로 재나 — 잔액 행이 0건인 LOT 은 부분 보류가 영영 막힌다

**구분: 통보**(회신을 기다리지 않는다 — `coverage-100/README.md` §2 1-1단계 「본질 아님 × 비용 낮음」)

| 칸 | 내용 |
|---|---|
| 걸리는 오퍼레이션 | POST `/quality/lot-holds` (I-20 PR ④) |
| 구현 상태 | 구현함 — 「보유」 = `inventory.inventory_balance.on_hand_qty` 의 **`lot_id` 축 합**. 열린 보류 합(`released_at IS NULL` 인 `hold_qty` 합) + 신규 `holdQty` **>** 보유이면 409 `HOLD_QTY_EXCEEDED` |
| 판정 | §2 1단계 **가장자리**(`holdQty` 를 보낸 요청에서만 갈린다) → 2단계 **기준 2**(거부하는 쪽 — 거부→허용이 호환 완화) · **기준 1**(재고·원장을 안 쓴다) |
| 되돌릴 때 | `assertHoldQtyWithinOnHand()` 의 집계 한 줄(`where`) 뿐이다. 서비스 구조·계약·마이그 변경 0 |

## 계약이 준 것과 안 준 것

계약은 **뜻**만 적었다 — 「`HOLD_QTY_EXCEEDED` 는 **부분 보류 합계가 보유 수량을 넘는다**는 뜻이다.
서버가 판정한다 — 화면이 계산하지 않는다」(`QualityConflictResponse.code` 설명).
⛔ 「보유 수량」이 어느 표의 어느 칸인지는 **한 자리도 안 적었다.**

## 정한 것 — 셋

**ⓐ 원천은 `inventory_balance.on_hand_qty` 다.** 계약이 **막은 것**이 길을 좁혔다 —
「⛔ `inventory_balance.blocked_qty` 는 쓰지 않는다 — 잔액은 서버가 파생한다(L-2)」(`:1845`)와
「⛔ `inventory_balance` 를 (보류량의) 정본으로 쓰지 않는다」(`:4299`). 두 문장이 막은 것은
**보류량**이지 **보유량**이 아니다. `trace.lot.initial_qty` 는 「태어날 때 수량」이라 소비·출고를
반영하지 않으므로 오늘 보유를 말할 수 없다 ⇒ 남는 축은 `on_hand_qty` 하나다.
⛔ GENERATED 칸 `available_qty` 도 안 본다 — 그 식에 `blocked_qty` 가 들어 있다.

**ⓑ 차원을 접는다.** 한 LOT 의 잔액 행은 창고·위치·품질상태·단위로 갈려 여럿일 수 있는데
`lot_hold` 에는 그 차원 축이 **`uom_id` 하나뿐**이고 그것도 `uq_inventory_balance_dim` 밖이다
(문의 **075** 와 같은 자리). 보류는 「이 LOT 을 얼마나 묶어 둔다」이지 「어느 창고의 이 LOT 을」이
아니므로 **`lot_id` 축 전건을 합한다.** ⚠ 단위 환산은 하지 않는다 — 환산표를 볼 자리가 계약에 없다(075).

⚠ **접는 축에 `ownership_type_code` 가 없다** — 사급(고객 지급)·수탁 재고의 잔액 행도 「보유」로
함께 센다(PR #389 리뷰 Nit-5). 소유가 우리 것이 아닌 수량까지 보류 한도에 넣는다는 뜻이라
**대가가 있는 선택**이다. 그 축을 빼야 한다면(= `ownership_type_code = 'OWNED'` 만 센다) 알려 달라 —
집계 `where` 한 칸이다. 오늘 안 뺀 이유는 위 ⓑ 와 같다: `lot_hold` 에 소유 축이 **없어** 보류 쪽과
잔액 쪽의 차원이 어차피 어긋나고, 좁히는 쪽이 「보유보다 큰 보류」를 더 쉽게 만든다.

**ⓒ 잔액 행이 0건인 LOT 은 보유 0 이라 `holdQty` 를 못 건다(409).**
입하 직후·재고에 안 잡힌 LOT 이 여기 걸린다. **전량 보류(`holdQty` 생략)는 그대로 된다** —
전량은 `hold_qty IS NULL` 이라 수량 판정 자체를 지나지 않는다. 즉 막히는 것은 **「수량을 적은
부분 보류」 하나**고, 화면은 수량을 지우면 그대로 걸 수 있다.

## 왜 「거부」인가

§2 2단계 **기준 2** — 「거부하는 쪽. 거부→허용은 호환 완화, 허용→거부는 깨는 변경」.
보유를 모를 때 통과시키면 그 LOT 은 **보유보다 큰 보류**를 갖고 화면의 `availableQty`
(= `onHandQty − heldQty`)가 **음수**가 된다. 계약은 그 칸에 음수를 정의하지 않았고, 되돌리려면
이미 쌓인 보류 행을 정정해야 한다. 반대로 지금 거부해 두면, 나중에 「잔액 0건이면 통과」로 여는
것은 **한 줄 완화**다.

## 요청 — 셋 중 하나로 확정해 달라

1. **그대로 좋다**(`on_hand_qty` 의 `lot_id` 축 합 · 잔액 0건이면 부분 보류 거부).
2. **원천이 다르다** — 「보유 수량」이 `lot.initial_qty` 이거나 다른 표라면 그 칸 이름을 달라.
3. **소유 축을 좁혀야 한다** — 사급·수탁 재고를 보유에서 빼야 하면
   `ownership_type_code = 'OWNED'` 한 칸을 더한다(Nit-5).
4. **잔액 0건은 통과여야 한다** — 재고에 안 잡힌 LOT 에도 부분 보류를 걸 수 있어야 한다면
   그렇게 적어 달라. 그때 `availableQty` 가 음수로 내려가도 되는지도 함께 골라 달라.
