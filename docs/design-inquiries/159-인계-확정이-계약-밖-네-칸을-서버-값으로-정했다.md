# 159. 인계 확정이 **계약 밖 네 칸**을 서버 값으로 정했다 — 상태 상수·번호 규칙·라인 번호·**수령량**

> ⚠ 넷 중 **`received_qty` 하나가 「계약 x-internal-note ↔ `plan-uiux.md:1195`」 어긋남 위에 서 있다.** 우리는 **화면 쪽(수량까지 채운다)** 을 따랐다 — 그 판단과 근거를 그대로 싣는다.
> ⚠ 계약이 **이 자리를 스스로 예고했다**: 「⚠ **M-02-01 §8 미결 2 는 그 «접기» 자체를 열어 두었다 — 축이 갈리면 그때 다시 본다.**」

## 무엇이 문제인가

계약이 `OperationHandover` 를 8칸으로 적었는데 물리 `operation_handover` 는 **12칸**, `operation_handover_line` 은 계약 4칸에 물리 **11칸**이다. 그 차이 중 **서버가 값을 «정해야» 하는 칸이 넷**이다.

### ⓐ `status_code` — 상수 `'HANDED_OVER'`

- 계약 `statusCode` 는 **required** 인데 `x-no-code-key` 다. 원문:

> ⌜코드 그룹을 세우지 않는다 — 계약이 **인계·인수를 «한 행위»로 접어**(`receivedAt` 을 같은 시각에 찍는다) **전이가 0개다**. 구간 형 리소스로 `handedOverAt` ↔ `receivedAt` 의 유무로 판정한다. **⚠ M-02-01 §8 미결 2 는 그 «접기» 자체를 열어 두었다 — 축이 갈리면 그때 다시 본다.**⌝

- DB `mdm.code_group` 에 `%HANDOVER%` **0행**(실측).
- ⇒ 같은 도메인의 0단계 선례 둘과 같은 모양으로 **상수**를 쓴다 — `material-consumption.constants.ts` `CONSUMPTION_STATUS='RECORDED'` · I-7 `RESULT_STATUS='CONFIRMED'`. 값은 **계약이 부른 행위 이름**을 그대로 쓴다.
- ⚠ **덤 — 이 필터는 화면이 그릴 수 없다.** `GET /production/operation-handovers` 에 `statusCode` 질의가 있는데 값 원천이 **어디에도 없다**(코드 그룹 0행 · 서버 상수 1값). 드롭다운을 그리려면 하드코딩해야 하고, 그러면 서버 상수와 **두 곳에서 갈린다**. 실제로 걸러지는 값도 하나뿐이다.

### ⓑ `handover_no` — `OH-{YYYYMMDD}-{SEQ4}`

- 계약 `handoverNo` 는 required 인데 `example` 이 `"값"` 자리채움이고 형식 선언이 **0**이다. `plan-api.md:1117` 채번 표도 「규칙 ❌ · 형식 —」이다. 물리는 `varchar(100) NOT NULL **UNIQUE**`.
- ⇒ 저장소 기본 패턴을 따른다(`plan.md` §0 #3) — `numbering.service.ts` `DEFAULT_PREFIX` 에 **`OPERATION_HANDOVER: 'OH'` 한 줄**(현재 19개 등재 · `OH` 접두어 충돌 없음).
- **기간 키 = `handedOverAt` 의 UTC 날짜** — 서버가 「오늘」로 다시 잡으면 오프라인 재전송이 하루 뒤 번호를 받는다(I-10 `:80-82` 와 같은 근거).
- **`plantId = null`** — 실적에도 W/O 에도 공장 축이 없다(`production-result.service.ts:79`).
- ⇒ **문의 14 표에 `handover_no` 한 행을 더한다**(형식 확정을 그 표에서 받는다 — `purchase_order_no`·`inbound_receipt_no` 와 같은 자리).

### ⓒ `line_no` — 요청 배열 순서대로 1..N

- 계약 `OperationHandoverLine` 에 칸이 **0**이고 물리는 `NOT NULL` + `CHECK line_no > 0` + `uq_operation_handover_line(operation_handover_id, line_no)` 다.
- ⇒ 같은 모듈의 같은 모양을 복제한다 — `material-return.service.ts:90` `line_no: index + 1`(새 헤더에 배열 순서 · 잠금 불필요).

### ⓓ ⭐ `received_qty` — **`= 그 라인의 handoverQty`** (계약과 화면 정본이 갈린 자리)

물리 `operation_handover_line.received_qty` 는 `Decimal @default(0)` + `CHECK ck_handover_qty (received_qty <= handover_qty)` 이고 **계약 스키마에는 칸 자체가 없다**(요청에도 응답에도).

**어긋남**

| 정본 | 무엇을 적었나 |
|---|---|
| 계약 `x-internal-note` | 「받는 쪽 화면이 없어 `received_at` 을 채울 경로가 생기지 않는다. 화면을 따라 인계 확정 시 **두 «시각»을 함께 찍는다**」 — **수량은 한 글자도 없다** |
| `plan-uiux.md:1195`(§9-1 D) | 「M-02-01 WIP 공정이동 스캔 / 화면이 요구하는 것 = 인계의 «수령» 쪽 — **`received_at`·`received_qty` 를 채울** 오퍼레이션·화면 / 처리 = **계약대로 한 번에 확정**」 — **두 칸 다** |

**우리가 화면 쪽을 따른 근거 넷**

1. **계약이 더 강한 말을 같은 자리에서 했다.** `description` = ⌜인계와 인수를 **«한 번에» 확정한다 — 화면의 버튼이 하나다**⌝ · `statusCode.x-no-code-key` = ⌜계약이 **인계·인수를 «한 행위»로 접어** … 전이가 0개다⌝. **접힌 것은 시각만이 아니라 «인수» 그 자체**다.
2. **`x-internal-note` 의 침묵은 근거가 아니다.** 그 문장의 범위는 **계약 «응답 스키마»**인데 `receivedQty` 는 계약에 **아예 없으므로** note 가 언급할 이유가 없다.
3. **물리 CHECK 가 수령량을 담으라고 걸려 있다.** `ck_handover_qty (received_qty <= handover_qty)` 를 0 으로 고정하면 이 제약은 **영원히 도달 불가**가 된다 — 코드가 제약 하나를 죽이는 신호다. `= handover_qty` 면 **경계에서 늘 만나 등호로 통과**한다.
4. **같은 트랜잭션에서 이미 넷을 도출한다.** `status_code`·`handover_no`·`line_no`·**위치 두 칸**을 계약 밖에서 채우면서 `received_qty` 하나만 도출을 거부할 근거가 없다. `received_at = handed_over_at` 자체가 **도출**이고, 그것을 시킨 계약 문장이 「인수를 접었다」도 함께 시켰다.

**대가**: 나중에 계약이 예고한 `:receive`(⌜인수 확인 화면이 나중에 생기면 `:receive` 를 더한다⌝)나 인수 화면이 서면, 이 구간의 행들은 **「인계 시점에 전량 수령됨」으로 이미 확정돼 있다**. 부분 수령·미수령을 소급해 가릴 값은 DB 에 없다(수령 시각도 인계 시각과 같다).

⚠ **계약이 이 자리를 스스로 열어 두었다** — 위 ⓐ 인용의 마지막 문장(「**미결 2 는 그 «접기» 자체를 열어 두었다 — 축이 갈리면 그때 다시 본다**」). 이 통보는 그 예고에 대한 보고다.

## 지금 서버는

- **아직 없다.** 계획이 정한 동작(한 트랜잭션): 헤더 INSERT(`status_code='HANDED_OVER'` · `handover_no` = 채번 · `received_at = handed_over_at`) → 라인 `createMany`(`line_no` 1..N · 위치 두 칸(문의 158) · **`received_qty = handoverQty`**).
- **넷 다 응답에 나오지 않거나(라인 셋) 값이 하나뿐이라(상태 상수)** API 단언으로는 지켜볼 수 없다 ⇒ e2e 가 **DB 를 직접 단언**한다.
- ⛔ 새 코드 그룹·시드를 만들지 않는다 · ⛔ `assertCodeValues` 를 걸지 않는다 · ⛔ 마이그레이션 0.

⇒ **알리는 것**: 계약 밖 네 칸의 값을 서버가 정했다(상수·번호 규칙·라인 번호·**수령량**). 특히 **`received_qty` 는 계약과 화면 정본이 갈린 자리**이고 우리는 화면 쪽을 따랐다 — 축이 갈리면 그때 다시 본다는 계약의 예고가 그대로 유효하다. 그리고 **`statusCode` 필터는 값 원천이 없어 화면이 그릴 수 없다**.
