# 277. 자재 LOT 번호를 QR·구분자 형식으로 바꾸고, 자재 LOT 라벨은 POP 이 구성한다

| 칸 | 내용 |
|---|---|
| **구분** | **통보** — 사용자 결정(2026-09-14). 회신을 기다리지 않는다. MLOT 확정기록 §2 #2·§5 와 설계 결정 18 을 개정한다 |
| 걸리는 오퍼레이션 | **횡단** — 발번 `POST /trace/lots` · 사전부착 `POST /logistics/inbound-receipts` · `PUT /logistics/inbound-receipts/{inboundReceiptId}/lines` · `POST /logistics/inbound-receipts:split` · 발행 `POST /app/document-issues` · `GET /app/document-issues/{documentIssueLogId}/rendition` |
| 구현 상태 | **서버 — 진행 중**(이 저장소, 브랜치 `feat/material-lot-qr-label`, PR ⓪~③b). 클라이언트(POP 라벨 구성·QR 파서)는 이 통보로 설계팀을 거쳐 별도 저장소에 전달 — 이 저장소에서 구현하지 않는다 |
| 판정 | 34자리 숫자 형식으로는 하노이 실 품목 9,813건 중 5건만 LOT 을 만들 수 있다(#620). 라벨은 서버 PNG → 드라이버 경로가 실기에서 백지를 냈고, POP 이 TSPL 을 RAW 로 보내는 경로만 실기 출력에 성공했다(client #798·#831·#1104) |
| 되돌릴 때 | `src/core/lot/lot-number.ts` 하나만 바뀐다 — `materialMesLotNo()`를 옛 34자리 조립으로 되돌리고 `inbound-receipt-rules.ts`의 형식 검사를 `^\d{34}$`로 되돌린다. 그 사이 만들어진 신형식 LOT 은 소급 변환하지 않는다(이미 라벨이 찍혀 있을 수 있다) |

## 1. 결정

| # | 항목 | 결정 |
|---|---|---|
| 1 | 코드 형식 | **QR 전용.** 문자·구분자를 허용한다 |
| 2 | 구성 | 기존 5칸 **그대로** — 제품코드 · 수량 · 날짜 · 공급사 성분 · 번호 (순서 유지) |
| 3 | 수량 단위 | ⚠ **미정** — 확정 전까지 **입하 라인 수량을 그대로** 싣고, 단위로 막지 않는다(§2-2) |
| 4 | 번호 카운터 | **앞 4칸**(제품코드·수량·날짜·공급사)이 같은 LOT 안에서 센다 |
| 5 | 사전부착 스캔 번호 검사 | 서버가 **형식**(5칸·문자집합·64자)과 **제품코드·공급사 일치**(입하 라인 대비)를 검사한다. 수량 칸은 비교하지 않는다(§2-3) |
| 6 | 번호 소진 | 앞 4칸의 번호가 9999 를 넘으면 **409**(종전 400 에서 변경 — 사용자가 고칠 수 없는 값이라는 계약 원칙을 따른다) |
| 7 | 라벨 | **80 × 30 mm.** 품명은 싣지 않는다 |
| 8 | 라벨 구성 주체 | **서버는 값만 준다 → POP 이 배치·명령 생성·출력까지 한다** |
| 9 | 적용 | POP 라벨 **전체에 적용**하되 **단계적** — 1단계는 자재 LOT 라벨만 |

## 2. 자재 LOT 번호 형식

```
040101-00022S|12.5|260731|100019|0001
제품코드      |수량 |날짜  |공급사|번호
```

| 칸 | 값 | 규칙 |
|---|---|---|
| 제품코드 | `mdm.item.item_code` 원본 | — |
| 수량 | 최초 납품 수량 스냅샷 — **입하 라인 단위 그대로**(단위 규칙 미정 · §2-2) | 정규형 문자열 — 후행 0 제거(`12.500000`→`12.5`) · 정수면 소수점 없음(`100`) · 선행 0 없음 · 천단위 구분 없음. **DB 스케일(`Decimal(20,6)`)과 일치하는 소수 6자리로 정규화한다** — 그래야 라벨에 찍힌 수량과 실제 저장값이 항상 같다 |
| 날짜 | `YYMMDD` | MES 발번 = 클라이언트가 보낸 `business_date`(공유계약 C-8) · 사전부착 = 공급사가 라벨을 찍은 날. ⛔ 업무 판단에 쓰지 않는다 |
| 공급사 성분 | `mdm.partner.partner_code` 원본 | — |
| 번호 | 4자리 0채움 `0001`~`9999` | 앞 4칸이 같은 기존 LOT 의 번호 **최댓값 + 1**. `9999` 초과는 409(결정 6) |

| 공통 규칙 | 값 |
|---|---|
| 구분자 | `\|` (U+007C) — 품목 9,269 + 거래처 931 코드에서 출현 0건(#632 실측) |
| 칸 수 | 정확히 5 |
| 칸 값 금지 | `\|` · 비ASCII · 제어문자 · 빈 칸 |
| 전체 길이 상한 | **64자**(`lot.lot_no` 는 `varchar(100)`) — 실 데이터로 재확인: 자재 품목코드 최대 13자(`30815-003BKR1`), 공급사 코드 최대 10자(`CVNET00006`, 99%는 6자). 날짜6+번호4+구분자4=14자를 빼도 여유가 크다 |
| 유일성 | 그대로 `UNIQUE(plant_id, lot_no)` |
| QR 내용 | **LOT 번호 문자열 그대로.** 다른 값을 덧붙이지 않는다 — 사전부착 라벨과 MES 라벨을 한 파서로 읽는다 |

### 2-1. 종전 설계와 달라지는 곳

| 종전 | 개정 | 이유 |
|---|---|---|
| 34자리 고정폭·전부 숫자·구분문자 없음(MLOT §5) | 구분자 5칸·가변 길이·문자 허용 | 「QR/바코드 겸용」 전제가 QR 확정으로 사라졌다 · 실 코드 체계와 맞지 않았다(#620) |
| 제품코드 9 · 공급사 성분 6 (도출 미정) | 마스터 코드 원본 | 도출 규칙이 필요 없어진다 — `M-01-02` §8-2 · `omf-mes#453` 을 이 결정이 닫는다 |
| 번호4 = (제품코드, 날짜, 공급사)별 카운터(`omf-mes#245` 회신) | **앞 4칸(수량 포함)** 별 카운터 | 사용자 결정. 현재 서버 구현과 같은 방식을 그대로 쓴다 |
| 수량 9자리 정수 | 정규형 소수(단위는 §2-2) | KG·GR·M2 등 소수 수량 품목 463건(4.7%)이 함께 열린다. 지금까지 정수만 허용해 소수 수량 자재 입하의 MES 발번이 400 으로 막혀 있던 잠재 결함도 같이 풀린다 |
| 사전부착 서버 검사 = 형식(길이·숫자)만 | 형식 + **제품코드·공급사 일치** | §2-3 |
| 번호 소진 = 400 | **409** | 결정 6 |

⚠ 계약 `LotCreate.lotNo` 설명은 「구분문자 없음이다... `MLOT #16` ✓확정 2026-07-27」이라고 못박아 뒀다 — 이 개정은 **확정된 계약 문구와 정면으로 다르다.** 계약 사본은 건드리지 않고 `docs/계약-선행-수정항목.md` P-3 에 그 괴리를 기록한다(설계 소관 파일은 별도 절차로 반영을 요청한다).

### 2-2. ⚠ 수량 단위 — 미정 (임시 동작)

「품목 기본 단위」로 정하려 했으나 근거가 아직 없어 **보류**한다(사용자 2026-09-14).

| 확인된 사실 | |
|---|---|
| 단위 환산 마스터 `item_uom_conversion` | 시드 **0건** · 환산율 방향이 설계에 없다 |
| 입하 라인 단위 | 화면이 발주 라인에서 승계(무발주는 사람이 고른다) · 서버는 기본 단위·발주 단위와 대조하지 않는다 |
| 발주 라인 단위 | 설계상 ERP 발주가 원천 — **ERP 발주 수신 인터페이스가 아직 없다** · 발주 시드 0건 |

**임시 동작** — 번호의 수량은 **입하 라인 단위 그대로**다. 환산하지 않고 단위로 막지 않는다.
- 입하 단위가 기본 단위와 같으면(자재 기본 단위의 92%가 EA) 확정안과 결과가 같다.
- 번호 자체에는 단위가 없다 — 라벨의 단위 코드가 유일한 단위 표시다.

**확정할 때 볼 것** — ERP 발주 단위가 품목 기본 단위와 같은가 · 다르면 어느 자리(ERP 발주 수신 · 입하 · LOT)에서 맞추는가 · 사전부착 공급사 규격서에 어느 단위를 적는가.

### 2-3. 사전부착 스캔 번호의 서버 검사

형식 검사(5칸·문자집합·64자)에 더해, **파싱된 제품코드가 그 입하 라인의 품목과, 파싱된 공급사 성분이 그 입하의 공급사와 일치하는지** 서버가 검사한다(결정 5). 틀린 라벨을 붙인 자재가 조용히 통과해 IQC·적치·투입까지 흘러가는 것을 막는다.

- **수량 칸은 비교하지 않는다** — 최초 납품 스냅샷이라 분할·부분 입고로 실제 입하 수량과 달라질 수 있다.
- **날짜 칸도 비교하지 않는다** — 업무 판단에 쓰지 않는 네임스페이스 분산용 값이다(§2 표).
- 파싱 자체가 실패하면(형식 위반) 이 대조는 하지 않는다 — 형식 오류로 이미 보고됐다.
- 품목·공급사 마스터 행을 찾지 못하면(있을 수 없는 FK 값) 대조를 조용히 건너뛴다 — 그건 별도 결정 사안(FK 존재 검증 여부)이다.
- **입하 등록(`POST /logistics/inbound-receipts`)과 초과분 분리(`:split`) 양쪽 모두** 이 검사를 받는다 — 둘 다 `supplierLotNo`로 LOT 을 직접 만드는 독립 경로다.

## 3. 자재 LOT 라벨 (1단계)

**용지 80 × 30 mm · 203 dpi · 흑백 · 전 항목 ASCII**

```
┌────────────────────────────────────────────────────┐
│ PART NO.: 040101-00022S                  ┌──────┐  │
│ QTY: 12.5 KG                             │  QR  │  │
│ ISSUE: 1                                 │      │  │
│                                          └──────┘  │
│ LOT NO.: 040101-00022S|12.5|260731|100019|0001     │
└────────────────────────────────────────────────────┘
```
배치는 예시다 — 좌표·글자 크기는 실기 출력으로 보정한다.

| 항목 | 값 | 비고 |
|---|---|---|
| PART NO. | `item_code` | |
| QTY | 입하 라인 수량(번호 안 수량과 같은 값) + **입하 라인 단위 코드** | 번호 안 수량과 같아야 육안 대조가 된다. 번호에는 단위가 없어 이 단위 코드가 유일한 단위 표시다 |
| LOT NO. | `lotNo` 그대로 | 한 줄 전체 폭. 자재 최대 39자 |
| ISSUE | 발행 회차 `issueSeq` | 재출력 식별 |
| QR | `lotNo` 그대로 | 오류정정 M · 셀 3 dot 이상 · 여백 포함 약 13~14 mm |

**싣지 않는 것**

| 항목 | 이유 |
|---|---|
| 품명 | 사용자 결정. 자재 품명 5,568건 중 857건(15%)이 비ASCII(가타카나·한자·전각 `【】`)라 프린터 내장 폰트로 찍을 수 없다 |
| 상태 | IQC 뒤 바뀌어 라벨이 거짓이 된다 |
| 제목(`MATERIAL LOT LABEL`) | 30 mm 높이에 줄이 모자란다 |
| 날짜·공급사 | 번호 안에 있다 |

⇒ 「MES 라벨 표준 사양」 §5.2 필수 항목(유형·상태·품명·일시)과 달라지므로 **사양서에 자재 LOT 서식을 따로 둔다.**

## 4. 라벨 구성 주체 변경 (설계 결정 18 개정)

| | 종전(결정 18) | 개정 |
|---|---|---|
| 서버 | 라벨을 그림(PNG)으로 완성 | **라벨에 실을 값만** 준다 |
| POP | 받은 그림을 넘기기만 함 | 배치 → TSPL 명령 생성 → RAW 출력 |
| 글꼴 | 서버 탑재(한/베) | 1단계는 전 항목 ASCII 라 프린터 내장 폰트로 충분 |

⛔ **POP 은 QR 에 서버가 준 `lotNo` 를 그대로 싣는다.** 칸을 모아 번호를 다시 만들지 않는다.

### 4-1. 계약에서 바뀌는 것 (제안 — 설계팀 확인 필요)

| 오퍼레이션 | 변경 |
|---|---|
| `POST /app/document-issues` 응답 · `GET /app/document-issues/{documentIssueLogId}` | `DocumentIssue` 에 라벨 값 추가 — 품번 · 수량 · 단위 코드 (`lotNo`·`issueSeq` 는 이미 있다). 재출력 이력에서도 라벨을 다시 구성할 수 있어야 한다 |
| `GET /app/document-issues/{documentIssueLogId}/rendition` | `MATERIAL_LOT_LABEL` 을 **다음 릴리스에서** 뺀다(POP 전환 확인 뒤). 다른 종류는 2단계 이후 |
| `LotCreate.lotNo`(SUPPLIER) 설명 | 34자리 → §2 형식 |
| `InboundReceiptLineUpsert.supplierLotNo` | 지금 설명이 없고 예시(`SL-2026-0001`)가 이미 34자리 규칙과 안 맞는다 — §2 형식으로 설명을 채운다 |

### 4-2. 2단계 이후에 다시 볼 것

- 납품 라벨은 지금도 서버 PNG 경로다 — 같은 백지 문제가 날 수 있다.
- 출하 라벨의 납품처·품명 등 **비ASCII 항목의 글꼴 방식**(POP 이 비트맵으로 그려 TSPL `BITMAP` 으로 보내는 안 등)을 그때 정한다.
