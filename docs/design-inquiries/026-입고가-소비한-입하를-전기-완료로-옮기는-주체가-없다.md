# 26. 입고가 소비한 입하를 «전기 완료»로 옮기는 주체가 없고, 저장된 입하를 다시 여는 화면도 없다

| 칸 | 내용 |
|---|---|
| 걸리는 오퍼레이션 | `PUT /logistics/inbound-receipts/{id}` · `PUT …/{id}/lines` · `GET /logistics/inbound-receipts?statusCode=` · (`POST /logistics/goods-receipts` 가 옮겨야 하는가) |
| 구현 상태 | **구현함(계약 문자 그대로 · 전이 0)** — 「작성중 = `REGISTERED`」 판정(I-2 023 과 같은 처리) + §7-4 의 임시 자물쇠(입고·차이·역참조 P/O 가 붙은 라인은 삭제·수량 변경 400 `SUCCESSOR_EXISTS`) |
| 판정 | `coverage-100/README.md` §2 1단계 **본길**(모든 입하가 `REGISTERED` 에 머문다) → 문의. 자물쇠는 2단계 기준 2 「거부하는 쪽」(원장이 가리키는 근거가 사라지는 사고는 되돌릴 수 없다) |
| 되돌릴 때 | 「전기 완료」 축이 서면 `inbound-receipt-update.service.ts` 의 `assertNoSuccessor` 를 걷어내고 `status_code` 전이로 대체한다. 화면이 서면 `manual-permissions.ts` 두 줄의 화면 ID 만 바뀐다 |

## 무엇이 문제인가

`LOGISTICS_DOCUMENT_STATUS` 4값(`REGISTERED`·`POSTED`·`CANCEL_REQUESTED`·`CANCELED`) 중 입하 전표가 **`REGISTERED` 밖으로 가는 오퍼레이션이 계약에 없다.**
취소 두 값은 I-5(다형 취소)가 열므로 여기서 묻지 않는다(023 이 「취소 경로가 있는 것은 입하·입고·출고」라 이미 적었다). 남는 갈래 넷:

| # | 갈래 | 실측 |
|:-:|---|---|
| ① | `POSTED` 도달 경로가 없다 | 입고 등록(`POST /logistics/goods-receipts`)은 `source_document_type_code='INBOUND_RECEIPT'` 를 적을 뿐 **입하를 옮기지 않는다** |
| ② | 그래서 계약이 두 번 적은 「**작성중 상태에서만 허용한다**」(`PUT …/{id}` description) · 「**확정·전기된 전표의 수정은 400 `STATE_LOCKED`**」(`x-internal-note`) 가드가 **아무것도 막지 않는다** | 서버는 `status_code !== 'REGISTERED'` 로 구현했고 단위 테스트로만 세웠다 — e2e 로는 도달 불가 |
| ③ | 그 결과 **이미 LOT 이 서고 입고·원장까지 간 입하 라인의 수량을 그대로 고칠 수 있다** — 계약이 막은 것은 「LOT 이 만들어진 라인의 «삭제»」 하나뿐 | 서버가 계약 밖 자물쇠를 걸었다(아래) |
| ④ | `PUT …/{id}`·`PUT …/lines` 를 **부르는 화면이 01 도메인 26장에 0건**(`plan-uiux.md` U5 「—」) | `M-01-09` §8 #1 이 출고에서 「취소 요청 후 재등록 · 새 화면 안 만든다 · 라인 치환은 쓸 수 없다」로 세운 선례가 있다 |

## 지금 서버는

- 헤더 수정·라인 치환을 계약대로 연다. 「작성중」은 값 목록에 없어 `REGISTERED` 하나로 푼다(I-2 P/O 와 같은 판정).
- **계약이 안 적은 자물쇠 하나를 걸었다** — `goods_receipt_line`·`inbound_variance`·`purchase_order.source_inbound_receipt_line_id` 가 붙은 입하 라인은 **삭제도 수량 변경도 400 `SUCCESSOR_EXISTS`**. 안 걸면 FK 위반이 500 으로 새거나(삭제) 원장이 가리키는 근거가 조용히 바뀐다(수량). 「전기 완료」 축이 서면 이 임시 자물쇠는 걷어낸다.
  - ⚠ 그래도 틈이 남는다: **입고가 아직 안 붙은 «부착» 라인**은 치환으로 `receivedQty`·`itemId`·`uomId` 를 바꿀 수 있고, 등록 때 그 값으로 만든 `trace.lot.initial_qty`·`item_id`·`uom_id` 와 어긋난다(계약은 「삭제」만 막았다). 어느 쪽이 참인지 데이터만으로 못 가른다 — I-5 취소 설계와 함께 본다.
- 두 PUT 의 403 권한은 `M-01-01` 로 **잠정 등록**(미등록이면 `PermissionGuard` 가 500). 코드 주석에 「부르는 화면이 없다 · 026」.
- 흔적: 단위 `수정/치환 — status_code 가 REGISTERED 가 아니면 400 STATE_LOCKED 다(1차에 도달 불가라 e2e 로 못 세운다)` · e2e `치환 — 입고가 붙은 라인을 지우면/수량을 바꿔도 400 SUCCESSOR_EXISTS 다(§7-4)` · 코드 주석 `// 계약이 LOT 만 적었다 — 입고·차이·역참조 P/O 도 막는다(I-3.md §7-4)`.

## 요청

1. **입하를 `POSTED` 로 옮기는 주체**를 정해 주십시오 — 입고 등록이 옮기는가(전 라인 소비 시? 첫 라인 소비 시?), 별도 오퍼레이션인가, 아니면 1차에 옮기지 않는가. 이 답이 서야 「작성중에서만」 가드가 실제로 무언가를 막습니다.
2. **LOT 이 만들어진 라인의 «수량·품목·단위 변경»**을 막아야 합니까? 계약은 삭제만 막았고, 서버는 입고가 붙은 뒤에만 막습니다. 그 사이 구간(LOT 은 있고 입고는 없음)의 변경이 허용이면 LOT 의 `initial_qty` 를 따라 고쳐야 하는지도 함께 알려 주십시오.
3. **저장된 입하를 다시 여는 화면**을 세울 것인지 — 세운다면 화면 ID 를 주시면 권한 매핑을 옮깁니다. 세우지 않는다면(출고 `M-01-09` §8 #1 선례대로 「취소 후 재등록」) 두 PUT 은 1차에 «화면 없는 오퍼레이션»으로 두고 배포 노트에 남깁니다.

우리 권고안(회신이 없으면 이대로 갈 값): **전이 0 · 임시 자물쇠 유지 · 두 PUT 열어 둠.** 023(P/O)과 같은 병의 입하판이라 서로 인용하되 합치지 않습니다(자원도 잠금 축도 다릅니다).
