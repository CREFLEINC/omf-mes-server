# 156. 첨부 3건을 건너뛴다 — 보관용 바이너리 저장소가 DB 밖이고, `CD-ATTACHMENT-TARGET-TYPE` 에 담을 값이 **둘** 없다

> ⚠ **「파일 업로드라 못 한다」가 아니다.** 이 저장소는 multipart 업로드를 **이미 한 자리 구현했다** — `POST /mdm/molds:import`(`src/mdm/mold/mold.controller.ts:142` · `FileInterceptor`). 갈리는 축은 **파일의 수명**이다: 그쪽은 **읽고 버리는 입력**이라 DB 안에서 끝나고, 첨부는 바이너리를 **보관**해야 하는데 그 저장소가 DB 밖이다.
> ⚠ **결손이 하나가 아니라 «둘»이다** — 고장 사진(`BREAKDOWN`)과 **입하 거래명세서 사진**. 한 값만 물으면 문의가 재발행된다.

| 칸 | 내용 |
|---|---|
| **구분** | ⭐ **통보** — 건너뜀 사실과 그 사유를 알린다 · 판별자 값을 **우리가 고르지 않는다**(계약이 「붙일 곳이 늘면 계약을 고친다」라 못 박았다). 회신을 기다리지 않는다 |
| 걸리는 오퍼레이션 | ⛔ **건너뜀 3건**: `POST /app/attachments` · `GET /app/attachments/{attachmentId}/content` · `POST /maintenance/breakdowns/{breakdownId}/attachments` · (파생) `GET /app/attachments`(목록만 산다) · `POST /logistics/inbound-receipts`(`deliveryNoteAttachmentId` 를 받아서 버린다) |
| 구현 상태 | **건너뜀 확정(I-34 · 계획 PR 만)** — 목록 GET 1건만 구현한다. `plan.md` §6 166~168행 · `plan-integration.md` §8 657~667행과 같다. 계획서 `docs/coverage-100/slices/I-34.md` §3 |
| 판정 | `coverage-100/README.md` §0 「**DB 안에서 끝나는 것만** 구현한다 — 바이너리 저장소·실제 외부 전송·프린터/PDF 가 필요한 오퍼레이션은 건너뛴다」 · §2 **2단계 기준 4**(값을 조용히 도출하지 않는다 — `storage_key` 를 지어내지 않는다) · **기준 3**(스키마·개념을 늘리지 않는다 — 판별자 값을 서버가 만들지 않는다) |
| 되돌릴 때 | 저장소(오브젝트 스토리지 등)가 서면 **세 오퍼레이션이 함께 열린다** — 목록 GET 은 이미 서 있으므로 코드 변경 0으로 값을 싣기 시작한다. 판별자 값이 더해지면 목록 GET 도 **코드 변경 0**으로 따라간다(enum 은 가드가 계약에서 읽는다). ⚠ 그 릴리스에서 **함께 해야 할 것 셋**: `(target_type_code, target_id)` 인덱스 · 페이지네이션(계약이 열면) · 판별자 값 둘 |

## 무엇이 문제인가

### ⓐ 보관용 바이너리 저장소가 DB 밖이다 — `storage_key` 에 넣을 값이 없다

- 물리 `app.attachment` 는 **10칸**인데 **바이너리 칸이 0개**다(`bytea`·`blob` 없음 · `prisma/schema.prisma:170-184`).
- 대신 **`storage_key varchar(500) NOT NULL`** 을 갖는다 — **DB 밖 저장소의 키**다. 저장소가 없으면 이 칸에 넣을 값을 **서버가 지어내야** 하고, 지어낸 키로는 **아무것도 꺼낼 수 없다**. 부수 칸 `checksum_sha256` 도 마찬가지로 대조할 원본이 없다.
- 계약 스스로 실물 파일이 흐른다고 적었다 — `POST /app/attachments` 가 **`413` 「파일이 너무 크다」**를 선언한다(`contracts/app-공통.json:3258`). 이 계약에서 413 을 선언한 몇 안 되는 자리다.
- `GET …/{attachmentId}/content` 는 응답이 아예 JSON 이 아니다(`application/octet-stream`·`image/png`·`image/jpeg` · `format: binary`). 계약이 스스로 예외라 적었다: 「이 계약에서 **application/json 이 아닌 두 번째 응답**이다 — 첫째는 출력물 rendition 이다」. ⭐ **그 첫째도 건너뜀**이다(`plan.md` §6) — 같은 이유로 걸린 둘이 계약 안에서 서로를 가리킨다.

⚠ **반대 증거를 직접 확인했다.** `POST /mdm/molds:import` 는 이미 구현돼 있고, 그 코드가 계약 주석을 인용해 스스로 갈라 적었다(`mold.controller.ts:135-138`):

> 「엑셀 대장 올리기. 전 계약에서 처음 두는 파일 올리기 경로다 — **첨부와 «다른 자리»다**(**첨부는 보관되는 파일이고 이것은 읽고 버리는 입력이다** · 계약 x-internal-note).」

⇒ **건너뜀 사유 한 줄**: **「보관할 바이너리 저장소가 DB 밖이라, `storage_key` 에 넣을 값을 서버가 지어내는 수밖에 없다.」**

### ⓑ ⭐ 판별자에 담을 값이 «둘» 없다

`CD-ATTACHMENT-TARGET-TYPE` 은 계약 **세 자리 전부**(POST 본문 · GET 질의 · `Attachment` 스키마) **`WAREHOUSE`·`NOTICE` 2값**으로 닫혀 있다. DB 코드 그룹은 아예 **0행**이다(`group_code ILIKE '%ATTACH%'` → 0 · `prisma/seed.ts` 에 0건).

그런데 계약 안에 **그 2값으로 못 담는 첨부가 둘** 있다:

| # | 담을 곳 없는 첨부 | 계약 근거 |
|:-:|---|---|
| **1** | **고장 사진** | `POST /maintenance/breakdowns/{breakdownId}/attachments` 가 실재하고(「고장 건이 만들어진 뒤에 사진을 한 장씩 붙인다. **최대 세 장**이다」 · `equipment-05설비툴.json:624~`), 담을 물리 표 `breakdown_attachment` 는 **없다**(전 마이그레이션 grep 0건) ⇒ 담을 곳은 `app.attachment` 뿐인데 **`BREAKDOWN` 값이 enum 에 없다** |
| **2** | ⭐ **입하 거래명세서 사진** | `InboundReceiptCreate.deliveryNoteAttachmentId` 가 **실재한다**(`logistics-01자재창고.json:9078`) — description 「촬영한 거래명세서 첨부 식별자. **첨부 계약은 이 파일이 갖지 않는다**」 · x-internal-note 「`app.attachment` 계약은 app-공통 파일 소관」. ⇒ 계약이 **첨부 표를 가리키는데** 그 유형 값이 enum 에 없다. 서버는 이 칸을 **받아서 버린다**(`src/logistics/inbound-receipt/inbound-receipt-rules.ts:46`) |

⛔ **값을 우리가 고르지 않는다.** 계약이 값 소유권을 스스로 못 박았다(`app-공통.json:3289`):

> 「⛔ **다형 참조 판별자라 값이 «우리 계약의 대상 표 이름»이다 — 고객이 늘릴 수 없고, 붙일 곳이 늘면 계약을 고친다**(공유계약 A-10 · A-16).」

### ⓒ 덤 — 같은 물리 칸을 두 계약이 **반대로** 읽는다

- app 쪽 `Attachment`(`app-공통.json:5871`)는 required **7** · 프로퍼티 8 이고 **`storageKey` 칸이 아예 없다**.
- equipment 쪽 `BreakdownAttachment`(`equipment-05설비툴.json:3278`)는 required **2** 중 **하나가 `storageKey`** 다.

⇒ **저장소 키가 화면에 나가야 하는지 정해져 있지 않다.** 서버는 app 쪽 계약대로 **안 싣는다**(계약에 없는 칸을 응답에 더하지 않는다).

## 지금 서버는

- **건너뜀 3건은 코드 0줄이다.** `POST /app/attachments`·`GET …/content`·`POST …/breakdowns/{id}/attachments` 에 `@Contract` 바인딩을 만들지 않는다.
- **첨부 «목록» GET 1건만 구현한다**(`GET /app/attachments` — 메타데이터만 읽는다 · 범위 안).
- `Breakdown` 응답의 `attachments` 는 이미 **`[]` 로 고정**돼 있다(`src/maintenance/breakdown/breakdown-view.ts:33`·`:78` · I-30).
- `deliveryNoteAttachmentId` 는 **받아서 버린다** — 담을 유형 값이 없어서다.
- 도출 권한표에 건너뜀 3건이 **이미 등재돼 있으나**(`derived-permissions.ts:19`·`:146`·`:190`) 구현이 없어 가드가 그 줄을 볼 일이 없다 — **지우지도 더하지도 않는다**(도출표는 요구서 §3 이 원천이다).
- ⛔ 하지 않는 것: 첨부 업로드 · `storage_key` 조작·생성 · `targetTypeCode` 에 값 추가 · `app.attachment` 에 어떤 쓰기도 · 고장 첨부 매핑.

### ⭐ 그래서 화면이 어떻게 되나 — **화면마다 다르다**

⛔ 「화면 두 장이 **반쯤** 열린다」로 뭉뚱그리지 않는다. `W-CO-08` 에 대해 **과대평가**다.

| 화면 | 이 릴리스 뒤 상태 |
|---|---|
| **`W-CO-04`**(공지) | **거의 다 열린다 — 첨부 «줄»만 빈다.** 공지 본체 8건은 이미 구현돼 있고, `Notice` 스키마에 `attachments` 칸이 없어 이 목록 GET 이 첨부의 유일한 경로다. 경로는 **살고 내용만 빈다**(writer 0 · DB 0행) |
| **`W-CO-08`**(창고 배치도) | ⭐ **이 릴리스로 달라지는 것이 0이다.** 계약이 적은 **유일한** 도면 경로가 `WarehouseLayout.drawingAttachmentId` → **`GET …/{id}/content`(건너뜀)** 이고(`mdm-기준정보.json:20479`), 도면 id 는 `POST`(건너뜀)로만 생긴다. layout GET/PUT 은 이미 구현돼 있다. ⇒ 화면은 계속 계약이 적은 문구 **「도면을 올리세요」**를 보이고 마커는 **배경 없는 캔버스**에 찍힌다. ⛔ 배포 스모크에 「배치도에서 도면이 뜨는지」를 넣으면 **오탐**이다 — 첫날부터 설계대로다 |
| **`M-05-02`**(고장) | **사진 칸이 영구 공백이다** — 여는 오퍼레이션이 건너뜀이고 담을 판별자 값도 없다 |

## ⇒ 알리는 것

1. **첨부 3건을 1차에서 건너뛴다.** 사유는 「파일 업로드를 못 해서」가 **아니라** 「**보관용 바이너리 저장소가 DB 밖**이라 `storage_key` 를 지어내야 해서」다.
2. ⭐ **판별자 값이 «둘» 없다** — 고장 사진(`BREAKDOWN`)과 **입하 거래명세서 사진**. 값은 계약이 정한다(「붙일 곳이 늘면 계약을 고친다」). **저장소가 서는 릴리스에 값과 함께 열어** 주십시오. ⛔ 한 값만 열면 다른 하나가 그대로 남는다.
3. **저장소 키가 화면에 나가야 하는지 정해 주십시오** — 같은 물리 칸을 app 쪽 `Attachment` 는 안 싣고 equipment 쪽 `BreakdownAttachment` 는 required 로 노출한다.
4. **화면별 영향을 위 표대로 받아** 주십시오 — 특히 **`W-CO-08` 은 「반쯤」이 아니라 「변화 0」**이다.
