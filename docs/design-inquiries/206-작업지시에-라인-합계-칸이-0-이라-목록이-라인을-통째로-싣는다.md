# 206. `ShipmentRequest` 에 **라인 합계 칸이 0개**라 목록이 **라인을 통째로 실어야** 한다

**구분: 통보**(회신을 기다리지 않는다)

| 칸 | 내용 |
|---|---|
| 걸리는 오퍼레이션 | `GET /logistics/shipment-requests` · `GET /logistics/sales-orders` |
| 구현 상태 | **구현 예정(I-22 PR ②·④)** — 목록에도 `lines` 를 싣는다 |
| 판정 | §2 **1단계 본길**(화면 셋의 유일한 수량 열) → 계약이 합계 칸을 안 줘 **라인을 싣는 쪽**을 고름 |
| 되돌릴 때 | 합계 칸이 생기면 뷰에서 `lines` 를 빼고 3칸을 채운다 |

## 화면 셋이 라인 합계를 «핵심 열»로 그린다

| 화면 | 요구 | 어디서 나나 |
|---|---|---|
| `W-04-02` §4-A | 목록 열 「**요청 / 배정 / 출하**」 — 7열 중 **유일한 수량 열** | ⛔ `ShipmentRequest` 에 합계 칸 **0개** · `lines` 뿐 |
| `W-04-05` §3 | 작업지시 드롭다운 「SR-2026-0470 · B사 · 08-07 · **배정 500**」 | ⛔ 〃 |
| `M-04-01` §3 ① | 「FG-1001 **배정 300 · 피킹 120**」 | ⛔ 〃 |
| `W-04-01` §3 ① | 지시서 목록 행 「08-06 · **3라인** · 미편성」 | ⛔ `SalesOrder` 에 라인 수 칸 **0개** |

계약은 `lines` 를 `required` 에 넣지 않았고, 저장소 선례(`purchase-order-query.service.ts:71`)는 **목록은 헤더 · 단건만 라인**입니다. 그대로 두면 **네 화면의 그 열이 통째로 빕니다.**

## ⇒ 우리가 정한 것

**목록에도 `lines` 를 싣습니다.**

⚠ 그런데 값이 싸지 않습니다 — `ShipmentRequestLine.required` 에 **`pickedQty` 와 `picks` 가 둘 다** 들어 있고, 그 둘은 `inventory_reservation` 롤업입니다. ⇒ **한 쪽(50건)마다 라인 수만큼 예약 조회가 따라옵니다.**
그래서 **페이지의 라인 id 를 모아 `source_document_id IN (…)` 한 번**으로 조립합니다(`ix_reservation_source` 가 그대로 탑니다).

## 📨 알려 드리는 것

**`ShipmentRequest` 에 합계 3칸(`requestedQtyTotal`·`allocatedQtyTotal`·`shippedQtyTotal`)을 서버 파생으로 열어 주십시오.**
`GET /logistics/shipment-requests/summary` 가 **필터 전체 기준**의 같은 합계를 이미 내리고 있으므로(일곱 칸), **행 단위 합계**만 더하면 목록이 라인을 안 실어도 됩니다.
지금은 「행마다 라인 전건 + 예약 롤업」이라 목록 한 쪽이 무겁습니다.

⚠ 참고 — `GET /logistics/sales-orders` 도 같은 이유로 `lines` 를 싣습니다(「3라인」을 셀 칸이 없습니다). 그쪽은 롤업이 없어 값이 쌉니다.
