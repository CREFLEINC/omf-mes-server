# 158. 인계 라인의 출발·도착 위치를 W/O 기본 WIP 위치로 채운다 — 못 풀면 400 이고, 그 값은 나중에 **복원되지 않는다**

> ⚠ **계약이 시킨 일이다.** `x-internal-note` 가 ⌜화면이 고르지 않는다 — **서버가 채운다**⌝ 라 «직접» 지시했다. 우리가 고른 것은 **무엇으로** 채우는가 하나다.
> ⚠ **되돌림이 «싸다»고 적지 않는다.** 계약이 이어 붙인 마지막 문장은 「위치 체계가 정해지면 그때 **필드로 올린다**」 — 즉 장차 **화면이 준다**. 오늘 넣는 값은 **W/O 기본값의 사본**이라 그때의 라인사이드 위치는 **복원 불가**다.

| 칸 | 내용 |
|---|---|
| **구분** | ⭐ **통보** — 계약이 서버에 채우라고 지시했고, 우리가 무엇으로 채웠는지와 그 대가(400 · 복원 불가)를 알린다. 회신을 기다리지 않는다 |
| 걸리는 오퍼레이션 | `POST /production/operation-handovers`(201 · 라인 INSERT) · `GET /production/operation-handovers`·`…/{operationHandoverId}`(⛔ 이 두 칸은 **응답에 안 나온다**) |
| 구현 상태 | **구현 예정(I-25 · 계획 PR 만 · 오늘 코드 0줄)**. 계획서 `docs/coverage-100/slices/I-25.md` §0 자리 1 · §4-2 |
| 판정 | `coverage-100/README.md` §2 **1단계 본길** — 계약이 「무엇으로」를 미확정으로 남겼다. **2단계 기준 2**(못 푸는 쪽을 거부한다 — 거부→허용이 호환 완화) · **기준 3**(스키마를 안 늘린다 ⇒ NOT NULL 완화 마이그·새 위치 개념을 안 만든다) · **기준 5**(새 개념 0 ⇒ `inventory_balance` 로 현재 위치를 푸는 길을 안 연다) |

## 무엇이 문제인가

### ⓐ 물리는 NOT NULL 인데 계약에 칸이 없다 — 그리고 계약이 그 사실을 알고 있다

- 물리 `production.operation_handover_line.source_location_id`·`destination_location_id` 가 **둘 다 NOT NULL** 이다(`prisma/schema.prisma:2810-2811`).
- 계약 `OperationHandoverLine` 은 **4칸**(`operationHandoverLineId`·`lotId`·`handoverQty`·`uomId`)뿐이고 **위치 칸이 0**이다.
- `POST /production/operation-handovers` 의 `x-internal-note` 가 그 자리를 직접 적었다:

> ⌜`operation_handover_line.source_location_id`·`destination_location_id` 는 NOT NULL 이지만 **화면이 고르지 않는다 — 서버가 채운다.** 무엇으로 채우는지는 미확정(**미결-대장 277** · **M-02-01 §8-1 라인사이드 위치 체계**). **위치 체계가 정해지면 그때 «필드로 올린다».**⌝

### ⓑ 서버가 고른 축 — `work_order.default_wip_location_id` 1홉

```
source_location_id      = fromWorkOrder.default_wip_location_id
destination_location_id = toWorkOrder.default_wip_location_id
```

- 후보는 다섯이었다 — ⓐ W/O 기본 WIP 위치 ⓑ 공장별 「WIP」 위치 신설 ⓒ NOT NULL 완화 마이그 ⓓ 아무 위치나 첫 행 ⓔ `inventory_balance` 로 그 LOT 의 현재 위치를 푼다. **ⓑⓒ 는 스키마를 늘리고(기준 3) · ⓓ 는 값을 조용히 도출하며(기준 4) · ⓔ 는 0행/N행 갈래라는 새 개념을 연다(기준 5)** ⇒ ⓐ 하나가 남는다.
- `work_order` 의 위치 칸은 셋(`default_wip_location_id`·`default_fg_location_id`·`default_scrap_location_id`)뿐이고 **WIP 인계에 맞는 것은 하나**다.
- 저장소에 **선례가 있다** — `work-order-release.service.ts:91` 이 `default_wip_location_id` 를 「이 W/O 의 WIP 도착 위치」로 삼아 출고요청을 만든다.
- ⚠ **다만 그 선례의 NULL 정책은 «반대»다.** 바로 다음 줄이 `if (plan.issueRequestNo !== null && destination !== null) {…}`(`:92-93`) — **NULL 이면 거르고 지나간다**(`release-plan.ts:101` 도 같다). 우리는 **NOT NULL 자식 칸이라 건너뛸 수가 없다** ⇒ 이 슬라이스가 저장소에서 **처음으로** 이 칸의 NULL 을 «거부»한다.

### ⓒ ⭐ 그 400 은 **현장에서 풀 수 없다**

- `work_order.default_wip_location_id` 는 **nullable** 이고(`schema.prisma:2918`), `plan.md:83` 이 「계획 **전개분은 NULL** 이라 이 걸음 없이는 출고요청이 0건」이라 적었다 — **NULL 이 정상 상태**다.
- 그 칸은 **W/O `PUT` 으로만 채워진다.**
- 계약은 400 을 ⌜검증 실패. **고쳐야 풀린다**⌝ 로 정의하는데, 같은 계약이 「**화면이 (위치를) 고르지 않는다**」라 못 박았다 ⇒ **M-02-01(POP 스캔)에 고칠 입력이 없다.**
- **실패 예**: 계획 전개로 만들어진 W/O #2002(기본 WIP 위치 NULL)로 인계 스캔 → `400 INVALID (toWorkOrderId)`. 현장 단말은 이 오더로 **영원히 인계할 수 없고**, 화면에는 고칠 칸이 없다. 관리웹에서 W/O 기본 WIP 위치를 세우는 것이 **선행**이다.
- ⚠ DB 실측 `production.work_order` **0행** — 실제 발생 빈도는 **측정할 수 없었다**.

### ⓓ ⭐ 되돌림은 「재계산」이 아니라 「필드 승격」이다

계약 마지막 문장 「위치 체계가 정해지면 그때 **필드로 올린다**」는 **장차 화면이 그 값을 준다**는 뜻이다.

- 그때 과거 행을 「재계산 마이그」로 정정하려 하면 나오는 값은 **그 W/O 의 `default_wip_location_id`(=오늘 넣은 그 값)** 뿐이다.
- 실제로 그 인계가 지난 **라인사이드 위치**는 그 순간 현장에만 있었고 **어디에도 남지 않는다**.
- ⇒ **오늘 값은 W/O 기본값의 사본**이라고 읽어야 하고, 「나중에 정확한 값으로 복원된다」는 약속은 **실행 불가**다. 설계팀이 「그때 필드로 올린다」를 앞당길지 판단할 근거가 이 문장이다.

### ⓔ ⭐ 덤 — 이 두 칸이 걸린 자리에서 **정본 둘이 어긋난다**

| 정본 | I-25(U26)의 원장·상태기계 |
|---|---|
| `plan-uiux.md:60`(§1-1 U26 행) | **`○ 이동`**(posting) · **`○ 인계`**(상태기계) |
| `plan-integration.md` §I-25(421~426행) | 「**원장 ⛔ 없다 — 둘 다 기록형**」 |
| `plan.md` §1 48행 코어 열 | **—**(코어 없음) |

형제 행들은 그 칸에 「없음」·「—」를 쓰므로 **U26 의 ○ 는 오타가 아니라 판정**이다. 우리는 **통합 정본을 따랐다**(원장 0 · 상태기계 0) — 물리 `operation_handover` 에 **재고·전기 연결 칸이 0**이고 계약 `description`·`x-internal-note` 에 **재고·원장·전기 언급이 0**이기 때문이다.

⚠ **이 어긋남이 위험한 이유**: 나중에 「WIP 공정이동이 재고를 옮기는가」가 다시 열려 이 행들을 전기의 근거로 쓰면, **위치 두 칸의 출처가 W/O 기본값**이라 **틀린 위치로 재고가 움직인다**. 원장은 `block_ledger_header_mutation` 으로 정정이 막혀 있다.

## 지금 서버는

- **아직 없다.** 계획이 정한 동작: 두 W/O 의 `default_wip_location_id` 를 읽어 **모든 라인에 같은 두 값**을 넣는다(계약이 라인별 위치를 안 받는다). 하나라도 NULL 이면 **400 `INVALID`**(field `fromWorkOrderId` / `toWorkOrderId`) — 트랜잭션에 들어가기 «전»에 막는다.
- 이 두 칸은 **응답에 나오지 않는다**(계약에 칸이 0) ⇒ 값이 뒤바뀌어도 API 로는 못 본다. e2e 가 **DB 를 직접 단언**한다(두 W/O 에 서로 다른 위치를 심고 각각 대조).
- 원장·상태기계·LOT 계보를 **만들지 않는다.**
- ⛔ NOT NULL 완화 마이그를 **내지 않는다** — 계약이 「서버가 채운다」라 적었으므로 **NULL 은 계약 문장에 없는 상태**다.

⇒ **알리는 것 셋**: ⑴ 위치 두 칸을 W/O 기본 WIP 위치로 채웠다 ⑵ 그 값이 없는 W/O 는 인계를 **전혀 기록할 수 없고 현장에서 못 푼다** — 라인사이드 위치 체계가 서기 전까지 운영은 W/O `PUT` 으로 그 칸을 채워 두어야 한다 ⑶ 「그때 필드로 올린다」가 오면 **과거 행의 라인사이드 위치는 복원되지 않는다**. 그리고 ⑷ 이 자리의 원장·상태기계 판정이 **정본 둘에서 갈려 있다**.
