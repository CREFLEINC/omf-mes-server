# 275. 실사 마감 차단 사유와 조정 완료 판정을 라인별로 고정했다

| 칸 | 내용 |
|---|---|
| **구분** | **통보** — 회신을 기다리지 않는다 |
| 걸리는 오퍼레이션 | `GET /inventory/counts/{id}` · `POST /inventory/counts/{id}:close` |
| 구현 상태 | I-15에서 구현 예정 |
| 판정 | 계약이 마감 조건과 사유 네 값을 이미 확정했다. 중복 조건의 우선순위와 조정 완료 SQL은 저비용 구현 결정이라 개발팀이 정한다 |
| 되돌릴 때 | 요약/마감의 공용 판정 함수와 테스트만 바꾼다. 원장·기존 데이터 정정은 없다 |

## 결정

1. 차단 사유 우선순위는 `ALREADY_CLOSED` → `STATE_LOCKED` → `COUNT_REMAINING` → `VARIANCE_UNADJUSTED`다.
2. `COMPLETED`가 아니면서 `IN_PROGRESS`가 아니면 `STATE_LOCKED`다.
3. 차이 라인은 `inventory_adjustment_line.inventory_count_line_id`로 연결된 조정 중 부모 `inventory_adjustment.status_code='POSTED'`가 하나 이상 있을 때만 조정 완료로 센다.
4. 등록·승인중·반려 조정은 완료로 세지 않는다. 차이 0 라인은 조정이 없어도 된다.
5. 요약과 close가 같은 함수를 사용하고, close는 부모 헤더 잠금 안에서 재계산한다.
6. close의 `businessDate`는 원장 없는 작업이라 형식만 검증하고 저장하지 않는다.
