# 101. 알림 규칙 수·표시 인원·실제 수신 인원은 다르다

| 칸 | 내용 |
|---|---|
| 걸리는 오퍼레이션 | POST `/app/notification-subscriptions/recipients:preview` · 조건부 GET/PUT `/app/notification-subscriptions` |
| 구현 상태 | **구현 예정(I-28 R-5). 아직 코드·업무DB 변경0** |
| 판정 | 0단계 계약 inactive 표시+화면 비활성 제외/표시를 함께 적용. 비활성 조직/역할은 가장자리→2단계④ 합성 활성/수신 차단을 조용히 도출하지 않음 |
| 되돌릴 때 | countActiveRecipients와 전개 where/표시·소비자 테스트 변경. 규칙/비활성 사용자를 삭제하지 않으므로 데이터 복원 불필요 |

`app-공통.json:2022`의 목록 개수는 recipients.length다. `:3451,3513`은 중복 제거와 비활성 표시를 요구하지만 totalCount는 integer일 뿐이다. W-CO-11 §6은 실제 받는 사람에서 비활성 제외+표시와0명 경고를 함께 요구한다.

ROLE은 실제 `app_user → department → business_unit`과 `user_role` 교집합이다. user_data_scope는 접근 범위이고 worker연결은 선택/비유일이라 소속을 대신하지 않는다. USER는 직접 지정하며 부서 없어도 포함한다.

R-5는 users에 중복 제거한 활성+비활성 전원을 싣고 `countActiveRecipients`로 totalCount에는 활성만 센다. ROLE2+USER1이 같은 활성1명을 가리키면 규칙3·표시1·수신1, 비활성1명뿐이면 규칙1·표시1·수신0이다. 비활성 조직/역할로 사용자 isActive를 합성하거나 규칙을 삭제하지 않는다.

**확인 요청: totalCount를 활성 실제 수신 인원으로 해석해도 되는가? 비활성 조직/역할 자체가 차단 조건인가?** 현재 판정은 위와 같고 정상 preview는 진행한다.

화면은 규칙 수를 인원 수로 표시하지 않는다. 이벤트의 실제0명 경고는 preview, 특정 ROLE의0명은 개별 규칙 preview로 얻는다. 전체 GET에 새 집계 칸을 넣지 않는다. `I-28.md` §5·8-2·8-4의 inactive1/count0, ROLE2+USER1 중복, 비활성 조직/역할 단언에 문의101 주석을 둔다.
