# 132. 잘못 전기한 재고 조정을 되돌릴 경로가 계약에 0건이다 — 취소도 역분개도 부를 오퍼레이션이 없다

> ⭐ 이 판정은 앞 슬라이스의 인계를 **뒤집는다**. `I-5.md:790-796` 이 「I-14 = `posting.reverse()` 의 **둘째 사용처**」로 적어 두었는데, 조정에는 그 함수를 부를 오퍼레이션이 계약에 하나도 없다. 세 관점이 각자 실측으로 재확인했다.

| 칸 | 내용 |
|---|---|
| 걸리는 오퍼레이션 | 조정 7건 전부의 뒷면(되돌릴 경로가 **없다**) · 관련: `POST /logistics/document-progress/{documentTypeCode}/{documentId}:cancel` |
| 구현 상태 | **미구현** — `:post` 자체가 아직 없다. 취소·역분개는 **만들 계획도 없다**(계약에 경로가 0이라 만들 자리가 없다) |
| 판정 | `coverage-100/README.md` §2 **1단계 본길**(잘못 전기한 조정 전건) → **계약이 침묵이 아니라 «닫았다»** — 취소 실행 경로의 유형 값이 enum 이라 조정이 들어갈 자리가 없다. 계약 문자 그대로 따른다(2단계로 가지 않는다) |
| 되돌릴 때 | 「조정도 취소 대상」이면 `documentTypeCode` enum 에 값 하나를 더하고 서버는 `transitions.ts` 에 취소 액션 2개 + `reverse()` 호출 한 자리를 연다(형제 출고 구현을 그대로 복제) |

## 무엇이 문제인가

**ⓐ 취소 «실행» 경로의 유형 값이 3값 enum 으로 닫혀 있다.**
`/logistics/document-progress/{documentTypeCode}/{documentId}:cancel` 의 `documentTypeCode` 는 ⌜`INBOUND_RECEIPT`·`GOODS_RECEIPT`·`GOODS_ISSUE`⌝ **3값**이고 설명이 ⌜⛔ 취소 실행 경로가 있는 3종뿐이다 — 입하·입고·출고⌝ 라 적었다(`contracts/logistics-01자재창고.json:7160-7169`). 조회 축(`DocumentProgress.documentTypeCode`)은 `PURCHASE_ORDER`·`INBOUND_RECEIPT`·`GOODS_RECEIPT`·`MATERIAL_ISSUE_REQUEST`·`PICKING_ORDER`·`STOCK_TRANSFER`·`SUBCONTRACT_ISSUE`·`SUBCONTRACT_RECEIPT`·`GOODS_ISSUE` **9값**인데(`:7249-7259`) 여기에도 `INVENTORY_ADJUSTMENT` 가 **없다**. 두 자리 다 조정을 담지 않는다.

**ⓑ 조정 자신에게도 되돌릴 오퍼레이션이 없다.**
계약의 조정 경로는 5개 · 7 오퍼레이션이다 — `GET`·`POST /inventory/adjustments` · `GET …/{id}` · `GET`·`PUT …/{id}/lines` · `POST …:post` · `POST …:request-approval`. `:cancel`·`:reverse` 는 **0건**이다(paths 전수).

**ⓒ 화면도 취소를 그리지 않는다.**
`W-01-13-물류문서진행현황취소.md` 전문에 「조정」이 **0건**이고, `W-01-12-재고조정.md` §6 예외 8행에도 취소가 없다(`:221-231`).

**ⓓ 그런데 조정은 되돌릴 필요가 가장 큰 전표다.**
조정은 원장을 직접 움직이는 판별자 넷 중 하나이고(`transactionTypeCode = 'INVENTORY_ADJUSTMENT'`), 부호·수량을 **사람이 손으로 넣는** 유일한 자리다. 화면이 그리는 것도 「장부 200 · 실물 180 · 차이 −20」처럼 사람이 확인해 넣는 수다(`W-01-12-재고조정.md:46-48`). 잘못 전기하면 오늘은 **반대 부호의 새 조정을 등록해 상쇄**하는 길밖에 없고, 그때 원장에는 취소 흔적이 아니라 **정상 조정 두 건**으로 남는다.

**ⓔ 저장소 안의 두 문서가 「조정 역분개가 있다」로 적혀 있다.**
`docs/coverage-100/slices/I-5.md:790-796` ⌜⭐ `reverse()` 의 **둘째 사용처**(조정 역분개)⌝ · `docs/coverage-100/plan-integration.md:665`(유혹 3 「역트랜잭션 3벌」의 셋째). 코어 주석도 같은 말을 한다 — `src/core/inventory-posting/inventory-posting.service.ts:110-111`. **셋 다 오늘의 계약과 어긋난다.** 회신이 「조정도 취소한다」로 오면 되살아나므로 지우지 않고 「계약에 경로 0 · 문의 132」로 고쳐 남긴다.

## 지금 서버는

- **아직 없다.** 전기(`:post`)가 미구현이고 취소·역분개는 아예 만들지 않는다.
- 상태기계에도 취소 액션을 두지 않는다 — `transitions.ts` 의 조정 키는 `REGISTERED → POSTED` 만 갖는다(계약 `statusCode` 설명이 `CANCEL_REQUESTED`·`CANCELLED` 두 값을 **문자로는** 적었지만(`contracts/…:9788`) 그 상태로 옮길 오퍼레이션이 0이다).
- `posting.reverse()` 는 조정에서 **부르지 않는다**. 오늘 그 함수의 둘째 사용처는 I-23(출하 취소)이다.

⇒ **묻는 것**: 잘못 전기한 조정을 **반대 부호의 새 조정으로 상쇄**하는 것이 정본인가, 아니면 조정을 **취소 대상 유형에 넣어** `:request-cancel`·`:cancel` 경로를 열 것인가.

「알려둘 것」으로 함께 보내는 것(문의 아님): 계약 `InventoryAdjustment.statusCode` 설명(`contracts/…:9788`)이 ⌜취소요청(CANCEL_REQUESTED) · 취소완료(CANCELLED)⌝ 를 값으로 적어 두었는데, 조정에는 그 두 상태로 옮길 오퍼레이션이 없다 — **도달 불가능한 값 둘**이다.
