## ⛔ 먼저 정정할 것 — 「계약이 `SCRAPPED` 전이를 안 적었다」는 **사실이 아니다**

우리 3관점 계획서 두 곳이 그렇게 적었다:

- `docs/coverage-100/plan-api.md:871` — 「`SCRAPPED` 로 가는 전이도 계약에서 못 찾았다 … **계약이 LOT 상태를 옮긴다고 적지 않았다**」
- `docs/coverage-100/slices/I-19.md` §11 ③ — 「⭐ **`SCRAPPED` 로 «가는» 전이를 계약이 어느 오퍼레이션에도 적지 않았다**」

**계약은 적었다.** `contracts/quality-03품질.json:2460`(`POST /quality/nonconformances/{nonconformanceId}/disposition-decisions` 의 `description`):

> ⭐ **판정 저장과 Lot Status 전이는 한 트랜잭션이다(공유계약 B-8)** — 처분만 남고 LOT 이 안 바뀌면 다음 화면이 잘못된 대상을 집는다. 근거: `W-03-10` §5-1·§5-2 · DR-008 확정 3-A
> ⭐ **도착 상태는 처분에 따라 갈린다 — 재작업 → `INSPECTION_PENDING`(검사 대기) · 폐기 → `SCRAPPED`(폐기) · 정상 → `NORMAL`(정상).**

7개 계약 파일 전수 grep 결과 **`SCRAPPED` 로 LOT 을 보내는 오퍼레이션은 이 하나뿐**이다(나머지 20 출현은 전부 「값 목록 열거」다). `plan-api.md` §5.1-E 의 「계약이 도착 상태를 직접 적은 자리는 넷이다」 열거가 **이 오퍼레이션을 빠뜨렸다.**

⇒ **없는 것은 「도착 상태」가 아니라 「전이 코드」뿐이다.**

## §1. 처분 3전이의 `transitionCode` — **`C17`·`C18`·`C19` 로 정했다**

### 무엇이 문제인가

ⓐ **도착 상태 셋은 계약이 줬는데, 그 전이를 «가리키는 코드»가 없다.**
`trace.lot_status_event.transition_code` 는 **NOT NULL**(`prisma/migrations/20260901030000_align_lot_status_event/migration.sql:21`)이고, 계약은 그 값을 **닫힌 enum 9값**으로 잠갔다(`LotStatusHistoryEvent.transitionCode` = required + `C4`·`C5`·`C6`·`C7`·`C8`·`C9`·`C10`·`C14`·`C15` · `contracts/logistics-01자재창고.json:11970`).

ⓑ **9값 어디에도 `to = SCRAPPED` 인 것이 없다.** 시드 이름 전건(`prisma/seed.ts:517-531`):

| 코드 | 이름 | 도착 |
|:-:|---|---|
| `C4` | 판정 → Release(합격) | `NORMAL` |
| `C5` | 판정 → 보류 | `INSPECTION_PENDING` |
| `C6` | 판정 → Hold(불합격) | `DEFECTIVE` |
| `C7` | 보류 → Release(재판정 합격) | `NORMAL` |
| `C8` | 보류 → Hold(재판정 불합격) | `DEFECTIVE` |
| `C9` | Release → Hold(클레임·리콜·재판정) | `DEFECTIVE` |
| `C10` | 의심자재등록 → 보류 | `INSPECTION_PENDING` |
| `C14` | 판정 → PQC 검사 필요(합격판정개수 초과) | `INSPECTION_PENDING` |
| `C15` | PQC 검사 필요 → Release(전수 재검 양품) | `NORMAL` |

ⓒ **그래서 어떤 선택을 해도 계약 밖으로 나간다** — 이 자리는 **통보 154 가 예고한 그 구멍**이고, 재등록(I-23)보다 **먼저** 열린다.

### 세 안을 비교했다

| 안 | 무엇을 하나 | 계약 정합 | 새 개념 | 되돌림 비용 | 판정 |
|:-:|---|---|:-:|---|:-:|
| **A** | **새 코드 3**(`C17`·`C18`·`C19`) | ⚠ enum 9값 밖 — 조회 응답이 계약을 벗어난다(통보 154 가 이미 그 대가를 판정했다) | 3 | `lot_status_event.transition_code` **UPDATE 한 문장** + 시드 3줄. ⭐ 그 표에는 **불변 트리거가 없다**(전 마이그레이션 `CREATE TRIGGER` 6개 전수 실측 — 이 표는 그중 하나도 아니다) | ✅ **채택** |
| **B** | **기존 9종으로 접기** — 재작업→`C5` · 정상→`C4`(도착이 같다) | ⛔ **폐기가 접힐 코드가 0개**다 ⇒ 셋 중 하나가 **구조적으로 성립하지 않는다.** 게다가 `C4`·`C5` 의 「판정」은 **검사 판정 전용**이라 설계가 못 박았다(`W-03-02` §5-1 「검사 판정 화면 — `W-01-01`(IQC)·`P-02-13`(PQC)·`W-04-03`(OQC)」) ⇒ 감사 조회가 **「검사 보류」와 「처분 재작업」을 한 통에 담아** 두 사건을 못 가른다 | 0 | — | ⛔ **탈락(성립 불가)** |
| **C** | **전이를 안 건다** | ⛔ 계약 `:2460` 이 「한 트랜잭션(B-8) — 처분만 남고 LOT 이 안 바뀌면 **다음 화면이 잘못된 대상을 집는다**」로 이유까지 적었다. 그리고 **폐기 판정된 LOT 이 계속 출고·출하·피킹 대상**이 된다(✓설계확정 결정 10 — 차단 판정은 Lot Status 단일 지점) | 0 | ⭐ **소급 불가에 가깝다** — 나중에 붙여도 이미 판정된 건의 LOT 상태를 되짚을 원본이 없다 | ⛔ **탈락** |

### 왜 번호가 `C17` 부터인가

도식이 **C1~C16 을 이미 쓰고 있다** — `W-03-02` §5-5 가 `C11`(보류 발신)과 `C16`(PQC 검사 필요 → 02-S-I 경계 위임)을 적었다(`:183-186`). 시드 9값은 그중 **「상태 전이인 것」만** 골라 담은 것이다(`seed.ts:511-516` 주석 — 「판정 유입 경계·데이터 배선·경계 위임은 상태 전이가 아니라 **제외**했다고 설계팀이 밝혔다(2026-09-01 회신 E-9)」).
⇒ **C11~C16 을 재사용하면 도식과 충돌한다. 비어 있는 첫 번호는 `C17`.**

### ⇒ 우리가 정한 것

| 코드 | 이름 | from → to | 여는 오퍼레이션 |
|:-:|---|---|---|
| **`C17`** | 처분 재작업 → 검사 대기 | `NORMAL`·`INSPECTION_PENDING`·`DEFECTIVE` → `INSPECTION_PENDING` | 판정 저장(`dispositionTypeCode='REWORK'`) |
| **`C18`** | 처분 폐기 → 폐기 | 〃 → `SCRAPPED` | 〃(`SCRAP`) |
| **`C19`** | 처분 정상 → 정상 | 〃 → `NORMAL` | 〃(`NORMAL`) |

- ⛔ **`SCRAPPED` 는 `from` 에 넣지 않는다** — 이미 폐기된 LOT 은 더 움직이지 않는다(그 요청은 400 `STATE_LOCKED`).
- ⭐ **`from` 을 세 값으로 넓게 둔 이유** — 대상 LOT 의 출발 상태가 원천 둘로 갈린다. `PRODUCT`(OQC 불합격)는 `DEFECTIVE`(C6)이고, `RETURN`(반품 입고)은 **원 LOT 을 그대로 쓰므로**(`W-04-07` §5-4) `NORMAL` 이거나 `INSPECTION_PENDING` 이다. 좁히면 반품 갈래 본길이 통째로 400 으로 죽는다.
- ⚠ **「불량(Hold)은 발신 전이가 0」**(계약 `quality-03품질.json:4472` · `W-03-02` §5-5)과 부딪히지 않는다: ⓐ 그 문장은 `W-03-02` 화면의 3전이(C7·C8·C9) 범위에서 쓰였고, **`W-03-10`(처분 판정 처리)은 2026-08-13 DR-008 확정 3-A 로 «나중에» 신설된 화면**이다 ⓑ 저장소가 이미 `DEFECTIVE` 발신 전이를 하나 갖고 있다(`stock-reinstate` · `transitions.ts:218-219`).

### 📨 함께 열어 주셔야 하는 것 (통보 154 의 요구를 확장한다)

> **`LotStatusHistoryEvent.transitionCode` 의 enum 과 `GET /trace/lot-status-events` 의 질의 파라미터 enum 을 `C17`·`C18`·`C19`(그리고 §7 의 재등록 코드)까지 열어 주십시오.**
> 열리지 않으면 그 조회의 응답이 계약을 위반한 채 나갑니다 — 서버에는 응답 런타임 검증이 없고(`src/common/contract/contract-validation.guard.ts` 에 response 경로 0), **행을 떨어뜨리는 쪽은 감사 조회가 사건을 숨기는 것**이라 하지 않기로 이미 판정했습니다(통보 154).

⇒ 우리 마이그레이션이 `app.code_value` 의 `LOT_STATUS_TRANSITION` 그룹에 3값을 더한다(추가만 · 삭제 0 · 백필 0). 값이 다르게 오면 **`UPDATE` 한 문장**으로 갈아 끼운다.

## §2. 특채(한도승인)의 「유효」 상태 값 — **`'APPROVED'`** (⇐ 회신 대기 **문의 12**)

### 먼저 — 문의 12 의 원 물음은 **이미 설계가 답했다**

문의 12 는 「한도승인(특채) 재고 상태 값」이었다. `W-03-09`(특채·한도승인 처리)가 답을 갖고 있다:

> 「✓설계확정 **결정 10** … **LOT 상태 확정(2026-08-07)** — 「**최종 상태는 셋 다 `정상`이고 다른 것은 조건이다**」」 (`:31`)
> 「검사 불합격 → LOT 상태 = 불량 ↓ 특채 승인 승인 수량만큼 → **LOT 상태 = 정상** + `concession` 이 범위를 건다」 (`:164-169`)
> 「⚠ **상태만 바뀌는 것이 아니다** — `concession` 행이 살아 있어야 출고 시점에 범위 검사가 걸린다(`allowed_*`·`valid_to`·`approved − consumed > 0`). **A-14**(상태와 조건의 분리)가 여기서 실제로 작동한다」 (`:171`)

⇒ **새 LOT 상태 값을 만들지 않는다.** 특채분은 `NORMAL` 이고 제한은 `concession` 행이 진다.
⚠ 다만 **그 전이를 «일으키는» 오퍼레이션이 계약에 0건**이다 — `Concession` 스키마 설명이 「⛔ 생성 경로를 두지 않는다 … ⛔ 조건 수정 경로를 두지 않는다 … 승인·반려는 app-공통 계약이다」라 적었다. ⇒ **I-21 은 특채를 읽기만 한다.**

### 남은 것 — `concession.status_code` 의 값 목록이 없다

`W-03-09` §8 #2 가 **미결**로 남겨 뒀고(`:225` — 「`concession.status_code` 값 목록 · 공통코드 · 조정 · `W-06-06`·`#145`」), 시드에 **`CONCESSION_STATUS` 그룹 자체가 없다**(전수 grep 0건). 그런데 계약은 그 값을 쓰라고 요구한다 — `GET /quality/concessions.usableOnly` = 「⭐ 지금 쓸 수 있는 것만 — **상태**·유효기간·잔여의 **3항 논리곱**을 서버가 판정한다」.

### ⇒ 우리가 정한 것

```
usable =  status_code = 'APPROVED'
      AND valid_from <= 기준일
      AND (valid_to IS NULL OR valid_to >= 기준일)
      AND (approved_qty - consumed_qty) > 0
```

- **`'APPROVED'`** 를 고른 근거 — `app.approval_request.status_code` 가 **이미 그 값을 쓴다**(`transitions.ts` 의 `approval-approve: PENDING → APPROVED`). §2 2단계 **기준 5**(새로 만드는 개념의 수가 적은 쪽) ⇒ **새 코드 그룹 0 · 새 값 0**.
- ⛔ **시드에 `CONCESSION_STATUS` 그룹을 세우지 않는다** — 이 표에는 **writer 가 0개**(생성·승인·수정 오퍼레이션이 계약에 전부 없다)라 임의 값이 들어올 길이 없다. 값 목록이 오면 그때 그룹을 세우고 `assertCodeValues` 한 줄을 더한다.
- **기준일** = `validOn` 이 오면 그 날짜, 없으면 **서버 UTC 달력일**(`CURRENT_DATE`). ⛔ **타임존 캐스팅을 하지 않는다**(`valid_from`·`valid_to` 는 `@db.Date`). ⚠ **`concession` 에 공장 축이 0개**라 `plant.timezone_code` 로 풀 길이 없다 — **하노이 로컬 자정과 최대 7시간 어긋난다.** 유효기간 마지막 날 오전(하노이)에 만료로 보이는 창이 생긴다. 공장 축을 주시면 그때 갈아 끼운다.

## §4. `DispositionDecision.followUpStatusCode`·`followUpQty` — **처분 셋 중 «폐기»만 셀 수 있다**

계약은 둘 다 **required** 로 두고 「⭐ 서버가 후속 전표를 롤업해 낸다(L-2). ⛔ 화면이 후속 전표를 세어 판정하지 않는다」라 적었다. 그런데 **처분 유형마다 후속 축이 다르고, 둘이 비어 있다**:

| 처분 | 후속 화면 | 후속 전표가 처분 결정을 가리키나 | 오늘 셀 수 있나 |
|---|---|---|:-:|
| **폐기** `SCRAP` | `W-04-10` 제품 폐기 요청 | ✅ `logistics.goods_issue.source_document_type_code='DISPOSITION_DECISION'` + `source_document_id`(**NOT NULL 실재** · `ix_goods_issue_source` 실재 · `W-04-10:104`·`:230` 이 enum 3값을 못 박았다) | ✅ **센다** |
| **정상** `NORMAL` | `W-04-11` 재고 재등록 | ⛔ **`logistics.stock_reinstatement` 표가 물리에 없다**(전 마이그레이션 grep 0건 — I-23 · 레인 C 몫). 게다가 그 화면의 본문 필수는 `lotHoldId` 이지 `dispositionDecisionId` 가 아니다(`W-04-11:192`) | ⛔ **원천 0** |
| **재작업** `REWORK` | `P-04-03` 재작업 실적 등록 | ⛔ 축이 **부적합**이다 — `production.work_order.rework_source_nonconformance_id`(`P-04-03:4`). `production_result` 에 처분 결정 칸이 없다 ⇒ **결정 단위로 못 센다**(부적합 하나에 재작업 결정이 둘이면 어느 W/O 가 어느 결정인지 알 수 없다) | ⛔ **원천 0** |

### ⇒ 우리가 정한 것

- **폐기**만 `goods_issue` 를 롤업한다 — `followUpQty` = 그 결정을 원천으로 하는 `goods_issue_line.issue_qty` 합(`status_code`가 취소가 아닌 것) · `followUpStatusCode` = `NOT_STARTED`/`PARTIAL`/`COMPLETED`.
- **정상·재작업**은 `followUpQty = 0` · `followUpStatusCode = 'NOT_STARTED'` **고정**이다. ⛔ 키를 생략하지 않는다(required).
- 그 필연으로 **`GET /quality/disposition-decisions.reinstatable` 이 절반만 산다** — 계약이 「처분이 **정상**이거나, 처분이 **재작업이고 그 재작업이 끝난 것**을 서버가 한 축으로 판정해 낸다」라 적었으나, **뒤 갈래는 오늘 언제나 false** 다. `reinstatable=true` 는 사실상 `dispositionTypeCode='NORMAL'` 로 접힌다.
- ⚠ **화면이 「후속 없음」을 「아직 안 함」으로 읽게 된다** — `W-04-11`(재등록)·`P-04-03`(재작업)의 진입 목록이 `followUpPending=true` 라 **처리한 건이 계속 남는다**(계약이 「같은 건을 두 번 처리한다」라고 경고한 그 상황). 재작업·재등록 전표에 `disposition_decision_id` 축이 서면 그날 이 롤업이 완성된다.

📨 **처분 결정 단위로 후속을 세려면 `production.work_order` 와 재등록 전표에 `disposition_decision_id` 축이 필요합니다.**

## §5. `DispositionRequest` 의 세 칸이 **갈 데가 없다**

`POST /quality/nonconformances/{nonconformanceId}:request-disposition` 의 본문 `DispositionRequest` 는 `requestedQty`(required) · `uomId`(required) · `remarks` 셋이다. **`quality.nonconformance` 에 그 셋을 담을 칸이 하나도 없다**(21칸 전수 실측 — `prisma/schema.prisma:3427-3457`).

⇒ **형식만 검증하고 버린다** — `requestedQty >= 1`(계약 「1 이상이어야 한다」 · `W-04-07` §5-7) · `uomId` 가 부적합의 단위와 같은가. 어긋나면 400.
⇒ 이 오퍼레이션이 실제로 바꾸는 것은 **`status_code`(`NOT_REQUESTED` → `PENDING_DECISION`)와 `version_no` 둘뿐**이다.
선례: `plan.md` §5-9 의 「읽고 버림형」(`X-Worker-No` 가 담을 칸 0인 자리들) · §5-7 「원장 안 지나면 형식만 검증하고 저장 안 함」.

⚠ **의뢰 수량을 남기려면 칸이 필요합니다** — 부분 의뢰가 성립하는지(대상 200 중 120 만 의뢰) 자체가 오늘 데이터로 표현되지 않습니다.

## §6. 부분 처분이 **LOT 상태를 갈라 담을 수 없다**

계약과 화면이 **부분 처분을 정상으로** 못 박았다 — 「부적합 하나를 **수량으로 갈라** 여러 번 부를 수 있다 — 일부 재작업 · 일부 폐기가 성립한다」(`:2460`) · `W-04-07` §5-5 「200 EA 중 160 은 재작업 · 40 은 폐기가 자연스럽다」.
그런데 **`trace.lot.status_code` 는 LOT 하나에 한 값**이다. 160 REWORK 뒤 40 SCRAP 이면 도착이 둘인데 담을 자리가 하나다.

### ⇒ 우리가 정한 것

- **매 판정 저장마다 옮긴다.** 계약 문자(「판정 저장과 Lot Status 전이는 **한 트랜잭션**」)를 그대로 따른다. ⇒ **부분 처분이면 마지막 판정의 도착 상태가 남는다.**
- 옮기는 대상은 **그 부적합의 `nonconformance_lot` 전건**이다 — `quality.disposition_decision` 에 **`lot_id` 칸이 없어**(10칸 전수 실측) 결정이 LOT 을 가리키지 못한다. `W-03-10` 도 대상 LOT 을 **단수**로만 그리고(`:71`), §8 #7 이 「대상 LOT 단위가 섞이면 수량 합 불성립」을 **미결**로 남겼다.
- 그 미결을 **우리가 닫는다** — **부적합 등록(`NonconformanceCreate.lots[]`)에서 `uomId` 가 전부 같기를 강제한다**(다르면 400 `INVALID`). 그래야 `Nonconformance.affectedQtyTotal`·`uomId` 와 `DispositionRemainingSummary` 4칸(전부 required)이 성립한다. §2 2단계 기준 2(거부하는 쪽 — 거부→허용이 호환 완화).
- **부적합 등록은 LOT 을 옮기지 않는다** — 계약이 등록 전이를 안 적었다(§2 2단계 기준 1). 그 필연으로 `NonconformanceLot.qualityStatusBeforeCode` 와 `qualityStatusAfterCode` 가 **같은 값**이 된다. 계약 문자가 「등록 «전»/«후»」라 그대로 따랐다.
- **`sourceCode` 는 파생이다** — `quality.nonconformance` 에 칸이 없고 계약이 「⭐ 서버가 대상 LOT 의 **입고 유형**으로 파생한다」라 적었다. `goods_receipt.receipt_type_code='RETURN'` 으로 들어온 LOT 이면 `RETURN`, 아니면 `PRODUCT`. **대상 LOT 이 여럿이고 섞이면 `RETURN` 을 이긴 값으로 둔다**(놓치지 않는 쪽).
- **처분에 결재를 걸지 않는다** — `disposition_decision.approval_request_id` 는 비운 채 둔다. 「처분이 언제 결재를 타는가」는 `W-04-07` §8 #3 이 **2026-09-02 재확인에서도 열려 있고**(「소관으로 지목한 화면이 소관을 «부인»한다」) 확정된 승인 유형에 처분이 없다. 없음 → 있음이 호환 완화다.

📨 **부분 처분에서 LOT 상태를 어떻게 두실지 정해 주시면 그대로 갈아 끼웁니다** — 지금은 「마지막 판정이 남는다」입니다.
