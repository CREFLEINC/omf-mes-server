# 29. 한 물리 공급사 LOT 이 정량분·초과분으로 갈릴 때 — `W-01-03` 대표 시나리오를 `uq_lot(plant_id, lot_no)` 이 막는다

| 칸 | 내용 |
|---|---|
| 걸리는 오퍼레이션 | `POST /logistics/inbound-receipts:split`(I-3 PR ⑤·⑥) — 그리고 같은 공급사 LOT 을 두 입하로 나눠 등록하는 `POST /logistics/inbound-receipts` 두 번 |
| 구현 상태 | **구현함(§2 절차 1단계 가장자리 → 2단계 기준 2 「거부하는 쪽」)** — 400 `INVALID`, field `excess.lines.{i}.supplierLotNo`, 메시지 「한 요청 안에서 겹칩니다」 |
| 판정 | `coverage-100/README.md` §2 1단계 **가장자리**(두 part 가 같은 공장·같은 번호를 실을 때만 갈린다) → 2단계 **기준 2**(거부→허용은 호환 완화, 허용→거부는 깨는 변경) |
| 되돌릴 때 | 「한 LOT 을 두 입하 라인이 공유한다」는 답이면 물리(`uq_lot` 유지 · 라인 `lot_id` 가 기존 LOT 을 가리키게 허용)와 LOT 코어 `createWithin`(0행 귀속 규칙)이 함께 열린다 — 소형이 아니다. 「초과분은 미부착으로 보낸다」·「접미를 붙인다」는 답이면 서버 변경 0 |

## 무엇이 문제인가

`W-01-03`(초과 입하 분리)의 **대표 시나리오**는 「발주 100 에 한 공급사 LOT 120 이 도착 → 정량분 100 + 초과분 20」이다.
화면이 이것을 `:split` 으로 보내면 두 part 의 라인이 **같은 `supplierLotNo`** 를 싣는다 — 물리적으로 한 롤·한 팔레트이기 때문이다.

그런데 입하 라인의 LOT 은 채번을 타지 않고 **공급사 스캔값이 그대로 `trace.lot.lot_no`** 가 된다(계약 「`numberSourceCode=SUPPLIER` 축」 · I-3.md §5-1).
그리고 `trace.lot` 은 `uq_lot(plant_id, lot_no)` 이다. 두 입하 라인이 같은 공장·같은 번호로 LOT 을 «각각» 만들 수 없다.

| 상황 | 계약이 적었나 | 물리가 받나 | 서버 |
|---|:-:|:-:|---|
| 정량분·초과분이 서로 다른 LOT | ⭕ | ⭕ | 각 라인에 LOT 을 만든다 |
| 초과분 `supplierLotMissing=true`(대체 사유) | ⭕(미부착 갈래) | ⭕ | 초과분은 LOT 없이 저장 · P-01-01 이 나중에 채운다 |
| **한 LOT 이 두 part 에 실림** | ✕ **침묵** — `W-01-03` §4-B 는 `purchase_order_line_id` 만 갈랐다 | ✕ `uq_lot` | **400 `INVALID`** ← 이 문의 |

계약 `InboundReceiptCreate` 의 「자재 LOT 은 공급사 LOT 이 부착된 라인에만 **함께 생긴다**」는 라인:LOT = 1:1 을 전제하고,
`W-01-03` 은 수량을 가르는 절차만 적었다. **한 물리 LOT 이 두 입하 라인에 걸치는 경우를 어느 쪽도 다루지 않았다.**

## 지금 서버는

- `:split` 은 두 part 를 **한 요청**으로 보고 `(plantId, supplierLotNo)` 겹침을 미리 거른다 — 400 `INVALID`, field `excess.lines.{i}.supplierLotNo`(요청 순서상 뒤에 오는 초과분 칸을 짚는다).
  두 part 의 `plantId` 가 다르면 같은 번호를 허용한다(`uq_lot` 이 공장 단위라 서버가 더 좁히지 않는다).
- 막지 않으면 트랜잭션 안 두 번째 LOT INSERT 가 P2002 로 죽고, 공용 그물이 이것을 필드 없는 `UNIQUE_VIOLATION`(「이미 있는 값입니다」)으로 내린다 — 화면이 어느 칸을 고칠지 모른다(I-3 R-7 ③ 이 없애려던 모양).
- `POST /logistics/inbound-receipts` 두 번으로 나눠 등록해도 두 번째가 `UNIQUE_VIOLATION` 이다(같은 물리 제약 · 요청이 갈려 미리 못 짚는다).
- 흔적: 단위 「분리 — 두 part 에 같은 공장의 같은 supplierLotNo 가 실리면 excess.lines.{i}.supplierLotNo 를 짚는 400 INVALID 다」 · e2e 「분리 — 정량분·초과분이 같은 공급사 LOT 을 실으면 400 INVALID 가 초과분 칸을 짚는다」 + 코드 주석 `// 설계 미정 — 문의 029`(`inbound-receipt-split.service.ts`).

## 요청

1. **`W-01-03` 에서 초과분 라인의 `supplierLotNo` 는 무엇입니까?** — ⓐ 정량분과 같은 번호(한 물리 LOT) ⓑ 화면이 `supplierLotMissing=true` 로 켜고 대체 사유를 붙인다 ⓒ 접미(`-EX` 류)를 붙여 다른 번호로 만든다 ⓓ 그 밖.
   ⓐ 라면 **한 `trace.lot` 을 두 입하 라인이 공유**해야 하고, 그러면 LOT 의 `initial_qty`·계보(`source_type_code=INBOUND_RECEIPT_LINE` 단건)·라벨 발행 단위가 «입하 라인»이 아니라 «물리 LOT» 으로 바뀝니다 — 초과분이 반품될 때 LOT 의 어느 부분이 나가는지도 함께 정해야 합니다.
2. ⓐ 라면 **초과분 → 신규 P/O(`W-01-11` §5-3) 승계 라인**(`purchase_order.source_inbound_receipt_line_id`)이 가리킬 입하 라인의 LOT 이 정량분 LOT 과 같은 것이어도 됩니까?
3. 곁들여: 같은 물리 LOT 이 **두 번의 도착**(다른 날 · 다른 입하)으로 나뉘어 오는 경우도 같은 제약에 걸립니다 — 「공급사 LOT 번호 = MES LOT 번호」 축을 유지할지, 공급사 번호는 속성으로 두고 MES 가 채번할지(`numberSourceCode=MES` 로 통일) 확인해 주십시오.

우리 권고안(회신이 없으면 이대로 갈 값): **ⓑ — 초과분은 `supplierLotMissing=true` + 대체 사유로 보내고, 서버는 겹침을 400 으로 거절한다.**
초과분은 정의상 P/O 비귀속이고 신규 P/O 로 넘어가 다시 입하 흐름을 타므로, 그때 `P-01-01` 이 MES 번호로 LOT 을 채우는 갈래가 이미 계약에 있습니다.
거절→공유는 나중에 열 수 있고(물리·코어 변경이 필요하나 호환 완화), 공유→거절은 깨는 변경입니다.
