# 193. **납품라벨 번호를 담을 칸이 저장소 전체에 0개**라 `GET /logistics/shipment-lot-allocations?q=` 가 겨냥할 축이 없다

**구분: 통보**(회신을 기다리지 않는다) · ⭐ **3관점 재검토가 초판의 판정(「`handling_unit_no` 에 붙인다」)을 뒤집었습니다**

| 칸 | 내용 |
|---|---|
| 걸리는 오퍼레이션 | `GET /logistics/shipment-lot-allocations`(질의 `q`) |
| 구현 상태 | **구현 예정(I-22 PR ⑦a)** — `q` 는 **어떤 행에도 안 걸립니다**(빈 목록) |
| 판정 | §2 **1단계 본길** → **2단계 기준 4**(값을 «조용히» 도출하지 않는다) — 축을 지어내지 않는다 |
| 되돌릴 때 | 칸이 생기면 `WHERE` 한 줄과 e2e 한 건 |

## 계약이 요구하는 것

> `q` — 「스캔한 **납품라벨** 값으로 배분을 찾는다. ⛔ **범위는 납품라벨 번호 하나다 — LOT 번호는 `lotId` 를, 포장은 `handlingUnitId` 를 쓴다.** ⭐ `P-04-01` 매칭 스캔의 진입이다 … 일치하는 배분이 없으면 «빈 목록»이다 — 화면은 `items` 가 비었는지로 「없는 납품라벨」을 판정한다. ⛔ **404 를 내지 않는다**」

`P-04-01` §3 목업이 실제로 찍는 값은 **`DL-2026-0455-001`** 입니다.

## ⛔ 그 값을 담는 칸이 없습니다

| 후보 | 실측 |
|---|---|
| `inventory.handling_unit` | `handling_unit_no` 하나뿐 — **라벨 번호 칸 0** |
| `app.document_issue_log`(발행 이력) | `document_type_code`·`target_type_code`·`target_id`·`lot_id`·`issue_seq` … — **발행 «번호» 칸 0** |
| `logistics.shipment_lot_allocation` | 라벨 축 0 |

⛔ **그리고 `handling_unit_no` 에 얹을 수도 없습니다.** 계약이 같은 문장에서 **포장 축을 `q` 에서 명시적으로 배제**하고 `handlingUnitId` 에 이미 배정했기 때문입니다. 얹으면 계약이 갈라 둔 두 축이 겹칩니다.
게다가 **첫 스캔에서 거짓 음성**이 납니다 — `P-04-01` §5-1 의 ① 납품라벨 스캔은 **포장을 만들기 «전»** 이라 그 배분에 `handling_unit_id` 가 아직 NULL 입니다. 실제 납품라벨을 찍으면 「없는 납품라벨」이 뜹니다. `P-04-01` §5-4 가 「형식 검증을 안 하니 **매칭 판정이 유일한 방어선**」이라 적은 그 방어선이 무너집니다.

## ⇒ 우리가 정한 것

`q` 는 **어떤 축에도 안 붙입니다.** 준 값과 무관하게 **200 + 빈 목록**입니다(계약이 「빈 목록 · 404 금지」를 이미 못박았으므로 형식은 지켜집니다).
`lotQ` + `shipmentId` 의 **`match` 판정은 그대로 구현합니다** — 그쪽은 `trace.lot.lot_no` 라는 실재하는 축이 있습니다.

## 📨 알려 드리는 것

**납품라벨 번호를 어디에 담을지 정해 주십시오.** 셋 중 하나로 보입니다:
ⓐ `shipment_lot_allocation` 에 `delivery_label_no` 를 신설 · ⓑ `document_issue_log` 에 발행 번호 칸을 신설(라벨 발행이 `P-04-02` 소관이라 자연스럽습니다) · ⓒ 「납품라벨 = 취급단위 번호」로 규약을 통일하고 계약 `q` 의 「포장은 `handlingUnitId` 를 쓴다」 문장을 지운다.

⛔ 그 전까지 **`P-04-01` 의 첫 스캔(①)이 서지 않습니다.** ② 생산 LOT 스캔(`lotQ`)만 동작합니다.
