# 52. ⭐ 「계보가 시작되는 지점」이라 적었는데 서버가 «어느 생산 LOT» 인지 가릴 축이 없다

| 칸 | 내용 |
|---|---|
| 걸리는 오퍼레이션 | `POST /production/material-consumptions` |
| 구현 상태 | **구현함(I-10 · `trace.lot_relation` INSERT 0 · `production.material_usage_allocation` INSERT 0 · 투입 상한 미검사)** |
| 판정 | `coverage-100/README.md` §2 1단계 **본길**(04 종결점 `GET /logistics/shipment-lot-allocations` 까지 흐르는 값이라 틀리면 출하 추적 전체가 틀린다) → 계약도 그 축은 **침묵** ⇒ 계약 문자 그대로 + 문의 · 2단계 기준 1·2·4 셋이 같은 답 · 계약이 이 자리에서 스스로 인용한 **A-21** |
| 되돌릴 때 | ① 「슬롯이 정확히 하나일 때만 이어라」면 예비안 — 서비스에 슬롯 1건 분기 + `lot_relation` INSERT ② 「계약이 요구한 것은 «등록 시점»이 아니라 «계보의 존재»」면 실적 시점(I-7 `production_result_lot_allocation`)에 잇는 **후속 오퍼레이션 신설** — 오늘 계약에 0건이다 ③ 어느 쪽이든 `relation_type_code`·`allocation_method_code`·`trace_accuracy_code` 세 값이 **먼저** 와야 한다(053 과 같은 뿌리) |

## 무엇이 문제인가

ⓐ 계약 POST 설명이 ⌜서버가 계보 관계를 이 등록과 **한 트랜잭션**으로 만든다(B-8)⌝ 라 적었으나, `trace.lot_relation` 의 NOT NULL 여섯 칸(`target_lot_id`·`relation_type_code`·`relation_qty`·`uom_id`·`allocation_method_code`·`trace_accuracy_code`) 중 **하나도 본문에 없다**. I-7 은 같은 문제를 클라이언트가 `allocations[].lotId` 를 보내서 풀었는데 투입에는 그 칸이 없다.
ⓑ 한 W/O 의 선발행 슬롯은 **N 개**(확정배포가 받은 `lotNos` 길이)이고 투입 시점에는 **전부 `WAITING`** 이다(`ACTIVE` 로 옮기는 것은 실적 · M2 체인이 「… 투입 → 세션 → 실적 …」 순). 긴급 W/O 는 슬롯이 **0 개**다.
ⓒ 「슬롯 전건에 N 행」은 `relation_qty` 합이 **N × `input_qty`** 가 되고(`uq_lot_relation` 축), 「첫 슬롯」·「지금 `ACTIVE`」는 사실상 언제나 `work_order_lot_seq = 1` 이라 **모든 자재가 1번 생산 LOT 에 붙는다**.
ⓓ 계약이 스스로 인용한 **A-21 ⌜일부만 채워진 것이 빈 것보다 위험하다⌝** 가 반쪽 안을 막는다. 화면도 ⌜⚠ 값 목록은 아직 서지 않았다⌝ · ⌜1:1 스캔만 우선 지원한다⌝(`P-02-03` §5-4)로 같은 자리에 서 있다.
ⓔ 덤으로 `material_usage_allocation` 은 CHECK `ck_material_usage_target` 이 `production_result_id`/`output_lot_id` 중 하나를 요구하는데 투입 시점에 **둘 다 없고**, I-7 이 「I-10 것」이라 넘겼다 ⇒ **이 표를 채우는 자리가 저장소 전체에서 0** 이다.
ⓕ 투입 상한(`shopfloor_receipt_line.received_qty`)도 소진 누계를 셀 칸이 I-9 에서 이미 없어 검사하지 않는다.
ⓖ 같은 결손이 **정확도도 함께 깎는다** — `P-02-11` §5-3 이 ⌜투입 Validation = 해당 LOT BOM 기준 · `Lot.bomSnapshot` 이 있으면 그 값, 없으면 W/O BOM⌝ 이라 적었고 `trace.lot.bom_id`·`bom_version` 이 물리에 실재하는데, 생산 LOT 축이 본문에 없어 서버는 **«물러난 가지»(W/O BOM)만** 탄다.

## 지금 서버는

- `trace.lot_relation` INSERT **0** — 사용처 0 인 상수를 두지 않으므로 후보 문자열(`'MATERIAL_CONSUMPTION'` — `app.entity_type_registry` 25행 중 실재하는 유일한 이름)은 **주석 한 줄**로만 남겼다.
- `material_usage_allocation` INSERT **0** · 투입 상한 검사 **0**(수령량보다 많이 투입해도 201).
- 셋 다 e2e 가 픽스처 `lot_id`/`item_id` 축의 **DB 직접 SELECT** 로 단언한다.
