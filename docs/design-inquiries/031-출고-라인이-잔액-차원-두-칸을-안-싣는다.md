# 31. 출고 라인이 잔액 차원 두 칸(`qualityStatusCode`·`inventoryStatusCode`)을 안 싣는다 — 한 (위치·LOT) 에 재고 행이 둘이면 어느 것을 내는지 계약이 말하지 않는다

| 칸 | 내용 |
|---|---|
| 걸리는 오퍼레이션 | `POST /logistics/goods-issues/{goodsIssueId}:post` · `POST /logistics/goods-issues`(`postImmediately=true`) — 라인 스키마 `GoodsIssueLineUpsert` |
| 구현 상태 | **구현함(§2 절차 1단계 가장자리 → 2단계 기준 2 「거부하는 쪽」)** — 7칸(le·bu·plant·창고·위치·품목·LOT)으로 잔액을 잠가 읽고 **1행이면 그 행의 값을 그대로 쓴다 · 0행이면 400 `NEGATIVE_BALANCE` · 2행 이상이면 400 `INVALID`**(field `lines[i].lotId`) |
| 판정 | `coverage-100/README.md` §2 1단계 **가장자리**(잔액 행이 둘 이상일 때만 갈린다) → 2단계 **기준 2**(서버가 하나를 고르면 «어느 품질 상태의 재고를 냈는가»가 조용히 원장에 남는다 — 되돌리기 비싸다) · 새 에러 코드 0(기준 5) |
| 되돌릴 때 | 「라인이 두 칸을 싣는다」로 오면 `GoodsIssueLineUpsert` 에 두 칸을 더하고 잠금 키를 9칸으로 넓힌다(`issue-posting.ts` 한 자리). 「서버가 정해진 우선순위로 고른다」로 오면 2행 분기 하나를 우선순위 선택으로 바꾼다 |

## 무엇이 문제인가

재고 잔액(`inventory.inventory_balance`)의 유일 차원 `uq_inventory_balance_dim` 은 **11칸**이다. 출고 라인이 주는 것은 그중 6칸(창고·위치·품목·LOT + 창고에서 푸는 le/bu/plant)이고, **`quality_status_code`·`inventory_status_code`·`ownership_type_code`(+`owner_partner_id`)를 계약이 안 싣는다.**

| 라인 스키마 | `qualityStatusCode` | `inventoryStatusCode` |
|---|:-:|:-:|
| 입고 `GoodsReceiptLineCreate` | ⭕ 있다 | ⭕ 있다 |
| 출고 `GoodsIssueLineUpsert` | ✕ | ✕ |

입고는 라인이 실어 보내는 값을 **그대로** `to` 차원에 싣는다(`src/logistics/goods-receipt/receipt-posting.ts:130-134`). 그래서 같은 (위치·LOT)에 `NORMAL` 입고와 `DEFECTIVE` 입고가 두 번 들어오면 **잔액 행이 두 벌 선다** — 이론이 아니라 지금 코드로 실제 도달한다. 출고는 «이미 있는 행»을 깎는 것이라 입고처럼 서버가 고르는 자리가 아니라 **찾는 자리**인데, 두 벌이면 찾을 수 없다.

화면도 이 경우를 표현할 길이 없다 — `W-01-05` §3 반품 목록은 (LOT·위치)당 **한 행**이라 품질 상태별 2행을 보이지 않는다.

## 지금 서버는

`(le, bu, plant, warehouse, location, item, lot)` 7칸으로 잔액을 `FOR UPDATE` 로 잠그고 읽는다.

| 결과 | 응답 |
|:-:|---|
| 1행 | 그 행의 `quality_status_code`·`inventory_status_code`·`ownership_type_code`·`owner_partner_id` 를 `from` 에 싣는다 |
| 0행 | 400 `NEGATIVE_BALANCE` — 「이 위치에 그 LOT 의 재고가 없습니다」 |
| 2행 이상 | 400 `INVALID` — 「재고 차원이 둘 이상이라 어느 것을 낼지 정할 수 없습니다」 |

- 도착이 `LOCATION`(창고 안/사이 이동)이면 `to` 의 두 칸도 **`from` 과 같은 값**을 쓴다 — 이동에서 품질·재고 상태가 바뀌는 축이 계약에 없다(값을 «바꾸지» 않는 쪽이 조용히 도출하지 않는 쪽 · §2 2단계 기준 4).
- 흔적: 단위 `전기 — 같은 7칸에 잔액 행이 둘이면 400 INVALID 다(문의 031)` + 코드 주석 `// 설계 미정 — 문의 031`(`src/logistics/goods-issue/issue-posting.ts`).

## 요청

1. **출고 라인이 `qualityStatusCode`·`inventoryStatusCode` 를 실어야 합니까?** 입고 라인과 같은 두 칸을 `GoodsIssueLineUpsert` 에 더하면 서버는 9칸으로 정확히 한 행을 찾습니다. 반품(`W-01-05`)·폐기(`W-01-06`)는 「불량 재고를 낸다」가 업무라 화면이 값을 알고 있을 것입니다.
2. **싣지 않는다면 — 두 벌일 때 서버가 어느 것을 먼저 내야 합니까?** (예: 불량 우선 · 정상 우선 · 오래된 것 우선). 규칙을 주시면 2행 분기를 그 우선순위로 바꿉니다. ⚠ 규칙 없이 서버가 고르는 것은 원장에 남는 값을 조용히 정하는 일이라 지금은 하지 않습니다.
3. 곁들여: 이동(`destinationTypeCode=LOCATION`)에서 **품질·재고 상태가 바뀌는 갈래**(예: 검사 뒤 정상 위치로 옮기며 `DEFECTIVE → NORMAL`)가 있는지 확인해 주십시오. 있다면 그것은 출고가 아니라 별도 오퍼레이션(`M-01-05`류)의 몫인지도 함께 알려 주십시오.

우리 권고안(회신이 없으면 이대로 갈 값): **2행 이상은 400 `INVALID` 로 거절한다.** 거절→선택은 나중에 풀 수 있고, 잘못 고른 재고는 원장에서 되돌릴 수 없습니다(역트랜잭션은 I-5).
