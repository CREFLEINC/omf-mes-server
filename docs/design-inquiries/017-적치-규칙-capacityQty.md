# 17. 적치 규칙 `capacityQty` 를 권장 판정에 어떻게 쓰나

| 칸 | 내용 |
|---|---|
| 걸리는 오퍼레이션 | `POST /logistics/goods-receipts`(적치 지시 생성) · `POST /logistics/putaway-tasks/{id}:complete` · `:complete-temporary` |
| 구현 상태 | 구현함 — 활성 규칙 중 `priority_no asc` 첫 건만 권장, 한도 미적용 (PR #180) |
| 판정 | §2 1단계 가장자리(한도에 걸리는 위치만) → 2-1 원장·상태 안 씀(권장값은 참고값) → 2-5 새 개념(한도 비교 축·초과 처리 상태) 안 만듦 |
| 되돌릴 때 | `createPutawayTask` 의 규칙 선택 함수 한 곳. 초과 시 「다음 우선순위」면 정렬 순회 추가, 「권장 없음」이면 null. 기존 지시는 참고값이라 이관 없음 |

## 무엇이 문제인가

`putaway_rule.capacity_qty` 가 물리에 있고 화면(`W-01-xx` 적치 규칙)도 입력받는데, 권장 위치 산출에
그것을 **어떻게** 쓰는지가 계약·워크플로 어디에도 없다. 계약은 「우선순위가 작을수록 먼저 권장」만 적었다.

한도를 보려면 둘이 필요하다.
1. **무엇과 견주나** — 그 위치의 현재 잔량 + 이번 지시 수량? 이번 지시 수량만? 대기 중 적치 지시까지 합산?
2. **넘치면 어디로** — 다음 우선순위 규칙으로 넘어가나, 권장 없음(`recommendedLocationId` 생략)인가, 경고만 하나?

## 지금 서버는

한도를 보지 않는다. 우선순위 첫 규칙의 위치를 권장한다.

## 요청

위 둘을 정해 달라. 우리 권고안(회신이 없으면 이대로 갈 값): **1 = 현재 잔량 + 이번 지시 수량**,
**2 = 다음 우선순위로 넘어가고 전부 넘치면 권장 없음**. 이유: 화면이 「권장 위치」를 참고값으로 쓰므로
틀린 권장보다 빈 권장이 낫고, 대기 중 지시까지 합산하는 것은 새 개념(예약)을 만든다.
