# 142. 확정된 포장을 «여는» 길이 0 이다 — 되돌리는 오퍼레이션도 삭제도 없고, 두 종류의 409 도 구분되지 않는다

| 칸 | 내용 |
|---|---|
| **구분** | **통보** — 계약에 없는 오퍼레이션을 짓지 않는다. 해제 경로를 열면 서버 한 자리다 |
| 걸리는 오퍼레이션 | `POST /inventory/handling-units/{handlingUnitId}:pack` · `POST /inventory/handling-units`(고아 `OPEN` HU) · ⛔ 계약에 **없는** 것: 확정 해제·포장 해체·HU 삭제 |
| 구현 상태 | **구현 예정(I-16 · 계획만 병합됨 · 오늘 코드 0줄)** |
| 판정 | `coverage-100/README.md` §2 **0단계에 선례 0**(계약·화면 둘 다 「경로를 두지 않는다」로 닫았다) → **2단계 기준 1**(상태를 «덜» 쓰는 쪽 — 전이를 하나만 만든다) **· 기준 2**(없는 오퍼레이션을 지어내지 않는다) |
| 되돌릴 때 | 해제 경로를 열면 오퍼레이션 1건 + 상수/전이 1건(서버 한 자리). 409 구분은 봉투에 칸이 생기면 서비스 한 자리. 고아 HU 는 삭제 오퍼레이션 1건 |

## 무엇이 문제인가

ⓐ **`PACKED` 를 되돌리는 경로가 계약에도 화면에도 0건이다.** I-16 의 7 오퍼레이션(등록·목록·상세·구성 조회·구성 치환·이력 조회·포장 확정)에 확정 해제가 없고, HU 를 지우는 DELETE 도 없다. 화면이 그 부재를 스스로 적었다:

- `P-02-08-포장작업.md:162` — 「**포장 해체** | ⚠ **화면이 없다** — 내용물이 기록 전용이라 되돌리려면 별도 경로가 필요하다 §8-4 ⚠ 가장 가까운 것은 `M-04-03` 포장 재구성(`PUT …/contents`)이나 **수량 합 = 원 수량 합** 제약이 걸려 포장 밖으로 빼지 못한다 — **해체가 아니다**」
- `P-04-01-Packing실적등록.md:241` — 「포장 해체 | ⛔ **두지 않는다** — 02 도메인의 되돌리기 계열(#78 코멘트)」
- `P-02-08-포장작업.md:194`(같은 화면의 교훈 절) — 「담는 관계(`content`)가 기록 전용이면 「해체」 경로를 함께 설계한다 — **되돌릴 수 없는 담기는 현장에서 반드시 문제가 된다**」

⇒ 작업자가 잘못 확정하면 그 포장은 **영구히 잠긴다.** 계약의 `x-no-code-key` 도 같은 부재를 근거로 삼았다 — 「⚠ P-02-08 §8-4 가 「포장 해체 화면이 없다」고 적어 **뒤쪽 값이 업무에 없다**」(`contracts/logistics-01자재창고.json:8547`).

ⓑ **`:pack` 이 내는 두 종류의 409 를 클라이언트가 가를 수 없다.** 계약 `ConflictResponse` 는 `conflictCause`(enum `user`·`erpSync`·`workerLease`)와 `message` **둘뿐**이고 `code` 칸이 없다. 그런데 이 오퍼레이션의 409 는 뜻이 정반대인 둘이다 — ⓘ **이미 확정된 포장**(`contracts/logistics-01자재창고.json:1585` 「이미 확정된 포장은 409 다」 — 다시 읽어 와도 안 풀린다) · ⓘⓘ **낙관적 잠금 토큰 불일치**(`If-Match` — 다시 읽어 오면 풀린다). 같은 봉투로 나가면 단말이 「재시도하면 되는가」를 판정할 수 없다(공유계약 G-1 이 그 둘을 반드시 가르라고 적은 자리다).

ⓒ **못 확정한 포장도 갈 곳이 없다 — 고아 `OPEN` HU.** 계약이 두 왕복 흐름을 적었다(`contracts/logistics-01자재창고.json` `:pack` 의 `x-internal-note`): 「**POST /inventory/handling-units 는 빈 포장 단위를 만들고**, 이 액션이 내용물과 함께 닫는다 — 두 왕복인 것은 스캔이 여러 번 일어나기 때문이다」. 화면도 확정 «전»에 이미 포장번호를 보인다. 그런데 **삭제 오퍼레이션이 0건**이고 화면은 「내용물 0 → 확정 **비활성**」(`P-02-08-포장작업.md:157` 「내용물 0 | 확정 비활성 — 빈 포장은 만들지 않는다」)이라, **스캔만 하고 이탈하면 번호를 단 빈 `OPEN` HU 가 영구히 남는다.** 더 나쁜 것은 그 행이 상위 포장 후보 목록에 그대로 섞인다는 점이다 — `P-04-01-Packing실적등록.md:172` 「`GET /inventory/handling-units?warehouseId=…&statusCode={포장 가능}`」.

## 지금 서버는

- **아직 없다.** 계획이 정한 동작: 상태 전이는 **`OPEN → PACKED` 한 방향뿐**이고 되돌리는 전이는 0이다(문의 141).
- `:pack` 이 이미 `PACKED` 인 HU 를 받으면 **409** 를 내고, 「이미 확정」 판정이 If-Match 대조보다 **먼저** 돈다(확정된 포장에 낡은 토큰으로 다시 쏘면 「다시 읽어 오면 풀린다」가 거짓말이 되기 때문). 봉투에 코드 칸이 없으므로 **`message` 문구를 상수 둘로 갈라** 단말이 문자열로 구분하게 두었다 — 새 `ERROR_CODE` 는 만들지 않는다.
- 고아 `OPEN` HU 를 지우거나 만료시키는 동작은 **없다**. 채번은 이미 나간 뒤라 번호도 그대로 소비된다.
- `PUT …/contents` 는 `PACKED` 포장도 그대로 치환한다(200) — 재구성이 확정된 포장을 다루는 본길이기 때문이다. 즉 「구성은 바꿀 수 있는데 상태는 못 되돌린다」가 된다.

⇒ **묻는 것**: `PACKED` 를 되돌리는 경로(확정 해제 또는 HU 삭제)를 열 것인가 · 열지 않는다면 ⓑ 두 종류의 409 를 클라이언트가 가를 수단을 봉투에 둘 것인가 · ⓒ 내용물 없이 남은 `OPEN` HU 는 누가 치우는가(치우지 않는다면 `P-04-01` 상위 포장 후보 목록에서 어떻게 거르는가).
