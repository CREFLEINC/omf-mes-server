# 161. 수리 왕복의 데이터 축 **셋**이 비어 있다 — 결과 코드 그룹 0행 · 동시 투입을 막는 제약 0 · 멱등의 둘째 그물 0

> ⚠ **셋 다 「오늘은 무해하고 내일 걸린다」 부류다.** 계약·물리가 준 것만 쓰고 서버가 축을 세우지 않았다는 사실을 알린다.
> ⚠ **초안이 적었던 「멱등 보존 72시간이 지난 뒤」 시나리오는 사실이 아니라 걷었다** — 저장소에 **만료 청소기가 없다**(§ⓒ).

| 칸 | 내용 |
|---|---|
| **구분** | ⭐ **통보** — 값·제약을 서버가 만들지 않는다(코드 값은 계약·기준정보 소관 · 부분 UNIQUE 는 마이그레이션이다). 그 대가를 사실로 알린다. 회신을 기다리지 않는다 |
| 걸리는 오퍼레이션 | `POST /production/repair-executions` · `POST /production/repair-executions/{repairExecutionId}:return` · `GET /production/repair-executions` |
| 구현 상태 | **구현 예정(I-25 · 계획 PR 만 · 오늘 코드 0줄)**. 계획서 `docs/coverage-100/slices/I-25.md` §1-5 · §5-2 · §6-2 |
| 판정 | `coverage-100/README.md` §2 **2단계 기준 3**(스키마를 안 늘린다 — 부분 UNIQUE 인덱스는 마이그레이션이고 이 슬라이스의 「마이그 0」과 충돌한다) · **기준 4**(값을 조용히 도출하지 않는다 — 코드 그룹을 서버가 시드하지 않는다) · **기준 5**(새 개념 0) |
| 되돌릴 때 | ⓐ 코드 그룹이 시드되면 **코드 변경 0**(ajv 가 계약 enum 으로 이미 막고 있어 서버는 대조하지 않는다) ⓑ 부분 UNIQUE `(defect_record_id) WHERE returned_at IS NULL` 는 **추가만 하는 마이그 1건**이다 — 다만 세우면 409 를 서비스가 아니라 DB 가 내므로 예외 매핑 한 줄이 붙는다 ⓒ `idempotency_key` 칸을 더하면 마이그 1건 + 서비스 두 줄 |

## 무엇이 문제인가

### ⓐ `CD-REPAIR-RESULT` 코드 그룹이 **DB 에 0행**이다

- 계약 `RepairExecutionReturn.repairResultCode` 는 enum **`SUCCEEDED`·`FAILED`** 로 **닫혀 있고** `x-code-key: CD-REPAIR-RESULT` 를 단다(응답 `RepairExecution` 쪽은 `null` 포함 3값).
- DB 실측 — `mdm.code_group` 에 `group_code ILIKE '%REPAIR%'` **0행**.
- ⇒ **`assertCodeValues` 를 걸지 않는다.** 걸면 정상 값(`SUCCEEDED`·`FAILED`)조차 **전건 400** 이 된다(I-10 §3-6 ⓐ 에서 같은 병이 났다). ajv 가 계약 enum 을 이미 강제하므로 **오늘은 무해**하다.
- ⚠ **내일 걸리는 자리**: 화면이 「수리 결과」 드롭다운을 기준정보에서 그리려 하면 값을 받아올 곳이 없다. 그리고 값이 셋 이상으로 늘면 **계약 enum 을 고쳐야** 한다(코드 그룹만 늘려도 가드가 막는다).

### ⓑ 같은 불량에 **동시** 투입이 오면 열린 수리 건이 둘 생길 수 있다

- 계약이 409 를 선언했다 — ⌜충돌 — **같은 불량에 열린 수리 건이 이미 있다**⌝(`ProductionConflictResponse.code` enum 의 `OPEN_SESSION_EXISTS`).
- 서버는 그 판정을 **읽기 검사**로 한다 — `findFirst({ defect_record_id, returned_at: null })` 이 있으면 409.
- ⛔ **`SELECT … FOR UPDATE` 를 쓰지 않는다.** 선례(`work-session.service.ts:61-64`)는 **W/O 를 이미 잠근 뒤** 열린 세션을 보는데, 이 자원에는 **잠글 부모가 없다** — `quality.defect_record` 는 계약이 ⌜기록 전용이라 이쪽을 갱신하지 않는다⌝ 라 못 박은 표라 잠금 대상으로 쓰면 기록 전용 표를 쓰기 대상으로 만드는 것이다.
- ⛔ **부분 UNIQUE 인덱스도 세우지 않는다** — `(defect_record_id) WHERE returned_at IS NULL` 은 마이그레이션이고, 이 슬라이스의 **「마이그 0」**(세 계획서가 전부 「없음」으로 적었다)과 충돌한다.
- ⇒ **경합 시 열린 건이 둘 생길 수 있다.** ⚠ 대가는 작다 — 한 불량을 두 단말이 «동시에» 투입하는 시나리오는 현장에서 발생하지 않고, 생기면 `open` 목록에 두 줄이 보인다(**데이터 손실 0** · 반출은 각각 닫힌다).

### ⓒ 멱등의 **둘째 그물**이 없다 — 그리고 「만료 뒤 재전송」은 오늘 일어나지 않는다

- 실측: `production.repair_execution` 과 `operation_handover` 에는 **`idempotency_key` 칸이 없다**. 같은 도메인에서 그 칸을 가진 것은 `material_consumption`·`material_return`·`work_session` 셋뿐이다.
- ⇒ 중복 방지의 **첫째 그물은 공용 멱등 봉투** 하나이고, **둘째 그물**은
  - `:return` — **구간 자체**다(이미 닫힌 구간은 `returned_at !== null` 판정이 409 `INVALID_STATE` 로 막는다),
  - `POST /operation-handovers` — **0**이다(유일 제약이 서버가 채번하는 `handover_no` 뿐이라 업무 축의 중복을 막지 못한다).

⚠ **초안이 적었던 「멱등 보존 72시간이 지난 뒤 같은 키로 재전송하면 409 가 된다」는 사실이 아니다.** 실측:

- `RETENTION_HOURS = 72` 는 `expires_at` 을 **쓰기만** 한다(`idempotency.service.ts:13`·`:125`).
- `idempotency_record` 를 **지우는 코드가 `src/` 전체에 0건**이다(테스트의 `deleteMany` 는 픽스처 정리다).
- ⇒ **만료 청소기가 없어** 72시간이 지나도 기록이 남고, 같은 키·같은 지문이면 `replay()` 가 **200/201 을 재생**한다. 그 시나리오는 **오늘 도달하지 않는다**.

⭐ **안전한 것도 함께 적어 둔다** — 같은 멱등키를 **다른 `repairExecutionId`** 에 재사용해도 조용한 오배송이 없다. 지문이 `${method} ${구체 경로}`(`master-write.ts:37`)라 지문이 갈려 **409 `DUPLICATE_KEY`** 가 난다.

### ⓓ 덤 — 계약의 전제가 물리와 다른 자리 하나

계약이 ⌜`defect_record.work_order_id` 가 NOT NULL 이라 애초에 **생산 불량만** 들어온다⌝ 라 적었는데 **물리는 nullable** 이다(`prisma/schema.prisma:3154` · `lot_id` 도 nullable). 서버는 **축을 세우지 않았다** — 자재 불량을 가르지 않고 받는다(계약이 시키지 않은 필터를 지어내지 않는다). `lotId` 필터는 `defect_record.lot_id` 1홉이라 **`lot_id` 가 NULL 인 불량은 그 필터에 안 걸린다**(정상).

## 지금 서버는

- **아직 없다.** 계획이 정한 동작: `repairResultCode` 는 **ajv 에 맡기고** 서버가 코드 값을 대조하지 않는다 · 열린 건 판정은 **잠금 없는 읽기 검사** + 409 `OPEN_SESSION_EXISTS` · 멱등은 공용 봉투(`runIdempotent(…, FAMILY_CONFLICT_CODE)`)만 쓴다.
- 새 코드 그룹·시드 **0** · 마이그레이션 **0** · 새 `ERROR_CODE` **0** · `schema.prisma` **0줄**.
- e2e 가 반대 갈래를 반드시 지켜본다 — 「**반출된 불량에는 다시 투입이 201**」(이 단언이 없으면 `returned_at: null` 조건이 죽어도 아무도 못 본다).

⇒ **알리는 것**: 수리 결과 코드 그룹이 기준정보에 **없고**, 같은 불량의 **동시 투입을 막는 물리 제약이 없으며**, 두 표에 **`idempotency_key` 칸이 없어** 중복 방지의 둘째 그물이 인계 쪽은 **0**이다. 셋 다 서버가 축을 지어내지 않은 결과이고, 되돌리는 비용은 각각 작다.
