1. 전체 구조

사내 서버는 내부망에 있습니다. 그래서 GitHub 이 서버로 들어오는 경로를 만들지 않고, 서버가 Harbor 에서 당겨오는(pull) 방향으로만 구성합니다. self-hosted runner 도 GitHub 으로 바깥을 향해 폴링합니다.

개발자 ──push──▶ GitHub Actions (ubuntu-latest) │ pnpm install → prisma generate → nest build → docker build ▼ hub.crefle.com/mes/backend (Harbor) │ ┌─────────────┴──────────────┐ ▼ ▼ 개발 서버(한국) 하노이 운영 서버 self-hosted runner 가 합의된 창에 사람이 머지 직후 자동 배포 deploy.sh 실행 IMAGE_TAG=main IMAGE_TAG=stable 또는 vX.Y.Z

이미지 태그 규칙

이벤트붙는 태그성격
main push/merge:main, :sha-a1b2c3d:main 은 가변, :sha- 는 불변
git tag v1.2.3:v1.2.3, :stable, :sha-a1b2c3d:stable 은 가변

불변 태그(sha-, vX.Y.Z)는 “무엇이었는지”를 기록하고, 가변 태그(main, stable)는 “무엇을 배포할지”를 가리킵니다.

워크플로 세 개

파일트리거실행 위치하는 일
ci.ymlpull_request → mainGitHub 호스팅lint · typecheck · unit / docker build / e2e
build-push.ymlmain push, v*.*.* 태그GitHub 호스팅이미지 빌드 → Harbor push
deploy-dev.ymlworkflow_run(위 성공), 수동사내 서버자산 동기화 → deploy.sh
깨뜨리면 안 되는 성질

deploy-dev.yml 에 pull_request 트리거를 추가하지 마세요. PR 검증(ci.yml)은 GitHub 호스팅 러너에서 돌기 때문에 외부 기여자의 코드가 사내 서버에서 실행될 경로가 없습니다. 트리거를 늘리면 이 성질이 깨집니다.

5. Phase 3 · 파이프라인 검증

필요 권한: Repo Write

서버를 건드리기 전에 로컬에서 Docker 빌드가 통과하는지 먼저 확인합니다. Actions 를 기다리는 것보다 훨씬 빠릅니다.

docker build --target runtime -t omf-mes-server:test .
함정 · Prisma Client 가 생성되지 않는다

pnpm install 만으로는 Prisma Client 가 생성되지 않습니다. @prisma/client 의 postinstall 이 자기 패키지 안에서 prisma CLI 를 찾는데, pnpm 의 격리 링킹(node-linker=isolated) 때문에 보이지 않아 경고만 남기고 건너뜁니다.

warning In order to use "@prisma/client", please install Prisma CLI.

결과물은 스텁입니다 — index.d.ts 가 4KB(정상은 수 MB), 쿼리 엔진 바이너리 없음. 그래서 Dockerfile 의 deps 와 prod-deps 양쪽 모두에 RUN pnpm exec prisma generate 가 필요합니다. runtime 스테이지가 prod-deps 의 node_modules 를 복사해 가므로 deps 만으로는 런타임에서 죽습니다. 이 두 줄을 지우면 조용히 깨집니다.

그다음 PR 을 만들어 세 job 이 초록인지 확인하고 main 에 머지합니다.

job id보고되는 체크 이름
verifyLint · Typecheck · Unit test
dockerDocker build
e2eE2E (실제 DB)
필수 상태 검사를 지정할 때는 job id 가 아니라 체크 이름을 씁니다. verify 로 걸면 영영 충족되지 않아 PR 이 머지 불가 상태가 됩니다.

6. Phase 4 · 서버 배포 디렉터리

필요 권한: sudo 1회 · docker 그룹

6-1. docker 그룹

id -nG | tr ' ' '\n' | grep -qx docker && echo OK || sudo usermod -aG docker hulk
# 반영에는 재로그인이 필요합니다

6-2. 디렉터리 생성

디렉터리만 root 로 만들고 소유자를 배포 계정으로 넘깁니다. 이후 배포·롤백·로그는 전부 sudo 없이 돕니다.

sudo mkdir -p /opt/omf-mes/logs
sudo chown -R hulk:hulk /opt/omf-mes
cd /opt/omf-mes

홈 디렉터리가 아니라 /opt 를 쓰는 이유는 .env.prod(DB 비밀번호, JWT 서명 키)와 DEPLOYED 기록이 개인 계정 수명에 묶이지 않게 하기 위해서입니다. 계정이 정리되면 홈과 함께 사라집니다.

deploy.sh·rollback.sh 는 자기가 놓인 위치를 배포 디렉터리로 인식하므로 경로를 바꿔도 스크립트는 그대로입니다. 워크플로의 DEPLOY_DIR 과 이 경로만 맞으면 됩니다.

6-4. .env.prod 작성

cp .env.prod.example .env.prod
vi .env.prod
chmod 600 .env.prod
함정 · 비밀번호에 URL 특수문자를 넣지 말 것

POSTGRES_PASSWORD 는 compose 에서 URL 안에 들어갑니다.

DATABASE_URL: postgresql://${POSTGRES_USER}:${POSTGRES_PASSWORD}@postgres:5432/${POSTGRES_DB}?schema=public

/ @ : ? # % 가 들어가면 URL 이 깨져 Prisma 가 엉뚱한 호스트를 찾습니다. openssl rand -base64 는 / 를 만들어내니 쓰지 마세요.

openssl rand -hex 24        # POSTGRES_PASSWORD — 안전 (16진수만)
openssl rand -base64 48     # JWT_SECRET — URL 에 안 들어가므로 무관
키개발 서버하노이 운영
IMAGE_TAGmainstable 또는 vX.Y.Z
LOG_TZAsia/SeoulAsia/Ho_Chi_Minh
API_PORT31003100
ADMIN_INITIAL_PASSWORD지정하면 시드 출력을 놓쳐도 안전 (빈 값이면 무작위 1회 출력)
.env.prod 는 서버에만 존재합니다. 커밋하지 않고, 배포 워크플로도 이 파일을 건드리지 않습니다. 기존 서버를 갱신할 때도 덮어쓰이지 않으므로, .env.prod.example 에 새 키가 생기면 손으로 추가해야 합니다.

6-5. Harbor 로그인

함정 · 로그인 위치

deploy.sh 는 자격증명을 ~/.docker 가 아니라 배포 디렉터리 안($APP_DIR/.docker)에서 찾습니다. 배포 디렉터리마다 다른 로봇 계정을 쓸 수 있게 한 설계입니다.

docker --config /opt/omf-mes/.docker login hub.crefle.com -u 'robot$mes+server-pull'
#   Password: <Phase 1-3 의 토큰>
chmod 700 /opt/omf-mes/.docker

사용자명은 작은따옴표로 감싸세요. 큰따옴표나 따옴표 없이 쓰면 셸이 $mes 를 빈 변수로 해석해 robot+server-pull 로 로그인을 시도합니다.

config.json 은 암호화가 아니라 base64 입니다. 그래서 700 으로 잠급니다.

왜 --config 가 아니라 환경변수인가

deploy.sh 는 DOCKER_CONFIG 환경변수로 겁니다. docker --config 플래그는 compose 플러그인에 인자로만 전달되고 DOCKER_CONFIG 를 설정하지 않기 때문입니다. 실측:

$ docker --config <dir> envprobe
ARGS              : --config <dir> envprobe
DOCKER_CONFIG env : <unset>

플래그 방식이면 같은 스크립트의 docker inspect·tag·prune 이 각자 ~/.docker 를 봅니다.

부작용 주의: DOCKER_CONFIG 는 CLI 플러그인 탐색 경로도 바꿉니다. compose 가 사용자 플러그인(~/.docker/cli-plugins/)으로 깔려 있으면 docker compose 자체가 사라집니다. 시스템 경로(/usr/libexec/docker/cli-plugins/)에 있으면 무관합니다. 확인: docker info --format '{{range .ClientInfo.Plugins}}{{.Name}} {{.Path}}{{"\n"}}{{end}}'

6-6. 첫 배포 — 손으로 한 번

러너를 붙이기 전에 배포 자체가 되는지 확인하는 것이 순서입니다.

cd /opt/omf-mes && ./deploy.sh

deploy.sh 의 동작 순서:

  1. 현재 api 이미지 ID 기록 (롤백용)
  2. Harbor 에서 IMAGE_TAG 이미지 pull
  3. migrate(1회성) → api 기동
  4. api 가 healthy 가 될 때까지 대기 (최대 180초)
  5. 실패하면 직전 이미지로 자동 롤백
확인 시작 로그에 자격증명: /opt/omf-mes/.docker, 마지막 줄에 ===== 배포 완료 =====. DEPLOYED 파일이 생깁니다.

6-7. 최초 시드 1회

deploy.sh 는 마이그레이션만 돌리고 시드는 돌리지 않습니다 — 자동 실행되면 안 되는 작업이라 분리했습니다.

cd /opt/omf-mes && docker compose -f docker-compose.prod.yml --env-file .env.prod run --rm -e NODE_ENV=production api node dist/seed.js

한 줄로 실행하세요. 여러 줄로 나눠 붙여넣다 \ 가 깨지면 unknown docker command: "compose run" 처럼 빈 인자가 낀 오류가 납니다.

ADMIN_INITIAL_PASSWORD 를 지정하지 않았다면 관리자 초기 비밀번호가 이때 한 번만 출력됩니다.

확인 
curl -s localhost:3100/api/health
# {"status":"ok","db":"up","uptime":...}

# 로그인이 되면 DB·Prisma·JWT·해시·권한 매핑이 한 번에 확인됩니다
curl -sS -X POST http://192.168.1.111:3100/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"loginId":"admin","password":"<시드 출력 비밀번호>"}'
Swagger UI: http://192.168.1.111:3100/api/docs

/api/health 는 SELECT 1 만 합니다 — 통과해도 업무 로직 정상을 보장하지 않습니다. 비밀번호 변경은 최소 10자 제약이 있습니다.

7. Phase 5 · self-hosted runner

필요 권한: Repo Admin(등록 토큰) · 사용자 systemd · Linger=yes

가장 먼저 확인할 것

서버에 다른 러너가 이미 돌고 있는지 보세요. 한 서버에 여러 레포의 러너를 붙일 수 있는데, 기존 디렉터리에서 config.sh 를 돌리면 그 레포의 등록이 날아갑니다.

ls -d ~/actions-runner* 2>/dev/null
cat ~/actions-runner/.runner 2>/dev/null | grep gitHubUrl   # 어느 레포 것인지
systemctl --user list-units 'gh-runner-*'
pgrep -af Runner.Listener

예: 이 서버의 ~/actions-runner 는 CREFLEINC/reports 용이고 gh-runner-reports.service 로 상주 중입니다. 그래서 우리 것은 ~/actions-runner-omf 를 씁니다.

7-1. 내려받기 (별도 디렉터리)

mkdir -p ~/actions-runner-omf && cd ~/actions-runner-omf

# 버전·체크섬은 https://github.com/actions/runner/releases 최신 릴리스에서 확인
curl -O -L https://github.com/actions/runner/releases/download/v2.336.0/actions-runner-linux-x64-2.336.0.tar.gz
echo "04cf0be1aff4c3ec3554466c39124ca250e3effd8873bb7e8d68535aa9505d5d  actions-runner-linux-x64-2.336.0.tar.gz" | sha256sum -c
tar xzf ./actions-runner-linux-x64-2.336.0.tar.gz && rm -f actions-runner-linux-x64-2.336.0.tar.gz

7-2. 등록 토큰 Repo Admin 필요

UI: Settings → Actions → Runners → New self-hosted runner → Linux / x64 화면의 --token 값

gh api -X POST repos/CREFLEINC/omf-mes-server/actions/runners/registration-token -q .token

토큰은 1시간 만료입니다. 내려받기·전개를 먼저 끝내고 토큰은 마지막에 받으세요.

UI 화면의 다운로드·전개 명령을 그대로 따라 하면 현재 디렉터리에 풀립니다. 다른 러너와 섞이지 않도록 7-1 의 디렉터리에서만 작업하세요.

7-3. 등록

cd ~/actions-runner-omf
./config.sh \
  --url https://github.com/CREFLEINC/omf-mes-server \
  --token <등록 토큰> \
  --name omf-dev-01 \
  --labels omf-dev \
  --work _work \

--labels omf-dev 가 핵심입니다. 워크플로의 runs-on: [self-hosted, omf-dev] 와 짝이 맞아야 합니다. 하노이에 추가할 때는 omf-hanoi 로 구분합니다.

중간에 실패해 다시 할 때는 새 토큰을 받고 --replace 를 붙입니다. 이 단계를 마쳐야 svc.sh 가 생깁니다 — 압축 푼 직후에는 없습니다.

7-4. 상주

상주 방법은 두 가지입니다. 한 서버에서 둘을 동시에 켜지 마세요 — 같은 등록을 두 프로세스가 잡을 수 없어 충돌합니다.

방법root언제 쓰나

(Linger 설정에만 필요)		이 서버의 방식. 기존 러너와 통일, sudo 없이 start/stop/status

함정 · 러너가 root 로 뜬다

svc.sh 는 run_as_user=${arg_2:-$SUDO_USER} 로 동작합니다. sudo 로 부르면 호출자 계정이 들어가지만, root 셸에 들어가 있는 상태에서 인자 없이 실행하면 $SUDO_USER 가 비어 러너가 root 로 뜹니다. help 텍스트가 Install runner service as Root or specified user 라 root 가 기본인 것처럼 읽히는 것도 함정입니다.

또한 공식 유닛 템플릿에는 Restart= 가 없습니다 — 러너가 죽어도 되살아나지 않습니다. drop-in 으로 Restart=always 를 보강하세요.

systemctl show -p User    --value 'actions.runner.*.service'   # hulk 여야 함
systemctl show -p Restart --value 'actions.runner.*.service'   # always
확인

# omf-dev-01 online self-hosted,Linux,X64,omf-dev
서버에서 로그아웃한 뒤 재접속해도 online 이어야 합니다. offline 이면 상주 실패입니다.

8. Phase 6 · 동작 확인과 리허설

8-1. 수동 실행으로 먼저

Actions → Deploy to dev server → Run workflow → (image_tag 비움) → 실행

4개 스텝(사전 점검 · 자산 동기화 · 배포 · 요약)이 모두 초록이어야 합니다. Summary 에 DEPLOYED 내용이 표시됩니다.

8-2. 자동 연쇄 확인

main 에 커밋 머지  →  Build & Push to Harbor 성공  →  Deploy to dev server 자동 시작

workflow_run 트리거는 기본 브랜치에 있는 워크플로 파일만 동작합니다. 브랜치에 두고 테스트해도 자동 트리거가 걸리지 않습니다 — 머지 후에 확인하세요.

문서만 바뀌는 PR 이 첫 시험용으로 적당합니다. 실패해도 잃을 것이 없습니다.

8-3. 릴리스·롤백 리허설

git tag v0.1.0 && git push origin v0.1.0     # Harbor 에 v0.1.0, stable 확인

# 서버에서
./rollback.sh v0.1.0 && curl -s localhost:3100/api/health
./rollback.sh main                            # ← 반드시 되돌리기
rollback.sh 는 이름과 달리 “IMAGE_TAG 를 바꾸고 배포”입니다. 특정 버전으로 올릴 때도 씁니다. .env.prod 를 영구히 바꾸므로 고정한 채 잊으면 그 뒤로 계속 같은 버전만 배포됩니다. 
IMAGE_TAG=v1.2.0 ./deploy.sh    # 일회성 — .env.prod 는 그대로
./rollback.sh v1.2.0            # 영구 변경

9. 배포된 버전 확인법

“태그가 같다”는 “코드가 같다”를 뜻하지 않습니다. :main 과 :stable 은 가변 태그라 언제든 다른 것을 가리킵니다.

이미지에 박힌 git 커밋으로 대조하는 것이 유일하게 확실한 방법입니다. build-push.yml 의 metadata-action 이 OCI 라벨을 붙여줍니다.

# 서버
grep git_revision /opt/omf-mes/DEPLOYED
# git_revision=145e8cccad0d97137a22a1dfbc52587459c5868c

# 로컬 — 같아야 한다
git rev-parse origin/main

# 릴리스 태그와 대조할 때
git rev-list -n1 v1.2.0

DEPLOYED 를 직접 읽지 않고 컨테이너에서 뽑을 수도 있습니다.

cid=$(docker compose -f docker-compose.prod.yml --env-file .env.prod ps -q api)
docker inspect --format '{{index .Config.Labels "org.opencontainers.image.revision"}}' "$cid"
함정 · digest 두 종류

같은 이미지인데도 값이 다릅니다. 서로 대조하면 안 됩니다.

값정체어디에 있나
api_image_idconfig blob digestDEPLOYED, docker inspect
image_digestmanifest digestHarbor UI, 빌드 로그, RepoDigests
Harbor 와 맞춰볼 값은 image_digest 입니다.

10. 보안 — 반드시 읽을 것

self-hosted runner 를 붙이면 생기는 등식
.github/workflows/ 수정 권한 → main 의 워크플로가 러너에서 실행 → 러너 계정으로 임의 셸 명령 → docker 그룹 = root (docker run -v /:/host) → 그 서버의 root

러너를 어느 계정으로 돌리든 마찬가지입니다. 서버에 다른 팀 서비스가 함께 돌고 있다면 그 전부가 사정권에 들어갑니다.

브랜치 보호가 그 관문입니다 — 러너보다 먼저 거세요

러너를 붙이기 전에는 사람이 손으로 배포하는 것이 관문이었습니다. 자동화가 그 사람을 없앴고, 브랜치 보호가 그 자리를 메웁니다.

추가로, prisma migrate deploy 는 forward-only 입니다. 리뷰 없이 main 에 들어간 마이그레이션이 몇 분 뒤 자동 적용되고 되돌릴 명령이 없습니다. deploy.sh 의 자동 롤백은 이미지만 되돌립니다.

설정 위치내용
Settings → Rules → Rulesets 신규 패턴으로 여러 브랜치 지정, 조직 단위 적용, Evaluate 로 시험 가동, bypass 목록
Settings → Branches 구 브랜치별 규칙 하나씩. Ruleset 으로 대체되는 중

걸어야 할 항목: Require a pull request before merging + Require status checks → Lint · Typecheck · Unit test (job id verify 가 아님).

이 저장소의 현재 상태 — 미해결

조직이 GitHub Free 라 private 레포에는 브랜치 보호도 Ruleset 도 걸리지 않습니다.

$ gh api repos/CREFLEINC/omf-mes-server/rulesets
403 "Upgrade to GitHub Pro or make this repository public to enable this feature."

즉 러너는 붙었는데 관문이 비어 있습니다. 쓰기 권한자가 8명(admin 3명)이고, 개발 서버에는 다른 팀 서비스가 30개 넘게 함께 돕니다. 미룰 문제가 아니라 결정할 문제입니다.

  1. 조직을 GitHub Team 으로 업그레이드 — Ruleset·환경 보호 규칙이 열립니다
  2. 러너의 폭발 반경 축소 — 플랜과 무관하고 사실 이것이 근본 해법입니다. 러너 전용 호스트로 분리, 또는 rootless Docker / docker socket proxy 로 데몬 접근을 우리 프로젝트에 한정
  3. 쓰기 권한 인원 축소 — 지금 당장 무료로 할 수 있는 조치

환경(environment: dev) required reviewer 도 private 레포에서는 유료이고, main 에 푸시할 수 있는 사람은 워크플로에서 그 줄을 지우면 그만이라 악의적 사용자에게는 통제가 못 됩니다 — 사고 방지용일 뿐입니다.

그 외

  • 레포가 private 인지 확인하세요. public 레포에 self-hosted runner 를 붙이면 외부인이 fork PR 로 그 서버에서 임의 코드를 실행할 수 있습니다.
  • 러너를 root 로 돌리지 마세요. 얻는 것이 없고 감사 로그에서 실행 주체만 흐려집니다.
  • deploy.sh·rollback.sh 에 sudo 를 넣지 마세요. 두 서버가 같은 스크립트를 쓰고, 다른 서버의 권한 상황은 다를 수 있습니다.
  • 로봇 계정 토큰 만료를 달력에 적어두세요. 만료되면 어느 날 갑자기 배포가 조용히 실패합니다.

11. 함정 모음

Prisma · 스키마

  • Dockerfile 의 prisma generate 두 곳을 지우지 마세요. deps(빌드 타입검사용)와 prod-deps(런타임용) 양쪽 모두 필요합니다. Phase 3 참조.
  • 마이그레이션은 하위 호환으로. 컬럼·테이블 삭제는 두 릴리스로 나눕니다 — 먼저 코드에서 사용을 제거해 배포하고, 다음 릴리스에서 컬럼을 지웁니다. 한 릴리스에 둘을 합치면 그 배포는 되돌릴 수 없습니다.
  • 이 프로젝트는 Prisma multiSchema 를 씁니다. 테이블이 app·mdm·production·logistics 등 10개 스키마에 나뉘어 있고 public 에는 _prisma_migrations 만 있습니다. public 만 보고 “테이블이 없다”고 오판하기 쉽습니다.

타임존

컨테이너 타임존은 UTC 입니다. Asia/Seoul 등으로 바꾸지 마세요. 공장 로컬 시각이 필요한 계산은 plant.timezone_code(IANA 이름)를 씁니다. 서버 TZ 에 의존하면 공장이 둘 이상이 되는 순간 어느 쪽에도 맞지 않습니다.

postgres 는 command: postgres -c timezone=UTC -c log_timezone=UTC 로 명시합니다 — initdb 가 감지한 타임존을 postgresql.conf 에 구워버려서 환경변수만으로는 기존 클러스터를 못 바꿉니다. -c 는 초기화 순서와 무관하게 항상 이깁니다.

business_date 는 타임존 캐스팅으로 구할 수 없습니다

shift.crosses_midnight 때문에 “실적이 속한 교대의 시작일”은 로컬 날짜 캐스팅으로 얻을 수 없습니다. 하노이 야간 교대(22:00~06:00)를 예로 들면:

02-02 05:30 실적 → business_date 는 02-01 이어야 함 · 로컬 캐스팅은 02-02 (틀림) 02-02 06:30 실적 → business_date 는 02-02 여야 함 · UTC 캐스팅은 02-01 (틀림)

어떤 TZ 로도 맞지 않습니다. 도출 순서는 이렇습니다.

실적 timestamptz → plant.timezone_code 로 로컬 시각 변환 → 그 로컬 시각이 속한 shift 판정 (start_time / end_time / crosses_midnight) → 그 shift 가 시작된 로컬 날짜 = business_date

@db.Timestamptz 컬럼은 절대 시각이라 안전합니다. 위험한 것은 @db.Date 입니다.

compose · 배포

  • docker-compose.prod.yml 의 이미지 YAML 앵커를 분리하지 마세요. migrate 와 api 가 반드시 같은 이미지를 써야 합니다. 따로 적으면 한쪽 태그만 고치는 사고가 나고, 구버전 코드가 신버전 스키마를 보게 됩니다. 
    x-api-image: &api-image ${REGISTRY:-hub.crefle.com}/mes/backend:${IMAGE_TAG:-main}
  • docker compose 는 셸 환경변수를 --env-file 보다 우선합니다. deploy.sh 도 같은 규칙을 따르게 맞춰뒀습니다. 두 쪽이 어긋나면 롤백 시 엉뚱한 태그에 이미지를 붙입니다.
  • docker-compose.prod.yml 에 name: omf-mes 가 박혀 있어 배포 디렉터리를 옮겨도 컨테이너·볼륨이 그대로 붙습니다.
  • docker image prune 은 데몬 전역에서 돕니다. 다른 서비스와 도커를 공유하는 서버에서는 라벨로 범위를 좁혀야 남의 dangling 이미지를 지우지 않습니다. 
    docker image prune -f --filter "until=168h" \
  --filter "label=org.opencontainers.image.source=https://github.com/CREFLEINC/omf-mes-server"
  • deploy.sh 는 flock 을 씁니다 — macOS 에는 없어서 로컬에서 돌리면 잠금 단계에서 멈춥니다. 리눅스 서버 전용입니다.

GitHub Actions

  • 러너가 죽으면 배포가 조용히 멈춥니다. Actions 는 러너가 없으면 실패가 아니라 큐 대기 상태가 되어 알림이 오지 않습니다. Settings → Actions → Runners 를 가끔 확인하거나 큐 대기 시간에 알림을 걸어두세요. 
    gh run list --workflow=deploy-dev.yml --status queued
  • 배포 자산은 항상 main 기준으로 동기화됩니다. 워크플로가 ref: main 을 체크아웃해 스크립트를 덮어씁니다. 그래서 브랜치의 파일을 서버에 손으로 복사해두면 러너가 처음 도는 순간 main 버전으로 되돌립니다. 머지를 먼저 하세요.
  • image_tag: v1.0.0 으로 수동 배포하면 이미지는 v1.0.0, compose 는 main 기준이 됩니다.
